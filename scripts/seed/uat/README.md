## 一、这套数据讲了什么故事

**示范企业：鼎晖智造集团股份有限公司**（复用基线租户 `tenant_id=1001`，code 保留 `DEMO`）
定位：一家"智能制造 + 全渠道零售"的集团企业，把 BONE 当作数字化底座，并在其上托管一个垂直行业演示应用（保险 TPA 门诊理赔）。

叙事主线（即客户演示动线）：

1. **组织与人（IAM）** —— 集团 → 11 个事业部/中心 → 48 个科室 → **200 名**员工，覆盖 CEO、主数据管家、审批人、财务、业务员、审计、低代码配置员、运维、只读访客。
2. **建模与治理（Metadata + MDM）** —— 建模模块定义 8 个业务对象；主数据沉淀**已治理**的客户/供应商/物料/商品/项目/员工/资产/渠道买家共 **2,400 条** 记录，带审批流、数据管家、参考数据集与质量工单。
3. **业务流程（Workflow）** —— 主数据变更、费用报销、采购申请、请假 4 条流程；150 条实例覆盖进行中/已通过/已驳回/已撤回，待办指派给真实审批人。
4. **真实交易（Commerce）** —— 淘宝/京东/抖音/拼多多/微信小程序/官网商城 6 渠道 → 商品上架 → **2,000 张订单**（三口径守恒）→ 发货与 4 段物流轨迹 → 支付对账。
5. **平台能力** —— ERP/企微/钉钉/快递100 连接器与 10 条集成流（800 条执行日志）；元数据反向出码；扩展点；高管看板与站内待办。
6. **垂直演示应用（Claim/Settle）** —— 150 例门诊理赔全流程（报案→核赔→理算→结算→额度→申诉→AI 辅助裁决），被保险人与证件**全量假名化**。

## 二、已落地的业界最佳实践

| # | 实践 | 落地方式 |
|---|---|---|
| A | DDL 与数据分离 | 建表只靠 `bone-init.sql` + `scripts/migration/*`；seed 只含业务数据 |
| B | 幂等确定性种子 | 固定随机种子 `20261028` + 固定 ID 段；`REPLACE INTO` + 灌前清表 ⇒ 重跑结果一致 |
| C | 黄金数据集 + 规模化合成 | `02_golden` 锚点手工策展一条贯穿全模块的动线，其余由 `gen.py` 放大 |
| D | 拓扑序加载 + 校验门禁 | `load.sh` 按依赖拓扑加载；`95_validate.py` 跑 8 类断言，失败即 exit 1 |
| E | 职责分离 SoD | 审批人 ≠ 发起人、提交人 ≠ 批准人、大额结算双人复核换人 |
| F | 数据血缘与老化 | `created_by/updated_by` 全填充；时间戳由基准日倒推，呈现真实"数据年龄" |
| G | 财务不变量 | 订单三口径、结算=核定、额度守恒、支付=应收，全部断言 |
| H | 真实多渠道建模 | 6 渠道 + CNY 本位币 + 3 仓库存 + 6 家物流商 |
| I | PII 最小化 | 理赔域 `insured_id_hash` 假名化，手机号/银行卡脱敏，无明文 PII |
| J | 环境护栏 | `load.sh` 校验 `BONE_ENV`，`prod` 直接拒绝；清理只动 `tenant_id=1001` |
| K | 可回放 / 版本化 | 每次执行自动全库备份；`_dump.py` 可导出快照随时重建 |

## 三、目录与脚本

```
scripts/seed/uat/
├── load.sh            # ★ 一键编排：备份 → 清理 → 灌数 → 校验（带环境护栏）
├── _conf.py           # ★ 数据库连接真源（口令只从 BONE_UAT_DB_PASSWORD 取，禁止字面量）
├── 90_clean.py        # 清理器（默认 dry-run，--apply 才执行；强制校验备份存在）
├── gen.py             # ★ 确定性种子生成器（受控中文词典 → build/*.sql，--apply 灌库）
├── 95_validate.py     # ★ 8 类校验门禁（RI / 金额 / SoD / 枚举 / 体量 / 时间轴 / 可读 / 黄金动线）
├── _dump.py           # 纯 Python 逻辑备份（本机无 mysqldump 客户端时使用）
├── _classify.py       # 只读盘点：把表分成 保留 / E2E残留 / 备份残留
├── _schema.py         # 导出目标表真实列定义，供 seed 对齐
├── build/             # gen.py 产出的 SQL（可评审；被 .gitignore 的 `build/` 忽略，属生成物不入库）
└── README.md          # 本文件
```

## 四、使用方式

> **先声明数据库口令**：口令一律走环境变量，仓库里不存字面量（`gitleaks` 门禁会阻断提交）。
> 缺 `BONE_UAT_DB_PASSWORD` 时脚本 **fail-fast** 并提示，不会静默回退到某个默认口令。
> 其余连接参数可用 `BONE_UAT_DB_HOST` / `BONE_UAT_DB_PORT` / `BONE_UAT_DB_USER` / `BONE_UAT_DB_NAME` 覆盖。

```bash
cd scripts/seed/uat
# 交互式录入口令（不落盘、不进 shell 历史）
read -rs BONE_UAT_DB_PASSWORD && export BONE_UAT_DB_PASSWORD

# 1) 一键重建 UAT 演示数据（推荐）
BONE_ENV=uat ./load.sh

# 2) 放大体量（订单 6000 / 主数据 ~5000）
BONE_ENV=uat ./load.sh --scale large

# 3) 只重建演示数据，不动清理
BONE_ENV=uat ./load.sh --skip-clean

# 4) 只跑校验门禁
BONE_ENV=uat ./load.sh --validate-only

# 5) 先看清理会做什么（dry-run，不落库）
python3 90_clean.py
```

## 九、注意事项

- **禁止对生产库执行**：`load.sh` 会在 `BONE_ENV=prod/production` 时直接退出；`90_clean.py` 在没有有效备份时拒绝执行。
- **重跑安全**：`gen.py` 使用 `REPLACE INTO` + 灌前按租户清表，可反复重跑，结果完全一致。
- **无 tenant_id 的子表**（`t_order_item`、`iam_role_permission`）清理时先快照父表 ID 再删，避免残留孤儿行。
- **口令策略**：演示账号统一 `123456`，对外演示前建议按角色改密并开启首次登录强制改密。
