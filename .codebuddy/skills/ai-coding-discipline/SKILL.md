# AI 编码纪律（四条）

## 概述

四条纪律：**先想后写 · 简单优先 · 精准修改 · 目标驱动**。

> **规范真源：`AGENTS.md` §11.12（准则）与 §11.13（提交前自检清单）。**
> 本技能**不重复规范条文**，只提供两件增量价值：① 何时触发；② 如何抵抗违反（合理化借口表 + 红线）。
> 规范变更一律改 `AGENTS.md`，本技能只同步触发与防违反部分。

## 何时使用

- 需求含糊、或存在 ≥2 种合理方案，却准备直接动手 → **先想后写**
- 准备改动任务范围外的文件（重构 / 重命名 / 格式化 / "顺手优化"）→ **精准修改**
- 准备加"将来可能用到"的抽象、配置项、扩展点 → **简单优先**
- 准备说"已完成" → **目标驱动**（拿证据）

**不适用**：L0 级纯格式化/重命名；已由 CI、ArchUnit、Spotless 强制的机械约束（交给门禁，不靠纪律）。

## 四条纪律

| 纪律 | 做法 | 违反信号（自查） |
|---|---|---|
| **先想后写** | 有歧义就问；呈现方案与取舍，再动手 | "我猜你是想…"、"先写着再说" |
| **简单优先** | 用能解决**今天**问题的最少代码 | "顺便支持一下…"、"以后可能要…" |
| **精准修改** | 只改必须改的；范围外问题**只登记、不擅改** | diff 里出现与任务无关的文件 |
| **目标驱动** | 先定可验证标准，收尾**逐条自证** | 只说"已完成"，无命令/测试输出 |

> "Don't tell it what to do, give it success criteria and watch it go." —— Karpathy

验收标准必须**可观测**：哪条命令通过、哪个测试变绿、什么输出算对。不可写成"功能正常""应该没问题"。

## 合理化借口表

| 借口 | 现实 |
|---|---|
| "顺手改一下，反正更好" | 无关改动放大 review 面、掩盖真实回归。**只登记，另开任务。** |
| "不加抽象以后会重写" | 预测的未来需求多数不会发生。等**第二次真实需求**再抽象。 |
| "需求猜一下就行，问了显得啰嗦" | 猜错的成本远高于问一次的 30 秒。 |
| "我知道能过，跑测试太慢" | 未执行的验证不是验证。**跑。** |
| "改动很小，不用自检" | 越界改文件、漏跑 spotless、漏测都发生在小改动上——自检收益最高处。 |
| "这次情况特殊，范围外改动是必要的" | 判定标准只有一条：**不改它，本次任务能否完成？** 能完成 → 越界。 |

## 红线 —— 停下来

- 需求未确认，就写出多方案之外的第三种实现
- diff 包含任务范围外的"优化"
- 为**假想**需求加扩展点/配置/开关
- 宣布"已完成"，但拿不出一条命令或测试输出

**出现任一红线：停下，收窄到必须改的部分，补上可验证证据再继续。**

## 常见错误

- 把"精准修改"当成"不做必要重构" —— 必要重构属**任务内**，不算越界
- 把"简单优先"当成"不做设计" —— 是**不过度**，不是不思考
- 把验收标准写成"功能正常" —— 必须可观测、可执行、可复现
