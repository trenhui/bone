# synapClaim 理算引擎设计（架构决策 · 算法 · 端口契约）

> **定位**：理算（Settlement）子域的**唯一设计真源**。本文合并了原先两份文档——《智能理算引擎设计（独立限界上下文）》回答"要不要独立、边界在哪"，《理算引擎内部设计（算法·端口契约·业界基准）》回答"怎么算"——这两问本就是一篇设计的两章，分列会导致"改算法时忘了改边界"。
>
> **权威边界**：领域模型与口径以《工程落地版》§5（责任与理算模型）/ §7.4（理算）为权威；DDL 见 §9.5，OpenAPI 见 §10；规则 ID 以 `delivery/04-业务规则书` 为权威。本文只写设计与算法，**验证资产**见《理算引擎验证套件》，**缺陷取证史**见《理算引擎诊断记录》。
>
> **业界基准锚定**为本文强制项：每个核心设计点必须能对应到可核查的行业实践，避免"自创不可证伪"的设计。

## 1. 决策：独立限界上下文，但有严格形态约束

**结论：YES —— 把理算设计为 synapClaim 内一个独立限界上下文（独立 module + 六边形架构 + 端口边界），但不是以下三者：**

| 否认项 | 原因（证据） |
|---|---|
| ❌ **整体照搬 `bone-tpa-intelligent-adjustment`** | 该模块是 pk-tpa-saas **生产验证、在用**的 proven 引擎（三类责任策略 + min 聚合控额已被真实业务检验）。但 synapClaim 采用六边形 + 端口防腐 + 多租户 + 监管快照架构，与 tpa-saas 的"进程内直连、实时读配置"风格不同；整体搬运会把其直连直付/公账、实时读 `plan.version` 等与架构约束不符的实现一并带入。故**复用其策略模式与控额语义作为基线**，在新模块内按 synapClaim 约束重构（端口隔离、快照固化）。 |
| ❌ **拆成独立微服务/进程** | 理算必须与会案件（`ClaimCase`）、责任（`AdjLiability`）、结算（`SettlementOrder`）、额度（`LedgerPort`/C11）在**同一事务边界**内写结果、占额度。独立进程引入分布式事务与额外延迟。现有"domain 纯逻辑 + port 防腐"已天然支持进程内 module 隔离，无需跨进程。 |
| ❌ **把理算塞进 `bone-ai-rules`（C2）当规则推理** | 理算 95% 是**确定性金额算术**（免赔累加、比例乘算、min 取交、公账/个账分账）。金融"同输入同输出可复算"要求精确 `BigDecimal` 语义，DSL 表达算术既不可控又破坏快照可复算。C2 只适合其**前置的条件/因子求值**。 |

**正解形态**：`synap-claim-settlement` 模块（hex），以 `SettlementEngine` 门面编排"规则求值(C2) → 确定性算术(本域) → 冻结快照 → 占额(C11) → 审计(C4) → 事件(Outbox)"，作为决策图 `Adjust` 节点的**唯一理算事实源**（避免双源漂移）。

## 2. 业界基准锚定（设计点 ↔ 行业实践）

| 设计点 | 行业基准 | 为什么这样设计 |
|---|---|---|
| 规则层(C2) + 算术层(本域) 双层分离 | Guidewire **Rules Engine（适用性）+ Calculation Engine（金额）** 分离；SAP MDG 决策与计算解耦 | 规则热更/回归门禁不污染金额精度；金额走确定性引擎 |
| 策略工厂 + 插件化责任类型 | 平安产险/众安"责任插件化"；保险核心系统普遍 Strategy+Factory | 新增责任类型零侵入主线 |
| min 聚合多维度控额 | ISO 834 比例分摊 + 团险/再保"多维度限额取交集最小"；太保/泰康限额矩阵 | 任一维度触顶即截断，防超赔 |
| `FormulaSnapshot` 物化 | SOX / NAIC Model Audit Rule "同输入同输出可复算"；金融台账不可变快照 | 配置变更后旧案可自包含复算，支撑争议复议 |
| 三值额度（initial − claim − frozen） | 团险/企业补充医疗公账池通用记账；ACORD 额度语义 | 冻结与已用互斥统计，杜绝双计 |
| 准入 `checkAdjustable` + 归因 `checkAdjustRecord` | 理赔"事实认定—归因"双轨（拒赔五要素）；监管可解释性 | 零赔付必须可归因 |
| 端口隔离 + Outbox 原子事件 | 六边形架构（Cockburn）；"业务落库 + 事件投递"原子性 | 引擎不触外部系统，防腐且可测 |

```
┌─────────────── synap-claim-settlement（独立 module，六边形）───────────────┐
│ domain/                                                                   │
│  ├ SettlementEngine（门面：编排，纯逻辑）                                   │
│  ├ strategy/  FixedAmount / Allowance / Reimbursement（§11 复用基线）        │
│  ├ LimitControl（min 聚合，只读 context 内存，不触外部）                      │
│  ├ IndemnityCalculation（A6 聚合：AdjLiability / AdjustmentLine / Snapshot） │
│  └ model/  LiabilityConfig† / InvoiceAdjustmentContext / Quota（本域值对象）  │
│ application/  SettleClaimUseCase → 编排 port：                              │
│  ① RuleEnginePort(C2) 求适用性/因子/目录编码  ② SettlementEngine 确定性算术   │
│  ③ LedgerPort(C11) 占/冲额度  ④ TracePort(C4) 快照  ⑤ OutboxPort 事件        │
│ infrastructure.client/  ← 防腐：上游 DTO → 本域值对象（禁泄漏 tpa/saas 术语）  │
└───────────────────────────────────────────────────────────────────────────┘
   † LiabilityConfig 由 C2 下发，但**落盘即物化为 FormulaSnapshot**
```

### 3.1 平台边界（关键串联点）

| 层 | 归属 | 理由 |
|---|---|---|
| 条件 / 因子 / 目录求值 | `bone-ai-rules`(C2) 规则 DSL | 责任适用性、赔付比例笛卡尔因子、目录编码匹配属**规则**，适合配置化 + 热更 + 回归门禁 |
| 金额算术 | 本域（native） | 免赔累加、比例乘算、min 取交、公账/个账分账——精确 `BigDecimal(10,2)` HALF_UP，**不可入 DSL** |
| 额度 | `LedgerPort`(C11) | 占/冲/信任额度由平台台账统一；反诈命中即熔断回退 |
| 审计 | `TracePort`(C4) | 快照不可变、可回放，对接后督 100% AI 质检 |

> 对《工程落地版》"理算语义迁入 bone-ai-rules"的精炼：改为**"求值层迁入 C2，算术层留本域"**。既享受规则热更/回归门禁，又保住财务精度与可复算——Guidewire / SAP MDG / 平安产险均采"规则管适用、引擎管金额"双层。

## 4. 引擎编排（权威顺序，不可调换）

```
0    幂等键命中？      → 返回首次结论（不占额、不双计累计）
0'   风控 P0（fraudHold）？→ HOLD：不出金额、不占额、发事件、转人工
0.5  重算冲正：同 claimId 旧结论先 reverseSettlement 回退累计
1    C4  TracePort.record —— 冻结 FormulaSnapshot（快照审计）
2    C2  策略求值 —— 产出「可赔基数 base + 比例 ratio + 理算层面免赔」
3    不可获利：第三方已付（社保统筹/他险已赔）从基数按比例分摊扣除（守恒）
4    年度免赔：作用于**费用基数**，跨案累计剩余，按行分摊（守恒）
5    比例 → 理算层面免赔 → 取整 → 分位配平（§8）
6    多维度 min 控额：责任 / 费用子限额 / 计划 / 年度限额
7    C11 累计提交（乐观锁 + 按 claimId upsert）→ 占额 → Outbox 事件
```

> **为什么这样排**：3 与 4 都在"比例"之前，因为**免赔额与不可获利的标的是"费用"而非"赔款"**（错序即系统性少赔，见《理算引擎诊断记录》D1）。6 把年度限额并入 min 聚合，使"行级金额之和 == 实际应付"恒成立（归因完备），避免"总额被砍但明细不变"的对账裂缝。
>
> **纯函数铁律**：步骤 2–5 不碰 DB/AI/网络，可在无 Spring 环境单测；1/6/7 全部经端口。

### 4.1 直付预授权（置于步骤 0 之前）

```
0''  preAuthorize(ctx, snap, estimatedTotal)
     auth = min(预估费用 − 剩余年度免赔, 剩余年度限额, 剩余责任限额, 计划剩余) × 保守比例
     保守比例 = 各可赔费用类型比例的最小值；无可赔费用 → 0
     仅计算：不占额、不提交累计（预授权 ≠ 结算）
     授权 = 0 → 直付通道降级为「先垫付后报销」或挂起人工，不阻塞就医
```

> 一致性护栏：结算净额必须 ≤ 预授权额度。按 100% 授权会使院端直付额高于实际结算，差额须向患者追收——这是直付网络的高频纠纷源。

## 5. 聚合与值对象

```
IndemnityCalculation（A6 聚合根）
 ├ claimId / planVersion / liabilityVersion / catalogVersion（三者皆锁定）
 ├ lines: List<AdjustmentLine>              // 每责任一条
 ├ formulaSnapshot: FormulaSnapshot          // 物化契约见下
 ├ totalPublic / totalIndividual             // 不变式 total = public + individual
 ├ settleStatus: PAY / PARTIAL / REJECT / HOLD
 ├ denied: boolean / denyReasons: List<String>
 ├ ruleTrace: Map<feeType, List<ruleId | rejectType>>
 └ status: FROZEN → CONFIRMED → PAID / ROLLBACKED

AdjustmentLine（六成分，落 adj_calculation_line）
 ├ liabilityUuid / liabilityVersion
 ├ fee_calculate  // 计算基准额（剔除不赔后）
 ├ ratio_payout   // 按比例应付 = (基准 − 免赔) × ratio
 ├ fee_payout     // 实付（经控额 min 后）
 ├ fee_deduct     // 免赔扣减（拒赔行强制 0）
 ├ fee_occupy     // 占额
 ├ fee_remain     // 剩余额度
 ├ rejectType     // CATALOG_EXCLUSION / EXCLUSION_CLAUSE / null
 └ formulaHash    // 六成分 + 输入的哈希，逐行可复算
```

**`FormulaSnapshot` 物化契约（防漂移核心）**：冻结以下不可变副本，而非仅存 `rule_version` 引用——
`{ liabilityVersion, catalogVersion, deductConfig, payPercentMatrix(已求值), liabilityLimit, feeTypeLimits, accountType, quotaInitial(各维度), 三段费用输入值, formulaHash }`。
理由：源 `plan.version` 被改后，旧案凭快照**自包含复算**，金额不变。

**额度语义铁律**（两条极易写反）：

| 项 | 语义 | 公式 | 写反的后果 |
|---|---|---|---|
| 年度免赔额 | **相减**（被保险人先自担） | `实付 = max(0, 净额 − 剩余免赔)`，同时累加 `consumed` | 免赔后置 → 系统性少赔 25% |
| 年度限额 | **封顶**（取交，非相减） | `实付 = min(净额, 剩余年限额)`，占用 = 实际应付 | 当成相减 → 限额内首案即赔 0 |

## 6. 三类责任策略（精确伪码）

### 6.1 FixedAmount（定额给付）

```
base = liability.fixedAmount
payable = min(base, liabilityLimit)          // 受责任额度截断
line(fee_calculate=base, ratio_payout=base, fee_payout=payable, fee_deduct=0, ...)
```
定额责任**无免赔、无比例乘算**，直接受限额截断。

### 6.2 Allowance（津贴，按天/次）

```
base = days × dailyAllowance
payable = min(base, liabilityLimit, timesLimit.amount)   // 责任额度 ∩ 次限额
```

### 6.3 Reimbursement（报销，主体）

```
for feeType in liableFeeTypes(ordered):        // 合理金额 → 自付二 → 总自费 → 丙类 → 超限价
   origin = invoiceFeeMap[feeType];  if origin < 0: origin = 0
   deduct  = DeductCalculator.calc(ctx, origin)          // ① 免赔（发票层/理算层，按 deductTarget）
   current = origin − deduct
   ratio   = payPercentMatrix[feeType]                   // ② C2 已求值，不在引擎内求值
   payout  = (current × ratio/100).setScale(6, HALF_UP)  // ③ 计算位 6
   payout  = payout.setScale(2, HALF_UP)                 // ④ 结果位 2
   feeLimit = feeTypeLimits[feeType] − invoiceFeeHistoryPayoutMap[feeType]
   payout  = min(payout, liabilityLimit − liabilityPayAmount, max(feeLimit, 0))   // ⑤ 多维 min
   liabilityPayAmount += payout
   if feeLimit == payout: nextLiabilityFlag = true       // ⑥ 后付责任链穿透
```

> 与参考实现逐环节对应，但**修正**：因子值由 C2 预求值注入（不在引擎内求值），外部额度经端口注入（不内联 Feign），全程不触网络。比例硬护栏 `ratio% ≤ 100%`（含 AI 加成后），防超赔。

## 7. 多维度控额（min 聚合 + 三值额度）

```
limit(ctx):
  quotaDetail = {}
  for dim in [PERSONAL, LIABILITY, PLAN, COVERAGE, SHARING, VISIT_TYPE, TIMES,
              DIRECT_PUBLIC, DIRECT_PERSONAL]:
     if not applicable(ctx): continue
     if quotaInitial[dim] <= 0: continue        // 0 = 该维度未配置，不得当"限额为零"
     avail = max(quotaInitial[dim] − used[dim] − frozen[dim], 0)   // 三值模型
     FORCE ? quotaDetail[dim] = avail : alarmQuota[dim] = avail    // ALARM 仅告警不截断
  return max(min(quotaDetail.values()), 0)
```

- **`0 = 未配置`** 是全部要点里最容易写错的一条：主流产品配置（含 tpa-saas）以 `0` 表示"该维度不限制"，引擎若当成"限额为零"就会**全额拒付且静默**——曾因测试数据恰好都传了大额子限额而被掩盖，属典型假绿（见《理算引擎诊断记录》N10）。
- 维度可插拔：一期 4 维，二期扩共保/直付余额；新增维度只扩枚举与初始额来源，**不改主链路**。

## 8. 精确计算顺序与分位配平

```
原始费用 origin
 → 目录/合理必要筛选（拒赔行 base=0，但保留 origin 供告知书）
 → 发票层免赔：   base = clamp(origin − deductInvoice, 0)
 → 第三方已付：   base ← base − 分摊(thirdPartyPaid)
 → 年度免赔：     base ← base − 分摊(min(年免赔余额, Σbase))
 → 比例：         calc = base × ratio%
 → 理算层免赔：   calc = clamp(calc − deductAdjust, 0)
 → 取整：         feeCalculate = round(calc)
 → 控额：         feePayout = min(feeCalculate, 责任剩余, 费用子限额, 计划剩余, 年度限额剩余)
```

| 项 | 公式 | 说明 |
|---|---|---|
| 占用额 | `feeOccupy = clamp(feePayout / ratio, 0, origin)` | 逆推占用的原始费用（比例件） |
| 免赔合计 | `feeDeduct = origin − base + deductAdjust` | **拒赔行强制 0**（拒赔 ≠ 免赔，否则告知书误导） |
| 年度免赔余额 | `max(0, 年免赔额 − 已用)` | 按「保单 + 账期」累计 |
| 年度限额剩余 | `max(0, 年限额 − limitUsed − frozen)` | ACORD 三值额度 |
| 责任限额剩余 | `max(0, 责任限额 − liabilityUsed)` | 责任维度亦须跨案累计 |
| 直付授权 | `min(预估 − 剩余免赔, 年限额剩余, 责任剩余, 计划剩余) × 保守比例` | 保守比例取各可赔费用最小值 |

**分位配平（最大余数法）**：逐行 `round` 后合计必须等于"总额口径 `round`"，否则对账出现 1 分差。算法：计算残差 cents，按小数余数从大到小依次 ±0.01，保证 `Σround(行) == round(Σ行)`。金融对账零容忍（SOX/NAIC 可复算）。

## 9. 增强能力（均已落地参考实现）

### 9.1 跨案累计（保单级年度免赔 / 年限额 / 责任限额）

单案理算不足以覆盖保单级聚合约束。`AccumulationPort` 以 `tenantId@policyId@periodKey` 为键，跨案聚合「已用免赔 / 已用年限额 / 已用责任限额」，理算时消费剩余、结算后回写。

- 年度免赔作用于**费用基数**（先免赔后比例）；年度限额是**封顶**；
- **责任维度也必须累计**——只做年度免赔/年限额累计而漏责任限额，是最常见的维度覆盖不完整（"门诊 5000/年"这类责任限额会被逐案重复给足）；
- 业界基准：Guidewire Accumulation / ISO 年度免赔累计 / ACORD 保单级限额。

### 9.2 可解释性与规则溯源

每条 `AdjustmentLine` 记录命中规则 ID（`ruleTrace`：`R-DED-01` / `R-RAT-01` / `R-CAP-01` / `R-DIR-01`），并生成客户告知级 `explain()` 文本。每条金额可回溯到「哪条规则 + 哪个因子值」，满足监管告知与 SOX/NAIC 可审计。基准：Guidewire "every payment line item explainable"。

### 9.3 幂等重算与快照版本化

- **幂等键 = `claimId + formulaHash(snapshot) + inputHash(ctx)`**：命中即返回首次结论，不重复占额、不双计累计。
  - 仅凭 `claimId` 不够：补交发票、AI 建议状态变化、快照变更都属**新的理算请求**，必须重算。
  - 仅凭 `snapshotVersion` 不够：源配置变更必须体现为新指纹，否则幂等会掩盖快照冻结缺陷。
- **重算必须冲正**：同 `claimId` 的旧占用先 `reverse()` 再按新输入计算，并把 `commitUsage` 改为**按 claimId upsert**（替换而非累加）。否则补交发票（理赔最高频动作）会被旧占用挤压而少赔，且账上额度与实付不符。
- 累计提交具备 `DUPLICATE`（同 claimId 不累加）与 `CONFLICT`（乐观锁失配，fail-closed 转人工）两种结果。

### 9.4 直付预授权生命周期

`PreAuthPort`：`hold(ttl)` 冻结（计入三值模型的 `frozen`）→ `capture(实际额，剩余自动释放)` → `void(撤销)` → `isExpired(到期释放)`。
**预授权必须进 `frozen`**：否则多科室分次授权可突破年限额（累计授权 18000 vs 年限额 10000），医院已直付后的差额需向患者追收。
基准：亿保「智慧E保即时结算」就诊前核验 + 预算授权；HMO/PPO prior authorization 通用模式。

### 9.5 拒赔建模

| 类型 | 载体 | 处理 |
|---|---|---|
| 整案拒赔 | `ClaimContext.denyReasons`（等待期内 / 免责条款 / 指定医院外） | `settleStatus=REJECT`，净付 0，**不提交累计、占额 0**，Outbox 发 `REJECTED` 事件 |
| 费用级拒赔 | `FeeConfig.rejectType`（`CATALOG_EXCLUSION` / `EXCLUSION_CLAUSE`） | 该行 `payout=0`、`feeDeduct=0`，原因由 `rejectType` 单列 |

`settleStatus ∈ {PAY, PARTIAL, REJECT, HOLD}`：`HOLD` 为风控 P0 挂起（不出金额、不占额）。基准：监管要求拒赔须告知**原因码**（禁自由文本）+ 理赔"事实认定—归因"双轨。

### 9.6 并发正确性

| 手段 | 做法 | 失败语义 |
|---|---|---|
| 幂等租约 | `SettlementStorePort.tryBegin(idempotencyKey)` CAS | 取不到租约 → `ConcurrentSettlementException`，fail-closed 不占额 |
| 乐观锁 | 累计提交携带 `version` | 失配 → `ConcurrentAccumulationException`，转重试/人工，禁静默覆盖 |
| 串行锁 | 同保单同周期临界区串行（单实例 JVM 锁；集群走 DB 租约） | **禁用 `SELECT ... FOR UPDATE`** |

> 顺序执行会被幂等挡住，但并发两请求可同时 `find(null)` 通过而各占额一次——所以幂等键之外还需要**租约**。

## 10. 决策图 `Adjust` 节点接线与 AI 边界

```
EvidenceLoad → RuleCheck(RULE+C2) → AiAssess(LLM+C5+C6+E5)
  → FraudScreen(FRAUD, 图E2+C9) → Arbitrate(DECISION+C3)
  → Adjust(RULE+C2+C11)  ← 【本引擎为唯一理算事实源】
       RuleEnginePort(C2) 求值 → SettlementEngine 算术
       → LedgerPort(C11) 占额 → TracePort(C4) 快照 → OutboxPort 事件
  → 结算 A7 由下游监听事件驱动，经 C10 直付三态灰度
```

| 项 | 值 |
|---|---|
| node_name / node_type | `Adjust` / `RULE`（不新增自定义类型） |
| handler | `SettleClaimUseCase`（**唯一**，禁止他处另写理算） |
| 失败分支 | 理算异常 / 反诈 P0 → 挂起 `MANUAL_REQUIRED`，不进算术 |
| 插入点 | `claim_flow_config.adjustment_order` 驱动 Shadow/Assisted/Automated（不硬编码） |

**与前后节点的契约**：`FraudScreen` P0 → 占额前短路返回 `PENDING_MANUAL`；`Arbitrate` 结论为总闸（`REJECT` 净付 0，`PARTIAL` 按比例缩放各行）；`AiAssess` 仅以 `AiSuggestion`（责任适用 / 目录编码 / 加成）经 `Confirmed` 护栏进入算术。

**"智能"的正确边界（AI 不碰钱）**：

| 增强点 | 位置 | 护栏 |
|---|---|---|
| 责任适用性推理 | AI 建议"哪些责任适用"，写入 C2 规则上下文作为先验 | 仅建议；最终适用性由 `RuleEnginePort` 判定；类型 `AiSuggestion`，须 `Confirmed` 方可计入 |
| 费用项 → 目录编码 | 多模态/LLM 将自由文本费用项映射到 `item_code` + `catalog_version` | 进 C2 匹配；低置信转人工；**不改写确定性算术** |

> **硬不变量**：AI 产出永不直接产生金额；任何赔付额必须来自本域算术 + `FormulaSnapshot`。参考实现的"智能"= 配置驱动多态，**非 AI/ML**——这一点必须说清，否则会把"配置化"误当作"智能化"。

## 11. 参考实现：可复用 vs 须补强

### 11.1 可复用（模式级，不是代码级）

| 模式 | 参考位置 | 映射 |
|---|---|---|
| 三类责任策略 + 工厂分发 | `engine/strategy/LiabilityAdjustmentStrategy` + `...Factory`（按 `LiabilityTypeEnum` 注入 Map） | 定额/津贴/报销三策略，新增类型可插拔 |
| 报销确定性流水线 | `ReimbursementLiabilityAdjustmentStrategy.adjustmentInvoice()` | 与《工程落地版》§5.1 流水线逐环节对应，可作策略蓝本 |
| min 聚合多维控额 | `LimitControlEngine.limitControl()`（各维度 `limit − historySum`，取 `min`） | 语义可整段移植 |
| 可读公式轨迹 | `buildNumericFormula()` 生成 `FormulaFactor` 串 + 记录 `version`/`tenantId` | 升级为**物化快照**（§5） |

### 11.2 须按 synapClaim 架构补强（架构升级，非修补破损）

| 项 | 参考实现现状 | 补强方案 |
|---|---|---|
| 端口隔离 | `LimitControlEngine` 内 `@Autowired` 直付/公账 Feign 并 `queryAccount()` | 严禁引擎触达外部；额度经 `LedgerPort`/`IntegrationPort` 在应用层取得后注入上下文 |
| 快照固化 | 全模块无 snapshot，重算时实时读 `plan.version` | 物化 `formula_snapshot` 钉入赔案，源版本变更仍可自包含复算 |
| 目录匹配 | 按名称字符串匹配 | 改为**目录编码** `item_code` + `catalog_version`（名称漂移即漏判） |
| trace / outbox | 模块内无痕迹 | 写 `TracePort` 快照 + 经 `OutboxPort` 发事件 |
| 跨案累计 | 单案内 min，无保单级累计 | `AccumulationPort`（§9.1） |
| 可解释性 | 公式轨迹仅工程可读，无规则 ID | `ruleTrace` + `explain()`（§9.2） |
| 直付预授权 | 无显式预授权步骤 | `preAuthorize` + 生命周期（§4.1 / §9.4） |
| 拒赔建模 | 无拒赔结论（永远付一点） | `settleStatus` / `rejectType` / `denyReasons`（§9.5） |
| 领域模型归属 | 模型在 `bone-tpa-sdk.adjustment` | 模型归本域，`infrastructure.client` 做转换，禁泄漏上游术语 |

## 12. 不做清单（Don't）

1. 不整体照搬参考模块（复用策略/控额基线 + 新架构重构）。
2. 不在引擎内调直付/公账 Feign（端口隔离）。
3. 不实时读 `plan.version`（物化快照）。
4. 不做名称字符串匹配目录（用编码）。
5. 不漏 trace / outbox（审计 + 原子事件）。
6. 不把 `BigDecimal` 算术塞进规则 DSL。
7. 不把 AI 产出直接当金额。
8. 不做单案孤立理算（补保单级跨案累计，含责任维度）。
9. 不双源记额度（三值模型）；不产生双理算事实源（唯一 handler）。
10. 不把年度限额当"免赔额"相减（封顶语义）；不把免赔额后置于比例。
11. 不产出负赔付金额；不允许赔付比例破 100%。
12. 不重复消费免赔/限额（幂等 + 乐观锁 + 租约）。
13. 不让额度跨租户串用（键含 `tenantId`）。
14. 不让被保险人因理赔获利（第三方已付先抵扣）。
15. 不给风控高风险案件出金额（HOLD fail-closed）。
16. 不把"限额 0"当限额为零（0 = 未配置）。
