# 20 - 额度投影自愈与释放阻塞（P0-6，2026-10-31）

> 定位：承接《19-额度释放原子性与占用归属（P0-5）》——那一册修掉了 F1（三事务 ⇒ 账实不符）与
> F2（释放只认共享池余额 ⇒ 越权释放）。但**F2 的修复方案自身留了一个残留缺陷**：归属校验加上了，
> **池级余额校验却没摘掉**，于是"投影被抽干的共享池"会把本单**合法**的释放永久拒掉。
> 本册修掉它，并把"账户是投影、流水是事实"这条原则真正落到写路径上。
> 本册只记录有代码证据的改动。

## 一、缺陷取证

### 1.1 现象：单据永久卡死，钱出不来

生产库残留的结算单 `SO771522015306711040-1`（claim `771522015306711040`，金额 18000）卡在
`funding_stage=REVIEW_FREEZE`，`cancel` 恒返回 400：

```json
{"success":false,"code":400,"message":"冻结额度小于释放金额", ...}
```

它的流水形态是 **F1 的教科书式实证**：个人账有 `SOFT 18000` + `RELEASE 18000`，
**责任账只有 `SOFT 18000`、没有 `RELEASE`** —— 个人账已解冻（且不会回滚），责任账仍冻结。

### 1.2 因果链（F2 污染 → 池被抽干 → 本单被卡死）

把流水的 `before_amount/after_amount`（字段绝对值快照）连成时间线，因果链完全闭合：

| 时刻 | 责任账 `quota_frozen` | 事件 | 依据 |
|---|---|---|---|
| 07:34 | 0 → 792 | `SO771517221850578944-1` 软占 792 | SOFT 流水 before/after |
| 07:53 | 18792 → **36792** | 本卡死单软占 18000 | SOFT 流水 before/after |
| 09:49 | 36792 → **22761.92** | 13 笔老单**越权释放** −14030.08 | RELEASE 流水 before/after 连减 |
| 09:49 | 22761.92 → **3969.92** | 两笔正常释放（792 + 18000） | RELEASE 流水 before/after |
| 09:49 | — | **本单责任账释放**：池里只剩 3969.92 < 18000 ⇒ 抛「冻结额度小于释放金额」 | 结算单卡死至今 |

越权释放的 13 笔全部是 **F2 形态**（建于责任账接线之前，责任账上"只有 RELEASE、没有 SOFT"）：

```
SO770803272792408064-1  RELEASE 24.30（无 SOFT）
SO770803628075122688-1  RELEASE 13500.00（无 SOFT）
... 共 13 笔，合计 −14030.08
```

**账实对账**（把 13 笔越权释放剔开后，责任账的真相是）：

| 组成 | 金额 |
|---|---|
| 本卡死单 SOFT（未结） | **+18000.00** |
| 13 笔越权释放（从未占用过责任账） | **−14030.08** |
| = 当前 `quota_frozen` | 3969.92 |

⇒ **本单自有 hold 足额 18000，却被"别人的越权释放抽干后的池余额"挡在门外。**

### 1.3 为什么 F2 的修复没能覆盖它（残留缺陷）

F2 引入的 `releaseOwned` 三态判定里，`ownHeld >= amount` 分支**仍然委托给池级 `release()`**：

```java
if (held.compareTo(amount) < 0) { throw ... }   // 归属校验（F2 新增）
return release(txnId, amount, ...);              // ← release() 内部还有一道池级余额校验
```

于是形成**两道闸门**：归属闸门放行后，池级闸门（`quotaFrozen >= amount`）仍会拦下。
F2 修好了"不许释放别人的"，却没修"**自己的钱取不出来**"。

### 1.4 业界语义对照（本仓原本就写着的规则）

《19》分册 2.1 节引用的业界 hold/escrow 语义：

> 一笔占用只能被它自己释放；**账户上的冻结总额是各笔 hold 的投影**，释放必须回到具体那笔 hold。

推论（本仓原先没落到代码里的一条）：

- 释放一笔 hold 的**唯一**前置条件是"**该 hold 存在且未被释放**"（归属校验）；
- 账户 `frozen` 是**投影**（Σ 各笔未结 hold），**不是释放的前置门槛**；
- 若投影 < 本单持有量，说明**投影已失真**（别人越权释放 / 并发丢失更新 / 跨版本代码路径），
  正确动作是**修正投影**，而不是把本单的合法释放拒掉 —— 后者会让结算单卡死、钱永远出不来。

## 二、修复

### 2.1 领域层：归属校验通过后，不再校验"共享池总额"

`QuotaAccount.releaseOwned(...)` 的 `ownHeld >= amount` 分支改走 `releaseHeld(...)`（**不做池级余额前置校验**）：

```java
if (held.compareTo(amount) < 0) { throw new DomainException("…拒绝越权释放共享池额度"); }
return releaseHeld(txnId, amount, claimId, settlementNo, idempotencyKey);   // 不再经过池级闸门
```

`releaseHeld` 只负责改投影 + 记事实，扣减后为负 ⇒ `assertConserved()` 以「额度守恒被破坏」
fail-closed（**负冻结仍被领域层拦住**，护栏没有丢）。

池级 `release(...)` 保留（生产代码零调用，只作"无归属信息"场景与测试夹具），它 = 池级前置校验 + 同一个 `releaseHeld`。

### 2.2 应用层：池投影亏空时，按流水事实重算自愈

`QuotaApplicationService.reconcileProjectionIfDeficit(account, amount)`：

- **触发条件（O(1)）**：账户 `frozen < 本次待释放金额` ⇒ 投影不足以支撑本次释放 ⇒ 投影可能失真；
- **动作**：按流水重算 `frozen` / `claimed` / `deductible_used` 三个投影并写回（`QuotaAccount.reconcileProjection`）；
- **正常路径零开销**：投影充足时只做一次比较，不重算。

重算口径（`projectFromLedger`）与 `ownHeld` **同源**，按结算单聚合后取净占用为正者求和：

| 流水 | 对 `frozen` | 对 `claimed` |
|---|---|---|
| `SOFT` | ＋amount | — |
| `HARD` | ＋`max(0, after − before)` | — |
| `PAID` | −amount | ＋amount |
| `RELEASE` | −amount | — |
| `REFUND` | — | −amount |
| `DEDUCTIBLE` | — | —（走 `deductible_used`） |

**越权释放（无对应占用的 RELEASE）净额为负，被 `max(0, …)` 剔除 ⇒ 投影回到事实**（那笔单从未占用过，
本就不该影响池）。这正是把本卡的 18000 找回来的机制。

### 2.3 口径统一：老版本 `HARD` 的真实占用

早期版本用 `HARD` **直接起手**占用（`before ≠ after`，真实增加了冻结额），与新版
"SOFT 起手 + HARD 升级（`before == after`，增量 0）"不同。若一律按"增量 0"处理，老单的自有占用会被算成 0
⇒ 释放被当成空操作、其占用永远留在池里。故 `HARD` 取 `max(0, after − before)`：
新版为 0（不计），老版为真实占用额（计入）。**`ownHeld` 与 `projectFromLedger` 同步采用该口径**，
否则单笔归属判定与池级投影会互相打架。

### 2.4 CORE-06 例外登记（补充）

本册不新增跨聚合写点，仍在《19》分册已登记的例外范围内；补充声明两点：

| 维度 | 补充声明 |
|---|---|
| **业务不变量** | 账户投影 = 流水事实的汇总。投影与事实失真时，**允许在写路径上按事实修正投影**（自愈），但**不得借修正之名释放不属于自己的占用** —— 前者有流水可依，后者无流水可依，属越权。 |
| **失败语义** | 自愈后若守恒仍被破坏（`initial − claimed − frozen < 0`）⇒ **fail-closed**，抛「额度守恒被破坏」，不做"尽力而为的部分写入"。 |
| **并发成本** | 自愈读全量流水（该账户该责任池的所有结算单）⇒ 单次 O(n)；只在**异常路径**（投影不足）触发，正常路径 O(1)。账户更新仍受 `@Version` 乐观锁保护，冲突时由上层重试。 |

## 三、口径自洽性验算（用生产数据反证）

重算口径不是拍脑袋写的，用生产库的两本账反算了一遍：

| 账户 | 字段 | 现有值 | 按流水重算 | 差 |
|---|---|---|---|---|
| 个人账 `9151002` | `frozen` | 0.00 | **0.00** | **0** |
| 个人账 `9151002` | `claimed` | 431020.23 | **431020.23** | **0** |
| 责任账 `9161003` | `claimed` | 208782.08 | **208782.08** | **0** |
| 责任账 `9161003` | `frozen` | 3969.92 | **18000.00** | **−14030.08** |

结论：

1. **`claimed` 与个人账 `frozen` 零误差** ⇒ 重算口径与既有写入路径**完全同源**，不会误伤正常数据；
2. 责任账 `frozen` 的缺口 **14030.08 精确等于 13 笔越权释放之和** ⇒ 因果链闭合，
   重算值 18000 正是本卡死单的自有 hold ⇒ 释放后归零，账实自洽。

## 四、变异验证（全绿不算证据）

变异脚本：`scripts/e2e/mutate_quota_release.py`（本册扩到 **7** 个变异体，覆盖 F1/F2/F3 三条线）。
纪律不变：变异标记必须命中 **1** 处；每次变异后先 `spotless:apply`（否则 `spotless:check` 先失败 ⇒
**测试根本没跑** ⇒ 假"被杀"）；必须断言**用例数与基线一致**且目标用例转红。

| 变异（改一段实现） | 被谁杀死 | 实测红信息 |
|---|---|---|
| M1 `releaseOwned` 绕过归属判定（直接释放，不看自有预占） | `releaseWithoutOwnHoldMustNotStealOthersHold`（场景）＋ `releaseOwnedWithoutOwnHoldIsNoop`（域） | `A 单在责任账无自有预占 ⇒ 释放必须空操作，绝不能吃掉 B 单的预占（越权释放）` expected `0` but was `-1` |
| M2 去掉「自有预占不足即拒」，改为只释放自有量 | `partialOwnHoldMustFailClosed`（场景）＋ `releaseOwnedRejectsInsufficientOwnHold`（域） | `自有预占不足时必须拒绝释放（fail-closed）` — Expected `DomainException` but was not thrown |
| M3 免赔回退去掉归属校验 | `deductibleOwnershipMustFailClosed`（场景）＋ `reduceDeductibleOwnedRespectsOwnership`（域） | `本单从未消抵免赔 ⇒ 空操作` — 空操作未发生 |
| M4 回冲 claimed 的 `txn_type` 改回 `RELEASE`（类型歧义） | `refundTxnTypeIsDistinctFromRelease`（域） | `回冲 claimed 必须与释放 frozen 区分：流水是事实表，类型歧义会让「本单还占多少冻结」算错` |
| M5 **冗余防线探针**：域层 `releaseOwned` 退回池级 `release` | `releaseOwnedWithDeficitProjectionFailsOnConservation`（域） | 错误语义从「额度守恒被破坏」变成「冻结额度小于释放金额」 |
| M6 **F3 未修**：应用层去掉投影自愈调用 | `deficitProjectionMustSelfHealAndRelease`（场景） | 扣减后冻结为负 ⇒ 「额度守恒被破坏」，取消失败 |
| M7 自愈重算只保留本单占用（抹掉他人占用） | `selfHealMustNotDropOthersHold`（场景） | `自愈重算必须保留他人（B 单）的占用：若重算只认本单，B 单的额度会被凭空抹掉（可赔额度被放大）` |

实测：**7/7 变异全部被杀**；基线 52 用例绿 → 变异 → 恢复 → 复跑基线仍绿。

**M5 的结果值得单独记一笔（它是一个"反预期"发现，不是失败）**：
M5 让域层退回池级校验后，**场景用例 T4 仍然绿** —— 因为应用层的投影自愈已把池级校验**完全旁路**
（自愈先把 `frozen` 重算回足额，域层校验自然通过）。这说明两道防线是**互补**的：

- 应用层自愈 ⇒ 业务不阻塞（**这条**被 M6 独立证明）；
- 域层不做池级前置校验 ⇒ 领域语义正确、错误信息不误导（**这条**被 M5 独立证明）。

因此 M5 被如实标注为"**冗余防线探针**"（纵深防御证据），而不是"独立判别力证据"。
**如实降级一个变异体的地位，比把它硬说成"杀死了 T4"更诚实** —— 否则这份报告就变成了自说自话。

## 七、给下一轮的三条提醒

1. **"全绿"不等于"有判别力"**：F3 修完时全部 375 个用例**照样全绿** —— 因为**没有任何一个用例覆盖它**。
   必须先写出会红的用例（把投影抽干），再改实现。
2. **池级余额校验不能与归属校验串联**：两者语义相反。归属校验问"这笔钱是谁的"，池级校验问"池里现在还剩多少"；
   后者在前者放行后**只会制造阻塞**，不会增加安全性（安全性由归属校验提供）。
3. **投影类字段（`frozen`/`claimed`）必须能被流水反算校验**：本册的口径自洽性验算（§三）之所以能一锤定音，
   正是因为流水的 `before/after` 记的是**字段绝对值快照**。若流水只记增量，账实对账就得靠人工考古。
