# 18 · 「次」分组维度落地与降级判据（发票日期 / 医院 / 科室 / 病种）

> **依据**：《synapClaim 智理理算引擎业务规则（V1·责任配置与理算基线）》§7.3「次」的六档定义。
> **前置**：`16-理算引擎V1重建`、`17-控额层接线修正与多次闭环`。
> **实施日期**：2026-10-30。**验证**：`synap-claim` 352 tests 绿（+6）；`bone-metadata-sdk` 新增 4 tests；7 项变异全部被抓。

---

## 1 问题：次限额配了，但"次"永远只会有一次

上一轮把次限额接进了控额栈（`QuotaStack.Demand.occurrenceCap`），并加了 `OCCURRENCE_DIMENSION_MISSING` 的 fail-closed：配了「同日/同院」却没发票日期就拒绝。

这条规则本身没错，但落地后必然踩到两件事：

1. **库里根本没有这些列**。`grep -rn "invoice_date\|hospital_code\|department\|diagnosis" db/migration` 在 V9 之前为空 —— 责任只要配成"同日"，**全部案件 100% 拒绝**。转人工率不是"偏高"，是"全量"。
2. **如果为了跑得通而静默并成一组**，两天各 500、次限额 300 的案子会赔 300 而不是 600（少赔），且不留任何痕迹。

所以真正要补的不是"再加一个 if"，而是**数据**，以及**缺失时能否证明等价的判据**。

---

## 2 数据模型：哪些维度该落在哪一层

| 维度 | 落位 | 理由 |
|---|---|---|
| 发票日期 `invoice_date` | `t_claim_case`（发票级） | 一赔案一发票（`uk_tenant_invoice` 限定单一发票号），一次就诊一个开票日 |
| 医院编码 `hospital_code` | `t_claim_case`（发票级） | 同上；按**编码**比对而非名称——名称可改，编码才是身份（与 `LimitedConditions.hospitalCode` 同口径） |
| 病种编码 `diagnosis_code` | `t_claim_case`（发票级） | 一次就诊一个主要诊断 |
| 就诊科室 `department` | `t_claim_item`（**行级**） | 一张发票可含同日多科室费用（挂号多科），科室是行级事实 |

**为什么不把三列都放明细**：发票级事实放明细要逐行重复存同一个值，且会引入"同一案内出现多个开票日期"这种 schema 允许、业务非法的裂缝。

**为什么科室必须放明细**：它是"同院同科室"这一档唯一能真正把一次就诊拆成多「次」的维度。放发票级就永远只有一组，等于该档配置永不生效 —— 又回到"配了不生效"。

**不使用 `out_insure_time` 顶替 `invoice_date`**：出险日是就医发生日，开票日是结算日，可相差数天。顶替会按错误日期切分，且错误不可见。

---

## 3 判据：什么时候可以降级，什么时候必须拒绝

`OccurrenceGrouper.Dimension` 给每个维度标了 `scope`，这是整个改动唯一的判断依据：

```
INVOICE 级（日期 / 医院 / 病种）：一赔案一发票 ⇒ 案内恒定
LINE    级（科室）：一张票可跨科室 ⇒ 案内可变
```

| 情形 | 处理 | 依据 |
|---|---|---|
| 全部有值 | 正常分组 | — |
| **全部缺失 + 发票级 + 有发票号** | **降级为"同一次"，进快照与诊断** | 有发票号 ⇒ 可证案内只有一张票 ⇒ 该维度案内恒定 ⇒ 分组结果与配置语义**相同** |
| 全部缺失 + 发票级 + **无发票号** | 拒绝 `OCCURRENCE_DIMENSION_MISSING` | 无法排除多天/多票混装，按一次算会少赔 |
| 全部缺失 + **行级** | 拒绝 `OCCURRENCE_DIMENSION_MISSING` | 科室可跨，缺了无法证明恒定 |
| **部分有值** | 拒绝 `OCCURRENCE_DIMENSION_INCONSISTENT`（新增码） | 数据不自洽：按有无分组会把同一张票拆成两个「次」，多赔一次次限额 |

一句话概括：**能证明"缺失不改变结果"就降级并留痕，不能证明就拒绝；不允许"猜"。**

`singleInvoiceProvable` 由 `ClaimCase.singleInvoiceProvable()`（发票号非空）判定 —— 判断放在聚合上，因为它读的是聚合自己的状态，而不是散落在引擎里的一个假设。

## 4 降级必须可见

`formulaSnapshot` 新增 `grouping` 段：

```json
"grouping":{"basis":"SAME_DAY","occurrenceLimit":300,"groups":1,
            "singleInvoiceProvable":true,
            "dimensions":["INVOICE_DATE"],
            "degraded":["发票日期缺失 2/2（发票级维度，有发票号故案内恒定，按同一次处理，不改变分组结果）"]}
```

同时写入 `diagnostics`（`次分组降级：…`）。理由与上一轮 `diagnostics` 落库相同：**没有痕迹的降级与正确实现，在审计报表上长得一模一样**。

## 5 写入链路：避免"加了列却没有写入方"

只加列不写入，就是本轮反复在修的同一类缺陷（配置齐全、文档齐全、代码从不读）。故本次是全链路贯通：

`SubmitClaimReq`（协议）→ `SubmitClaim` / `ClaimItemDto`（应用命令）→ `ClaimCase.bindInvoiceContext(...)` / `ClaimItem.assignDepartment(...)`（聚合）→ 落库 → `findClaimWithItems.sql` 投影 → `OccurrenceGrouper.Fact` → 分组。

两个刻意的取舍：

- **不给 `ClaimCase.draft(...)` 加参数**（14 处调用方都是造赔案、无人关心发票维度），改用显式方法 `bindInvoiceContext(...)`：让"报案"与"补录"两种意图不共用入口，漏传也不会静默变成空值。
- **`ClaimItem.of(...)` 签名不动**，补录走 `assignDepartment(...)`，避免 10+ 处测试夹具连锁改动。

`ClaimWithItemsProjection` / `factsOf` 也不再"按一赔案一次"糊过去：分组维度一律取自投影真实列，这样 `Adjustment.apply → calculate(request)` 这条**生产路径**才真正读到科室。

## 6 顺带修掉的 SDK 隐患：`LocalDate` 读不出来

新增 `DATE` 列触发了两处 SDK 缺口，都会在**读取阶段**炸，且报错与列值无关、极难定位：

| 缺口 | 现象 | 修法 |
|---|---|---|
| `TypeConverter` 的 `LocalDate` 分支不认 `LocalDate` 自身 | Connector/J 8 部分版本 `getObject()` 对 DATE 直接返回 `LocalDate` ⇒ `Unsupported LocalDate conversion`，整张表读不出 | 增加身份转换 + `LocalDateTime → LocalDate` |
| `DATE_FORMATTERS` 缺 `ISO_LOCAL_DATE` | 最标准的 `"2026-03-10"` 反而解析失败（原列表只有日期时间格式） | 把 `ISO_LOCAL_DATE` 排首位 |

新增 `TypeConverterLocalDateTest`（4 例）。这两处是纯增量：只会让原本抛异常的情形成功，不改变既有类型的转换结果。

## 7 验证

**用例**：`synap-claim` 352 全绿（+6）；`bone-metadata-sdk` 新增 4 例全绿。旧路径（`LiabilityRule.fromLegacy`）未动，**赔付金额与上线前一致**。

**变异验证（7 项全部被抓，无"0 红"）**：

| # | 变异 | 抓到它的用例 |
|---|---|---|
| M1 | `factsOf` 不读投影列（回到"一赔案一次"） | `groupingDimensionsComeFromProjection`（RuleGap，而非静默 300） |
| M2 | 发票级维度缺失一律拒绝（删降级分支） | `invoiceLevelDimensionDegradesWhenProvable` |
| M3 | 行级维度也允许降级 | `lineLevelDimensionNeverDegrades` |
| M4 | 不校验"部分缺失" | `partialDimensionRejects` |
| M5 | `singleInvoiceProvable` 恒 true | `invoiceLevelDimensionRejectsWhenNotProvable` + `missingDimensionFailsClosed` |
| M6 | 降级不进快照 | `invoiceLevelDimensionDegradesWhenProvable`（快照断言）+ `groupingDimensionsComeFromProjection` |
| M7 | 报案不写发票维度 | `submitPersistsInvoiceContext` |

判别力设计要点：M1 之所以能抓，是因为用例同时断言**金额 600 与 `"groups":2`**；只断言金额时，若科室缺失导致拒绝，测试会以异常"看起来红了"，但那是另一种错（把可算的案子拒了）。

## 8 影响面与兼容性

| 变化 | 兼容性 |
|---|---|
| `t_claim_case` +3 列、`t_claim_item` +1 列（V10） | 历史数据为空/NULL，不回填不猜测；无默认值变更 |
| `SubmitClaim` / `SubmitClaimReq` / `ClaimItemDto` 增字段 | 均为可空/空串；MapStruct 同名自动映射，老调用方无需改动 |
| `OccurrenceGrouper.requireDimensions(basis, facts)` | **签名变更为** `(basis, facts, singleInvoiceProvable)` 并返回降级列表（内部类，仅引擎调用） |
| 新增 `RuleGap.Code.OCCURRENCE_DIMENSION_INCONSISTENT` | 域内原因码，与既有 12 类同处 `RuleGap`，不进全局错误码登记 |
| `TypeConverter` | 纯增量，既有类型转换结果不变 |

**行为变更（唯一一处）**：配了「同日/同院/同病种」且发票维度缺失、但**有发票号**的案件，此前一律拒绝，现降级为同一次并在快照留痕。赔款金额不变（单票案内本就只有一次），变化的是"从转人工变为可自动理算"。

## 9 未做（显式拒绝或留待业务定口径）

| 项 | 原因 |
|---|---|
| 科室缺失时的降级 | 一张票可跨科室，缺了无法证明等价。**责任配了"同院同科室"而明细无科室，仍转人工**——这是数据问题，只能靠录入/OCR 补齐 |
| 理算后修改发票维度 | 会改变分组数与金额，需走重算（`recalculate`）而非静默更新；当前由调用方保证，未加状态机拦截 |
| 多票赔案（一赔案多张发票） | 当前模型 `uk_tenant_invoice` 限定单票。若未来放开，`singleInvoiceProvable` 的判据必须同步改为"逐票比对"，否则降级路径会变成少赔通道 |
| 病种维度按明细区分 | V1 未定义；当前按"一次就诊一个主要诊断"落在发票级 |
| 逐行分位归因 | 需给 `t_adj_calculation_line` 加明细维度列（否则同一费用池只有一行，无法回答"这 300 是哪个项目被砍的"） |
