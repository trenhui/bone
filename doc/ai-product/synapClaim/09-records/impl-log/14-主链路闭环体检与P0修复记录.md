# 14 - 主链路闭环体检与 P0 修复记录（2026-10-29）

> 定位：跨聚合、跨角色的**端到端**体检（区别于 00–13 的单模块/单能力完善）。
> 结论：方案族在"文档一致性 + 单模块工程质量"上已很高，但**四本账（费用账/额度账/责任账/资金账）在同一条链路上没有对齐**。
> 本册记录已完成的三项 P0 修复（含变异证据）与尚未动的缺口（含"先写什么红测试"）。

## 一、自我更正：先把上一轮的判断校准

上一轮诊断称"能力缺失时 100% 产出系统建议拒赔"，**该结论不成立，已撤销**。复核证据：

| 断言 | 实测 | 结论 |
|---|---|---|
| 知识能力缺失 → `SUGGEST_REJECT` | `DecisionTriage.evaluate` 中 `fraudGatePassed` 判定（第 89 行）**先于** `rejectSuggested`（第 106 行）；而 E1/E2 桩恒 `available=false` ⇒ 闸恒不过 ⇒ 恒 `MANUAL_REQUIRED` | 拒赔路径**当前不可达**，风险是**潜伏**而非线上事故 |
| 自动通过的真实条件 = 验真 + 置信度 ≥0.85 | `RuleCheckNodeHandler` 要求 `visualAvailable && graphAvailable` 才可能过闸 | 自动通过**当前不可达**（被 E1/E2 桩挡住），规则路"没核责"因此**没暴露** |

**真正的风险形态因此改写为**："一旦 E1/E2（或 C2）先于 C6 接入，链路会在**没有任何一处代码变更**的情况下开始自动放款/产出拒赔"——这不是 bug 的常态，而是**护栏前提失效**。第 4 节的变异证据直接复现了这个切换：把 `capabilityMissing` 兜底删掉，同一场景从 `MANUAL_REQUIRED` 变 `AUTO_APPROVE`。

另有一处**测试把缺陷锁成了预期**：`DecisionGraphFunctionalTest` 场景 G 原断言 `知识能力缺失 → SUGGEST_REJECT`，即以测试固化"没接线 = 对客户不利决定"。本次已改断言并补充理由，见 §3.1。

## 二、本次完成的三项 P0（+1 项积压债）

| # | 缺陷 | 修法 | 文件 |
|---|---|---|---|
| P0-1 | "无法判定"被映射为"建议拒赔" | 三态能力语义：`capabilityMissing` 与 `rejectSuggested` 彻底分离 | `AiAssessNodeHandler`、`DecisionGraphExecutor`、`DecisionNodeHandler` |
| P0-2 | 核责规则未并入硬闸（"没查"被当成"查过且干净"） | `capabilitiesPresent = ruleAvailable && visualAvailable && graphAvailable` | `RuleCheckNodeHandler` |
| P0-3 | 软占/硬冻都记 `txn_type=HARD`（接线即双冻结） | 拆为 `reserveSoft`（SOFT，frozen+）与 `upgradeToHard`（HARD，不新增占用） | `QuotaAccount`、`QuotaApplicationService` |
| 积压 | `ClaimCaseApplicationServiceTest` 缺 `ClaimItemRepository` mock（HEAD 已红） | 补 `@Mock` | 同名单测 |

### P0-1　无法判定 ≠ 拒赔（fail-safe 落点是人，不是不利决定）

```java
// 修前：能力缺失并入拒赔建议
rejectSuggested = a.rejectSuggested() || !knowledgeConfirmed;

// 修后：只有"有依据的不利结论"才置拒赔
boolean knowledgeAvailable = k.available();
boolean clinicallyUnreasonable = knowledgeAvailable && !k.clinicallyReasonable();
rejectSuggested = a.rejectSuggested() || clinicallyUnreasonable;
out.put("capabilityMissing", !knowledgeAvailable);
out.put("capabilityReason", "KNOWLEDGE_UNAVAILABLE");
```

**为什么必须分开**：拒赔触发《保险法》24 条 3 日书面通知、五要素通知书、48h 申诉通道、AI 参与告知与监管投诉计量；转人工只是进一个队列。用拒赔做兜底，等于让"没接线"变成对客户的**不利事实认定**，且该结论会随决策轨迹落库。

**执行器侧的优先级（关键，决定不误伤）**：
- 结构性缺能力（确定性节点**无处理器**，装配不全）→ 一律 `MANUAL_REQUIRED`，**不得**判成"缺件"（否则让客户补一件没缺的材料）；
- 节点自报的能力缺失（知识/规则等未接入）→ **只兜"本会 AUTO_APPROVE"**，其余结论保留更精确的原因码（大额复核档、风控命中、验真未过），否则会把"大额双人复核"降级成"普通人工"，或把"有依据的拒赔建议"抹成"无法判定"。

### P0-2　核责规则并入硬闸（ADR-002 前提已失效）

`RuleEnginePort.RuleCheckResult.available` 的契约本就写着"不可用绝不等同于无冲突"，但实现只**标注**不**拦**。原豁免理由（ADR-002）是"C2 未交付，而 E1/E2 也没接 ⇒ 闸本就恒不通过，并入无意义"。**这个前提在 E1/E2 先于 C2 接入的那一刻自动失效**——那时闸会放行"没核责"的案件。故一次收敛：

```java
boolean capabilitiesPresent = ruleAvailable && visualAvailable && graphAvailable;
boolean fraudGatePassed = capabilitiesPresent ? (r.fraudGatePassed() && !fr.tampered() && !gr.hit()) : false;
```
原因码同步细分：`RULE_ENGINE_UNAVAILABLE` / `ANTI_FRAUD_CAPABILITY_MISSING` / `RISK_HIT` / `VERIFY_NOT_PASSED` / `PASSED`，并把"没查"（`capabilityMissing`）与"查出了问题"（`riskHit`）分开——两者的人工处置路径不同（补能力 vs 风控复核）。

**代价与待办**：`AUTO_APPROVE` 从此以 C2 真实交付为前置。这是一次**资金路径策略变更**，需在 ADR-002 登记"豁免已撤销"，并同步 §5.3/§6.3 口径（见 §6）。

### P0-3　软占/硬冻必须分型（否则接线即双冻结）

修前 `freeze()` 无论软占硬冻都写 `txn_type=HARD`，且都 `frozen += amount`。§5.3 的映射矩阵是 `SettlementOrder 创建 → QuotaTransaction(SOFT)`、`HARD_RESERVED → QuotaTransaction(HARD)` 且**不新增占用**。现按矩阵拆两个方法：

```java
reserveSoft(...)   // OCCUPY / SOFT，frozen += amount
upgradeToHard(...) // OCCUPY / HARD，before == after，且 amount <= 已冻结
```
流水是 append-only 的**事实表**（账户只是投影）；软占记 HARD 会让按 `txn_type` 的软/硬统计、对账"SOFT→HARD 阶段单调"全部失真，一旦按 F1 接线就是**同一笔钱双冻结、可用额度凭空蒸发**。

## 四、尚未动的主缺口（按"能不能被证伪"排序）

### P0-4　额度账没有读者：免赔/封顶/责任限额"每案从满额重算"（最高优先，最大工作量）

证据：`Adjustment.apply(rows, liability)` 无任何"已用"入参；`liability.deduct()/limit()` 取**配置值**而非剩余值；`QuotaApplicationService` 全仓 **0 调用方**；`SettlementApplicationService` 不引用 quota；`accumulateDeductible` 仅测试调用；`capUsed` 有写无读。
后果：同保单年度第 2 案起，**免赔重新全额扣（系统性少赔）+ 责任限额重新满额（系统性超赔）**。300 条评测、279 单测**结构上测不出跨案**（全部单案断言）。

**执行顺序（不可颠倒）**：
1. 先写**跨案红测试**：同保单三案（6000/4000/…），断言第 2 案免赔只扣剩余、限额按已用递减；此时**必须红**（红是交付物，证明缺口真实）；
2. 建读侧：`AccumulationPort`（按 `policy_no + plan_id + quota_year + liability_uuid` 分行读 `t_quota_account` 的 `deductible_used / cap_used / claimed+frozen`），适配器走 `QuotaAccountRepository`；
3. `Adjustment` 入参显式接收 `Usage`，**禁止**提供"默认 usage=0"的便捷重载——那正是"配了不生效"的温床；
4. 再移植 F1 的护栏（顺序反了就会把护栏写成 `used=0` 的假绿）。

### P1（接得进、接不动的口径缺口）

| # | 缺口 | 现状 | 对标差距 |
|---|---|---|---|
| 1 | 责任模型仅 5 标量 | `AdjLiability` 只有 `payPercent/deduct/limit/socialOnly/waitingPeriod`；`waitingPeriod` **无读者**（等待期出险照赔） | 六维免赔 15 值、11 因子笛卡尔积、后付责任链、次限额、黑白名单目录匹配全无对应 ⇒ "新保司 ≤7 天接入"实为"每家改一次代码" |
| 2 | 理算只产 1 条 OUTPUT 行 | 所有费用行聚合成单个 `base` | 逐行是"拒赔五要素事实认定/客户逐项明细/团险公账个账分账/Σ分账对账"的唯一载体；单行下 §11.7 守恒校验无判别力 |
| 3 | KPI 只有自动化率 | PRD §15 | 自动化率**可被阈值刷**；保司验收看 leakage rate + 理算准确率（抽样置信区间） |
| 4 | 缺历史案件金额回归 | 有 300 条字段/命中评测集，无 book-of-business regression | 规则/目录/条款一改，答不出"影响多少案、金额变多少"（`formula_snapshot` 已具备自包含复算能力，只差做成发布门禁） |

### 结构性判断（比修 bug 更影响成败）

1. **护城河位置错了**：确定性分层/幂等/乐观锁/审计是**入场券**；普康的护城河是三大目录 + ICD + 机构库的**运营团队**，平安是规则密度与产品工厂，众安是医疗数据直连。工程纪律让你能卖，数据与目录密度让你能赢。
2. **AI 叙事与合规姿态互相拆台**：金发〔2026〕8 号已把"关键环节人工监督"定死。可卖的是"**AI 做证据整理、差异提示、找依据；人做结论**"，度量换成"单案人工工时下降 %"——客户当场能验，自动化率不能。
3. **反欺诈冷启动矛盾未解**：新租户=空图，跨租户联邦图撞数据隔离红线。务实解：租户内先跑规则 + 单证验真 + 设备指纹，跨租户只做**脱敏四元组碰撞**（发票号/金额/机构/时间），不建全图。
