# 19 - 额度释放原子性与占用归属（P0-5，2026-10-31）

> 定位：承接《15-跨案累计读侧与责任账接线（P0-4）》——那一册把**责任账（LIABILITY_CAP）接进了 A7 写侧**，
> 但接的方式留下了一个更隐蔽的洞：**额度占用横跨两本账、三个事务**，且**释放只认共享池余额、不认归属**。
> 本册修掉这个洞，并把"CORE-06 例外"按规约要求登记在案。
> 本册只记录有代码证据的改动。

---

## 一、两个缺陷（先取证，再动手）

### 1.1 F1（P0）：三事务 ⇒ 账实不符 + 结算单永久卡死

改前的额度方法一律 `@Transactional(propagation = REQUIRES_NEW)`，而 `SettlementApplicationService`
的 `create / pay / cancel / refund` 各自 `@Transactional`。于是**一笔结算的三个写点分属三个事务**：

```
结算单状态变更（外层事务）
  ├─ 个人账 释放（REQUIRES_NEW，独立提交）
  └─ 责任账 释放（REQUIRES_NEW，独立提交）   ← 这一步抛错时，前两步已提交、无法回滚
```

生产库实证（E2E 收尾时抓到的历史残留）：一笔结算单卡在 `REVIEW_FREEZE`，其个人账上**有** `RELEASE`、
责任账上**没有** `RELEASE` —— 个人账已解冻且不会回滚，责任账仍冻结，结算单再也取消不掉
（再取消必撞同一错「冻结额度小于释放金额」）。这是**账实不符**且**结算单永久卡死**。

同一形态的洞还有三处，本册一并收口：

| 路径 | 旧语义下的失败形态 |
|---|---|
| `create` 建结算单 | 个人账软占已提交、责任账软占失败 ⇒ 结算单回滚，但留下**无结算单对应的幽灵预占** |
| `pay` 支付 | 个人账已 `frozen→claimed`（钱已扣），责任账失败 ⇒ 结算单未支付，但**额度已扣** |
| `refund` 退款 | 同上，红冲了一半 |

`create()` 里那段注释当时写的是"软占是 REQUIRES_NEW 独立事务（已提交），异常回溯会把结算单回滚掉、
却留下一条没有责任账对应的预占"——**它已经写明了缺陷，却把它当成了既定约束**。本册把它改掉。

### 1.2 F2（P1）：释放只认共享池余额 ⇒ 越权释放

`QuotaAccount.release(amount)` 只校验 `quotaFrozen >= amount`（**共享池**口径）。共享池里压着多张
结算单的预占，于是 **A 单释放会吃掉 B 单的预占**。生产库实证：claim `770803272792408064`
（`account_type=NO_ACCOUNT`，建于责任账接线之前）在责任账 `9161003` 上**只有 RELEASE 24.30、没有 SOFT** ——
一笔从未占过责任账的结算单，从共享池里放走了一笔钱；池被抽干后，他人合法的释放被拒。

免赔同理：`reduceDeductible(amount)` 只钳到 0，不校验"本单是否真的消抵过这笔免赔" ⇒
从未消抵免赔的结算单去回退，会把**别的案件**已消抵的免赔退回来 ⇒ 客户下一案重复消化免赔（系统性少赔）。

## 二、修复

### 2.1 F2：释放按"本单自有预占"校验（流水推导，fail-closed）

业界做法（支付/银行的 hold 语义）：**一笔占用只能被它自己释放**；账户上的冻结总额是各笔 hold 的投影，
释放必须回到具体那笔 hold，而不是从池子里随手拿。

本仓的"具体那笔 hold"就是**结算单号**：流水的 `settlement_no` 天然带着归属，`append-only` 的流水就是事实表。
因此新增 `QuotaAccount.releaseOwned(...)` / `reduceDeductibleOwned(...)`，三态判定：

| `ownHeld`（本单自有量，由流水推导） | 行为 |
|---|---|
| `= 0` | **空操作**：不落流水、不触碰共享池（幂等重入的正常形态） |
| `0 < ownHeld < amount` | **抛异常 fail-closed**：账实不符，拒绝越权释放 |
| `>= amount` | 正常释放 |

自有量从流水推导（`QuotaApplicationService.ownHeld` / `ownDeductible`）：

- 冻结口径：`SOFT` ＋、`PAID` −（冻结转已扣减）、`RELEASE` −（归还冻结）；
  `HARD` 不新增占用、`DEDUCTIBLE` 不占冻结、`REFUND` 回冲的是 claimed ⇒ 三者不计入；
- 免赔口径：`DEDUCTIBLE + OCCUPY` 是消抵、`DEDUCTIBLE + ROLLBACK` 是回退。

配套两处：

1. **`ledger(account)` 合并视图**：已落库流水 + 本事务内存中新增流水（按幂等键去重）。
   两本账现在同事务写，同事务内刚 append 的流水未必对 `findTransactions` 可见 ⇒ 只看 DB 会漏、
   只看内存会漏历史，合并去重后两侧都全。
2. **流水类型去歧义**：`rollback()`（回冲 **claimed**）的 `txn_type` 由 `RELEASE` 改为 **`REFUND`**。
   两者若共用 `RELEASE`，流水就无法区分"释放冻结"与"回冲已扣减"，按流水推导"本单还占多少冻结"会算错
   （已退款的结算单会被算成还占着冻结）。**流水是事实表，事实表的类型必须无歧义。**
   （核查：对账的额度通道只看账户投影、支付通道用 `FundingEvent`，均不依赖 `txn_type`；全仓无测试断言旧值。）

### 2.2 F1：额度方法改为 `REQUIRED`，与结算单同事务

`QuotaApplicationService` 全部写方法的传播语义由 `REQUIRES_NEW` 改为 **`REQUIRED`**（加入调用方事务）。
于是「结算单状态 ＋ 个人账 ＋ 责任账」三者**同事务、要么全成、要么全败**。

## 三、CORE-06 例外登记（规约要求"须声明业务不变量、失败语义与并发成本，并记录例外"）

> 规约原文：`CORE-06 | 聚合是默认一致性边界 | 跨聚合默认最终一致；同库本地跨聚合事务须声明业务不变量、
> 失败语义与并发成本，并记录例外`（`Bone-DDD-最终实践方案` §CORE-06；扫描规则 `oneAggregatePerTransaction`
> 为 **Advisory**，非硬门禁）。

| 维度 | 声明 |
|---|---|
| **业务不变量** | 一笔结算单的额度占用在**两本账上同时存在、同时消失**。任一本账缺这笔占用（或多出别的结算单的占用），即账实不符，禁止记账。这条不变量跨越 `SettlementOrder` 与两个 `QuotaAccount`，**单事务不可表达**。 |
| **失败语义** | 任一本账写失败 ⇒ **全部回滚**，结算单状态**不推进**（仍停在原阶段，可重试）。领域层一律 fail-closed：账实不符 ⇒ 抛异常，不做"尽力而为的部分写入"。 |
| **并发成本** | ① 两本账按**固定顺序**（个人 → 责任）访问，避免交叉更新造成死锁；② 账户用 `@Version` **乐观锁**做冲突检测（不改用 `SELECT ... FOR UPDATE`）；③ 归属推导基于流水幂等键（`{claimNo}:{stage}:{attempt}`），重复调用不重复记账；④ 共享池仍受"可用额度不足"护栏约束，超额占额在写入前即被拒。 |
| **例外范围** | 仅限 `synap-claim` 的**资金写路径**（`create / pay / cancel / refund` 及其额度方法）。只读侧与理算侧不变。 |

## 四、变异验证（全绿不算证据）

变异脚本：`scripts/e2e/mutate_quota_release.py`（自动跑变异→重跑→恢复→复跑基线）。
纪律：变异标记必须命中 **1** 处；每次变异后先 `spotless:apply`（否则 `spotless:check` 先失败 ⇒ **测试根本没跑** ⇒ 假"被杀"）；
必须断言**用例数与基线一致**且目标用例转红。

| 变异（改一段实现） | 被谁杀死 | 实测红信息 |
|---|---|---|
| M1 `releaseOwned` 退回按池余额释放（忽略自有预占） | `releaseWithoutOwnHoldMustNotStealOthersHold`（场景）＋ `releaseOwnedWithoutOwnHoldIsNoop`（域） | `A 单在责任账无自有预占 ⇒ 释放必须空操作，绝不能吃掉 B 单的预占（越权释放）` expected `0` but was `-1` |
| M2 去掉「自有预占不足即拒」，改为只释放自有量 | `partialOwnHoldMustFailClosed`（场景）＋ `releaseOwnedRejectsInsufficientOwnHold`（域） | `自有预占不足时必须拒绝释放（fail-closed）` — Expected `DomainException` but was not thrown |
| M3 免赔回退去掉归属校验 | `deductibleOwnershipMustFailClosed`（场景）＋ `reduceDeductibleOwnedRespectsOwnership`（域） | `本单从未消抵免赔 ⇒ 空操作` — 空操作未发生 |
| M4 回冲 claimed 的 `txn_type` 改回 `RELEASE`（类型歧义） | `refundTxnTypeIsDistinctFromRelease`（域） | `回冲 claimed 必须与释放 frozen 区分：流水是事实表，类型歧义会让「本单还占多少冻结」算错` |

实测：**4/4 变异全部被杀**；基线 44 用例绿 → 变异 → 恢复 → 复跑基线仍绿。

**一次脚本自身的假绿被当场抓到**：变异报告里"被杀=False"但日志里目标用例明明红了 —— 是报告正则
抓错了方法名（取成了包名段）。**判定脚本与被测代码同样需要证伪**，否则"变异被杀"和"断言有判别力"
都会变成自说自话。

## 六、给下一轮的两条提醒

1. **单案测试测不出归属缺陷**：单案的释放永远"池里正好有我那笔钱"，按池余额释放与按自有预占释放
   **结果完全一样**。必须把两个结算单放进**同一本共享账**（责任账按 `liability_uuid` 分行）才区分得开。
2. **内存仓没有事务**：F1 的原子性（部分失败必须整体回滚）**无法用场景测试证明** —— 内存仓里
   `release()` 之后的异常不会回滚已做的内存变更。该性质必须用**真实数据库 + 真实事务**验证
   （见 E2E 脚本的"资金原子性"探针：人为把责任账的自有预占改小，逼出释放失败，
   然后直查个人账断言**没有被释放**）。
