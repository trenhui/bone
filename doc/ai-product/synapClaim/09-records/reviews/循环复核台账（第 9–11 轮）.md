## 二、仍在生效的两条纪律

1. **「合理」要拆成两栏**：字面动作 ≠ 合理形态。第 9 轮的结论是——照字面执行会产出「刷绿字符串 / 文档抢跑 / 全量停摆」三类动作，与 Google《Rules of ML》《ML Test Score》、CD4ML、NIST AI RMF 及本仓 §1.7 ⑤ 纪律冲突。**执行前先问：这条动作是在补能力，还是在补一个能过判据的字符串。**
2. **判据的可信度取决于证据是否同源**（附录 D）：环境变量、裸判词、参与率三者都能手写，故 `RUNTIME_MODEL_COVERAGE` 要求 `probeEvidence` 自洽（`httpStatus=200` / `model` 非空 / `provenance=PROVIDER` / token > 0 / 合法 `requestId`），且由 E2E 从同一次探活响应透传。这条已进 `tools/_ai_native_readiness.py`，是当前 fail-closed 的直接来源。

#### 业界实践依据

- **Google《Rules of ML》/《ML Test Score》**：判据必须可证伪、数据与模型分别验证、
  「每条规则写成可执行 assertion」；用配置/文档字符串冒充能力就绪属反模式。
- **CD4ML / Thoughtworks**：可复现证据链（provenance、内容哈希、样本量）是先决条件，
  `status` 字段必须由采集结果推导，人手不可直接改。
- **NIST AI RMF 1.0（MEASURE / MANAGE）**：文档状态须与实证一致；「文档抢跑」
  会误导风险判定。
- **fail-closed / blast radius**：缺文件、缺册、真源不可读时必须判 BLOCKED，
  不得判绿；把默认值从「静默超赔」改成「全量停摆」不是修复。
- 仓库自身：`AI技术方案.md §1.7 ⑤`（不得先改文档宣告完成）、`:289`
  （禁止以判据/目标态替代实证）、`:457`（BLOCKED→SATISFIED 唯一合法路径是闭环外部条件）。

### 二、#26 后督 DIFF 回流闭环（已落地）

#### 取证发现

- `InspectionFeedbackRecorder` 产出 `AiEvalSampleCollectedEvent` → `EventAiEvalSamplePortAdapter`

#### 落地（方案 B 主 + 方案 A 叠加）

| 件 | 内容 |
|---|---|
| `InspectionRepository.findDiffConcludedInWindow(from,to)` | 只加方法；SQL 直接过滤 `result='DIFF'`，避免复用全量查询时 500 条上界被 PASS 挤满造成「静默裁剪」 |

### 三、#27 初审字段级完整性（已落地）

#### 取证发现

`ParsedDocument.complete`（必填字段齐备，真源在 `TextLayerDocumentParsePortAdapter.requiredFields()`）
此前只映射到 `OcrStatus`（缺字段→MANUAL），**从未汇入 `ClaimContextView.evidenceAllParsed()`**；

`EvidenceApplicationService.parseImage(long)` 是**零调用方死代码**。

#### 落地（方案 R：opt-in 标记，零公共签名变更）

| 件 | 内容 |
|---|---|
| `EvidenceFieldReader.declaredComplete()` | 只认顶层**显式布尔** `complete` 键；键缺失 / 坏 JSON / `"false"` 字符串 / 数字 / null 一律 `Optional.empty()` |
| `LocalClaimContextPortAdapter` | `allParsed` 收紧为「DONE/MANUAL **且** `declaredComplete().orElse(true)`」 |
| `LlmDocumentParsePortAdapter` | payload 补写 `complete`，与 TextLayer / Image 两通道同口径 |
| `EvidenceController` | 新增 `POST /{evidenceId}/parse-image`（`ApiResponse<ParseOutcome>` + `@PreAuthorize('claim:claims:write')`） |

**为什么必须 opt-in 而不是重建齐备**：必填真源在 infrastructure 层，而外部回填通道
（人工补录 / OCR 回调，含全仓唯一的手工 JSON `{"amount":...}`）本就不带字段清单。
无条件按 fields 重建会把所有人工补录判成「不齐备」——那是把「收紧」做成「全量退补件」，
与 #25 的 MANDATORY 无端口同型。同时 `Evidence` 在 domain 层，引用 infrastructure 会直接触发
`domain_independent` ArchUnit 违规，故判定逻辑放在同层的 `EvidenceFieldReader`（本就是唯一解析入口）。

#### 验证

- `FieldCompletenessGateTest`(6) 全绿，含**成对正向钉子**：显式 `complete=false` 收紧、
  显式 `true` 保持、无标记回退、坏 JSON 回退、`FAILED` 状态闸不被标记绕过。
- **双向变异验证**：① `orElse(true)→orElse(false)`（过度收紧）→ 恰 2 条回退用例转红；
  ② 摘除 `complete` 收紧（恢复旧行为）→ 恰 2 条收紧用例转红；恢复后 RC=0。
- **真实 E2E**：`/parse-image` 端点可达（不存在的材料返回受控 404 而非路由 404），
  无 token 返回 401；门控默认关闭时不会伪造解析成功。

#### 诚实边界

验证的是「**数电票文本层**」子集的初审完整性，**不得**据此宣称 OCR+NLP 自动录入 / 影像分类 /
旋转纠偏已达成（需平台文档 IR 与真实 provider，Phase B）。

## GAP 登记 · `RUNTIME_MODEL_COVERAGE` 双条件「不同源」可伪造风险

> 登记轮次：第 11 轮循环复核（2026-11-07）
> 收敛轮次：第 14 轮（2026-11-07）
> 状态：**判据侧已收敛（方案 A）；采集侧待外部前置**——判据已要求 `probeEvidence` 自洽，但
> `/ai-provider-probe` 尚未返回 token / requestId，真实 provider 接入前该判据恒 BLOCKED（预期 fail-closed，非恒假）。
> 现状：`RUNTIME_MODEL_COVERAGE` = BLOCKED / `PROVIDER_NOT_CONFIGURED`，`l3Claimable=false`，L0。

---

### 一、问题：两个"条件"来自不同源，且都有一个可被书面伪造的入口

`RUNTIME_MODEL_COVERAGE` 要求三要素同时成立：

| # | 要素 | 读取来源 | 可否被"写"伪造 |
|---|---|---|---|
| 1 | provider 已配 | 环境变量 `provider_env`（如 `BONE_AI_GATEWAY_BASE_URL`） | ✅ 可：设个变量即"已配"（不含密钥是否有效） |
| 2 | 探活判词 `REACHABLE` | E2E 产物里的一个**裸字符串** | ✅ 可：手写一行 `probeVerdict=REACHABLE` 即"通了" |
| 3 | 运行期参与率 > 0 | E2E 产物 `participationRate` | ✅ 可：同样手写一个非零小数 |

也就是说：**三要素全部来自"可手写的产物 + 可设置的环境变量"，没有任何一项来自不可伪造的运行期事实**
（如真实 HTTP 200 + 真实模型返回 + 真实 token 计数）。这与本项目「判据不得以配置/文档字符串冒充能力就绪」
的红线（`第9轮-合理性判定矩阵` §业界实践依据、`ADR-生产数据库增量迁移策略` 同源纪律）**直接冲突**。

---

### 二、当前为什么不判红

`self_test` 已有反向探针覆盖了部分路径（`配置态全齐但探活失败 ⇒ 档位须为 L0`、
`配置态全齐但无 E2E 产物 ⇒ 档位须为 L0`），但这些探针验证的是「**缺**条件时是否正确降级」，
**没有**验证「三要素同时被书面伪造时是否仍会被识别」。前者是 fail-closed 探针，后者是
**伪造鲁棒性探针**，二者不等价。

---

### 三、精确修复方案（三个候选，推荐 A）

#### 方案 A（推荐）：让第 2、3 要素必须"同源可追溯"到一次真实调用记录

- E2E 产物不再接受裸 `probeVerdict` 字符串，改为要求 `probeEvidence` 对象：
  `{ "httpStatus": 200, "model": "<实际返回的 model 名>", "promptTokens": n, "completionTokens": m, "requestId": "<供应商侧 id>" }`。
- 判据改为：`httpStatus == 200 && model 非空 && (promptTokens + completionTokens) > 0 && requestId 非空`。
- 加校验：`requestId` 必须形如供应商真实格式（正则），且 `completionTokens > 0`（空返回 = 未真正跑模型）。
- **成本**：只改 `_ai_native_readiness.py` 与 `/api/v1/claim-ops/ai-provider/probe` 的产物字段（均在并行会话在途文件内）。
- **收益**：裸字符串伪造路径直接消失——要伪造必须同时伪造一个自洽的 token 计费记录，成本远高于收益。

#### 方案 B：把探活结果落到不可手改的位置（服务端内存/落库），判据只读服务端

- 探活由 `AiProviderProbeApplicationService` 执行后写入一个**服务端权威快照**（进程内存或一张 `t_ai_probe_snapshot`）。
- 判据只读该快照，不读文件产物。
- **成本**：需新表（L3 DDL 审批）或至少进程内单例 + 端点暴露；跨进程/多实例语义复杂。
- **缺点**：比 A 重，且多实例下"哪个实例的快照算数"要再定义。

#### 方案 C：最保守——把第 2 要素降级为"证据指纹"，只在自测里用

- 即：`probeVerdict` 不参与 L3 判定，只作为**运维可读的诊断信息**；L3 判定要求方案 A 的 `probeEvidence`。
- **成本**：最小；**缺点**：等价于方案 A 的严格子集，不如 A 直接。

**推荐 A**：改动面最小、把"可伪造字符串"换成"自洽的计费证据"、与业界（ML Test Score 的
"模型必须有真实推理证据"、NIST AI RMF 的 MEASURE 函数）一致。
