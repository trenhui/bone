## 三、需要评审拍板的 8 个决策点

每条给出「默认建议」与「反对方会怎么说」，供直接裁定。

| # | 决策点 | 建议 | 反对意见 / 代价 |
|---|---|---|---|
| **R1** | 3 个金额列改 JSON 的落名用 `*_rule` 后缀，还是**另建一张 `t_adj_liability_rule` 扩展表** | `*_rule` 后缀（同表 expand，回滚窗口内新旧代码可共存） | 另建表能彻底避免列名冲突，但引入一次 JOIN、且「责任」这个概念被劈成两张表，后续每次读都要拼装 |
| **R2** | 回填范围：只回填「能无损还原」的行，其余保持 `NULL` | 是（`NULL` = 业务未配，不编造） | 保持 `NULL` 意味着下游要处理「JSON 空」的情形，代码分支变多；补齐需业务提供默认值，成本高 |
| **R3** | 双写周期长度 | **1 个完整发版周期**（约 2 周），期间两套列都写 | 拉到 2 个发版更稳，但双写期间任何一侧写失败都会产生分叉，观察成本翻倍 |
| **R4** | 谁批准 ④ Contract（删列不可逆） | 需 **DBA + 架构 + 业务** 三方签字，且附「零读点」取证报告 | 只走架构签字更快，但删列事故不可逆，组织上应保留三方闸门 |
| **R5** | 是否加**租户级灰度开关**（部分租户先切新列读） | 是（本次迁移本身已是高风险，灰度能把爆炸半径缩到单租户） | 增加一个开关 = 增加一个「配了不生效」的面，需要同批出「开关状态可观测」的判据 |
| **R6** | 历史案件重算按**绑定版本**读旧列，还是按最新配置读新列 | 绑定版本（重算必须能回到当时那套配置，其余方案会让历史赔付额随配置变更漂移） | 绑定版本要求旧列在 contract 后仍可追溯 → 需要归档策略，否则删列即失去重算能力 |
| **R7** | 迁移窗口：在线（低峰执行）还是停机 | 在线低峰（expand 与 contract 都是 DDL，MySQL 8 支持 `ALGORITHM=INSTANT` 加可空列；migrate 是纯 `UPDATE`，分批提交） | 在线执行需控制批次大小与主从延迟；停机最稳但业务不接受 |
| **R8** | 是否先在 staging 做**全量克隆演练**（含脏数据探测） | 是，且演练脚本与生产脚本**同一份**（不接受「演练版」与「生产版」两套） | 演练环境数据量小，可能测不出锁表/延迟问题；需明确「演练通过 ≠ 生产安全」 |

2. **读点清单（按读取点取证）**：全仓谁在读 `pay_percent` / `liability_deduct` / `liability_limit`。
   2026-11-08 实测：`Adjustment.apply()`（`:430-444`）用 `LiabilityRule.fromLegacy(...)` 读三个标量列，

   **切读会直接改变运行时赔付计算**，「影响面可能很小」的推断不成立，双轨比对是硬闸门。
3. **回滚演练记录**：② 阶段影子列清空重跑、③ 阶段切回旧列读，各做一次并留证据。

## 五、前置问题已核销（2026-11-08，以代码为准）

**原断言不成立**。本节原写「`AdjustmentEngine` 全仓没有调用点、`liabilityLimit` 无引擎外读取方、`t_adj_liability` 金额列不参与运行时赔付计算」，并据此要求「路 A 先接线引擎 / 路 B M2 定位为结构收敛」二选一。按 `bone-apps/synap-claim` 代码复核，三条断言均与事实相反：

| 原断言 | 实测 |
|---|---|
| 引擎零调用点 | `Adjustment.java:459` 在 `apply()` 内直接调 `AdjustmentEngine.calculate(Request)`；入口 `AdjustmentController` → `IndemnityApplicationService` → `Adjustment.calculate`（`/adjust`、`/adjust/recalculate`），另有 `ClaimInternalOpsController` 的 preview / recompute 两条 |
| 金额列不参与运行时计算 | `Adjustment.java:430-444` 用 `LiabilityRule.fromLegacy(...)` 把 `pay_percent` / `liability_deduct` / `liability_limit` 映射进引擎入参；`AdjustmentEngine.java:1429` 用 `liabilityLimit` 控额，`InvariantGuard` 同式校验 |
| 只是「设计态收敛」 | 改动会直接改变赔付额；M2 属**资金核心变更**，风险定级维持「高」 |

**结论**：路 A / 路 B 二选一撤销，「先接线引擎」不再是 M2 前置。M2 的价值重新定义为**让九要素可配置**（分段比例、多子维免赔、控款方与次数限额），不是「让配置进入赔付计算」。D3 已拍板 **B：配置与引擎并行**——M2（数据形态）与 M4（算法结构）在冻结的 SDK 契约下并行，经 `LiabilityRule.fromLegacy(...)` 适配层隔离，切读与策略切换不得同窗口发版；纪律见《总体技术方案》§9.1。

**取证方法**（通用规则见 `方法论-能力取证.md`）：按读取点扫完整调用链，不按类/字段的声明处下结论。本次误判源于只统计 `AdjustmentEngine` 类型的直接引用，漏掉聚合内部对静态 `calculate` 的调用。R1–R8 与开工前三项证据仍待评审拍板。
