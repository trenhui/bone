# 理算引擎诊断记录（两轮取证，2026-10）

> **本文是过程记录，不是当前设计**。它记录"曾经实测到什么缺陷、怎么修的、凭什么证明修住了"——时效性材料，结论已回写《理算引擎设计》与《理算引擎验证套件》。读者若只想了解引擎现在长什么样，请直接读设计篇；本文的价值是**证据链**：任何一条护栏，都能追到它当初是为了堵哪个实测缺陷。

> **方法**：不看文档宣称，先写诊断探针打印实测值，再与业界正解比对；坐实后才修。tpa-saas 原代码未做任何改动，`bone-tpa-intelligent-adjustment` 作为 proven 基线被复用。
>
> **可复现**：`reference-impl/synap-claim-settlement/src/main/java/.../diag/Diagnostics2.java`（第二轮）；`mvn test` 覆盖 `ProbeSuite` / `ScenarioSuite` 全量。

## 1. 为什么"全绿"之后还要再查一轮

第一轮的结论是：18 条探针全绿、10 类变异全被捕获、20 个场景全通过。这是典型的"看起来已经很充分"。

但"全绿"只证明**已写出的探针**有判别力，不证明**没写出的维度**没问题。第二轮刻意去找"没有对应探针的维度"，又坐实 10 项缺陷（含 4 个 P0）。结论：**防假绿不是一次性动作，而是持续取证**。

## 2. 第一轮：实测取证（修复前）

| 编号 | 输入 | 引擎实测 | 业界正解 | 判定 |
|---|---|---|---|---|
| D1 | 费用 20000 / 比例 80% / 年免赔 10000 | **6000** | **8000** | ❌ 免赔额错序（系统性少赔 25%） |
| D2 | 费用 1000 / 发票免赔 5000 / 比例 80% | **−3200** | **0** | ❌ 产出负赔付金额 |
| D3 | 同案重复提交两次 | 首 6000 → 重复 **16000** | 两次均 6000 | ❌ 幂等缺失，免赔双计（超赔 2.7 倍） |
| D4 | 同 policyId、不同 tenant，年限额 1000 | T1=1000 / T2=**0** | 各 1000 | ❌ 跨租户额度串用 |
| D5 | 比例 95% + 已确认 AI 加成 10% | **1050** | **1000** | ❌ 比例破 100% |

D1–D4 属 P0：直接造成少赔/超赔/负金额/数据隔离违规，任一进入生产都是资金事故级缺陷。且四项都发生在"看起来最基础的语义"上——正是"文档写对了、代码没做对"的典型。

### 2.1 缺陷清单与根因

| # | 缺陷 | 根因 | 业务后果 |
|---|---|---|---|
| D1 | 免赔额**后置于**比例（`赔付额 − 免赔`） | 把"保单级年度免赔（作用于费用基数）"错当"赔付额减项" | 少赔 25%，规模化即巨额少赔 + 客诉 + 监管风险 |
| D2 | 免赔 > 费用时产出负赔付 | `(current − deduct) × ratio` 后未做非负钳制 | 负金额进付款/对账链路，清算失败 |
| D3 | 重复提交双计免赔与限额 | 无幂等键，`commitUsage` 每次无条件累加 | 6000 → 16000；重试/双提交/消息重投均会触发 |
| D4 | 累计键与控额键不含 `tenantId` | 键仅 `policyId@periodKey` | 不同租户同保单号互占额度，SaaS 红线 |
| D5 | 比例可破 100% | AI 加成无上限，护栏本身失守 | 超赔 |
| D6 | 不可获利原则缺失 | 社保统筹/他险已赔未从基数扣除 | 理赔获利（1 万费用、统筹付 5000 仍赔 8000），重复理赔通道 |
| D7 | 反欺诈未接入理算 | 决策图有 `FraudScreen` 节点，引擎无 fail-closed 入口 | 高风险案件照常出金额并占额（"配了不生效"） |
| D8 | 跨案累计读-改-写竞态 | `getUsage → 计算 → commit` 无版本约束 | 并发双计、超赔 |
| D9 | 预授权按 100% 授权且无生命周期 | 无 hold/capture/void/TTL | 院端直付额高于结算额，差额向患者追收 |
| D10 | 拒赔仍消费控额；状态机无 HOLD | 拒赔未短路；状态枚举缺挂起态 | 拒赔案占用额度，影响后续真实赔付 |

### 2.2 修复与回归证明

| 修复 | 做法 | 回归证明 |
|---|---|---|
| 免赔额作用于费用基数 | 年度免赔在可赔基数上按行比例分摊（末行取残差保守恒），再乘比例；开关 `deductibleBeforeRatio` | P16（关掉 → 6000 → 红） |
| 负赔付钳零 | `Money.clampNonNegative()` 取整前强制，**非开关** | P3b |
| 比例 ≤100% | `Money.clampMax(100)`，AI 加成后生效；开关 `clampRatioAt100` | P15 |
| 幂等键 | `claimId + 公式指纹 + 输入指纹`；开关 `applyIdempotency` | P12 / S19 |
| 租户隔离键 | 累计键/控额键统一加 `tenantId@`；开关 `tenantScopedKeys` | P13 / S20 |
| 乐观锁累计 | `commitUsage(..., expectedVersion)` → `COMMITTED/DUPLICATE/CONFLICT`，冲突转人工 | P18 |
| 不可获利 | `thirdPartyPaid` 先从基数扣除，`explain` 标注 `PRINCIPLE_INDEMNITY`；开关 `applyIndemnityPrinciple` | P14 / S17 |
| 风控 fail-closed | `fraudHold` → `HOLD`，不出金额、不调用占额端口、不消费累计 | P17 / S18 |
| 保守比例授权 | 授权额 × 最低赔付比例 | S16（15000@80% → 12000 而非 15000） |
| 预授权生命周期 | `PreAuthPort`：`hold(ttl)` → `capture` → `void` → `isExpired` | S15 |
| 状态机补全 | `PAY / PARTIAL / REJECT / HOLD`；拒赔与挂起均不消费控额 | — |

## 3. 第二轮：在"全绿"之上再取证

| # | 场景（输入） | 引擎实测 | 业界正解 | 级别 | 为什么是问题 |
|---|---|---|---|---|---|
| **N1** | 责任年限额 5000，同责任两案各 4000 | 首案 4000 / 次案 **4000** | 次案 1000 | **P0 超赔** | 责任限额只做单案内 min，未跨案累计。年度免赔/年限额都做了累计，唯独漏责任维度——维度覆盖不完整 |
| **N2** | 年额度 1 万，首案 6000；补交发票重算 8000 | 重算净付 **4000**，占用仍 6000 | 净付 8000，占用 8000 | **P0 少赔 + 账实不符** | 幂等键含输入指纹（视为新请求），但累计按 claimId 只做"首次锁定"，旧占用不冲正 |
| **N3** | 年限额 1 万，3 次直付预授权各预估 6000 | 累计授权 **18000** | ≤ 10000 | **P0 超授权** | 预授权不进 `frozen`；多科室分次授权可突破年限额 |
| **N4** | 责任限额 5000（已用 3000），预估 10000 | 授权 **5000** | ≤ 2000 | P1 | 预授权读总额而非剩余，与 N1 同源 |
| **N5** | 费用全部丙类（目录外），预估 8000 | 授权 **8000** | 0 | P1 | 无可赔费用时保守比例回落到 100% |
| **N6** | 费用含丙类 500（拒赔） | 拒赔行 `deduct=500` | `deduct=0` | P1 | 告知书写"您的免赔额 500"，实为"不在目录内"，语义错误易致投诉 |
| **N7** | 同请求并发提交两次 | 有窗口，无租约 | 第二个 fail-closed | P1 双占额 | 顺序被幂等挡住，并发两请求可同时 `find(null)` 通过 |
| **N8** | 后督改判/撤件 | 只有 `commitUsage`，无 reverse | 可回退占用 | P1 额度永久虚耗 | 撤件后额度不释放，客户后续理赔被错误拦截 |
| **N9** | 3 个费用项各 1000，比例 33.333333% | 逐行合计 **999.99** | 1000.00 | P1 对账不平 | 逐行取整与总额取整差 1 分；须最大余数法配平 |
| **N10** | 产品**未配置**费用子限额（`feeSubLimit=0`），费用 1000 / 80% | 净付 **0.00** | 800.00 | **P0 静默少赔** | `0` 在主流产品配置中语义是"该维度不限制"，引擎当成"限额为零"→ 全额拒付 |

### 3.1 N10 为什么最危险：被测试数据掩盖的假绿

N10 的根因极简单（`LimitControl` 把 `0` 当成真实限额），但**第一轮 20 个场景用例全部通过**——因为构造测试数据时所有 `feeSubLimit` 都"恰好"传了大额（`1_000_000`）。**没有任何一条用例传入 0**，缺陷从未被触发。

这暴露了防假绿最需警惕的形态：

- 探针全绿 ≠ 覆盖完备；**测试数据的分布**本身可能系统性绕开缺陷；
- 判据应是"**边界值是否被覆盖**"，不是"用例数是否够多"；
- 修复动作：补 P28（`feeSubLimit=0` → 期望正常赔付）+ S25，并配 `zeroIsLimit` 变异开关。

### 3.2 修复与回归

| 缺陷 | 修复 | 业界基准 |
|---|---|---|
| N1 | `AccUsage` 增 `liabilityUsed`；责任维度纳入跨案累计 | Guidewire Accumulation / ISO 责任限额 |
| N2 | 结论自携带占用信息；重算前 `accumulation.reverse()`；`commitUsage` 改按 claimId upsert | Guidewire recalculation / reversal |
| N3 | `AccUsage` 增 `frozen`；可用额 = `annualLimit − limitUsed − frozen` | ACORD 三值额度 |
| N4 | 预授权用剩余责任限额 | 同上 |
| N5 | 无可赔费用 → 保守比例 0 | 直付网络追收风险治理 |
| N6 | 拒赔行 `feeDeduct=0`，原因由 `rejectType` 单列 | 客户告知书合规 |
| N7 | `SettlementStorePort.tryBegin()` CAS 租约，取不到即抛异常 | 幂等租约 |
| N8 | `AccumulationPort.reverse()` + `reverseSettlement(prev)` | Guidewire reversal |
| N9 | 最大余数法 `apportionRounding()` 配平 | SOX/NAIC 可复算 |
| N10 | 限额非正 = 维度未配置，**不进入控额维度** | tpa-saas 与主流配置惯例 |

## 4. 两处"正确引擎转红"的处理（值得留档）

过程中两次出现"正确引擎被判红"，都按**真缺陷**处理而非改测试预期：

1. **P21 首次未绿** → 定位到"剩余额度为 0 时用 `isPositive()` 守卫反而跳过该维度"，修正为"维度已配置即参与取交"。
2. **`rejectDeductPollution` 变异逃逸** → 定位到护栏被写成了常量（用了 `rejected` 而非开关），修正为正确挂开关。

> 教训：**测试失败先怀疑实现，再怀疑测试**；同时要检查"开关是否真的挂上了"——挂了常量的护栏等于没挂，且会伪装成"已验证"。

## 5. 已知限制（诚实披露，未做）

1. **第三方已付归因粒度**：当前按可赔基数比例分摊；生产应按费用类别归因（社保内优先核销），需条款确认。
2. **年度限额截断顺序**：按费用行顺序先到先得，未按比例摊薄；多费用类型并存时需条款确认优先级。
3. **多保单分摊（S13）仅独立理算**，未实现 ISO 834 的 pro-rata by limit / 等额分摊，需产品确认条款后另开工。
4. **生产落库未做**：幂等存储、累计、快照在参考实现为内存实现；生产需幂等唯一键、`@Version` 乐观锁、快照表。
5. **无真实数据库级并发压测**：P18/P25 仅验证乐观锁与租约契约及 fail-closed 行为。

- 权威编排顺序以《理算引擎设计》§4 为准，缺陷语义口径以该文 §5/§8 为准；
