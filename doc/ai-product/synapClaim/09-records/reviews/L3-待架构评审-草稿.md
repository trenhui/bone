## #10 评审材料补充（2026-11-04，仅补事实与选项，不含任何实现）

> 本节为**双签决策包**：把「要不要让映射域偏离全仓软删」从一句原则，收敛成可核对的事实、可比较的选项、可勾选的结论。
> 依据均为本轮对 `bone-init.sql`（DDL 真源）、8 张映射表实体、参考态 V20/V22、生效通道 0112/0120 与开发库 `bone` 的逐项复核；**未改任何 SDK 代码、未改活库结构**。

### 一、先纠正三个会误导评审的事实

| 常见理解 | 复核后的事实 | 证据 |
|---|---|---|
| 映射表「没有 deleted 列」，所以 SDK 读取会炸 | 8 张表**都有** `deleted TINYINT NOT NULL DEFAULT 0`，DDL 注释明写「映射只关闭不删除，该列恒 0」；实体用 `status` 表达生命周期，不等于表里缺列 | `bone-init.sql` 8 段建表；活库 `information_schema.columns` 列集合与 init 完全一致 |
| `active_flag` 是待补的布尔开关 | 现网是 `CHAR(1) DEFAULT NULL`，取值 'Y' / NULL；`uk_active (..., active_flag)` 靠「唯一索引允许多 NULL」让历史行不占槽位、同键至多一条 'Y'。上方迁移草稿的 `TINYINT(1) NOT NULL DEFAULT 1` 与之冲突，已标注作废 | `t_claim_code_mapping` DDL + 活库 `information_schema.statistics` |
| 这是「单模块想省事」的例外申请 | 偏离已是既成事实且已随 0112/0120 进入生效通道：8 张表、`status` 生命周期、`uk_miss` 刻意不含 status、`active_flag` 可空哨兵语义都在生产路径上。评审对象是「是否给既有事实一个合法的契约位置」 | 生效通道 0112 / 0120；`ClaimInsurer`、`StdCodeSplit`、`StdCodeAlias` 实体 |

### 二、三个选项（爆炸半径由小到大）

| 方案 | 具体改动 | 影响面 | 回滚方式 | 主要风险 |
|---|---|---|---|---|
| **A 显式例外（建议）** | SDK 基类**不动**；在《数据库开发规范》与 SDK 契约附录登记这 8 张表为「status 生命周期域」，补单测锁定三不变量（deleted 恒 0 / uk_active 含 active_flag / uk_miss 不含 status），并把例外写进 ArchUnit 白名单说明 | 零 DDL、零 SDK 改动；仅文档 + 单测 | 改文档/删单测 | 例外被后人当范例扩散 → 靠白名单注释 + 门禁说明收敛 |
| **B SDK 提供可选开关** | 新增类似 `@NoSoftDelete` 的可选注解，实体显式声明不继承软删语义；重跑全仓实体回归、软删拦截器用例、ArchUnit 基线 | 全仓框架契约变更（L4），所有实体回归 | 需新版本 SDK + 回滚发布 | 收益是例外有类型系统承载，成本与回归面最大 |
| **C 收敛回全仓软删** | `status` → `deleted`，改 8 张表 + 全部查询 + 唯一键语义；`active_flag` 的 NULL 技巧需重写 | 8 表 DDL + 全链路查询 + 数据回填 | 需反向迁移 | 「同键至多一条生效」从数据库保证退化为应用层判定，资金/映射正确性风险最高，**不建议** |

**建议 A，暂缓 B，明确否决 C**：A 零结构变更即可消除「文档说一套、代码做一套」；B 值得立项但应由 SDK owner 排期，不该由理赔模块夹带；C 会拆掉 0112/0120 刚锁定的数据库不变量。

### 三、需要双签人明确勾选的结论

1. 选 **A / B / C**（默认按 A 执行；选 B 需给出 SDK 版本与回归范围，选 C 需附风险接受书）。
2. 若选 A：例外清单登记位置与长期 owner（建议《数据库开发规范》§3「模块前缀」后新增「生命周期例外」小节，owner = SDK owner）。
3. 统计口径：审计/监控报表对这 8 张表按 `status` 还是 `deleted` 计数——目前两者语义不同（恒 0 vs 生命周期），不指定就会出现「统计真空」。
4. 白名单是否允许「后续新表」复用此例外（建议否：新增一张表就重新走一次双签）。
