# synapClaim 生产就绪完善包 · 总纲与 Go-Live 门禁

> **定位**：本包（子目录 `生产就绪完善（业界最佳实践）/`）是对《工程落地版》SSOT 的**伴随式完善**，不修改 SSOT 既有权威章节。它把 `outputs/synapClaim-生产就绪独立诊断.md` 识别出的真实缺口，按业界最佳实践落成为**可直接合入系统**的内容草案。
>
> **与文档族机检的关系**：既有四套机检（`_check_xref` / `_check_contract_drift` / `_check_ddl` / `_check_numbers`）扫描根目录与 `delivery/` 固定文件，本包置于子目录，**不会触发也不会破坏既有 CI 门禁**。本包内的 `《工程落地版》 §X` 引用均指向已核实存在的章节号（§3.3 / §6.6 / §7.3 / §7.5 / §7.6 / §9.5 / §10 / §11.3 / §11.4 / §11.6 / §11.7 / §11.8 / §11.9 / §12.2），作为人工合入时的定位锚。
>
> **合入节奏**：建议在下一轮文档整合（P8）时，将各分册"可落地内容"折叠进《工程落地版》对应章节，并把"Go-Live 门禁"并入 §12.2 验收清单。折叠时须同步更新 `_check_numbers.py` 的 REQUIRED/FORBIDDEN（如将"AI 算法备案 0 命中"转为 REQUIRED 在位口径）。

## 二、Go-Live 发布门禁（A 阶段阻断级，9 项带 owner/到期/验收）

> 门禁原则：**任一项未闭环，不得对正式客户投产**（试点/Shadow 不受此限，见 §11.4 三态开关）。
> Owner 角色：交付组、安全合规、架构、平台（bone-ai）、业务（理赔运营）。
> 到期以"MVP 里程碑"相对计：I4=灰度试点完成；Phase B=Assisted 放开；Phase C=Automated 放开。

| # | 门禁项 | 来源 | Owner | 最晚时点 | 验收标准（可证伪） |
|---|---|---|---|---|---|

## 三、本包与既有治理机制的衔接

1. **ADR 可追溯**：本包新增任何设计决策，若需固化为架构决策，应在《工程落地版》§14 ADR 索引登记（沿用"ADR 生效状态表：Accepted ≠ 已实现"纪律），不得仅在分册内自说自话。
2. **宣称态 vs 实现态分线**：本包内容一律标注"目标态/待落地"，不与《工程落地版》§12.2.1"能力已落地但触发入口未建"的登记口径冲突；折叠进 SSOT 时须保留该分线。
3. **机检扩展点**：折叠时建议把以下新定型口径加入 `_check_numbers.py`：
   - REQUIRED：`AI 算法备案` 章节在位、`外部依赖 SLA 矩阵` 在位、`支付未知态处置` 在位、`租户隔离 ArchUnit 规则` 在位（✅ 该规则已落地于 `ArchitectureTest`，折叠时转为在位口径即可）。
   - FORBIDDEN：合规项仍写为"待建"且无 owner/到期（防债务固化）。
4. **不重复造轮子**：资金安全（§7.5）、四向对账（§11.7）、租户设计（§3.3）、WORM 审计（§11.3）、MRM 模型卡（T6/BONE-AI 增强）等**已扎实的护城河本包不触碰**，只在缺口处补强。

## 四、使用方式

- 评审者：按本总纲 §二 门禁逐项核对 `bone-apps/synap-claim` 与交付进度，未闭环项标红。
- 开发/交付：按各分册"可落地内容"执行，执行后回填本总纲 §二 验收列。
- 折叠负责人（P8）：将分册内容并入《工程落地版》对应章节，删除本伴随包冗余，保留总纲作审计轨迹（或归档至 `archive/`）。
