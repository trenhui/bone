> 定位：承接《14-主链路闭环体检》§四 第 4 项——**先建读侧、跨案用例先红、再接 A7 写侧**。

## 一、先更正 14 分册的一条事实

《14》称 `QuotaApplicationService` **0 调用方**、额度账"没人读写"。该判断**不成立，已撤销**。

| 断言 | 实测 | 结论 |
|---|---|---|
| `QuotaApplicationService` 无调用方 | `SettlementApplicationService` 有 4 处（`reserve` / `confirmPay` / `release` / `refund`） | 个人账 `PERSONAL` **有完整读写** |
| `capUsed` 有写无读 | 全仓除 `QuotaAccount` 自身外无读写点 | 属实（`R-CAP` 封顶仍未接线，见 §六） |
| 免赔/责任限额每案从满额重算 | `Adjustment.apply` 入参无任何"已用"量；`liability.deduct()` / `liability.limit()` 取配置值 | 属实，本册修复 |

**真实缺口的精确表述**：A7 只占 `PERSONAL` 一本账，`loadPersonal` 硬编码 `"PERSONAL"`；**责任账（`LIABILITY_CAP`，按 `liability_uuid` 分行）与免赔累计全程空转**。缺的不是"调用方"，是"第二本账的读写两侧"。

## 二、四本账的现状（改前 / 改后）

| 账本 | 载体 | 改前 | 改后 |
|---|---|---|---|
| 费用账 | `t_adj_calculation_line` | 有 | 有（仍单行汇总，见 §六） |
| 额度账（个人） | `t_quota_account` `PERSONAL` | 有读写 | 不变 |
| 额度账（责任） | `t_quota_account` `LIABILITY_CAP` | **有表无读写** | **A6 读 + A7 写** |
| 免赔账 | 同上 `deductible_used` | 有字段无读写 | **A6 读 + A7 写/退** |
| 资金账 | `t_settlement_order` | 有 | 不变 |

为什么**不另立"累计表"**：多一本账就多一次对账，而"四本账对不上"正是这类系统最难查的资金事故。责任限额的 `claimed+frozen` 与年度免赔的 `deductible_used` 天然同属"某被保人 × 某保单 × 某计划 × 某年度 × 某责任"这一维度，共用一张表、一套三值模型、一套守恒校验即可。

## 三、实现（读侧 → 内核 → 写侧，顺序不可颠倒）

### 3.1 读侧：`AccumulationPort` + 真实适配器

```
application/port/out/AccumulationPort.java           ← 端口（返回 Accumulation，不是两个 BigDecimal）
domain/model/adjustment/Accumulation.java            ← 快照值对象（available 是 fail-closed 信号）
infrastructure/quota/QuotaDrivenAccumulationPortAdapter.java  ← 读真实 t_quota_account
```

三个设计取舍，每个都有对价：

| 取舍 | 为什么 | 反面代价 |
|---|---|---|
| 累计量**显式入参** `Adjustment.calculate(..., Accumulation)`，内核不查仓储 | 理算必须"同输入同输出"才可复算；查仓储会把它变成依赖基础设施的可变对象 | 所有调用点签名变更（本次改了 12 个测试文件），但**缺失即编译不过**，杜绝"默认 0" |
| `limitUsed = claimed + frozen` | 只算 `claimed`：两案先后理算、都未支付时，后案仍看到"零占用"⇒ 照样超赔（参考实现诊断 N3 的成因） | 需要保证 `frozen → claimed` 不双记（`QuotaAccount.confirm` 已按内部转移实现，测试锁定） |
| 缺账户返回 `available=false` 而非"已用 0" | 未开户与"确认为零"在数值上不可区分；伪造零 = 把超赔风险藏进默认值 | 上层必须分两处处理：A6 只标记、A7 拒绝占额 |

`available` 的两级用法是本册最关键的语义切分：

- **A6 理算**：不阻断（结果还要给人看），但把 `accumulationAvailable` **物化进快照**并告警；
- **A7 结算**：`if (!adj.accumulationAvailable()) throw 422` —— 资金路径不允许在账实不明的账本上记账。

### 3.2 内核：只改两行减法，加一处归因

```java
// Adjustment.java:244  免赔扣"剩余"而非"配置全额"
BigDecimal deductible = accumulation.remainingDeductible(deductibleConfigured).min(base);

// Adjustment.java:255  限额截"剩余"而非"配置满额"
BigDecimal limitRemaining = accumulation.remainingLimit(limit);
```

两处 `max(0, 配置 − 已用)` 的钳制在 `Accumulation:52/62`——钳到 0 而不是取负数，因为"负免赔"会反向放大赔付基数、"负限额"会变成无限额。

新增零赔付归因 `ZERO_LIMIT_EXHAUSTED`（`Adjustment:272`，原因码仍映射 `09`）：拒赔五要素要求事实认定能说清是"**本次超限**"还是"**本年度用尽**"，两者对客户的解释完全不同。

快照新增四个物化字段：`deductibleBefore` / `deductibleUsedBefore` / `limitUsedBefore` / `accumulationAvailable`。**只存"本次扣了多少"而不存"扣之前已用多少"，历史案件复算时就无法区分"首案扣 1 万"与"次案扣 5 千"**。

### 3.3 写侧：A7 补上第二本账

```
SettlementApplicationService.create      → reserveLiability（额度软占 + 免赔消抵回写）
SettlementApplicationService.pay         → confirmLiabilityPay
SettlementApplicationService.cancel      → releaseLiability（额度归还 + 免赔回退）
SettlementApplicationService.refund      → refundLiability（已付回冲 + 免赔回退）
```

两条纪律：

1. **免赔与额度分两条流水落**（`claimNo:DEDUCTIBLE:{attempt}` vs `claimNo:LIABILITY_SOFT:{attempt}`）。二者幂等周期不同——重算改金额但免赔不一定改；合成一条，"重算后免赔没回退 / 回退了两次"这类差异无法从流水里查出来。
2. **只还额度不还免赔 = 客户白消化一笔没赔出去的免赔**。撤件、拒赔、支付失败三条路径都必须同时回退，故 `releaseLiability` / `refundLiability` 把两者绑在同一事务内。

`reserveLiability` / `releaseLiability` 用 `REQUIRES_NEW` 与 `reserve` 分属两个事务：CORE-06"一事务一聚合"，额度账户与结算单不是同一个聚合。

## 六、尚未动的（明确交接，不含糊）

| # | 缺口 | 证据 | 为什么本轮不做 |
|---|---|---|---|
| 1 | 理算**只产 1 条 OUTPUT 行** | `Adjustment.apply` 把全部费用行聚合成单个 `base`，`lines` 只 add 一条 | 逐行归因牵动 `AdjustmentLine` 表结构与分账守恒（`Σ行=total`、`public+individual=total`），属独立改动；单行下守恒校验没有判别力，先做会得到一条测不出东西的断言 |
| 2 | `cap_used`（R-CAP 封顶）仍无人读写 | 全仓除 `QuotaAccount` 自身无引用 | 封顶语义与责任限额在"是否跨责任共享"上不同，需产品口径确认，不能照抄 `LIABILITY_CAP` |
| 3 | `quota_year` 用自然年而非保单年度 | 读写两侧均 `Year.now()`；DDL 注释写"按保单年度" | 切保单年度需保单快照提供生效日；**读写必须同批切换**，单边改动会让两本账立刻对不上。本轮先把 DDL 注释改成与实现一致（`V9`），消除"注释宣称 X、代码做 Y" |
| 4 | 责任配置仅 5 个标量 | `AdjLiability` 只有 `payPercent/deduct/limit/socialOnly/waitingPeriod`；`waitingPeriod` 无读者 | 六维免赔 / 11 因子 / 后付责任链需要配置 schema 与目录编码匹配，工作量在 10–15 人日量级 |
| 5 | 无历史案件金额回归门禁 | 有 300 条评测集（字段/命中），无 book-of-business regression | `formula_snapshot` 已自包含可复算，能力现成，只差做成发布门禁 |

## 七、给下一轮的两条提醒

1. **`spotless:check` 会伪装成"测试红/测试绿"**：变异验证与基线验证都必须先确认测试真的跑了（看 `Tests run:` 行数是否与基线一致），否则 `BUILD FAILURE` 会被误读成"变异被杀"。
2. **Zsh 下 `grep "a\|b"` 不可靠**：本机为 BSD grep，`\|` 不生效，多次导致"证据为空"的误判。查多点位一律用 Grep 工具或 `grep -E`。
