# 17 控额层接线修正与多「次」闭环（把死配置变成「生效或拒绝」）

> **依据**：V1 §1.2 / §7.2 / §7.3，及本文自检发现的实现空洞。
> **实施日期**：2026-10-30。**前序**：`16-理算引擎V1重建`。
> **验证**：`synap-claim` 全量 **346 tests 绿**（含 26 条架构门禁）；**8 项变异全部被对应用例抓到**。

---

## 1 一句话结论

16 号文档宣称的「七层控额」在代码里**只有三层真实接线**：`次限额 / 险种 / 计划 / 共保` 四个额度字段被声明、被校验，却**从未被任何算式读取**。
这不是"少实现一个特性"，而是**配了不生效**——最危险的一类缺陷，因为配置、文档、评审三处都显示"已支持"，只有赔付金额是错的。

本轮把这类字段全部收敛为两条路：**要么真的生效，要么装载期拒绝**，不允许第三种状态。

---

## 2 证据：四层额度是死配置

```bash
$ grep -rn "occurrenceLimit()\|productLimit()\|planLimit()\|sharedLimit()" src/main/java \
    | grep -v "LiabilityRule.java"
（无输出）
```

`LimitSet` 里四个字段，除 `LiabilityRule` 自身（声明 + 校验）外没有任何读取点。对应的后果：

| 死配置 | 语义 | 不生效的后果 | 何时被发现 |
|---|---|---|---|
| `occurrenceLimit` 次限额 | 每一次赔付的上限 | **超赔**（每案按全额赔） | 计划总额被穿透时 |
| `productLimit` 险种额度 | 险种跨案总额 | **超赔** | 同上 |
| `planLimit` 计划额度 | 计划跨案总额 | **超赔**，且是最高层兜底 | 财务对账时 |
| `sharedLimit` 共保额度 | 多责任共享池 | **超赔** | 同上 |
| `personalLimit` + 方式 1/2/3 | 个人额度 | **超赔**（该方式无消耗路径） | 同上 |

单案上全都"看起来对"：每笔都不超责任额度，加起来却超了险种/计划。这正是七层存在的理由。

## 3 本轮六项修正

### 3.1 次限额真正接线（层③）

`QuotaStack.Demand` 增加 `occurrenceCap`，在 `cap()` 入口**统一预截断**：本「次」总额超限时按各组原额等比压低，再进入分组/逐层逻辑。

为什么不放进 `layers` 列表：两种扣减方式（求和后截断 / 逐组顺序消耗）若各自实现，必然出现"方式 1 生效、方式 5 忘掉"；更糟的是方式 4/5 若把它放到池消耗之后，个人/责任池会被**截断前的金额**占用，多占的额度不会退。一处实现，两条路径都覆盖。

顺序上它在层④共保、层⑤责任之前（V1 §7.2），因此不会用未截断的金额去占用责任额度。

### 3.2 次限额「每组各一份」，责任额度「全案一本账」

两者混用会一个多赔一个少赔，故在类型上分开：

- `occurrenceCap` 每次分组都从**配置额度**起算，不进入跨组账本（否则第二个「次」一分不赔）；
- `liabilityRemaining` 保留在 `MutableQuotaPool` 跨组递减（否则每组重置一次 ⇒ 赔出 N 倍责任额度）。

用例 `liabilitySharedAcrossOccurrences`：两个「次」各 400、责任额度 500 ⇒ **500**（若 800 即责任额度被每组重置）。
用例 `occurrenceLimitAppliesPerGroup`：两组各 400、次限额 300 ⇒ **600**（若 300 即对总额取了一次 min）。

### 3.3 「次」的分组维度缺失必须拒绝

`OccurrenceGrouper.requireDimensions`：配了「同日 / 同院 / 同科室 / 同病种」而明细缺该维度时抛 `OCCURRENCE_DIMENSION_MISSING`。

理由不是洁癖：分组键在维度缺失时退化成空串，全部明细落进一组，次限额只被应用一次 —— 两天各 500、次限额 300 会赔 300 而不是 600，**静默少赔**，且不会报任何错。
缺一个维度即整体拒绝（而不是"能分几组算几组"）：混合分组会把一张票拆成"有日期的组"和"日期未知的组"，后者白拿一次独立次限额。

配套新增 `AdjustmentEngine.calculate(Request, List<Fact>)`：调用方有分组维度时显式传入（下标须与明细一一对应，错位直接拒绝），不传则回落"一赔案一次"并受上面的闸门约束。

### 3.4 年度免赔跨「次」共享，按次免赔每组重置

`DeductibleLedger`：年度免赔在本次理算的多个「次」之间**递减**；按次免赔每组都取配置额。

修的是真实缺陷：此前每组各自 `resolveRemaining(rule, accumulation.deductibleUsed())`，第二组又拿到一份满额免赔 —— 多扣的钱直接变成客户少赔；且 `InvariantGuard` I4 会以 `IllegalStateException`（非业务异常）形式炸出来，把"口径错误"伪装成"程序缺陷"。

用例 `annualDeductibleSharedAcrossOccurrences`：两组各 8000、免赔 1 万 ⇒ 首组吃光 + 次组扣 2000 = **赔 6000、消抵 10000**。
用例 `perClaimDeductibleResetsPerOccurrence`：两组各 1000、每次免赔 500 ⇒ 各扣 500 = **赔 1000**。

### 3.5 上层额度必须给出「可用余额」来源

`险种 / 计划 / 共保` 都是跨案共享池，剩余额只能来自外部账本（责任额度就是靠 `accumulation.limitUsed` 做到的）。现在：

| 配置状态 | 行为 |
|---|---|
| 声明了额度 + `extraLayers` 给了可用余额 | 生效，且交叉校验 `可用 ≤ 配置`（不等即拒绝：两个数必有一个错） |
| 声明了额度 + 无可用余额 | `LIMIT_LAYER_UNDEFINED`，拒绝理算 |
| 只给可用余额（未声明额度） | 按余额截断（显式的外部账本入口） |

个人额度单独一条：`personalLimit > 0` 而扣减方式不是 4/5 ⇒ 拒绝（该方式没有个人额度的消耗路径）。

### 3.6 诊断落库

`Outcome.diagnostics` 此前只存在于内存返回值里，聚合外壳从不读 —— 生产环境一条也看不到，等于没报。现物化进 `formulaSnapshot.diagnostics`，与 `ratioHits / deductibleBranches / quotaSteps` 同级，可审计、可复算。

覆盖内容：三方已赔未扣、比例配置超 100% 被钳制、责任不承担的费用类型、socialOnly 剔除的金额、次分组数、票面负残差（无三方已赔时降级）。

### 3.7 三方重复赔付闸门（GAP③ 的一半）

逐行残差 = 发票金额 − (合理 + 不合理 + 三方已赔 + 自付二 + 总自费)：

- `valid_amount` 已按 §3.4 ① 扣过 ⇒ 残差 = 自付一 ≥ 0；
- 未扣 ⇒ 残差为**负**，缺口恰为被重复计入的部分。

**负残差 + 有三方已赔 ⇒ `INVOICE_SETTLEMENT_INCONSISTENT` 拒绝理算**（可证明会被再赔一次）；无三方已赔的负残差降级为诊断（数据质量噪声，不阻断）。

为什么只在这半边收紧：引擎擅自扣减会与票面结算对不上账；口径归上游，引擎只负责"发现不自洽就拒绝"。收紧范围限定在"有三方已赔"的案子上，正是重复赔付资金风险所在，误判时的爆炸半径可控。

## 4 变异验证（8 项，全部被抓）

| # | 变异（删掉实现） | 抓到它的用例 |
|---|---|---|
| M1 | `occurrenceCap()` 恒返回 null | `occurrenceLimitCaps`、`occurrenceLimitAppliesPerGroup` |
| M2 | 年度免赔不跨组共享（每组重读累计） | `annualDeductibleSharedAcrossOccurrences`（I4 抛错） |
| M3 | 按次免赔也走年度账本（不每组重置） | `perClaimDeductibleResetsPerOccurrence` |
| M4 | 上层额度来源不校验 | `declaredUpperLayerWithoutSourceRejected`、`availableExceedsConfiguredLayerRejected` |
| M5 | 分组维度不校验 | `missingDimensionFailsClosed` |
| M6 | 诊断不写快照 | `diagnosticsPersistedInSnapshot` |
| M7 | 三方重复赔付闸门不校验 | `doublePayDetectedByNegativeResidual` |
| M8 | 个人额度无消耗路径不校验 | `personalLimitWithoutSequentialModeRejected` |

> 过程中 M3 首轮"0 红"暴露的是**冗余分支**：账本 `consume` 里的 basis 判断被 `remaining()` 的同一判断遮蔽，属死代码。已删除冗余判断，再用"按次也走年度账本"的变异重验才转红 —— 0 红先怀疑变异没打到点，而不是先怀疑用例。

## 5 仍不做（及理由）

| 项 | 状态 | 理由 |
|---|---|---|
| 费用类型级免赔 × 多「次」 | **拒绝**（`DEDUCTIBLE_CONFIG_INVALID`） | Q-04：各类型免赔额度是否跨组共享未定义。按"每组满额"实现等于放大免赔，按"跨组递减"等于缩小，两种都是猜 |
| 共保池（`relation.sharedCode`） | 拒绝 | Q-02：池额度来源、耗尽回落、多池截断顺序均未定义；`sharedLimit` 单列配置可按 3.5 走外部余额 |
| 日限额 | 拒绝 | Q-05：主流程无判定点 |
| 第三方已付从 base 扣减 | 不做，改为闸门 | §3.4 ① 的口径归上游 `valid_amount`；引擎改了会与票面结算打架 |
| 逐行分位归因（GAP⑨） | 不做 | 需在 `t_adj_calculation_line` 增加明细维度列；当前每费用池 1 行已满足拒赔五要素 |
| 明细投影缺发票日期/医院/科室 | 不做 | 现由 `calculate(Request, facts)` 由调用方提供；投影扩列属另一变更（届时 `factsOf` 替换即可，分组算法不变） |

## 6 影响面

| 变化 | 兼容性 |
|---|---|
| `QuotaStack.Demand` 增加 `occurrenceCap` 字段 | 内部类，仅引擎使用 |
| `calculate(Request, List<Fact>)` 新增重载 | `calculate(Request)` 保留，行为不变（回落单组） |
| 上层额度声明但无来源 ⇒ 拒绝 | **行为变更**：此前静默忽略。现有旧配置（`LiabilityRule.fromLegacy`）只设责任额度，不受影响 |
| 年度免赔多组共享 | 仅影响多「次」分组场景（此前不可达，故无存量金额漂移） |

`LiabilityRule.fromLegacy` 未改动：旧四列配置依旧只映射责任额度 + 年度绝对免赔，**赔付金额与上线前一致**。
