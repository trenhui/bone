# 07 · 事件响应与 Runbook（IRP）

> **定位**：补齐 `outputs/synapClaim-生产就绪独立诊断.md` 盲区 **B2**。原独立诊断已识别"告警 35 处 + 混沌 CI + 季度演练"，但**告警是感知层、Runbook 是处置层**——金融系统上线强制要求"可执行的事故流程"，而非仅有指标。本册补全 Incident Response Plan（IRP）、on-call、严重级与常见故障处置手册。
>
> **业界基准**：等保 2.0 GB/T 22239-2019 8.1.4（安全事件处置）、ISO/IEC 27035（信息安全事件管理）、银保监/金监总局对银行保险机构**信息科技风险**与**业务连续性**的监管要求。

---

## 一、为什么是生产前置

| 现有覆盖 | 缺口 |
|---|---|
| 告警 35 处（Metrics/Trace 告警规则） | 告警触发后**谁来处置、按什么步骤、什么时限**无定义 |
| 混沌 CI（韧性验证） | 验证"会坏"，但未定义"坏了怎么 recovery" |
| 季度演练（声明） | 演练脚本与复盘（postmortem）机制未成文 |
| WORM 审计 | 无事故时间线留痕与责任追溯联动 |

> 结论：仅有可观测性不等于有事件响应能力。金融场景（尤其是涉及资金出款的理赔系统）上线前必须有**可执行的 IRP + on-call + Runbook**，否则一次支付故障/租户越权可能在无流程状态下演变为资损或监管事件。

---

## 二、IRP 框架（须建设）

| 组件 | 内容 | 验收 |
|---|---|---|
| **严重级定义（SEV）** | SEV1（资金差错/大规模租户越权/系统不可用）· SEV2（单租户资金异常/核心功能降级）· SEV3（非核心功能故障）· SEV4（轻微/无用户影响） | 各级有明确定义与示例（附本系统场景） |
| **on-call 轮班** | 7×24 主备值守，升级链：一线（SRE/研发）→ 二线（架构/领域 owner）→ 三线（安全合规/业务） | 轮班表 + 升级时延（SEV1 ≤ 15min 触达） |
| **事故生命周期** | Detect → Triage(定级) → Mitigate(止血) → Resolve(恢复) → Postmortem(复盘) | 每阶段有 SLA（SEV1：5min 响应 / 30min 止血 / 4h 恢复 / 3 工作日复盘） |
| **复盘（Postmortem）** | 无责复盘，含时间线、根因（5 Whys）、改进项（带 owner+到期） | 复盘模板 + 改进项入跟踪台账 |
| **事故时间线留痕** | 与 WORM 审计联动，事故处置操作可追溯 | 事故 ID 关联审计轨迹 |

## 三、常见故障 Runbook（须建设，金融理赔高频场景）

| Runbook | 触发信号 | 止血动作（摘要） | 升级路径 |
|---|---|---|---|
| **支付卡住 / 未知态** | 支付状态机停滞在"已指令未确认"超阈值（见 `02` §2.3 未知态处置） | 触发超时补偿（重试/冲正/人工介入），冻结该批次出款 | SEV1 → 资金 owner + 支付渠道方 |
| **租户越权 / 串号** | 租户隔离护栏（§4 守护）告警或审计发现跨租户访问 | 立即隔离会话、冻结涉事租户读写、回滚越权操作 | SEV1 → 安全合规 + 架构 |
| **LLM / 推理服务宕机** | bone-ai 推理端点不可用（G1 依赖） | 决策图降级到规则兜底（确定性分支），关闭自动化出款转人工 | SEV2 → 平台(bone-ai) + 业务 |
| **理算金额异常** | 理算结果与历史/预期偏差超阈值（F1 护栏告警） | 暂停自动化理算、回退人工复核、比对 `Adjustment` 聚合输出 | SEV1/SEV2 → 架构 + 精算 |
| **规则发布异常（防投毒，见 `08`）** | 规则加载验签失败 / 灰度指标恶化 | 拒绝加载未验签规则（fail-closed）/ 秒级回滚到上一已签版本 | SEV1 → 安全 + 架构 |

> Runbook 必须**可操作、带具体命令/接口/责任人**，而非原则性描述；每季度结合混沌演练更新一版。
