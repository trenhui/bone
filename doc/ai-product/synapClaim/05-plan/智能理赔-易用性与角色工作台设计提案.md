# 智能理赔 · 易用性与角色工作台优化方案

> v2.2 ｜ 2026-11-13 ｜ **性质：设计提案 + P0/P1 前端实现 + 后端联调契约 + 前后端真实联调均已落地并验证**
> 范围：信息架构（菜单体系）、角色分工、查询便利性、作业便利性、AI 深度融合
> 证据口径：以 2026-11-13 主工作树实测为准，关键结论均带 `文件:行` 定位，见文末「证据索引」
> **v2.3 增补（2026-11-13）**：见文末第十三章。v2.2 的菜单与导航结论**逐字未改**；本轮只补「作业台深度能力」——
> 任务分配与代理、独立复审、抽检打回、AI 自动初审配置面、统一查询契约，属**设计 + 文档交付，不改任何代码**。
>
> **v2.2 改判（本轮）**：用户实测反馈「菜单还是这么多、功能应该整合到一起」。复核 NN/g 隐藏导航
> 实验与 SAP Fiori / Guidewire 形态后，**撤回 v2.0「侧栏折叠四空间」与「侧栏一律不动」两条口径**：
> ① 功能整合发生在**对象层**——6 个单案作业页拆成无壳内容组件、内嵌为案件 360 的 Tab，
> 一次进入案件后不再手输 18 位 ID；② 导航层给 15 条菜单加**常驻可见**的四空间分组标题
> （作业 / 查询 / 配置 / 治理），子项默认展开、直接可点，**不折叠、不减条目、不改顺序**；
> ③ 菜单数据 / 权限码 / 0078 SIGNAL / 后端契约一律未动，撤菜单另立 change；
> ④ 探针与 UI 冒烟同批加断言并做三种缺陷写法的互补变异验证（第十二章）。
>
> **v2.0 变更**：① 补入可引用的业界设计规范与量化门槛（Fiori 官方配额、Nielsen 启发式、
> Duck Creek 90% 人机一致率、Five Sigma 四级自主度、NAIC/EIP 监管数据）；② 原「未动 / 待拍板」
> 9 条改为**有实证的默认裁定**；③ 落地 P0 纯前端代码（我的工作台 / 案件 360 / 全局命令面板 /
> AI 结论卡与采纳回流埋点），并给出文件清单与验收结果（第十二章）。
> **硬约束不变**：不改 IAM 菜单数据、不改权限码、不新增迁移、不碰资金与拒赔终审。

## 〇、一页结论

**根因不是「菜单太多」，而是三件事叠加：按流程环节切菜单、按权限码裁可见性、按案件 ID 找活干。**

| 用户感受 | 代码层根因 | 实测规模 |
|---|---|---|
| 菜单散乱、找不到入口 | 15 条一级叶子平铺在「智能理赔」单个目录下，无分组 | `routes.tsx:105-129` 共 19 条路由（15 可见 + 4 hidden） |
| 没按角色分工 | 菜单可见性只看 JWT 里的权限码，无角色维度；15 条菜单仅用 3 个读权限码 | `MenuApplicationService.java:195-219` |
| 作业要来回跳 | 菜单顺序＝作业链路，一件赔案要跨 8 个菜单；6 个页面必须手输案件 ID 才能操作 | `EvidenceUploadPage.tsx:154` 等 6 处 |
| 查不到案 | 无全局检索；进度页只认纯数字案件 ID；筛选各页重复实现 | `ClaimProgressPage.tsx:22-28` |
| AI 没帮上忙 | AI 建议在前端 0 触点、采纳/驳回 0 回流；对话式助手后端已实现、前端 0 引用 | `ClaimAssistantController.java:38-52` |

**目标态一句话：一个入口（我的工作台）＋ 一个对象（案件 360）＋ 一个搜索框（全局检索）＋ 一层 AI（每一屏）。**
把 15 条菜单从「用户的主路径」降级为「低频入口与配置面」，让「人今天要办什么事」成为第一组织轴。

**三条硬约束（本方案明确不动）**

1. 不改 `iam_menu.permission` 的角色口径 —— 迁移 0078 已把「全部理赔菜单 permission 统一为读码」写进 SIGNAL 校验，改码会重演 DEMO 角色看不见菜单的事故。
2. 不动确定性内核 —— AI 只出建议、金额与资金全在确定性代码；拒赔必须人工确认；五要素证据链与职责分离保留（项目护城河）。
3. 不重做已收敛项 —— 单导航架构、`routes.tsx` 唯一真源、菜单命名统一、配置页下钻、AI 治理深链按钮、探针 74 项，均已完成。

> **v2.0 实证补正（重要）**：进一步取证发现仓库里**根本不存在理赔业务角色码**
> （`bone-init.sql:281-285` 只有 SUPER_ADMIN / USER / TENANT_ADMIN_demo；
> `scripts/seed/uat/gen.py:239-252` 是 12 个平台通用 DEMO_* 角色）。
> 所以 v1.0 的「按角色渲染工作台」若照字面实现会拿到一个永远为空的数组 —— 又一处「配了不生效」。
> **v2.0 改为权限码能力画像**：写权限码是运行时唯一有区分度的信号，角色码降级为未来 IAM
> 下发业务角色后的可选优先信号。同理，理赔后端**没有** AI 建议采纳端点、网关不转发
> `/api/ai/v1/**`，故采纳/驳回先落「本地结构化事件 + 明确未落库」，绝不拿一个 404 冒充回流成功。

## 一、现状诊断：散乱从哪里来

| # | 诊断 | 关键证据 | 后果 |
|---|---|---|---|
| D1 | **菜单平铺且无角色差异** | `10_bootstrap_seed.sql:18` 中租户 0 / 1001 各 15 条 `type=1` 叶子，全挂同一目录；15 条菜单仅用 `claim:claims:read`(10) / `claim:policy:read`(4) / `claim:quota:read`(1) 三个读码；`0078_seed_claim_preexam_menu.sql:230-240` 把统一读码写成 SIGNAL 硬约束；`MenuApplicationService.java:212-219` 唯一判据是 `scopes.contains(m.getPermission())` | 审计员、只读访客、复核岗、超管看到**同一套 15 条菜单**；「按角色分工」在机制上不可能 |
| D2 | **按流程环节而非「角色＋对象」切分** | `routes.tsx:58` 注释自述「顺序 = 作业链路顺序：初审→核赔→理算→材料→资金→申诉→挂起→后督」 | 菜单是「系统能力目录」，不是「我今天要干的活」；一件赔案从受理到结案要跨 8 个菜单 |
| D3 | **作业断点：6 个页面先手输案件 ID** | `EvidenceUploadPage.tsx:154`、`FundWorkbenchPage.tsx:82`、`AppealPage.tsx:58`、`SuspendPage.tsx:47`、`AdjustmentAttributionPage.tsx:138`、`InspectionWorkbenchPage.tsx:103` 均用 `CaseIdBar`；仅核赔 / 初审 / 后督 3 页有待办队列；全仓 `navigate()` 无一处把 `claimId` 带到作业页 ⇒ **0 条案件级深链** | 每换一次菜单丢一次上下文、重输一次 ID；8 环节作业至少 14 次无价值操作（7 次切菜单 + 7 次输入核对）；输错 ID 会串案，在资金域是资损面 |
| D4 | **查询缺口** | `claimApi.ts` 全文无 `keyword/search/保单号/姓名/发票号` 检索；`ClaimProgressPage.tsx:22-28` 只按纯数字案件 ID 查单案，注释明确「不做全量列表」；筛选在 Policy / Insurer / Mapping / Quota / Liability 各写一遍，无共享组件、无保存视图、无最近访问 | 客服 / 员工 / 主管「找不到案」→ 转后台代查；查询是作业前置，查不到就干不了活 |
| D5 | **效率设施缺失** | 作业工作台 0 个 `rowSelection`（批量）；唯一案件详情抽屉在 `ReviewWorkbenchPage.tsx:598-697`；全部 pages 目录 0 命中 `onKeyDown` / `hotkey`；工程详细设计第 11.10 节设计的「审核疲劳防控四项」（单班 120 件 / 2h 提醒 / ≥3% 抽检 / 大额不派超量人）只在文档、未上屏 | 高频作业全靠鼠标逐条点；文档里的约束不进界面＝不生效 |
| D6 | **AI 悬空：能力在后端，用户看不见** | `AiSuggestion` 前端 0 展示、采纳/驳回 0 回流（人工决策只有通过 / 拒赔 / 补件）；`blindLabel.ts:30` 反而把建议当禁区屏蔽；`ClaimAssistantController.java:38-52` 三个端点已实现但 `bone-frontend` 全域 0 引用；AI 治理 / 盲标是 hidden 路由，唯一入口是核赔页两个按钮；OCR 只在材料页有状态与置信度列 | AI 只是「藏在角落的面板」，不是作业助手；**没有采纳/驳回回流 ⇒ 评测集停在离线 300 条，模型飞轮不转** |

> **一句话归因**：功能按系统能力组织、可见性按权限码组织、作业按 ID 组织、AI 按面板组织 —— 四者都不按「人今天要办什么事」组织。

**已经做过、本方案不重复建议的事**：2026-10-28 单导航重构（消除双层菜单 + 命名统一 + 子层排序）、0071 菜单改名、0078 统一读码、0093 撤下计划/责任配置并改为保单下钻、AI 治理与盲标加深链按钮、探针族 74 项断言。本方案是在这些收敛之上的**组织轴升级**，不是推倒重来。

| Five Sigma 四级自主度 | Assist / Collaborate / Lead / Autonomous；**capability（模型能做什么）与 permission（允许它做什么）是两个独立旋钮** | 把 §6.3 三档升级为四级映射；埋点事件不扩大任何自动生效范围 | 行业框架，结构性强 |

| Guidewire ClaimCenter / Duck Creek Claims（2026 评测） | 把 tasks / documents / decision points / event history 绑到**同一 case record**；规则驱动队列与指派；settlement authority limit 强制审批权限 | 案件 360 按 case record 收敛；受保护动作禁批量 | 多家评测一致，方向性强 |

### 2.2 六条设计原则（每条附 Why 与反例）

| 原则 | 含义 | 为什么 | 反例（要避免） |
|---|---|---|---|
| **P1 角色优先于功能** | 登录后先看到「我今天要办的活」，再按需要进功能 | 角色决定任务，任务决定入口；功能清单是研发视角 | 给每个角色复制一套侧栏（N 套必然漂移） |
| **P2 案件为中心** | 一个 `claimId` 贯穿所有环节，页面是案件的不同视图 | 赔案是唯一业务对象；按环节切页会强制用户重建上下文 | 每页一个 CaseIdBar，各记各的 ID |
| **P3 队列驱动而非 ID 驱动** | 待办队列是起点，点开即作业 | 「找活」比「找功能」高频一个数量级；ID 是机器键不是人的记忆单位 | 让用户记住 19 位数字 ID 才能干活 |
| **P4 搜索是作业前置** | 全局检索与通知常驻，与作业同级 | 找不到案就干不了活；Fiori 把 enterprise search 放 shell bar | 把检索藏在某个列表页的筛选里 |
| **P5 AI 是一层不是一个菜单** | 建议、解释、助手、推送出现在每一屏的相关位置 | AI-native 与 AI-bolted-on 的分界；藏进 hidden 面板＝没人用 | 再做一个「AI 中心」菜单 |
| **P6 确定性内核不动** | AI 不碰钱、拒赔人工确认、职责分离、可解释 | 可审计、零资金差错是护城河，也是监管要求 | 为效率把拒赔/调账/支付做成批量自动 |
| **P7 不造不存在的契约** | 后端没有的能力，前端不假装成功；用显式 `pending` 状态 + 结构化本地事件占位 | 「配了不生效 / 假绿」比缺功能更致命；也避免拿 404 冒充回流 | 发一个必然失败却提示「已保存」的 POST；编造置信度 0.87 |
| **P8 护栏只防膨胀** | 配额护栏判上限不判建议下限，低权限画像稀疏属正常 | 误报会让维护者关掉整条护栏，比没有护栏更糟 | 把 Fiori「2–5 sections」硬判成只读用户判红 |

**三条「不做」**：不做大爆炸重构；不用 `iam_menu.permission` 做角色裁剪；不把 AI 放进金额决策路径。

## 三、信息架构重构方案

### 3.1 现状 → 目标

| 维度 | 现状 | 目标 |
|---|---|---|
| 一级入口 | 15 条平铺叶子 | **4 个空间**（作业 / 查询 / 配置 / 治理）＋ **1 个角色工作台首页** |
| 默认落点 | 核赔工作台（所有人） | **我的工作台**（按角色渲染） |
| 组织轴 | 流程环节 | 角色任务 + 案件对象 |
| 可见性 | `scopes` 权限码（安全下限） | 权限码**不变**（安全下限）＋ 角色工作台配置（体验层，新增） |
| 对象上下文 | 每页重输 ID | 案件 360 单一 `claimId`，深链可分享可回退 |
| AI 位置 | hidden 面板 + 2 个按钮 | 每屏一层：建议卡 / Copilot / 主动推送 / 治理 |

### 3.2 四个空间：按「变更节奏 × 影响半径」分组

| 空间 | 内容 | 频率 / 影响半径 | 主要使用者 |
|---|---|---|---|
| **作业 Work** | 我的工作台、案件 360、待办队列、初审 / 核赔 / 理算 / 资金 / 申诉 / 挂起 / 后督 | 日频；改一次影响**一件赔案** | 初审、核赔、复核、财务、风控、后督 |
| **查询 Find** | 全局检索、案件列表、保存视图、员工/客服进度 | 日频；只读跨案 | 全部角色（员工限本人） |
| **配置 Configure** | 保单管理、额度管理、基础目录库、承保主体、主数据映射 | 低频；改一次影响**该保单所有未来赔案** | TPA 运营、保司管理员 |
| **治理 Govern** | AI 治理、盲标工作台、评测集 / 漂移 / 模型卡 / 质检 DIFF | 低频；专业角色 | 风控、模型治理、管理员 |

**Why**：变化频率、影响半径、使用者、误操作代价四个维度都不同。把「日常高频」与「偶发高风险」放在同一列，会共享同一份视觉权重与心理负担，这正是当前散乱感来源之一。Fiori 用 Spaces 按工作域分组是同一逻辑。**配置面沿用 0093 的下钻形态，不拆回独立菜单。**

### 3.4 关键机制：角色化**不能**靠改 `permission`

- 现状证据：`0078_seed_claim_preexam_menu.sql:230-240` 的 SIGNAL 把全理赔菜单 permission 钉成统一读码；`MenuApplicationService.java:195-219` 的 `current()` 完全没有 role 维度；`0078:34-40` 记录过「初审菜单误用写码 ⇒ 三个 DEMO 角色看不见菜单」的真实事故。
- **结论**：改权限码 = 重演事故 + 撞 G40 / SIGNAL / 探针三角。角色分工必须另找机制。

分两步走：

| 阶段 | 机制 | 改动面 | 收益 |
|---|---|---|---|
| **P0 / P1（零 IAM 改动）** | 不动菜单树；把**默认落点**改为「我的工作台」，卡片按 JWT 内的角色 / 权限码在前端渲染；侧栏按四空间加**常驻展示层分组标题**（不折叠、不减条目、菜单名 / 顺序 / permission 全不变） | 前端 + 一个默认落点配置 | 一登录就看到自己今天要干的活，先拿到约 80% 体验收益 |
| **P2（新增机制）** | 新增「角色 → 工作台配置」（建议 `iam_workbench_profile`，或配置 + 新端点下发 `workbenchProfile`），描述默认落点、卡片集合、可见空间 | IAM 新表 / 新端点 + 迁移（末尾追加） | 角色可运营配置，不必发版 |

**Why 分两步**：权限与体验解耦。工作台配置**只做展示裁剪**，后端 `@PreAuthorize` 与 `row_policies` 仍是安全下限，绝不拿它做越权放行；先用零风险方式拿收益，避免一上来同时撞 IAM 迁移、门禁与探针。

## 四、作业便利性：案件 360 ＋ 队列驱动

### 4.1 三段式统一作业面

**待办队列（找活） → 案件 360（一个 claimId 看全） → 决策动作（就地办完）**

所有角色共用同一骨架，差异只在「队列筛选条件」与「可用动作集合」。
**Why**：把「找菜单」变成「找活」，把「记 ID」变成「点案件」。Guidewire / Duck Creek 的 adjuster workbench 正是把任务、文档、审批、事件历史收敛到同一 case record。

### 4.2 案件 360 的 Tab 规划（收编现有 6 个单案页）

| Tab | 收编自 | 关键内容 | 约束 |
|---|---|---|---|
| 概览 | 新增 | 状态机时间轴、关键字段、五要素、SLA、当前责任人 | 只读 |
| 材料与 OCR | 材料上传 | 单证列表、OCR 状态/置信度、解析回填、补件 | 低置信主动提示补件 |
| 理算归因 | 理算归因 | 理算明细、控额链路、免赔维度、字段 lineage | 计算字段只显示不决策 |
| 资金与结算 | 资金工作台 | 结算单状态机、额度、对账 Timeline | 两段式幂等不变 |
| 申诉与挂起 | 申诉复议 / 挂起恢复 | 复议结论、5 类挂起 | `FRAUD` 仅风控岗可恢复 |
| 决策与 trace | 核赔 Drawer | 决策图轨迹回放、规则命中、**AI 结论卡** | 可解释 + AI 参与显著标识 |
| 后督质检 | 后督抽检 | 四维结论、DIFF、抽检记录 | 不改原案结论 |

### 4.3 上下文不丢失

- URL 契约（**v2.0 修正**）：`/claim#/case?claimId=<id>&tab=material`。放弃 v1.0 的 path 参数，因为仓库既有真源是 `useClaimIdParam.ts:29` 的 `?claimId=`：6 个单案页全从 query 读 ID，另立 path 参数会造成「同一语义两处配置源」，且一个现有页面组件都无法复用。生成/解析/白名单统一收口到 `workbench/caseDeepLinks.ts`，将来换 path 形式只改一处。
- 返回队列时保留筛选 / 页码 / 滚动位置；面包屑显示「来源队列 › 当前案件」。
- 旧 6 个路由保留重定向（不删页），避免收藏夹、探针、外部深链失效。
- **Why**：现有全仓 `navigate()` 0 处带 `claimId`；隐式缓存（记住上次 ID）不可分享、不可回退、跨标签页丢失，只有 URL 里的 `claimId` 是可审计、可深链、可恢复的真源。

**P0 实现口径（已落地）**：`Case360Page` 是**深链桥而非内嵌重写**。8 个 Tab 中「概览」直接读
`claimApi.detail` + `aiDisclosureApi` + `reviewTaskApi.execution` 渲染案件事实与 AI 结论卡；
其余 7 个 Tab 提供「带着案件上下文前往」按钮，用 `buildCaseDeepLink` 生成
`/evidence?claimId=...` 等链接 —— 这是全仓第一次让 `navigate()` 携带 `claimId`。
不把 6 个现有页面硬嵌进 Tab，是因为它们各自带 `PageHeader` / `CaseIdBar` / 独立取数，
硬嵌会出现双标题与双 ID 源；P1 应先拆成「无壳内容组件」再内嵌。
**一处改动覆盖 6 页**：`CaseIdBar` 按 `location.pathname` 反查 Tab，给全部单案页自动加上
「案件 360」入口，6 个页面文件零改动。

### 4.4 批量与快捷键（分层授权）

| 类别 | 动作 | 理由 |
|---|---|---|
| 可批量 | 领取、指派、标记已阅、导出、低风险初审通过（规则全命中且非大额/非拒赔） | 重复且低风险，压缩鼠标成本 |
| **禁批量** | 拒赔生效、调账、支付、恢复 FRAUD 挂起、≥1 万复核 | 人工终审与职责分离不可被效率优化绕过 |
| 快捷键 | `/` 或 ⌘K 全局搜索、`j/k` 队列移动、`Enter` 打开、`e` 领取、`[` `]` 切 Tab、`?` 帮助 | 渐进提供、可关闭，不替代鼠标路径 |

### 4.5 把「已设计但未上屏」的控制搬进工作台

单班 120 件上限（超量自动转派）、连续 2h 休息提醒（soft prompt，不阻断）、主管 ≥3% 抽检、大额/高风险不派给当日超量或临近班末的复核人 —— 变成工作台的可见提示与队列规则，参数走 `feature_toggle`。
**Why**：文档写了但界面不体现，等于「配了不生效」；且 AI 只建议、人工终审的模式把正确性压给核赔员，疲劳防控是质量下限。

### 4.6 为什么这样设计（可量化对照）

| 动作 | 现状 | 目标 |
|---|---|---|
| 8 环节作业切换 | ≥7 次切菜单 + ≥7 次输入/核对 ID | 1 次进入案件 360 + Tab 切换，全程 ≤3 屏 |
| 找到目标案件 | 记住 19 位数字 ID 或找后台代查 | 全局搜索 1 次输入 |
| 上下文丢失 | 每次换菜单 1 次 | 0 |
| 熟练用户作业 | 全鼠标逐条点 | 队列 + 快捷键 + 低风险批量 |

依据：Fiori 1-1-3（1 人 1 用例 1 应用 ≤3 屏）、Guidewire / Duck Creek case record 收敛、项目现有 14 次无价值操作的实测推算。

## 五、查询便利性：全局搜索 ＋ 统一基座

### 5.1 全局检索（一等入口）

- **位置**：shell 顶栏常驻搜索框 + ⌘K 命令面板；结果按对象类型分组（案件 / 保单 / 发票 / 承保主体 / 目录 / 功能菜单）。
- **检索键（v2.0 按后端契约分层，不造不存在的端点）**：
  - *P0 已落地*：菜单名（IAM 已下发的可见叶子）+ 纯数字案件 ID 直达案件 360 + 工作台内案件速查。
  - *P1 ✅ 后端已落地并联调*：保单号 / 姓名证件 / 手机号 / 发票号 / 收款账户的统一跨键检索端点
    `GET /api/v1/claims/search?keyword=&limit=`（挂在网关已白名单的 `/api/v1/claims/**` 下，不新开 `/api/ai/v1/**`），
    复用 SDK `@TenantScope` 做租户隔离、结果只回最小字段不回 PII 原值；前端 `claimSearchApi` 已接线，命中以 `matchedKey` 标记分类。
- **出口**：结果直达案件 360 对应 Tab；无结果给「新建申请 / 联系客服 / 检查权限」而不是空白页。
- **数据权限**：复用平台 `row_policies`（后端 WHERE 真源），租户过滤为下限、数据权限再收窄；前端不拼 WHERE、不自建数据权限引擎；结果按角色裁剪（员工仅本人）。
- **Why**：Fiori shell bar 的 enterprise search 是「一个词找到应用或数据」；2026 年理赔软件评测明确把 *document searchability and status tracking* 放在功能清单之前；本项目 `claimApi.ts` 零 keyword 检索，是查询便利性最大的空洞。

### 5.2 统一查询基座

| 组件 | 职责 |
|---|---|
| `ClaimQueryBar` | 统一筛选条：状态 / 时间 / 金额区间 / 风险等级 / 作业组 / 保司 / 保单 |
| `useClaimQuery` | 查询状态与 URL 双向同步（可分享、可回退、可进通知深链） |
| `ClaimListView` | 表格 + 空态 + 骨架 + 导出 + 列配置，统一交互语义 |
| `useSavedViews` | 保存视图、最近访问、收藏 |

**Why**：现状 5 个配置页各写一套筛选，同一语义多处实现必然漂移（项目已反复踩过）；查询状态进 URL 是「作业上下文可恢复」的前提。

### 5.3 保存视图与「工作来找人」

预置视图：我的待办 / 今日新增 / 高风险 / 临近 SLA / 待补件 / 已达封顶 / 支付失败 / 对账差异 / 质检 DIFF。通知（待办变化、补件到期、大额待复核）深链回案件 360。
**Why**：Fiori 把 notifications 与 enterprise search 并列放在常驻 shell bar —— 工作来找人，而不是人在菜单里找活。

### 5.4 员工端与客服自助

- 进度页从「只认纯数字案件 ID」改为多键查询（保单号 / 手机号 + 证件后四位 / 申请时间）；登录后「我的申请」列表免输入。
- 时间轴补齐：缺什么材料、为什么挂起、预计时效、申诉入口、决策解释（五要素）。
- **Why**：现状 `ClaimProgressPage.tsx:22-28` 让「没 ID 就查不了」，把本可自助的查询转成客服工单，是查询便利性 ROI 最高的一处。

### 6.2 四层融合

**L1 建议进主决策面（P0，最高 ROI）**
案件 360「AI 结论卡」＝ 结论 + 置信度 + 依据（规则命中 / OCR 证据 / 相似案件）+ 五要素证据链 + 可解释 trace + AI 参与显著标识；三个动作：**采纳 / 驳回（必选原因码 ReasonType）/ 修改后采纳（记 diff）**。金额与资金仍由确定性引擎计算，AI 卡只读展示建议，不改金额。驳回流进评测集难例、盲标样本池、漂移监控；**盲标禁区继续屏蔽 `aiSuggestion`**，防止建议泄漏给标注员污染金标准。
*Why*：没有采纳/驳回，模型只有离线 300 条评测集；行业把采纳率列为领先指标、把「用户绕开系统」列为早期预警。后端已有 ReasonType 语义，缺的只是前端动作 + 落库，是全案最短闭环。

*v2.0 实现口径（已落地）；v2.1 后端联调闭环*：`components/AiSuggestionCard.tsx` 放进案件 360「决策与 trace / 概览」，
数据只来自两个真实只读端点（`GET /claims/{id}/decision/disclosure`、`GET /review/tasks/{id}/execution`）。
四条硬约束已写进代码：① **四态 fail-closed** —— 只有 `AI_ASSISTED` 才出现采纳/驳回按钮；
② **不编造置信度** —— 后端无该字段，界面明写「未提供，不做估算」；
③ **本地事件纯总线语义** —— `telemetry.ts` 仍是纯函数事件层（`persisted:false` 仅表示事件对象自身非落库真源，由 32 例单测锁定），
真实写库由独立的 `persistWorkbenchEvent` 异步完成，写库失败只提示、绝不谎称已落库；
④ **AI 不碰钱** —— 事件体永不含金额字段，后端 `@JsonAnySetter` 双保险拒绝任何越界字段（实测 `approvedAmount` 夹带 → 400）。
曝光埋点是采纳率的分母；盲标禁区直接拒绝生成曝光事件，防金标准污染。
*v2.1 后端落地*：`ClaimWorkbenchController` 挂在网关已白名单的 `/api/v1/claims/**` 下，提供
`POST /{claimId}/ai/feedback`、`GET /{claimId}/ai/feedback`、`GET /ai/feedback/summary` 三端点；
落库 append-only 表 `t_claim_ai_feedback_event`，`event_id` 作租户内幂等键（重放返回 `replayed=true`）。
**经网关 8888 真机联调通过**：曝光/采纳/驳回落库 200、幂等重放 `replayed=true`、服务端 `summary` 返回 `serverSide=true` 的 30 天窗口口径；
负向 7 类（eventId 非法 / AI_STUB 裁决 / 未知金额字段 / 盲标 scene / REJECT 缺原因码 / MODIFY 缺 modifiedFields / 检索过短或 limit=0）全部 400 且返回规范错误码。

**L2 Copilot 常驻（P1）**
接已有 `ClaimAssistant` 三端点做右侧可折叠助手，工具白名单：查案件 / 查保单条款 / 查目录 / 查进度 / 找相似案件 / 起草客户说明。上下文自动带当前 `claimId`；回答给「依据 + 跳转链接」，不给结论性金额；拒赔、调账、支付不提供工具。
*Why*：从「AI 是一个菜单」变成「AI 在每次作业里」；后端已实现、前端零引用，是现成的低垂果实，且不违反 BONE-AI 能力依赖图谱的「不做清单」（不自研 OCR / LLM / PII）。

**L3 主动推送（P1–P2）**
高风险、重复发票、图谱团伙线索、OCR 低置信、SLA 临期、质检 DIFF → 进「我的待办」并按风险重排，每条带「为什么推给我」+ 一键进案件 360。
*Why*：自动化率越高，人越应只处理例外。泰康 97% 自动化、众安 100% AI 质检在界面上的含义是「例外队列」，不是「全流程菜单」。

**L4 治理可见（P2）**
AI 治理 / 盲标从 hidden 提升为治理空间一级入口（按角色可见），上屏指标：建议采纳率、驳回原因分布、置信度校准曲线、漂移 PSI、评测集覆盖、champion/challenger 状态；撤下核赔页两个临时按钮。
*Why*：治理能力没有可见入口＝「配了不生效」；但也不该塞进核赔员的主路径。

### 6.3 分级自动化（escalation protocol）

| 档 | 适用 | 人的动作 | 留痕 |
|---|---|---|---|
| 全自动 STP | 低风险小额、规则全命中、置信度达标 | 无（事后 100% AI 质检） | 五要素 + decision trace |
| 人工确认后生效 | 自动通过建议、一般案件 | 一键采纳 / 驳回 | reasonCode + operator_id |
| **仅建议，人做终审** | 拒赔、≥1 万、FRAUD、质检 DIFF | 必须人工决策 | 双人复核 / 职责分离 |

*Why*：NAIC Model Bulletin 与金发〔2026〕8 号的可解释、人工复核要求；项目「拒赔必须人工确认」「AI 不碰钱」护城河；业界明确要求「定义哪些全自动、哪些人工确认、哪些只给建议」。

**与 Five Sigma 四级自主度的对位**（v2.0 补充）：Assist＝Copilot 查资料 / 起草说明（P1）；
Collaborate＝AI 出建议、人逐案确认（本轮 L1）；Lead＝规则明确的低风险小额跑完主干、例外才推给人（P2）；
Autonomous＝窄口径 STP + 事后 100% 质检（未排期，须先过 90% 人机一致率闸门）。
**capability 与 permission 分开**：本轮埋点只增强观测能力，**不提高任何自动生效档位**。

### 6.4 明确不做

前端不做金额决策、不改理算结果；不自研 OCR / LLM / PII；不把 AI 治理做成第二个核赔工作台；不因 Copilot 放宽任何 `@PreAuthorize` / `row_policies`；不让采纳/驳回数据污染盲标金标准。

## 八、度量与验收（防假绿）

**原则**：先埋基线，再定目标；区分「自动决策率 / 自动支付率 / 零人工介入结案率」三口径（沿用《业界对标整改台账》第五节），不把自动决策率当自动化率对外承诺；生产口径与评测集口径分列。

| 指标 | 现状 | 目标 | 测法 | 口径陷阱 |
|---|---|---|---|---|
| 找到目标案件耗时 | 未埋点 | 埋点后定阈值 | 搜索框 → 案件 360 打开时长 P50/P90 | 只统计成功检索会美化；无结果单独计 |
| 单案跨菜单次数 | 可由路由切换推算 | 下降 ≥70% | 同一 `claimId` 会话内路由切换数 | 排除 Tab 内切换，否则口径不可比 |
| 案件 ID 重复输入次数 | 可实测（CaseIdBar 提交埋点） | → 0 | 同会话同 `claimId` 输入次数 | 排除外部深链首次进入 |
| 待办 → 决策点击数 | 未埋点 | ≤3 屏（1-1-3） | 关键路径点击计数 | 不含主动展开 trace |
| AI 建议采纳率 / 驳回原因分布 | **0（无动作）** | 先有数，再定阈值 | 采纳/驳回事件 ÷ **曝光**次数 | 展示 ≠ 被看见，必须加曝光埋点 |
| 客服代查率 | 未埋点 | 下降 | 进度页查询失败后转人工比例 | 区分登录态 / 游客态 |

## 十、为什么这样设计（决策速查表）

| # | 决策 | 被否决的替代 | 为什么 |
|---|---|---|---|
| 1 | 用「我的工作台」做默认落点 | 给每个角色复制一套菜单 | 复制 N 套必然漂移（已吃过双 Sider 命名漂移的亏）；一套骨架 + 角色卡片，成本 O(1) |
| 2 | 四空间分组，不再按流程环节排序 | 保持 15 条链路顺序 | 链路顺序是研发视角；用户视角是「我今天干什么 / 我要找什么 / 我要配什么」；且分组不改菜单数据，零门禁风险 |
| 3 | 案件 360 收编 6 个单案页 | 每页「记住上次 ID」/ 全局缓存 | 隐式缓存不可分享、不可回退、跨标签页丢失；URL 里的 `claimId` 才可审计、可深链、可恢复 |
| 4 | 角色化走新的工作台配置，不改 `permission` | 给不同角色分配不同读码 | 0078 已把统一读码写进 SIGNAL，改码会重演 DEMO 角色看不见菜单的事故，且 `current()` 无 role 维度 |
| 5 | 先做采纳/驳回埋点，再谈新模型 | 先上 RAG / 视觉反诈 | 无回流则评测集不增长、采纳率不可测；后端已有 ReasonType 语义，是最短闭环 |
| 6 | AI 治理从 hidden 提升为治理空间 | 在更多页面加「AI 治理」按钮 | 按钮是补丁，第三份入口只会继续散乱；按角色可见的空间才是稳定归属 |
| 7 | 批量/快捷键只覆盖低风险动作 | 全动作可批量 | 拒赔、调账、支付必须逐案人工终审，职责分离不可被效率优化绕过 |
| 8 | 全局搜索复用 `row_policies` | 前端过滤 / 独立搜索权限表 | 同一语义两处配置源 = 配了不生效或越权；后端 WHERE 是唯一真源 |
| 9 | 分 P0/P1/P2，P0 零 IAM 改动 | 一次性重构菜单 + 角色 + AI | 大爆炸会同时撞门禁、探针、权限三道；先拿 80% 体验收益，再动机制 |
| 10 | 保留确定性内核与「AI 不碰钱」 | 让 AI 直接给结案金额 | 可审计、零资金差错是护城河；监管要求可解释与人工复核 |
| 11 | 用权限码能力画像，不等角色码 | 先建 `iam_workbench_profile` 表 | 仓库无理赔业务角色码，先建表 = 建一张没人读的表；画像当天可用且零迁移 |

### 13.1 默认视图「我的待办」，可切「全部待办」

三段作业台（初审 / 审核 / 复审）默认只显示 `assignee_id = 当前用户 ∪ 当前用户代理的人` 且
`status ∈ (PENDING_CLAIM, PROCESSING)` 的任务；「全部待办」需 `claim:assign` 或主管权限。
归属载体是 `t_claim_task`（一案 × 一任务类型一条存活任务），**不是**在 `t_claim_case` 加列——
案件主表已有 40+ 列且只能表达「当前一个归属」，转交无留痕、无法承载队列与 SLA。

真实场景：理赔员上班第一屏只看自己的活；主管按组看积压并干预；峰值允许从公共池自领兜底。
派单**不等于锁定**：`PENDING_CLAIM` 超过 30 分钟未领取自动回池，避免一人请假拖死一批案件。

### 13.2 三工作台统一查询条件集

| 字段 | 控件 | 请求参数 | 真实场景 |
|---|---|---|---|
| 关键词（报案号 / 保单号 / 被保人哈希） | Input | `keyword` | 客服拿报案号找案 |
| 状态集 | 多选 Select | `statuses[]` | 主管筛「待复审 + 复审中」 |
| 任务类型 | Select | `taskType` | 区分金额闸门(44 双人复核) 与质量闸门(43 复审) |
| 处理人 / 作业组 | 人员选择 / 部门树 | `assigneeId` / `deptId` | 按人、按组看积压 |
| 渠道 | Select | `sourceChannel` | 线上/线下分流复盘 |
| 金额区间 | 双 Input | `amountMin` / `amountMax` | 捞大额案 |
| 报案时间 | RangePicker | `createdFrom` / `createdTo` | 月度对账 |
| SLA 分桶 | Segmented | `slaBucket` | 临期/超期优先处置 |

后端统一 `ClaimQuery`，**服务端分页 + 返回真实 `total`**。当前初审页只有 1 个状态 `Select`，
核赔页则是**假分页**（固定拉 50 条、前端切 20/页，第 3 页即空）——这不是「条件少」，是分页契约错误，
用户会丢掉 2/3 待办，故与条件扩充同批修。

### 13.3 AI 建议触达与采纳回流

初审页新增 AI 建议卡：结论建议、**置信度**、命中规则原因码、可展开的决策轨迹，以及「采纳 / 驳回」。
采纳率分母用曝光事件（`t_claim_ai_feedback_event`），盲标场景禁生成曝光事件以防污染金标准。
后端能力已具备（5 节点决策图 + 三分诊 0.7/0.85 + 金额上限 10000 + 放量四档），
但 `AUTO_APPROVE` 默认关闭、治理页只读、前端 0 触点，所以本轮的关键是**把已有能力送到屏上**，而非重造模型。
规则配置分三层（L1 代码规则 / L2 租户策略 / L3 作业参数），阈值**只收紧不放开**，不引入自动拒赔；
详见《AI技术方案》§10.1.1。

### 13.4 核赔页假分页修正（与查询增强同批）

服务端 `total` 取自同一 `COUNT(*)` 口径，禁止前端用固定 50 条切片；验收用「造 137 条待办 → 翻到第 7 页」探针，
断言每页条数、总数、无重复、无遗漏。这是数据正确性缺陷，不归入「体验优化」。
