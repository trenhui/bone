# synapClaim 智能理赔平台-部署集成方案（FDE）

**FDE = Fast Deployment Engine（快速部署引擎）**

> 定义：一套**标准化、可复制、轻量可落地**的交付方法论与工程产物——产品就绪后，以**单客户 4-6 周**完成存量理赔环境旁路接入（Phase A 影子验证 + Phase B 辅助上线），先旁路验证、再人机协同、后自动化，全程可回退、可灰度、可审计。产品自身成熟周期（Gate 0 + MVP 迭代）见 §六节奏，不在本口径内。
>
> **文档关系**：本文档是 synapClaim 的"交付/集成层"方案，上游依赖《工程详细设计（落地版）》（确定性分层 / 防腐层 / 评测方法论 + §3.8 技术选型落点）、《产品需求文档》（功能与验收）、《Synap 创业方案》（商业与节奏）。三者中已有的绞杀者迁移、ACL 防腐、评测方法论在本方案中落地化。原《系统设计方案》**已于 2026-10-21 归档**至 `10-archive/`（其结论已上收落地版），不再作为本文依赖。

## 一、买方价值与壁垒（摘要）

- **价值承诺**：单案成本 15-25 元 → ≤8 元（↓≥50%）；快赔时效 3-7 天 → ≤30 秒（建议结论口径，报销模式）；赔付损失率 ↓≥30%（**多智能体风控为 V2 能力；一期由规则反欺诈 R-FRAUD + 后督抽检部分兑现，不对一期做全额承诺**）；决策 100% 可解释（证据链 + 条款引用 + 决策轨迹）；新保司接入 ≤7 天（前提：配置复制模板就绪 + 2-3 人并行交付，单人串行约 25-35 人日，见 §3.5）；私有化/信创数据不出域。
- **完整论证与业界对标**：《Synap（思纳普）创业方案》§3.4（价值主张量化与壁垒分层）。

## 二、这份方案解决什么

- 理赔 AI 的落地难点不在模型，而在把模型的理解翻译成系统动作（字段、状态、接口调用）+ 让客户看得见的业务价值。
- 本方案只解决"翻译与证明"这一层：阶段化灰度、可回退、可审计；产品功能与工程契约见《工程详细设计（落地版）》。

## 三、与存量理赔系统打通（集成架构）

### 3.1 集成对象与现状（As-Is 盘点）

客户环境常见存量系统（按对接优先级）：

|**系统**|**对接内容**|**对接难度**|**对接优先级**|
|---|---|---|---|
|TPA/保司理赔系统|案件、审核结论、材料影像|中（接口或文件）|P0（旁路审核的前提）|
|保司核心（承保/保单）|保单有效性、责任范围、免赔额|中|P0|
|OA/HR/企业微信|员工报案入口、通知触达|低|P0（获客入口）|
|财务/资金系统|支付指令、对账文件|中|P1（Phase C 需要）|
|医院HIS/医保|直付结算（演进方向）|高|P2（V3+）|
|电子票据平台|发票验真、开票|中|P1|

### 3.2 四层集成模式矩阵（业界最佳实践）

|**集成层**|**模式**|**技术**|**典型场景**|**侵入性**|
|---|---|---|---|---|
|数据层|CDC 实时同步 / ETL 批处理 / 文件交换|binlog 订阅、SFTP、对象存储|保单、历史案件导入|低（只读）|
|接口层|REST API / 事件 / Webhook|网关按工程落地版 §10.3 实际配置（Higress 未在 bone 落地，属待验证选型）；消息/事件：一期进程内领域事件总线 + 发件箱（RocketMQ 二期）|报案受理、审核结果回写|中|
|流程层|人工交接 / 工作台嵌入|iFrame + SSO + 待办集成|核赔员审核（不动原系统）|低|
|身份层|SSO / OIDC / LDAP|bone-iam（OIDC）|登录打通|低|

### 3.3 集成关键原则（来自理赔自动化实战）

1. **默认只读旁路**：先不写存量系统，审核建议旁路输出，业务风险最低（对应 Phase A）
2. **幂等设计**：所有写回操作带幂等键（接口层 `Idempotency-Key` 请求头：**创建类取客户端业务键**（`batchNo+invoiceNo` 或客户端 UUID——报案号由服务端生成，客户端无法预知），**状态推进类取 `{claimNo}:{stage}:{attempt}`**；资金层 `idempotency_key` 同三段式，`attempt` 为占额周期序号），防止接口超时重试导致重复立案/重复支付——理赔自动化最容易出事故的细节（口径真源：工程落地版 §10.3）
3. **先 mock 后真实**：集成对接先用 mock 数据跑通全链路，再逐步替换真实接口，报错时可隔离"模型输出问题"与"接口问题"
4. **审计三件套**：每个 AI/集成节点落三类日志——输入摘要（≤200字）、模型输出（完整）、平台动作结果（HTTP 状态码+耗时），用于事后复现与瓶颈定位
5. **防腐层（ACL）**：外部系统 DTO 不进核心域，适配器内做字段映射（工程落地版 §3.6 限界上下文/ACL 已涵盖）
6. **结果回写双通道**：有接口走 API 回写；无接口场景走文件/邮件人工导入兜底，保证 100% 场景可交付
7. **断点续传/可重跑**：数据同步任务支持断点续传与幂等重跑，不因单次失败阻塞后续

### 3.4 三个典型集成场景

**场景 1：员工报案入口集成（OA/HR/企微）**
```
员工在 OA/企微发起理赔 → Webhook 转发 synapClaim → 自动受理+材料预检
→ 缺件/异常推送提醒 → 完整案件进入审核流水线
```
- 交付物：企微/OA 适配器模板（配置化，无需定制开发）
- 入口契约：员工经 OA/企微侧 OIDC 单点登录入站（员工端面）；OA/企微 **Webhook 转发**经 `/integration/**`（API Key + HMAC 防重放）入站并归一为 `ClaimCaseChangedEvent`（工程落地版 §10.4）——两种入口按客户身份体系二选一，适配器模板内置，不在员工端 OIDC 面开放 Webhook

**场景 2：存量理赔系统旁路审核（P0 核心场景）**
```
存量系统案件（CDC/文件）→ synapClaim 只读同步 → AI 审核建议（带证据链）
→ 建议回传存量系统工作台（嵌入/API/邮件）→ 核赔员参考处理
```
- 交付物：理赔系统适配器 + 工作台嵌入 SDK + 建议回写双通道

**场景 3：支付/对账对接（Phase C）**
```
synapClaim 决策通过 → 资金状态机（两段式）→ 调财务/资金系统 API 或输出对账文件
→ 回执确认 → 结案
```
- 交付物：资金适配器 + 对账文件模板 + 幂等重试

### 3.5 集成工作量控制

|**适配器**|**模板复用度**|**单客户定制工作量**|
|---|---|---|
|理赔系统|70% 复用|3-5 人日|
|保单/承保|70% 复用|3-5 人日|
|OA/企微报案|90% 复用|1-2 人日|
|资金/财务|60% 复用|3-5 人日|
|医院HIS（演进）|40% 复用|10-15 人日|

> 关键：**FDE 的工程化目标就是让"每个新客户接入"从项目制变成配置制**——单客户集成工作量压到 ≤15 人日（前提：交付 2–3 人并行；单人串行约 25–35 人日），支撑"新保司接入 ≤7 天"承诺。
>
> 口径：上表四项主用适配器合计 10–17 人日，取中位口径 ≤15 人日/客户；上限场景以并行交付摊平。

## 四、落地路径：三阶段渐进（轻量、可回退、可灰度）

|**阶段**|**模式**|**行为**|**对客户影响**|**回退代价**|
|---|---|---|---|---|
|**Phase A（Shadow 4 周，可延至 6 周）**|Shadow 旁路|只读存量数据，AI 审核建议与人工结论对照，产出评测报告|零侵入，业务无感|零成本（关掉同步即可）|
|**Phase B（4-6 周）**|Assisted 辅助|核赔员工作台嵌入：AI 建议 + 证据链 + 置信度，人工终审（不出款）|核赔员提效，流程不变|低（关闭建议开关）|
|**Phase C（≥8周）**|Automated 自动化|低风险案件自动通过 + 自动支付；高风险/大额人工；后督抽检|流程变革，人力重分配|按案件比例灰度回退|

**阶段切换门槛**（与评测方法论一致）：Phase A 评测达标才进入 Phase B/C，阈值以 07-delivery/07 测试方案与性能基准为唯一真源。

**灰度纪律**（理赔自动化实战最佳实践）：
- 灰度三步走：内部测试全自动 + 人工双录对照 → 单分支 5% 新案分流 → 看三指标（自动化完成率/人工介入率/结案时效）决定放量
- **变量隔离**：灰度期间不同时改模型版本和工作流版本；模型、提示词、工作流三版本绑定记录，回滚可对齐
- 转人工案件单独复盘：七成介入是字段校验问题（改 Schema/提示词），少数是接口问题（改集成层），别盲目动模型
- **已出金案件不回退**：灰度回退只冻结新增自动通过；已 `PAID` 案件按当前阶段自然完成，不回退、不冲正（冲正仅走工程落地版 §11.1.2 补偿矩阵的退款/回冲路径）——防止回退动作对已付案件产生二次资金操作

**部署形态**：
- 试点期：单机/轻量形态（Docker Compose 或 4 节点小集群），降低首单部署门槛
- 生产期：K8s 集群（工程落地版 §11.8）；信创环境（麒麟 OS + 鲲鹏/海光 CPU）适配
- AI 推理：敏感数据（病历/身份）本地 vLLM，非敏感数据（条款检索）云端 API，按客户合规要求切换

**可用性档位与部署形态映射（工程落地版 §11.8，不得超卖）**：

| SLA 档位 | 部署形态 | 说明 |
|---|---|---|
| 99.9%（一期对外承诺档） | 单集群 + 同城多 AZ + DB 主从切换 | 落地前对外只承诺此档（工程落地版 §11.8） |
| 99.99%（V2） | 同城双活：跨 AZ 双活 + 数据库强一致同步 + 定期切换演练 | 单集群形态不适用该档 |
| 异地容灾 | V2+ | 触发条件：客户监管要求或异地 SLA 合同 |

## 六、节奏与验收（总周期示意）

```
Gate 0（2周）：场景定义 + 客户/数据验证（未通过则暂停）
    ↓
MVP 迭代开发（10 周，含缓冲；排期真源见《MVP 可落地执行方案》）：解析 + 规则知识库 + 核责引擎 + 工作台 + 评测集
    ↓
Phase A 旁路验证（4 周，可延至 6 周）：零侵入，评测达标（阈值见 07-delivery/07）
    ↓
Phase B 辅助上线（4-6周，与《MVP 可落地执行方案》§五 M5 同源）：核赔员提效，关闭建议即可回退
    ↓
Phase C 自动化（≥8周）：低风险自动 + 灰度放量 + 后督抽检
```

**每个阶段都以"客户可验证的业务指标"为验收，不以"技术跑通"为验收。**

**Phase A 入口条件（数据前置，缺一不出结论）**：

1. 保单快照同步链路最小可用（按 `policyNo` 查询保单快照，工程落地版 §3.5）——否则报案校验为空，核责/理算无输入；
2. 存量案件经旁路 sync 全量导入（`sourceClaimNo` 可溯源，迁移脚本幂等可重跑，工程落地版 §12.3）；
3. 责任/限额配置版本化迁移完成（`ia_liability` → `adj_liability`，已生效版本不可改）。

三项齐备方可进入 Phase A 影子比价；任一缺失，Phase A 降级为「链路联调」，不计入验收周期。

### 6.1 迁移与 cutover（工程落地版 §12.3）

- **路径**：双跑（Shadow 比价）→ 切流（按租户 × 险种灰度）→ cutover
- **cutover 判据**：全量 Automated 运行 ≥2 周且三向对账零差异 → 关停 pk-tpa 写、进入只读保留期
- **数据校验三件套**：三向对账覆盖迁移全周期 / 存量重算 dryRun / ID 映射全量对账（无孤儿案件）
- **双轨期纪律**：以 pk-tpa 为权威回退源，禁止新系统反向写 pk-tpa
- **前置门禁**：cutover 前完成金发〔2026〕8号上线前置合规门禁

**cutover 检查清单（逐项打勾方可切流）**：

- [ ] 全量 Automated 运行 ≥2 周，三向对账（支付/TPA/额度）零差异（第 4 向「请款/回款」随直付/垫付启用后追加，工程落地版 §11.7）
- [ ] 存量重算 dryRun 差异报告经风控 + 运营双签，影响面已评估
- [ ] ID 映射全量对账无孤儿案件（新 `claim_id` ↔ `source_claim_no` 双向可溯）
- [ ] 回退源声明生效：双轨期 pk-tpa 为权威，新系统无任何反向写
- [ ] 金发〔2026〕8号上线前置合规门禁完成（风险管理委员会批准件 + 监管报告回执归档编号）
- [ ] 值班表 + 回滚剧本（RB-ROLLBACK-*）就位，切换窗口不在禁发期（禁周五 16:00 后与节假日前一日）

### 6.2 阶段验收签收单（模板，每阶段切换前签署）

| 项 | 内容 |
|---|---|

## 七、集成落地风险与对策

|**风险**|**触发条件（可观测）**|**责任方**|**对策**|**回退路径**|
|---|---|---|---|---|
|存量系统接口不开放/不稳定|接口不可用；或连续失败率>5%|交付|文件交换兜底；只读优先（不改写存量）；断点续传 + 幂等重试|退回 Phase A 只读旁路，AI 结论不落流程|
|存量数据质量差（缺字段、口径不一）|字段映射失败率>10%|交付|数据沙箱先行验证；字段映射白名单；坏数据标记转人工，不阻塞流程|缩小接入范围（仅试点医院），其余转人工|
|业务方不信任 AI 结论|人工采纳率<70%；或关闭建议率>30%|交付 + 理赔|Shadow 阶段用评测报告建立信任；Assisted 阶段"人工终审权"保留；拒赔责任归属明确（AI 建议、人工/保司终审）|退回 Phase A：只出评测报告，不进主流程|
|合规（数据出境、日志保留）|合规门禁未通过；或提出数据出境诉求|安全合规|敏感数据本地 vLLM；DPA 约定数据不用于训练；资金/决策日志≥7年（PRD §13.3）|停止数据流出，切换本地推理；必要时暂停试点|
|部署环境信创/资源受限|资源水位超阈值；或信创适配项未通过|架构 + 交付|轻量部署形态 + 信创适配；AI 推理按需降级（云端/本地切换）|降级为云端推理（仅限已判定为非敏感数据的租户/场景，敏感数据不出域）；仍不达标则关闭 AI 建议，仅保留规则路径|

> **责任方（owner）**：架构=技术架构与一致性 · 底座=AI 平台与数据链路 · 理赔=理赔业务与规则 · 交付=集成实施与客户对接 · 安全合规=数据与合规准入。
>
> **跟踪机制**：上表每项风险须指定 owner 与复盘时点，纳入遗留风险台账（owner + 到期 + 状态），随复盘滚动更新。
