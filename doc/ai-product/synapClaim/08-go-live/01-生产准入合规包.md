# 01 · 生产准入合规包（PIA · 等保 · 算法备案 · SBOM）

> **目标态**：将《工程落地版》§11.3/§11.4 已识别但标"待建"的合规项（PIA/DPIA、等保备案、SBOM）与**全库 0 命中的 AI 算法备案**落地为可执行载体；对齐 PIPL、《个人信息保护法》、《生成式人工智能服务管理暂行办法》、金发〔2026〕8号、《网络安全等级保护条例》。这些是**对正式客户投产的法定前置**，不是可选优化。
>
> **范围**：本文只给"可落地内容草案 + 验收口径"，不替代法律意见；具体备案以监管最新口径与法务复核为准。

## 1.1 监管基线梳理（synapClaim 触发了哪些义务）

| 义务 | 触发条件（本系统命中） | 依据 | 当前状态 |
|---|---|---|---|
| **PIA / DPIA（个人信息保护影响评估）** | 处理敏感个人信息（医疗+金融）+ 自动化决策（AI 影响拒赔/给付） | PIPL 第 55 条 | §12.2 清单已增补，**无执行载体，待建** |
| **AI 自动化决策影响评估 + 报告回执** | 面客 AI 应用上线前须报告并留存回执 | 金发〔2026〕8号 第 29 条 | §11.4/§12.2 登记，**"备案"动作缺失** |
| **算法备案** | 具有舆论属性或社会动员能力的算法；或影响用户权益的自动化决策（拒赔直接减损用户权益） | 《互联网信息服务算法推荐管理规定》第 24 条、《生成式人工智能服务管理暂行办法》 | **全文档族 0 命中** |
| **网络安全等级保护定级备案 + 测评** | 处理大量公民敏感个人信息，按等保 2.0 至少二级、大型保司三级 | 《网络安全等级保护条例》 | 试点后启动定级备案（07-delivery/10 §四），测评未规划 |
| **SBOM + 依赖漏洞扫描** | 软件供应链安全（金融强监管） | 行业实践 + 等保"安全建设管理" | §2940 标"待建" |
| **渗透测试 + 等保测评** | 金融系统上线前强制 | 等保 2.0 测评要求 | 仅 OWASP ZAP（扫描器≠渗透） |

> **关键判断**：synapClaim 同时命中"敏感个人信息 + 自动化决策 + 影响用户权益"三重高敏感特征，**PIA + 等保 + 算法备案三者须并联推进**，且算法备案与金发 8 号第 29 条"报告回执"应共用一套材料（见 §1.7 闭环）。

## 1.2 PIA / DPIA 模板（可填，对齐 PIPL 第 55 条）

> 落地形式：一份 `PIA-synapClaim-<租户/产品>.md` 模板，每个正式租户/产品上线前填制并归档；归档编号入《工程落地版》§12.2 清单。

**字段清单（PIPL 第 55 条规定的必备内容）**：

| 字段 | 填写要点（本系统示例） | 对应既有控制 |
|---|---|---|
| 处理者/受托者 | synapClaim 运营方；保司/TPA 为共同控制者 | — |
| 处理目的与必要性 | 门诊小额快赔自动化核定；必要性=提升时效（≤30s 初筛）、降人工成本 | PRD §7 |
| 处理的个人信息类型 | 被保人身份（身份证/手机号，假名化 `insured_id_hash`）、医疗票据、理赔结论 | §11.3 假名化 |
| 敏感个人信息说明 | 医疗健康信息（票据/诊断）+ 金融账户（出款）均属敏感个人信息 | §11.3 |
| 自动化决策说明 | 决策图（`FraudScreen`+`AiAssess`）输出建议，自动通过跳过人工审核态但**不跳过反欺诈硬闸** | §7.3 / §6.3 `SUGGEST_REJECT` |
| 风险识别 | ① PII 泄露（传输/存储）；② prompt injection 操纵结论；③ 算法歧视导致误拒赔；④ 模型幻觉致资损 | §7.2 / §11.3 |
| 风险处置措施 | ① mTLS + KMS 双人分片 + HMAC 假名化 + WORM；② 网关 C8 脱敏/注入检测复用（不自研）；③ 公平化训练 + 分群偏差监控（MRM §1.4）；④ 资金三段式幂等 + 四向对账 | §11.3 / §7.2 / §11.7 |
| 对个人权益的影响 | 误拒赔（损害用户求偿权）、误付（资损）、歧视（平等权） | §6.6 法定时限 |
| 告知与权利保障 | 显著标识 AI 结论（金发 8 号第 21 条）、撤回/申诉通道（`/appeals`，§10.6） | 07-delivery/05 |
| 残留风险与接受理由 | 模型不确定性→fail-safe 转人工；残留风险由人工复核兜底接受 | §6.7 安全不变量 |
| 合规结论 | 风险可控，准予上线（附风险管理委员会批准，金发 8 号第 16 条） | §11.4 门禁 |

> **禁止写成"待建"空壳**：模板 + 首份正式租户 PIA 出具 + 归档编号，是 G3 门禁（总纲 §二）的验收证据。

## 1.3 等保定级备案路径

| 档位 | 适用 | 路径 | 现有控制覆盖度（自检） |
|---|---|---|---|
| **二级** | 试点 / 中小保司 | 定级报告 → 公安备案 → 等保测评（二级） | 身份鉴别/访问控制/审计/加密 基本覆盖（§11.3 mTLS/KMS/WORM）；缺**测评机构出具报告** |
| **三级** | 大型保司 / 监管强要求 | 定级 → 备案 → **三级测评**（更严：入侵防范/恶意代码/集中审计） | 同上 + 需补 **WAF/边界防护 + 审计物理分离（§5.2）+ 渗透测试（§1.6）** |

**备案材料清单**：定级报告、网络拓扑、安全管理制度、应急预案、测评机构出具的《网络安全等级保护测评报告》。
**与现有控制映射（避免重做）**：

| 等保控制项 | 本系统既有落地 | 缺口 |
|---|---|---|
| 身份鉴别 | OIDC + 认证主体为租户权威（§3.3） | — |
| 访问控制 | RBAC + 数据权限 + 禁授权后门（§2799） | — |
| 安全审计 | WORM Object Lock ≥7 年（§11.3） | 审计库与业务库物理分离（§5.2） |
| 加密 | KMS 双人分片 + HMAC + mTLS（§11.3） | — |
| 入侵防范 | — | **WAF（§3 容量包）+ 渗透测试（§1.6）** |
| 数据完整性 | append-only 表禁 UPDATE/DELETE（§11.3） | hash 链（§5.2） |

## 1.4 AI 算法备案（填补全库 0 命中）

> 触发判断：本系统决策图直接影响"通过/拒赔/金额"，属"影响用户权益的自动化决策"，**应当备案**。即便不单独走算法推荐规定，金发〔2026〕8号第 29 条已要求"上线前报告并留存回执"，二者材料同源。

**备案/报告材料清单（建议合并一套）**：

| 材料 | 内容 | 数据来源 |
|---|---|---|
| 算法/模型清单 | 进入 `AiAssess`/`FraudScreen` 的全部模型（视觉 E1、图 E2、LLM 评测） | MRM 模型卡（T6 / BONE-AI 增强 §1.2） |
| 算法原理与目的 | 决策图 6 节点（`FraudScreen`→`AiAssess`→…）、输入输出、置信度三档 | §7.3 |
| 数据来源与训练 | 训练/微调数据范围、是否含个人医疗信息、脱敏方式 | §11.3 |
| 人工干预机制 | `SUGGEST_REJECT` 一律人工确认后生效、自动通过 fail-safe 转人工 | §6.3 / §6.7 |
| 用户权益保障 | 显著标识 AI 结论、申诉通道、撤回权 | 金发 8 号第 21 条 / 07-delivery/05 |
| 风险与防控 | PIA 风险处置（§1.2） | PIA 报告 |

**落地动作**：
1. 建 `algorithm-filing-synapClaim.md` 模板，字段直接对齐上表与 MRM 模型卡（避免双份维护）。
2. 每个新模型启用前，模型卡（C7 评测门禁）必须存在且字段齐备（MRM §1.2 已要求"无模型卡不得启用"）。
3. 备案/报告回执编号写入《工程落地版》§12.2 清单 → 这是 G5 门禁证据。

## 1.5 SBOM + 依赖漏洞扫描门禁

> **执行状态**：✅ **已落地并实机验证**（2026-10-28）。`bone-apps/synap-claim/pom.xml` 已加 `cyclonedx-maven-plugin`（独立 `sbom` profile，不绑默认 lifecycle，避免离线构建崩），`scripts/gen-sbom.sh` 封装调用。实跑 `mvn -P sbom verify` 成功产出 `target/bom.json`：合法 **CycloneDX 1.4**，含 **129 个组件**（全依赖树含 `spring-boot-starter`、各 `bone-*` 模块），可直接喂 `Dependency-Track`/`grype` 做漏洞门禁。插件首次运行需联网下载（一次性，已缓存至 `~/.m2`），后续 CI 可离线复用。

| 项 | 建议 | 范围 | 门禁 |
|---|---|---|---|
| 工具 | `cyclonedx-maven-plugin`（✅ 已配 `sbom` profile）+ `grype`/`Dependency-Track` 扫描 | `bone-apps/synap-claim` jar（其余模块同法推广） | CI 阻塞 |
| 生成对象 | `bone-apps/synap-claim` jar（已验证）、Docker 镜像、`bone-ai-*` 客户端、`bone-metadata-sdk`、`Docling` sidecar、前端 `claimApi` | 镜像 + jar | 每次构建 |
| 漏洞门禁 | **高危（CVSS≥7.0）0 通过**；中危限期修复 | SBOM 全量 | 高危阻断发布 |
| 产物留存 | SBOM 随版本归档，与 PIA/备案同册 | 发布物 | 审计可追溯 |

> 与现有 §11.14 依赖扫描呼应：把"待建"转为"CI 门禁 + 产物归档"，这是 G6 门禁证据。
> **CI 接入要点**：① `sbom` profile 不绑默认 lifecycle，CI 显式 `mvn -P sbom verify`（或 `bash scripts/gen-sbom.sh`）；② 首跑联网下载插件，建议 CI 缓存 `~/.m2`/插件目录；③ 产物 `target/bom.json` 归档并接入漏洞扫描，高危 0 方放行。

## 1.6 渗透测试 + 等保测评门禁（ZAP ≠ 渗透）

| 测试类型 | 角色 | 频率 | 门禁 |
|---|---|---|---|
| OWASP ZAP（既有） | CI 常态化扫描（越权/注入/敏感泄露） | 每次构建 | 高危 0（已落地 07-delivery/07） |
| **专业渗透测试** | 第三方/红蓝人工对抗（含越权横向、业务逻辑、支付绕过） | **上线前一次性 + 重大变更** | 无高危未闭环不得投产 |
| **等保测评** | 测评机构按等保级别出具报告 | 定级后 + 重大变更 | 测评通过（G4） |

> 重点补强：ZAP 不覆盖**业务逻辑越权**（如伪造 `X-Tenant-Id` 跨租户读案、并发占额绕过），这些必须靠人工渗透 + §4 租户隔离 CI 护栏双保险。

## 1.7 模型卡 ↔ 备案/报送闭环（P2-4）

> 避免"MRM 模型卡（T6）"与"算法备案/金发 8 号报送"各做一套。把模型卡字段**直接对齐**备案/报送要求，一处维护、多处复用。

| MRM 模型卡字段（§1.2） | 算法备案/金发 8 号报送字段 | 复用方式 |
|---|---|---|
| `intendedUse` | 算法目的 | 同字段 |
| `biasAssessment` | 用户权益保障/公平性 | 同字段 + 分群偏差阈值 |
| `driftPolicy` | 风险防控（持续监测） | 同字段 |
| `modelId` + 版本 | 模型清单 + 变更报送 | 同字段 |
| `humanIntervention` | 人工干预机制 | 同字段（§6.3） |
| `evaluationGate` | 评测门禁证据 | CI 门禁产物直接作为报送附件 |

**闭环动作**：模型卡（C7）更新 → 触发"是否触发备案/报送变更"判定 → 是则生成/更新 `algorithm-filing` 增量并重新报送。命名 `model-card-to-filing-mapping.md` 固化映射。
