# 08 · 规则发布鉴权与防投毒

> **定位**：补齐 `outputs/synapClaim-生产就绪独立诊断.md` 盲区 **B3**。系统已规划"规则热更 + 评测门禁"（《业界对标整改台账》P0-2 反欺诈图/视觉、Rulebook `07-delivery/04`），但**发布通道本身的安全**——谁有权发、发了能否被篡改、发错能否秒级回滚——是另一道防线。一条恶意或错误规则可造成**规模化错赔**，与"资金零差错"原则（§7.5）直接冲突。
>
> **业界基准**：NIST SP 800-53 `CM-5`（变更访问控制）、`SI-7`（软件/固件完整性）、`AU-6`（审计评审）；支付/保险系统的"规则/模型发布双人复核 + 签名 + 灰度 + 回滚"是资金安全标配。

---

## 一、威胁模型：规则即攻击面

| 威胁 | 路径 | 影响 |
|---|---|---|
| 内部越权发布 | 单点账号被盗/误操作，直接推送错误规则 | 规模化错赔/漏赔 |
| 规则篡改（中间人/存储） | 规则包传输/落库被篡改 | 静默植入恶意赔付逻辑 |
| 错误规则上线 | 评测门禁未覆盖的边界场景 | 个别案件大额资损 |
| 回滚不及时 | 发错后无快速通道 | 资损窗口扩大 |

> 现有"评测门禁"是**质量门**（保证规则效果），本册是**安全门**（保证发布可信、可恢复）。二者互补，不可替代。

---

## 二、防投毒控制矩阵（须建设）

| 控制 | 机制 | 验收（可证伪） |
|---|---|---|
| **双人复核** | 规则发布须 `publisher + approver` 两角色分离，同人不可自批 | 发布记录含两独立签名身份 |
| **数字签名** | 规则包带 `publisher` 与 `approver` 双签名（非对称密钥），加载时**验签失败拒绝加载（fail-closed）** | 篡改后的规则包在加载端被拒，有拒绝日志 |
| **不可变版本** | 每条规则版本一经发布**不可变**，更新=新版本；历史可审计 | 规则版本表 append-only，无 UPDATE 原值 |
| **灰度发布** | 按租户/比例灰度（如 1%→10%→100%），灰度期监控赔付偏差 | 灰度开关存在；灰度指标异常自动暂停 |
| **秒级回滚** | 保留上一已签版本，回滚 = 切回该版本（不重新构建） | 回滚演练 < 分钟级生效 |
| **发布审计** | 全量发布日志：谁/何时/什么内容/哈希/灰度范围 | 日志入 WORM 审计（§11.3） |
| **加载失败熔断** | 验签失败/版本缺失/灰度指标超标 → 拒绝使用该规则，回退确定性兜底 | 故障注入测试：注入坏规则包 → 系统拒绝而非执行 |

---

## 三、与现有 Rulebook 的衔接

- `07-delivery/04-Rulebook` 是**规则内容真源**；本册在其**发布通道**上叠加安全控制，不改变规则定义本身。
- 评测门禁（P0-2 已规划）在发布**前**拦截低质规则；本册控制在发布**中/后**保证可信与可恢复。
- 灰度指标应与 §7.3 的 AI 置信度阈值、错误预算（P2-3）联动：灰度期赔付偏差超错误预算 → 自动暂停发布。
