## 1. 执行摘要

### 1.1 产品定位

synapClaim 是保险行业首个 **“智能决策操作系统”（Claim OS）**，以“决策图”为核心，将AI概率推理与规则确定性统一收敛，实现理赔全流程的自动化、智能化与配置化。

### 1.2 核心矛盾与解法

保险理赔面临\*\*确定性（规则）与不确定性（AI）\*\*的结构性冲突：

- 传统规则引擎：僵化但资金安全，难以应对复杂医疗场景

- 纯AI方案：灵活但不可控、不可解释，无法通过金融监管审计

  **synapClaim 解法**：

  ```plaintext
  资金安全层（100%确定性 Java 内核） → 决策收敛层（规则+AI融合） → 效率增强层（AI原生）
  ```

  通过 **确定性分层架构**，将AI的不确定性与金融核心的确定性完美解耦。

### 1.3 关键指标承诺

|**指标**|**目标值**|**行业基线**|**提升幅度**|
|---|---|---|---|
|自动化率（STP，分阶段：POC ≥60%/MVP ≥70%/规模化 ≥80%）|≥80%|30%|2.7x|
|建议结论时效（P95，提交→返回建议结论）|≤30秒|3-7天|10,000x|
|新保司接入周期|≤7天|2-4周|3x|
|单案处理成本|≤8元|15-25元|↓50%|
|资金差错率|0（生产出款口径；mock 期口径=幂等+对账测试 100%，随 Phase C 启用）|0.01%|100%|
|系统可用性|**99.9%（一期对外承诺档，单集群形态）**；**99.99% 自 V2 同城双活起适用**——一期不得对外承诺 99.99%（见 §13.2 / 落地版 §11.8 档位映射）|99.9%|金融级|


### 1.4 商业价值（ROI）

- 成本下降 ≥50%（人工成本从40%降至20%）

- 时效提升 10倍（从天级到秒级）

- 赔付损失率 ↓≥30% 为 V2 多智能体风控能力；一期由规则反欺诈 R-FRAUD + 后督抽检部分兑现，不对一期做全额承诺

- 投资回正周期：6-9个月（客户视角，测算口径见 §17 ROI测算）

## 4. 产品范围与约束

### 4.1 包含范围

- 理赔申请、单证采集、智能审核、决策、理算、支付、结案、后督

- 多保司多租户管理

- 规则引擎、决策图配置、低代码表单

- **存量系统集成**（与客户既有理赔/保单/报案/资金系统打通，旁路→辅助→自动三阶段，详见《存量系统集成与快速部署（FDE）方案》）

### 4.2 不包含范围

- 核保系统（保单承保）

- 核心财务总账系统（仅提供对账接口）

- 医院HIS直连（提供标准API，由保司或TPA负责对接）

### 4.3 约束条件

- 必须遵守《个人信息保护法》及保险行业数据安全规范

- 所有资金操作须满足金融级审计要求（日志保留≥7年）

- 支持信创环境：国产数据库（TiDB）、操作系统（麒麟）、CPU（鲲鹏/海光）

### 5.1 MVP 核心需求条目（BDD 规格）

> 以下 8 条为 MVP 纵向切片（门诊小额快赔）的核心需求，按“需求ID + 用户故事 + BDD验收 + 业务规则 + As-Is/Gap”规格展开，作为迭代开发（见《MVP 可落地执行方案》）的直接输入；其余需求见 §7 功能表。

**RQ-MVP-001 材料解析与字段提取**

|**维度**|**内容**|
|---|---|
|用户故事|US-01：作为员工，我希望上传发票照片后系统自动识别金额和医院，以便无需手动填写|
|BDD 验收|Given 一张清晰的二级公立医院门诊发票 When 上传后 Then 异步受理（202）并返回解析结果：单张 ≤5s（P95，工程落地版 §11.2 口径卡）返回医院/金额/日期/诊疗项目字段，且每个字段带置信度与原文证据位置；Given 发票模糊或翻拍 When 上传 Then 提示重传并标记 OCR 置信度<阈值|
|业务规则|发票/清单/病历/医保结算单（MEDICAL_SETTLEMENT，R-DED-03 三段拆分输入）四类材料自动分类；金额以“发票价税合计”为准；字段缺失不允许默写（宁缺勿猜，缺则转人工/补件）|

|**维度**|**内容**|
|---|---|

**RQ-MVP-004 拒赔解释与申诉**

|**维度**|**内容**|
|---|---|

### 6.2 简化资金状态机（两段式）

> **设计取舍**：理赔资金流向单一（审核通过后单笔支付）、并发量低，采用**软预占→硬预占→已支付**两段式即可满足资金安全与审计（聚合根内乐观锁 + `funding_events` 事件溯源）。
> 五段式（预分配/分配）面向信贷分账户等复杂账务场景，本方案不采用，避免过度设计；如未来扩展账户池/分期赔付，可按 V3+ 演进预留。

主路径所有资金操作必须经过以下三个阶段，确保资金安全零差错；补偿态（复核冻结/释放/失败/退款）见下方状态图：

|**阶段**|**状态**|**业务含义**|**技术实现**|**回滚策略**|
|---|---|---|---|---|
|Stage 1|软预占|余额充足性校验|聚合根内 `@Version` 乐观锁（**禁 `SELECT FOR UPDATE`**）|写 `RELEASED` 事件释放预占|
|Stage 2|硬预占|扣减冻结金额；大额（≥1万元）触发双人复核|聚合根内 `@Version` 乐观锁|复核不通过转 `RELEASED`；支付失败转 `FAILED` 回冲|
|Stage 3|已支付|支付网关成功，生成不可变资金流水|调用支付网关 + 事务提交，写 `funding_events`|不可逆，仅可发起退款（生成红冲发票）|


状态转换图：

```plaintext
stateDiagram-v2
    [*] --> SOFT_RESERVED: 决策通过，启动理算
    SOFT_RESERVED --> HARD_RESERVED: 余额充足，乐观锁冻结
    SOFT_RESERVED --> [*]: 余额不足 → 转人工/垫付评估

    HARD_RESERVED --> REVIEW_FREEZE: 大额（≥1万元）进入双人复核
    REVIEW_FREEZE --> HARD_RESERVED: 复核通过，解除冻结
    REVIEW_FREEZE --> RELEASED: 复核不通过，释放预占
    HARD_RESERVED --> PAID: 支付网关成功，生成不可变流水
    HARD_RESERVED --> FAILED: 支付失败，回冲硬占
    HARD_RESERVED --> RELEASED: 撤销/放弃，释放预占

    PAID --> [*]: 结案，电子发票 + 存证哈希（区块链存证为可选项）
    PAID --> REFUNDED: 发起退款（红冲发票）
```

> **补偿态不可省**：`REVIEW_FREEZE`/`RELEASED`/`FAILED`/`REFUNDED` 是两段式主路径的必要分支（大额复核、复核不通过、支付失败、已付退款），状态机真源为工程落地版 §6.4/§7.5 与 Saga 补偿矩阵 §11.1.2；资金状态机仅由 A7 `Settlement` 聚合根推进，AI 层无写入口。

### 6.3 决策图引擎

- **节点类型**（工程落地版 §7.3 为准）：`EvidenceLoad`（证据装载与解析）、`RuleCheck`（核责）、`AiAssess`（AI 评估）、`Arbitrate`（确定性仲裁）、`Adjust`（理算）；对外 `node_type` 仅 `OCR`/`RULE`/`LLM`/`DECISION` 四类。规则引擎 QLExpress（`bone-ai-rules`），LLM 接入 `bone-ai-gateway`。

- **执行特性**：拓扑排序并行、证据传递、短路优化、人机回环

- **AI降级**：每个AI节点可配置 `fallback_rule_node`，超时或失败自动回退规则

### 6.4 设计原则

- **配置优先于编码**：业务差异通过元数据配置，非硬编码

- **决策集中化**：所有终审必须经过决策图，输出单一事实源

- **事件驱动解耦**：上下文间通过领域事件通信（一期进程内事件总线 + 事务性发件箱，RocketMQ 二期；选型真源：工程落地版 §3.8）

- **幂等与补偿**：所有写操作基于幂等键，Saga处理长事务

- **可观测性**：OpenTelemetry统一埋点，全链路追踪

### 8.5 申诉与复议流程

> 拒赔不是终点：被保险人对拒赔结论有异议时可发起申诉，进入人工复议通道（满足《保险法》对拒赔说明理由与及时核定的要求，避免客诉升级）。
>
> **监管基线（2026-10-14 补录）**：① **金发〔2026〕8号**（2026-06-18，金融监管总局）——承保理赔列高风险业务，关键环节须建立人工监督和干预机制，可解释性不足的模型仅能辅助；故本 PRD“自动拒赔”一律指“系统建议 + 人工确认后生效”；② **《保险法》第23/24条**——30 日内核定（情形复杂 +10 日）、核定后 3 日内发出拒赔通知书并说明理由；③ **法定时限状态机**：报案 T0 → 立案 ≤T0+1d → 核定 ≤T0+30d（复杂 ≤40d）→ 拒赔通知 ≤核定+3d → 申诉 48h 响应，各节点超时前置预警，对应工作台 SLA 提醒与后督抽检。；④ **上线前置（金发〔2026〕8号第 16/21/29 条）**：高风险 AI 应用上线须经甲方风险管理委员会批准（第 16 条）、面客/高风险生成式 AI 应用向监管报告并留存回执（第 29 条）、AI 参与生成的内容/结论带显著标识（第 21 条）——未完成前仅限试点/Shadow 模式运行。

```plaintext
flowchart LR
    A[拒赔通知（含理由与条款依据）] --> B[员工发起申诉]
    B --> C[自动复核：重放决策轨迹 + 相似历史案件匹配]
    C -->|证据充分| D[复议通过 → 重新进入理算支付]
    C -->|证据不足| E[资深核赔员人工复议（48h内响应）]
    E -->|维持原判| F[出具最终复议意见书（可向监管/仲裁机构申诉）]
    E -->|改判| D
```

**配套规则**：申诉案件进入内部状态码 `60`（申诉中，48h 复议）——**对外状态仍投影为 `REVIEWING`**，不新增对外枚举值（真源 `delivery/05`，见 §12.1）；原拒赔决定在复议期间不产生新费用；复议结果必须留痕（决策轨迹+复议意见），审计可追溯。

|医保接口不稳定|中 / 高|医保通道错误率>5% 且持续 10 分钟|交付|熔断降级为企业垫付；多通道备用；本地缓存|退回垫付/转人工通道，暂停直付|
|新保司配置复杂|低 / 中|新保司接入耗时超 7 天里程碑|交付|提供配置模板和向导式界面；提供沙箱环境|该保司暂不接自动化，仅旁路同步|
|用户数据安全|低 / 极高|明文凭证扫描命中；或未授权访问告警|安全合规|等保三级认证；数据加密；隐私计算；操作审计|停止数据流出、切换本地推理；按工程落地版 §11.3 启动安全响应|
|长流程状态丢失|低 / 高|发件箱积压超阈值；或死信队列非空|底座|事件溯源 track 聚合（append-only）+ 幂等回调 + 死信队列|从 append-only 流水重放恢复；暂停自动推进|
|向量检索召回率不足（二期 RAG 能力）|中 / 中|二期：检索命中率不达评测线|底座|备用 Milvus；混合检索（向量+关键词）|切 Milvus；相关结论转人工|

> **责任方（owner）**：架构=技术架构与一致性 · 底座=AI 平台与数据链路 · 理赔=理赔业务与规则 · 交付=集成实施与客户对接 · 安全合规=数据与合规准入。

### 16.3 关键假设

1. **假设1**：保司提供的保单数据质量满足基本要求（保单号唯一、保额有效）。

2. **假设2**：OCR对主流医院的发票识别准确率可达95%以上（基于训练数据集）。

3. **假设3**：AI 置信度阈值按三档分派（<0.7 强制人工终审 / 0.7–0.85 复核档 / ≥0.85 直出）可平衡自动化率与风险，后续可根据数据调整。

4. **假设4**：单模块 + 事件溯源的流程持久化能支撑年千万级案件量（需压测验证）。
