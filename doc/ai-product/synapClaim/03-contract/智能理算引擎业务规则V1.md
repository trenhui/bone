## 1 概念与层级模型

### 1.1 承保层级〔定〕

```
团险：保险保单 ─┬─ 计划1（计划额度）─┬─ 险种A（险种额度）─┬─ 责任a（责任额度）
                │                    │                    └─ 责任b
                │                    └─ 险种B
                └─ 计划2（计划额度）
个险：保险产品条款 ─ 险种 ─ 责任（保额由个单额度提供）
```

- 一个保单有多个计划；**计划额度**控该计划下所有险种与责任的赔付总额〔定〕
- 一个计划下有多个险种；**险种额度**控该险种下所有责任的赔付总额〔定〕
- 一个险种下有多个责任；每个责任分别配置**责任额度**〔定〕
- 个险：产品 → 险种 → 责任；额度以个人保单实际额度为准，责任可不设保额〔定〕
- 责任是**理算的最小单位**，赔付金额同时受险种与保单额度控制〔定〕

**责任配置校验〔定〕**
1. 同一计划下所有责任，**责任名称不可重复**；
2. **保司责任代码可在不同责任重复**配置；
3. 不同计划下的责任名称可重复。

### 1.2 额度扣减层级（7 层）〔定〕

理算流程图明确给出责任内额度顺序与理算后的扣额对象：

```
① 发票费用项目可用金额
② 发票费用类型可用金额
③ 责任次限额金额
④ 责任共保可用金额
⑤ 责任可用金额
⑥ 险种可用金额
⑦ 计划可用金额
```

这 7 层是**从细到粗**截断的顺序，也是本引擎与普通"单责任算钱"最大的结构差别——**第③④⑥⑦层在多数 TPA 系统里不存在，但它们决定了团体保单是否会超赔**。

### 1.3 账户维度〔定〕

| 账户 | 定义 | 范围 |
|---|---|---|
| 个账 | 投保单位**具体个人**在该保单下**所涉责任**在该账户下的可赔额度 | 单个被保险人 |
| 公账 | 投保单位**所有员工**在该保单下**所涉责任**在该账户下的可赔额度 | 全保单共享 |

- 「所涉责任」= 责任配置中「账户类型」指向该账户的责任〔定〕
- 一保单**只有一个公账额度**，且目前挂在**直付保单**上，故公账必须走直付保单〔定〕
- 各责任额度**各自限额**，与账户额度是"双重控额"关系〔定〕

> 原文示例：保单 A 个账 10 万、公账 500 万，承保主被保险人 100 人；个账所涉责任 a/b/c 累计上限 10 万，公账所涉责任 d/e 累计上限 500 万。示意图中 a/b/c 各 5 万 —— 说明**账户额度是共享池、责任额度是池内个人上限**，两者取小〔推〕。

### 1.4 理算对象粒度〔定〕

```
赔案 → 发票（多张）→ 费用类型（合理金额 / 自付二 / 总自费 / 自定义）
```

理算的基本单元是 **(发票, 责任)** 二元组，输出"发票单责任赔付金额"；再按赔案汇总。

**保额语义〔定〕**

| 保额形式 | 费用报销型 | 定额给付型 | 津贴给付型 |
|---|---|---|---|
| 固定保额 | 赔付**限额** | 赔付**金额** | — |
| 基础保额 | 非特殊约定下的赔付限额 | 特殊约定时：赔付金额 = 基础保额 × 赔付比例 | 特殊约定时：赔付金额 = 津贴单位保额 × 数量 |
| 固定保额 + 个人额度 | 受固定额度与个人额度**双重控额** | 同左 | 同左 |
| 个单额度 | 额度由客户保单提供，责任不设保额 | 同左 | 同左 |

> 〔疑〕原文写"赔付保额 = 「具体适用情形」×「对应赔付比例」"。"适用情形"是枚举（医疗/意外…），不是数值，此式无法计算；结合上下文应理解为"**基础保额 × 赔付比例**"或"**津贴单位保额 × 数量**"。见 10 章 Q-09。

## 3 发票结算口径（计算底座）

### 3.1 字段〔定〕

| 字段 | 说明 |
|---|---|
| 医疗总费用 | 发票医疗费用合计 |
| 医保统筹比例 | 该票适用的统筹比例 |
| 医保起付线 | 该票起付线 |
| 自付一 | 统筹自付（口径有争议，见 3.3） |
| 自付二 | 乙类先行自付 + 乙类自费 |
| 丙类自费 | 丙类费用 |
| 超限价自费 | 超限价部分 |
| 总自费 | 丙类其他自费 + 超限价自费 |
| 基金支付总额 | 基本统筹 + 其他基金 |
| 个人负担 | 见 3.3 |
| 其他基金 | 大额补充 / 大病保险 / 求助基金 / 公务员医疗补助 / 企业补充医疗基金（**地区差异，不固定**） |

### 3.2 六个公式〔定〕

```
基本统筹金额 = (医疗总费用 − 起付线 − 自付二 − 丙类自费 − 超限价自费) × 统筹比例
基金支付总额 = 基本统筹金额 + 其他基金金额
总自费       = 丙类自费 + 超限价自费
自付二       = 乙类先行自付 + 乙类自费
```

### 3.3 「自付一」与「个人负担」的原文自相矛盾〔疑〕

原文两张表给了两个互斥的「自付一」定义：

| 来源 | 自付一公式 |
|---|---|
| 责任配置要素表 | 自付一 = (总费用 − 起付线 − 自付二 − 丙类 − 超限价) × (1 − 统筹比例)　**不含起付线** |
| 发票医保结算表 | 自付一 = 起付线 + (总费用 − 丙类 − 超限价 − 自付二 − 起付线) × (1 − 统筹比例)　**含起付线** |

而「个人负担 = 自付一 + 自付二 + 总自费 + 起付线」两处一致。代进去就能看出**只有第一种定义成立**：

设 总费用 2000、起付线 500、自付二 0、丙类 0、超限价 0、统筹比例 80%：
- 基本统筹 = (2000−500)×0.8 = **1200**
- 定义一：自付一 = 1500×0.2 = **300** → 个人负担 = 300+0+0+500 = **800** = 2000−1200 ✅
- 定义二：自付一 = 500+300 = **800** → 个人负担 = 800+0+0+500 = **1300** ❌ 多算了一个起付线

**判定**：采用定义一（自付一不含起付线）；「个人负担 = 自付一 + 自付二 + 总自费 + 起付线」保持原样。定义二的公式属笔误，若照抄会**每个有起付线的发票多算一次起付线**。

### 3.4 企补合理金额：三种表达式**不等价**〔定+推〕

原文给了三个等价写法，并注明"（新TPA现有逻辑）"挂在第一个上：

```
① 合理金额 = 医疗总费用 − 基金支付总额 − 总自费 − 自付二 − 三方支付 − 不合理费用
② 合理金额 = 自付一 + 起付线
③ 合理金额 = 个人负担 − 总自费 − 自付二
```

- ② 与 ③ **恒等**（由 3.3 的恒等式直接得出）〔推〕
- ① 与 ② **仅在「三方支付 = 0 且 不合理费用 = 0」时等价**〔推〕：

```
① = (总费用 − 基金支付总额) − 总自费 − 自付二 − 三方 − 不合理
   = 个人负担 − 总自费 − 自付二 − 三方 − 不合理
   = ② − 三方 − 不合理
```

**这条差别是实质性的**：企补场景里"三方已赔"恰恰常态不为 0（社保先赔、个险后赔、团险再补），若用 ②/③ 而不扣三方支付，会**把已由第三方赔付的钱再赔一次**。故：

> **口径**：默认取 ①（含扣三方与不合理）。②③ 仅作为"无第三方赔付、无核减"场景下的校验用恒等式。

另附可自定义合理金额公式（"通用版本无法满足业务时"）〔定〕，引擎须支持表达式插槽而非硬编码。

〔推〕**落地口径：① 的两个扣减项分别落在两处，不能任何一侧重复扣。** 引擎消费的 `valid_amount` 由初审核定写入（`ClaimItem#approveValidAmount`），口径是「明细金额 − 核减（不合理费用）」，差额自动记 `invalid_amount`——所以它**已含「不合理费用」的扣除，但尚未扣统筹与第三方已付**。对应的分工是：

| 扣减项 | 唯一扣除点 | 数据落点 |
|---|---|---|
| 不合理费用（核减） | 初审核定（上游，且只做一次） | `valid_amount` 已扣、差额进 `invalid_amount` |
| 统筹支付 + 第三方已付 | 理算归集（`FeePools.aggregate`） | 归集时从 `valid_amount` 净扣，`clamp ≥ 0` |
| 已付 > 合理 | 一致性校验（`checkSettlementConsistency`） | 拒绝 `INVOICE_SETTLEMENT_INCONSISTENT` |

任一侧重复扣即少赔（客户吃亏），漏扣即超赔（不可获利原则破）。`invalid_amount` 因此**不需要被理算读取**——它是上游核减的事实记录，不是待扣金额；把它再扣一遍是最容易犯的一次双扣。

### 3.5 医保范围内 / 范围外拆分〔定+推〕

```
医保范围内（统筹+合理）= (总费用 − 基金总支付 − 自付二 − 总自费 − 三方已赔 − 不合理) + 基金总支付
                      = 总费用 − 自付二 − 总自费 − 三方已赔 − 不合理金额
医保范围外（自费+乙类）= 总自费 + 自付二
```

〔推〕两式相加 = 总费用 − 三方已赔 − 不合理金额，即"可赔基数"，与 ① 的合理金额 + 基金支付 + 自付二 + 总自费口径自洽。

### 3.6 企补三个费用池〔定〕

| 池 | 公式 |
|---|---|
| 企补理赔合理金额范围（通用） | 同 3.4 ① |
| 企补理赔自费范围 | 总自费（丙类自费 + 超限价自费） |
| 企补理赔部分自费 | 自付二 |
| 企补理赔不合理金额 | 三方已报销 + 团险责任外购药 + 诊断不符的药费等 |

## 4 单发票 × 单责任 理算主流程

### 4.1 前置校验（不过即退回，不进理算）〔定〕

流程图给出三路并行校验，任一不符即"提示"并走「理赔流程校验退回」：

| 校验路 | 输入 | 校验内容 |
|---|---|---|
| 发票结算数据校验 | 发票结算数据 List | 是否符合发票结算理算规则 |
| 出险人信息校验 | 出险人信息 | 是否符合出险人理算规则（等待期、适用对象） |
| 保单责任数据校验 | 保单责任数据 List | 是否符合保单责任理算规则（适用限定、责任有效期） |

前置校验之前还有一道「赔案前置流程规则」校验：不符合进入理算流程的赔案**根本不进理算**〔定〕。

#### 4.1.1 适用限定的落地口径〔定〕

三路校验里，「保单责任数据校验」的**适用限定**此前是"配了不生效"：`t_adj_liability` 没有对应列，引擎里 `LimitedConditions` 恒为 `disabled()`，唯一分支是"一旦启用就整条拒绝"。现在按事实可得性分两层落地：

| 维度 | 状态 | 判定事实 | 说明 |
|---|---|---|---|
| 医院 | **已落地** | `t_claim_case.hospital_code`（V10 随「次」分组落地） | 按编码比对，不按名称——名称可改，编码是身份 |
| 病种 | **已落地** | `t_claim_case.diagnosis_code`（同上） | 一次就诊一个主要诊断 |
| 区域 / 医保 / 药品 / 诊疗 | **无配置列** | 无 | 依赖外部目录（药品/诊疗编码表）或保单层面的区域划分口径，本仓库无法闭环。**故意不建列**：表达不出来，就不会出现"配了但引擎不读" |

四项判定纪律：

| 情形 | 结论 | 为什么不能是别的 |
|---|---|---|
| 白名单命中 / 黑名单未命中 | 正常理算 | — |
| 白名单未命中 / 黑名单命中 | `LIMITED_CONDITION_NOT_MET`（该责任不适用，正常拒付） | 与"算不出来"分开：这是业务结论，不是系统缺陷 |
| 案情缺该维度编码 | `LIMITED_CONDITION_UNDETERMINED` | 按"符合"放行 ⇒ 白名单形同虚设；按"不符"拒赔 ⇒ 替客户下了拒赔决定，而原因只是录入漏了 |
| 同案出现多个编码 | `LIMITED_CONDITION_UNDETERMINED` | 这两列是**发票级**事实（一案一值），多值说明数据串了，任取其一都可能把不该赔的判成该赔 |

两维同时配置时取**与**：条款里"限 A 医院"与"限 D 病种"是同一条责任的叠加限制，任一维不符即整条不适用。模式（白/黑）是**责任级单一模式**——"医院白名单 + 病种黑名单"这种混用 V1 没有依据，需由两条责任表达，不在这里发明语义。

装载期两条反向一致性校验：「启用了模式但两个名单都空」拒绝（白名单空 = 全不赔、黑名单空 = 不设限，都不是业务意图）；「配了名单但模式为 `NONE`」时名单被忽略——所以配置岗必须显式开模式，不存在"填了名单就自动生效"的隐式路径。

### 4.2 主流程九步〔定〕

进入理算后：**费用归类型 → 发票匹配责任（发票医疗类别 × 责任医疗类别）→ 一发票一责任控制 → 逐责任三项定型 → 计算 → 控额 → 汇总**。

| 步 | 逻辑点 | 规则 |
|---|---|---|
| 1 | 定「适用情形」 | 由责任配置的【医疗】确定「发票医疗类别」与「承担医保费用类型」 |
| 2 | 定「适用情形」金额 | 取发票结算信息中对应字段金额 |
| 3 | 定「赔付比例」 | 同一比例 → 直接取；不同比例 → 按「赔付比例要素」匹配发票信息，**定位到唯一适用的比例** |
| 4 | 定「免赔信息」 | 6 子维，见第 6 章；默认：绝对免赔 / 按年度 / 免赔金额 / 医保三方均可抵扣 / 对象=理算金额 / 不同免赔按医保费用类型 |
| 5 | 算「免赔后理算金额」 | 按「免赔对象」决定扣免赔与乘比例的**先后**，见 6.3 |
| 6 | 累加费用类型 | 发票单责任理算金额 = Σ(各费用类型金额 × 各费用类型赔付比例) 再作免赔处理 |
| 7 | 责任内控额 | 按「扣减方式」在 7 层额度上逐层截断，见第 7 章 |
| 8 | 次限额分组 | 按「次」的定义分组，各组分别理算赔付（见 7.3） |
| 9 | 扣减与落账 | 在对应各「可用额度」上扣减本次赔付，更新余额 |

**日限额的位置**〔定〕：日限额**不单独成步**，它夹在「每组次限额之后、责任额度截断之前」生效（见 7.4）。原文流程图没有这一步，正是"配了不生效"的来源——配置页能填、能保存、能自检，赔付金额里却完全不起作用。按本文口径实现后，第 8 步的每组结果还须再过一次"当日可用额"。

**第 3 步的匹配语义要特别注意**〔定〕：赔付比例是一个**多维查找表**，不是一个数值。匹配不中必须 fail-closed，不能回落默认比例——示例配置的截图显示矩阵按「承担费用类型 × 区分医保赔付 × 费用限额 × 赔案累计区间」展开，任一维缺格都是配置缺失。

### 4.3 精确计算式（两个 Min 嵌套）〔定〕

原文给出的责任级理算公式（示例 2）：

```
责任理算金额 = Min(
                  Min(医保范围内 × 对应赔付比例, 医保范围内可用额度)
                + Min(医保范围外 × 对应赔付比例, 医保范围外可用额度),
                  责任可用额度
                )
```

即：**先按费用类型分级"比例折算 + 该类额度截断"，再求和，最后用责任额度截断**。这个嵌套顺序决定了"某一类费用额度用尽"不会吞掉另一类的可用额度。

## 5 赔付比例规则族

### 5.1 两种形态〔定〕

| 形态 | 语义 |
|---|---|
| 同一比例 | 该责任下所有费用类型用同一个比例 |
| 不同比例 | 按「不同比例因素」组合定位比例；**因素值间存在与「责任形式」「适用情形」的联动互斥关系** |

### 5.2 11 个「不同比例因素」〔定〕

区分：医保目录类型、医保费用类型、医保赔付（有/无）、医院等级、医院性质、疾病类型、年龄区间、赔付次数、程度比例、发票总费用分段区间、本案理算金额分段区间、**保单内历史赔案累计分段区间**。

### 5.3 配置矩阵的真实维度〔定，来自配置截图〕

示例 1 的配置界面显示，实际是全维笛卡尔展开：

```
承担费用类型（总自费 / 自付二 / 合理金额）
  × 区分医保赔付（有医保 / 无医保）
  × 费用限额（如 1000，按维度独立设限）
  × 赔案累计区间（[0,1000) / [1000,2000) / [2000,10000)）
    → 赔付比例（每格一个 %，未填即 0）
```

区间控件支持「起 / 止 / 起止类型（左闭右开）」，为**半开区间**，相邻区间无重叠无空隙〔定〕。

> **实现含义**：赔付比例不能存成 `BigDecimal`，必须存成"维键 → 比例"的映射，且**每格可独立配费用限额**（截图里每行都有 1000 的费用限额输入框）。

### 5.4 「赔案累计区间」因子：累计口径〔定〕

这是唯一有独立文档的因子，规则最完整：

**累计键**：以**自然人**（姓名 + 证件类型 + 证件号码）为单位，累计**同一保单内**的历史已完成案件金额信息。

**纳入累计**：历史已完成案件金额信息 + 当前理算案件的发票金额信息。

**排除累计**〔定〕：
1. 已完成案件**不包括**"已推送保司被退回至审核中"的案件；
2. 不包括发票结论为**「拒付」**的发票金额；
3. 发票查验结果为 **假票 / 红冲** 的，**不参与理算也不参与累计**；
4. 其他情形均累计。

**「金额信息」的定义**〔定〕：指**承担费用类型**的统称 —— 默认含「总自费」「自付二」「合理金额」，**还包括自定义新增费用类型**。

> **实现含义**：累计不是"累计一个金额"，是**按费用类型分别累计**（示例表头即：发票总金额累计 / 统筹累计 / 自费累计 / 部分自费累计 / 合理金额累计）。

**区间定位**〔定〕：每张发票的金额信息（历史累计 + 当前发票）**逐张**定位到区间并取该区间的比例。

> 〔缺〕同一赔案内有多张发票时，第 2 张的"累计"是否包含第 1 张本赔案已算金额？原文示例只给了"历史累计表 + 当前 3 张发票表"，未给第 2、3 张的定位过程。这是**多发票场景必踩的坑**（见 10 章 Q-03）。

### 5.5 免赔粒度决定"先分后扣"还是"先扣后分"〔定，来自三个示例的对比〕

三个示例的差异就在这一点上，是全文最容易实现错的地方：

| 示例 | 免赔粒度 | 计算顺序 |
|---|---|---|
| A(1) 无免赔 | — | 各费用类型 × 比例 → 求和 → 控额 |
| A(2) 区分是否社保 | **责任级**免赔（100/300） | 各费用类型 × 比例 → **求和** → 减责任剩余免赔 → 控额 |
| A(3) 区分费用类型 | **费用类型级**免赔（合理200/自付二100/总自费100） | 各费用类型 × 比例 → **各自**减对应免赔 → 求和 → 控额 |

原文原话：「∵ 免赔是责任免赔非费用类型免赔，即费用类型理算金额相加后再扣减免赔」〔定〕。

## 6 免赔规则族

### 6.1 六个子维度〔定〕

| 子维 | 取值 | 默认 |
|---|---|---|
| 是否启用 | 无免赔 / 启用免赔 | 无免赔 |
| 免赔类型 | 绝对免赔 / 相对免赔 | 绝对免赔 |
| 免赔方式 | 按年度 / 按次 / 按天数（三选互斥） | 按年度 |
| 免赔形式 | 免赔金额 / 免赔比例 / 免赔天数 | 免赔金额 |
| 免赔抵扣 | 医保及三方均可抵扣 / 均不可抵扣 / 医保不可但三方可抵扣 | 均可抵扣 |
| 免赔对象 | 理算金额 / 发票费用 | 理算金额 |
| 是否不同免赔 | 否 / 是（6 维差异化） | 按医保费用类型 |

### 6.2 绝对 / 相对免赔的数学定义〔定，含原文笔误修正〕

先定义初值：
```
应赔金额   = 发票费用金额 × 对应赔付比例
剩余免赔额 = 免赔额（本维度剩余可抵扣额）
```

| 情形 | **相对免赔**（达到即全免） | **绝对免赔**（总是扣掉） |
|---|---|---|
| 应赔 > 剩余免赔 | 应赔保持**不变**；剩余免赔 = 0 | 应赔 = 应赔 − 剩余免赔；剩余免赔 = 0 |
| 应赔 ≤ 剩余免赔 | 应赔 = 0；剩余免赔 = 剩余免赔 − **应赔** | 应赔 = 0；剩余免赔 = 剩余免赔 − **应赔** |

〔疑〕原文相对免赔的第二个分支写的是"若 **发票费用金额** < 剩余免赔"，与第一分支的"**发票费用理算金额**"口径不一致。按免赔的本意（抵扣的是可赔部分），第二个分支必须是"**应赔金额** < 剩余免赔"。照抄原文会在"发票金额大但比例低"的情形下判错分支。另：绝对免赔第一分支的"剩余免赔 = max(剩余免赔 − 理算金额, 0)"在数学上恒为 0（因为理算金额 > 剩余免赔），结果对但语义绕，建议直接置 0。

### 6.3 免赔对象决定运算顺序〔定〕

这是原文写得最清楚、也最容易被简化掉的一条：

| 免赔对象 | 顺序 | 公式 |
|---|---|---|
| **理算金额**（默认） | 先理算，后扣免赔 | 理算金额 = 发票费用金额 × 赔付比例 − 剩余免赔 |
| **发票金额** | 先扣免赔，再理算 | 理算金额 = (发票费用金额 − 剩余免赔) × 赔付比例 |

两者结果不同：前者是"折后减固定额"，后者是"减固定额后再打折"。**口径搞错会导致系统性少赔或超赔**，且金额越大差越大。

### 6.4 免赔方式与累计键〔定〕

| 方式 | 定义 | 累计键 |
|---|---|---|
| 按年度 | **同一保单 + 同一主被保险人下，所有赔案的同责任（或同类型责任）共享免赔额度** | 保单 + 主被 + 责任（或责任类型）+ 保单年度 |
| 按次 | 每次赔案独立，**不累计至下一次**，每次都是初始值 | 赔案（无跨案状态） |
| 按天数 | 结合「免赔天数」，多用于津贴理赔 | 赔案 + 天数 |

**年度免赔的三元组**〔定〕：
```
年度免赔额 = 固定初始额度
已用免赔额 = 历次责任赔付所占用的免赔额度累计
剩余免赔额 = 年度免赔额 − 已用免赔额
```

> **这是全文最重要的一条工程约束**：年度免赔的累计键是**「保单 + 主被保险人 + 责任」**，不是「赔案」。任何以 `claim_id` 为键做免赔累计的实现，第 2 案起就必然重扣满额。

### 6.5 免赔形式〔定〕

| 形式 | 免赔额计算 | 常见搭配 |
|---|---|---|
| 免赔金额 | 固定额度 | 年度 |
| 免赔比例 | 免赔额 = (理算金额 或 发票费用) × 免赔比例 | 多与"按次"结合 |
| 免赔天数 | 可赔天数 = 实际天数 − 免赔天数 | 多与"按天数"结合（津贴） |

### 6.6 免赔抵扣三口径 → 已用免赔额的算法〔定〕

| 口径 | 已用免赔额 |
|---|---|
| 医保及三方赔付**可**抵扣 | 已用 = 历次已用 + 历次医保赔付 + 历次三方赔付 |
| 医保及三方赔付**不可**抵扣 | 已用 = 历次已用 |
| 医保**不可**抵扣但三方**可**抵扣 | 已用 = 历次已用 + 历次三方赔付 |

> **读法**：这条决定"医保已经报掉的钱算不算已经把免赔额填满了"。同一份责任配成三种口径，第一个赔案的免赔扣减就不同——这是条款谈判的高频争议点，必须逐责任配置而非全局配置。

### 6.7 六维差异化免赔〔定〕

启用「是否不同免赔」后，以下 6 个维度可各自设不同免赔额：

1. 区分是否社保（示例：使用社保 100 / 未使用社保 300）
2. 区分年龄区间
3. 区分医院等级
4. 区分医院性质
5. 个人免赔额度
6. 区分医保费用类型（示例：合理金额 200 / 自付二 100 / 总自费 100）

前 4 个维度（+适用对象的年龄/性别/职业）组合后即"不同人群不同免赔"。**第 6 维是粒度开关**：一旦按费用类型设免赔，就从"责任级免赔"变成"费用类型级免赔"，计算顺序随之改变（见 5.5）。

## 7 控额规则族

### 7.1 控额类型〔定〕

| 类型 | 额度来源 | 前置约束 |
|---|---|---|
| 普康 TPA 控额 | 本系统额度账本 | 默认 |
| 普康直付控额 | **调用直付接口**（直付保单）获取额度 | 必须指定直付保单号 |
| 保司三方控额 | **调用保司接口**获取额度 | 必须对接保司/三方 |

> **工程含义**：后两类意味着「额度」不是本地账本，而是**外部系统的实时余额**。这带来三个必须处理的问题：外部调用超时/失败时的处理（必须 fail-closed，不得按本地满额继续）、幂等（同一发票重复查询）、对账（外部余额与本地记录不一致时的仲裁）。原文均未涉及〔缺〕。

### 7.2 额度扣减方式（5 种）〔定〕

| # | 方式 | 公式 |
|---|---|---|
| 1 | 统一额度-责任额度 | 发票单责任赔付 = min(发票责任理算金额, 责任可用额度) |
| 2 | 统一额度-责任额度+就诊类别 | 发票费用类型理算 = min(该类理算, 该类可用额度)；赔付 = min(Σ各类理算, 责任可用额度) |
| 3 | 统一额度-责任额度+费用项目 | 发票费用项目理算 = min(该项目理算, 该项目可用额度)；赔付 = min(Σ各项目理算, 责任可用额度) |
| 4 | 个人额度-个人额度 | 发票费用项目理算 = min(该项目理算, 责任个人可用额度) |
| 5 | 个人额度-责任额度+个人额度 | 发票费用项目理算 = min(该项目理算, 责任个人可用额度, 责任可用额度) |

原文补充：「同时，在对应各'可用额度'扣减'发票单责任赔付金额'」〔定〕。

〔疑〕**扣减口径不闭合**：方式 2/3 里，费用类型/项目层先被 min 截断过，最后却用"发票单责任赔付金额"（可能被责任额度进一步截断的**总额**）去扣每一个明细层额度。若总额 < Σ明细，没问题；但若责任额度是瓶颈，明细层究竟扣"实际占用"还是"截断前金额"，原文没说。二者对后续发票的可赔额影响不同，必须定义（见 10 章 Q-06）。

### 7.3 次赔付限额（分组语义）〔定〕

6 档（原文"无 + 5 档"）：

| 档 | 「次」的定义 |
|---|---|
| 无次赔付限额 | 跳过本逻辑 |
| 一赔案计一次 | 每个赔案 1 次 |
| 同赔案且发票同日计一次 | 赔案 + 发票日期 |
| 同赔案且发票同日同院计一次 | 赔案 + 日期 + 医院 |
| 同赔案且发票同日同院同科室计一次 | 赔案 + 日期 + 医院 + 科室 |
| 同赔案且发票同日同院同病种计一次 | 赔案 + 日期 + 医院 + 病种 |

原文："根据'次'的定义，将一次赔案提交的内容按定义**分组**，分别理算赔付金额"〔定〕。

> **注意语义**：次限额不是"对总额再取一次 min"，而是**先分组、每组独立走一遍完整理算（含各自的免赔与比例）、每组各自受次限额约束**。若实现成"总额 min 次限额"，多组场景会系统性少赔。

〔缺〕分组后各组是否共享责任额度、组内免赔是否各自独立 —— 原文未定义，但由"分别理算"可推断组间独立〔推〕。

### 7.4 日赔付限额〔定〕

配置要素里存在两档：「按同日赔案累计」「按同日发票累计」。原图流程图里没有出现日限额判定，属"配了不生效"的高危缺口；2026-10-31 口径已收敛为下列可执行规则（Q-05 关闭），实现落在 `AdjustmentEngine` 的日窗口判定、`QuotaStack.Layer.DAILY` 截断层，与 `t_quota_transaction`（`txn_type=DAILY`）的按日流水。

判定式：

```
当日可用 = clamp(日限额 − Σ该业务日日用量, 0, +∞)
赔付     = min(次限额后的金额, 当日可用)
```

| 项 | 口径 | 为什么必须这样 |
|---|---|---|
| 配置 | `daily_limit`（金额，0 = 不启用）与 `daily_limit_basis`（`NONE` / `SAME_DAY_INVOICE` / `SAME_DAY_CLAIM`）**必须同配或同不配** | 只配金额不配口径 ⇒ 窗口判不出来；只配口径不配金额 ⇒ 口径永远不会生效。两者都是"配了不生效"，装载期即拒绝 |
| 业务日 | 按发票累计取明细**发票日期**；按赔案累计取**赔案受理日** | 原文两档口径的全部内容；两者不是同一个日期，混用会让跨月补票穿透日限额 |
| 累计范围 | 同一业务日的**所有赔案**合计，不是单案或单票口径 | "累计"二字；单案口径下同一天多案连报可无限赔付 |
| 截断位置 | 次限额之后、责任额度之前 | 日限额控"一天赔多少"，责任额度控"这个责任赔多少"。顺序颠倒会让同一笔赔付在日额度上被算两次 |
| 用量存储 | 落 `txn_type=DAILY` 的流水（带 `biz_date`），读侧按业务日聚合 `OCCUPY − ROLLBACK`；**不存"当日已用"字段** | 存状态就要有每日清零作业，漏跑一天即静默重置为满额。落流水则补赔、倒签发票、冲正都能自然算对 |
| 归因 | 赔 0 且各行均因日限额截断 ⇒ `ZERO_DAILY_EXHAUSTED`（拒赔原因码 09），**不复用** `ZERO_LIMIT_EXHAUSTED` | 前者"改日再赔"，后者"本年度额度用完"。混码会把客户可以明天再报的票说成今年不给赔了 |

窗口判不出来时一律 fail-closed，不猜一个日期：

| 情形 | 处理 |
|---|---|
| 按发票日累计，但明细缺发票日期 | `DAILY_LIMIT_WINDOW_UNDETERMINED` |
| 按发票日累计，但多明细的发票日期不是同一天 | 同上——一次赔案内含多日发票时，"按同日累计"本就该拆案，不能按任取一天算 |
| 按赔案日累计，但入参未带赔案受理日 | 同上 |
| 账本给出的窗口**晚于**本案业务日 | `DAILY_LIMIT_WINDOW_STALE` |

> **为什么最后一种必须拒绝，不能"差一天就当 0"**：账本按业务日聚合，读到的窗口比本案新，说明本案在时间上是倒签的（补赔、补录发票）。此时"当日已用"是未知量，取 0 等于把日额度重新发一遍——正是 Q-05 要防的超赔，只是换了个入口。

〔推〕同一赔案内多个「次」分组共享同一天，故日余额在组间**递减传递**，不是每组各自从满额起算（否则 N 组日限额等于 N 倍的配置值）。

## 8 责任关系（共享保额 / 先赔后赔）

### 8.1 默认赔付顺序〔定〕

同一计划下所有责任，**默认按该计划下"可适用的责任顺序"依次赔付**。

### 8.2 共享保额〔定〕

- 触发条件：同一计划下部分责任之间存在共享关系，且**险种额度不足以表达**时使用
- 表达方式：设置「**共保代码**」，所设置的责任**共享一个额外的保额控额**
- 数量约束：
  - 一个责任**最多同时配置 2 个**「共享保额」关系
  - 同一个「共享保额」**最多配置 5 个**责任
- 对应 1.2 的额度层④「责任共保可用金额」

〔缺〕共享池的额度从哪来（独立新建？从某责任划拨？）、池耗尽后是否回落到各责任自身额度、多共享关系（一个责任同时在 2 个池里）的截断顺序 —— **均未定义**。给真实保司条款做配置时，这三问必被问到。

### 8.3 先赔后赔〔定/缺〕

三种关系：

| 关系 | 语义（原文） |
|---|---|
| 一起赔 · 先赔比例外后赔不赔 | 先赔责任按其比例赔付；超出该比例的部分，后赔责任不赔 |
| 一起赔 · 先赔比例外后赔可赔 | 先赔责任按其比例赔付；超出部分后赔责任可赔 |
| 不一起赔 | 两责任互斥 |

约束〔定〕：
- 最多 **3 层**线性关系
- 同一个责任**不能同时存在多个**「先赔后赔」关系
- 共享保额关系与先赔后赔关系**可以共存**

〔缺〕**三种关系的金额推导公式全部缺失**。例如"先赔比例外"的"比例"指什么（先赔责任的赔付比例？还是约定的分摊比例？）、"后赔可赔"时后赔责任的基数是否要扣掉先赔已赔金额 —— 原文只有名称。这是 V1 无法实现多责任链的根本原因。

### 8.4 多责任组合情形〔缺〕

原文第二章列出四种组合（无共保无先后赔 / 有共保无先后赔 / 无共保有先后赔 / 有共保有先后赔），**四个小节全部为空**；多发票多责任、同保单多赔案、跨保单多赔案（3 个情形）同样为空。

## 9 计算不变量（引擎必须自证）

以下 8 条是从上述规则推出的**可断言的不变量**，建议直接作为引擎合同测试：

| # | 不变量 | 依据 |
|---|---|---|
| I1 | 任一时点 `Σ各费用类型理算金额 = 发票单责任理算金额` | 4.2 步 6 |
| I2 | `发票单责任赔付金额 ≤ min(各类可用额度, 责任可用额度, 险种可用额度, 计划可用额度)` | 7.2 + 1.2 |
| I3 | 半开区间无重叠：相邻区间 `[a,b)` `[b,c)`，任一金额**恰好命中一个**比例 | 5.3 |
| I4 | `剩余免赔额 ≥ 0` 且 `已用免赔额 ≤ 年度免赔额` | 6.4 |
| I5 | 相对免赔下，`应赔 > 剩余免赔` 时 **赔付不减少**（免赔被"跳档"） | 6.2 |
| I6 | 拒付发票 / 假票 / 红冲：既不产生理算金额，也不进入累计 | 5.4 |
| I7 | 同一输入（发票 + 责任配置 + 累计快照 + 版本）**必得同一输出**；累计快照须物化进结果 | 5.4 + 6.4 |
| I8 | 跨案累计可复现：用案件结果里物化的"累计前值"重算，必得相同金额 | I7 |

> I5 是最容易写错的：多数实现会把"相对免赔"写成"如果够了就减掉"，实际语义是"**够了就一分不减**"。这条必须有专门的用例，且用例金额要跨过门槛两侧。

## 附录 A 原文数值示例复核（发现 2 处与配置矛盾）

三个示例的责任配置与原文算式逐项比对：

| 示例 | 项目 | 配置比例 | 原文用值 | 原文算式 | 按配置应为 |
|---|---|---|---|---|---|
| A(1) | 合理金额 1925.33 | 90% | 90% ✅ | 1732.80 | 1732.80 |
| A(1) | 总自费 631.88 | 90% | 90% ✅ | 568.70（笔误，应 568.69） | 568.69 |
| A(1) | 合计 | — | — | 2301.49 | 2301.49 |
| A(2) | 合理金额 1925.33 | 90% | 90% ✅ | 1732.80 | 1732.80 |
| A(2) | 总自费 631.88 | **70%** | **90% ❌** | 568.70 | **442.32** |
| A(2) | 减责任免赔 100 | — | — | 2201.50（又写作 2201.49） | **2075.12** |
| A(3) | 合理金额 − 免赔 200 | 90% | 90% ✅ | 1532.80 | 1532.80 |
| A(3) | 自付二 273.42 − 免赔 100 | 80% | 80% ✅ | 118.74 | 118.74 |
| A(3) | 总自费 631.88 − 免赔 100 | **70%** | **90% ❌** | 468.70 | **342.32** |
| A(3) | 合计 | — | — | 2120.24 | **1993.86** |

**结论**：A(2)/A(3) 的总自费均误用 90% 计算（配置为 70%）。更值得警惕的是——**三个示例的最终赔付都被 `min(…, 责任额度 1000)` 截断为 1000**，所以这个错误在示例里**不产生任何可见差异**。

> 这正是"示例不具备判别力"的典型：用这些示例做验收，算错了也会通过。引擎的用例必须让**控额不成为瓶颈**（责任额度设大），才能验出比例是否取对。这一条建议写进验收准则。
