# 第 11 轮循环复核 · 事件消费方生产接线 + 分层门禁收口（2026-11-07）

> 承接第 10 轮「零 DDL / 零公共签名闭环落地」。第 10 轮已把后督 DIFF → 评测样本事件这条链路的
> **导出事实源**（`t_claim_inspection` DIFF + `DiffSampleExportApplicationService` + `GET /api/v1/claims/eval/diff-samples`）
> 与**事件消费方**（`AiEvalSampleProjection` 的 `@EventListener`）落地，但二者之间仍存在收口缺口，
> 本轮一并补齐并修掉由此暴露的分层门禁违规。

## 一、第 10 轮遗留的两处收口缺口

1. **「已写但零消费」未闭环**：第 10 轮新增的 `AiEvalSampleProjection` 有 `snapshot()` / `size()`，
   但全仓唯一调用方是它自己的单测——注释宣称「供治理面观测」却没有任何**生产**消费方。
   属于典型的「配了不生效」：链路末端（事件真的被吃了）在运维侧不可观测。
2. **ArchUnit P0-1 分层违规**：把治理面观测接到生产时，原 `AiEvalSampleIndexApplicationService`
   直接 `@RequiredArgsConstructor` 注入 `com.bone.claim.infrastructure.evaluation.AiEvalSampleProjection`
   （infrastructure 实现），触发 `ArchitectureTest.applicationMustNotDependOnInfrastructure` 红线。

## 二、本轮落地内容

| 项 | 改动 | 归属 | 说明 |
| --- | --- | --- | --- |
| 生产消费方接线 | 新增 `AiEvalSampleIndexApplicationService`（应用层，仅依赖端口）+ `AiEvalSampleIndexController`（`GET /api/v1/claim-ops/ai-eval-sample-index`） | 应用 / 适配层 | 让「DIFF 样本事件确实被真实消费」变成运维可查的事实 |
| 分层门禁收口 | 新增 `AiEvalSampleIndexPortAdapter`（infrastructure 实现 `application.port.out.AiEvalSampleIndexPort`）；`AiEvalSampleProjection` 改用端口 DTO `AiEvalSampleIndexPort.Entry` | 端口 / 基础设施 | 应用层只依赖端口接口，不直触 infrastructure 实现；命名满足 E-13.3（*PortAdapter） |
| 单测补齐 + 变异验证 | `InspectionFeedbackChainWiringTest`（真实 Spring 事件总线 + H2 事务） | 测试 | 见第三节 |

- `AiEvalSampleIndexPort` 端口接口与 `AiEvalSampleIndexController` 由第 11 轮起步，本轮随收口一并纳入版本管理。
- `AiEvalSampleProjection` 角色不变：仍是「吃事件、维护易失索引」的基础设施组件；新增 `AiEvalSampleIndexPortAdapter`
  仅作为应用层读取索引的六边形边界，二期若换落库视图只需替换适配器，应用层零改动。

## 三、验证（真实事件总线 + 变异探针，杜绝假绿）

`InspectionFeedbackChainWiringTest` 在**真实 Spring 事件总线**上跑通全链路
（`H2 内存库 + DataSourceTransactionManager + TransactionTemplate` 提供真实提交边界）：

```
InspectionConcludedEvent(DIFF)
  → InspectionFeedbackRecorder  @TransactionalEventListener(AFTER_COMMIT)
  → AiEvalSamplePort.collect()
  → EventAiEvalSamplePortAdapter → SpringDomainEventPublisher.publish()
  → AiEvalSampleProjection      @EventListener
```

并做**反向变异探针**证明判据有判别力（非恒绿）：

| 变异 | 预期 | 结果 |
| --- | --- | --- |
| 移除 `AiEvalSampleProjection` 消费方 | 全链红（索引数 0） | ✅ 全红 |
| 移除 `InspectionFeedbackRecorder` 记录器 | 3 个用例红 | ✅ 3 红 |
| 还原 | 全绿 | ✅ RC=0 |

该测试同时钉住「消费方必须用普通 `@EventListener` 而非事务型」这一接线前提
（`@TransactionalEventListener` 默认 `fallbackExecution=false`，无事务时不触发）。

## 五、诚实边界（不得越界宣称）

- 本端点的索引是**进程内、有界（≤500）、易失**的：进程重启即清空、多实例各持一份，**不是持久化事实源**。
- 可回溯 / 可审计的**权威事实源**是已落库的 `t_claim_inspection`，经 `DiffSampleExportApplicationService`
  与 `GET /api/v1/claims/eval/diff-samples` 导出。
- 本端点只回答「本次进程内，DIFF 样本事件有没有被真实消费、消费了多少、按什么归因」，
  **不得**被当作评测集、盲标金标准或任何准确率数值。
- 真正的闭环（评测集消费、独立盲标金标准、阈值校准）仍属 Phase B / V2；迁移 0122 明确要求盲标与后督抽检物理分离，**本端点不替代它**。
- **严禁宣称 L3**：`PROVIDER_CONFIGURED` / `PERCEPTION_MODEL_DRIVEN` / `RUNTIME_MODEL_COVERAGE` 仍为 BLOCKED，
  `_ai_native_readiness.py` 的 `l3Claimable=false`（L0）。

## 六、外部前置（L3 判据）登记 — 防假绿守卫现状

- `RUNTIME_MODEL_COVERAGE` 的判定要求 **provider 已配 + 探活判词 REACHABLE + 运行期参与率** 三要素同时成立，
  缺一即 BLOCKED；「探活判词缺失」一律 fail-closed，绝不把「没测过」当成「通了」。
- 该双条件（裸字符串 `REACHABLE` 与 `provider_env`）路径已在 `_ai_native_readiness.py` 的 self_test 中
  注册为反向探针（见 `RUNTIME_MODEL_COVERAGE` 相关 `add(...)`），本轮**未做任何放宽判据的改动**，
  未引入让判据局部假绿的逻辑。
- 风险登记：若未来有人把 `REACHABLE` 当作可随意注入的常量而非真实探活结果，判据仍可能被绕过；
  该守卫须在该脚本持续存在，不在本轮放宽。
