# 14 真实企业 POC 推进计划

> 定位：回答「内部模拟 POC 已通过之后，**怎样一步步走到真实企业 POC、再到正式投产**」。本文是 12 号《POC 就绪度评估与启动清单》与 13 号《内部模拟 POC 验证报告》的**执行路线图**——把 2 项红线、16 项 Go-Live 门禁按 owner 拆成「可执行动作 + 签核材料 + 外部依赖 + 判定标准」，并按三态给出阶段节奏。
>
> **一句话结论**：企业 POC 分三态推进——**Shadow 技术验证现在即可进场**（无硬门槛、旁路只读）；**Assisted 对客建议**须先采购真实 provider 并现场验收指标（3 项技术能力，可控、1–2 周量级）；**Automated 自动赔付 / 正式投产**须跨团队闭环 2 项红线 + 16 项门禁（监管 / 资金 / 合规硬前置，周–月级、强依赖外部）。内部模拟 POC 只清零了「技术链路可达」的不确定性，**不替代任何外部签核**。

---

## 一、推进总原则（不可跳级）

| 原则 | 含义 |
|---|---|
| **三态不跳级** | Shadow → Assisted → Automated 逐级放开；前一级未验收，不得启动后一级的对客动作 |
| **红线不可伪造** | 2 项红线（资金护栏 / 合规转正）的唯一翻转路径是闭环其外部条件并经 owner 签核；改默认值、批量改 draft→current、伪造探活判词均属刷绿，禁止 |
| **模拟只验技术** | 内部模拟 provider（`poc-internal-v1`）只能证明「链路可达 + 契约正确」，不能证明模型准确率、不能替代现场指标、不能打开资金闸 |
| **判定以复核器为准** | 每阶段是否达标，以 `tools/_ai_native_readiness.py` 运行实测 + 现场验收报告为判据，不以文档自述为准 |

三态门槛与当前态见 `12-POC就绪度评估与启动清单.md` §一/§三；内部模拟验证见 `13-内部模拟POC验证报告.md`。

## 二、路线总览（四阶段）

| 阶段 | 形态 | 对客影响 | 关键解锁 | 当前状态 |
|---|---|---|---|---|
| **S0 内部准备** | 内部技术验证 | 无对客 | 全链路测试 + 内部模拟 provider 闭环 3 技术项 | ✅ **已完成**（13 号报告，10 SAT / 2 BLOCKED / L2） |
| **S1 进场** | Shadow 技术验证 | 旁路只读，AI 不出对客结论，随时可关停 | 无硬门槛，签 NDA/MOU/DPA 后用授权脱敏样本跑链路 | ✅ **现在可进**（12 号结论） |
| **S2 辅助** | Assisted 对客建议 | AI 出建议，人工确认后生效 | 真实 provider + parse_mode=llm + 现场指标验收（3 项技术能力） | ⚠️ 技术已具备，待采购真实 provider + 现场验收 |
| **S3 自动/投产** | Automated 自动赔付 | 自动出款，资金安全 + 监管硬前置 | 2 项红线 + 16 项门禁全闭环 | ❌ 差 2 项红线 + 16 门禁（跨团队签核） |

> 交付节奏与商务阶段对齐见 `00-落地交付包清单.md` §三：试点准备（试点前 4 周）→ 试点执行（Shadow，交付评测报告）→ Phase B 之后规模化。S3 的自动出款放开对应 Phase C，须在 G7（支付实时对账）闭环后。

## 三、S2 辅助态：3 项技术能力解锁（可控，1–2 周量级）

这 3 项即复核器中已被内部模拟闭环的 `PROVIDER_CONFIGURED` / `PERCEPTION_MODEL_DRIVEN` / `RUNTIME_MODEL_COVERAGE`。真实企业场景须用**真实商业 provider**重做，并用客户授权样本现场验收。

| # | 能力 | 可执行动作 | 签核材料 / 证据 | 外部依赖 | 判定标准 |
|---|---|---|---|---|---|
| T1 | 真实 provider 接入 | 采购商业模型服务 → 密钥托管 → 注入 `BONE_AI_GATEWAY_BASE_URL/API_KEY/MODEL`（模型名须非 `mock*`、非 `local-stub`） | 采购合同 / 密钥托管记录；按 `11-L3外部前置运行手册.md` §三–§四探活 | 采购流程、供应商 SLA | 复核器 `PROVIDER_CONFIGURED`=SATISFIED；探活 `verdict=REACHABLE` + 证据束自洽 |
| T2 | 感知模型驱动解析 | 设 `BONE_CLAIM_DOCUMENT_PARSE_MODE=llm`，接支持视觉的端点跑影像件 | 现场样本抽取记录；D2 归因码验证 | 客户授权脱敏样本；多模态端点 | `PERCEPTION_MODEL_DRIVEN`=SATISFIED；字段准确率 ≥95%、规则匹配 ≥90%（现场生成，不预置） |
| T3 | 运行期模型覆盖 | 真实服务栈跑端到端 E2E，落探活 + 参与率证据 | E2E 产物 `claims-e2e-result.json`；复核器输出快照 | 客户数据与联调窗口 | `RUNTIME_MODEL_COVERAGE`=SATISFIED；`probeEvidence` 自洽、`participationRate` 非零 |

**边界**：T1–T3 闭环后仅代表「Assisted 技术条件达成」，AI 建议仍须人工确认后生效；**不得**据此宣称 L3 或打开自动出款（`l3Claimable` 在 S3 门禁全闭环前恒为 false）。

## 四、S3 自动/投产态：2 项红线（必须外部签核，不伪造）

这 2 项是内部模拟 POC **明确不碰**的红线，对应复核器 `CATALOG_ADMISSION_ACTIVE` 与 `GOLIVE_NOT_DRAFT`。

### 红线 R1 — 目录准入资金护栏（`CATALOG_ADMISSION_ACTIVE`）

| 维度 | 内容 |
|---|---|
| 根因 | 生效通道默认 NONE，目录准入护栏未生效；视觉桩 / 目录缺失时 fail-closed 未纳入资金路径 |
| 影响 | Automated 自动赔付、资金安全（错误准入可直接导致错赔 / 超赔） |
| Owner | **业务（理赔运营）+ 法务**（平台 / 架构配合落地） |
| 可执行动作 | ① 医学目录库数据接入（见 `06-医学目录库建设方案.md`）；② 准入策略置 MANDATORY；③ 资金路径挂载白名单校验（与 G2/F1、G13 联动）；④ 目录缺失 / 未准入 fail-closed 测试 |
| 签核材料 | 目录数据源授权书；准入策略 MANDATORY 配置记录；业务负责人 + 法务联签的准入生效确认单；fail-closed 故障注入测试报告 |
| 外部依赖 | 目录数据供应商；业务与法务签核排期 |
| 判定标准 | 复核器 `CATALOG_ADMISSION_ACTIVE`=SATISFIED；未准入案件转人工（MANUAL_REQUIRED）而非自动通过 |
| 禁止行为 | 把视觉桩 `available=false` 改 `true` 以刷绿——这会打开 AUTO_APPROVE 资金闸，属 L2 资金行为变更，须双人 Review + 产品签核 |

### 红线 R2 — Go-Live 合规转正（`GOLIVE_NOT_DRAFT`）

| 维度 | 内容 |
|---|---|
| 根因 | `08-go-live/` 下 13 册合规分册仍为 `currency: draft`（总纲 00 为 current），未配验收证据 |
| 影响 | 正式投产、监管合规 |
| Owner | **安全合规**（交付组 / 平台 / 架构 / 业务法务按册配合） |
| 可执行动作 | PIA/DPIA、等保定级备案与测评、AI 算法备案、DSAR、规则发布防投毒、条款费率报批等逐册完成并附验收证据后，方可逐册 draft→current（与 G3/G4/G5/G10/G12/G13 一一对应） |
| 签核材料 | 各册对应归档编号 / 备案号 / 测评报告 / 回执 / 演练报告等（见下 §五 G3–G13 验收列） |
| 外部依赖 | 监管机构（等保、算法备案、条款费率报批）；第三方测评机构；法务 |
| 判定标准 | 复核器 `GOLIVE_NOT_DRAFT`=SATISFIED；13 册逐册升 current 且有对应 G 门禁验收证据 |
| 禁止行为 | 先改 frontmatter 宣告完成——13 册 draft 是准确状态，升 current 必须与某一 G 门禁验收证据一一对应 |

## 八、每阶段验收方法（不预置实测值）

1. **S1 进场验收**：按 `12-POC就绪度评估与启动清单.md` §八 Checklist 逐条勾；复核器实测 = 7 SAT / 5 BLOCKED / L0 / `l3Claimable=false`（默认态）。
2. **S2 辅助验收**：按 `11-L3外部前置运行手册.md` §三–§八配置真实 provider → 探活 → 实跑 E2E → 复核器归因；三项技术判据 SATISFIED，且现场指标报告达标。
3. **S3 投产验收**：按 `../08-go-live/00-总纲与Go-Live门禁.md` §二逐项核对 G1–G16，任一项未闭环标红；2 项红线 SATISFIED 且对应签核材料归档。
4. **指标现场生成**：字段准确率、规则匹配率、人工复核率等一律用客户授权样本现场跑出，**不预置、不照抄内部模拟值**（内部模拟值不得作为对客证据）。

---

## 九、不可伪造红线（刷绿的 5 种表现，逐条禁止）

1. 无 provider 时改默认配置 / 伪造探活判词 → 禁止（`PROVIDER_CONFIGURED` 只能靠真实接入翻转）。
2. 把视觉桩 `available=false` 改 `true` → 禁止（会打开 AUTO_APPROVE 资金闸）。
3. 批量把 13 册 `currency: draft` 改 current → 禁止（须逐册配 G 门禁验收证据）。
4. 把历史时点快照（2026-11-07 的 5 SAT / 7 BLOCKED）回改成当前值 → 禁止（原文保留作审计轨迹）。
5. 用内部模拟产物冒充真实企业 POC 证据 → 禁止（内部产物标注 `internal-simulated-poc`，仅供内部技术验证）。

## 十、风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| 真实 provider 采购 / 密钥托管排期 | 阻塞 S2 | 提前启动采购； Shadow 阶段不依赖 provider，可并行推进 |

| G7 支付对账未闭环却放开自动出款 | 资金差错晚发现 | G7 列为 Phase C 硬约束，未闭环不得放开自动出款 |
