# synapClaim 理算引擎设计（架构决策 · 算法 · 端口契约）

> **定位**：理算（Settlement）子域的**唯一设计真源**。本文合并了原先两份文档——《智能理算引擎设计（独立限界上下文）》回答"要不要独立、边界在哪"，《理算引擎内部设计（算法·端口契约·业界基准）》回答"怎么算"——这两问本就是一篇设计的两章，分列会导致"改算法时忘了改边界"。
>
> **权威边界**：**业务口径**（该赔多少、比例/免赔/控额规则）以《synapClaim 智理理算引擎业务规则（V1·责任配置与理算基线）》为权威——V1 带〔定〕〔推〕〔疑〕〔缺〕可信度标记，〔疑〕〔缺〕项澄清前不得据以实现；领域模型与口径以《工程落地版》§5（责任与理算模型）/ §7.4（理算）为权威；DDL 见 §9.5，OpenAPI 见 §10；规则 ID 以 `07-delivery/04-业务规则书` 为权威。本文只写设计与算法，**验证资产**见《理算引擎验证套件》，**缺陷取证史**见《理算引擎诊断记录》。
>
> **⚠️ 实现状态声明（必读）**：本文 §1–§13 记录的是**参考实现（synap-claim-oracle）语义的架构决策**，其中 §4 的编排是 0–7 八步、以 `FormulaSnapshot` 为快照契约。**当前生产实现已按 V1 重建为九步分层管线**（三费用池 / 比例多维查表 / 免赔六维 / 控额七层 / 次分组 / 不变量自证），代码落点 `com.bone.claim.domain.model.adjustment.engine`。**判断"现在实际怎么算"请看 §14，不是 §4。** 保留 §1–§13 原貌是因为：架构决策（独立限界上下文、三类责任策略、端口边界、快照防漂移）仍然有效，且 synap-claim-oracle 作为双轨 oracle 的语义基线仍需本文解释。
>
> **业界基准锚定**为本文强制项：每个核心设计点必须能对应到可核查的行业实践，避免"自创不可证伪"的设计。

## 1. 决策：独立限界上下文，但有严格形态约束

**结论：YES —— 把理算设计为 synapClaim 内一个独立限界上下文（独立 module + 六边形架构 + 端口边界），但不是以下三者：**

| 否认项 | 原因（证据） |
|---|---|
| ❌ **整体照搬 `bone-tpa-intelligent-adjustment`** | 该模块是 pk-tpa-saas **生产验证、在用**的 proven 引擎（三类责任策略 + min 聚合控额已被真实业务检验）。但 synapClaim 采用六边形 + 端口防腐 + 多租户 + 监管快照架构，与 tpa-saas 的"进程内直连、实时读配置"风格不同；整体搬运会把其直连直付/公账、实时读 `plan.version` 等与架构约束不符的实现一并带入。故**复用其策略模式与控额语义作为基线**，在新模块内按 synapClaim 约束重构（端口隔离、快照固化）。 |
| ❌ **拆成独立微服务/进程** | 理算必须与会案件（`ClaimCase`）、责任（`AdjLiability`）、结算（`SettlementOrder`）、额度（`LedgerPort`/C11）在**同一事务边界**内写结果、占额度。独立进程引入分布式事务与额外延迟。现有"domain 纯逻辑 + port 防腐"已天然支持进程内 module 隔离，无需跨进程。 |
| ❌ **把理算塞进 `bone-ai-rules`（C2）当规则推理** | 理算 95% 是**确定性金额算术**（免赔累加、比例乘算、min 取交、公账/个账分账）。金融"同输入同输出可复算"要求精确 `BigDecimal` 语义，DSL 表达算术既不可控又破坏快照可复算。C2 只适合其**前置的条件/因子求值**。 |

**正解形态**：`synap-claim-settlement` 模块（hex），以 `SettlementEngine` 门面编排"规则求值(C2) → 确定性算术(本域) → 冻结快照 → 占额(C11) → 审计(C4) → 事件(Outbox)"，作为决策图 `Adjust` 节点的**唯一理算事实源**（避免双源漂移）。

## 2. 业界基准锚定（设计点 ↔ 行业实践）

| 设计点 | 行业基准 | 为什么这样设计 |
|---|---|---|
| 规则层(C2) + 算术层(本域) 双层分离 | Guidewire **Rules Engine（适用性）+ Calculation Engine（金额）** 分离；SAP MDG 决策与计算解耦 | 规则热更/回归门禁不污染金额精度；金额走确定性引擎 |
| 策略工厂 + 插件化责任类型 | 平安产险/众安"责任插件化"；保险核心系统普遍 Strategy+Factory | 新增责任类型零侵入主线 |
| min 聚合多维度控额 | ISO 834 比例分摊 + 团险/再保"多维度限额取交集最小"；太保/泰康限额矩阵 | 任一维度触顶即截断，防超赔 |
| `FormulaSnapshot` 物化 | SOX / NAIC Model Audit Rule "同输入同输出可复算"；金融台账不可变快照 | 配置变更后旧案可自包含复算，支撑争议复议 |
| 三值额度（initial − claim − frozen） | 团险/企业补充医疗公账池通用记账；ACORD 额度语义 | 冻结与已用互斥统计，杜绝双计 |
| 准入 `checkAdjustable` + 归因 `checkAdjustRecord` | 理赔"事实认定—归因"双轨（拒赔五要素）；监管可解释性 | 零赔付必须可归因 |
| 端口隔离 + Outbox 原子事件 | 六边形架构（Cockburn）；"业务落库 + 事件投递"原子性 | 引擎不触外部系统，防腐且可测 |

│ application/  SettleClaimUseCase → 编排 port：                              │

### 3.1 平台边界（关键串联点）

| 层 | 归属 | 理由 |
|---|---|---|
| 条件 / 因子 / 目录求值 | `bone-ai-rules`(C2) 规则 DSL | 责任适用性、赔付比例笛卡尔因子、目录编码匹配属**规则**，适合配置化 + 热更 + 回归门禁 |
| 金额算术 | 本域（native） | 免赔累加、比例乘算、min 取交、公账/个账分账——精确 `BigDecimal(10,2)` HALF_UP，**不可入 DSL** |
| 额度 | `LedgerPort`(C11) | 占/冲/信任额度由平台台账统一；反诈命中即熔断回退 |
| 审计 | `TracePort`(C4) | 快照不可变、可回放，对接后督 100% AI 质检 |

> 对《工程落地版》"理算语义迁入 bone-ai-rules"的精炼：改为**"求值层迁入 C2，算术层留本域"**。既享受规则热更/回归门禁，又保住财务精度与可复算——Guidewire / SAP MDG / 平安产险均采"规则管适用、引擎管金额"双层。

## 4. 引擎编排（参考实现语义 · 已被 V1 取代）

> **本节描述的是 `synap-claim-oracle` 的 0–7 八步编排，不是当前生产实现。** 生产实现已按 V1 §4.2 重建为九步分层管线，见 §14。本节保留的原因：① 它解释 synap-claim-oracle 为什么长这样（双轨 oracle 需要一个**独立于生产实现**的语义基线）；② 其中"免赔与不可获利必须前置到比例之前""年度限额并入 min 聚合以保证归因完备"两条不变量，在 V1 实现中依然成立。

```
0    幂等键命中？      → 返回首次结论（不占额、不双计累计）
0'   风控 P0（fraudHold）？→ HOLD：不出金额、不占额、发事件、转人工
0.5  重算冲正：同 claimId 旧结论先 reverseSettlement 回退累计
1    C4  TracePort.record —— 冻结 FormulaSnapshot（快照审计）
2    C2  策略求值 —— 产出「可赔基数 base + 比例 ratio + 理算层面免赔」
3    不可获利：第三方已付（社保统筹/他险已赔）从基数按比例分摊扣除（守恒）
4    年度免赔：作用于**费用基数**，跨案累计剩余，按行分摊（守恒）
5    比例 → 理算层面免赔 → 取整 → 分位配平（§8）
6    多维度 min 控额：责任 / 费用子限额 / 计划 / 年度限额
7    C11 累计提交（乐观锁 + 按 claimId upsert）→ 占额 → Outbox 事件
```

> **为什么这样排**：3 与 4 都在"比例"之前，因为**免赔额与不可获利的标的是"费用"而非"赔款"**（错序即系统性少赔，见《理算引擎诊断记录》D1）。6 把年度限额并入 min 聚合，使"行级金额之和 == 实际应付"恒成立（归因完备），避免"总额被砍但明细不变"的对账裂缝。
>
> **纯函数铁律**：步骤 2–5 不碰 DB/AI/网络，可在无 Spring 环境单测；1/6/7 全部经端口。

### 4.1 直付预授权（置于步骤 0 之前）

```
0''  preAuthorize(ctx, snap, estimatedTotal)
     auth = min(预估费用 − 剩余年度免赔, 剩余年度限额, 剩余责任限额, 计划剩余) × 保守比例
     保守比例 = 各可赔费用类型比例的最小值；无可赔费用 → 0
     仅计算：不占额、不提交累计（预授权 ≠ 结算）
     授权 = 0 → 直付通道降级为「先垫付后报销」或挂起人工，不阻塞就医
```

> 一致性护栏：结算净额必须 ≤ 预授权额度。按 100% 授权会使院端直付额高于实际结算，差额须向患者追收——这是直付网络的高频纠纷源。

## 5. 聚合与值对象

```
IndemnityCalculation（A6 聚合根）
 ├ claimId / planVersion / liabilityVersion / catalogVersion（三者皆锁定）
 ├ lines: List<AdjustmentLine>              // 每责任一条
 ├ formulaSnapshot: FormulaSnapshot          // 物化契约见下
 ├ totalPublic / totalIndividual             // 不变式 total = public + individual
 ├ settleStatus: PAY / PARTIAL / REJECT / HOLD
 ├ denied: boolean / denyReasons: List<String>
 ├ ruleTrace: Map<feeType, List<ruleId | rejectType>>
 └ status: FROZEN → CONFIRMED → PAID / ROLLBACKED

AdjustmentLine（六成分，落 adj_calculation_line）
 ├ liabilityUuid / liabilityVersion
 ├ fee_calculate  // 计算基准额（剔除不赔后）
 ├ ratio_payout   // 按比例应付 = (基准 − 免赔) × ratio
 ├ fee_payout     // 实付（经控额 min 后）
 ├ fee_deduct     // 免赔扣减（拒赔行强制 0）
 ├ fee_occupy     // 占额
 ├ fee_remain     // 剩余额度
 ├ rejectType     // CATALOG_EXCLUSION / EXCLUSION_CLAUSE / null
 └ formulaHash    // 六成分 + 输入的哈希，逐行可复算
```

**`FormulaSnapshot` 物化契约（防漂移核心）**：冻结以下不可变副本，而非仅存 `rule_version` 引用——
`{ liabilityVersion, catalogVersion, deductConfig, payPercentMatrix(已求值), liabilityLimit, feeTypeLimits, accountType, quotaInitial(各维度), 三段费用输入值, formulaHash }`。
理由：源 `plan.version` 被改后，旧案凭快照**自包含复算**，金额不变。

**额度语义铁律**（两条极易写反）：

| 项 | 语义 | 公式 | 写反的后果 |
|---|---|---|---|
| 年度免赔额 | **相减**（被保险人先自担） | `实付 = max(0, 净额 − 剩余免赔)`，同时累加 `consumed` | 免赔后置 → 系统性少赔 25% |
| 年度限额 | **封顶**（取交，非相减） | `实付 = min(净额, 剩余年限额)`，占用 = 实际应付 | 当成相减 → 限额内首案即赔 0 |

## 6. 三类责任策略（精确伪码）

### 6.1 FixedAmount（定额给付）

```
base = liability.fixedAmount
payable = min(base, liabilityLimit)          // 受责任额度截断
line(fee_calculate=base, ratio_payout=base, fee_payout=payable, fee_deduct=0, ...)
```
定额责任**无免赔、无比例乘算**，直接受限额截断。

### 6.2 Allowance（津贴，按天/次）

```
base = days × dailyAllowance
payable = min(base, liabilityLimit, timesLimit.amount)   // 责任额度 ∩ 次限额
```

### 6.3 Reimbursement（报销，主体）

```
for feeType in liableFeeTypes(ordered):        // 合理金额 → 自付二 → 总自费 → 丙类 → 超限价
   origin = invoiceFeeMap[feeType];  if origin < 0: origin = 0
   deduct  = DeductCalculator.calc(ctx, origin)          // ① 免赔（发票层/理算层，按 deductTarget）
   current = origin − deduct
   ratio   = payPercentMatrix[feeType]                   // ② C2 已求值，不在引擎内求值
   payout  = (current × ratio/100).setScale(6, HALF_UP)  // ③ 计算位 6
   payout  = payout.setScale(2, HALF_UP)                 // ④ 结果位 2
   feeLimit = feeTypeLimits[feeType] − invoiceFeeHistoryPayoutMap[feeType]
   payout  = min(payout, liabilityLimit − liabilityPayAmount, max(feeLimit, 0))   // ⑤ 多维 min
   liabilityPayAmount += payout
   if feeLimit == payout: nextLiabilityFlag = true       // ⑥ 后付责任链穿透
```

> 与参考实现逐环节对应，但**修正**：因子值由 C2 预求值注入（不在引擎内求值），外部额度经端口注入（不内联 Feign），全程不触网络。比例硬护栏 `ratio% ≤ 100%`（含 AI 加成后），防超赔。

## 7. 多维度控额（min 聚合 + 三值额度）

```
limit(ctx):
  quotaDetail = {}
  for dim in [PERSONAL, LIABILITY, PLAN, COVERAGE, SHARING, VISIT_TYPE, TIMES,
              DIRECT_PUBLIC, DIRECT_PERSONAL]:
     if not applicable(ctx): continue
     if quotaInitial[dim] <= 0: continue        // 0 = 该维度未配置，不得当"限额为零"
     avail = max(quotaInitial[dim] − used[dim] − frozen[dim], 0)   // 三值模型
     FORCE ? quotaDetail[dim] = avail : alarmQuota[dim] = avail    // ALARM 仅告警不截断
  return max(min(quotaDetail.values()), 0)
```

- **`0 = 未配置`** 是全部要点里最容易写错的一条：主流产品配置（含 tpa-saas）以 `0` 表示"该维度不限制"，引擎若当成"限额为零"就会**全额拒付且静默**——曾因测试数据恰好都传了大额子限额而被掩盖，属典型假绿（见《理算引擎诊断记录》N10）。
- 维度可插拔：一期 4 维，二期扩共保/直付余额；新增维度只扩枚举与初始额来源，**不改主链路**。

## 8. 精确计算顺序与分位配平

```
原始费用 origin
 → 目录/合理必要筛选（拒赔行 base=0，但保留 origin 供告知书）
 → 发票层免赔：   base = clamp(origin − deductInvoice, 0)
 → 第三方已付：   base ← base − 分摊(thirdPartyPaid)
 → 年度免赔：     base ← base − 分摊(min(年免赔余额, Σbase))
 → 比例：         calc = base × ratio%
 → 理算层免赔：   calc = clamp(calc − deductAdjust, 0)
 → 取整：         feeCalculate = round(calc)
 → 控额：         feePayout = min(feeCalculate, 责任剩余, 费用子限额, 计划剩余, 年度限额剩余)
```

| 项 | 公式 | 说明 |
|---|---|---|
| 占用额 | `feeOccupy = clamp(feePayout / ratio, 0, origin)` | 逆推占用的原始费用（比例件） |
| 免赔合计 | `feeDeduct = origin − base + deductAdjust` | **拒赔行强制 0**（拒赔 ≠ 免赔，否则告知书误导） |
| 年度免赔余额 | `max(0, 年免赔额 − 已用)` | 按「保单 + 账期」累计 |
| 年度限额剩余 | `max(0, 年限额 − limitUsed − frozen)` | ACORD 三值额度 |
| 责任限额剩余 | `max(0, 责任限额 − liabilityUsed)` | 责任维度亦须跨案累计 |
| 直付授权 | `min(预估 − 剩余免赔, 年限额剩余, 责任剩余, 计划剩余) × 保守比例` | 保守比例取各可赔费用最小值 |

**分位配平（最大余数法）**：逐行 `round` 后合计必须等于"总额口径 `round`"，否则对账出现 1 分差。算法：计算残差 cents，按小数余数从大到小依次 ±0.01，保证 `Σround(行) == round(Σ行)`。金融对账零容忍（SOX/NAIC 可复算）。

## 9. 增强能力（均已落地参考实现）

### 9.1 跨案累计（保单级年度免赔 / 年限额 / 责任限额）

单案理算不足以覆盖保单级聚合约束。`AccumulationPort` 以 `tenantId@policyId@periodKey` 为键，跨案聚合「已用免赔 / 已用年限额 / 已用责任限额」，理算时消费剩余、结算后回写。

- 年度免赔作用于**费用基数**（先免赔后比例）；年度限额是**封顶**；
- **责任维度也必须累计**——只做年度免赔/年限额累计而漏责任限额，是最常见的维度覆盖不完整（"门诊 5000/年"这类责任限额会被逐案重复给足）；
- 业界基准：Guidewire Accumulation / ISO 年度免赔累计 / ACORD 保单级限额。

### 9.2 可解释性与规则溯源

每条 `AdjustmentLine` 记录命中规则 ID（`ruleTrace`：`R-DED-01` / `R-RAT-01` / `R-CAP-01` / `R-DIR-01`），并生成客户告知级 `explain()` 文本。每条金额可回溯到「哪条规则 + 哪个因子值」，满足监管告知与 SOX/NAIC 可审计。基准：Guidewire "every payment line item explainable"。

### 9.3 幂等重算与快照版本化

- **幂等键 = `claimId + formulaHash(snapshot) + inputHash(ctx)`**：命中即返回首次结论，不重复占额、不双计累计。
  - 仅凭 `claimId` 不够：补交发票、AI 建议状态变化、快照变更都属**新的理算请求**，必须重算。
  - 仅凭 `snapshotVersion` 不够：源配置变更必须体现为新指纹，否则幂等会掩盖快照冻结缺陷。
- **重算必须冲正**：同 `claimId` 的旧占用先 `reverse()` 再按新输入计算，并把 `commitUsage` 改为**按 claimId upsert**（替换而非累加）。否则补交发票（理赔最高频动作）会被旧占用挤压而少赔，且账上额度与实付不符。
- 累计提交具备 `DUPLICATE`（同 claimId 不累加）与 `CONFLICT`（乐观锁失配，fail-closed 转人工）两种结果。

### 9.4 直付预授权生命周期

`PreAuthPort`：`hold(ttl)` 冻结（计入三值模型的 `frozen`）→ `capture(实际额，剩余自动释放)` → `void(撤销)` → `isExpired(到期释放)`。
**预授权必须进 `frozen`**：否则多科室分次授权可突破年限额（累计授权 18000 vs 年限额 10000），医院已直付后的差额需向患者追收。
基准：亿保「智慧E保即时结算」就诊前核验 + 预算授权；HMO/PPO prior authorization 通用模式。

### 9.5 拒赔建模

| 类型 | 载体 | 处理 |
|---|---|---|
| 整案拒赔 | `ClaimContext.denyReasons`（等待期内 / 免责条款 / 指定医院外） | `settleStatus=REJECT`，净付 0，**不提交累计、占额 0**，Outbox 发 `REJECTED` 事件 |
| 费用级拒赔 | `FeeConfig.rejectType`（`CATALOG_EXCLUSION` / `EXCLUSION_CLAUSE`） | 该行 `payout=0`、`feeDeduct=0`，原因由 `rejectType` 单列 |

`settleStatus ∈ {PAY, PARTIAL, REJECT, HOLD}`：`HOLD` 为风控 P0 挂起（不出金额、不占额）。基准：监管要求拒赔须告知**原因码**（禁自由文本）+ 理赔"事实认定—归因"双轨。

### 9.6 并发正确性

| 手段 | 做法 | 失败语义 |
|---|---|---|
| 幂等租约 | `SettlementStorePort.tryBegin(idempotencyKey)` CAS | 取不到租约 → `ConcurrentSettlementException`，fail-closed 不占额 |
| 乐观锁 | 累计提交携带 `version` | 失配 → `ConcurrentAccumulationException`，转重试/人工，禁静默覆盖 |
| 串行锁 | 同保单同周期临界区串行（单实例 JVM 锁；集群走 DB 租约） | **禁用 `SELECT ... FOR UPDATE`** |

> 顺序执行会被幂等挡住，但并发两请求可同时 `find(null)` 通过而各占额一次——所以幂等键之外还需要**租约**。

## 14. V1 重建：当前实现（权威）

> **本节回答一个问题：金额实际怎么算。** §1–§13 的架构决策（限界上下文、端口契约、快照物化、并发与幂等）全部仍然有效，被取代的只有 §4 的**金额算式**。
>
> **口径来源**：V1 §4.2（主流程九步〔定〕）/ §4.3（两个 Min 嵌套〔定〕）/ §1.2（额度七层）/ §6（免赔六维）/ §7.2（扣减方式五种）。
> **过程记录**（某时点做了什么、发现了什么）：`生产就绪完善（业界最佳实践）/16-理算引擎V1重建`、`17-控额层接线修正与多次闭环`。那两份是取证，本节是设计；两处表述不一致时以本节为准。

**§4 与 §14 是"换算式"而非"换系统"，逐个步骤的归属如下。** 这张表存在的理由：若把 §4 整节当成"已废弃"处理，幂等、冲正、风控前置会一起被删掉——它们不参与九步，却决定了重算会不会双计累计、高风险案件会不会被放出金额。

| §4 的步骤 | 在 V1 实现中的去向 |
|---|---|
| 0 幂等键命中 / 0.5 重算冲正 / 1 快照 / 7 累计提交 | **保留**，属横切事务语义，不进九步；V1 未定义这些系统行为，不得因"换算法"而删除 |
| 0′ 风控 HOLD | **保留**，且仍在九步之前：高风险案件不出金额、不占额 |
| 0″ 直付预授权 | **保留**，见 §4.1；但预授权额度须按九步口径重算（旧式 `min(…) × 保守比例` 是近似） |
| 2 策略求值 | **被 ①②③④ 取代**：不再是"一个 `base` 加一个 `ratio`" |
| 3 不可获利 / 4 年度免赔 | 概念保留、位置改变：并入 ⑥ 的费用类型累加与 ④ 的免赔维度，不再是两个独立步骤 |
| 5 比例 → 免赔 → 取整 → 分位配平 | **被 ⑤⑥ 取代**，且两段的先后由「免赔对象」决定（见 14.2） |
| 6 单层 min 控额 | **被 ⑦ 取代**：单层 `min` → 七层逐层截断 × 五种扣减方式 |

### 14.1 为什么必须重建：旧内核是标量四步

旧 `Adjustment.apply` 的算式是「一个基数 → 扣免赔 → 乘比例 → 截断」，能表达单责任、单比例。四类条款它表达不了，而且不是"少个功能"，是**给出错金额**：

| V1 要求 | 旧内核为何做不到 | 赔付后果 |
|---|---|---|
| 三费用池 × 医保内外 | 只有一个 `base`，各费用类型的比例与额度互不区分 | 一类额度用尽会吞掉另一类的可用额度（超赔或少赔，方向取决于哪类先耗尽） |
| 赔付比例多维查表 | 比例是单值，承载不了「承担费用类型 × 是否医保赔付 × 费用限额 × 赔案累计区间」的展开 | 只能落一个平均比例，条款里每条差异化比例都失效 |
| 免赔六维 | 免赔是标量，无对象/粒度/抵扣方式之分 | 无法区分"先免赔后折"与"先折后免赔"，同一免赔额在两种条款下差一个比例系数 |
| 控额七层 | 只有责任额度一层 | 次限额 / 共保 / 险种 / 计划四层无处安放，团体保单超赔 |

把这四类条款塞进标量四步，偏差是结构性的，补丁修不掉——修好一处，另一处又回到同一个根因。所以按 V1 重建管线，而不是继续在旧算式上打补丁。

### 14.2 九步编排（权威顺序，不可调换）

对应 V1 §4.2：

```
① 定适用情形      发票医疗类别 × 责任医疗类别 → 确定「承担医保费用类型」
② 定情形金额      取发票结算信息中对应字段
③ 定赔付比例      多维查表定位唯一适用比例；未命中即 fail-closed（禁止回落默认）
④ 定免赔信息      六维：类型 / 方式 / 形式 / 抵扣 / 对象 / 粒度
⑤ 算免赔后金额    按「免赔对象」决定扣免赔与乘比例的先后
⑥ 累加费用类型    Σ(各费用类型金额 × 各自比例) 再作免赔处理
⑦ 责任内控额      七层额度逐层截断，按「扣减方式」执行
⑧ 次限额分组      按「次」的定义分组，各组独立理算
⑨ 扣减与落账      在对应可用额度上扣减本次赔付，更新余额
```

**⑤ 是全管线最容易写错的一步，也是新旧实现差异最大的一处。** 换个「免赔对象」，扣免赔与乘比例就得换序：

```
免赔对象 = 发票费用   →  先扣免赔，再乘比例     (max(base − 免赔, 0)) × ratio
免赔对象 = 理算金额   →  先乘比例，再扣免赔     max(base × ratio − 免赔, 0)
```

两者**都有真实条款在用，不能统一成一种**。统一了必然一半产品算错，而且错得安静：结果是个正数，界面上看不出异常，只有懂这条条款的人对账时才能发现。

> **当前实现有一处例外，须留意**：`DeductibleRule` 在 `Target` 为空时回落到 `CALCULATED_AMOUNT`（先乘比例再扣免赔），并未按 fail-closed 拒绝。这与 14.5 的原则存在张力——若某条款实为"发票费用"口径而配置漏填，会静默少赔。V1 未定义该缺省值，属待业务确认项；确认前配置侧应显式填写，不要依赖回落。

### 14.3 两个 Min 嵌套：控额的精确语义

V1 §4.3〔定〕的责任级公式，**嵌套顺序不可交换**：

```
责任理算金额 = Min(
                 Min(医保范围内 × 比例, 医保范围内可用额度)
               + Min(医保范围外 × 比例, 医保范围外可用额度),
                 责任可用额度
             )
```

先按费用类型"比例折算 + 该类额度截断"，**再**求和，**最后**用责任额度截断。换成"先求和再截断"，某一类额度用尽时会吞掉另一类的可用额度，这是超赔与少赔的共同来源。

**额度层：V1 说七层，代码枚举是八个值，这不是漂移。** 七层之外多出的那个是账户维度：

| V1 §1.2 七层（细 → 粗） | `QuotaStack.Layer` | 说明 |
|---|---|---|
| ① 发票费用项目 / ② 发票费用类型 | `FEE_ITEM` / `FEE_TYPE` | 方式 2/3 的分组截断层 |
| ③ 责任次限额 | `OCCURRENCE` | 需先按「次」分组（步 ⑧）才生效 |
| ④ 责任共保 / ⑤ 责任 / ⑥ 险种 / ⑦ 计划 | `SHARED` / `LIABILITY` / `PRODUCT` / `PLAN` | V1 原话：③④⑥⑦「在多数 TPA 系统里不存在，但它们决定团体保单是否会超赔」 |
| —（§1.3 账户维度） | `PERSONAL` | 个账额度，**只在扣减方式 4/5 参与**，不是第八层业务额度 |

判读代码时不必把"8 还是 7"当矛盾：`PERSONAL` 是否进场由 `DeductionMode` 决定，方式 1/2/3 下它不参与。

**截断归因必须记全，且层级标签要标对。** `QuotaStack.GroupResult.cappedBy` 按「细→粗」记录该组真实被哪些维度截断（`FEE_TYPE:REASONABLE` / `PLAN` …），逐组带回 `Line` 并落行快照。两条理由：一个组同时撞多层是常态，只报首维会让"为什么少赔"答错一半；算完不接（丢在中间态）等于没归因——客户告知、双跑差异归因、后督复盘都拿不到这一维标识。**组级截断的层标签固定为 `FEE_TYPE`**：组额度的来源是费用类型子限额，不是「分组维度」；方式 1/5 下若沿用分组维度，会把费用子限额误报成责任额度截断。

**汇总层截断按比例回摊。** 责任/共保/险种/计划作用于总额，截断后按各组原额等比回摊（`Money.proRata`），保 Σ组 ≡ 总额。相比 reference-impl 的逐行顺序消耗，这同时消掉了"先到先得"——同一组的明细排在前面不会多分。

### 14.4 五条不变量：写在引擎里，不只写在测试里

| 不变量 | 内容 | 为什么必须在引擎内 |
|---|---|---|
| I1 精度 | 中间 6 位 / 结果 2 位 / HALF_UP；比例按百分数除 100 后量化 6 位 | 财务可复算的前提；散落在各处的 `setScale` 迟早不一致 |
| I2 归因完备 | 行级金额之和 == 实际应付；零赔付必须能说出为什么（受控原因码，禁自由文本） | "总额被砍但明细不变"是对账裂缝的根源 |
| I3 区间 | 半开区间 `[from, to)`，两两不重叠无空隙 | 重叠会命中多格，空隙会漏配 |
| I4 分位配平 | 按权重分摊后补尾差，使分项之和恒等于总额 | 逐项四舍五入必然差几分钱 |
| I5 免赔抵扣 | 相对免赔的 `deducted` 记 0，不记满额 | 记满额会让"未达门槛"的案子在下一次被错误抵扣 |

`InvariantGuard` 在引擎内自证这些性质（违反即抛），测试是第二道防线。理由是**测试只保护被它覆盖的入口**：换一个调用方、加一条批量通道、补一个运营工具，走的就是另一条路径，不变量没人守。分位配平的算法细节见 §8，本节只界定"哪几条必须恒成立"。

### 14.5 V1 边界：显式拒绝，而不是猜一个算法

V1 明确标为〔缺〕的能力（定额/津贴给付、共享保额、先赔后赔、外部控额）在原文里**只有名称、没有规则**。处理方式是装载期显式拒绝 + 受控原因码，而不是回落到默认值。

> **日限额已移出本清单（Q-05，2026-10-31）**：原 §7.4 只有两档名称（同日赔案 / 同日发票）而无判定位置，故与上述四项同列。现在它有了完整口径（业务日如何取、累计读哪里、截断排在第几层、窗口判不出来怎么办，见《业务规则 V1》§7.4），引擎按实现处理，不再拒绝。留在本清单里的四项仍缺规则，**不得**因为"日限额做出来了"就推断它们也能靠推导补齐。

`RuleGap.Code` 现有 16 个码，按语义分四组——**只有第一组是"V1 未定义"，其余三组不是**：

| 组 | 码数 | 典型码 | 应走的路 |
|---|---|---|---|
| 能力未定义 | 4 | `LIABILITY_FORM_UNSUPPORTED`、`SHARED_LIMIT_UNSUPPORTED`、`PRIORITY_CHAIN_UNSUPPORTED`、`EXTERNAL_QUOTA_UNSUPPORTED` | 转人工，并回执"该责任暂不支持自动理算" |
| 配置不成立 | 8 | `RATIO_NOT_MATCHED`、`RATIO_AMBIGUOUS`、`DEDUCTIBLE_CONFIG_INVALID`、`LIMIT_LAYER_UNDEFINED`、`OCCURRENCE_DIMENSION_MISSING`、`DAILY_LIMIT_WINDOW_UNDETERMINED` 等 | 退回配置岗补齐，不产生金额 |
| 前置不满足 | 2 | `WAITING_PERIOD_NOT_MET`、`LIMITED_CONDITION_NOT_MET` | 正常拒付结论（不属保险责任），不是系统缺陷 |
| 数据不自洽 | 2 | `INVOICE_SETTLEMENT_INCONSISTENT`、`INVALID_INPUT` | 退回录入/上游，附字段定位 |

> **一处待澄清**：第三组是**业务正常拒付**，与"规则不成立"不同源，却共用同一枚举。二者对外表述完全不同——前者应出"不属保险责任"的结论，后者应出"待补充材料/配置"。目前靠 `Code` 分发，新增原因码时若落进错组，拒赔理由会写反（客户收到的是"系统问题"而非"不属责任"，或反之）。建议后续按组拆成两个出口类型，或至少在码表上标注组别。

这条原则比任何单条算法都重要：**规则缺失时给出一个"看起来合理"的金额，比给出"不能算"危险一个数量级**——前者会安静地赔错一整年，且没人知道是配置问题。它同时满足合规（可解释、可追溯）与工程（fail-closed）两侧要求。

### 14.6 一条教训：文档宣称 ≠ 代码做到（死配置）

16 号分册曾宣称"七层控额已落地"。实际只有三层真接线：`occurrenceLimit`（次限额）、`productLimit`（险种）、`planLimit`（计划）、`sharedLimit`（共保）四个字段**被声明、被装载期校验，却没有任何算式读它**。配置界面能填、能保存、能通过自检，赔付金额里却完全不起作用。

这类缺陷的危险不在金额偏差本身，而在**三处证据都指向"已支持"**：配置页、文档、代码评审。没有一处会报错。

17 号分册把它收敛为两个合法状态——**真的生效，或装载期拒绝**，不允许第三种「声明了但不用」。当前状态是前者：四个额度已在 `AdjustmentEngine` 装入 `QuotaStack`，次限额经 `hasOccurrenceLimit()` 判定后读取。

**怎样查才可信**：不要按字段名在"定义处"确认，要按**读取点**确认——同一字段若只出现在自己的声明与校验里，就是死配置：

```bash
# 正确做法：找「除声明类之外」的引用。有输出 = 真的被读；零输出 = 死配置
grep -rn "\.occurrenceLimit()" src/main/java | grep -v "LiabilityRule.java"
```

> **工具陷阱（本轮实测）**：上面这条命令在本机会**静默返回空**（同一模式用 Python 扫出 `AdjustmentEngine` 2 处、`OccurrenceGrouper` 4 处引用）。也就是说，`grep` 零输出既可能是真死配置，也可能是工具没匹配上——**它不能单独作为"不存在"的证据**。凡要做"某能力确实没实现"这种否定判断，必须换一种方式复核（Python/IDE 全局检索/编译期引用），否则会把"没查到"当成"没有"，写进文档就成了假证据。

这条已升格为通用规则：**任何"已支持"的声明，必须能指向一处实际读取该值的算式**。它同时也是本轮给 `design/` 加术语门禁的理由——只靠人记得核对，下一次还会漏。

### 14.7 代码落点与验证

**先厘清一件事：这里的类名与 §5–§7 不是同一套。** §5–§7 描述的是 `synap-claim-oracle` 的 `com.bone.synap.settlement`；本节是生产包 `com.bone.claim.domain.model.adjustment.engine`（纯 Java、无框架依赖，满足 `domainMustNotDependOnOuterLayers`）。两套类职责相近但实现不同源，这是双轨比对成立的前提——不要把 §7 的 `LimitControl` 当成生产代码去找。

| 类 | 职责 | V1 对应 |
|---|---|---|
| `FeePools` | 三费用池 × 医保内外拆分；三式核对 | §3.4–3.6 |
| `PayRatioTable` | 多维比例查表，未命中/命中多格均 fail-closed | §5 全族、§4.2 步 ③ |
| `DeductibleRule` / `DeductibleEngine` | 免赔六维；绝对/相对 × 跨门槛/未跨 四分支 | §6.1 / §6.2 / §6.6 |
| `QuotaStack` | 七层额度（+个账维度）与五种扣减方式，**唯一实现** | §1.2 / §7.2 |
| `OccurrenceGrouper` | 「次」六档分组，只分组不算钱 | §7.3、步 ⑧ |
| `LiabilityRule` | 十一维强类型配置 + 装载期自检 | §2 全表 |
| `AdjustmentEngine` | 九步编排 + 快照物化 + 归因 | §4.2 |
| `InvariantGuard` / `RuleGap` | I1/I2/I4 引擎内自证；fail-closed 原因码 15 个 | §9 |

`Adjustment.apply` 退化为外壳（状态机 + 快照 + 持久化），**类里没有第二条算式**。这是硬约束：同一个条款出现两种算法，比没有算法更难排查——遇到不一致时没人能判断该信哪一个。

**验证三轨，互不顶替**（任何一轨单独存在都不成立）：

1. **双轨比对** — `AdjustmentDualTrackConsistencyTest`：生产实现 vs 从 `synap-claim-oracle` 抽取语义子集另写的独立 oracle，逐场景比对赔款金额。防的是"实现与规格同错"：两边都错成一样时，单轨测试照样全绿。
2. **缺口哨兵** — `AdjustmentSemanticGapInventoryTest`：把 oracle 链路的 10 个环节逐项标注 `SUPPORTED` / `PARTIAL` / `GAP`，每个 GAP 配一条**反证测试**，证明它现在确实没做（如 GAP③ 第三方已付抵扣不生效、GAP⑨ 多费用行只落 1 条汇总行）。补齐时反证会转红，**这是设计意图**，应改档并回填门禁，不要删断言。它防的是"双轨全绿 ⇒ 与参考实现等价"这种放大解读。
3. **变异验证** — `AdjustmentMutationDiscriminationTest`：19 类"被改坏的 oracle"（顺序颠倒、漏钳零、舍入方向错、漏社保过滤等）每一类都必须在至少一个场景与生产实现分歧，且正确 oracle 的分歧数为 0，另加一条比对器灵敏度对照（人为扰动 0.01 必须被识别）。只断言"正确实现全绿"排除不了假绿——它同时容忍"比对器失明"。

`synap-claim-oracle` 仍保留在 `doc/ai-product/synap-claim-oracle/synap-claim-settlement/`，**不并入生产模块**：第二轨的价值全在"独立于被测实现"，同 module 共享依赖会让比对退化为自证。它由独立 CI job 常跑（`.github/workflows/synap-claim-oracle.yml`），避免"资产在、但没人执行"。
