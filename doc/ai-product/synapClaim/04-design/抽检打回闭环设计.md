# 抽检打回闭环设计

> v1.0 ｜ 2026-11-13 ｜ 性质：设计（代码落在批 4）
> 适用：结案后后督抽检的结论处置——把「只登记」升级为「可执行」，并与资金状态强一致。

## 一、决策摘要

| # | 决策 | 理由 |
|---|---|---|
| D7-1 | 结论可执行化：新增 `t_claim_inspection_action` 承载处置 | 现状 `action_taken`/`target_status` 只是意图字段，无人消费 |
| D7-2 | 未支付可直接打回；**已支付必须先冲正**才能打回 | 已赔付案件直接回退状态会造成「案在审、钱已出」的账实不一致 |
| D7-3 | 不新增案件状态码，打回复用既有迁移 | 打回是「回到核赔/复审」，不是新业务阶段 |
| D7-4 | 一单一处置（幂等） | 抽检单号确定性生成，重复处置必须被拒绝而不是覆盖 |

## 二、现状

| 事实 | 证据 |
|---|---|
| 结论「只登记不执行」 | `InspectionRecord.java:30-31` |
| 处置动作枚举 `RECALCULATE/REVIEW/REFUND/CLOSE` 仅作意图 | `InspectionRecord.java:270-285` |
| `target_status` 允许 30/31/32 但无人消费 | `InspectionRecord.java:38-39` |
| 结论不可改写（终态） | `InspectionApplicationService.java:136-139` |
| 抽样比例全局配置（默认 5%），非租户可配 | `InspectionSamplingJob.java:52-54` |
| 无抽检列表接口，只能按 claimId 查 | `InspectionController.java:41,133` |

## 三、处置模型

`t_claim_inspection_action`：`id` / `tenant_id` / `inspection_no` / `action`（`RETURN`/`RECALCULATE`/`CLAWBACK`/`CLOSE_ONLY`）/ `from_status` / `to_status` / `reverser_ref`（冲正流水号）/ `operator_id` / `executed_at` / `result`（`APPLIED`/`BLOCKED_PAYMENT_NOT_REVERSED`）/ `version`。唯一：`UNIQUE(tenant_id, inspection_no)`（一单一处置）。

## 四、两条打回路径

```
质检结论 = DIFF（差异）
  │
  ├─ 案件未支付（无 SUCCESS 支付流水）
  │     → action=RETURN：回 ADJUSTING(41) 或 REVIEWING(44)，写 action(result=APPLIED)
  │     → 同时把关联 t_claim_task(该案) 置 CANCELLED，重新生成核赔任务
  │
  └─ 案件已支付（存在 SUCCESS 支付流水且未冲正）
        → 允许的 action 只有 CLAWBACK 或 CLOSE_ONLY
        → 打回请求返回 SC_CLAIM_INSPECTION_PAYMENT_NOT_REVERSED
        → 冲正（REFUND 回冲）成功并回写 reverser_ref 后，才可执行 RETURN
```

**判断顺序固定**：① 案件是否终态（现状要求）→ ② 是否存在成功且未冲正的支付 → ③ 才决定允许的 action 集合。顺序颠倒会出现"先改状态再发现钱已出"的不可回滚。

## 五、与既有能力的对接

- 差异回流不变：`InspectionFeedbackRecorder` 继续发 `AiEvalSampleCollectedEvent`（评测集），处置动作是**新增**而非替换。
- 资金一致性：冲正走既有 `SettlementController` 的 REFUND 语义，不新造资金路径。
- 抽检待办：抽检单接入 `t_claim_task`（`task_type=INSPECTION`），修掉"必须先知道 claimId 才能干活"的缺口。
- 比例可配：抽样比例从 `@Value` 迁到 `t_feature_toggle` 的 `INSPECTION_SAMPLING`（`config_json: {rate, strata}`），并保留全局默认值兜底。

## 六、分批落地

批 4：处置表 + 两条路径 + 抽检队列 + 比例可配。验收：未支付打回成功且任务重建；已支付未冲正返回明确拒绝码；冲正后打回成功；重复处置返回冲突而非覆盖；抽检列表可按状态/时间/质检人筛选。

## 七、风险与回退

| 风险 | 缓解 |
|---|---|
| 已支付打回造成账实不一致 | 强制冲正前置 + 拒绝码 + action 记录 `BLOCKED_*` 结果 |
| 打回后任务重复生成 | 任务存活唯一约束（`alive_key`）保证一案一类型只有一条存活任务 |
| 抽样比例调整导致样本突变 | 比例变更需 dry-run 预览当日样本量，且写审计 |

**回退**：处置能力带开关 `INSPECTION_ACTION`；关闭后回到"只登记差异"现状，历史 action 记录保留可读。

## 八、不做清单

- 不新增案件状态码（打回复用既有迁移）。
- 不做批量打回（受保护动作禁批量）。
- 不做自动追偿/自动扣款。
- 不改「结论不可改写」的终态约束。

## 九、待决策

2. 抽检比例是否按险种分别配置（当前按分层标识统一比例）。
