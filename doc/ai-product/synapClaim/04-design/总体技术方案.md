# synapClaim 智能理赔系统-总体技术方案

> **本文回答**：系统边界在哪、由哪些模块构成、**每个模块对外提供什么、守什么不变量**（§4.1 组件视图）、模块之间怎么协作、关键链路怎么跑通、怎么迁到目标形态。**不回答**：模块内部的算法步骤、字段级 DDL 与端点参数——这些按 §4.1「详设落点」列指向对应真源章节，不在本文重述。
>
> **事实基线**：`bone-apps/synap-claim` 实测 **370 个 Java 类 / 20 个领域子域 / 35 个应用服务 / 31 个 Controller / 19 个外部端口**；前端 `bone-frontend` 为 10 个微应用（`bone-shell` 壳 + `bone-claim-app` 理赔）。参考基线 `pk-tpa-saas`（937 类 / 7 模块 / 前端 `policyConfig` 9,501 行）仅作**业务形态**参照，不作工程质量标尺（§10）。
>
> **数字口径**：类数、服务数、端点、端口、错误码均为 2026-11-07 对 `bone-apps/synap-claim` 实测，重跑命令见 §4 末。**§0 的三条结论已逐条回读代码核验**（2026-11-07 修正，见 §0 末）。

## 0. 决策摘要

**一句话**：`ClaimPolicy`/`ClaimPlan`/`ClaimCoverage` 三聚合根的**数据层已经落地**（"有表无实体"是错的），但映射层仍是 `role=draft`（见 `04-design/多保司保单配置面与主数据映射设计`）；卡住"配置驱动"的是另外四处——保单/计划主数据 CRUD 端点未接线、责任要素固定列、引擎不按类型分派、流程配置零消费方。

| # | 缺口 | 实测事实（代码为准） | 后果 |
|---|---|---|---|
| 1 | **保单/计划主数据 CRUD 端点未接线** | `ClaimPolicy`/`ClaimPlan`/`ClaimCoverage` 三聚合根 + 3 个 Repository + `V16` 迁移都在，被 6 个配置应用服务读取，应用层已有 `createPolicy`/`updatePolicy`/`createPlan`/`createCoverage` 六个写方法。**但** 31 个 Controller 里没有三聚合根的 CRUD 端点；`PolicyDetailApplicationService` 生产零调用方（仅单测引用）。配置面**并非整体不可写**：`LiabilityConfigController` / `CoverageOverrideController` / `QuotaConfigController` / `ReferenceLibraryController` / `CodeMappingController` 已有写端点，`ClaimConfigController` 才是唯一字典 GET | 保单/计划仍只能靠迁移或外部同步；**缺口精确落在「三聚合根缺 REST 端点」，不是「配置面无法编辑」** |
| 2 | **责任要素未要素化，且三层口径已错位** | **活库** `t_adj_liability` 实测 31 列全标量（`pay_percent DECIMAL(6,2)` 等），零 JSON，**9 个目标要素里有 6 个活库根本没有列**；**`工程落地版 §9.5`** 写的 `adj_liability` 却是 46 列、含 3 个 JSON 列与 `restrict_*`，与活库差 23 处业务列；**本文 §5.2** 的 9 个 JSON 列是更远的目标态（TPA 基线形态） | 按任一层写代码都会错：照 §5.2 写查不到列，照 §9.5 写字段类型对不上。三层必须显式标注时态（§5 开头已加横幅） |
| 3 | **引擎不按责任类型分派** | `AdjustmentEngine` **2,334 行单类**；`engine/` 包 13 个类里没有策略接口。而 `AdjLiability.liabilityType` 已定义 `REIMBURSEMENT`/`FIXED_AMOUNT`/`ALLOWANCE` 三值 | 类型字段配了却不驱动算法；新增责任类型必须改主类（基线是 861 行 + 三策略工厂） |
| 4 | **流程配置是死配置** | `ClaimFlowConfig` 有 `config_json` + 版本化仓储（`findByFlowKey`/`highestVersion`），但**全仓仅 2 个 Java 文件引用它**（实体自身 + 仓储），`ClaimFlowConfigRepository` 零调用方；无 Stage/Fire/Trigger/Condition 层 | "配了不生效"——比"只有开关"更危险，因为配置页、文档、评审三处证据都看着像已支持 |

> **2026-11-07 事实修正（重要）**：本表原先写作「`Policy`/`Plan`/`Coverage` 有表无实体、配置面无法编辑」，**其中"无实体"是错的**——只查了 `PolicyQueryPort` 与 Event 就下了结论，属于「按声明处取证、没按读取点取证」。核验结果：三聚合根在 `domain/model/policy/`、三仓储在 `domain/repository/`、V16 已建表、6 个配置服务在用。同步修正 §9.1 的 M2（不再是"补实体"）。
>
> **一条方法论（通用规则与工具陷阱的权威版见 `方法论-能力取证.md`）**：查"某能力是否存在"要按**读取点**取证（谁调用、谁消费），不能按**声明处**（类/字段/配置项存在）取证；反过来，断言"不存在"时也要把调用链扫完，不能只看某个 Port。两条都踩过，本表四条结论已逐条按调用链复核。

**目标形态（D1 已决，2026-11-08）**：`bone-apps/synap-claim` 升为父聚合，业务模块改名下沉，三模块互不反向依赖。**代码现状仍是单 module `com.bone:synap-claim`，下图是目标态**（时态标注同 §5 开头横幅）。

```
bone-apps/synap-claim/                # 父 POM：com.bone.claim:synap-claim，packaging=pom，不含业务代码
├── synap-claim-app/                 # 原 bone-apps/synap-claim 整体迁入；可执行 jar，ClaimApplication
├── synap-claim-sdk/                 # 契约：四级配置模型 + Request/Outcome/Port 接口，零框架依赖
└── adjustment-engine/               # 纯算术：仅 JDK，calculate(Request)→Outcome
```

| Maven 坐标 | artifactId | 形态 |
|---|---|---|
| `com.bone.claim` | `synap-claim` | 父聚合，`packaging=pom`，parent 仍是 `com.bone:bone-parent` |
| `com.bone.claim` | `synap-claim-app` | 业务应用，可执行 jar |
| `com.bone.claim` | `synap-claim-sdk` | 契约，零框架依赖 |
| `com.bone.claim` | `adjustment-engine` | 纯算术，仅 JDK |

**engine 用短名 `adjustment-engine` 的前提是独立 groupId**：全仓其余模块 groupId 都是 `com.bone`，裸 artifactId 会脱离命名空间；三模块统一 `com.bone.claim`（与 Java 包名一致，实测当前未被占用），由 groupId 承担归属，artifactId 不再重复 `synap-claim`。依赖方向单向 `app → sdk`、`app → engine`、`engine → sdk`；父 POM 只管 `dependencyManagement` / `pluginManagement`；`bone-apps/pom.xml` 的 `<module>synap-claim</module>` 路径不变，指向聚合根。

**坐标变更影响面（实测）**：全仓无其他 pom 依赖 `com.bone:synap-claim`，CI 与本地脚本按模块路径定位（`-pl bone-apps/synap-claim`），不按 artifactId；需同步的是三个子模块 pom 的 `<parent>` 与彼此 `<dependency>` 坐标。业务模块名 `synap-claim` → `synap-claim-app` 与外层聚合一并落。

**落地顺序（D3 已决：配置与引擎并行）**：M1 父聚合化 + 契约定型 → **M2 责任要素 JSON 化 ∥ M4 引擎拆三策略**（共享 SDK 契约并行）→ M3 接通配置编辑端点 → M5 抽流程层并让 `config_json` 真正被消费。依赖与并行纪律见 §9.1。

**§12 待决策：无**。D1 / D3 / D4 已于 2026-11-08 拍板，结论分别回写 §0（目录与命名）/ §4（子域归属与收敛规范）/ §9.1（并行排期）；D2 早前按 C 案收口（§9.2）。

> **2026-11-08 事实修正（以代码为准）**：`09-records/reviews/M2-责任额度列迁移评审.md` §五 断言「`AdjustmentEngine` 全仓零调用点、`t_adj_liability` 金额列不参与运行时赔付计算」**与代码相反**。实测链路：`AdjustmentController` → `IndemnityApplicationService` → `Adjustment.calculate` → `Adjustment.apply()`（`Adjustment.java:459` 直接调 `AdjustmentEngine.calculate(Request)`），另有 `/adjust/recalculate` 与 preview/recompute 两条入口；同一 `apply()` 在 `:430-444` 用 `LiabilityRule.fromLegacy(...)` 把 `pay_percent` / `liability_deduct` / `liability_limit` 三个标量列喂进引擎，`AdjustmentEngine.java:1429` 以 `liabilityLimit` 控额。因此「先接线引擎」的前置问题**不存在**，路 A / 路 B 二选一已核销；M2 的价值是让九要素可配置，不是让配置进入赔付计算。见该评审 §五 与本文 §9.1。

## 1. 目标、约束与非目标

### 1.1 业务目标（一期）

| # | 目标 | 可验收的口径 |
|---|---|---|
| G1 | 门诊小额医疗**自动理算**，人工只处理异常 | 自动通过率、转人工原因可归因 |
| G2 | 赔付金额**可复算、可解释** | 同一输入任意时刻重算结果一致；每笔金额能回溯到「哪条规则 + 哪个因子值」 |
| G3 | 配置**由业务自己改**，不发版 | 新增责任 / 改赔付比例不需要 DDL、不需要改代码 |

### 1.2 硬约束（只列判断架构走向必读的三条）

| 约束 | 来源 | 落点 |
|---|---|---|
| **AI 不碰钱** | synapClaim P1 | AI 节点只产 `AiSuggestion`（建议 + 置信度 + 证据引用）；金额计算与资金流转全在确定性代码 |
| **拒赔必须人工确认** | Rulebook R-MAN-03 | `SUGGEST_REJECT` 为待确认态，核赔员提交后生效；拒赔必填五要素 |
| **领域零框架依赖** | AGENTS.md §1 | `adapter → application → domain ← infrastructure`；domain 不引 Spring |

**完整 11 条**（另含持久化唯一入口、租户以认证主体为准、禁悲观锁、双阈值熔断、统一响应、入站边界、可回放审计、幂等）**见《工程详细设计（落地版）》§2（硬约束映射）**——那张表是唯一真源，本节不复制其余八条：两处各维护一份，改一处不会通知另一处。

### 1.3 非目标（一期明确不做）

| 不做 | 理由 |
|---|---|
| 住院 / 意外 / 重疾险 | 一期只做企业补充医疗·门诊·小额；住院的理算结构（按天、按次、分段）与门诊不同源 |
| 多租户 SaaS 化 | 单租户日案件 ≤5000；租户隔离已按字段实现，但计费 / 配额 / 自助开户不在本期 |
| 低代码规则可视化编辑器 | 规则配置先做表单；任意画布是独立产品 |
| 医疗目录全量 | 只接医学目录子集，且目录是**外部主数据**，本库不存副本（存了就成第二真源） |
| 独立微服务部署 | 理算必须与案件、责任、结算、额度在**同一事务边界**内；拆进程引入分布式事务 |
| 把理算塞进规则引擎（C2） | 理算 95% 是确定性金额算术；DSL 表达算术不可控且破坏快照可复算 |

## 2. 系统上下文（C4 L1）

系统不是孤岛：**上游有保司与存量 TPA，下游有支付与中台**。边界不清会导致"同一个事实两处维护"。

| 外部系统 | 与本系统的关系 | 交互方式 | 本系统承担 |
|---|---|---|---|
| `bone-shell` 微前端壳 | 宿主 | qiankun 挂载 | 子应用可独立调试，但验证须走 shell（脱离壳不渲染） |
| `bone-claim-app` | 理赔工作台 | HTTP `/api/v1/claim-ops/*` | 提供 31 个 Controller 的对外契约 |
| `bone-ai` 中台 | 规则求值（C2）/ 知识检索 / AI 网关 | `RuleEnginePort` / `KnowledgeRetrievalPort` / `AiGatewayPort` | **只做决策，不碰钱**；AI 输出必须带证据引用 |
| 保司 / 存量 TPA | 上游保单与案件来源 | `PolicyQueryPort` + 推送回传 | 保单配置**外部同步**（§0 缺口 1 的由来） |
| 支付通道 | 资金出账 | 两段式预占到实付 | 金额取理算产出的确定性结果，支付端不重算 |
| 医院 / 医保 / 目录 | 主数据 | `ItemCatalogPort` | 目录不落库；端口未接线即全部 `UNKNOWN`，退补件而非安静全额赔 |
| `bone-iam` | 认证与租户 | JWT | 租户身份取认证主体，不取请求头 |
| `bone-metadata` | 元数据与持久化 | SDK | 唯一持久化入口 |

**读图要点**：所有外部依赖都经 **Port** 出站（19 个 Port 与 `infrastructure/` 19 个子包一一对应），domain 不直接感知任何外部系统。

## 3. 总体架构（C4 L2）

```
┌────────────────────────── 表现层 ──────────────────────────┐
│ bone-shell（壳）  └─ bone-claim-app（理赔工作台）            │
│              配置面 / 案件面 / 稽核面 / 治理面                │
└──────────────────────────┬─────────────────────────────────┘
                           │ HTTP /api/v1/**（31 Controller）
┌──────────────────────────▼─────────────────────────────────┐
│ bone-apps/synap-claim/  父聚合（packaging=pom，目标态）      │
│  └─ synap-claim-app/    业务（现状 = 整个 synap-claim 模块）  │
│      adapter/       rest（31）· schedule · web               │
│      application/   35 个 ApplicationService                │
│      domain/        现状 20 子域平铺 → 目标态 7 上下文目录    │
│      infrastructure/ 19 个子包 ──→ 19 个 Port 出站           │
└──────┬──────────────────────────────────────┬──────────────┘
       │ 纯函数调用（同进程，无 RPC）           │ Port
┌──────▼─────────────────────────────┐  ┌──────▼──────────────────┐
│ adjustment-engine                 │  │ bone-ai / 支付 / 保司 / 目录│
│ （目标态）calculate(Request)→Outcome │  │ 全部经 Port 防腐           │
└────────────────────────────────────┘  └─────────────────────────┘
```

**三条架构判据**（每条都对应一次真实踩坑）：

1. **编排在应用层，算术在引擎**。把"读配置→算→冻额→落库"揉进引擎，引擎就依赖事务与持久化，无法脱离 DB 回放与批量验算。
2. **domain 零框架依赖**。否则单测要起 Spring 上下文，理算场景从毫秒级变成秒级，回归跑不动。
3. **出站一律经 Port**。domain 里出现任何 `Feign`/`RestTemplate` 都是越界。

## 4. 模块划分（7 个限界上下文）

**D4 已决（2026-11-08）**：现状 **20 个子域平铺在 `domain/model/` 下**，目标态收敛为 7 个限界上下文目录（归属判据、包结构与迁移纪律见本节末）。下表类数按目标态归属统计，`quota` 只归 Funds，不再重复计入 Config。

| 上下文 | 子域 | 类数 | 应用服务 | 职责 |
|---|---|---:|---|---|
| **案件 Claim** | `claim` `inspection` `evidence` `sla` `appeal` `review` | 37 | ClaimCase / Inspection / ClaimAssistant / Appeal / Sla | 报案、查勘、证据、时效、申诉、复核 |
| **配置与主数据 Config** | `config` `policy` `liability` `mapping` `reference` | 49 | ClaimConfig / LiabilityConfig / LiabilityFeeRule / CoverageOverride / PolicyDetail / ClaimDict / CodeMapping / ReferenceLibrary | 保单→计划→险种→责任四级配置、码表映射、字典 |
| **理算 Adjustment** | `adjustment` | 17 | Indemnity / AdjustmentOps | 九步管线、免赔、控额、快照 |
| **决策 Decision** | `decision` `evaluation` `rule` `event` | 25 | DecisionRun / DecisionExecution / AutoApproval / InvoiceVerification | 决策图执行、AI 编排、自动审批、发票查验 |
| **资金 Funds** | `settlement` `reconciliation` `quota` | 18 | Settlement / Reconciliation / Quota / QuotaConfig | 结算单、对账、额度占用与释放、额度账户开户与调额 |
| **AI 治理 AI Ops** | —（跨 application） | — | AiCalibrationReport / AiProviderProbe / AiRollout / AiRolloutDrill / AiRuntimeHealth / BlindLabel / DiffSampleExport / EvalSampleExport / AiEvalSampleIndex | 模型探活、灰度、校准、评测样本、盲标 |
| **分析出站 Analytics** | `stakeholder` | 1 | ClaimAnalytics / Outbox | 指标、事件投递 |

**两条结构性结论**：

1. **配置与计算必须物理分离**。参考基线里 `adjustment` 域 12 类只做配置增删改查，算法在独立 module——"业务能自己配"和"算法不因配置改动而改"是两件事，混在一起后每次加要素都要动算法类。
2. **`mapping` 26 类是最大子域**，超过 `claim` 16 类。这说明**多保司映射是真实复杂度**，不是附属功能；它承担的是"同一概念在 N 家保司的不同叫法与不同结构"的翻译层。

**归属判据与收敛规范（D4 已决，物理子域归属的唯一真源）**：

1. **按聚合根与不变量归属，不按类名或 URI**。`domain/model/quota/` 实测 6 类全是资金运行时状态——`QuotaAccount`（`initial − claimed − frozen` 守恒）、`QuotaTransaction`（append-only 占用流水）、`QuotaChangeLog`（保全/调额）、`QuotaProjection` / `QuotaLedgerChain`（余额投影与串链校验）、`QuotaCap`（纯计算原语），**零个配置定义**；`config/` 域对 quota 零引用，`reconciliation/` 13 处类型/常量引用、`SettlementApplicationService` 10 处占额/释放调用。额度的**规则定义**实际落在 `liability` 的 `liability_limit` / `pay_percent` 与 `policy`。故 `quota` 归 **Funds**，Config 行的重复登记撤销（55 → 49 类、9 → 8 服务；Funds 保持 18 类、3 → 4 服务）。
2. **命名与归属不一致要显式登记，不改代码**。`QuotaConfigController` / `QuotaConfigApplicationService` 做的是额度账户**开户与调额**（写 `t_quota_account`），按用例归 Funds；名称里的 `Config` 是历史命名，列为后续重命名候选。**代码现状是事实真源**，本节只定文档归属，不暗示包路径已迁移。
3. **一名多义登记**：PRD §9.1 的 A5 `PersonalQuota` 是**业务能力**命名，《工程详细设计-落地版》§3.6 的 8 上下文是**需求侧切法**，《理算引擎设计》里的 `Quota` 是**纯计算值对象**。三者视角不同、不冲突；物理子域 `domain/model/quota/` 的归属以本节为准。
4. **包结构**：`com.bone.claim.domain.model.<context>/<subdomain>/`，7 个上下文目录为一级，原子域名保留不改（一次只动目录层级，避免同时改包名与类名）；跨上下文**禁直接 import 领域模型**，经 application 编排 / 领域事件 / Port；`common/`（错误码、`Money`、常量）为共享内核，不归任一上下文。
5. **收敛纪律（逐上下文迁移，禁止一次性全改 import）**：一次一个上下文、一个 PR，按风险从低到高 `Analytics → Adjustment → Funds → Decision → Config → Claim`；每批验收 = `mvn clean test` + ArchUnit + 全仓 grep 旧包路径为 0 + 零行为变更；迁移期间不新增跨上下文直接引用。收敛是**目标态**，当前 `domain/model/` 仍是 20 子域平铺。

### 5.1 四级结构

```
Policy 保单      policy_no · config_status · status · effdate / expdate · adjustment_order · certificate_config
 └ Plan 计划     plan_limit · version · status
    └ Coverage 险种   coverage_limit · version
```

**`version` 贯穿 Plan / Coverage / Liability**：一次配置变更 = 一个新版本，赔案绑定立案时的版本重算。可复算不靠代码里的常量，靠数据版本。

### 5.2 Liability 的 9 个要素（JSON 列）

> **命名约定（实施期必读）**：下表的列名是**语义指代**。其中 `pay_percent` / `liability_deduct` / `liability_limit` 与活库现存的标量列同名，expand/contract 下同名不同类型无法双写共存，故 M2 实施时这 3 个 JSON 列的实际落名为 **`pay_percent_rule` / `liability_deduct_rule` / `liability_limit_rule`**（`*_rule` 后缀），旧标量列在 contract 阶段才删。详见 §9.1.1 ①。

| 目标列（JSON） | 含义 | 活库现状 `t_adj_liability`（实测） |
|---|---|---|
| `pay_percent` | 赔付比例（可分段、按金额区间、按赔案累计） | **同名但标量** `DECIMAL(6,2)`，只能表达单一比例 |
| `liability_deduct` | 免赔（年 / 次 / 日 × 金额或比例） | **同名但标量** `DECIMAL(12,2)`；另有 `invoice_deduct` / `adjust_deduct` 两个标量免赔 |
| `liability_limit` | 责任额度（单次 / 年累计 / 终身） | **同名但标量** `DECIMAL(12,2)`；另有 `daily_limit` |
| `quota_controller` | 控款方（个账 / 公账 / 直付 / 不限） | **活库无此列**；§9.5 设计态写了 `VARCHAR` |
| `restrict_scope` | 适用限定（医院等级 / 地区 / 网络） | **活库无此列**；部分语义由 `limit_hospital_codes` / `limit_mode` 分散承载 |
| `restrict_object` | 适用对象（本人 / 配偶 / 子女，年龄性别） | **活库无此列** |
| `restrict_out_insure` | 适用出险（疾病 / 意外，含除外） | **活库无此列** |
| `times_limit` | 次数限额（日 / 年 / 终身次数） | **活库无此列**；§9.5 设计态写了 `JSON` |
| `adjustment_rule` | 理算明细（费用项映射 / 目录 / 共保分摊） | **活库无此列**；§9.5 设计态叫 `adjustment_detail VARCHAR` |

另加 `formula` VARCHAR(512)：只读展示用公式文本，不参与计算——**活库同样没有 `formula` 列**。

**九要素的落地差距**：3 个有同名标量列（`pay_percent` / `liability_deduct` / `liability_limit`），**6 个在活库完全不存在**。因此 M2 不是"把 9 个 VARCHAR 改成 JSON"，而是"**6 列要新建 + 3 列要做标量→JSON 的类型迁移与存量数据回填**"，工作量与风险都比原描述大。

**为什么 JSON 而不是 9 张子表**：要素会持续增加（基线从 6 个长到 9 个）。每加一个要素都做 DDL，等于把"业务自己能配"变成"每次都要发版"。代价是丢掉数据库层校验，所以必须补**写入期 JSON Schema 校验**（§10 第 2 行）。

| 9 | 赔付比例（11 因子） | `pay_percent` | `pay_percent DECIMAL(6,2)` | **标量降级**：分段 / 按金额区间 / 按累计 无法表达 |
| 10 | 保额设置 | `liability_limit` | `liability_limit` + `daily_limit` | **部分落地**（单次 / 日限额；年累计、终身缺） |
| 11 | 控额规则 | `quota_controller` + `times_limit` | `limit_mode` / `daily_limit_basis` / `shared_code` / `prior_liability_uuid` + `quota_account*` | **部分落地，语义不等价**：控款方与次数限额无列 |

**读法**：11 维里只有「等待期」和「责任形式的列」是完整单列落地；**4 维无列**（保额形式 / 适用对象 / 适用情形 / 控额规则中的新列）、**2 维标量降级**（免赔 / 比例，这是最影响理赔结果的）、其余分散承载。这解释了为什么 §1.1 的 G3「配置由业务自己改、不发版」还达不到：不是缺页面，是**物理列装不下业务语义**。

> **实施约束**：V1 §2 中标〔疑〕〔缺〕的维度（责任形式的定额/津贴分支、区域与医保限定等）**澄清前不得据以实现**；M2 的范围只含已〔定〕维度的 JSON 化与存量回填，不顺手把 11 维一次补齐。

### 5.3 `liability_type` 是配置驱动的枢轴

| 类型 | 算法骨架 |
|---|---|
| `REIMBURSEMENT` 报销型 | `min(发票可赔额, 责任额度) × 比例 − 免赔`，再受控额约束 |
| `FIXED_AMOUNT` 定额型 | 固定金额 × 次数（手术定额、床位日额） |
| `ALLOWANCE` 津贴型 | 日津贴 × 天数，受起付期与最长天数约束 |

配置面选类型，引擎按类型选策略——这是"配置驱动算法"的唯一枢轴。

## 6. 理算引擎（纯算术）

### 6.1 接口是纯函数（现有形态是对的，迁移时别改坏）

```java
// adjustment-engine（目标态）  com.bone.claim.adjustment.engine.AdjustmentEngine
public record Request(...)     // 配置快照 + 费用项 + 历史累计 + 目录准入
public record Outcome(...)     // 责任级明细 + 零赔付归因 + 不变量自证
public static Outcome calculate(Request request);
```

**这是 `synap-claim-app` 已经做对、而基线没做到的地方**：基线 `adjustClaim(claimId)` 把「读配置→算→冻额→落库」揉进一个方法，引擎因此依赖事务与持久化，**无法脱离数据库回放与批量验算**。

| 层 | 职责 |
|---|---|
| `adjustment-engine` | `calculate(Request) → Outcome`，纯函数，可并行、可回放、可单测 |
| `synap-claim-app` 应用服务 | 读配置快照组装 `Request` → 调 `calculate` → 冻额 → 落库 → 发事件 |

**引擎已接线**：`AdjustmentController` → `IndemnityApplicationService` → `Adjustment.apply()` → `AdjustmentEngine.calculate`，M2 / M4 是对这条既有链路的结构改造，不是「接线」。`Adjustment.apply()` 里的 `LiabilityRule.fromLegacy(...)` 已把旧标量金额列适配成引擎入参，是 M2（数据形态）与 M4（算法结构）能并行的防腐层依据（§9.1）。

**迁移只搬不改**：包名改到 engine 模块，签名不动。若为"对齐基线"把 `claimId` 塞进引擎，等于把已解耦的边界重新耦合回去。

### 6.2 按 `liability_type` 分策略

```
LiabilityAdjustmentStrategy
├── checkAdjustable(ctx)           // 该责任是否可赔（限制条件）
├── adjustmentInvoice(ctx)         // 算一条责任 → 明细
├── buildAdjustFormula(liability)  // 生成展示公式（仅展示，不参与计算）
└── getSupportedType()             // 声明支持的类型

实现：Reimbursement / FixedAmount / Allowance 三支
分派：LiabilityAdjustmentStrategyFactory，注入 List → Map<LiabilityTypeEnum, Strategy>
      查不到 → 抛异常（fail-closed，不返回 0 元）
```

**为什么按类型分策略**：三类算法**输入结构不同**——报销型吃发票明细，定额型吃次数与项目，津贴型吃住院天数。塞进一个类，三类字段互相为 null，等于一个类承载三种领域模型。新增一种责任类型必须改主类，是最贵的维护成本。

### 6.3 控额

```
limitControl(ctx):
  1. 取责任配置的 quota_controller（个账 / 公账 / 直付 / 不限）
  2. 按来源查可用额度：个账 = 初始值 − 历史理算汇总；公账 / 直付走外部
  3. 截断：应赔额 = min(算得金额, 可用额度)
  4. 返回截断后金额，由上层落明细
```

**额度读时计算，不做 UPDATE 扣减**。与现有「账户是投影、流水是事实」同一口径。

### 6.4 保留 synap-claim 更严的部分

`Money` 精度封装、`InvariantGuard` 不变量守卫、`AmountRange` 分段。基线这三处是短板（裸 `BigDecimal` 无统一舍入、无不变量校验），不要退回去。

## 7. 作业流程（最后做）

基线 `claim/flow` 36 类，三段式：

```
Stage（阶段：做什么）→ FlowFireService（怎么驱动）→ Trigger（什么条件落到这个阶段）
```

五阶段可**开关**、可**自动或人工**、可**跳过**：

| 条件类 | 用途 |
|---|---|
| `AutoInputCondition` | 录入能否自动完成（OCR 置信度达标） |
| `AutoPrecheckCondition` | 初审能否自动通过 |
| `AutoApproveCondition` | 审核能否自动通过（自动结案阈值） |
| `ChannelOnlineCondition` / `ChannelOfflineCondition` | 按渠道分流 |
| `ScriptCondition` | 业务可配判断表达式，不写代码 |

`ScriptCondition` 是基线最有价值的设计——把"什么情况走哪条路"从代码搬到配置。但基线**没有沙箱、没有超时**，业务脚本等于任意代码执行，这一处必须补（§10）。

**现状**：流程逻辑散在应用服务与 `AdjustNodeHandler` 里，只做到"能开不能配"。**放最后做的理由**：配置与引擎不稳时，编排只是把不确定性放大。

## 8. 关键链路

### 8.1 正常快赔（自动通过）

```
报案 → 受理（ClaimCase）→ OCR 解析（DocumentParsePort）
  → 组装 Request（读 Policy/Plan/Coverage/Liability 快照 + 历史累计 + 目录准入）
  → calculate(Request) → Outcome（责任级明细 + 归因）
  → 决策校验（DecisionExecution：金额阈值 / 风控命中 / 置信度）
  → 冻额（Quota @Version 乐观锁）→ 落库 + Outbox 事件
  → 支付（两段式）→ 结算 → 对账
```

**关键约束**：决策在理算之后、冻额之前。顺序反了会出现"钱已占、决策又要求退"，退不退都错。

### 8.2 转人工（任一阈值命中）

```
OCR 置信度 < 0.7  ┐
AI 置信度  < 0.85 ├→ 转人工（两个阈值独立判定，不取最小、不串联）
风控命中          ┘
```

**转人工不抛异常**：抛异常会让案件停在中间态，实测出现过"16 次执行 0 个离开状态 13"。越界转人工必须是**受控原因码 + 正常返回**。

### 8.3 配置生效链路

```
配置页保存 → 写入期 JSON Schema 校验 → 落库（新 version）
  → 赔案立案时绑定版本 → 重算用绑定版本，不用最新版本
```

**最后一句是最常被写错的地方**：用最新版本重算会导致"昨天赔 100，今天同一张单赔 80"，而客户手里拿的是昨天的钱。

### 9.1.1 M2 详细迁移方案（高风险步，按 ADR expand/contract）

> **为什么单列一节**：M2 在 §9.1 被标为「高」，却此前只有一行描述。它要动的是**金额相关的存量列**（`t_adj_liability.pay_percent` / `liability_deduct` / `liability_limit`），任何一个值在迁移中变形，都会让历史案件的赔付额算错且**不会报错**——金额引擎出错的典型表现是静默算错。方案依据《ADR-生产数据库增量迁移策略》（已接受 2026-06-19）的 expand → migrate → switch → contract 四阶段。

**迁移前的范围（实测，不是估计）**：活库 `t_adj_liability` 31 列全标量。M2 = **新增 6 列**（`quota_controller` / `restrict_scope` / `restrict_object` / `restrict_out_insure` / `times_limit` / `adjustment_rule`）+ **3 列标量→JSON**（`pay_percent` / `liability_deduct` / `liability_limit`）+ 写入期 JSON Schema。另 14 张有业务列差异的表**不在 M2 范围**（§9.0（4）已登记，单独排期）。

> **本节的脚本编号 `0123`–`0126` 是规划占位，文件尚未创建、manifest 尚未登记、代码一行未改。** 写出来的目的是把「高风险」拆成可评审的四阶段与可判定的验收，避免开工时才发现命名冲突。**M2 尚未开工**，本文不是实施记录。

**一条命名冲突必须先解决**：§5.2 给目标 JSON 列用了与现存标量列**完全相同的名字**。同名不同类型无法在同一张表里双写共存，expand 阶段会立刻失败。因此实施时这 3 个 JSON 列落名为 **`pay_percent_rule` / `liability_deduct_rule` / `liability_limit_rule`**（`*_rule` 后缀），§5.2 的逻辑列名只作语义指代；旧标量列在 contract 阶段才处理。**不做 `CHANGE COLUMN` 就地改类型，也不做事后 rename**——两者都会让回滚窗口内新旧代码无法共存。

| 阶段 | 动作 | 交付物 | 验收判据 | 回滚 |
|---|---|---|---|---|
| **① Expand** | 新增 9 个 `JSON NULL` 列（6 个新维度 + 3 个 `*_rule` 影子列），全部 `nullable` 且不设默认值语义；旧标量列**原样保留、继续服务线上读** | `scripts/migration/0123_synap_claim_liability_expand.sql` + `migration-manifest.json` 登记 + `bone-init.sql` 同批 | 线上读写**零行为变更**；`information_schema` 强断言 9 列存在且为 JSON/可空；旧代码全量回归通过 | 只需 DROP 新增列，无数据损失 |
| **② Migrate** | 后台任务把 3 个标量值按固定 schema 包装成 JSON 回填影子列；**历史行不编造**——无值/不可考的行保持 `NULL`；6 个新维度列全为 `NULL`（业务未配，不做默认填充） | `0124_…_backfill.sql` + 回填核对报告 | 抽样 + 全量 `COUNT` 对账：每个非 NULL 影子列反序列化后必须还原出**同一数值**；脏数据先探测打印清单，**多条/异常一律 SIGNAL 中止，不自动删** | 影子列可整列清空重跑 |
| **③ Switch** | 应用侧切读：实体 `@Column`、读侧 SQL 模板、写入期 JSON Schema、配置编辑端点（M3）同批落码；**双写**旧标量与新 JSON 一个完整发版周期；历史案件重算仍按**绑定版本**读旧列 | 应用代码 + 4 个 SQL 模板 | 双轨比对：同一批案件走「旧列」与「新列」两条路径，赔付额逐笔相等；非法 JSON 写入被拒且字段级报错；`LlmOutputGuard`/`InvariantGuard` 判据不退化 | 切回旧列读，影子列仍在 |
| **④ Contract** | 确认至少一个完整发版周期内**无任何读点**引用旧标量列后，删除 3 个旧列；`bone-init.sql` 同步收敛到终态 | `0126_…_contract.sql` + manifest 登记 | 全仓 `grep` 读点为零（不能只看声明处）；终态断言旧列不存在、9 个 JSON 列齐备 | **不可回滚**（删列不可逆），故必须等 ③ 的观察期 |

**五条硬约束（都来自本仓已踩过的坑，不是通用建议）**：

1. **已发迁移不可回改**（含注释）：`migrate.py` 按 sha256 记 journal，改已应用脚本会让所有环境报校验和不符。修正一律**写新迁移**；序号从 `0123` 起（`scripts/migration/` 当前最大 `0122`，`migration-manifest.json` 的 `executableCount=122`）。
2. **每个脚本末尾必须有 `information_schema` 强断言 + `SIGNAL`**：沿用 `0121` 的临时 `PROCEDURE sp_verify_XXXX` 范式，`MESSAGE_TEXT` ≤128 字符（超长报 ERROR 1648），过程体用完即 `DROP`。「跑过」不等于「做到」。
3. **清单、脚本、全量基线同批入库**：`migration-manifest.json` 的 `entries` 是唯一真源（M1 存在即登记 / M2 登记即存在 / order 连续且与文件名词典序一致）；`bone-init.sql` 同批补列，否则「新装 vs 升级」结构分叉。
4. **建得进还要读得出**：SDK 的 SQL 模板列由实体元数据生成，新增列必须同批交 `sql/.../<Repo>/<method>.sql`；模板首行必须是语句关键字（SDK 不剥注释，塞注释会 500）。漏列会导致整实体 `save` 把值抹成空串——**静默数据丢失**。
5. **金额写用 `REQUIRED` 事务，禁 `REQUIRES_NEW`**；双轨比对必须同时覆盖 M2 切读前后与 M4 拆分前后；M2 与 M4 并行期间各自独立回滚，③ Switch 与 M4 策略切换不得同窗口发版（§9.1）。

**明确不做**：不就地 `MODIFY COLUMN` 改类型、不回填 6 个新维度默认值、不为历史行编造 JSON、不在同一脚本里同时做 expand 与 contract、不把 §9.5 的设计态 DDL 当执行脚本（§9.0（4））。

## 10. 与基线的差异（含不照搬）

| 维度 | 基线做法 | 问题 | 目标设计 |
|---|---|---|---|
| 契约注解 | SDK 接口带 `@RequestParam` | 契约被 Spring Web 污染 | 契约零框架依赖 |
| JSON 校验 | 9 个 JSON 列零 schema 校验 | 配置错误推迟到理赔时刻才暴露 | 写入期 JSON Schema 校验 |
| 脚本条件 | `ScriptCondition` 无沙箱说明 | 业务脚本可执行任意代码 | 白名单函数 + 超时 + 禁 IO |
| 金额精度 | 裸 `BigDecimal`，无统一舍入 | 分厘误差累积 | 保留 `Money` / `InvariantGuard` |
| 引擎接口 | `adjustClaim(claimId)` 揉进事务与持久化 | 无法脱离 DB 回放、批量验算 | 纯函数 `calculate(Request)`（现状已对，保持） |
| 配置主数据端点 | Policy/Plan/Coverage 有 CRUD 端点 | — | **三聚合根 + 应用层写方法已落地，缺的是 REST 端点（M3 补）** |
| 引擎分型 | 861 行 + 3 策略 | — | **必须照做**（现状 2,334 行单类） |

前五条是**基线自身的短板**，业务形态照它做，工程约束按更高标准；后两条是**基线的正确做法**，要补齐并守住。

## 11. 风险与回退

| # | 风险 | 触发信号 | 缓解 | 回退动作 |
|---|---|---|---|---|
| R1 | M2 新增 JSON 列时 `@Column` 与活库不一致，读数缺失后在整实体 `save` 时被抹成空串 | 配置页显示空值、金额变 0、无报错 | 实体列**必须先对齐活库 `information_schema`**，不凭印象写；仓储方法与 `sql/` 模板同批交 | 保留旧投影读取路径，按开关切回；**不回改已发迁移**，修正写新迁移 |
| R2 | M4 拆三策略后金额与现行实现不一致 | 双轨比对出现任一差异 | 双轨比对 + 变异体检测作为上线闸门，**不是"测试通过"就算过** | 策略工厂开关切回单类实现（旧类保留不删，只标 `@Deprecated`） |
| R3 | M3 开启 JSON Schema 校验后，存量不合规配置无法保存 | 配置页保存大面积报字段级错误 | 上线前先跑存量探测，产出不合规清单，人工确认后再开闸 | 校验降为 `warn` 模式（记录不拦截），数据修完再转 `reject` |
| R4 | 并行失控：SDK 契约未冻结就同时动 M2/M4，或 M2 切读与 M4 策略切换同窗口发版 | 两条线各自改 `Request` 字段；单窗口内出现两个金额变更来源 | 见 §9.1「依赖与并行纪律」：M1 冻结契约为硬前置；两线独立发版、独立回滚 | 停止较晚的一条线，回滚到 M1 冻结态；恢复后再按串行窗口重放 |
| R5 | 模块详细方案越写越散，回到"同一主题换角度重写" | 同一结论在两份文档里出现且措辞不同 | 每份模块方案先声明 authority（它拥有哪些主题），与 manifest 的 `authority` 字段逐字一致 | 合并或归档到 `09-records`，不保留第二份 |

**R1 是唯一会造成静默数据损失的风险**：它不是报错，是"读不出来 → 存回去的时候写成空"。所以缓解动作放在写入前（对齐活库），而不是事后校验。
