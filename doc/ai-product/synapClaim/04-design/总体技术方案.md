## 0. 决策摘要

**一句话**：`ClaimPolicy`/`ClaimPlan`/`ClaimCoverage` 三聚合根的**数据层已经落地**（"有表无实体"是错的），但映射层仍是 `role=draft`（见 `04-design/多保司保单配置面与主数据映射设计`）；卡住"配置驱动"的是另外两处——责任要素固定列（M2）、引擎不按类型**分派策略**（M4）；责任形式的**读取链路**已于 2026-11-08 修通（非报销型不再静默按比例算钱，见缺口 3）。M3 的配置主数据端点与 M5 第一阶段的流程配置消费方均已落地（2026-11-08，见 §9.1）。

## 1. 目标、约束与非目标

### 1.1 业务目标（一期）

| # | 目标 | 可验收的口径 |
|---|---|---|
| G1 | 门诊小额医疗**自动理算**，人工只处理异常 | 自动通过率、转人工原因可归因 |
| G2 | 赔付金额**可复算、可解释** | 同一输入任意时刻重算结果一致；每笔金额能回溯到「哪条规则 + 哪个因子值」 |
| G3 | 配置**由业务自己改**，不碰数据库迁移 | ① 改现有要素**取值**（比例 / 限额）：不需要 DDL、不需要改代码（标量列已支持）；② 新增要素**类型**：不需要 DDL（JSON 列可容纳），但须改代码（JSON Schema 校验器 + 引擎读取 + 前端表单）。M2 的真正价值是「配置结构可演进、免数据库迁移」，而非「业务免发版」——后者超出所选架构能力（已排除规则引擎，见 §1.3）。**可证伪判据（防假绿）**：在不执行任何 DDL/迁移的前提下新增一类责任要素并让其参与赔付——若必须 `ALTER TABLE` 才能落地，则 ② 不成立；当前架构下只需扩展 JSON 结构 + 代码消费方（Schema 校验器 + 引擎读取 + 前端表单）+ 一次应用发版即可生效，印证「免 DDL 不免代码」。 |

### 1.2 硬约束（只列判断架构走向必读的三条）

| 约束 | 来源 | 落点 |
|---|---|---|
| **AI 不碰钱** | synapClaim P1 | AI 节点只产 `AiSuggestion`（建议 + 置信度 + 证据引用）；金额计算与资金流转全在确定性代码 |
| **拒赔必须人工确认** | Rulebook R-MAN-03 | `SUGGEST_REJECT` 为待确认态，核赔员提交后生效；拒赔必填五要素 |
| **领域零框架依赖** | AGENTS.md §1 | `adapter → application → domain ← infrastructure`；domain 不引 Spring |

**完整 11 条**（另含持久化唯一入口、租户以认证主体为准、禁悲观锁、双阈值熔断、统一响应、入站边界、可回放审计、幂等）**见《工程详细设计（落地版）》§2（硬约束映射）**——那张表是唯一真源，本节不复制其余八条：两处各维护一份，改一处不会通知另一处。

### 1.3 非目标（一期明确不做）

| 不做 | 理由 |
|---|---|
| 住院 / 意外 / 重疾险 | 一期只做企业补充医疗·门诊·小额；住院的理算结构（按天、按次、分段）与门诊不同源 |
| 多租户 SaaS 化 | 单租户日案件 ≤5000；租户隔离已按字段实现，但计费 / 配额 / 自助开户不在本期 |
| 低代码规则可视化编辑器 | 规则配置先做表单；任意画布是独立产品 |
| 医疗目录全量 | 只接医学目录子集，且目录是**外部主数据**，本库不存副本（存了就成第二真源） |
| 独立微服务部署 | 理算必须与案件、责任、结算、额度在**同一事务边界**内；拆进程引入分布式事务 |
| 把理算塞进规则引擎（C2） | 理算 95% 是确定性金额算术；DSL 表达算术不可控且破坏快照可复算 |

## 2. 系统上下文（C4 L1）

系统不是孤岛：**上游有保司与存量 TPA，下游有支付与中台**。边界不清会导致"同一个事实两处维护"。

| 外部系统 | 与本系统的关系 | 交互方式 | 本系统承担 |
|---|---|---|---|
| `bone-shell` 微前端壳 | 宿主 | qiankun 挂载 | 子应用可独立调试，但验证须走 shell（脱离壳不渲染） |
| `bone-claim-app` | 理赔工作台 | HTTP `/api/v1/claim-ops/*` | 提供 35 个 Controller 的对外契约 |
| `bone-ai` 中台 | 规则求值（C2）/ 知识检索 / AI 网关 | `RuleEnginePort` / `KnowledgeRetrievalPort` / `AiGatewayPort` | **只做决策，不碰钱**；AI 输出必须带证据引用 |
| 保司 / 存量 TPA | 上游保单与案件来源 | `PolicyQueryPort` + 推送回传 | 保单配置**外部同步**（§0 缺口 1 的由来） |
| 支付通道 | 资金出账 | 两段式预占到实付 | 金额取理算产出的确定性结果，支付端不重算 |
| 医院 / 医保 / 目录 | 主数据 | `ItemCatalogPort` | 目录不落库；端口未接线即全部 `UNKNOWN`，退补件而非安静全额赔 |
| `bone-iam` | 认证与租户 | JWT | 租户身份取认证主体，不取请求头 |
| `bone-metadata` | 元数据与持久化 | SDK | 唯一持久化入口 |

**读图要点**：所有外部依赖都经 **Port** 出站（20 个 Port 经 `infrastructure/` 各适配器实现；`OutboxPort` 在 `domain/port/out`、M5a 适配器落 `infrastructure/config`，**非严格一一对应**），domain 不直接感知任何外部系统。

## 3. 总体架构（C4 L2）

```
┌────────────────────────── 表现层 ──────────────────────────┐
│ bone-shell（壳）  └─ bone-claim-app（理赔工作台）            │
│              配置面 / 案件面 / 稽核面 / 治理面                │
└──────────────────────────┬─────────────────────────────────┘
                           │ HTTP /api/v1/**（35 Controller）
┌──────────────────────────▼─────────────────────────────────┐
│ bone-apps/synap-claim/  父聚合（packaging=pom，目标态）      │
│  └─ synap-claim-app/    业务（现状 = 整个 synap-claim 模块）  │
│      adapter/       rest（35）· schedule · web               │
│      application/   36 个 ApplicationService                │
│      domain/        现状 20 子域平铺 → 目标态 7 上下文目录    │
│      infrastructure/ 19 个子包 ──→ 20 个 Port 出站           │
└──────┬──────────────────────────────────────┬──────────────┘
       │ 纯函数调用（同进程，无 RPC）           │ Port
┌──────▼─────────────────────────────┐  ┌──────▼──────────────────┐
│ adjustment-engine                 │  │ bone-ai / 支付 / 保司 / 目录│
│ （目标态）calculate(Request)→Outcome │  │ 全部经 Port 防腐           │
└────────────────────────────────────┘  └─────────────────────────┘
```

**三条架构判据**（每条都对应一次真实踩坑）：

1. **编排在应用层，算术在引擎**。把"读配置→算→冻额→落库"揉进引擎，引擎就依赖事务与持久化，无法脱离 DB 回放与批量验算。
2. **domain 零框架依赖**。否则单测要起 Spring 上下文，理算场景从毫秒级变成秒级，回归跑不动。
3. **出站一律经 Port**。domain 里出现任何 `Feign`/`RestTemplate` 都是越界。

**两条结构性结论**：

1. **配置与计算必须物理分离**。参考基线里 `adjustment` 域 12 类只做配置增删改查，算法在独立 module——"业务能自己配"和"算法不因配置改动而改"是两件事，混在一起后每次加要素都要动算法类。
2. **`mapping` 26 类是最大子域**，超过 `claim` 16 类。这说明**多保司映射是真实复杂度**，不是附属功能；它承担的是"同一概念在 N 家保司的不同叫法与不同结构"的翻译层。

**G3 门禁前置（多保司配置驱动）**：`mapping` 是承载「多保司配置由业务自配」愿景的最大复杂度层，却仍是 `role=draft` 且有 5 个硬缺口（见 `多保司保单配置面与主数据映射设计`）。在它转正前，G3 的"多保司配置自配"子目标无法成立，故 mapping 转正须与 M2 **并行排期**，并设**明确 owner**——无 owner 的映射表约 3 个月内退化为垃圾场（见该文档 §11.2）。把它当"顺手做"的附属项，是 G3 落地最大的隐藏风险。

**归属判据与收敛规范（D4 已决，物理子域归属的唯一真源）**：

1. **按聚合根与不变量归属，不按类名或 URI**。`domain/model/quota/` 实测 6 类全是资金运行时状态——`QuotaAccount`（`initial − claimed − frozen` 守恒）、`QuotaTransaction`（append-only 占用流水）、`QuotaChangeLog`（保全/调额）、`QuotaProjection` / `QuotaLedgerChain`（余额投影与串链校验）、`QuotaCap`（纯计算原语），**零个配置定义**；`config/` 域对 quota 零引用，`reconciliation/` 13 处类型/常量引用、`SettlementApplicationService` 10 处占额/释放调用。额度的**规则定义**实际落在 `liability` 的 `liability_limit` / `pay_percent` 与 `policy`。故 `quota` 归 **Funds**，Config 行的重复登记撤销（55 → 51 类、9 → 8 服务；Funds 保持 18 类、3 → 4 服务）。
2. **命名与归属不一致要显式登记，不改代码**。`QuotaConfigController` / `QuotaConfigApplicationService` 做的是额度账户**开户与调额**（写 `t_quota_account`），按用例归 Funds；名称里的 `Config` 是历史命名，列为后续重命名候选。**代码现状是事实真源**，本节只定文档归属，不暗示包路径已迁移。
3. **一名多义登记**：PRD §9.1 的 A5 `PersonalQuota` 是**业务能力**命名，《工程详细设计-落地版》§3.6 的 8 上下文是**需求侧切法**，《理算引擎设计》里的 `Quota` 是**纯计算值对象**。三者视角不同、不冲突；物理子域 `domain/model/quota/` 的归属以本节为准。
4. **包结构**：`com.bone.claim.domain.model.<context>/<subdomain>/`，7 个上下文目录为一级，原子域名保留不改（一次只动目录层级，避免同时改包名与类名）；跨上下文**禁直接 import 领域模型**，经 application 编排 / 领域事件 / Port；`common/`（错误码、`Money`、常量）为共享内核，不归任一上下文。
5. **收敛纪律（逐上下文迁移，禁止一次性全改 import）**：一次一个上下文、一个 PR，按风险从低到高 `Analytics → Adjustment → Funds → Decision → Config → Claim`；每批验收 = `mvn clean test` + ArchUnit + 全仓 grep 旧包路径为 0 + 零行为变更；迁移期间不新增跨上下文直接引用。收敛是**目标态**，当前 `domain/model/` 仍是 20 子域平铺。**时序约束**：D4 纯属组织性重构、零行为收益却有回归风险，须**避开 M2 / M4 资金主链路与 M5a/M5b 流程层改造窗口**单独排期——不在同一发版周期内既搬包又改资金逻辑，两类 cutover 错峰，避免"同一链路双变更"放大风险（§9.1 纪律 4/5 已对 M2∥M4 设隔离，D4 同样适用）。**启动触发条件（写死，避免"已决未启动"无限悬空）**：满足下列任一条才启动 D4，否则保持「已决、未启动」，不计入任何里程碑 —— ① `domain/model/` 子域数 > 25；② 单个 PR 被迫跨 ≥3 个子域改同一个不变量；③ 新人定位一个聚合根所属上下文需 >1 天。三条都不满足时做 D4 是纯成本，没有收益。

### 4.1 组件视图（C4 L3 / arc42 §5 构建块视图）

> **为什么在本文件里，而不是新建 3 份文档**：C4 的 L1/L2/L3 本来就是同一套图的不同放大倍率，arc42 也把「系统上下文 / 构建块视图」放在同一份架构文档里。此前 §9.2 把「案件 / 决策 / AI 治理」标为"未写"，实测后发现内容分别已在 `工程详细设计-落地版 §4/§6/§7`、`AI技术方案 §6/§11`——缺的是**一份统一的组件级契约**，不是三份内容。按治理规约 §三之一「新结论优先回写」，这里补的是视图与索引，明细仍指向原真源，**文档数保持 63**。

**统一组件规约**（7 个上下文都适用，违反即为架构缺陷）：

1. **编排在应用层**：`*ApplicationService` 负责事务与跨聚合编排；`domain/` 不引 Spring、不碰 DB。
2. **出站一律经 `*Port`**：20 个 Port ↔ `infrastructure/` 子包一一对应；domain/application 禁 import 平台实现（ArchUnit 强制）。
3. **错误码必须有归处**：`ClaimErrorCodes` + `ClaimErrors.DEFAULT_HTTP_STATUS` + 前端两语言包三处齐备，否则新增码会在类加载期抛异常。
4. **写操作幂等**：创建类端点带 `Idempotency-Key`，键冲突返回 409 且回吐首次响应。
5. **金额只在确定性代码里算**：AI 节点只产建议 + 置信度 + 证据引用，不产结算赔付额。

### 5.1 四级结构

```
Policy 保单      policy_no · config_status · status · effdate / expdate · adjustment_order · certificate_config
 └ Plan 计划     plan_limit · version · status
    └ Coverage 险种   coverage_limit · version
       └ Liability 责任   liability_code · liability_type · payment_basis + 9 个可配置要素（§5.2）
          └ LiabilitySharing 共保 → SharingRelation
```

**`version` 贯穿 Plan / Coverage / Liability**：一次配置变更 = 一个新版本（**每个版本是不可变快照：变更 = 新建行 + 新版本号，不就地 UPDATE 当前行**）；赔案绑定立案时的版本重算。可复算不靠代码里的常量，靠数据版本。⚠️ 此粒度是 M2 迁移的硬前提——**回落判定必须按"版本行"而非"当前行"**：历史行 `*_rule` 为 NULL ⇒ 永远走旧列；新行有 JSON ⇒ 走新列。若按"当前行"判断，历史案件会被新列的形态影响，④ Retire 后历史重算即失真（见 §9.1.1 ③）。**此模型已落地（非新增假设）**：实测 `LiabilityConfigApplicationService` 在配置变更时生成同 `liability_uuid` 的新行 + `nextVersion()`（"已生效版本不可改：生成同 UUID 的新版本草稿（新行）"），`t_adj_liability` 按 `(liability_uuid, liability_version)` 多行存储；`Adjustment.formula_snapshot` + `liability_version` 钉死历史复算版本。故 M2 的"逐版本复算"前提成立，双轨比对可直接枚举历史版本行；**但"逐版本回填"不再需要**——回落逻辑让历史行无需回填即可复算（§9.1.1 修正）。

### 5.2 Liability 的 9 个要素（JSON 列）

> **命名约定（实施期必读）**：下表的列名是**语义指代**。其中 `pay_percent` / `liability_deduct` / `liability_limit` 与活库现存的标量列同名，expand/contract 下同名不同类型无法双写共存，故 M2 实施时这 3 个 JSON 列的实际落名为 **`pay_percent_rule` / `liability_deduct_rule` / `liability_limit_rule`**（`*_rule` 后缀），旧标量列在 contract 阶段才删。详见 §9.1.1 ①。

| 目标列（JSON） | 含义 | 活库现状 `t_adj_liability`（实测） |
|---|---|---|
| `pay_percent` | 赔付比例（可分段、按金额区间、按赔案累计） | **同名但标量** `DECIMAL(6,2)`，只能表达单一比例 |
| `liability_deduct` | 免赔（年 / 次 / 日 × 金额或比例） | **同名但标量** `DECIMAL(12,2)`；另有 `invoice_deduct` / `adjust_deduct` 两个标量免赔 |
| `liability_limit` | 责任额度（单次 / 年累计 / 终身） | **同名但标量** `DECIMAL(12,2)`；另有 `daily_limit` |
| `quota_controller` | 控款方（个账 / 公账 / 直付 / 不限） | **活库无此列**；§9.5 设计态写了 `VARCHAR` |
| `restrict_scope` | 适用限定（医院等级 / 地区 / 网络） | **活库无此列**；部分语义由 `limit_hospital_codes` / `limit_mode` 分散承载 |
| `restrict_object` | 适用对象（本人 / 配偶 / 子女，年龄性别） | **活库无此列** |
| `restrict_out_insure` | 适用出险（疾病 / 意外，含除外） | **活库无此列** |
| `times_limit` | 次数限额（日 / 年 / 终身次数） | **活库无此列**；§9.5 设计态写了 `JSON` |
| `adjustment_rule` | 理算明细（费用项映射 / 目录 / 共保分摊） | **活库无此列**；§9.5 设计态叫 `adjustment_detail VARCHAR` |

另加 `formula` VARCHAR(512)：只读展示用公式文本，不参与计算——**活库同样没有 `formula` 列**。

**九要素的落地差距**：3 个有同名标量列（`pay_percent` / `liability_deduct` / `liability_limit`），**6 个在活库完全不存在**。因此 M2 不是"把 9 个 VARCHAR 改成 JSON"，而是"**6 列要新建 + 3 列要做标量→JSON 的类型迁移与存量数据回填**"，工作量与风险都比原描述大。

**为什么 JSON 而不是 9 张子表**：要素会持续增加（基线从 6 个长到 9 个）。每加一个要素都做 DDL，等于把"业务自己能配"变成"每次都要发版"——而 JSON 列只免去 **DDL/迁移**，新增要素的**业务语义仍要代码消费**（扩展 JSON Schema 校验器 + 引擎读取该字段 + 前端表单），所以"免发版"只成立在"改现有要素取值"上，不成立在"新增要素类型"上（见 G3 口径）。代价是丢掉数据库层校验，所以必须补**写入期 JSON Schema 校验**（§10 第 2 行）。

**九列 vs 一列（M2 开工前须拍板，§13 · O-04）**：本表把"一个业务维度 = 一个 JSON 列"，好处是按维度独立演进、独立校验；代价是**下次加维度仍要 `ALTER TABLE`**——而这正是选 JSON 想避免的事，等于把 DDL 依赖从"改值"推迟到"加维度"，「新增要素类型免发版」并未真正成立。更彻底的形态是 **1 个聚合列 `liability_rule_json` + JSON Schema（跨字段约束一次表达）+ 少量提升为列的检索字段**：加维度只改 Schema 与消费方，不动 DDL，总列数从 9 降到 4。本表暂保留九列，因为 3 个 `*_rule` 已按列名进了 M2 方案、改动面最小；**取舍登记为开放项，不在此处单方面改设计**（改设计须同批改 M2 脚本、实体与双轨判据）。

| # | 业务维度（V1 §2） | 目标态列（§5.2） | 活库 `t_adj_liability` 实际承载 | 判定 |

### 5.3 `liability_type` 是配置驱动的枢轴

| 类型 | 算法骨架 |
|---|---|
| `REIMBURSEMENT` 报销型 | `min(发票可赔额, 责任额度) × 比例 − 免赔`，再受控额约束 |
| `FIXED_AMOUNT` 定额型 | 固定金额 × 次数（手术定额、床位日额） |
| `ALLOWANCE` 津贴型 | 日津贴 × 天数，受起付期与最长天数约束 |

配置面选类型，引擎按类型选策略——这是"配置驱动算法"的唯一枢轴。

**当前落地状态（2026-11-08）**：①「类型 → 责任形式」已接通——`LiabilityRule.fromLegacy(...)` 接收 `liability_type` 并装配真实 `LiabilityForm`，非报销型在 `validate()` 期以 `LIABILITY_FORM_UNSUPPORTED` 拒绝并转人工（此前硬编码成报销型，拒绝分支不可达）；②「类型 → 策略」待 M4，期间**非报销型责任 100% 转人工**，配置页应在选定定额/津贴时给出该提示（O-03）。配置面**仍允许建档**非报销型（业务要能落保单），拒绝只发生在自动理算——两层不能合并，否则业务无法录入未上线类型的保单。

## 6. 理算引擎（纯算术）

### 6.1 接口是纯函数（现有形态是对的，迁移时别改坏）

```java
// adjustment-engine（目标态）  com.bone.claim.adjustment.engine.AdjustmentEngine
public record Request(...)     // 配置快照 + 费用项 + 历史累计 + 目录准入
public record Outcome(...)     // 责任级明细 + 零赔付归因 + 不变量自证
public static Outcome calculate(Request request);
```

**这是 `synap-claim-app` 已经做对、而基线没做到的地方**：基线 `adjustClaim(claimId)` 把「读配置→算→冻额→落库」揉进一个方法，引擎因此依赖事务与持久化，**无法脱离数据库回放与批量验算**。

| 层 | 职责 |
|---|---|
| `adjustment-engine` | `calculate(Request) → Outcome`，纯函数，可并行、可回放、可单测 |
| `synap-claim-app` 应用服务 | 读配置快照组装 `Request` → 调 `calculate` → 冻额 → 落库 → 发事件 |

**引擎已接线**：`AdjustmentController` → `IndemnityApplicationService` → `Adjustment.apply()` → `AdjustmentEngine.calculate`，M2 / M4 是对这条既有链路的结构改造，不是「接线」。`Adjustment.apply()` 里的 `LiabilityRule.fromLegacy(...)` 已把旧标量金额列适配成引擎入参，是 M2（数据形态）与 M4（算法结构）能并行的防腐层依据（§9.1）。

**迁移只搬不改**：包名改到 engine 模块，签名不动。若为"对齐基线"把 `claimId` 塞进引擎，等于把已解耦的边界重新耦合回去。

### 6.2 按 `liability_type` 分策略

```
LiabilityAdjustmentStrategy
├── checkAdjustable(ctx)           // 该责任是否可赔（限制条件）
├── adjustmentInvoice(ctx)         // 算一条责任 → 明细
├── buildAdjustFormula(liability)  // 生成展示公式（仅展示，不参与计算）
└── getSupportedType()             // 声明支持的类型

实现（分期）：**先只交 Reimbursement**；FixedAmount / Allowance 待规则书补齐
分派：LiabilityAdjustmentStrategyFactory，注入 List → Map<LiabilityTypeEnum, Strategy>
      查不到 → 抛异常（fail-closed，不返回 0 元）
```

**为什么按类型分策略**：三类算法**输入结构不同**——报销型吃发票明细，定额型吃次数与项目，津贴型吃住院天数。塞进一个类，三类字段互相为 null，等于一个类承载三种领域模型。新增一种责任类型必须改主类，是最贵的维护成本。

**但"接口现在拆"不等于"三支现在实现"（2026-11-08 修正）**：其中两支**没有可写的算法**——V1 §2 明文标定额/津贴"整章空白"（`LiabilityRule` 的 `LIABILITY_FORM_UNSUPPORTED` 就是为此设的），且次数 `times_limit` 与住院天数在活库无列、无输入，双轨比对也没有 oracle。为它们造空策略，只会得到"看起来完整、实则无法与保司对账"的实现。故：**接口与工厂照上图落，实现先只交 `Reimbursement` 一支，未知类型由工厂 fail-closed 拒绝并转人工**。接口分层的收益（新增类型不必改主类）与"现在就实现三支"无关——`2,334` 行单类的主要成本是**改动面**，不是**策略数量**。

### 6.3 控额

```
limitControl(ctx):
  1. 取责任配置的 quota_controller（个账 / 公账 / 直付 / 不限）
  2. 按来源查可用额度：个账 = 初始值 − 历史理算汇总；公账 / 直付走外部
  3. 截断：应赔额 = min(算得金额, 可用额度)
  4. 返回截断后金额，由上层落明细
```

**额度读时计算，不做 UPDATE 扣减**。与现有「账户是投影、流水是事实」同一口径。

### 6.4 保留 synap-claim 更严的部分

`Money` 精度封装、`InvariantGuard` 不变量守卫、`AmountRange` 分段。基线这三处是短板（裸 `BigDecimal` 无统一舍入、无不变量校验），不要退回去。

## 7. 作业流程（最后做）

基线 `claim/flow` 36 类，三段式：

```
Stage（阶段：做什么）→ FlowFireService（怎么驱动）→ Trigger（什么条件落到这个阶段）
```

五阶段可**开关**、可**自动或人工**、可**跳过**：

| 条件类 | 用途 |
|---|---|
| `AutoInputCondition` | 录入能否自动完成（OCR 置信度达标） |
| `AutoPrecheckCondition` | 初审能否自动通过 |
| `AutoApproveCondition` | 审核能否自动通过（自动结案阈值） |
| `ChannelOnlineCondition` / `ChannelOfflineCondition` | 按渠道分流 |
| `ScriptCondition` | 业务可配判断表达式，不写代码 |

`ScriptCondition` 是基线最有价值的设计——把"什么情况走哪条路"从代码搬到配置。但基线**没有沙箱、没有超时**，业务脚本等于任意代码执行，这一处必须补（§10）。**沙箱不自造**：手写白名单 + 禁 IO 远不等于安全（反射、超时外的内存炸弹、死循环仍是攻击面），应直接采用受控嵌入式脚本运行时（GraalVM 受限 `Context` 带资源上限，或 Aviator / MVEL 等带 allowlist 的表达式引擎），把"禁 IO/超时/内存上限"交给成熟库而非自写解释器。

**现状**：流程逻辑散在应用服务与 `AdjustNodeHandler` 里，只做到"能开不能配"。**放最后做的理由**：配置与引擎不稳时，编排只是把不确定性放大。

## 8. 关键链路

### 8.1 正常快赔（自动通过）

```
报案 → 受理（ClaimCase）→ OCR 解析（DocumentParsePort）
  → 组装 Request（读 Policy/Plan/Coverage/Liability 快照 + 历史累计 + 目录准入）
  → calculate(Request) → Outcome（责任级明细 + 归因）
  → 决策校验（DecisionExecution：金额阈值 / 风控命中 / 置信度）
  → 冻额（Quota @Version 乐观锁）→ 落库 + Outbox 事件
  → 支付（两段式）→ 结算 → 对账
```

**关键约束**：决策在理算之后、冻额之前。顺序反了会出现"钱已占、决策又要求退"，退不退都错。

### 8.2 转人工（任一阈值命中）

```
OCR 置信度 < 0.7  ┐
AI 置信度  < 0.85 ├→ 转人工（两个阈值独立判定，不取最小、不串联）
风控命中          ┘
```

**转人工不抛异常**：抛异常会让案件停在中间态，实测出现过"16 次执行 0 个离开状态 13"。越界转人工必须是**受控原因码 + 正常返回**。

**阈值的真源（回读代码核验，2026-11-08）**：`0.7 / 0.85` 是 `DecisionTriage` 的**代码常量**（`AI_MANUAL_THRESHOLD` / `AI_REVIEW_THRESHOLD` / `OCR_MANUAL_THRESHOLD`）；`AiConfidenceCalibration` 只产出 `recommendedThreshold` **建议**，不写配置、不改门限。故上图不是"可配阈值"：改它 = 改代码 + 产品/架构签核（§4.1.6 的"落地须签核"指的就是这条路）。**不得把校准报告里的建议值当成已生效门限**——那正是本仓"配了不生效"的同族坑，只是方向相反（读到建议就以为生效）。

**金额阈值是另一档可配性**：`ClaimThresholds` 持代码基线（1 万元双审门），`TriageLimits` 在应用层套 `feature_toggle` 覆盖且**只收紧不放开**；域模型（结算 / 案件）无 Spring 上下文，直接用基线常量。两种阈值别混为一谈：一个"改代码才生效"，一个"可被开关收紧"。

### 8.3 配置生效链路

```
配置页保存 → 写入期 JSON Schema 校验 → 落库（新 version）
  → 赔案立案时绑定版本 → 重算用绑定版本，不用最新版本
```

**最后一句是最常被写错的地方**：用最新版本重算会导致"昨天赔 100，今天同一张单赔 80"，而客户手里拿的是昨天的钱。

### 9.1.1 M2 详细迁移方案（高风险步；expand/contract 仅在可映射子集适用）

> **为什么单列一节**：M2 在 §9.1 被标为「高」，却此前只有一行描述。它要动的是**金额相关的存量列**（`t_adj_liability.pay_percent` / `liability_deduct` / `liability_limit`），任何一个值在迁移中变形，都会让历史案件的赔付额算错且**不会报错**——金额引擎出错的典型表现是静默算错。
>
> **方案修正（2026-11-08）：expand/contract 只适用于「双向可映射」的子集，原方案的「存量回填 + 双向双写一个发版周期」在此不成立。** ADR《生产数据库增量迁移策略》的隐含前提是**新旧表示双向可映射**——它为"同语义换存储"（如 VARCHAR→JSON 的等价包装）设计。M2 是**表达力升级**：标量 → 可分段 / 按金额区间 / 按累计的 JSON，是**超集**关系。标量→JSON 可逆，`JSON 分段比例 → DECIMAL(6,2)` **不可逆**。于是原 ③ 阶段有一个无解的必答题：新配置是"0–1000 报 80%，1000 以上报 90%"时，旧 `pay_percent DECIMAL(6,2)` 写什么？**写 80 → 回滚后该责任静默少赔；写 NULL → 回滚即丢配置**。两条路都是静默算错，而静默算错正是本节要防的唯一事故类型。
>
> 因此把迁移切成**「可映射子集」与「超集解锁」两段**：②③ 只在可映射子集内双写（`scalar == project(json)` 恒成立，回滚安全），**超集表达（分段/区间/累计）的解锁点推到 ④**，那时旧代码必须已全量下线。代价是 M2 当期的表达力不等于 JSON 的全部表达力——这是诚实的边界，而不是把不可逆映射塞进回滚窗口。
>
> **另有两处修正**：① **取消批量存量回填**——读侧"JSON 空则回落旧列"让历史行天然可用，回填只是把旧值抄进新列，收益为零、风险却要逐行承担；② **历史行不编造 JSON** 从"纪律"升级为"结构保证"（历史行 `*_rule` 恒为 NULL，永远走旧列）。

**迁移前的范围（实测，不是估计）**：活库 `t_adj_liability` 31 列全标量。M2 = **新增 6 列**（`quota_controller` / `restrict_scope` / `restrict_object` / `restrict_out_insure` / `times_limit` / `adjustment_rule`）+ **3 列标量→JSON**（`pay_percent` / `liability_deduct` / `liability_limit`）+ 写入期 JSON Schema。另 14 张有业务列差异的表**不在 M2 范围**（§9.0（4）已登记，单独排期）。

> **本节的脚本编号 `0123`–`0126` 是规划占位，文件尚未创建、manifest 尚未登记、代码一行未改。** 写出来的目的是把「高风险」拆成可评审的四阶段与可判定的验收，避免开工时才发现命名冲突。**M2 尚未开工**，本文不是实施记录。

**一条命名冲突必须先解决**：§5.2 给目标 JSON 列用了与现存标量列**完全相同的名字**。同名不同类型无法在同一张表里双写共存，expand 阶段会立刻失败。因此实施时这 3 个 JSON 列落名为 **`pay_percent_rule` / `liability_deduct_rule` / `liability_limit_rule`**（`*_rule` 后缀），§5.2 的逻辑列名只作语义指代；旧标量列在 contract 阶段才处理。**不做 `CHANGE COLUMN` 就地改类型，也不做事后 rename**——两者都会让回滚窗口内新旧代码无法共存。

**五条硬约束（都来自本仓已踩过的坑，不是通用建议）**：

1. **已发迁移不可回改**（含注释）：`migrate.py` 按 sha256 记 journal，改已应用脚本会让所有环境报校验和不符。修正一律**写新迁移**；序号从 `0123` 起（`scripts/migration/` 当前最大 `0122`，`migration-manifest.json` 的 `executableCount=122`）。
2. **每个脚本末尾必须有 `information_schema` 强断言 + `SIGNAL`**：沿用 `0121` 的临时 `PROCEDURE sp_verify_XXXX` 范式，`MESSAGE_TEXT` ≤128 字符（超长报 ERROR 1648），过程体用完即 `DROP`。「跑过」不等于「做到」。
3. **清单、脚本、全量基线同批入库**：`migration-manifest.json` 的 `entries` 是唯一真源（M1 存在即登记 / M2 登记即存在 / order 连续且与文件名词典序一致）；`bone-init.sql` 同批补列，否则「新装 vs 升级」结构分叉。
4. **建得进还要读得出**：SDK 的 SQL 模板列由实体元数据生成，新增列必须同批交 `sql/.../<Repo>/<method>.sql`；模板首行必须是语句关键字（SDK 不剥注释，塞注释会 500）。漏列会导致整实体 `save` 把值抹成空串——**静默数据丢失**。
5. **金额写用 `REQUIRED` 事务，禁 `REQUIRES_NEW`**；双轨比对必须同时覆盖 M2 切读前后与 M4 拆分前后；M2 与 M4 并行期间各自独立回滚，③ Dual-read 与 M4 策略切换不得同窗口发版（§9.1）。

**明确不做**：不就地 `MODIFY COLUMN` 改类型、不回填 6 个新维度默认值、不为历史行编造 JSON、**不做全量存量回填**（读侧回落已覆盖历史行）、**不在 ② 期间启用标量无法表达的分段/区间/累计**（解锁点是 ④）、不在同一脚本里同时做 expand 与 contract、不把 §9.5 的设计态 DDL 当执行脚本（§9.0（4））。

**回滚粒度是「版本行」，不是「二进制」**：因为 §5.1 是版本不可变快照，正确回滚 = 把新版本行置 `INACTIVE`、前端回到上一版本，旧版本行原封不动仍可复算。仅当代码本身有缺陷才回滚二进制，此时新配置行同批作废。把"回滚二进制"当唯一手段，会逼出"标量列必须能表达一切"这个做不到的要求——这正是原方案卡住的地方。

### 13.1 里程碑二分（建议，替代"一条长链"）

原 §9.1 把 M1–M5b、D4、mapping 转正、14 张表差异放进同一张依赖图，没有回答"哪些不做也能上线"。按业务价值切成两条，**互不阻塞**：

| 里程碑 | 内容 | 判据（能验的） | 不含什么 |
|---|---|---|---|
| **A · 能赔对** | M2 ①（9 列只增）+ **6 个新维度列的引擎消费** + M3（已落）+ O-06 mapping 转正 + O-03 提示 | 已〔定〕维度可配可回放；历史案件逐笔不变（3 个旧标量列从未被改写） | 不含 3 个 `*_rule` 的 ②③④、M1 搬运、M4 分层、D4、M5b、O-02 |
| **B · 好维护** | M1、M4（接口 + 单策略）、M5b、M2 的 ②③④（可映射子集双写 → 读侧回落 → 解锁）、D4（按触发条件）、O-01/O-02 | ArchUnit / 模块边界 / 门禁真接线；`scalar == project(json)` 成立 | 不含任何**已上线**金额口径的变更（解锁前 JSON 与标量等价） |

**为什么把 3 个 `*_rule` 列从 A 里摘出来**：② 只允许可映射子集（JSON 必须能压回同一个 `DECIMAL`，即与旧值等价），③ 的读回落在该子集内与旧路径同源——**在 ④ 解锁之前，这两步不产生任何新的表达能力，却要动金额列**。把它们塞进 A，等于用"资金列变更的风险"换零业务价值；真正让"配置驱动"成立的是那 6 个新维度列加引擎消费。这也是把 B 叫作"好维护"而不是"后续功能"的原因：它买的是**可扩展性与门禁**，不是当期赔付能力。

**为什么这么切**：一期业务目标（G1 能赔对、G2 可回溯）只依赖 A；B 全是工程质量项，把它们与 A 绑在同一里程碑，会让"能不能赔对"被"代码好不好维护"拖住——而 B 里任一项延期都不会让客户赔错钱。反过来，A 里若混入 B 的重构，一次发版就同时改了资金逻辑与包结构，回归面相乘。
