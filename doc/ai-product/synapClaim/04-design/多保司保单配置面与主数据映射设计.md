## 0. 一页结论

参考站的能力不是"更好的表单"，而是**四样基础设施**：① 配置作用域显式化（保单→计划→险种→责任，选中即作用域）；② 标准值与保司值的**双轨 + 映射**；③ 配置的**发布/预览/留痕**；④ 变更的**管控**（谁能改、影响多少、怎么退）。

前 3 条初版已有，第 4 条为治理主线：**映射不是一张表，而是一条带闸门的流水线**。业界（MDM / 保险核心配置管理）的共识是，映射类项目失败很少因为缺功能，而是因为「没人负责、改完不知道影响谁、出错退不回」。

第二轮复核的重点不是再加能力，而是**修自洽性**：DDL 里写着"允许 1:N"而唯一键根本插不进第二条、用 NULL 表示"标准基线"导致基线可以重复、门禁把合法的 N:1 判成病、成本表分项相加对不上总数。这类错误不会让方案看起来更差，但会在实现阶段变成"随机命中某个标准码"和"金额对不上账"——最难查的那一类。

| # | 能力 | 优先级 | 落地形态 | 为什么（机制） |
|---|---|---|---|---|
| 1 | 保单规则配置单页承载"计划/险种/责任"三级树 + 选中责任驱动下方规则页签 | P1 | `/claim#/policy` → 「配置」进单页控制台 | Bone 现在三跳（/policy→/plan→/liability），配一条责任丢两次上下文；树选中即作用域，避免"先点菜单再补保单" |
| 2 | 责任规则分区（适用范围/发票金额项/承担费用类型/赔付规则/控额规则/理算信息） | P0 | 责任配置页重构为 6 分区 | 把「钱从哪来→赔哪些→怎么算→谁封顶」顺序化；现有扁平字段无法表达 `invoiceDeduct/adjustDeduct` 的先后语义 |
| 3 | 发票金额项「录入项 / 计算项 + 表达式」 | P1 | 费用池定义可配置，表达式物化进 `formula_snapshot` | 各家发票结构不同；用配置吸收差异，而不是为每家改代码 |
| 4 | 字段 → 选项集绑定（标准列 + 专属列，逐字段可覆盖） | P0 | 新增「字段绑定」，挂在 `/claim#/library` | 同一业务字段在多保司下码值/名称不同；绑定层让"规则写一遍、码值各认各的"成为可能 |
| 5 | 保司专属码表 + 标准码表双轨 | P0 | 保司码表 + 映射表 + 未命中队列 | 直接共享一套码表 ⇒ 每接一家保司都要复制全部规则；这是成本中枢 |
| 6 | 双保单号（保司号 / 平台号） | P0 | `insurer_policy_no` + `policy_no` | 保司退保重出、批改换号是常态；单号必然断链（详见 §2.3） |
| 7 | 主体专属配置「标准基线 + 差异覆盖 + 同步标准」 | P1 | 作业/单证开关上移到保司级默认，保单级覆盖 | 90/10 法则；Bone 现在两个单证开关挂在每张保单上，1000 张保单=2000 次重复配置 |
| 8 | 发布 / 预览 / 编辑记录 | P1 | 发布单 + 快照 diff + 预演 + 双时态 | 配置面改一次影响该保单所有未来赔案；没有版本只能靠备份回滚 |
| 9 | **变更管控（本轮新增）**：制单-复核分离、影响面分析、灰度与整体回滚 | P1 | `t_claim_config_release` + maker-checker + 体检门禁 | 参考站有"发布"但没有职责分离与影响面；金额相关配置单人可改是合规硬伤 |
| 10 | 个人专属额度作为保单规则子页 | P2 | `/quota` 能力以保单上下文复用 | 运营动线是"这张保单的额度"，不是"全局额度列表" |
| 11 | 复制责任 / 责任推送配置 / 理算演示 / 责任编辑记录 | P2 择要 | 复制 + 预演先做 | 批量配置效率与可解释性，但优先级低于正确性 |
| 12 | 三级树的行内编辑按钮群（一屏 10 个） | 改造 | 收敛为行内「配置」+ 更多 | 语义重复且按钮态与选中态耦合（未选中时点了没反应也无提示） |

一句话取舍：**映射闭环（含未命中与门禁）、双保单号、责任规则分区进 P0；单页控制台、字段绑定、发布与变更管控进 P1；额度/推送/演示进 P2；表单布局类细节一律不照搬。**

## 1. 取证：参考站实际是什么

### 1.1 四处页面

| 页面 | 路径 | 实测到的结构 |
|---|---|---|
| 保单规则配置 | `/policyConfig/policyRuleConfig?policyNo=…` | 顶部保单摘要（保司保单号/生效期间/状态/规则开关）+ 10 个操作按钮 + 三级树（计划层/险种层/责任层）；下方 9 个页签：责任规则、个人专属额度、医院库、疾病库、药品库、费用项目规则、职业列表、作业配置、快捷理算 |
| 主体专属配置 | `/jobConfig/bizIdentityConfig?code=1:YCBX&type=1` | 基本信息 + TPA 流程配置（签收/初审/录入/质检/审核/复核 + 跳过/进入 + 复核准入条件 + 脚本规则）+ 各环节作业规则 + 字段选项集 + 专属字段 + 编辑记录/预览/发布 |
| 系统选项配置 | `/systemManage/optionConfig` | 选项集列表（适用范围/名称/标识/描述）+ 详情抽屉（选项值标识/名称/启用状态 + 批量导入） |
| 保单列表 | `/policyConfig/groupPolicyList` | 列：保司保单号 / 普康保单号 / 保险公司 / 投保公司 / 生效日 / 失效日 / 操作（配置规则） |

### 1.2 四条关键实证

1. **选项值带映射载荷**。`EX_证件类型_永诚1` 的选项值是 `0=身份证`，其 `extraProperty` 为
   `{"主被保险人映射1":"a","领款人映射1":"a","出险人映射1":"a","主被保险人映射2":"a"}`。
   → 同一保司码在不同**业务字段/不同映射代际**下映射到不同目标码；映射是**按字段维度**的，不是全局一对一。
2. **码值空间确实不同源**。`PK_医院库`：`s_01=杭州第一人名医院`（3 条样例）；`EX_医院库_永诚总`：`5232068251008710=如皋市康慈医院`（3003 条保司自有机构码）。
   → 保司码无法与标准码共用一套值域，必须映射。
3. **绑定形态是"逐字段二选一"**。字段选项集页每行是 `系统业务字段 | 普康标准选项集 | 主体专属选项集 | 配置数据源`，未配置专属时专属列回落标准（如"受益人职业"两侧都是 `PK_职业类型`）。
4. **发布语义被明确写死**：「发布后请谨慎切换，切换后已处理赔案保留原选项值，适用于新签收赔案和作业中赔案」。
   → 配置切换不回改历史单据，只影响新进件；这是配置版本化必须有的边界声明。注意它**没有说明"在办赔案"怎么办**，这正是我们要显式回答的问题（§7.1）。

### 1.3 参考站自身的缺陷（不照搬的直接理由）

| 缺陷 | 证据 | 后果 |
|---|---|---|
| 搜索区与表格列不对齐 | 保单列表 6 列（含两个保单号），搜索区只有 5 个输入框，且第一个输入框占位是"请输入普康保单号" | 用户按保司保单号查不到，只能试 |
| 页签整体禁用且依赖条件不可见 | 未选中责任行时，医院库/疾病库/药品库/费用项目规则/职业列表 5 个页签 `is-disabled`；实测**点选表格行后仍为禁用**，元素无 `title`/`aria-label`，悬停无 tooltip | 用户无法得知"还缺哪个前置条件"，只能逐项试；功能实际可达但看起来不存在 |
| "专属"靠命名约定而非结构 | 50 个选项集的 `useScope` 全部为 `1`（通用）；专属与否只体现在 `EX_` 前缀 | 无法按保司检索/鉴权/统计；命名一破，语义即失真 |
| 有"发布"无"复核" | 页面提供编辑记录/预览/发布，未见制单与复核的职责分离 | 单人可改影响全部未来赔案的金额规则，出错无第二双眼睛 |

另有两处治理隐患：`extraProperty` 用中文键（`主被保险人映射1`）当契约、目标码是单字母（`a`/`d`/`ac`）不可读；同一类目录存在两份真源（`PK_医院库` 选项集 vs 医院库业务表）。

### 1.4 从参考站反推的三条设计原则

| 原则 | 来源 | 对 Bone 的约束 |
|---|---|---|
| 配置必须携带"适用边界" | 参考站把发布语义写进 UI 文案 | 每条配置与映射都带 `effective_from/to`；历史单据锁版本，不随配置漂移 |
| 值域必须可结构化查询 | 参考站用 `extraProperty` 中文键传映射，无法校验 | Bone 用 `(field_code, insurer_code) → 选项集` 结构表，禁止 JSON 承载契约 |
| 作用域必须显式 | 三级树选中即作用域 | 任何配置写操作必须能回答"改的是哪个作用域"，不允许隐式继承当前列表上下文 |

## 2. Bone 现状（可验证）

### 2.1 页面与接口

| 面 | 现状 | 证据 |
|---|---|---|
| 保单列表 | 关键字 + 规则开关筛选；列：保单号/名称/类型/保司/分公司/投保公司/承保期间/等待期/被保人/开关；操作：详情/配置/编辑/启用/停用 | `PolicyManagementPage.tsx` |
| 下钻 | 「配置」跳 `/plan?policyNo=`，再跳 `/liability?policyNo=&planId=`（两次换页） | 同上 |
| 作业开关 | 理赔申请书/通知单两个开关**挂在保单上**，编辑弹窗内配置 | 同上 |
| 目录库 | 医院/疾病/药品/费用类别四页签，单表 CRUD，同租户同编码唯一 | `LibraryPage.tsx` |

### 2.2 后端模型

- `t_claim_policy`：单 `policy_no`、`insurer_name`（自由文本）、`biz_identity_code`、期间、`config_status` 三态、两个单证开关。`UNIQUE KEY uk_policy_no (tenant_id, policy_no)`。
- `t_claim_plan` / `t_claim_coverage` / `t_adj_liability`：四级树，责任字段已相当丰富（赔付比例/三层免赔/日限额/限定名单/目录准入/等待期）。
- `t_ref_hospital/disease/drug/fee_category`：租户级、单一码空间，**无保司维度**。
- 全仓无承保主体（insurer）实体，`grep` 无 `CREATE TABLE *insur*`。

### 2.3 五个硬缺口

| # | 缺口 | 事实 | 影响 |
|---|---|---|---|
| 1 | 险种层是装饰性的 | `ClaimCoverage` 未被 `domain/model/adjustment` 引用；`planLimit`/`coverageLimit` 只出现在配置 CRUD，无读取方 | 界面上的"计划保额/险种保额"配了不生效，与实际赔付无关联——仓内头号债务「配了不生效」的又一实例 |
| 2 | 目录库只有一套码 | `t_ref_hospital` 唯一键含 `hospital_code`，无 `insurer` 维度 | 接第二家保司时，要么污染标准库（把保司码当标准码入库），要么为每家复制一套责任配置 |
| 3 | 单证开关位置不对 | 开关在保单上 | 同一保司 500 张保单要配 1000 次；保司改口径时无批量入口 |
| 4 | **子表外键锚在业务号上** | `t_claim_plan/t_claim_coverage/t_adj_liability` 全部以 `policy_no` 关联，而非 `policy_id` | 一旦 `policy_no` 语义从"平台号"改成"保司号"，改号需同批迁移全部子表 + 赔案 + 额度账户，漏一处即孤儿数据 |
| 5 | **软删语义与唯一键冲突** | 全仓约定 `deleted TINYINT(1)` 且常被放进唯一键（`uk_iam_*`）；映射表若照抄，"同码停用后重建"会撞唯一键 | 保司改码→停用→重新启用是**常态操作**，不是异常；用 `deleted` 承载会逼出"物理删除历史映射"，直接违反不变量 4 |

**辨析**：`uk_policy_no` 不含 `deleted` 在保单表上是**正确**的——平台号不可变、永不回收，历史号不允许被复用。但同一个模式套到保司码表就错了：保司码会被停用、重启、换绑。两个场景的唯一键策略必须不同（见 §6.3）。

## 3. 差距矩阵

| 维度 | TPA-SAAS | Bone 现状 | 差距性质 |
|---|---|---|---|
| 保单标识 | 保司保单号 + 普康保单号双列 | 单 `policy_no`，且子表以它为准 | **结构性**：保司改号即断链 |
| 主体建模 | 业务主体（保司/经纪）+ 主体专属配置 | `insurer_name` 自由文本 | **结构性**：无法挂任何保司级配置 |
| 配置作用域 | 单页三级树，选中即作用域 | 三页跳转，靠 URL 传参 | 交互性：易丢上下文、易配错层级 |
| 责任规则 | 6 分区 + 费用项来源/表达式 | 扁平字段 + 费用类别规则表 | 表达力：发票结构差异无法用配置吸收 |
| 保额/控额 | 控额方/账户类型/保额类型/控额方式 | 有额度账户与控额策略，但计划/险种额度未接入 | 一致性：字段有、消费方无 |
| 码值 | 标准码表 + 保司码表 + 字段绑定 | 单套目录 + `sys_dict_item.external_code`（单槽） | **结构性**：`external_code` 一列装不下 N 家保司 |
| 目录映射 | 选项集 `extraProperty` 按字段映射 | 无 | **结构性** |
| 映射治理 | 无（只靠人工约定） | 无 | **治理性**：无裁决流程、无质量指标、无失败队列 |
| 配置发布 | 发布/预览/编辑记录 | 乐观锁 + 直接生效 | 治理性：不可回滚、不可预演 |
| 变更管控 | 无职责分离 | 无 | **合规性**：单人可改金额规则 |
| 作业开关 | 保司级 + 环节级 | 保单级两个开关 | 效率性：重复配置 |

## 4. 值得借鉴的六项（及为什么）

### 4.1 双保单号（保司号 / 平台号）

**机制**：`insurer_policy_no`（保司来单标识，可空、可重复、可被保司复用）+ `policy_no`（平台内部稳定标识，不可变，作所有外键）。

**为什么**：保司退保重出、批改换号是常态；若用保司号作主键，一次改号会让赔案、额度账户、结算单全部悬空。反过来只存平台号，则对账时无法与保司台账对齐。两个号各有唯一职责，这是保险核心系统的通行做法（业务号 vs 系统号）。

**不做的后果**：接第二家保司当天就会遇到"同一张保单两个号"，届时只能加字段 + 回填，且历史赔案无法自动归位。

**本轮补强的三点**：
- 平台号生成规则要写明（如 `P{yyyyMMdd}{8位序列}`），且**永不回收**，故 `uk_policy_no` 不含 `deleted` 是对的——这条现状不要"顺手修正"。
- 保司号需 `(tenant_id, insurer_code, insurer_policy_no, active_flag)` 部分唯一，因为保司可能复用号（退保后重出给别的投保人）。
- 索引与搜索：列表与对账都要能按任一号码检索，`insurer_policy_no` 必须有独立索引，不能只靠联合唯一键的最左前缀。

### 4.2 配置控制台：单页三级树 + 选中即作用域

**机制**：`/claim#/policy-rules?policyNo=` 一页承载「摘要条 + 三级树 + 规则页签」；点选责任行 → 下方页签作用域切到该责任。

**为什么**：配置的本质是"在某个作用域下调参数"。三页跳转把作用域藏在 URL 里，用户看不见当前在改哪条责任；参考站的树选中把作用域**显式化**，也天然支持"同一屏对比计划/险种/责任三层"。

**改造点**：参考站 10 个按钮与选中态耦合（未选责任点"编辑责任"无反应、无提示）。Bone 应改为：行内「配置」为主入口 + 「更多」收纳（复制/发布/下线），未选中时禁用并给出 tooltip 说明——把参考站的可发现性缺陷在 Bone 侧修掉，而不是复制。

### 4.3 责任规则六分区

**机制**：适用范围（对象/限定/出险类型/发票医疗类型/医保情形）→ 发票金额项（含来源方式与表达式）→ 承担费用类型 → 赔付规则（等待期/比例/免赔/次限额）→ 控额规则（控额方/账户类型/保额类型/控额方式）→ 理算信息（公式 + 费用限额 + 比例明细）。

**为什么**：这六个分区不是 UI 分组，而是**金额计算的物理顺序**。现有 `invoiceDeduct/adjustDeduct/dailyLimit` 平铺，运营看不出"发票级免赔在比例之前、理算级免赔在比例之后"，配错顺序不会报错但会赔错。分区即把隐式顺序变成可读契约。

### 4.4 费用项「录入项 / 计算项 + 表达式」

**机制**：每个发票金额项声明来源（录入 / 计算）与表达式；计算项如 `自付一 = 统筹起付线 + (发票总费用 − 统筹起付线 − 自付二 − 总自费) × (1 − 统筹赔付比例)`。

**为什么**：保司给的发票字段集不统一。硬编码 = 每接一家改一次引擎；表达式 = 配置吸收差异。Bone 已有 `formula_snapshot` 物化机制，表达式天然可物化进快照，历史案件复算不受配置变更影响。

**约束（本轮细化）**：
- 表达式必须白名单化（只允许已声明项 + 四则运算 + `MIN/MAX/ROUND`），禁止任意脚本，禁止访问上下文外变量。
- **类型系统**：每个项声明 `DECIMAL(12,2)` 金额或 `DECIMAL(9,6)` 比率，禁止金额与比率混算（否则"比例 80"与"比例 0.8"会静默差 100 倍）。
- **精度与舍入**：中间计算保留 4 位，落库前 `HALF_UP` 到 2 位（分）；显式声明舍入点，不在每步四舍五入。
- **失败语义**：除零、超界、引用缺失项 → fail-closed 转人工，**不得回落 0**（回落 0 = 静默不赔，与"静默多赔"同为资金事故）。

### 4.5 字段 → 选项集绑定（标准/专属双列）

**机制**：每个业务字段声明一个**有效选项集**；全局标准绑定做基线，保司可逐字段覆盖；页面同时展示两列以便一眼看出"这家保司哪些字段与标准不同"。

**为什么**：这是"多保司"最便宜的落点。规则（责任、限定名单）只写标准码；录入侧按保司码表收单，映射层翻译。绑定粒度到字段，才能处理"同一保司在性别上跟标准一致、在证件类型上自成一套"这种真实形态。

### 4.6 标准基线 + 差异覆盖 + 同步

**机制**：保司配置默认继承标准；只存差异；提供「同步标准」把标准新增项拉进来（不覆盖已显式覆盖项）。

**为什么**：90/10 法则。整份复制会在标准演进时产生 N 份漂移，且无法回答"这条规则是保司要求还是我们默认"。

**Bone 的直接受益点**：`docClaimApply/docClaimNotice` 从保单级上移到保司级默认 + 保单级覆盖，500 张保单从 1000 次配置降为 1 次 + 例外。

## 6. 多保司主数据映射设计（核心）

### 6.1 三层结构

```
标准主数据（唯一真源，规则只认它）
   t_ref_hospital / t_ref_disease / t_ref_drug / t_ref_fee_category
        ▲                                   │
        │ 映射（保司码 → 标准码）             │ 反查（标准码 → 保司码，回传/直付用）
        │                                   ▼
保司码表（按保司隔离，只存码值+名称+可选属性）
   t_claim_insurer_code_item(insurer_code, domain, item_code, item_name)

字段绑定（值域型字段，非目录实体）
   t_claim_field_binding(field_code, insurer_code?, source_type, ref_code)
```

三层之外还有**第 0 层：标准码自身的生命周期**（§6.7）。原方案漏了它，导致"标准码被合并/弃用后，历史映射指向幽灵码"无解。

### 6.2 为什么是三层，而不是"每家保司一套目录库"

一套库/保司的代价不在存储，而在**规则复制**：责任限定名单、费用类别规则、目录准入全部引用码值，换库就要重建全部规则，且标准升级（医保目录年度调整）时要改 N 份。三层把"语义"和"写法"分开：规则锚定标准码，保司码只是入口方言。这也是参考站的实际形态（`extraProperty` 承担同一职责），只是它把映射塞进了 JSON，我们要把它做成可查询、可校验、可发布的表。

**软删模型：这里刻意偏离仓内约定，有实测依据**

仓内通用约定是 `deleted TINYINT(1)` 且把 `deleted` 放进唯一键。本地 MySQL 8 实测两条：

| 实测 | 结果 | 含义 |
|---|---|---|
| 同键第二次软删：`UPDATE t SET deleted=1` | `ERROR 1062 Duplicate entry '1-A-1'` | 一个业务键**只能被软删一次**，"停用→重启→再停用"直接报错 |
| `NULL` 列参与唯一键 | 两条 `insurer_code=NULL` 的基线**都能插入** | 用 NULL 表达"标准基线"等于放弃唯一性 |

因此本方案的删除语义按**表的性质**分两类，而不是全仓一刀切：

| 表类型 | 表 | 唯一键 | 删除语义 |
|---|---|---|---|
| 身份型 | insurer / code_item / mapping / alias | **不含** deleted | 只"关闭"（status/active_flag），不删除；同身份复活走 UPDATE |
| 记录型 | release / change / miss | 不含 deleted（本无删除语义） | 按保留期归档，不做业务删除 |

**修正后的约束实测**（同一台 MySQL 8，按修正后的 DDL 建表）：

| 验证 | 期望 | 实测结果 |
|---|---|---|
| 同字段再插一条 `insurer_code='*'` 的基线 | 拒绝 | `Duplicate entry '1-cert_type-*'` ✔ |
| 同码两条 ACTIVE、`disambiguation_key` 分别为"剂型=注射剂/片剂" | 允许 | 3 行、2 条 ACTIVE ✔ |
| 同码同 key 再插第二条 ACTIVE | 拒绝 | `Duplicate entry '1-YCBX-DRUG-D001-剂型=片剂-Y'` ✔ |
| 同码 miss 三次（OPEN→RESOLVED→OPEN→IGNORED→OPEN） | 一行、`occur_count=3`、不撞键 | 一行、`occur_count=3`、状态 OPEN ✔ |

这四条同时也是 P0 的回归用例（§14 判据 ⑤⑦⑧⑨），不是一次性脚本。

**与 SDK 的兼容**：若 `bone-metadata-sdk` 的实体基类强制 `deleted` 列，本域实体恒置 0 并在仓储层把删除方法覆盖为"置 status"，禁止物理删；映射聚合需支持"关闭旧行 + 插入新行"的单事务写入。这一点需要架构评审确认（见 §16 待拍板 10），因为它偏离全仓软删约定。

**为什么映射表需要 `reason_code` 与 `reviewed_by`**：映射错了会直接导致赔错钱。出险时要能回答"谁在什么时候因为什么把 `5232068251008710` 认成了这家医院"。

### 6.4 七条不变量（写进聚合根，不靠约定）

1. 同一 `(保司, 域, 保司码, disambiguation_key)` 在任一时刻只能有 **1 条 ACTIVE** 映射 —— 由 `uk_active` 强制，不靠代码自觉。
2. 多条保司码可映射到同一标准码（N:1 归并，允许）。同一保司码映射到多个标准码（1:N）**仅当**每条都带**互不相同**的 `disambiguation_key`，且该键能由收单字段确定性算出（如 `剂型=注射剂|规格=2ml` 的规范化 hash）；算不出键或键不匹配即 fail-closed。"默认拒绝"要落在数据库上（唯一键含 `disambiguation_key`），不能只写在文档里——上一版的唯一键没有这一列，等于把"允许 1:N"写成了空话。
3. 映射目标 `standard_code` 必须存在于对应标准目录（发布期校验，禁止指向幽灵码）；发布后标准码被合并的，按 `t_claim_std_code_alias` 重定向，解析层必须走一次 canonicalize；命中 `t_claim_std_code_split` 的父码直接 fail-closed（拆分无单一目标）。
4. 停用映射不删除数据（历史单据要能解释当时为什么映射到那个码）。
5. **时序不重叠**：同一 `(保司, 域, 保司码, disambiguation_key)` 的 ACTIVE 行 `[effective_from, effective_to)` 区间不得交叠。MySQL 无 exclusion constraint，靠"先关旧行（带 `version` 条件）再插新行"在同一事务完成；并发双写由 `uk_active` 兜底降级为唯一键冲突（fail-closed），不使用 `SELECT … FOR UPDATE`（仓规）。`effective_to` 用 `9999-12-31 23:59:59` 而非 NULL，使区间恒闭合、范围查询不踩 NULL 语义。
6. **映射变更不改变已结案赔案**：赔案在收案时锁定 `config_snapshot_version`，重算必须显式触发且留痕。
7. **内容 append-only**：映射的"修改"= 关闭旧行（`active_flag=NULL`、`effective_to` 截断、`superseded_by_id` 指向新行）+ 插入新行。`standard_code`、`insurer_item_code`、`disambiguation_key` 一经写入**不得 UPDATE**。这一条是 §7.1"按版本回放"能否成立的前提：若允许原地改判，`release_no` 指向的行会在发布后被改写，历史案件的赔付依据即无法重建——版本号退化成装饰。

### 6.5 映射方向与四个消费点

| 消费点 | 方向 | 口径 |
|---|---|---|
| 收单（报案/发票/明细） | 保司码 → 标准码 | 落库**双码**：`raw_*`（原值）+ `std_*`（映射值）+ `mapping_version` |
| 规则配置（限定名单/费用类别/目录准入） | 只用标准码 | 配置界面只从标准目录选，杜绝混入保司码 |
| 回传（责任推送/直付/结算单） | **raw 原路返回**，兜底才反查 | 见下（上一版把反查当主路径，是次优设计） |
| 报表/对账 | 标准码为主，保司码可下钻 | 跨保司可比 |

**回传优先"原路返回"，反查只是兜底（本轮修正）**

上一版把"标准码 → 保司码反查"当作回传主路径，这有结构性缺陷：N:1 归并（多家分院 → 一家机构）在反查时天然多义，靠"按映射版本取"仍可能选到另一家分院。而绝大多数回传都针对**已有单据**，单据上本来就存着 `raw_*` 原值——直接原路返回，既无歧义，又天然与保司台账一致。

| 场景 | 取码方式 | 失败处置 |
|---|---|---|
| 回传已有单据（结算单 / 直付申请 / 责任推送） | **优先原路返回该单据的 `raw_*`**，前提是该码在保司码表仍为 ACTIVE | raw 已停用（保司改码）→ 反查新码；raw 缺失 → 反查 |
| 我方主动发起、无原始单据 | 反查该保司 ACTIVE 映射；多义时用该保司的"默认回传码" | 无 ACTIVE 或无默认码 → 阻断 + `PENDING_MAPPING` |

**原路返回不是无条件的**：保司改码后，旧码在它自己的系统里已不认，照原样回传会被对账拒绝或退单。所以原路返回前必须校验该 raw 码在 `t_claim_insurer_code_item` 仍是 ACTIVE；已停用则走反查取新码，并在单据上留一条"码已随保司变更重写"的记录。这一条上一版漏了——"原路返回"只说对了方向，没说完条件。

**反查未命中**：不得自动挑"最像"的码，也不得留空——阻断该笔回传、标记 `PENDING_MAPPING`、进 miss 队列并告警。静默回传错误码值会导致保司侧对账失败或拒付，比在本地阻断代价高得多。

这个修正同时消掉了一处自相矛盾：上一版的门禁要求"同一标准码在保司侧对应多个码即不通过"，但 N:1 本就是允许的形态（§6.4 第 2 条），门禁会把合法数据判成病。改成"回传默认码缺失"才对准真正的风险点（§6.10）。

**为什么存双码**：映射会变（保司改码、我们纠错）。只存标准码 ⇒ 无法复现"当时为什么这么判"；只存保司码 ⇒ 规则无法复用、报表无法跨保司。双码 + 映射版本号 = 可重算、可审计。

### 6.6 "标准不一样"的桥接策略

用户提到的不一致有三层，不能用一个手段解决：

| 不一致类型 | 例子（实测） | 桥接手段 | 无桥时的退路 |
|---|---|---|---|
| 码值不同 | 保司 `0`=身份证 vs 标准 `10`=身份证 | 直接映射（人工/导入） | 未命中转人工队列 |
| 名称不同 | 杭州第一人名医院（标准）vs 保司自有简称/错字 | 名称归一化（去空格/括号/全半角）+ 别名字段 | 名称只做**候选提示**，绝不自动落库 |
| 粒度/口径不同 | 保司医院码按"分院区"、标准按"机构"；药品按"商品名"vs"通用名" | N:1 归并（多分院→一机构）、按属性拆解（通用名+剂型+规格） | 标记 `GROUP` 并保留原码明细 |

**域级桥接优先级（升级为对齐国家编码标准）**：

| 域 | 首选权威桥 | 次选 | 说明 |
|---|---|---|---|
| 医院 | 统一社会信用代码（18 位，含校验位） | 国家医保定点医疗机构代码 / 卫健委执业许可证登记号 | 校验位可程序化验真，命中率高，优先于名称匹配 |
| 药品 | 国家医保药品代码 | 药品本位码 / 批准文号 | 医保目录年度调整时用同一桥做版本比对 |
| 疾病 | ICD-10 医保版 | 院内诊断名 + 归一化 | 版本升级会改码，必须走 §6.7 的 alias |
| 费用类别 | 无国标 ⇒ 平台自建枚举 | 保司费用项编码 | 标准侧由我们定义并**承诺稳定**，这是映射体系成立的前提 |
| 医疗服务项目 | 国家医保医疗服务项目代码 | 院内收费项目 + 对照 | 与"发票金额项"配合，避免用费用类别硬套 |

对齐国家医保信息业务编码标准的价值：它给了我们一棵**外部既有的、医保局每年维护的树**。保司码与医院 HIS 码都向它靠，我们不必自己发明标准，也不必承担标准维护的全部成本。没有权威桥的域（如保司自定义费用类别），标准侧由我们定义并承诺稳定——这句话必须写进契约，否则标准会随客户需求漂移。

### 6.7 标准主数据的生命周期（原方案缺口）

标准码不是永恒的：医保目录年年调，医院会合并，药品会退市。原方案只处理"保司码→标准码"，没处理"标准码自己变了"，结果是历史映射指向不存在的码。

| 事件 | 语义 | 处置 |
|---|---|---|
| 新增 | 标准侧新增码 | 无需动作；提示"有 N 条保司码可能对应新码"（按名称候选） |
| 弃用（DEPRECATE） | 码不再用于新业务，历史仍有效 | 标准行置 `status=DEPRECATED` + `effective_to`；已有映射保留，反查时打标"该码已弃用，建议迁移" |
| 合并（MERGE） | A 码并入 B 码 | 写 alias `A → B`（relation=MERGE）；解析层 canonicalize 后**规则命中不变**（规则早已引用 A，重定向到 B 后仍要能命中，故规则侧也要能跟随 alias） |
| 拆分（SPLIT） | 一码拆成多码（如医院分院独立） | **无单一目标，不能进 alias 表**（alias 的 `canonical_code NOT NULL` 是刻意的：1:1 才可自动）。写入 `t_claim_std_code_split` 记录父码→子码集合与分流依据；解析命中父码即 fail-closed 转人工，并列出子码候选 |
| 更名（RENAME） | 码不变、名称变 | 只更新名称，不动映射；历史单据保留原名称快照 |

**关键约束**：alias 只在**解析入向**生效（保司码→标准码后再次 canonicalize）。规则配置侧引用旧码时，发布期体检要报"引用了已合并码"并给出迁移建议，但**不自动改写规则**——自动改写规则等于静默改变赔付口径。

### 6.8 匹配与人工裁决（MDM stewardship）

实体解析（entity resolution）的通行做法不是"算个相似度就自动落库"，而是**分级 + 双阈值 + 人工兜底**。本方案定为五级：

| 级别 | 判据 | 处置 | 是否需人工 |
|---|---|---|---|
| L0 | 保司码 == 标准码，或已声明同源 | 自动 ACTIVE | 否（留痕） |
| L1 | 权威桥命中（信用代码/医保编码/ICD）且校验位通过 | 自动 ACTIVE | 否（留痕） |
| L2 | 归一化名称精确且候选唯一 | 进入"批量确认"清单 | 是（可批量 200 条一次确认） |
| L3 | 相似度 ≥ 0.92 **且** top1−top2 ≥ 0.05 | 单条候选确认 | 是 |
| L4 | 无候选 / 多候选无区分度 | 人工检索指定 | 是（双人复核） |

**为什么要看 top1−top2 的间隔而不只看相似度**：两家名称相近的医院（"XX市第一人民医院" vs "XX市第一人民医院东院"）相似度都可能是 0.95，只设绝对阈值会把"两个都像"误判为"可以自动"。间隔（margin）是判定"是否有唯一最优解"的标准手段。

**双人复核的触发条件**（不做全量双人，否则运营成本翻倍）：

| 场景 | 复核要求 |
|---|---|
| 新增映射（首次建立） | 单人确认 + 留痕 |
| 修改已 ACTIVE 映射（尤其金额相关域 DRUG/FEE_CATEGORY） | 必须第二人复核 |
| L4 无候选 / 拆分冲突 | 必须第二人复核 |
| 批量导入（> 100 条） | 抽样 5% 复核 + 全量导入报告留档 |

**SLA**：miss 队列 24h 首次响应；按 `occur_count × 收单量` 排序，先修高频。**AI 只出候选与理由，落库必须人点**——与"确定性分层、AI 不碰钱"的护城河一致。

### 6.9 未命中、冲突与 STP 闸门

- 收单命中失败：**不猜、不回落空串**。转 `t_claim_mapping_miss`（按 `(保司,域,码)` 聚合 `occur_count`，避免队列被同一码刷爆），赔案进"待补件/人工"分支，日志与页面同源可查。
- 冲突（同一保司码出现两个标准码候选）：标记冲突，暂停该域自动映射，只允许人工裁决。

**未命中解决后必须自动恢复，不能靠运营逐单重提**（本轮补的最后一公里）

`POST /mapping-misses/{id}/resolve` 成功后，同一流程内完成：① miss 置 `RESOLVED` 并关联 `resolved_mapping_id`；② 定位受影响案件（`last_case_no` 非空则单案，否则按 `(insurer, domain, raw_code)` 扫在办且停在"待补件/人工"的案件）；③ 异步重解析（幂等：已解析成功的明细跳过，不重复落账）；④ 输出"恢复 N 件 / 仍失败 M 件"报告，失败项回队列并 `reopen_count+1`。

缺这一步，映射修好了案子还卡着，运营会误判"映射没生效"而重复劳动——这是上一版只有队列、没有出队的缺口。

**已 RESOLVED 的码再次未命中 = 高危信号**：意味着映射被停用、或保司又改了码。`reopen_count > 0` 必须单独告警，而不是当普通队列项排队，因为它推翻的是"我们以为已经修好了"这个前提。

**覆盖率与命中率是两个问题，不能互相替代**：

| 指标 | 口径 | 防的是什么 |
|---|---|---|
| 覆盖率 | 已映射在用码值 / 在用码值 | **没做**（存量口径，治理进度） |
| 命中率 | 自动解析成功请求 / 总请求 | **做错**（流量口径，运行质量） |

只盯覆盖率会在 98% 时误以为健康，而剩下 2% 可能正是高频大额医院。
- 覆盖率指标（运营抓手）：`已映射在用码值 / 在用码值`，按收单量排序展示 TOP 未映射项——先修高频，才修得动长尾。

**STP 闸门**：把"映射质量"翻译成"业务风险开关"。

| 闸门条件（按 保司 × 域） | 未满足时的行为 |
|---|---|
| 明细级命中率 ≥ 99.5% | 该域赔案强制打 `manual_review_required` |
| **赔案级直通率 ≥ 95%** | 同上 |
| OPEN 状态 miss = 0 | 同上 |
| 近 7 天无"映射纠错导致金额变动"事件 | 同上 |
| 冲突数 = 0 | 该域禁止自动理算，仅人工 |

**为什么必须两把尺**：一张赔案 200 条明细、命中 199 条 ⇒ 明细级 99.5%（看着达标），赔案级 0%（整单转人工）。业务痛感发生在赔案维度，治理动作发生在明细维度；只设一个指标，必有一边失真。STP（straight-through processing）率是保险业衡量自动化程度的通用指标，用闸门而非"平均覆盖率"控制风险，是因为平均值会掩盖单点塌陷：整体 99% 的覆盖下，某家保司某域 0% 覆盖一样会造成批量人工积压。

### 6.10 发布前一致性门禁（配置体检）

对标仓内文档门禁的思路，把"配置是否正确"变成可自动判定的清单，发布前必须全绿：

| 检查项 | 判据 | 不通过的后果（若放行） |
|---|---|---|
| 孤儿映射 | `standard_code` 不在标准目录 | 解析出幽灵码，理算查不到目录规则 |
| 重复 ACTIVE | 同键 > 1 条 ACTIVE | 收单结果不确定（随机命中） |
| 别名环 | alias 图存在 A→B→A | canonicalize 死循环 |
| 回传无兜底码 | 主动发起类回传（无原始单据）缺少该保司的默认回传码 | 直付/结算单卡在 `PENDING_MAPPING` |
| 基线重复 | 同 `(field_code, insurer_code='*')` 存在多条绑定 | 绑定结果随机（实测 NULL 不判重，换成 `'*'` 才治得住） |
| 消歧键为空却存在 1:N | 同码多条 ACTIVE 但 `disambiguation_key=''` | 收单随机命中，且无法解释为什么是这条 |
| 拆分父码仍被引用 | 规则或映射引用 `t_claim_std_code_split.parent_code` | 该码一律 fail-closed，案件批量卡死 |
| 绑定失效 | 字段绑定指向已停用/已删除码表 | 录入下拉为空，单据录不进 |
| 规则引用弃用码 | 责任限定名单/目录准入引用了 DEPRECATED 码 | 新案件按旧口径赔付 |
| 时序交叠 | 同键 ACTIVE 区间重叠 | 版本切换时金额跳变 |
| 导入残行 | 导入批次存在未处理错误行 | 静默缺映射，后期集中爆 |

门禁输出必须是**逐条可定位**的（表名 + 主键 + 原因），不能只回"体检失败"。

### 6.11 性能、缓存与多租户隔离

| 关注点 | 设计 |
|---|---|
| 解析路径 | 收单时一次解析，下游全用标准码；`uk_active` 与 `idx_reverse` 覆盖两条主查询 |
| 缓存 | 进程内 Caffeine，key=`(tenant, insurer, domain)`，value=该域全量映射；命中走内存，未命中回源 |
| 失效 | 以 `release_no` 作为缓存版本；发布事务提交后广播失效（本地 + 多实例）；禁止"定时过期"式弱一致 |
| 热更新风险 | 发布后缓存未失效 ⇒ 新案件仍按旧映射解析，属静默错赔；必须有"发布后探针"：写入一条金丝雀码值，验证解析结果等于新版本 |
| 多租户 | 所有表带 `tenant_id`；缓存 key 含租户；后台任务按租户分片，禁止跨租户扫描 |
| 数据权限 | 保司是客户，A 保司的码表与映射不得被 B 保司的运营看到。分两层：功能权限沿用三段式 `claim:library:read` / `claim:library:write`（**不把 domain 塞进权限码**——`claim:library:{domain}:read` 会与既有 `claim:policy:read` 的规范分叉，且每加一个域就要加一批权限码）；数据范围按 `insurer_code` 做行级过滤（仓储层强制拼接，不靠前端隐藏） |

### 6.12 与平台既有设施的关系

Bone 已有「枚举选项源」（`inline/dict/reference/external` + snapshot/live）与 `sys_dict_item.external_code`。**不要另造第五套**：

- 值域型字段（性别/证件类型/关系）→ 复用 `sys_dict` 作为标准侧，新增 `t_claim_field_binding` 指向"保司专属字典"，专属字典的项用 `external_code` 指向标准项（此即参考站 `extraProperty` 的结构化等价物）。
- 目录型（医院/疾病/药品/费用类别）→ 标准侧仍是 `t_ref_*`（属性齐全、有治理），保司侧入 `t_claim_insurer_code_item`，映射入 `t_claim_code_mapping`。
- `external_code` 单槽问题：它只够一家外部标准，**不能**承载 N 家保司；这也是必须新增映射表而非复用该列的理由。

## 7. 配置版本与变更治理（本轮新增）

### 7.1 双时态（bitemporal）：回答"当时按什么规则算的"

配置有两个独立的时间轴：

| 轴 | 字段 | 回答的问题 |
|---|---|---|
| 业务有效期（valid time） | `effective_from / effective_to` | 这条配置在业务上什么时候算数 |
| 记录时间（transaction time） | `release_no / released_at` | 我们什么时候知道的、什么时候改的 |

只用一条时间轴会出两类事故：补录上月生效的映射时，若按"记录时间"判定，上月案件会被算成未映射；若按"业务时间"判定，已结案的历史案件金额会被回改。双时态才能同时正确。

**由此推出三条硬规则**：

1. 配了 `effective_from` 早于今天的（回溯生效），只影响"尚未收案"与"在办未结案"，**不得**改变已结案赔案金额。
2. 已结案赔案的金额解释只认 `config_snapshot_version`（收案时锁定），重算必须人工显式触发并留痕。
3. 在办案件是否自动跟随新配置，是产品决策而非技术细节（见 §16 待拍板 6）。默认建议：**锁定收案版本，不自动跟随**——自动跟随会让同一案件的赔付金额在流程中变化，复核人无法解释。

**"锁定版本"必须落到具体字段，否则是句口号**（上一版只说了要锁，没说锁在哪）：

| 落点 | 字段 | 作用 |
|---|---|---|
| 赔案 | `config_release_no`、`config_snapshot_hash` | 回答"这个案子按哪一版配置算" |
| 明细行 | `raw_*` / `std_*` / `mapping_version` | 逐行可解释，不依赖案件级汇总 |
| 快照内容 | **不存全量配置副本**，存 `(release_no, hash)` + 所依赖各行的 `id + version` 清单 | 全量副本会让案件表爆炸；存 id+version 才能在回放时验证行未被改写 |

**回放校验**：按 `release_no` 取回配置行后，比对 `id + version` 与快照清单；不一致即判定"配置被原地改写"，转人工并告警，**不得**静默按新值重算。这是不变量 7（append-only）在运行期的保险丝——只靠"约定不改"，迟早会被一次数据修复脚本破坏。

### 7.2 maker-checker：分级审批

| 变更类型 | 制单人 | 复核人 | 发布 | 依据 |
|---|---|---|---|---|
| 字典项新增/改名（不影响金额） | 运营 | 同组另一人 | 自动 | 低风险，防手误即可 |
| 映射新增（L0–L3） | 运营 | 抽样 | 自动（走发布单） | 高频，全量复核不可行 |
| 映射修改/停用（已 ACTIVE） | 运营 | 必须复核 | 复核后 | 直接改判历史口径 |
| 责任规则/控额/赔付比例 | 配置员 | 必须复核 | 复核后 | 涉金额 |
| 标准码合并/弃用 | 标准 owner | 产品 + 技术双签 | 计划窗口 | 影响全部保司 |

**为什么分级而不是全量双人**：全量双人在日均几十条映射的节奏下会退化成"闭眼点通过"，反而比单人留痕更差。分级把复核资源集中在"改判"而非"新增"上。

### 7.3 影响面分析（发布前必答）

发布单必须自动算出三个数，达不到就阻断或升级审批：

| 指标 | 计算方式 | 阻断阈值（建议） |
|---|---|---|
| 影响规则数 | 引用该码的限定名单/目录准入/费用类别规则条数 | > 50 需二级审批 |
| 影响在办赔案数 | 在办案件中该域码值出现次数 | > 500 需二级审批 |
| 预计金额变动 | 抽样 100 件按新旧配置各算一次，比对差额 | 任一案件差额 ≠ 0 且非预期 ⇒ 阻断 |

第三项是"预演（dry-run）"的量化形态：不是给个界面看看，而是给一个**可比对的数字**。参考站有"预览"但没有金额比对，这是我们要超过它的地方。

### 7.4 灰度与影子比对

新映射上线的风险不是"错"，而是"错得无声"。三步灰度：

1. **影子模式**：新映射只算不用，与旧逻辑并行跑，记录差异率；差异率 > 0.1% 不上线。
2. **按保司灰度**：先 1 家保司 1 个域全量，观察 7 天 STP 与 miss 队列。
3. **按比例灰度**：同保司内按案件 5% → 25% → 100% 放量，每档观察 48h。

灰度的前提是"开关可回退"，因此映射解析必须读 `release_no` 而非"最新行"，否则无法做比例分流。

### 7.5 回滚

- **只支持整单回滚**（`rollback_of` 指向目标 release），不支持逐条撤销。逐条撤销会破坏时序完整性，产生"某码在某段时间无 ACTIVE 行"的黑洞。
- 回滚 = 生成一个新 release（内容等于旧快照），而不是物理还原旧行——审计链必须是 append-only。
- 回滚后必须重跑 §6.10 体检，防止"回滚到的是一个当年就带病的版本"。

## 11. 经济性与运营模型

### 11.1 接一家新保司的成本对比（估算，须实测校准）

假设：1 张保单 × 3 计划 × 5 险种 × 8 责任 = 120 条责任配置；500 张在保保单；映射首期 3 个域共 900 条保司码。

假设：1 张保单 × 3 计划 × 5 险种 × 8 责任 = 120 条责任配置；500 张在保保单；映射首期 3 个域共 900 条保司码；**单条码值处理 1.5 分钟（含查证与录入），两边同口径**。

| 环节 | 现状（每保司复制） | 目标（复用 + 映射） | 假设 |
|---|---|---|---|
| 责任规则配置 | 120 条 × 10 min = 20.0 人时 | 0（引用标准模板） | 标准模板覆盖 90% |
| 单证/作业开关 | 1000 次 × 30 s ≈ 8.3 人时 | 保司默认 1 次 ≈ 0.2 人时 | 例外保单 < 5% |
| 码值处理 | 900 条 × 1.5 min = 22.5 人时 | 900 × (1−70%) × 1.5 min ≈ 6.8 人时 | 自动匹配率 70% |
| 复核与发布 | 0（直接改，无留痕） | ≈ 2.0 人时 | 抽样复核 |
| **合计** | **≈ 50.8 人时** | **≈ 9.0 人时** | — |

降幅约 **82%**。（上一版此处合计写 12 人时而分项相加为 9.0，是算错的；现状码值口径也只算了 640 条，两边不可比。已按同一口修复。）

| 自动匹配率 | 人工映射 | 目标合计 | 相对现状 50.8 |
|---|---|---|---|
| 50% | 11.3 | 13.5 | −73% |
| 70% | 6.8 | 9.0 | −82% |
| 85% | 3.4 | 5.6 | −89% |

**关键结论：收益的大头不在匹配算法**。结构性收益（规则复用 20.0 + 单证 7.8 ≈ 27.8 人时）与匹配率无关；匹配率只影响码值那一段（22.5 → 11.3/6.8/3.4）。所以：

- 自动匹配率从 70% 掉到 50%，降幅仍 73%，项目依然值得做 ⇒ **不要因为"外部锚拿不到"就否定整个方案**（这条直接支撑待拍板 9）。
- 反过来说，若规则复用做不出来（仍逐保单复制），整个收益模型立刻塌掉——**P0 的价值锚是"规则锚标准码"，不是"匹配得多准"**。

**这些数字是假设推演，不是实测**。用途是判断"值不值得做"，不是承诺。落地后应用 §12 的指标回填真实值。

### 11.2 运营模型（RACI）

映射类项目失败的主因是"没人负责"，不是技术。必须点名：

| 角色 | 职责 | 建议归属 |
|---|---|---|
| 标准 owner | 定义/维护标准码，审批合并与弃用 | 产品（理赔域）1 人 |
| 码表维护员 | 导入保司码、处理 miss 队列 | 运营 1–2 人/保司组 |
| 映射复核人 | 复核改判类变更 | 运营组长 / 配置管理员 |
| 发布审批 | 金额相关变更放行 | 技术负责人 |
| 指标 owner | 覆盖率/STP/差异率看板 | 产品运营 |

**没有 owner 的映射表会在 3 个月内变成垃圾场**——这条不是修辞，是 MDM 项目的普遍结局。若组织上无法保证 owner，宁可先只做 2 个域（医院 + 药品）也不要铺开 6 个域。

## 12. 度量与 SLO

| 指标 | 定义 | 目标 | 用途 |
|---|---|---|---|
| 明细级命中率 | 自动解析成功明细行 / 总明细行（按保司×域） | ≥ 99.5% | STP 闸门输入（流量口径） |
| 赔案级直通率 | 全明细均自动解析的赔案 / 总赔案 | ≥ 95% | 业务痛感口径；与上一行**不可互替** |
| P99 解析耗时 | 缓存命中 / 回源分别统计 | < 5ms / < 20ms | 收单体验 |
| miss 队列 24h 处理率 | 24h 内首次处理 / 新增 | ≥ 90% | 运营健康度 |
| 冲突数 | 同码多候选且未裁决 | 0 | 闸门硬条件 |
| 映射纠错引发金额变动 | 发布后因映射错误导致的金额调整笔数 | 0 | 质量红线 |
| 覆盖率（在用） | 已映射在用码值 / 在用码值 | ≥ 98% | 长尾治理（存量口径，防"没做"） |
| 发布后探针 | 金丝雀码解析结果 == 新版本 | 100% | 缓存失效正确性 |
| 配置读取可用性 | 只读接口成功率 | ≥ 99.95% | 收单依赖 |

**注意**：覆盖率是"是否做过"，命中率是"是否做对"。只看覆盖率会在 98% 时误以为健康，而剩下 2% 可能是高频大额医院。

## 13. 迁移与上线（按 ADR-生产数据库增量迁移策略）

存量 `insurer_name` 是自由文本，`policy_no` 语义待锁定，不能一把 rename。四步 expand/contract：

| 步 | 动作 | 回退方式 | 判据 |
|---|---|---|---|
| E1 expand | 加 `insurer_policy_no`、`insurer_code`、映射相关表；双写开关 | 关开关，忽略新列 | 新列可空、旧路径不受影响 |
| E2 backfill | 按 `insurer_name` + `biz_identity_code` 归一化到主档；无法归一的行导出人工确认（列 TOP 20） | 只回填不切换读 | 归一化覆盖率 ≥ 95%，剩余有清单 |
| E3 switch read | 读切到 `insurer_code`；`policy_no` 明确锁定为平台号 | 切回读旧列 | 列表/报表口径一致，抽样对账通过 |
| E4 contract | `insurer_name` **物理改名为 `insurer_name_snapshot`**，只读（不删列） | — | 保司更名后历史单据仍显示原名；改名让"误把它当配置源"在编译期就失败 |

**为什么 E4 是改名而不是只留着**：保司会改名、会被合并，历史单据必须显示"当时那家保司叫什么"，这是审计要求，所以列不能删。但**留着旧名等于留着误用入口**——下一个开发者看到 `insurer_name` 会顺手拿它做匹配，映射就被绕过了。改名成本只有一次 ALTER，收益是把"不该用"变成"用不了"。

**不要做的事**：不用"DROP DATABASE 重建"处理存量（那是开发库做法）；不在同一批里既改 `policy_no` 语义又改子表外键——两步之间必须有一次可观测的稳定期。

## 14. 分期与验收

| 期 | 范围 | 验收判据（**双向**变异验证） |
|---|---|---|
| **P0**（映射闭环） | 承保主体主档；双保单号；保司码表 + 映射 + 未命中队列；标准码 alias / split；规则配置改引标准码；收单落双码；发布前体检 | ① 保司码明细能解析出标准码并落 `std_*`；② **删掉映射查询 ⇒ 收单转人工且写 miss 记录（必须转红）**；③ **反向对照：映射存在且唯一时必须命中并落标准码（若实现永远拒绝，此条转红）**；④ 未命中**不得**回落空串/0（`null` 断言 + 金额断言双查）；⑤ 同键并发双写 ⇒ 一方唯一键冲突而非双 ACTIVE；⑥ 标准码 MERGE 后旧映射仍能解析到新码；⑦ **直接 `UPDATE standard_code` 被仓储层拒绝**（放开守卫应转红）；⑧ 同码两条 ACTIVE 靠不同 `disambiguation_key` 共存，键相同时必冲突（双向：去掉键列应转红）；⑨ miss 解决后自动重解析，案件从"待补件"恢复且重复解析不重复落账 |
| **P1**（配置面与治理） | 保单规则控制台单页；责任规则 6 分区；计划/险种额度接入控额；字段绑定；保司级作业/单证默认 + 保单覆盖；发布/maker-checker/影响面/回滚 | ① 计划保额=1000、责任=800 时赔付取 min 且快照可见来源；② 配置跳转次数 3 → 1；③ 发布后旧版本赔案按快照复算，金额逐分不变；④ 单证开关继承：改保司默认后未覆盖的保单行为随之变化，已覆盖的不变；⑤ **移除复核校验 ⇒ 同一人发布应被拒（转红）**；⑥ 体检门禁：注入一条孤儿映射 ⇒ 发布被阻断 |
| **P2**（效率与可解释） | 个人额度子页；复制责任；责任推送配置；理算演示；责任编辑记录 | ① 从保单上下文能完成额度初始化/保全；② 预演只读、不落账（用金额与流水双断言） |

**判据设计原则**（本项目历次踩坑的总结）：

1. **删掉实现必须转红**——否则只是"跑过"，不是"做到"。映射"表建了但没人调用"是本项目最常见的假绿形态。
2. **必须有正向钉子**——只写"未映射必须拒绝"会导致后人把实现改成"永远拒绝"也全绿；必须配"已映射必须命中"的对照用例。
3. **断言最终状态而非 SQL 文本**——`assert` 落在库里的 `std_*`、金额、状态，不落在"是否执行了某条语句"。
4. **E2E 真实链路**——§10 的样例走查要落成集成测试，而不是文档里的表格。

## 15. 风险与不做的事

| 风险 | 处置 |
|---|---|
| 映射治理成本被低估（长尾码值永远填不完） | 覆盖率驱动：只对"已出现过的码值"要求映射；用 miss 队列而非全量预映射；按 `occur_count` 排序先修高频 |
| 保司改码导致历史映射失真 | 映射带生效期 + 版本；历史单据锁版本；停用不删除；只支持整单回滚 |
| 双码造成存储与查询复杂度 | 只在收单入口解析一次，下游一律用标准码；仅在明细表保留 raw 列 |
| 配置发布被当成"改完立即生效" | 发布即版本切换 + 明确"只影响新进件"（参考站这条边界声明值得照抄） |
| 缓存未失效导致静默错赔 | 发布后金丝雀探针 + 版本化缓存 key；不用定时过期 |
| 标准侧随客户需求漂移 | 标准码由我方定义并**承诺稳定**；变更走 alias + 审批，不直接改码 |
| 组织无 owner | §11.2 明确 RACI；无 owner 时缩减域范围而不是降低标准 |

**明确不做**：

- 不把"职业列表/快捷理算/脚本规则"整体搬入（前者可由字典承载；后者与"确定性分层、AI 不碰钱"的护城河冲突，须单独立项）。
- 不为每家保司建独立数据库 schema（会摧毁跨保司统计与规则复用）。
- 不用 `extraProperty` 式 JSON 承载映射契约（不可校验、不可索引、不可审计）。
- 不做"AI 自动落库映射"（只出候选，人点确认）。
- 不做逐条映射撤销（破坏时序完整性）。

## 16. 待拍板

前 5 条是原方案遗留，6–9 为第一轮补强新增，10–11 为复核新增。

1. **P0 范围**：是否先只做"医院 + 药品"两个域（收单量最大、桥最清晰），疾病/费用类别留到 P0.5？
2. **双保单号命名**：`policy_no` 保留为平台号、新增 `insurer_policy_no`（推荐，因 §2.3 缺口 4：子表外键全锚在 `policy_no` 上，反过来的迁移面是数倍）。
3. **保司主档粒度**：只到法人，还是同时建"分公司"（现 `branch_name` 为自由文本）？后者影响 `biz_identity_code` 四级匹配口径。建议：主档只到法人，分公司用 `parent_code` 挂在同一张表，避免两套实体。
4. **计划/险种额度**：接入控额（取 min）还是先显式标注"暂不参与理算"？前者动金额链路，须配回归证据。
5. **发布体系范围**：一期是否只做"映射发布"，配置发布留到 P1？
6. **在办赔案遇到配置变更**：锁定收案版本（推荐，可解释）还是自动跟随新配置（省人工但金额会漂移）？
7. **maker-checker 强制范围**：金额相关强制双人 + 字典类单人（推荐），还是全量双人？
8. **标准码 owner**：由产品（理赔域）兼任，还是设专职主数据管理员？若前者，需要明确其时间预算。
9. **是否引入国家医保编码作为外部锚**：涉及数据获取许可与年更维护成本；不用则退化为"名称归一化 + 人工"，自动匹配率预计下降 15–25 个百分点。**注意 §11.1 的结论：匹配率降到 50% 方案仍降本 73%，故这条不是 P0 的前置条件，可以后补。**
10. **是否接受映射域偏离全仓软删约定**（§6.3）：`t_claim_code_mapping` 等身份型表不设 `deleted`、改用 status + `active_flag`，需要 SDK 基类允许"不继承软删"。若架构评审不同意，退路是接受"同码只能软删一次"并禁用物理删除，但会牺牲"停用→重启"的顺畅度。
11. **回传默认码谁维护**（§6.5）：主动发起类回传需要一个"该保司该标准码的默认码"，这是运营数据而非配置，建议纳入码表维护员的日常职责，否则直付会长期停在 `PENDING_MAPPING`。
