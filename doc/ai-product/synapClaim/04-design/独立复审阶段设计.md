# 独立复审阶段设计

> v1.0 ｜ 2026-11-13 ｜ 性质：设计（代码落在批 3）
> 适用：智能理赔三段作业的第三段「复审」，与「≥1 万双人复核」并列而非合并。

## 一、决策摘要

| # | 决策 | 理由 |
|---|---|---|
| D5-1 | 新增状态码 `43 = PENDING_RE_REVIEW`、`46 = RE_REVIEWING` | `44 = REVIEWING` 已承载「≥1 万双人复核」，两者触发条件与度量口径不同 |
| D5-2 | 复审与双人复核**并列**，不合并成同一队列 | 一个是金额闸门（必须两人），一个是质量闸门（按规则抽复审）；合并后主管无法分别度量积压与质量 |
| D5-3 | 新增权限码 `claim:re-review:write`，复审人 ≠ 初审人 ≠ 第一审核人 | 职责分离是审计要求，复用同一码等于没有分离 |
| D5-4 | 不新增流程内「质检」状态 | 质检是结案后事后监督，见《抽检打回闭环设计》；流程内只加复审一个环节 |

## 二、现状

| 事实 | 证据 |
|---|---|
| 现有 14 个状态，`44 = REVIEWING` 是双人复核 | `ClaimStatus.java:14-43` |
| 复核人 ≠ 第一审核人（仅字段比对） | `ClaimCase.java:534-535` |
| 初审/审核共用 `claim:review:write` | `ClaimCaseController.java:157-270` |
| `ClaimStage.INSPECTION` 定义了但 `stageOf` 从不产出 | `ClaimCase.java:780-788` |
| 状态码 43 / 46 / 47–49 空闲 | 上述枚举全集比对 |

## 三、状态与流转

### 3.1 新增状态

| 码 | 枚举名 | 含义 | stage |
|---|---|---|---|
| 43 | `PENDING_RE_REVIEW` | 复审待办（已生成任务、尚未领取） | `REVIEWING` |
| 46 | `RE_REVIEWING` | 复审中（已领取） | `REVIEWING` |

### 3.2 合法迁移（仅新增，不改既有）

| 从 | 事件 | 到 | 守卫 |
|---|---|---|---|
| 42 `ADJUSTED` | `submitForReReview()` | 43 | 命中复审规则（比例/金额段/风险标记）且未结案 |
| 44 `REVIEWING` | `completeSecondReview(通过)` | 43 或 50 | 命中复审规则 → 43；否则直接 50（保持现行为） |
| 43 | `claimReReviewTask(reviewerId)` | 46 | 复审人 ≠ 初审人 ≠ 第一审核人 |
| 46 | `completeReReview(PASS)` | 50 | 结论必填，留痕 `t_claim_review_record(role=RE_REVIEW)` |
| 46 | `completeReReview(REJECT)` | 41 | 必填打回原因，回到核赔处理中 |
| 43 | `rejectReReview()` | 41 | 主管可直接退回，需原因 |

其余状态与迁移**一律不变**；未命中复审规则的案件行为与现在完全一致（默认关闭，见 §六）。

### 3.3 优先级与队列

- 复审任务进 `t_claim_task`（`task_type=RE_REVIEW`），走《作业分配与代理交接设计》的同一套分配与我的待办。
- 队列分列展示：**双人复核队列（44）** 与 **复审队列（43）** 不共用一个筛选值，避免用户把"金额闸门"当成"质量闸门"。
- SLA：复审沿用 `ClaimStage.REVIEWING` 的工时口径，不新造 stage（避免再出现"定义了却从不产出"的 `INSPECTION` 式空转）。

## 四、职责分离与权限码

- 新增 `claim:re-review:write`（复审动作）与复用 `claim:claims:read`（查询）。
- 校验顺序：① 当前用户具备 `claim:re-review:write`；② `reviewerId ≠ firstReviewerId`；③ `reviewerId ≠ secondReviewerId`；④ 非同一人重复提交（幂等键）。任一失败 → `SC_CLAIM_REVIEWER_CONFLICT`（复用既有码，不新增语义重叠码）。
- 权限码登记需同步：`iam_permission` 新增一行 + 角色绑定；前端 `constants/permissions.ts`；错误码台账 §6（若新增码）。

## 五、对既有断言的影响与配套

| 影响面 | 处理 |
|---|---|
| 前端状态字典 `statusOptions` | 追加 43/46，标签「待复审」「复审中」 |
| 状态机穷举测试 | 新增 6 条迁移用例，既有用例断言不变 |
| `ReviewTaskStatusMapper` | 43→WAITING，46→PROCESSING；DONE 不含 43/46 |
| SLA/超时关单 | `CloseExpiredClaimJob` 不覆盖 43/46（复审不自动关单，需人工退回复审结论） |
| 探针/契约 | 状态枚举契约文档同批更新，禁止只改代码不改字典 |

## 六、开关与灰度

- `t_feature_toggle` 新增 `RE_REVIEW`（默认 `off`，`config_json` 存 `{ratio, amountMin, riskOnly}`）。
- 关闭时：不产出 43，`completeSecondReview` 直通 50，与现状完全一致。
- 灰度：先按 `riskOnly=true` 只复审风险标记案件，观察 2 周通过率与打回率后再放开比例。

## 七、分批落地

批 3：状态码 + 迁移 + 权限码 + 复审队列 + 开关。验收：开关关闭时全量回归与现状一致（状态分布比对）；开启后 43→46→50/41 三条路径各有单测；职责分离 4 种冲突各有用例。

## 八、风险与回退

| 风险 | 缓解 |
|---|---|
| 新状态码波及 40+ 处状态断言 | 同批补字典 + 穷举测试；灰度默认关闭 |
| 用户混淆「复审」与「双人复核」 | 队列分列 + 权限码分离 + 页面文案标注"金额闸门 / 质量闸门" |
| 复审成为新的积压点 | 复审队列纳入"我的待办"同一负载模型，主管可见积压量 |

**回退**：关闭 `RE_REVIEW` 开关，存量 43/46 案件由脚本退回 41 或推进 50（一次性迁移，append-only 留痕）。

## 九、不做清单

- 不新增 `ClaimStage`。
- 不做自动复审（复审必须人工，属质量闸门）。
- 不做多轮复审（一轮打回即回核赔，避免无限循环）。
- 不改 `44` 的既有语义。

## 十、待决策

2. 复审 SLA 是否短于双人复核（当前沿用同一 stage 工时）。
