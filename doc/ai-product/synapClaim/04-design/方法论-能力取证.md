# 方法论：按读取点取证，不按声明处（死配置显式拒绝）

> **SSOT 定位**：本文是「某能力是否真的存在 / 生效」取证方法的唯一权威。总体技术方案 §0、理算引擎设计 §14.6、AI 技术方案 §4.2、多保司映射设计 §2.3 等处的同主题论述，均以本文为口径来源，本地只保留领域落点，不重述通用规则。

## 1. 核心规则

判断"某能力（字段 / 配置项 / 端口 / 服务）是否存在且生效"，要按**读取点**取证，不能按**声明处**取证：

- **读取点**：谁调用它、谁消费它的输出。有真实读取方 = 真的被用；零读取方 = 死配置。
- **声明处**：类 / 字段 / 配置项 / 端口的存在本身。只出现在自己的声明与校验里，就是死配置。
- 反过来，断言"不存在"时也要把调用链扫完，不能只看某个 Port 或某个定义文件就下结论——"没查到" ≠ "没有"。

## 2. 工具陷阱（实测）

`grep -rn "x" --include=*.java`（zsh 下 `--include` 会被当通配符导致整条命令未执行，输出看着像"没搜到"）；BSD/macOS `grep` 不支持 `\|` 交替，会静默返回空。凡要做"某能力确实没实现"这种**否定判断**，必须换一种方式复核（Python / IDE 全局检索 / 编译期引用），否则会把"没查到"当成"没有"，写进文档就成了假证据。

> 反例：`AdjustmentEngine` 的 `occurrenceLimit()` 在本机 `grep` 静默返回空，但 Python 扫出 `AdjustmentEngine` 2 处、`OccurrenceGrouper` 4 处引用。所以 `grep` 零输出既可能是真死配置，也可能是工具没匹配上——它不能单独作为"不存在"的证据。

## 3. 与 fail-closed 的关系

规则缺失 / 配置不成立时，给出"看起来合理"的金额比给出"不能算"危险一个数量级——前者会安静地赔错一整年，且没人知道是配置问题。因此：任何"已支持"的声明，必须能指向一处实际读取该值的算式；不允许"声明了但不用"的第三种状态（要么真的生效，要么装载期拒绝）。这同时也是给 `design/` 加术语门禁的理由——只靠人记得核对，下一次还会漏。
