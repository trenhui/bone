# `04-design` 方案质量诊断报告（基于业界最佳实践）

> 诊断对象：`04-design/` 下 6 份设计文档（总体技术方案、理算引擎设计、风控与支付通道设计、BONE-AI能力依赖图谱、多保司保单配置面与主数据映射设计、AI技术方案）。
> 方法：逐篇通读 + 跨文档一致性比对 + 业界实践对照（保险核心系统 / MDM / ML 工程 / 金融合规）。
> 结论基调：**这是一套罕见地诚实、可证伪、以代码事实为准的设计集**，主要问题不在"方案错"，而在"表达过载、跨文档重复、少数内部不一致、一处具体缺陷"。

## 1. 逐项对照你的 7 个问题

### 1.1 逻辑是否自洽？
**总体自洽，但有 1 处真实裂痕 + 1 处口径风险：**

- **真实裂痕（P4）**：理算引擎 §14.2 把"免赔对象为空"定为 fail-closed（不回落默认），但 §14.5 自曝 `DeductibleRule.Target` 为空时实际回落到 `CALCULATED_AMOUNT`（先乘比例再扣免赔）。这是金额引擎内部的**设计与代码不一致**，且风险方向是"静默少赔"——正是 S2 反复警告的最危险失败模式。文档把它标成"待业务确认项"，但"未定义缺省"在资金引擎里本身就是缺陷，不应长期悬空。
- **口径风险（P5）**：总体 §0 用"配置面数据层已落地"作一句话结论（指 Policy/Plan/Coverage 三实体已存在），而多保司文档证明映射层（承保主体、双保单号、保司码表、发布治理）还是 draft 且有 5 个硬缺口。两处都在讲"Config"，读者不逐篇读容易误判 Config 域已完工。
- **其余核心逻辑闭环良好**：九步管线 ↔ 五条不变量 ↔ 双轨/变异验证自洽；三层时态（活库/设计态/目标态）标注到位；AI 不碰钱红线全 6 份文档一致。

### 1.2 务实合理吗？
**绝大多数务实，唯一可质疑的是"抽 jar"（P6）：**
- 抽 `adjustment-engine` 纯算术 jar 的动机是"复用 + 双轨 oracle 隔离"。但文档自己也承认"该 jar 尚未抽出""当前是单 module 九步内核"，且**全仓唯一消费方仍是 synap-claim**。在第二个消费者出现前，抽 jar 只带来 jar 发布/版本/框架纯净度验证的额外成本。建议：保留单 module + ArchUnit 证明 domain 零框架依赖（文档已能做到），等确有第二消费者再抽。这不是错误，是 ROI 待证。〔2026-11-08 决议更新：D1 已拍板三模块切分与 `adjustment-engine` 坐标（`com.bone.claim`），本条「保留单 module」不再是现行口径；YAGNI 判断已收窄为《总体技术方案》§9.1 的 M4 ROI 权衡，不改变目标态。〕
- 多保司映射的 P0/P1/P2 分期、经济学模型（已自纠 12↔9.0 人时口径错误）、RACI 都务实且诚实标注"估算须实测校准"。
- 风控/直付"Phase B 增量、不挤占 MVP、不为想象规模预付"的节奏纪律非常务实。

### 1.3 可落地吗？
**高度可落地：**
- 多保司文档给了 DDL（经本地 MySQL 8 实测）、7 条不变量、双向变异验收判据、E2E 走查样例——可直接变测试用例。
- 理算引擎给了"删实现必须转红 + 必须有正向钉子"的判据设计原则，直接对应"可落地+不可假绿"。
- 迁移方案（M2 expand/contract、多保司 §13 四步）按 ADR 且标注"脚本编号 0123–0126 为规划占位、未创建"——诚实区分规划与实施。
- 主要落地风险在**组织侧**（多保司 §11.2：无 owner 则映射表 3 个月变垃圾场），文档已点名，这是真风险而非方案缺陷。

### 1.4 内容与业界最佳实践对照（亮点，呼应"基于业界最佳实践"）
见 §0.1 的 S1–S8。特别值得说：
- **防假绿体系（S3+S4）**在国内保险/金融 AI 方案里极少见到这种 rigor：双轨 oracle、缺口哨兵反证、变异验证、静态就绪度复核器带负向探针。**这是本方案最该保留并对外讲清楚的差异点。**
- **MDM 级映射治理（S5）**：双时态、maker-checker、双码、STP 闸门、miss 队列自动恢复——已经超过参考站（TPA-SAAS）的"有发布无复核"。
- **诚实的 L3 成熟度**：明确"aiParticipated=0、l3Claimable=false"，不把目标态写成现状——符合金发8号/监管总局 32 项的"可解释、可复核、可治理"精神。

### 1.5 内容有没有冲突或重复？
**有，集中在两处：**
1. **重复（P3）**："死配置 / 按读取点取证" 这一方法论在 总体 §0+修正、多保司 §2.3、理算 §14.6、BONE-AI图谱 §2 各讲一遍；理算 §14.6 已把它"升格为通用规则"，但其他文档仍在重述。
2. **版本表缺陷（P2）**：AI技术方案 版本历史表把 v1.5 排在 v1.9 之后，且表末 v2.2 而正文已到 v2.10——这是事实性不一致，且说明该 changelog 已无人维护。
3. **风控 §00 vs §5**：四道闸闭环（模型门禁→反诈→额度熔断→降级转人工）在决策摘要和串联图各写一次。
4. **轻微**：`MVP I0–I4 容量矩阵` 被风控与图谱反复引用，但不在 04-design 本批文档内定义，属跨目录悬引（低优先级）。

### 1.6 有没有无用的废话？
**最大废话源是 AI技术方案.md（P1）：**
- 正文 §1 大量内联 `（v1.5 落地）/（v1.6 落地）/（v1.7 修正）/…/（v2.3 落地）` 标注，与文首版本历史表重复。
- §1.7 把"循环复核第 2/3/4/5/6/8 轮"的实施日志（①–⑫）整个塞进设计文档——这是**过程记录**，不是设计。
- §11.1–11.13 每个小节又各自带版本标签。
- 结果是：一份标着"技术方案（可评审）"的 181KB 文档，实际是"设计 + 实施日志 + 变更记录"三合一，评审者很难在噪声中抓到当前设计。
- 讽刺的是，AI技术方案 §1.3 自己立过纪律："同一事实两份描述，比对时答不出哪个对"——但这份文档恰恰没把这条纪律用在自己身上。

## 2. 优化建议清单（带"为什么"）

### 建议 1（高优先）：拆分/瘦身 `AI技术方案.md`，把 changelog 与实施日志外置
- **做法**：① 保留文首"版本历史表"作为唯一 changelog 入口，并**修正顺序 + 补全到 v2.10**；② 删除 §1 内联的 `（v1.x 落地/修正）` 标注；③ 把 §1.7 的"循环复核第 N 轮"整段、§11 各小节的版本标签，迁入独立附录 `实施日志与复核记录.md`（或并入版本表）；④ 正文只保留"目标态/当前态 + 时态标记"。
- **为什么**：a) 181KB 带版本噪声的文档评审效率极低，未来你自己重读也会丢设计；b) 它违反文档自身 §1.3 的"不双写"纪律；c) 设计文档的价值是"现在该怎么建"，过程应进历史。

### 建议 2（中优先）：把"死配置 / 按读取点取证"收敛为单一方法论 annex
- **做法**：新建 `方法论-能力取证.md`（或并入总体 §0），全仓统一引用；其他 4 处改为一句话 + 链接。
- **为什么**：同一课讲 4 遍必然漂移（这正是文档自己警告的），且理算 §14.6 已认定它是"通用规则"，就该只有一处权威。

### 建议 3（中优先）：解决或显式升级 DeductibleRule 缺省回落矛盾（P4）
- **做法**：二选一——要么把"免赔对象为空"在配置侧定为必填（装载期拒绝），要么在 §14.5 把回落 `CALCULATED_AMOUNT` 写成**有意为之并登记其风险**（静默少赔）。不要保留"未定义缺省"悬空。
- **为什么**：这是资金引擎内部"设计说 fail-closed、代码却回落"的真实裂痕，方向与 S2 警告的最危险失败模式一致；长期悬空会在某个条款配置漏填时静默少赔。

### 建议 4（中优先）：修正版本历史表 + 给"配置面已落地"加定语（P2/P5）
- **做法**：① 把 v1.5 归位、补全到 v2.10；② 总体 §0 一句话改为"**Policy/Plan/Coverage 三实体的数据层已落地**，映射层见多保司（draft）"——把结论限定到被核验的对象。
- **为什么**：P2 是事实性不一致，P5 是口径误导；两者都让评审者误判进度。

### 建议 5（中优先）：重新审视"抽纯算术 jar"的时机（P6）
- **做法**：在总体 §9.1 M4 增加一句判定——"当且仅当出现第二个消费方（如独立理算服务/对账批量）时再抽 jar；当前以单 module + ArchUnit 证明 domain 零框架依赖为满足态"。
- **为什么**：YAGNI + 文档自己承认 jar 未抽、二次消费方未现；提前抽 jar 增加发布/版本/纯净度验证成本，而收益（复用）尚未发生。

### 建议 6（低优先）：风控 §00 与 §5 四道闸去重；把双轨 oracle 维护成本列为显式权衡（P7/P8）
- **做法**：§5 图保留，§00 只写一句"详见 §5"；理算 §15 增加一行"R6：oracle 双轨需持续与生产同步，作为防假绿的代价，纳入维护预算"。
- **为什么**：减少重复；让评审看到"双轨"既是证据也是成本，决策更平衡。

② **扫描必须排除匿名/局部类**：`DecisionMetricsPort` 自带一个 NOOP 匿名实现（`DecisionMetricsPort.java:27`），首版把它的空类名当成第二个适配器判红——这类误报只有真跑一次才会暴露，纯静态推演发现不了。故判据用 `isAnonymousClass()/isLocalClass()` 过滤，并保留 4 条负向探针（两个无条件必红 / 一个无条件 + 条件实现不误报 / 两个 `@Primary` 必红 / 全条件实现不误报）。
