# 作业分配与代理交接设计

> v1.0 ｜ 2026-11-13 ｜ 性质：设计（本 change 只交付设计，代码落在批 1 / 批 4）
> 适用：智能理赔三段作业（初审 / 审核 / 复审）与后督抽检的任务归属、分配、转交与代理。
> 证据口径：现状结论均带 `文件:行号`，字段级论断对齐 `bone-init.sql`。

## 一、决策摘要

| # | 决策 | 一句话理由 |
|---|---|---|
| D1 | 新增 `t_claim_task`，一案 × 一任务类型 = 一条存活任务 | 案件主表已有 40+ 列且只能存"当前一个归属"，转交无留痕、无法承载队列视图 |
| D2 | 作业组真源 = IAM `iam_dept`；删除文档中的 `org_id` 依据 | `org_id` 在 DDL 与实体中**均不存在**，按它实现会建出一个永远读不到值的路由条件 |
| D3 | 分配 = 规则表 + 候选集打分 + 超时回落公共池 | 规则表达"派给哪一群人"，打分表达"这群人里谁现在有空"；回落池保证请假不卡案 |
| D4 | 转交 / 代理 / 不可用三层拆开，不自建 HR | 自建请假 = 与 HR 双写必然不一致；但必须有 fail-closed 的"此人现在不能接活"信号 |

## 二、现状与缺口（真实证据）

| 事实 | 证据 |
|---|---|
| 案件表无组织/归属/队列/优先级列，人员字段只有两个复核人 | `bone-init.sql:2717-2800`、`ClaimCase.java:174-180` |
| 「分配初审」只做状态 7→10，不记录派给谁 | `ClaimCase.java:408-411`、`ClaimCaseController.java:156-162` |
| 无任务实体，`ReviewTaskController` 自述"任务 ID 即案件 ID" | `ReviewTaskController.java:42-47` |
| 列表查询只有 `statuses`/`sourceChannel`/`page`/`size` | `ClaimPageReq.java:20-29`、`ClaimCaseRepository.java:125-144` |
| 初审与核赔共用权限码 `claim:review:write` | `ClaimCaseController.java:157-270` |
| 全库 `assignee_id` 仅命中 `mdm_issue`/`mdm_feedback`/`t_claim_blind_label_task`/`wf_task` | `bone-init.sql:2280,2328,3805,4340` |
| IAM 有 `iam_dept` 与 `iam_account.dept_id`，无代理人模型 | `bone-init.sql:80,98` |

**缺口**：无 `t_claim_task` / `t_claim_assign_rule` / `t_claim_user_agent`；无 assign / transfer / delegate 接口；无「我的待办」过滤；无任务优先级与 SLA 截止。

## 三、数据模型

### 3.1 `t_claim_task`（作业任务）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键（分布式 ID） |
| `task_no` | VARCHAR(64) | 任务号 `TK` + yyyyMMdd + id，全行唯一 |
| `claim_id` | BIGINT | 案件 ID |
| `task_type` | VARCHAR(32) | `PRE_EXAM` / `REVIEW` / `SECOND_REVIEW` / `RE_REVIEW` / `INSPECTION` |
| `status` | VARCHAR(32) | `PENDING_ASSIGN` / `PENDING_CLAIM` / `PROCESSING` / `DONE` / `TRANSFERRED` / `CANCELLED` |
| `assignee_id` | BIGINT NULL | 当前处理人（NULL = 在池中） |
| `assignee_dept_id` | BIGINT NULL | 归属作业组快照 |
| `assign_type` | VARCHAR(16) | `AUTO` / `MANUAL` / `SELF_CLAIM` |
| `priority` | INT | 越大越优先；由金额段/风险/SLA 共同计算 |
| `due_at` | DATETIME NULL | SLA 截止 |
| `claimed_at` | DATETIME NULL | 领取时间 |
| `assigned_by` / `assigned_at` | BIGINT / DATETIME | 分配人（NULL = 系统分配） |
| `alive_key` | VARCHAR(96) **生成列** | `IF(status NOT IN ('DONE','CANCELLED'), CONCAT(claim_id,':',task_type), NULL)` |
| `tenant_id` / `version` / `created_at` / `updated_at` | — | 与既有表同口径 |

唯一约束（MySQL 无 partial unique index，用生成列实现"一案件 × 一任务类型 只有一条存活"）：

```sql
UNIQUE KEY uk_tenant_task_alive (tenant_id, alive_key)
KEY idx_tenant_assignee_status (tenant_id, assignee_id, status, due_at)
KEY idx_tenant_dept_status (tenant_id, assignee_dept_id, status, priority)
```

### 3.2 `t_claim_assign_rule`（分配规则）

`id` / `tenant_id` / `rule_name` / `task_type` / `priority`（规则优先级，越大越先命中）/ `match_insurance_type` / `match_amount_min` / `match_amount_max` / `match_source_channel` / `target_type`（`USER`/`DEPT`/`ROLE`）/ `target_id` / `strategy`（`ROUND_ROBIN`/`LEAST_LOAD`/`FIXED`）/ `active_flag` / `version`。

匹配语义：全部 `match_*` 为 NULL 表示不限；同一 `task_type` 内按 `priority` 降序取**第一条命中**，不做多规则叠加（避免规则冲突不可解释）。

### 3.3 `t_claim_user_agent`（代理关系）与 `t_claim_task_transfer`（转交留痕）

- `t_claim_user_agent`：`principal_id`（被代理人）/ `agent_id`（代理人）/ `task_types`（逗号分隔或子表）/ `start_at` / `end_at` / `status`（`ACTIVE`/`REVOKED`）/ `created_by`。
- `t_claim_task_transfer`：append-only，`task_no` / `from_assignee` / `to_assignee` / `reason` / `operator_id` / `created_at`。转交不改历史，只追加。

## 四、分配求解流程

```
新任务产生（案件进入 10 / 40 / 43 / 抽检建单）
  │
  ├─① 显式指派：上一环节/主管指定了人 → 直接 PENDING_CLAIM(assignee=该人)
  │
  ├─② 命中规则：按 task_type + 租户/险种/金额段/渠道 取最高优先级规则
  │      → 展开候选集（USER 单人 / DEPT 组内具备该 task_type 权限的人 / ROLE 角色内人）
  │      → 排除：不可用（请假）、已达在办上限、与本案存在职责冲突（初审人≠审核人≠复审人）
  │
  ├─③ 候选集打分：技能匹配 > 在办量（负载）> SLA 紧迫度 > 轮询公平
  │      → 取 Top1 定为人选，落 assignee_id
  │
  └─④ 无候选 → 落公共池 PENDING_CLAIM(assignee=NULL)，任何持权人可自领
```

**派单不等于锁定**：`PENDING_CLAIM` 超过 `assign_timeout`（默认 30 分钟）仍未领取 → 自动回池；已指派人的在办量达到上限时不再接新单。

**规则配置的安全阀**：保存规则前必须做 dry-run——用近 7 天同条件案件回放命中量，命中 0 人时禁止保存（否则等于把所有案件甩进池子）。

## 五、转交、代理与不可用

| 能力 | 入口 | 语义 | 留痕 |
|---|---|---|---|
| 转交 | `POST /api/v1/claim/tasks/{taskNo}/transfer` | 单案移交，归属即时变更，原处理人失去写权限 | `t_claim_task_transfer` |
| 代理 | 主管建 `t_claim_user_agent` | 时间窗内，代理人可看到并可处理被代理人的任务；新派单可路由给代理人 | 代理关系表 + 任务分配记录 |
| 不可用 | 主管置标记 / 消费 IAM 信号 | 分配器跳过；其名下 `PENDING_CLAIM` 任务在下一扫描周期转代理或回池 | 可用性标记表（或 IAM 字段） |

**「我的待办」口径**：`assignee_id = 我` **∪** `assignee_id ∈ 我代理的人`，且 `status IN (PENDING_CLAIM, PROCESSING)`。默认视图为「我的待办」，可切「全部待办」（同租户同任务类型）。

**fail-closed 原则**：请假信号缺失时，不得默认按"在职"处理；宁可在池中多等，也不要把案件派给一个不在岗的人后在 SLA 上烧掉。

## 六、并发、幂等与一致性

- 领取/转交/分配均以 `version` 乐观锁（`@Version`）实现，冲突返回 `SC_CLAIM_TASK_CONFLICT`，不静默覆盖。
- 同一任务重复分配：命中 `uk_tenant_task_alive` 或版本冲突即拒绝，不做"后者覆盖前者"。
- 分配与案件状态迁移必须在同一事务边界内完成；先落任务再改状态，任一失败整体回滚。
- 扫描型作业（超时回池/代理切换）需单写者锁，与既有 `InspectionSamplingJob` 同模式。

## 七、查询与性能

统一 `ClaimQuery`：`keyword`（报案号/保单号/被保人哈希）、`statuses[]`、`taskType`、`assigneeId`、`deptId`、`sourceChannel`、`amountMin/Max`、`createdFrom/To`、`slaBucket`、`page/size`，返回真实 `total`。

- 「我的待办」查询走 `idx_tenant_assignee_status`，目标 P95 < 300ms（1 万在办量级）。
- 禁止 `SELECT ... FOR UPDATE`（项目架构约束），并发控制统一用 `@Version`。

## 八、分批落地

| 批 | 内容 | 验收判据 |
|---|---|---|
| 批 1 | 任务表 + 规则表 + 分配器 + 我的待办 + 统一查询 | 分配命中率 ≥ 90%；回落率可观测；我的待办 P95 < 300ms；分页 `total` 与 `COUNT(*)` 一致 |
| 批 4 | 转交 + 代理 + 不可用 + 超时回池扫描 | 转交后原处理人写操作 403；代理生效期内"我的待办"并集正确；请假标记后 1 个扫描周期内回池 |

## 九、风险与回退

| 风险 | 缓解 |
|---|---|
| 规则误配导致无人可派 | ④ 强制回落公共池 + 保存前 dry-run 命中量预览 |
| 请假信号缺失导致派给不在岗的人 | fail-closed 回池 + 主管手工置不可用 |
| 一案多任务与既有"任务 ID = 案件 ID"契约冲突 | `ReviewTaskController` 的 `{claimId}` 路径保留为兼容层，内部映射 `task_no`，不直接 BREAKING |
| 新增表拖慢案件列表 | 任务查询与案件查询分表分接口，不改 `t_claim_case` 既有索引 |

**回退**：分配器带独立开关（`t_feature_toggle` 的 `AUTO_ASSIGN`）。关闭后任务仍落表但全部进池，人工自领，不影响案件流转。

## 十、不做清单

- 不做跨租户共享池。
- 不做技能标签体系（本批用权限码 + 组归属近似，技能维度留待有真实数据后评估）。
- 不做移动端派单。
- 不把 `wf_task` 改造成理赔作业队列（跨模块耦合）。
- 不做排班表/工时管理（属 HR 域）。
