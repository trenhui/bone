## 三、治理规则（防再次膨胀）

1. **新结论优先回写，不新建文档**。写下任何分析前先回答：这条结论的真源章节是谁？能回写到 PRD/工程落地版/design 对应章节的，不许新建文件。
2. **确需新建的，当天在本文登记**，并归类到六层之一；未登记的文档不计入 SSOT，7 天内被引用 <2 次即归档。**这轮 7 天从 13 份涨到 45 份，就是缺这条规则。**
3. **一份文档只占一个 Diátaxis 象限**。Reference（契约/设计）不写叙事，Explanation（愿景/诊断）不定义口径，How-to 不复述设计。
4. **同一主题只允许一个真源**。理算类的能力现在只有 `design/理算引擎设计.md`（设计）+ `verification/理算引擎验证套件.md`（验证）+ `reviews/理算引擎诊断记录.md`（历史）三份，职责不重叠。
5. **改名或移动必须同步改引用**。`_check_xref.py` 的 `DOC_MAP` 与 `_check_numbers.py` 的 `MAIN` 硬编码了 8 个核心文件名与路径——这 8 份**不要重命名、不要移出根目录**（路径失效会让所有 § 引用判为"目标文档无此章节"，四机检全红）。

## 四、交叉引用约定（防漂移）

- 引用其他文档用 **`《文档名》 §X（标题）`** 稳定形式；禁止用产品名简写代指章节（裸 `synapClaim §X`）。
- 领域模型 / 聚合 → 引《工程落地版》§4；**契约细节（规则 ID / 对外枚举 / MVP 端点）→ 引 `delivery/04-05`**；DDL / 全量 OpenAPI / 非功能 / 时序 → 引《工程落地版》§9/§10/§11；需求 → 引 PRD。
- 金额与理算 → 引《理算引擎设计》；验证用例 → 引《理算引擎验证套件》；模型治理与反诈 → 引《风控与支付通道设计》。
- `_check_xref.py` 校验未解析的 § 引用与裸 `synapClaim §` 引用。

## 五、自动化机检

| 脚本 | 作用 |
|---|---|
| `_check_xref.py` | 跨文档 § 引用完整性（含简写列表）+ 契约-设计一致性断言（`delivery/05` 端点子集 / 枚举真源引用）+ **双向库存一致性**（`delivery/` ↔ README 索引、`生产就绪完善/` ↔ 00-总纲映射表） |
| `_check_contract_drift.py` | 契约漂移：规则 ID（落地版引用 ⊆ Rulebook 定义、同 ID 名称唯一）、对外枚举双向、错误码集合、表清单对位、**C7/C8 分层真源**（`design/` `verification/` 的规则 ID ⊆ Rulebook、表名 ⊆ 工程落地版） |
| `_check_ddl.py` | DDL 可执行性：主键唯一 / 列名唯一 / 索引列已声明 / `) ENGINE=InnoDB` 收尾 / append-only 禁注入变更列 / 建表数 = 35 |
| `_check_numbers.py` | 数值与口径回归：FORBIDDEN（已定性错误的表述零命中）+ REQUIRED（关键口径在位）+ ADR 可追溯性；**当前 49 / 46**，含「性能/SLO 唯一真源」锁值（§11.2 的 5s/60s/500ms/30s/3s 五值与 99.99% 档位前提） |

**扫描范围**：根目录 + `delivery/` + `design/` + `verification/`。`reviews/`、`生产就绪完善/`、`archive/` **不纳入机检**——前者是冻结的历史记录，后两者是伴随完善包与归档件，纳入会导致"改历史文档才能过 CI"。

**门禁范围与真源范围必须同步**（P9 教训）：文档分层后，`design/理算引擎设计.md`、`design/风控与支付通道设计.md`、`verification/理算引擎验证套件.md` 升为理算/风控主题的唯一真源，但四道机检原本只认根目录三份文件——真源写错也不会有任何拦截。故本轮同步做了两件事：`_check_xref.py` 的 `DOC_MAP`/`REF_RE` 纳入 4 个新真源短名（否则「见《理算引擎设计》§8」会**静默漏检**而非报错），`_check_contract_drift.py` 新增 C7/C8。两处均以"注入错误必红、还原后必绿"的负向验证确认非假绿。
