# 文档治理规约

> 本文是**强制规则**，不是建议。规则的作用是防住同类事故复发：本目录曾在 7 天内从 13 份涨到 45 份，原因就是"没有登记与收敛的强制点"。
>
> 机检脚本按本文实现；若发现规则与脚本行为不一致，**以脚本为准并立刻修本文**（规则写在空中等于没有）。

## 一、命名约定

| 对象 | 规则 | 理由 |
|---|---|---|
| 目录 | `NN-<英文语义>`，两位序号 = 层号 | 目录号=层号，路径即能推出权威性 |
| L1–L3、L5 的核心文档 | `synapClaim 智能理赔平台-<类型>（<修饰>）.md` | 全仓统一品牌；修饰符进括号 |
| L4、L6、L7、L8、L9 内文档 | **短名**（目录已含分类，不再套长前缀） | 避免 `synapClaim 智能理赔平台-` 重复占宽 |
| 交付包 / 上线分册 | `NN-<主题>.md`，编号连续且**必须在索引表登记** | 编号即对外编号，缺号=交付物缺失 |
| 品牌 | **Synap（思纳普）** = 公司；**synapClaim** = 产品 | 两者不混用 |
| 设计原则 | `synapClaim Pn`（P1–P6），定义见 `AI 技术方案` §1.2 | 引用须带编号与出处 |

**禁止**：中英文混排目录名、全角括号目录名（已清理 `08-go-live/` → `08-go-live/`，因为全角括号在 URL / shell / 工具链里都要转义）、文件名错别字（已修 `智理理算` → `智能理算`）。

## 二、登记即 SSOT

1. **新建文档必须先登记** `docs.manifest.json`，否则 `tools/_check_manifest.py` 判红（未登记 = 不计入 SSOT）。
2. 登记字段的最低要求：`id`（稳定标识，不随文件名变）、`path`、`layer`、`diataxis`、`summary`（一句话"什么时候该读它"）、`authority`（它拥有哪些主题）、**`role`**、**`currency`**（见 §三之二）。
3. **7 天内被引用 < 2 次**的文档，下一轮整合时归档或合并——这条是针对上一轮膨胀的直接对策。
4. 删除文档时同步删 manifest 条目；**不要留"指向不存在路径"的条目**（符号基线里已有 1 条 `ClaimSphere …` 的历史欠账，属反面教材）。

## 三、权威与时效：让 AI 判得准

### 三之一、一篇一主题，一主题一真源

1. **一份文档只占一个 Diátaxis 象限**：Reference（契约/设计）不写叙事；Explanation（愿景/诊断）不定义口径；How-to 不复述设计。
2. **同一主题只允许一个 authority 命中**。理算类现在是三份、职责不重叠：`04-design/理算引擎设计`（结构）+ `03-contract/…V1`（业务口径）+ `06-verification/…验证套件`（验证）。
3. **新结论优先回写，不新建文档**。动手写之前先回答："这条结论的真源章节是谁？"能回写就回写。

### 三之二、`role` / `currency`：写进工件本身，而不是只写在地图里

**为什么需要**：人类会先读 README 再决定读哪份；**AI 不会**——AI 靠相似度检索，容易把"过程证据"和"待合入草案"当成"当前设计"。若权威与时效只存在于一份人读的地图里，AI 检索到的片段就没有任何信号区分"现行契约"与"某时点的取证"。

因此这两组字段必须写在**可被检索的工件本身**（manifest 条目 + 文档 front-matter 两处）。

| 字段 | 取值 | 含义 | AI 应当如何处理 |
|---|---|---|---|
| `role` | `ssot` | 当前权威真源 | 可引用为事实 |
| `role` | `navigation` | 导航/治理元文档 | 用于路由，不含业务口径 |
| `role` | `draft` | 待合入草案（如 go-live 01–13） | 仅作计划/提案，不当现行契约 |
| `role` | `evidence` | 冻结的过程证据（L9/L10） | 仅回答"为什么/历史" |
| `role` | `tooling` | 工具/参考实现（oracle） | 非产品代码，不当设计引用 |
| `role` | `guide` | 操作指南（可执行步骤 / 逐项裁定台账，不含现行契约） | 按步骤执行；其中的状态与数值以对应 `ssot` 为准，不据此宣称能力已具备 |
| `currency` | `current` | 现行 | 默认可引用 |
| `currency` | `draft` | 草案 | 仅在明确询问规划时引用 |
| `currency` | `frozen` | 冻结 | 只作历史取证，**禁止当作现状** |
| `superseded_by` | 目标文档路径 | 本文档已被哪份撤销/修正 | 读到它 ⇒ 必须去读取代者 |

**填写规则**：

- `role` 由**文档承担什么职责**决定，不由它在哪一层决定（L8 的总纲是 `ssot`，同层分册是 `draft`）。
- `currency=frozen` 必配 `role=evidence`（或 `tooling`）；有 `superseded_by` 时必须同时写 `supersede_note`（一句话说清被撤销的**具体结论**，而不只是"已被取代"）。
- **每份文档的 front-matter 必须与 manifest 逐字段一致**（`doc_id` / `role` / `currency`），由 `tools/_check_manifest.py` 的 M9 强制——front-matter 是绕过 manifest 直读单文件时 AI 判断"证据还是现状"的唯一依据。

### 三之三、AI-INDEX.md 是生成物，不是手写文件

- `AI-INDEX.md` 由 `tools/_gen_ai_index.py` **从 manifest 派生**，禁止手工编辑；改了 manifest 必须重跑生成器。
- **路由表（`aiRouting`）的真源在 manifest 里**，不在生成器代码里，也不在 AI-INDEX 里——否则"路由"会变成第二处需要手工同步的地方。
- 门禁 M7 校验 AI-INDEX 与 manifest 派生结果**逐字节一致**；不一致即红，提示 `python3 tools/_gen_ai_index.py` 修复。

## 四、交叉引用约定

- 引用格式：**`《文档短名》 §X（标题）`**。短名取自 manifest 的 `shortNames`。
- 禁止裸产品名代指章节（形如「产品名 + §章节号」的写法无效）——机检会报"遗留裸引用"。
- **短名一旦登记就进入 § 校验**：新增短名等价于给全仓加了新断言，先在本地跑 `tools/_check_xref.py` 再提交。
- 正文里提到文件路径时，**必须用真实相对路径**（如 `../03-contract/…md`）；`tools/_check_manifest.py` 会校验带已知前缀的路径 token 是否真实存在，防止"文中链接指向已删除文件"这种静默腐化。

## 五、机检（本目录自带；统一入口 `check_all.py` / 9 条不变量 M1–M9）

> **统一入口是 `tools/check_all.py`**（2026-11-08 起为唯一真源）：`python3 tools/check_all.py` 一次跑完**登记表里的全部步骤**（各道主判据 + 判据自证 + 附加校验；步数见 `--list`），`--self-test` 只测接线判据、`--list` 列登记项。此前 §六 第 7 条是 18 条手写 `&&`，实测「规范写的」与「实际跑的」已经漂移（校准内核两道被漏跑），且 **9 道门禁在 CI 中零调用**。**新增/删除 `tools/_check_*.py` 必须同时改 `check_all.py` 的两张表**（`GATES`/`EXTRA` 执行清单 + `EXPECTED_CALLS` 期望清单），G1–G6 会判红。

> **为什么要两张表**：首版只有一张执行清单，**删掉其中一行（如 `_check_ddl.py --self-test`）脚本名集合不变、判据仍全绿**——与 P22「覆盖率静默归零」同族。故 `EXPECTED_CALLS` 独立定义每个脚本必需的 argv 组合，与执行清单做键集合与调用组合的**双向**对账（G5）；拿登记表验登记表是自证，没有判别力。

**CI 接线**：`.github/workflows/synap-claim-docs.yml` 在 push / PR（`dev`/`main`/`master`）与 `workflow_dispatch` 时跑 `--self-test` + 全套。**刻意不设 `on.paths` 过滤**：门禁输入不止文档，还包含 `claim-ruleset.json`、`ClaimErrorCodes/ClaimErrors.java`、前端 `zh-CN`/`en-US.json`、oracle CI workflow 与迁移脚本；白名单漏列一项就会让「改了资产但 CI 不触发」静默放过。该 workflow **不进 `scripts/check.sh`**（pre-commit 只认已 staged 的 `.java`，删码/未 stage 是盲区），两者互补而非替代。另按最小权限加 `permissions: contents: read`、`concurrency` 取消同分支堆积、`timeout-minutes: 10`。改后 `scripts/check-gate-liveness.py --strict` 仍 exit 0。

**接线自身要被守护（G6）**：workflow 的分支集合须 ⊇ `ci.yml`、两条 `run` 须分别是 `check_all.py --self-test` 与全套、不得出现 `paths:` 白名单、须保留最小权限；判据是 `check_all.py` 的纯函数 `ci_wiring_errors()`，5 个文本注入反证（删文件 / 删自测步 / 加 paths / 去 dev / 改权限）全部判红，全程不写文件。

> **不可机械验证的边界，如实登记**：**CI 无法守护「自己被删除」**——workflow 一旦被删，本判据也不会被 CI 触发；只能在本地执行、其它 workflow 运行时或 PR 审查中发现。这与 `scripts/check-gate-liveness.py` 对「根入口是否被触发」的标注同口径。要进一步收紧，须把该 workflow 纳入 CODEOWNERS 或仓库级 workflow 存活清单（属平台治理，不在本目录权限内）。

**一道不进门禁的体检（门禁仍是 9 道）**：`tools/_audit_ddl_vs_db.py` 把 §9.5 的 `CREATE TABLE` 与 `bone` 库 `information_schema.columns` 做**列级对账**，区分「完全一致 / 仅审计列差异 / 含业务列差异 / 活库无同名表」。实跑带 **ratchet**（按表集合只减不增，新增差异 exit 1）；`--self-test` 5 个探针守护解析与判据（含「`PRIMARY KEY` 不得被当列名」「数量不变但换表仍被抓」）。

> **为什么不接进 CI**：它依赖活库连接，CI 无 DB。做成必过门禁会让「没起数据库」等于构建失败，与「误报比漏报更致命」同族。故定位为**人工可复跑的 report-only 体检**：`BONE_DB_PASSWORD=… python3 tools/_audit_ddl_vs_db.py`，DB 不可达时 **exit 2 明确报错**，绝不静默输出「无差异」。它的存在是为了给 `_check_ddl.py` 划清边界：**后者的绿只代表「文档内部自洽」，不代表「与活库一致」**——两道检查互补，不能互相替代。2026-11-07 首次全量体检：26 张表中 5 张列一致、7 张仅审计列差异、**14 张含业务列差异**，全量结论在 §9.0（4）、**逐张定性与整改台账在 §9.0（5）**。

校准内核机检（`_check_ai_native_calibration.py`）的**定位边界**：它只证明「内核真实、可证伪」，**不判定飞轮是否已接线到生产链路**，也不判定 L3 达标。配套判据是 `tools/_ai_native_readiness.py` 的 `FLYWHEEL_DOWNSTREAM` 三要素强校验：校准实现类存在、盲标样本源有生产调用、校准计算有生产调用，三者同时成立才判 SATISFIED；`import` / 注释 / 单测均不算接线，脚本自带「摘除校准计算生产调用（import 假绿回归钉子）」等负向探针。三要素齐备只能代表「可编码消费方与调用链已就位」；真实闭环仍须由独立盲标样本、冻结集回归与运行期覆盖证据给出，静态事实给不出，绝不因文件存在就宣称达标。

**自身接线**（避免校准内核机检变成新的孤儿门禁）：`scripts/tests/test_check_ai_native_calibration.py` 11 例通过 `[42/59] 门禁脚本自身单元测试` 被 pre-commit 自动发现，逐条验证 C1–C5 精确归因、合规正例、扫描失效闸与负向探针有效性；判据被改成恒绿/恒红、锚点被删、扫描路径漂移都会在那一步判红。注意区分两层：`check.sh` 主流程**并未调用**该机检本体（本目录自带脚本一贯不进 `check.sh`，`R4` 也只扫 `scripts/check-*.py`）；被守护的是**机检自身的判据**，不是「每次提交都扫一遍校准内核」。人工跑全套按 §六 第 7 条（现为 `python3 tools/check_all.py` 单命令）；CI 侧另由 `.github/workflows/synap-claim-docs.yml` 在每次 push/PR 跑同一入口——「不进 `check.sh`」只约束 pre-commit，不约束 CI。

**治理端点接线（6 个只读端点）**：`/api/v1/claim-ops/` 下为 `ai-readiness` / `ai-runtime-health` / `ai-calibration/report` / `ai-rollout` / `ai-rollout/drill` / `ai-provider-probe`（第 6 个为本轮新增）。三条口径在此登记，避免下游文档各自复述：

- 证据窗口单一真源：前端 `governanceWindow()` 与 E2E `EVIDENCE_WINDOW` 同算法——`to = ceil(now / 86400000) * 86400000`、`from = to - 30 * 86400000`（UTC 日界 30 天，同日恒定、长度恰 30 天且小于端点 31 天上限）；字符串统一为秒级 ISO（`...Z`，无毫秒），与后端 `Instant` 回显逐字一致——逐字一致靠同一份规范串，不靠比较时再归一化。E2E A 组断言后端回显窗口逐字一致，B 组断言治理面板声明窗口逐字一致。
- `ai-provider-probe` 每次真实消耗一次 provider 用量，只允许用户在治理面板显式点击触发；默认加载、刷新与轮询均不得发起请求（E2E 用 `page.on('request')` 断言进入页面 0 次、点击后 1 次）。
- `tools/_ai_native_readiness.py` 的 `RUNTIME_MODEL_COVERAGE` 为**四条件**：`provider_env` 已配 **且** `runtime.probeVerdict == REACHABLE` **且** `runtime.probeEvidence` 证据束自洽 **且** `nodes>0 / rate>0 / participated>0`。第二条件对应 `AI技术方案 §11.7` 记录的「探活绿灯、业务全量降级」事故——配了环境变量 ≠ 上游通了 ≠ 输出契约对；判词由 E2E 同一次手动探活响应写入产物，缺失或非 `REACHABLE` 一律 fail-closed，绝不把「没测过」当成「通了」。第三条件堵住第 11 轮 GAP 的「三要素同源可伪造」：环境变量、裸判词、参与率都能手写，故证据束须含 `httpStatus=200`、`model` 非空、`provenance=PROVIDER`、`promptTokens>0`、`completionTokens>0` 与合法 `requestId`，且由 E2E 从同一次探活响应透传；采集侧尚未产出这些字段时产物为 `null`，按 `PROBE_EVIDENCE_*` 阻断，绝不回落到裸判词或编造 token / requestId。reason 按 `PROVIDER_NOT_CONFIGURED` > `PROBE_NOT_REACHABLE` > `PROBE_EVIDENCE_*` > `MODEL_PARTICIPATION_ZERO` > `ADMITTED` 归因，detail 附 `providerConfigured=` / `probeVerdict=` / `probeEvidence=`；`--self-test` 的 stay 类与伪造鲁棒性探针、`scripts/tests/` 下表征测试（含「摘除任一条件须被自测判红」与证据束源码变异）守护该判据；条数以脚本为准，文档不写死计数。窗口统一、参与率非零或伪造判词都不改变 `l3Claimable=false`。

**成熟度档位（第 11 轮收敛）**：`tools/_ai_native_readiness.py` 的 `current_level()` 描述**运行态**，不再只看两个配置态判据。`PROVIDER_CONFIGURED` 与 `PERCEPTION_MODEL_DRIVEN` 全齐、但 `RUNTIME_MODEL_COVERAGE` 非 SATISFIED 时，一律回落 `L0（配置态就绪但运行期未达标：<reason>）`；四条件齐备且感知由模型驱动才判 L2（三要素伪造但缺证据束须回落 L0）。`scripts/tests/test_ai_native_readiness_flywheel.py` 的 `MaturityLevelTest`（含「退化成只看配置态」变异）与 `--self-test` 第四类「成熟度档位」探针共同守护该约束；条数以脚本为准。E2E 在最终产物落盘后**再跑一次复核器做终态对账**，堵住 C 组中途快照之后产物被污染无人复核的盲点；产物新增 `runtime.probeVerdictCapturedAt` 与 `runtime.finalReadinessSnapshot`。

**M1–M9 速查**（细节见各脚本 docstring）：

### 六之二、迁移脚本变更纪律（新增 2026-11-07）

> **催生这条的真实事故**：`scripts/migration/` 从 `0058` 到 `0122` 陆续给理赔表加列（`confidence_source` 0121、`manual_review_required` 0115、`mapping_version` 0102、`hospital_code` 0079 …），**没有任何环节要求同步 `工程详细设计-落地版` §9.0**。2026-11-07 列级体检一次查出 14 张表含业务列差异、11 张可追溯到已发迁移——不是谁写错了，是**缺一条同步纪律**，漂移自然累积。

**判据为什么用「不增加」而不是「归零」**：14 张是存量欠账，一次性归零不现实；ratchet（只减不增）让纪律**今天就能生效**，同时把存量挂在台面上。与 §七 的 `BASELINE` 是同一套做法。

## 七、方案文档结构规范

### 七之一、为什么需要这一节

§一–§六 管的是「文档怎么登记、怎么引用、怎么判时效」，**没有一条管「一份方案文档内部该长什么样」**。后果是实测到的：8 份 `diataxis=reference` 的方案/契约文档，章节数从 9 到 17 不等，同一层级的文档骨架各不相同——

| 文档 | 节数 | 读者要找的东西在哪 |
|---|---:|---|
| `总体技术方案` | 12 | 结论在 §0、待决策在 §12 |
| `理算引擎设计` | 14 | 决策在 §1、不做清单在 §12、**§4 自标"已被 V1 取代"却仍在** |
| `工程详细设计-落地版` | 16 | 无摘要、无风险、无待决策 |
| `AI技术方案` | 17 | 同上 |
| `BONE-AI能力依赖图谱` | 10 | 无不做清单、无待决策 |

**这不是篇幅问题，是结构不可预期**：读者每换一份都要重新找"结论在哪、风险在哪、要不要我拍板"。对 AI 更糟——检索到某一份的片段时，无法判断它是不是决策所需的那几节。

### 七之二、两档节：必选四节 / 推荐五节

**必选四节**——缺任一节，本文不构成可决策的方案文档：

| 节 | 必须回答的问题 | 缺了会怎样 |
|---|---|---|
| **决策摘要** | 不读全文，能否拍板？ | 强制全文阅读，决策者的时间成本最高 |
| **风险与回退** | 走错了怎么办、怎么退？ | 那是承诺书，不是方案 |
| **不做清单 / 边界** | 明确**不**做什么？ | 范围蔓延的第一道闸失守 |
| **待决策** | 哪些必须由人拍板？ | 隐含决策 = 事后返工；没有也要写"无" |

**推荐五节**——按文档职责取舍，缺了不判红但要说明理由：

| 节 | 必须回答的问题 |
|---|---|
| 目标与约束 | 要解决什么、不能违反什么（合规/技术/组织） |
| 现状与差距 | 现在什么样、差在哪（**必须带证据**） |
| 方案 | 怎么解决（可分主题展开） |
| 关键决策 | 为什么这样选、否掉了什么（ADR 摘要） |
| 质量属性与验收 | 怎么算做对了（可测口径，不是"体验良好"） |

**标题必须写成职责短语**。`## 总体情况`、`## 其他`、`## 补充说明` 一律不合格——标题是读者与 AI 唯一的定位锚点。允许同义措辞（`待决策` ≈ `待拍板` ≈ `待澄清`），但必须在 §0 摘要里给出章节导航。

### 七之三、与业界模板的对应关系（为什么是九节，不是 arc42 的十二节）

本规范是 **arc42 的裁剪 + C4 的视图约定 + ADR 的决策颗粒度**，不引入新体系：

| 本规范 | arc42（12 节） | C4 | ADR（Nygard） |
|---|---|---|---|
| 0 决策摘要 | §1 目标 + §4 方案策略（合并压缩） | — | — |
| 1 目标与约束 | §2 约束、§3 上下文与范围 | L1 系统上下文 | — |
| 2 现状与差距 | §1 引言与目标（现状部分） | — | — |
| 3 方案 | §5 构件视图、§6 运行时视图 | L2 容器 / L3 构件 | — |
| 4 关键决策 | §9 架构决策 | — | 决策 + 状态 + 后果 |
| 5 质量属性与验收 | §10 质量需求 | — | — |
| 6 不做清单 | §2 约束（反向）/ §4 策略中否决项 | — | 否决的备选方案 |
| 7 风险与回退 | §11 风险与技术债 | — | 后果（负面） |
| 8 待决策 | §9 中 status=proposed 的条目 | — | 状态为 proposed |

**裁剪理由**：arc42 的 §7 部署视图、§8 横切概念、§12 术语表在本仓已有独立承载（部署见 `07-delivery`/`08-go-live`，横切见《工程详细设计-落地版》§3，术语见各文档 front-matter 与 `AI-INDEX`），**再复制进每份方案文档等于制造多个真源**——这正是 §三之一「一主题一真源」要防的。

### 七之四、写法铁律

1. **断言现状必须带证据**：类名、表名、行数、文件路径之一。禁止「目前较为完善」「已基本实现」这类无指向判断。
2. **数字必须实测**，并在首次出现处注明口径与测量时间。禁止从其他文档转抄未经核对的数字。
3. **约束强度用「必须 / 应当 / 可以」**（RFC 2119 的中文对应）。凡写「必须」，必须可被机检或测试验证；不可验证的降级为「应当」。
4. **引用外部实践必须可核**：产品名 + 组件名 / 规范编号（如 `arc42 §9`、`ISO 834`、`Guidewire Calculation Engine`）。禁止「业界最佳实践表明」这类无主体引用——本目录已因此踩过坑（曾把保费 `rating` 错挂到理赔引擎上）。
5. **同一文档内不得有两套口径并存**。已被取代的章节必须删除或整体移入 `09-records`，不得保留正文再加一句「本章已被 X 取代」——这会让检索命中旧口径，而检索不带上下文。

### 七之五、适用范围与豁免

适用于 manifest 中 `layer ∈ {L3, L4}` 且 `diataxis=reference` 且 `role=ssot` 的文档。

**豁免**（脚本内登记，附理由）：纯清单类文档不承担方案语义，只要求「决策摘要 + 待决策」两节。当前唯一豁免项：`03-contract/智能理算引擎业务规则V1.md`（规则 ID 与公式清单，本身就是待执行条目，没有"方案/风险/回退"可言）。

**机检**：`tools/_check_doc_structure.py`，判定用 **ratchet（只减不增）**：

- 必选四节缺失，且不在 `BASELINE` 内 → **判红**（exit 1）；在 `BASELINE` 内 → 只提示「存量欠账」
- 补齐某份后**必须从脚本内 `BASELINE` 删除对应条目**，脚本会提示 stale；留在基线里不会判红，但会永远显示「待补齐」
- 推荐五节缺失只提示，不判红
- `--self-test` **11 个探针**守护判据（含「豁免不等于放行」「基线外新增必红」「补齐全绿须转 stale」「基线清空后不再有 stale」）

**为什么不直接对存量判红**：发布时 5 份文档存在存量缺口，上线即红会让门禁从第一天就不可用，作者第一反应是关掉它——与「误报比漏报更致命」是同一条教训。ratchet 让门禁**当天就能拦住新增不合规**，同时把存量欠账显式挂在台面上，而不是假装不存在。
