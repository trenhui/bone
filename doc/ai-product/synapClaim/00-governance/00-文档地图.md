### 进 L3 的判据（可判定，不看文档自称）

一份文档放 L3 当且仅当**满足其一**：

1. 被 `tools/_check_ddl.py` 或 `tools/_check_contract_drift.py` 当作判据真源读取（§9.5 DDL 集合 / 规则 ID / 对外枚举 / 错误码 / 表清单）；**表数不在治理文件里登记**——D7 已改为集合对账，任何写下「N 张表」的地方都会变成第 N+1 个待同步副本；
2. 承载 DDL、OpenAPI、错误码集合、非功能指标（SLO/容量/安全）之一；
3. 承载业务规则口径（责任 11 要素、公式、免赔、控额），且带可信度标记（〔定〕〔推〕〔疑〕〔缺〕）。

**不满足以上三条的一律放 L4**，即使它有唯一真源、即使它写满契约式表格。设计原则、评测体系、模块映射属于**设计**——它们回答"为什么这样"，可以被推翻；L3 回答"照这个写"，改了要过门禁。

> **本条由一次真实归类错误催生**：`AI技术方案` 原在 L3，但它 67% 的体量是设计原则（§1，406 行）与评测可观测（§11，611 行），文首自己也写着「本文不定义契约」。它在 L3 的直接后果，是让"03-contract 只放契约"这条规则失效——读者按目录判断权威性时会误判。

## 三、权威边界（最容易读错的四处）

1. **L3 业务口径 vs L4 实现结构**：`智能理算引擎业务规则（V1）` 里标〔疑〕〔缺〕的 Q-01–Q-15，**澄清前不得据以实现**；实现结构与算法以 `理算引擎设计` 为准。两侧冲突时先澄清 Q 项再收敛，**禁止单方面改一侧**。
2. **L9 是证据，不是现状**。`impl-log/14` 说过"额度服务 0 调用方"，`15` 已撤销该判断——**不要拿记录当配置说明书**。要"现在是什么样"，读 L3/L4 或直接读代码。
3. **L8 尚未合入**。`01`–`13` 是对契约的**伴随完善草案**，只有被折叠进 L3 对应章节后才具备契约效力；引用它们时必须写明"草案，待合入"。
4. **REF 不是设计，也不并树**。`doc/ai-product/synap-claim-oracle/` 是可执行参考实现（双轨 oracle），`role=tooling` / `currency=frozen`——**不得被引用为产品设计**；也**不整合进 synapClaim 文档树**（独立 CI + 双轨独立性，见 §一 REF 行）。它的语义已在《理算引擎设计》§1–§13 承载，且 §1 开头有统一时态横幅；**读 oracle 语义去那份文档，读可执行代码去独立工程**，两者不必物理合并。

## 四、实现现状与文档冲突时

| 冲突类型 | 裁决 |
|---|---|
| 契约（DDL / 接口 / 枚举） | 以 L3/L7 为准；**代码与契约不一致即为缺陷**，登记整改项，不许反向改文档迁就代码 |
| 业务口径 | 以 V1 规则为准；V1 有〔疑〕项时先澄清 |
| 实现细节（类名 / 分层 / 事务边界） | 以 `bone-apps/synap-claim` 代码为事实；文档滞后按缺陷处理 |
