## 1. 诊断方法：先取证，再下结论

复用项目既有取证铁律（「全绿」≠ 有判别力；「注释宣称 X」≠「代码做了 X」）：
1. 对每个怀疑项写一段**最小可运行输入**，打印引擎实测值 + 业界正解；
2. 若两者不一致 → 判定为缺陷（附实测数值，不用形容词）；
3. 修复后把该输入固化为**回归探针/场景用例**，并配一个「关掉护栏必红」的变异开关。

### 1.1 实测取证表（修复前）

| 编号 | 输入 | 引擎实测 | 业界正解 | 判定 |
|---|---|---|---|---|
| D1 | 费用 20000 / 比例 80% / 年免赔 10000 | **6000** | **8000** | ❌ 免赔额错序（系统性少赔） |
| D2 | 费用 1000 / 发票免赔 5000 / 比例 80% | **−3200** | **0** | ❌ 产出负赔付金额 |
| D3 | 同一案件重复提交两次 | 首次 6000 → 重复 **16000** | 两次均 6000 | ❌ 幂等缺失，免赔双计 |
| D4 | 同 policyId、不同 tenant，年限额 1000 | T1=1000 / T2=**0** | 各 1000 | ❌ 跨租户额度串用 |
| D5 | 比例 95% + 已确认 AI 加成 10% | **1050** | **1000** | ❌ 比例破 100%（超赔） |

> D1–D4 属 **P0**：直接造成少赔/超赔/负金额/数据隔离违规，任一进入生产都是资金事故级缺陷。
> 这四项恰好都发生在「看起来最基础的语义」上——正是「文档写对了、代码没做对」的典型。

## 2. 缺陷清单与根因（含为什么是问题）

### P0

| # | 缺陷 | 根因 | 业务后果 | 业界基准 |
|---|---|---|---|---|
| **D1** | 免赔额**后置于**赔付比例：实现为 `赔付额 − 免赔`，而非 `(费用 − 免赔) × 比例` | 把「保单级年度免赔（作用于费用基数）」错当成「赔付额减项」 | 少赔 25%（2 万/80%/1 万免赔：6000 vs 8000），规模化即巨额少赔 + 客诉 + 监管风险 | 泰康/平安/百万医疗条款：免赔额从**符合约定的医疗费用**中扣除后再按比例给付；Guidewire 计算引擎 deductible 作用于 eligible amount |
| **D2** | 免赔额大于费用额时产出**负赔付** | `(current − deduct) × ratio` 后未做非负钳制 | 负金额进入付款/对账链路，账单异常、清算失败 | 保险金额不得为负是**类型层不变式**（金额值对象即应保障，而非靠调用方自觉） |
| **D3** | 重复提交/重算**双计**年度免赔与限额 | 无幂等键，`commitUsage` 每次无条件累加 | 6000 → 16000（超赔 2.7 倍）；重试/双提交/消息重投均会触发 | 幂等命令模式（Idempotency-Key）；金融交易必须幂等（PCI/SOX 对账要求） |
| **D4** | 累计键与控额键**不含 tenantId** | 键仅用 `policyId@periodKey` | 不同租户同保单号互相占用额度 → 数据隔离违规（SaaS 红线） | 多租户隔离（ADR-4 租户主键）；ACORD 额度按保单归属隔离 |

| # | 缺陷 / 缺口 | 为什么是问题 | 业界基准 |
|---|---|---|---|
| **D5** | 赔付比例可破 100%（AI 加成后 95%+10%=105%） | 超赔；AI 建议本就需护栏，护栏本身再无上限即双重失守 | 赔付比例 ≤100% 为条款硬上限；AI 仅输入侧 + 类型护栏（`AiSuggestion`/`Confirmed`） |
| **D6** | **不可获利原则缺失**：社保统筹支付 / 其他保险已赔未从可赔基数扣除 | 被保险人因理赔获利（1 万费用、统筹付 5000，仍赔 8000 → 合计 13000 > 实际支出），违背损失补偿原则，且是重复理赔的常见通道 | 保险法损失补偿原则；ISO「Other Insurance」条款；医保分割后仅对自付部分理算（普康普康宝内置医保三大目录即为此） |

|---|---|---|---|

## 3. 修复方案（已执行）

### 3.1 金额语义

| 修复 | 做法 | 回归证明 |
|---|---|---|
| **免赔额作用于费用基数** | 年度免赔在「可赔基数」上按各费用行基数比例分摊（末行取残差，保证守恒），再乘比例。开关 `deductibleBeforeRatio` | 场景：20000/80%/1 万 → **8000**；探针 **P16**（关掉开关 → 得 6000 → 红） |
| **负赔付钳零（类型层）** | `Money.clampNonNegative()` 在取整前强制；非开关（永不关闭） | 探针 **P3b**：费用 1000/免赔 5000 → **0** |
| **赔付比例 ≤100%** | `Money.clampMax(100)`，AI 加成后生效。开关 `clampRatioAt100` | 探针 **P15**（关掉 → 1050 → 红） |

### 3.2 额度与并发

| 修复 | 做法 | 回归证明 |
|---|---|---|
| **幂等键** | `claimId + 公式指纹 + 输入指纹`。命中则返回首次结论，不重复占额、不双计累计。开关 `applyIdempotency` | 探针 **P12**（关掉 → 150 → 900 → 红）；场景 **S19** |
| **租户隔离键** | 累计键/控额键统一加 `tenantId@` 前缀。开关 `tenantScopedKeys` | 探针 **P13**（关掉 → T2 得 0 → 红）；场景 **S20** |
| **乐观锁累计** | `AccumulationPort.commitUsage(..., expectedVersion)` → `COMMITTED / DUPLICATE / CONFLICT`；`CONFLICT` 抛 `ConcurrentAccumulationException` 转人工 | 探针 **P18**：stale 版本 → CONFLICT；同 claimId 重复 → DUPLICATE；引擎对 CONFLICT fail-closed |

### 3.3 业务原则与风控

| 修复 | 做法 | 回归证明 |
|---|---|---|
| **不可获利原则** | `ClaimContext.thirdPartyPaid`（社保统筹 + 其他保险已赔）先从可赔基数扣除，记入 `thirdPartyApplied`，`explain` 标注 `PRINCIPLE_INDEMNITY`。开关 `applyIndemnityPrinciple` | 探针 **P14** + 场景 **S17**：(10000−5000)×80% = **4000**，且 赔付+已付 ≤ 总费用 |
| **风控 fail-closed** | `ClaimContext.fraudHold` → 结论 `HOLD`，不出金额、**不调用占额端口**、不消费累计，发 `FRAUD_HOLD` 事件 | 探针 **P17**（`reserveCalls == 0`）；场景 **S18** |

### 3.4 直付预授权

| 修复 | 做法 | 回归证明 |
|---|---|---|
| **保守比例授权** | 授权额 = min(预估−剩余免赔, 剩余年限额, 责任限额, 计划剩余) × **最低赔付比例** | 场景 **S16**：15000@80% → 授权 **12000**（旧为 15000，差额 3000 需追收） |
| **生命周期** | `PreAuthPort`：`hold(ttl)` → `capture(实际额，剩余自动释放)` → `void(撤销)` → `isExpired` | 场景 **S15**：hold 5000 → capture 3000 → 冻结归零 → void 后失效 |

### 3.5 状态机

`SettlementStatus` 补全为 **PAY / PARTIAL / REJECT / HOLD**；判定规则：
拒赔 → REJECT；有费用级拒赔或被限额削减或当期应付 0 → PARTIAL；否则 PAY；风控 → HOLD。
整案拒赔/风控挂起**均不消费控额维度**。

## 4. 引擎编排（修复后的权威顺序）

```
0  幂等键命中？ → 返回首次结论（不占额、不双计）
0' 风控 P0？    → HOLD：不出金额、不占额、发事件、转人工
1  C4  TracePort.record（快照审计）
2  C2  策略求值 → 产出「可赔基数 + 比例 + 理算层面免赔」
3  不可获利：第三方已付（社保统筹/其他保险）从基数扣除（按比例分摊，守恒）
4  年度免赔：作用于**费用基数**，跨案累计剩余，按比例分摊（守恒）
5  赔付比例 → 理算层面免赔 → 取整 → 负赔付钳零
6  多维度 min 控额：责任 / 费用子限额 / 计划 / **年度限额**（年度限额即一个控额维度）
7  C11 累计提交（乐观锁 + 幂等）→ 占额 → Outbox 事件
```

> **为什么这样排**：3 与 4 都在「比例」之前，因为**免赔额与不可获利的标的是"费用"而非"赔款"**；
> 6 把年度限额并入 min 聚合，使「行级金额之和 == 实际应付」恒成立（归因完备），避免"总额被砍但明细不变"的对账裂缝。

## 6. 已知限制与未做项（诚实披露）

1. **第三方已付归因粒度**：当前按可赔基数比例分摊；生产应按费用类别归因（社保内优先核销），需条款确认。
2. **年度限额截断顺序**：按费用行顺序先到先得，未按比例摊薄；多费用类型并存时需条款确认优先级。
3. **多保单分摊（S13）仅独立理算**，未实现 ISO 834 的 pro-rata by limit / 等额分摊 —— 需产品确认条款后另开工。
4. **生产落库未做**：幂等存储、累计、快照在参考实现为内存实现；生产需幂等唯一键、`@Version` 乐观锁、快照表。
5. **无真实并发压测**：P18 仅验证乐观锁契约与 fail-closed 行为（未做数据库级并发验证）。

| **N6** | 费用含丙类 500（拒赔） | 拒赔行 `deduct=500` | `deduct=0` | P1 告知书误导 | 拒赔行 `base=0` → `origin−base` 把原始费用记成"免赔额"。客户告知书会写"您的免赔额 500"，实际是"该项目不在目录内"，语义错误且易引发投诉。 |

### 9.2 N10 为什么最危险：它是被测试数据掩盖的假绿

N10 的根因极其简单（`LimitControl` 把 `0` 当成一个真实限额），但**第一轮 20 个场景用例全部通过**——
因为构造测试数据时，所有 `feeSubLimit` 都"恰好"传了大额（`1_000_000`）。
**没有任何一条用例传入 0**，于是缺陷从未被触发。

这正是防假绿最需要警惕的形态：

- 探针全绿 ≠ 覆盖完备；**测试数据分布**本身可能系统性地绕开缺陷；
- 判定标准应是"**边界值是否被覆盖**"，不是"用例数是否够多"；
- 修复动作：补 P28 探针（`feeSubLimit=0` → 期望正常赔付）+ S25 场景，并配 `zeroMeansUnlimited` 变异开关。

### 9.3 修复方案（第二轮，全部已执行）

| 缺陷 | 修复 | 业界基准 |
|---|---|---|
| N1 | `AccUsage` 增 `liabilityUsed`；责任维度纳入跨案累计，`commitUsage` 增 `liabilityDelta` | Guidewire Accumulation / ISO 责任期限额 |
| N2 | 结论自携带 `policyId/periodKey/三项占用`；重算前 `accumulation.reverse()` 旧占用；`commitUsage` 改**按 claimId upsert**（重算替换而非累加） | Guidewire recalculation / reversal |
| N3 | `AccUsage` 增 `frozen`；`commitFrozen/releaseFrozen`；预授权可用额 = `annualLimit − limitUsed − frozen`；剩余为 0 时授权压到 0 | ACORD 三值额度 `initial−claim−frozen` |
| N4 | 预授权用剩余责任限额（`liabilityLimit − liabilityUsed`） | 同上 |
| N5 | 无可赔费用 → 保守授权比例 0 | 直付网络追收风险治理 |
| N6 | 拒赔行 `feeDeduct = 0`，原因由 `rejectType` 单列 | 客户告知书合规 |
| N7 | `SettlementStorePort.tryBegin()` CAS 租约；取不到租约抛 `ConcurrentSettlementException` fail-closed | 幂等租约 / 分布式锁 |
| N8 | `AccumulationPort.reverse()` + `SettlementEngine.reverseSettlement(prev)` 对外冲正 | Guidewire reversal |
| N9 | 最大余数法 `apportionRounding()` 配平分位，逐行合计 ≡ 总额口径 | SOX/NAIC 可复算、对账守恒 |
| N10 | `putLimit()`：限额非正 = 维度未配置，**不进入控额维度** | tpa-saas 与主流产品配置惯例 |
