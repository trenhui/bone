## 0. 范围澄清：现有 procuraAI 只是子集

| 维度 | 现有 procuraAI 方案包 | 本设计（完整采购域） |
|------|----------------------|----------------------|
| 覆盖范围 | AI 风险审查 + 合同智能处理（标前→标中→标后） | 供应商主数据（含 **Vendor**）+ 生命周期 + 采购交易履约 + 供应商协同 + 跨域契约 + 工程治理 + 平台能力 |
| 性质 | 独立智能体（AI 子能力，已到 POC） | 领域架构 + 平台能力编排（含 AI 子能力） |
| 与 BONE | 复用元数据/低代码 Runtime，Clean Core | 复用同一底座 + 工作流主干/事件信封/IAM 审计日志；**存量 `bone-app-purchase` 适配层保留**；子流程、SLA、统一待办与审计 schema 走共建（能力基线 §2 / §7） |
| 交付形态 | 可独立交付产品 | 平台内多上下文 + AI 能力模块 |

> **结论**：procuraAI 是采购域里「AI 风险/合同智能」这一能力的最优落点，但不等于采购域本身。本设计在 §9 明确其嵌入点，其余章节补齐 JD 要求的供应商主数据（**Supplier 与 Vendor 角色分离**）、生命周期、交易履约、协同、跨域契约与工程治理。

## 2. 领域全景与限界上下文（战略 DDD，CORE-01 / P-2）

### 2.1 上下文地图（Context Map）

```
                          ┌─────────────────────────────────────────────┐
                          │            采购域（Procurement Domain）        │
  外部系统          ┌──────┴──────────────────────────────────────┬───────┴────────┐
  ┌─────────┐      │  Supplier MDM    Sourcing     Qualification   │  Contract(CLM)  │
  │ Finance │◀────▶│  (Supplier+      (寻源 RFx)   (资质·准入)      │  (合同·用印)    │
  │(AP/发票 │      │   Vendor 角色)       │            │          │       │         │
  │ 校验/付款)│     │      ▲共享内核        ▼            ▼          │       ▼         │
  └─────────┘      │  Procurement   Fulfillment   Risk & CAPA      │  Supplier       │
  ┌─────────┐      │  (PO/成本/     (GR/ASN/开票/ (风险·整改)       │  Portal(B2B)    │
  │Inventory│◀────▶│   调拨/RTV)     绩效/IR例外)    │             │  协同 Separate  │
  │(库存/仓)│      │      │              │           │             │      Ways       │
  └─────────┘      └──────┬──────────────┴───────────┴─────────────┴───────┴─────────┘
  ┌─────────┐              │ 事件协作 / ACL（防腐层）               │
  │Warehouse│◀─────────────┘                                        ▼
  └─────────┘      平台能力（三轨）：WorkflowEngine(S) / IAM(S) / 事件信封(S) / TaskCenter·审计事件契约·Outbox-starter(共建)
  ┌─────────┐
  │  OA/ERP │◀────▶ 通过 ACL 接入（D3-v2 §5 webhook：document.archived / contract.draft / contract.signed / payment.recorded / acceptance.recorded）
  └─────────┘
  ┌─────────┐
  │外部信用源 │◀────▶ Risk 上下文（天眼查/征信，对齐 D3 `vendor_profile.credit_source`）
  └─────────┘
  ┌──────────────────────────────────────────────────────────────────┐
  │ Finance 裁决边界：采购域产出 PO/GR/Invoice 数据，Finance 执行匹配，      │
  │ 回传 InvoiceMatched（匹配状态 / 例外码，见 D3-v2 §2.1）；采购域发 PaymentRequested│
  └──────────────────────────────────────────────────────────────────┘
```

**上下文关系语义**：
- **共享内核（Shared Kernel）**：`Supplier MDM` 持有 Supplier/Vendor Golden Record，是其他上下文的权威主数据来源；寻源/资质/合同/交易均引用 `supplier_id` / `vendor_id`（只读投影，不复制主档）。
- **下游/上游（Customer/Supplier）**：交易上下文（PO）依赖主数据上下文的产品与供应商投影；主数据变更经事件广播（§6）。
- **防腐层（ACL）**：与 Finance/Inventory/Warehouse/OA/ERP 的集成一律经 ACL + Outbox，禁止交易上下文直连外部 ERP 表（HC-001 持久化唯一性 + 边界纪律）。
- **分离方式（Separate Ways）**：供应商协同门户（B2B）作为独立前端上下文，经 API 网关与内部上下文对话，保证多租户/多法人隔离（可见性矩阵见总体 §9.1）。
- **裁决边界（v0.2 新增）**：三单匹配与付款许可属 **Finance/AP** 上下文，采购域不裁决；跨域协作经 `InvoiceMatched` / `PaymentRequested` 事件（总体 §3.1/§7.1）。

### 2.2 核心聚合与实体建模（对应 JD ①）

> 聚合划分原则（CORE-03/CORE-06/CORE-11）：强一致不变量才放同一聚合；跨实体默认最终一致。**主数据 EAV/长尾扩展走 metadata SDK 扩展字段（CORE-09），核心事务字段用物理列。**
>
> **BONE 落地映射（v0.3，能力基线 §3）**：每个聚合根 = `@Table` 实体 + `Repository<T,ID>`；继承 `TenantAbstractEntity`（漏继承会静默跨租户读）、显式 `@Id`/`@Version`、保留基类 `@Deleted`；`created_by/updated_by` 由应用层赋值（SDK 无自动审计填充）。**DDL 手写进 `bone-init.sql`，不存在注解生成 DDL**；`@Sql` 方法必声明 `@TenantScope`，手写 SQL 模板须覆盖实体全部显式 `@Column`（列级对账门禁）。`ApplicationService.save()` 必配 `publishFrom()` 或 `@NoDomainEvent`（E-5.4 ArchUnit）。一期实体/表清单与负向探针见能力基线 §3.4 / §3.5。

#### 2.2.1 供应商主数据聚合（Supplier MDM 上下文）

| 概念 | 类型 | 聚合归属 | 关键不变量 / 说明 |
|------|------|----------|------------------|
| **Supplier（供应商）** | 聚合根 | 根 | 唯一 `supplier_code`（租户内）；`lifecycle_status`（§4.1）；**寻源/资质/绩效语义**，与 Golden Record 对齐 |
| **Vendor（交易供应商）** | 聚合根 | **独立聚合** | **可交易/可开票/可付款的财务主体**；按 `legal_entity_id` + `company_code` 隔离；承载 `Company Code data`（统驭科目、付款条件、付款方式、付款冻结、银行账号引用、重复发票检查标志）；`vendor_status`（§4.3） |
| **VendorActivation（Vendor 开通）** | 聚合根 | 独立聚合 | Supplier→Vendor 的**转换闸门**：准入通过 + 银行账号核验 + 税务校验 + 付款条件 + 重复发票检查；幂等键 `(supplier_id, legal_entity_id)`；开通失败不得被 PO 引用 |
| **Legal Entity（法律实体）** | 实体（受管控） | 可独立聚合 | 用于**多法人/财务对账/合规**（JD ⑤）——一个 Supplier 可含多个 LE；统一信用代码为强一致键；映射 Company Code / 账套 / 税区 / 币种；跨法人交易须按 LE 隔离账务（总体 §9.1） |
| **Site（供应商地点）** | 实体 | Supplier 子实体或独立聚合 | 供货/收货/工厂地址；多对一 LE；`site_type`（工厂/仓库/办公室） |
| **Contact（联系人）** | 值对象/实体 | 多对多 | 角色（采购/质量/财务）；加密存储（PII） |
| **Factory（工厂）** | 实体 | 独立或 Site 子类 | 产能/资质/审核记录；食品安全/体系认证关联 Qualification |
| **Supplier Item（供应商货品）** | 聚合根 | 独立聚合 | 供应商×物料的供货能力（价格条件引用、交期、最小起订量）；跨 Supplier+Item+Org |
| **Supply Relationship（供货关系）** | 聚合根 | 独立聚合 | 组织×供应商×品类×Site 的供货授权（有效期的强一致不变量：不可与已生效 PO 冲突；同库跨聚合事务须按 CORE-06 登记例外，E-5.1/E-5.4） |

> **建模决策（对标 SAP MDG-S / Business Partner CVI / vendor master 三层）**：
> 1. `Supplier` 主档 + `Legal Entity` + `Site` + `Contact` 组成「企业档案」（General data，主数据管家所有）；
> 2. **`Vendor` 承载财务侧的 Company Code data，Owner = 财务**；`SupplyRelationship` / `SupplierItem` 承载采购侧的 Purchasing Org data，Owner = 采购。业界明确这两层数据分属不同部门，压进单一 Supplier 会导致「同一供应商在多法人下不同付款条件/银行/税号/冻结状态」无法表达；
> 3. `Supplier Item` / `Supply Relationship` 因高频变更且被交易上下文独立引用，设为独立聚合，经 CQRS 读侧投影（`QueryPort`）供 PO/寻源消费（CORE-05）；
> 4. **`vendor_profile`（D3 §4.2）是信用画像表，不是 Vendor 主档**，不可混用（总体 §12.1）。
>
> **字段 Owner 分层表与可见性矩阵**：总体 §6.1、§9.1。

#### 2.2.2 资质与准入聚合（Qualification 上下文）

| 概念 | 类型 | 说明 |
|------|------|------|
| **Qualification（资质）** | 聚合根 | 证照类型/有效期/附件/核验状态；过期驱动风险事件；OCR 自动识别（§9.2） |
| **Onboarding（准入）** | 聚合根 | 背调报告/准入评分/审批流实例引用（workflow）；准入通过才允许触发 `VendorActivation` |

#### 2.2.3 合同聚合（Contract 上下文，复用 procuraAI M2/M7）

| 概念 | 类型 | 说明 |
|------|------|------|
| **Contract（合同）** | 聚合根 | `contract_no`（贯穿 OA-ERP，D3 中为**审查入参关联键**）；条款/金额/主体/有效期；AI 审查结论以 `review_id` / 风险项 / `review_snapshot` 挂接；用印审批引用 workflow |
| **Clause（条款）** | 实体 | `clause_library`（D3 §4.2）：STANDARD/ALTERNATIVE/FORBIDDEN，版本化；`legal_reviewed` 才可被起草引用 |
| **PriceCondition（价格条件）** | 实体/值对象 | 阶梯价、折扣、附加费、运费/关税/税率；由合同或报价派生，被 PurchaseCost 引用（§5.3） |

#### 2.2.4 采购交易聚合（Procurement 上下文，JD ③）

| 概念 | 类型 | 说明 |
|------|------|------|
| **Requisition（请购单 PR）** | 聚合根 | 需求来源/预算占用/Guided Buying 目录项或 PunchOut；审批通过转 PO（对标 Ariba Guided Buying） |
| **PurchaseOrder（采购订单）** | 聚合根 | `po_no` + `po_version`；行 PO Line（物料/数量/单价/交期/Site/`vendor_id`/`legal_entity_id`）；状态机（§5.1）；价格引用 PurchaseCost 快照；审批引用 workflow；支持 Blanket PO 按累计额度核销 |
| **PurchaseCost（采购成本）** | 聚合根 | 供应商×物料×组织×有效期 的价格版本 + PriceCondition；价税分离；形成 PO 价格快照（详细模型 §5.3） |
| **Transfer（调拨）** | 聚合根 | 跨仓/跨组织/**跨法人**调拨；跨法人时带 `legal_entity_from/to` 并触发双方账务事件（业界 STO 思路，是其归入采购域的理由）；与 Inventory/Warehouse 协作（§6） |
| **RTV（Return to Vendor，退供）** | 聚合根 | 退供冲销；关联原 GR/发票；触发应付账款红冲（Finance）+ 库存回冲（Inventory）+ 质检/退货授权（RMA） |

> **聚合一致性边界**：PO 与其 PO Line 同聚合（强一致：金额 = Σ 行金额）；PO 与 PurchaseCost 经「价格快照」解耦（避免成本变更回滚已下 PO）；PO 与 Contract 经 `contract_no` 引用（合同变更经事件通知，不阻塞 PO 写）；**PO 与 Vendor 经 `vendor_id` 引用，Vendor 状态变更经事件通知，PO 创建时校验 Vendor 已开通（负向探针，总体 §12.2）**。

## 3. 供应商主数据治理（DAMA / SAP MDG-S 实践）

| 治理项 | 设计 | BONE 落地 |
|--------|------|-----------|
| Golden Record | 每供应商唯一主档版本化（`supplier_version`）；来源系统映射复用 D3「附：与 OA/ERP 适配的字段映射」 | `@Table` 实体 + `@Version` 乐观锁（ADR-0031；DDL 须含 `version` 列） |
| **角色分离与 Owner** | General data（主数据管家）/ **Company Code data（财务，Vendor）** / **Purchasing Org data（采购，SupplyRelationship）** 三层，字段按 Owner 分权限维护（总体 §6.1） | `@PreAuthorize("hasAuthority(...)")` 动作级细码；低代码 Runtime 字段可见性用 `RuntimeFieldVisibilityProjector` |

| 去重合并 | 同一法人多编码/重复供应商的合并与存活（survivorship）规则，由数据管家确认 | 版本戳 + 合并审计留痕 |
| PII 治理 | Contact/法人身份证/银行账号加密（合规 §24 禁 PII 入 AI） | 字段级加密 + 脱敏展示 |

## 4. 供应商生命周期（SLM）能力设计（JD ②）

### 4.1 生命周期状态机（主状态 + 子状态）

```
[PROSPECT 潜在] ──寻源中标──▶ [ONBOARDING 准入中]
     ▲                          │ 背调+资质+审批(workflow) + VendorActivation
     │                          ▼
[EXITED 已退出] ◀──整改失败/主动退出── [ACTIVE 合作中] ──供货/绩效/风险──▶ [CORRECTIVE 整改中]
                             │  ↑风险超标/绩效不达标触发整改
                             │  │绩效优良/风险可控
                             ▼  │
                        [SUSPENDED 暂停] ──恢复──▶ [ACTIVE]
                             │ 整改达标
```

| 主状态 | 子状态/关键动作 | 领域事件 | 审批/AI 介入 |
|--------|----------------|----------|--------------|
| PROSPECT | 寻源建档 | `sourcing.prospect_created` | 寻源 RFx（Sourcing 上下文） |
| ONBOARDING | 背调/资质收集/准入审批 | `supplier.onboarding_submitted` | workflow 准入审批；AI 背调报告（§9.2） |
| ACTIVE | 建供货关系/签合同/供货 | `supplier.activated` | procuraAI 合同审查（M2） |
| SUSPENDED | 风险/合规暂停 | `supplier.suspended` | 风险事件触发（Risk 上下文） |
| CORRECTIVE | 整改计划/复核 | `supplier.corrective_opened` | CAPA 工作流 |
| EXITED | 退出清算/关系关闭 | `supplier.exited` | 退出审批 + 未结 PO/合同/应付校验 |

> **关键不变量**：`EXITED` 前必须零未结 PO/未结合同/未清应付账款**且全部 Vendor 角色已关闭**（跨域校验，见 §6.4 对账）；`ACTIVE`→任意状态变更须经对应审批/事件。

### 4.2 各阶段能力与 procuraAI 衔接

| 阶段 | 业务能力 | procuraAI 嵌入点 | 供应商协同（§4.4） |
|------|----------|------------------|--------------------|
| 寻源 | RFx/招投标/报价 | M1 招标文件检测、M4 智能评标（现有） | 供应商注册、资质自助提交 |
| 背调 | 信用/诉讼/股权核查 | `vendor_profile` 信用画像（D3 §4.2）、AI 背调报告（§9.2 扩展） | 资料补件 |
| 准入 | 资质核验 + 审批 + Vendor 开通 | 资质 OCR 真伪（§9.2）；workflow 准入审批 | 开通状态查询 |
| 资质 | 证照有效期管理 | 过期驱动 Risk 事件 | 证照自助更新（写后审批） |
| 工厂 | 产能/体系审核 | Factory 审核记录 + AI 报告 | 审核预约/整改反馈 |
| 合同 | 起草/审查/用印 | M2 风险审查 + M7 起草（现有，D3 §4.3） | 合同确认 |

| 整改 | CAPA | 整改工作流 | 整改提交/复核反馈 |
| 退出 | 关系关闭 | 跨域未结校验 | 对账查询 |

### 4.3 Vendor 生命周期与转换闸门（v0.2 新增，对应 JD ①/⑤）

```
Supplier(ACTIVE) ──VendorActivation 提交──▶ [PENDING_VENDOR]
                                              │ 准入通过 + 银行核验 + 税务 + 付款条件 + 重复发票检查
                                              ▼
                                       [ACTIVE_VENDOR] ──风险/合规──▶ [PAYMENT_BLOCKED]
                                              │  ▲ 放行(MRBR 式人工复核)
                                              │  │
                                              ▼  │
                                        [INACTIVE_VENDOR] ◀── Supplier 退出 / 主动关闭
```

| 状态 | 允许动作 | 领域事件 |
|------|----------|----------|
| `PENDING_VENDOR` | 补充财务资料、审批 | `vendor_activation_submitted` |
| `ACTIVE_VENDOR` | 被 PO 引用、开票、参与付款 | `vendor_activated` |
| `PAYMENT_BLOCKED` | 只收不改（付款冻结），可查历史 | `vendor_payment_blocked` |
| `INACTIVE_VENDOR` | 不得新建 PO；存量 PO 走完 | `vendor_deactivated` |

- **不变量**：① 一个 `(supplier_id, legal_entity_id)` 至多一个有效 Vendor（唯一约束 + 幂等）；② 未开通 Vendor 的 Supplier **不可建 PO**（负向探针）；③ Supplier 进入 `EXITED` 前所有 Vendor 角色须为 `INACTIVE_VENDOR`；④ `PAYMENT_BLOCKED` 由 Finance/风控触发，采购域不可自行放行。
- **与 Supplier 状态机关系**：两套状态机并行、互不覆盖；Supplier 是「合作资格」，Vendor 是「交易与付款资格」。业界 S/4HANA 用 Business Partner 统一主档，但 Supplier / FI Vendor **业务角色仍分离**。

### 4.4 供应商协同的领域语义（v0.2 新增，JD ③ 任职要求 3）

> 技术接入（方向/鉴权/一致性）见总体 §4.3；本节定义**协同动作落在哪个聚合、产生什么领域事件**。

| 协同动作 | 承载聚合 | 领域事件 | 不变量 |
|----------|----------|----------|--------|
| 供应商注册 / 资质自助更新 | Qualification / Supplier MDM | `qualification_submitted` | 写后走审批，生效前不覆盖 Golden Record |
| PO 确认 / 部分确认 | PurchaseOrder | `po_acknowledged` | 幂等 `po_no+po_version` + CAS；不得确认已关闭 PO |
| ASN 发货通知 | GoodsReceipt（预置） | `asn_submitted` | `asn_no` 唯一；与 GR 对齐后推进匹配输入 |
| 自助开票（PO-based） | InvoiceSubmission | `invoice_submitted` | `invoice_no+vendor_id` 去重；金额须在 PO 未开票余额内 |
| IR 例外补料 / 申诉 | IRException | `ir_exception_raised` | 例外状态由 Finance 事件回写，采购域不裁决 |
| 绩效查看 / 整改反馈 | PerformanceScore / CorrectiveAction | `corrective_submitted` | 只读投影；整改提交走 CAPA |

## 5. 采购交易与履约（JD ③）

### 5.1 交易聚合与三单匹配（v0.2 修订裁决边界）

```
PR(请购/预算检查) ──▶ PO ──▶ PO Ack ──▶ ASN ──▶ GR(收货/Inventory) ──▶ Invoice(供应商自助/Finance)
                       │                            │                      │
                       └──── 采购域产出 PO/GR/发票数据 ────────────────────┤
                                                                          ▼
                     Finance 执行匹配（2-way / 3-way + 容差 + 冻结/放行 + IR 例外）
                                                                          │
                              InvoiceMatched ──▶ 采购域 PaymentRequested ──▶ ERP 付款 PaymentRecorded
调拨 Transfer：PO/库存 跨仓/跨法人 ──▶ Warehouse（带 legal_entity_from/to）
退供 RTV：GR 退回 ──▶ 应付红冲(Finance) + 库存回冲(Inventory) + RMA 质检
```

| 聚合 | 状态机要点 | 幂等/补偿 |
|------|------------|-----------|
| Requisition | DRAFT→SUBMITTED→APPROVED→CONVERTED→CLOSED | 预算占用与释放补偿；`Idempotency-Key` |
| PurchaseOrder | DRAFT→SUBMITTED→APPROVED→SENT→ACKNOWLEDGED→PARTIAL_RECEIVED→FULLY_RECEIVED→CLOSED；可 CANCELLED（终态不可回写） | `po_no+po_version` CAS；取消经补偿回滚预留 |
| PurchaseCost | 版本化价格 + PriceCondition；新版本不影响已下 PO（快照隔离） | 价格变更审批经 workflow |
| Transfer | CREATED→IN_TRANSIT→RECEIVED→CLOSED | 在途丢失补偿：冲销 + 重发；跨法人触发双边账务 |
| RTV | OPEN→APPROVED→RETURNED→SETTLED | 退供冲销幂等（`eventId` 去重） |

### 5.2 跨域协作不变量（v0.2 修订）

- **匹配与付款裁决在 Finance**（v0.1「三单匹配作为跨域强一致不变量」已废弃）：PO 在采购域、GR 在 Inventory、发票校验在 Finance，**跨系统**；按 DDD E-5.4 决策树走「状态机 + Outbox + 幂等 + 补偿 + 对账」，**不设强一致不变量**。采购域侧可校验的不变量是「PO 与 PO Line 金额一致」（单聚合内）与「GR 累计不超过 PO 承诺量（本域投影，最终一致）」。
- **匹配形态**（对标 SAP MIRO/LIV、Ariba IR）：实物/高价值用 3-way（PO×GR×Invoice），服务/订阅无 GR 用 2-way（PO×Invoice）；按品类/税区配置数量·价格·金额容差；超容差 → 发票冻结 + IR 例外队列 + 人工放行；GR/IR 清算在 Finance 侧完成。详见总体 §3.2。
- **PO↔Contract**：PO 条款须不劣于已审合同；AI 审查结论回写 `review_id` / 风险项 / `review_snapshot`，**`contract_no` 仅作关联键**（D3 §2 为审查入参，v0.1「结论回写 contract_no」为语义错，已修正）。
- **PO↔Vendor**：PO 创建时校验 `vendor_id` 已 `ACTIVE_VENDOR` 且 `legal_entity_id` 匹配（负向探针）。
- **RTV↔Finance/Inventory**：退供必须原子冲销应付与库存，跨域经 Saga 补偿（§7.4）；预付款/红冲/部分付款单列例外台账（§6.4）。

### 5.3 采购成本（Purchase Cost）模型（v0.2 新增，JD ③ / 任职要求 4·7）

> 对标 SAP Condition Technique / Info Record / PPV；JD 把 Purchase Cost 列为可独立负责的方向，需给出可落地的模型与价值度量，而非一行「版本化价格」。

**5.3.1 成本构成与价格链**

| 层级 | 内容 | 归属 |
|------|------|------|
| 报价 Quotation | 寻源中标价（RFx/Bid），含税/未税、币种、有效期 | Sourcing |
| 合同价 / PriceCondition | 阶梯价、折扣、返利 rebate、附加费、运费、关税、保险、税率、汇率规则 | Contract / SupplierItem |
| 标准成本 / 计划价 | 财务核定的标准价，用于差异分析 | Finance（只读投影） |
| PO 价（快照） | 下单时冻结的净价 + 条件结果 + 税 + 币种/汇率 + `price_snapshot_ref` | PurchaseCost → PO |
| 发票价 | 供应商开票金额，Finance 匹配时比对 | Finance |
| 差异 | **PPV（采购价格差异）= 实际 PO/发票价 − 标准成本**；另计运费/关税/汇率差异 | 分析侧（QueryPort 投影） |

**5.3.2 聚合与不变量**

| 概念 | 类型 | 不变量 |
|------|------|--------|
| PurchaseCost | 聚合根 | `(vendor_id, item_id, org_id, valid_from, version)` 唯一；同一生效期不得存在两个有效价（强一致，唯一约束/条件更新） |
| PriceCondition | 实体（随根） | 条件类型/计算顺序/基数/阶梯；条件优先级不可重叠冲突；计算结果可复现（存快照） |
| PriceSnapshot | 值对象 | PO 引用后不可变；成本版本变更不回滚已下 PO（快照隔离） |

**5.3.3 价值度量与跨域契约**

| 指标 | 定义 | 消费方 |
|------|------|--------|
| PPV | 实际采购价 − 标准价（按行、按期间聚合） | Finance / 品类管理 |
| Savings（降本） | 基线价（上期/预算/首轮报价） − 实际成交价，需标注 savings 类型（avoidance / realized） | 采购绩效 / Spend Analysis |
| 价格合规率 | PO 价落在合同/PriceCondition 允许区间的行占比 | 内控 / procuraAI 三一致 |

> 成本真源归 Procurement，但标准成本与 PPV 归集口径须与 Finance 共同确认；跨域只读经 `QueryPort`，写协作经事件（§6）。

## 6. 跨域契约（JD ④）

### 6.1 主数据同步（MDM）

- **归属**：Supplier/Vendor/Item/Cost 的 Golden Record 分别在 Supplier MDM / Procurement；交易上下文只读投影。
- **机制**：主档变更 → Outbox → 事件广播 → 下游消费幂等更新投影（CORE-05 读侧 `QueryPort`）。
- **双向同步**：与存量 ERP（SAP/U8/金蝶/Oracle）经 ACL 双向同步，冲突以「主数据域为系统真源 + 版本戳 + 字段 Owner 优先级」解决（D3-v2 §1 适配层映射表）。
- **边界重构路径（JD ⑧）**：现状（ERP 承载供应商/价格/合同主档）→ 目标（采购域为 Golden Record 权威、ERP 为账务与库存执行）分三阶段：① 只读镜像 + 差异清单；② 双跑（写回 ERP，逐日对账）；③ 按租户/法人/品类灰度切流，停止双向写。回退与割接见总体 §8.4。

### 6.4 状态同步与对账（v0.2 删除错误等式）

- **最终一致**：跨域状态不双真源；流程 `phase` 权威、业务 `status` 为投影（对齐 workflow 引擎纪律）。
- **对账三通道**（借鉴 synap-claim 不变量实践，改为**分通道、带例外台账**的可核对定义，技术口径见总体 §6.3）：

| 通道 | 核对对象 | 不变量 |
|------|----------|--------|
| `SUPPLY` | PO 承诺量 vs GR 实收累计 vs 未收量 | 未收量 = PO 承诺量 − GR 实收累计（按行、按版本） |
| `INVOICE` | 已开票 vs 已匹配/冻结/放行 | 发票状态机与 `InvoiceMatched` 序列一致，无重复发票号 |
| `PAYMENT` | 匹配放行金额 vs PaymentRequested vs PaymentRecorded | 已付累计 = Σ PaymentRecorded |

> **例外台账（必须单列，不得并入净额等式）**：预付款（业界须挂 special G/L，不与应付净额相抵）、贷项凭证红冲、部分付款、RTV 冲销、跨币种汇兑差异。v0.1「未结应付 = 已收未付发票净额」在上述场景均不成立，已废弃。
> **退出前校验**：零未结 PO / 未结合同 / 未清应付 + 全部 Vendor 角色关闭（§4.1）。

## 7. 复杂工程治理模式（JD ⑤，落地 BONE 平台）

> 本章经实证与平台真源一致（事件规范、workflow README、DDD CORE/E 条文、D3 契约），**原样保留**，仅 §7.2 补充 v1 缺口降级方案。

### 7.1 长流程 / 状态机

- **聚合状态机 + Orchestrator 按步推进**（E-3.3）：每步独立事务、可断点续跑；如「采购履约」= PR→PO→Ack→ASN→GR→Invoice→Payment 由 Orchestrator 驱动，单步失败可重试不回滚全局。
- 状态真源在聚合；对外投影经端口落地（与 workflow `phase` 纪律一致）。

### 7.2 审批流（复用 `bone-workflow-engine`）

| 采购场景 | 流程 | 引擎能力映射 |
|----------|------|--------------|
| 供应商准入/信息变更 / Vendor 开通 | 准入审批 | `WorkflowDefinition`+`ApproverResolver`(IAM) |
| 合同用印 | 用印审批 | `SINGLE/ALL/ANY` 签；`WorkflowStatusPort` 推合同状态 |
| 采购订单/价格 | PO/成本审批 | 条件分支（可替换端口 `WorkflowConditionEvaluator`；domain 缺省 `StructuredConditionEvaluator`，禁 SpEL RCE） |
| 整改 CAPA | 整改审批 | 串行节点 + 阶段字段模拟子流程；驳回直接 `rejectToNode`、抄送直接 `CC`（能力基线 §4） |

### 7.4 异步补偿（Saga / Orchestration）

- 跨聚合/跨部署单元写（如 RTV 冲销：Inventory 回冲 + Finance 红冲 + PO 关闭）用 Orchestrator + **补偿动作**；正向步骤失败触发反向补偿。
- 发件原子性用 **Outbox**（业务事务内写业务表+outbox，独立进程轮询发 MQ，避免双写不一致，事件规范 §7）。
- 不可重试错误进 DLQ，工具/人工重放（重放须新 `eventId` 或标 `replayOf`）。

### 7.5 幂等

| 层级 | 机制 | 来源 |
|------|------|------|
| 写接口 | `Idempotency-Key` 头（24h 去重） | D3 §1 |
| 事件消费 | `eventId` / 业务唯一键落采购域 `t_proc_processed_event`（`consumer_group + event_id` 唯一键） | 事件规范 §5 + 能力基线 §5.1 |
| 流程发起 | 同单据重复 `start` 复用实例 | workflow 引擎 |
| 批量 | 失败保留原始输入 + 重试 ≤3（FIFO+优先级） | D3 §4.3 batch |

### 7.6 批量处理

- 批量 PO 下发、批量审查（procuraAI `POST /reviews/batch`）、批量对账：统一 FIFO+优先级队列，失败重试≤3，保留原始输入供人工处理，禁止「批中一条失败全批回滚」（单条隔离）。

### 7.7 数据一致性

- **同库跨聚合**：声明业务不变量、失败语义、并发成本并记录例外（CORE-06 / E-5.1，如 Supply Relationship 有效期与已生效 PO 不冲突）；例外仅限同库本地事务。**E-5.4 实为 `save()` 必配 `publishFrom()` 的 ArchUnit 规则，不是跨聚合不变量条款**（能力基线 §6.2）。
- **跨部署单元/跨进程**：默认最终一致（Outbox+幂等+对账）；强一致边界仅限单聚合（CORE-06）。
- **跨系统（PO/GR/Invoice/付款）**：按 E-5.4 决策树走状态机 + Outbox + 幂等 + 补偿，不设强一致不变量（§5.2、总体 §3.1）。
- **对账**：三通道定期对账（§6.4），不变量被破坏即告警。

### 7.8 缓存一致性

- 读模型投影（按 CORE-05 定义的**业务侧** `*QueryPort`，框架无该接口）缓存以「事件驱动失效 + 版本戳」为主，**禁止双真源**；主档变更事件触发投影缓存失效，而非定时全量刷新。
- 热点（供应商信用画像、条款库、价格条件）用短 TTL + 事件失效，避免 stale read 导致审批误判。

### 7.9 生产稳定性

- **降级**：LLM 不可用时 `rules_only` 模式（沿用 procuraAI，不另设 `DEGRADED` 终态）；审批能力缺口降级见 §7.2。
- **熔断/限流/超时**：外部信用源/LLM 调用加熔断；批量审查限流。
- **可观测**：`trace_id` 贯穿 REST+MQ（事件规范 §9），指标 `bone_mq_lag`/`consume_total`；NFR 见总体 §8.3。
- **回滚演练**：dry-run 只读回滚（借鉴 synap-claim 第 8 轮回滚演练），上线前证伪。
