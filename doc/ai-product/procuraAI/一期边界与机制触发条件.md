## 3. 重试预算分层表（R6：不盲目统一 8 vs 3）

诊断 P1-9 指出 `06 卷 §13.1`「retry budget 最多 8 次 / 累计 ≤10min」与 `06 卷 §9`、`总纲 §15/§19`「重试 ≤3」冲突。**按建议原文「二选一并全族替换」会造成新的语义错误**：二者约束的是**不同对象**——

- `≤3` 约束 **Saga 补偿步骤 / 批量单条重试**（业务侧、有人工台账兜底，重试过多会放大业务副作用）；
- `8 次 / 10min` 约束 **Outbox 中继到 broker 的投递**（基础设施侧、at-least-once，需要更长退避以度过短暂不可用）。

B17 的要求恰是「明确 retry budget + **禁止多层重试叠加**」，而非「所有层用同一个数」。因此本轮**统一的是口径表，不是数字**：

| 层 | 对象 | 预算 | 退避 | 失败去向 | 依据 |
|----|------|------|------|----------|------|
| L1 | Saga 补偿步骤 | **≤3 次** | 固定短退避 | DLQ + 人工台账（保留原始输入） | `总纲 §15`、`06 卷 §9` |
| L2 | 批量任务单条 | **≤3 次**，单条隔离（禁止一条失败全批回滚） | 固定短退避 | 例外台账 + 续跑 | `总纲 §19`、`领域 §7.6` |
| L3 | **Outbox 中继投递** | **≤8 次 / 累计 ≤10min** | `delay = min(cap, base×2^attempt) × (0.5 + rand())`（full jitter） | `platform.dead_letter.v1` | `06 卷 §13.1`、B17 |
| L4 | 外部 HTTP 客户端 / SDK | **由 L3 预算统一托管**，不得独立叠加 | — | 计入 L3 | `06 卷 §11` M6-12 |

**总预算约束**：L1/L2 与 L3 处于不同调用链，**不得同时作用于同一条消息**；`06 卷 §13.1` 的「禁三层重试叠加」探针（M6-12）守护这一点。若未来出现 L1→L3 嵌套，必须由 retry budget 校验器拒绝配置。

> **A10 守护**：全族不得再出现「重试 ≤3」与「8 次」指向同一对象的表述；本文件必须同时给出 L1–L4 四行与「不同对象」的显式说明。

## 4. 三处分期统一（R7 前置）

诊断 P1-10 指出 `04 卷 §0`「一期 ✅ PR/PO/成本」、`总体 §12`「采购交易整体二期」、`总纲 §1`「01/02/03/04/06 五卷一期 ✅」三处冲突。本轮以 **B19 按 spend capture 排序 + 先跑通端到端** 的口径统一为：

| 阶段 | 时间窗 | 统一范围（**分期唯一真源**，与总体 §12 一致） | 关键交付 |
|------|--------|----------------------|----------|
| **一期 Design & Data Foundation** | T0+0~12 周 | M01 供应商主数据 / M03 准入 / M04 合同（复用 procuraAI）/ **M05 的 PR→PO 最小闭环（不含调拨/RTV/成本全量）** / M08 门户只读 / M09 壳 / M11 适配层 | MDM + VendorActivation + workflow 接入 + 合同 AI 审查 + request→PO 端到端 + DDL/契约冻结 |
| **二期 Core Buying Channel + Fulfillment** | T0+13~28 周 | M05 采购成本/价格链/调拨/RTV 全量、M06 履约协同、门户完整能力、跨域事件与三单匹配数据链 | 全流程 E2E（request→PO→invoice→ERP write-back）+ 对账零差异 + 压测达标 |
| **三期 Supplier Enablement & Scale** | T0+29~44 周 | M02 寻源全量、M07 风险/CAPA/退出、平台能力共建三项 | 共建能力被 ≥1 个其他域复用 + 回归门禁绿 |

- **为什么把 PR→PO 最小闭环提到一期**：B19 明确「先跑通 request→PO→invoice→ERP write-back 端到端再扩宽度」；一期只做 MDM + 合同而无任何交易链路，无法验证领域模型与跨域契约，属于「模块容易开」而非「按 spend capture 排序」。
- `04 卷 §0` 改为「**一期范围：✅ PR/PO 最小闭环；成本全量 / Transfer / RTV 二期**」，与 `总体 §12`、`总纲 §1` 一致。
- `D4` 从「日历排期真源」降为「POC 阶段排期参考」（`文档资产登记与真源裁决.md §3.2`）；WBS 人力见 `总体 §12` 新增列（R7）。

> 字段级事件契约中 `InvoiceMatched` payload 字段已在 D3-v2 §2.1 冻结（`match_status` enum(`MATCHED`/`EXCEPTION`/`REVIEW`) / `matched_at` / `match_id`），是跨域 ACL 的**真源**；`StockSnapshot` 字段级 schema 尚待 D3-v2 §2.1 补全（当前仅 §7.5 列 `snapshot_id` 幂等键），Mock 阶段先按 §7.5 约定字段回放。本策略只解决「F-A 未交付前采购域如何独立闭环」。

- **Mock 形态**：进程内 Mock Adapter 实现 `FinanceMatchResultPort` / `InventorySnapshotPort`；回放 `InvoiceMatched` 冻结 payload（`match_status`/`matched_at`/`match_id`），`StockSnapshot` 暂按 §7.5 的 `snapshot_id` 幂等键 + `staleness` 约定字段回放（字段级 schema 待 D3-v2 §2.1 补全），不连真实 Finance/Inventory。
- **可验证项**：对账不变量（已付累计 = Σ PaymentRecorded，预付款 / 红冲 / 部分付款 / RTV 单列例外台账；见 `总体 §6.3`，第四轮随 `RECON-01` 同步去除保险域「理算总额」口径）、三单匹配容差挂起、staleness fail-closed（S5）、幂等重放，均可在无跨域依赖下跑通并留痕（对应评测集 `RECON-01` / `MATCH-01` / `MATCH-02`）。
- **可逆切换**：跨域 ACL 真交付后，仅将 Mock Adapter 替换为真 adapter，端口契约与 payload 字段不变，属纯替换、零逻辑改动。
- **边界**：Mock 仅供设计态验证与评测集运行；一期生产部署**必须**换成真 adapter，且 `InvoiceMatched` 仍为 Finance 裁决回传、采购域不裁决（S4）。

### 7.7 Handler 骨架示例（Proposal，1 个端点即可达成 R-7 验收）

```java
// VendorActivationAppService.handleActivate —— 切片 B 的最小 handler 骨架
// 不变量：同库本地事务；激活成功才发 VendorActivated（跨单元事件）；失败整体回滚（S6）
@Transactional
public VendorActivationResult handleActivate(ActivateVendorCmd cmd) {
    Vendor vendor = vendorRepository.mustFind(cmd.vendorId(), cmd.tenantId()); // S2 四维隔离
    VendorActivation activation = vendorActivationRepository
        .findByVendor(cmd.vendorId())
        .orElseGet(() -> VendorActivation.pending(vendor, cmd.tenantId()));
    activation.activate(cmd.reviewedBy());     // 状态机 PENDING→ACTIVE（守卫）
    vendorActivationRepository.save(activation);
    outboxPort.enqueue(new VendorActivated(     // 仅跨单元：发事件（T2）
        activation.id(), cmd.tenantId(), cmd.vendorId()));
    return VendorActivationResult.ok(activation.id());
}
```

### 7.8 诚实边界（续诊 O7 收口说明）

- 本 §7 是 **Proposal 设计草案**，**不创建真实模块、不写 `bone-init.sql`**；文档族门禁本身已接 CI blocking（§5），但最小切片的真实模块 / handler 红绿仍属 owner 执行，owner 在 L38 冻结后据此落盘。
- R-7 验收判据（"`bone-init.sql` 出现 `t_proc_*` ≥1 / `bone-procurement-*` 目录 ≥1 / 1 个 handler 测试 + CI 红绿"）属 **owner 执行项**，本文提供的是**开工蓝图与门禁保护对象**，不伪造「已落地」证据。
- 门禁 A10.12 守护本 §7 的存在性（目录树 + `t_proc_` DDL 草案块 + Proposal/bone-init.sql 标注），防止切片骨架被误删或退化为纯口头描述。
