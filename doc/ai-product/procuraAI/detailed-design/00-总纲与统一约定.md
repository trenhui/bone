# Procura 模块详细设计总纲与统一约定（LLD Charter）

> **版本**：v0.3（2026-11-08）
> **v0.3 修订依据**：六组新业界锚点 B12–B17（§13）+ 逐卷实证诊断（§0.2）。原则：**不重订已冻结的业务结论、不新增事件/错误码/权限码**，只把 §14–§22 的通用基线**实例化到每一卷**，并为一卷补一个差异化可执行专题（§23、各卷 §13）。
> **v0.2 修订依据**：`Bone-消息与事件规范` §2/§4 实证核验 + 业界锚点 B7–B11（§13）。原则：**不推翻 v0.1 已冻结的业务结论，只补「可直接编码」的契约与治理缺口**；诊断结论均经源码/规范复核，不以印象评审。
> **状态**：**Proposal（设计提案，待架构评审冻结）**——本族描述的是"批准后的实现方案"，**不是已实现代码**；arc42 要求每张图与每份设计显式标注状态，禁止把设计态当作部署态/运行态证据。
> **定位**：Procura 各模块 **详细设计（LLD）真源**。回答"怎么实现"；不重定义已冻结的"是什么/边界"。
> **上游真源**：领域语义 = [采购领域架构设计方案.md](../采购领域架构设计方案.md)；技术架构 = [采购总体架构方案.md](../采购总体架构方案.md)；框架能力实证与落地约束 = [采购域-BONE框架能力对齐与落地基线.md](../采购域-BONE框架能力对齐与落地基线.md)；AI 子能力契约 = `采购AI-接口契约与数据字典-v2.md`（D3-v2；D3 已判历史归档）。
> **冲突裁决**：领域语义以领域真源为准、技术约束以总体方案为准、**平台能力状态以能力基线源码实证为准**；本族与上列任一冲突时，**以上列为准并回改本族**。新增实现级概念（表、字段、端点、事件）由本族定义，冻结后回填上游 §7.1 / §12.2。
> **门禁**：`tools/check_procura_alignment.py` A1–A10 + `--self-test`；ship-ready 权威判据是 **CI blocking**，本地 `check.sh` 只是辅助（总体 §13、能力基线 §6）。

## 0. 为什么需要这一层（HLD → LLD 的差距）

总体方案与领域设计已冻结「限界上下文、聚合、生命周期、跨域契约、部署单元、ADR、NFR」，但开发仍无法直接编码：缺**字段级表结构、端点级契约、状态迁移守卫、幂等键、补偿步骤、权限码、错误码、负向探针**。业界 LLD 的职责正是把 HLD 的 what 翻译成可无歧义实现的 how。

| 业界锚点 | 对本族的要求 | 落点 |
|----------|--------------|------|
| C4 Level 3（Component）/ arc42 building-block + runtime + cross-cutting | 每卷给容器内组件视图与职责边界，标状态、协议、方向；不把概念图当物理模型 | 每卷 §2 |
| LLD 模板（Overview / C4 L3 / Class / API / DB / Sequence / State / Error / Cache / Config / Test / Migration） | 固定 12 节模板，评审可按节挑战 | §2 |
| API-first / contract-first（OpenAPI + AsyncAPI 先行） | 端点与事件先评审 schema、错误、授权、幂等，再写 handler；非法迁移返回具名错误 | §5 / §6 |
| SAP MDG-S（官方：General / Company Code / Purchasing Org 三层分段 + 各层双人复核 Change Request + 分层 Block/Unblock + duplicate check + staging/replication） | 主数据按字段 Owner 分权维护，变更请求分段落库、分段审批、生效前不覆盖 Golden Record | 01 卷 §3/§5/§10 |
| ANSI X12 850 → 855 → 856 → 810（+997 语法回执、820 汇款通知） | 协同链路的文档编号、幂等（BEG03 + 交易伙伴）、ASN 与发票一致性、SSCC/包装层级 | 05 卷 §5/§6 |
| SAP MIRO/LIV（2-way/3-way、容差、冻结放行、IR 例外） | 采购域只产出匹配输入与数据，**不裁决**；`InvoiceMatched` 由 Finance 回传 | 04/05 卷 §7 |
| DAMA-DMBOK Golden Record / survivorship | 版本戳 + 来源优先级 + 合并留痕 | 01 卷 §3/§9 |
| Platform Engineering golden path / SAP Clean Core A–D | 一律按能力基线三态分派（S 复用 / D 共建 / N 自建），禁止把规范承诺写进"已复用" | 每卷 §8 |

> **本族不做的三件事**：① 不推翻 v0.3 已冻结的业务结论（Vendor 角色分离、Finance 裁决、一期单应用单库、平台三轨、存量 `bone-app-purchase` 保留）；② 不把设计态写成"平台已有能力"；③ 不替 owner 决定 NFR 数值、日历排期、财务账套清单（总体 §8.3 / 能力基线 §9.2）。

## 3. 分层、包结构与命名（BONE 六边形）

```
bone-apps/bone-procurement-<module>/src/main/java/com/bone/procurement/<module>/
├── adapter/          # REST Controller、事件 Consumer、Webhook 入站（依赖 application）
│   ├── web/          #   @RestController + @PreAuthorize + ApiResponse<T>
│   └── messaging/    #   Consumer：幂等 → 应用服务 → 标记 processed
├── application/      # 语义化 *ApplicationService（ADR-0028）；事务边界在此
│   ├── port/in/      #   Command / Query 入站端口（复杂度升级才加 Handler）
│   └── port/out/     #   *QueryPort（读）、*AclPort（外部）、*EventPort（发件）
├── domain/           # 聚合根 / 实体 / 值对象 / 领域服务 / 领域事件（纯 Java）
│   ├── model/        #   @Table 实体 + @Id/@Version + TenantAbstractEntity
│   ├── repository/   #   Repository<T,Long> 接口；@Sql 方法必带 @TenantScope
│   └── event/        #   DomainEvent 空接口实现
└── infrastructure/   # Repository 实现由 SDK 代理生成；ACL/中继/HMAC/缓存适配
```

- **依赖方向**：`adapter → application → domain ← infrastructure`（HC-002 / `BoneDddArchRules.java:142-160`）；domain 不得依赖 Spring / SDK 之外层。
- **类名**：`<Aggregate>ApplicationService`、`<Aggregate>Repository`、`<Aggregate>QueryPort`、`<External>AclPort`、`<Event>Consumer`。
- **表名**：`t_proc_<snake_case>`；**字段名**：snake_case；**索引**：`uk_` 唯一 / `idx_` 普通；**事件 topic**：`domain.procurement.<aggregate>_<verb>.v1`。
- **API 路径**：`/api/v1/procurement/<resource>`；门户侧 `/api/v1/portal/<resource>`；错误响应统一 `ApiResponse<T>` / `PageResult<T>`（HC-003）。
- **权限码**：`procurement:<resource>:<action>`（action ∈ `read/write/approve/export/admin`）；门户 `portal:<resource>:<action>`。

## 4. 持久化统一约定（能力基线 §3，不得二次发明）

| 项 | 约定 | 漏了会怎样 |
|----|------|-----------|
| 实体基类 | **必须** `extends TenantAbstractEntity<Long>` | `TenantFilterInjector.inject()` 直接 return ⇒ **静默跨租户读** |
| 主键 / 版本 | **显式** `@Id private Long id`、`@Version private Long version` | 无版本即无乐观锁；DDL 无 `version` 列 UPDATE 直接失败 |
| 软删 | 保留基类 `@Deleted`，不重写 `deleteById` | 走物理 `DELETE FROM` |
| 列声明 | `@Column` 可选（覆盖列名/nullable/unique）；不写按蛇形自动成列 | — |
| `@Sql` 通道 | 每个 `@Sql` 方法**必须** `@TenantScope`；模板覆盖实体全部显式 `@Column` | 启动期拒绝注册；字段恒 null 再被 `save` 抹掉 |
| 审计人 | `created_by` / `updated_by` 由 **ApplicationService 显式赋值**（从登录上下文） | SDK 无自动审计填充，DDL `DEFAULT NULL` |
| DDL 真源 | **手写 `bone-init.sql`**（无注解→DDL 生成器）；同步 `doc/architecture/数据库开发规范.md` §2 清单 | 实体与表漂移、运行期 500 |
| 必备列 | `id, tenant_id, created_at, updated_at, created_by, updated_by, deleted, version` | HC-008 门禁 + 列级对账 |
| `save()` | 必配 `publishFrom()` 或类级 `@NoDomainEvent` + JavaDoc | ArchUnit E-5.4（`BoneDddArchRules.java:1245-1298`）转红 |
| 扩展字段 | 长尾属性走 EAV（`ExtensionMode`）；核心/事务/高频字段**必须物理列** | CORE-09；EAV 上做范围查询 = 性能事故 |
| 子实体 | 随根落盘用 `@Cascade` + `@Transient`，不得提升为独立聚合 | CORE-11 |

## 6. 事件统一约定

- **信封 8 字段**：`eventId / eventType / topic / occurredAt / tenantId / traceId / schemaVersion / payload`（`IntegrationEventEnvelope.java:7-15`、事件规范 §3）。
- **分区键不在信封内**，落 `t_proc_outbox.partition_key`，**双轨取值（v0.2 修正 P0-2）**：
  - **非顺序敏感**事件（主档变更、预警、审计）：`tenant_id`，保持租户内均衡。
  - **顺序敏感链路** PO→Ack→ASN→GR→Invoice→Payment：**`tenant_id + <aggregate_key>`**（聚合键取 `po_no`，跨法人再并 `legal_entity_id`），否则「同 `po_no` 保序」与「默认 `tenant_id`」互斥；payload 必须带 `aggregate_version`（如 `po_version` / `supplier_version`）供消费侧**丢弃乱序或旧版本事件**。
  - 依据：事件规范 §2「顺序敏感链路同一 key」+ B10（per-aggregate 顺序仅在同一分区键下成立）；全局跨聚合顺序**不承诺**。
- **发件**：`t_proc_outbox`（列对齐 `bp_outbox`：`event_id` 唯一、`topic`、`partition_key`、`envelope_json`、`schema_version`、`status`），业务事务内写业务表 + outbox；中继独立投递。
- **消费**：`t_proc_processed_event`（`(consumer_group, event_id)` 唯一键）；**不得跨上下文直写 `bp_processed_event`**。
- **失败**：不可重试 → `platform.dead_letter.v1` + 重放（新 `eventId` 或标 `replayOf`）；平台 `IntegrationOutboxRelay` 超限仅 `markFailed()`，**DLQ 转投须采购域自建**（能力基线 §5.2）。
- **一期边界**：同库同进程调用不发事件；事件只用于 → 平台 / → 门户 / → 外部系统 / 审计留痕（总体 §8.1）。
- 已冻结事件以总体 §7.1 + 领域 §6.2 为准（**不得改名**）；**所有事件（含 LLD 级新增）逐条登记在附录 B 事件契约注册表**，命名 `domain.procurement.<aggregate>_<verb>.v1`，不得与已冻结事件同名异义，冻结例外见 §16.8。
- **契约工件、schema 演进、tolerant reader、replay 隔离见 §16**；`t_proc_processed_event` 即 **Inbox**（B10），去重占位与业务副作用必须同本地事务。

## 14. 数据语义基线：金额 / 币种 / 汇率 / 税 / 数量 / 时间 / UOM（B9）

> **为什么单列一节**：v0.1 各卷有 `amount`、`tax_rate`、`fx_rate`、`qty`、`valid_from`，但全族没有一句话规定它们的**类型、精度、舍入与单位**。多法人 + 多币种采购下，这是最典型的生产事故（发票差一分、JPY 出现小数、红冲按新汇率、行合计与总额不等），也是 JD「多法人 / 多组织」考点里最能体现落地能力的一环。**所有卷 §4 的物理列与 §6/§7 的 payload 一律遵守本节。**

| # | 规则 | 实现约束 | 违反后果 |
|---|------|----------|----------|
| D-01 | **禁用 `float` / `double`** 承载金额、单价、税率、汇率计算结果 | Java `BigDecimal`；DB `DECIMAL(19,4)`（金额）/ `DECIMAL(19,8)`（汇率、比率）；JSON 金额用**字符串**传递（避免 JS 浮点截断） | `0.1+0.2 != 0.3`，对账差异不可收敛 |
| D-02 | **金额与币种同行** | 任何表 / payload / 方法签名不得出现裸金额；`Money(amount, currency)` 值对象，ISO 4217 三位大写（`CNY`/`USD`/`JPY`，符号仅展示层） | 跨币种直接相加产出无意义总额 |
| D-03 | **小数位由币种 minor unit 驱动**，禁硬编码 2 位 | 从 ISO 4217 元数据取 `decimal_digits`（USD/EUR/CNY 2、JPY/KRW 0、KWD/BHD 3）；落库保留足够 scale、展示与校验按币种量化 | ¥1,234.56 不是合法日元金额 |
| D-04 | **汇率锁一次、存永久** | `price_snapshot` / 发票 / 付款请求存 `fx_rate + fx_as_of + fx_source`；取值时点 = 业务单据日（GAAP/IFRS 交易日记账）；**红冲 / RTV / 退款复用原汇率**，付款日汇率差进 **FX 损益单列台账** | 审计无法复现「为什么是 €18.44」；汇兑差异混入净额等式 |
| D-05 | **舍入策略显式且跨层一致** | 逐行计算 → 按币种 minor unit 舍入 → 汇总 → 校验 `total == Σ lines`；舍入模式（`HALF_UP` vs `HALF_EVEN`）由 L34 冻结后全链路统一；汇率本身不预先舍入 | 行合计与总额差一分，发票被 Finance 冻结 |
| D-06 | **税口径可复现** | 明确含税/未税标志、`tax_rate` + `tax_region` + `tax_code_version`；税额单独舍入；跨法人按 LE 税区 | 同一 PO 在不同 LE 算出不同税 |
| D-07 | **数量与 UOM** | `DECIMAL(19,6)`；每物料存基准单位 + 换算系数快照；不同 UOM 不得直接相加；ASN/GR/发票行的 UOM 换算在传输前校验（B3） | 100 EA 与 1 BOX 相加 |
| D-08 | **时间统一** | 存储 ISO-8601 **UTC**（`DATETIME(3)`），展示层按租户时区；`valid_from` 含 / `valid_to` 不含的半开区间；`occurredAt` 与 HTTP MDC 一致 | 跨时区出现「当天失效」或重复生效 |
| D-09 | **分摊余数确定性分配** | 折扣/运费/税额按行分摊时，余数按固定规则（最大余额法或末行兜底）分配，保证 `Σ parts == total` | 分摊后总额漂移 |

**落点矩阵**（各卷 §4 必须体现的列）：

| 卷 | 关键列 | 必须补充 |
|----|--------|----------|
| 01 | `t_proc_vendor.reconciliation_account`、`payment_terms` | 币种与统驭科目按 LE 归属；银行引用不含明文 |
| 02 | `t_proc_quotation.net_price / tax_rate / currency` | 含税标志 + 币种；报价密文解出的金额同样遵守 D-01 |
| 03 | `t_proc_contract.amount / currency` | 合同金额币种与后续 PO 快照一致 |

| 05 | `t_proc_invoice_submission.amount / tax / currency`、`t_proc_recon_exception.diff_amount` | 金额 ≤ 未开票余额按同币种比较；汇兑差异单列 `exception_type=FX_GAIN_LOSS` |

## 15. 长流程 / Saga 隔离与补偿（B7）

> v0.1 §7 只写「每个正向步骤配反向动作」，这在评审里会被追问：**并发 Saga 读到中间态怎么办？补偿本身失败怎么办？哪些步骤根本不能补偿？** 业界答案（Azure Saga / Richardson）是显式的三分类 + 四类隔离对策。

**15.1 步骤三分类与排序（强制）**

| 类型 | 语义 | 排序 | 采购域例子 |
|------|------|------|------------|
| `COMPENSATABLE` | 可用新事务语义撤销 | **必须在 pivot 之前** | 预算占用、库存预留、资质占位、CR 草稿 |
| `PIVOT` | 提交点 / 不可回头，成功后必须走到底 | **尽量靠后** | `PaymentRequested` 发出、用印完成、授标生效 |
| `RETRIABLE` | 幂等且最终必成功，只前向重试不回滚 | pivot 之后 | 审计事件写入、通知、Outbox 投递、DLQ 转投 |

> `OrchestrationStep.step_type` 增列三分类（06 卷 §4），**未标注分类的步骤拒绝启动**（兼容 M6-6「无补偿动作」探针）。pivot 之后的失败**只重试 + 告警 + 人工，不触发前序补偿**。

**15.2 补偿三性质**：① **幂等**（同一 `saga_id + step_no` 重复执行无副作用）；② **可交换**（不依赖补偿顺序，用增量而非绝对赋值）；③ **完整**（每个改变状态的正向步骤必须有补偿，否则该步骤不得进入 Saga——用 2PC/同步调用替代）。

**15.3 隔离四对策（Saga 天然缺 I，必须用设计补）**

| 对策 | 落地 | 采购域应用 |
|------|------|------------|
| **语义锁** | `PENDING / IN_REVIEW / MATCH_PENDING` 等中间态即应用级锁；其它操作只读或拒绝（返回 `409 invalid_transition` + 稍后重试） | 01 卷 CR 审批中禁止再开同段 CR；05 卷 `MATCH_PENDING` 禁止改为 `MATCHED` |
| **可交换更新** | 累计量用条件增量 `SET x = x + ?` 而非 `SET x = ?` | GR 累计 `received_qty`、Blanket PO 累计核销 |
| **重读值 / 版本检查** | 提交前重读 `@Version` / `aggregate_version`，变化则中止当前步骤并重跑 | PO 确认、价格版本生效、供货关系变更 |
| **按风险分级** | 高风险（付款、跨法人调拨）走更严路径（人工复核 + 对账），低风险走 Saga | PA-04 付款只认 Finance 事件 |

**15.4 采购域 Saga 清单与编排状态持久化**

| Saga | 步骤（分类） | 补偿 / 失败语义 |
|------|--------------|-----------------|
| PR → PO → 预算 | 占用(C) → 转换(C) → 下单(P) → 通知(R) | 转换失败释放预算；下单后失败不回滚占用，走取消流程 |
| `OnboardingApproved` → `VendorActivated` → `COMPLETED` | 准入审批(C) → 开通闸门(P) → 状态回写(R) | 开通失败**事件重放 + 人工重试，不自动重复建档**（02 卷 §9） |
| RTV 三步 | 应付红冲(C) → 库存回冲(C) → RMA 质检(P) | 任一步失败保留原始输入 + 重试 ≤3；补偿不成进 DLQ + 人工台账 |
| Transfer 在途 | 出库(C) → 在途(P) → 入库(R) | 在途丢失 → 冲销 + 重发；不得静默标记 `RECEIVED` |

> **编排状态必须持久化**：`t_proc_orchestration_step` 在发出每一步命令前落库（B7：orchestrator 崩溃后从最后已知步骤恢复，不重复触发补偿）；`correlation_id = trace_id` 贯穿，监控 Saga 时长，超时即告警。

**负向探针（S1–S4）**：① 并发取消订单与审批通过交错（语义锁缺失 → 丢失更新）；② pivot 之后失败触发前序补偿；③ 补偿重复执行两次（幂等缺失 → 库存回冲两次）；④ orchestrator 重启后重复触发补偿。四条均须注入必红、还原必绿。

## 16. 事件契约工件、注册表与演进（B8 / B10）

**16.1 两类事件不得混用**：① **领域内部事件**（各卷 §5 状态机里 `supplier.activated` 这类小写事件）同进程同步分发，**不落 Outbox、不进注册表**；② **集成事件**（§7 的 CamelCase `eventType` + 8 字段信封）跨部署单元，必须登记附录 B。v0.1 未区分，易被实现者误当成同一套。

**16.2 单一 schema 真源（v0.3 收口，拆解诊断 P0-5 自指环）**：**总纲附录 B 是事件注册表的唯一真源（生成源）**；`contracts/asyncapi.yaml` 是**由 `generate_asyncapi.py` 从附录 B 生成的派生物**；各卷 §7 是速查视图，**INBOUND 事件的唯一 payload 定义见 `采购AI-接口契约与数据字典-v2.md §2`**。**冲突以附录 B（及其引用的真源）为准，回改工件或消费方并重跑生成器；禁止反向改附录 B 以迁就派生物**（裁决链见 `文档资产登记与真源裁决.md §4.2` 第 8 条）。门禁 A8 双向校验的是「工件是否忠实于真源」，并额外比对总体 §7.1 / 领域 §6.2 的冻结值。**Producer owns schema**；消费方不得自行重述或裁剪 payload 语义。

**16.3 每条事件契约必须写全 9 项**：`eventType / topic / schemaVersion / payload JSON Schema / owner(生产方) / producer / consumers[] / partition_key / delivery + ordering + retention + latency + producer guarantee`。其中 delivery 默认 **at-least-once**（Outbox 不提供 exactly-once），消费侧必须 Inbox 幂等（§6）。

**16.4 兼容性规则（版本内）**

| 变更 | 允许 | 说明 |
|------|------|------|
| 新增**可选**字段 + 默认值 | ✅ | 旧消费者忽略；新消费者读旧数据得默认值 |
| 新增描述 / 示例 | ✅ | — |
| 删除 / 改名 / 改类型 / **改单位或含义** | ❌ | 改含义最危险：schema 不变但数据全错（如 cents→dollars） |
| 新增必填字段 | ❌ | 存量在途事件缺该字段 |
| **枚举扩容** | ❌（按破坏性处理） | 旧消费者穷举 switch 会崩；要么 `.v2`，要么所有消费者证明容忍未知值 |
| 无 `eventId` / 顺序假设不绑定 `partition_key` | ❌ | 无法去重 / 顺序不成立 |

**16.5 Tolerant reader（消费侧强制）**：忽略未知字段；未知枚举值映射到 `UNKNOWN/OTHER` 路径并**隔离告警**，不得崩溃、不得静默压成「失败」或「通过」（与 AI 三态 `UNKNOWN` 不得压成「AI 未参与」同一纪律）；只读取自身需要的字段；**禁止 `additionalProperties: false` 式严格校验**把生产方的加性变更变成破坏性。永久无效 / 瞬时失败 / 未知版本三类分别处理，不得一律 catch 后提交位点。

**16.6 破坏性变更迁移**：新建 `.v2` topic → 双发布 v1+v2（迁移窗口）→ 消费组指标确认 v1 无人订阅 → 下线 v1。双发布期间须给两种表示可追溯的关联，且**不得让两个消费者各应用一次业务效果**。

**16.7 Replay 是独立契约（B8）**：重放只用于**重建投影 / 审计历史**，必须抑制不可逆副作用（付款请求、邮件、Webhook、AI 计费调用）；重放须记录 code / schema / reference-data 版本，否则「五年前的事件用今天的税率重算」会产出错误结果。06 卷 `/ops/events/{id}/replay` 与 `/ops/dead-letters/{id}/redeliver` 必须标注 `mode=REBUILD|REDELIVER`，默认 `REBUILD`。

**16.8 冻结例外与入站归属（P0-3 / P0-4，实证校准）**

| 事实 | 处置 |
|------|------|
| 总体 §7.1 已冻结 `po_created.v1` / `gr_recorded.v1` / `po_acknowledged.v1` 等缩写 topic，与 §3 的 `<aggregate>_<verb>` 规则不符 | **登记为冻结例外**，缩写白名单 `po / gr / rfx / asn / ir / capa / rtv / pr / recon`；**不得改名**（改名即双真源）；新事件一律用全拼 |

## 17. API 契约工件与错误语义（B11）

**17.1 工件与流程**：`contracts/openapi.yaml`（OpenAPI 3.1）为 REST 真源，先评审 schema / 错误 / 授权 / 幂等再写 handler；端点清单由各卷 §6 给出，门禁 A8 校验关键路径存在、**A10.9 按 (method, path) 校验六卷 §6 与工件的双向全覆盖**（55 行 / 54 唯一组合，另允许 5 个跨域只读投影端点；下界与白名单写死在门禁内作外部锚点）。路径模板参数一律在 Path Item 级 `parameters` 声明，`no` 等 YAML 1.1 歧义词加引号。接口变更遵循 §16.4 的加性规则；破坏性升 `/api/v2` + `Sunset` + 用量遥测。

**17.2 错误体**：采用 **RFC 9457 `application/problem+json`** 作为机器可读错误格式，与 HC-003 的 `ApiResponse<T>` **兼容共存**——成功响应仍为 `ApiResponse<T>`；错误响应若平台统一异常处理器尚未支持 `problem+json`，则在 `ApiResponse` 的扩展字段中提供同语义成员，不得两套语义。**客户端只按 `type`（稳定 URI）与 `code`（`31xxx`）分支，禁止解析 `detail` 文案**。

```json
{
  "type": "https://bone.example/problems/invalid_transition",
  "title": "Invalid state transition",
  "status": 409,
  "code": "31403",
```

**17.3 状态码与可重试性**（驱动客户端行为，不得泛化 400）

| 码 | 语义 | 客户端 |
|----|------|--------|
| `400` / `422` | 语法错误 / 语义校验失败 | **不重试**，改请求 |
| `401` / `403` / `404` | 未认证 / 无权限 / 不存在 | 不重试；越权返回**零数据** |
| `409` | 版本冲突、非法迁移、幂等键指纹冲突、重复业务键 | 不重试，按 body 决策 |
| `429` | 限流 | 退避重试，遵 `Retry-After` |
| `5xx` | 服务端 / 上游失败 | **同 `Idempotency-Key` 退避重试** |

**17.4 分页**：列表接口默认 `page/size/sort`（小后台表可用）；**大表、流水、事件、审计、DLQ、对账例外一律 cursor/keyset**（`?limit=&cursor=`，opaque `next_cursor` + `has_more`），服务端强制 `max_page_size`，**禁止 `COUNT(*)` 精确总数**（深翻 O(n) 且在并发写入下会跳/重记录）。RFC 8288 `Link` 头承载 `rel=next`。各卷 §6 的 `GET` 列表须标注采用哪种。

**17.5 幂等状态机**：`Idempotency-Key` + `sha256(canonical_body)` 绑定；首次处理中返回 `409 Request in progress`；已完成且指纹相同**回放原响应**（不重执行）；同键不同指纹 `409`；保留 24h（D3 §1）；清理作业见 §18.5。

**17.6 契约测试**：基于 OpenAPI/AsyncAPI 的 schema diff 与消费者驱动契约测试进 CI；每卷至少覆盖：未知字段容忍、未知枚举隔离、缺失可选字段、错误体 `type` 稳定性、cursor 翻页在并发写入下不重不漏。

## 18. 物理数据模型、索引理由与容量（B10 / B11）

**18.1 列类型基线**（覆盖各卷 §4 业务列）

| 语义 | 类型 | 备注 |
|------|------|------|
| 金额 / 单价 / 税额 | `DECIMAL(19,4)` + `currency CHAR(3)` | 禁用 `FLOAT/DOUBLE`；金额与币种同行（D-02） |
| 汇率 / 税率 / 比率 | `DECIMAL(19,8)` | 汇率保留全精度，只在最终换算后舍入（D-05） |
| 数量 | `DECIMAL(19,6)` + `uom` | 基准单位换算快照 |
| 时间 | `DATETIME(3)` UTC | ISO-8601；`occurred_at` 有索引 |
| JSON 扩展 | `JSON` / `TEXT` | 仅长尾属性；**不得在 JSON 列上做范围查询或主过滤**（CORE-09） |
| 大对象 | 对象存储引用 | Claim Check：Outbox / 事件 payload 只放引用，避免大 payload 撑爆 broker 限制 |

**18.2 access pattern → index 映射**：每卷 §4 的「唯一键 / 索引」列必须能回答「哪条查询用、为什么这个顺序」。规则：联合索引遵守最左前缀；高选择性列靠前；区分 `uk_`（约束）与 `idx_`（查询）；避免低选择性单列索引（`status` 单独建索引通常无效，应与 `tenant_id + 时间` 组合）；覆盖索引减少回表。示例：`t_proc_po(vendor_id,status)` 服务于「按供应商查未结 PO」；`t_proc_outbox(status,next_retry_at)` 服务于中继扫描；`t_proc_qualification(expires_at)` 服务于到期巡检。

**18.3 软删与唯一键冲突（v0.1 未处理的真实缺陷）**：`deleted` 逻辑删除 + `uk(tenant_id, code)` 会导致**同编码删除后无法重建**（唯一键仍被软删行占用）。统一处置：唯一键纳入 `deleted` 语义（如 `uk(tenant_id, code, delete_token)`，`delete_token=0` 表示有效、删除时置为行 id）或在应用层先校验「存在软删同码」并走**恢复流程**；**禁止物理 DELETE 规避**。各卷 §4 的 `uk` 定义按此复核。

**18.4 深分页 / 批量 / N+1**：列表走 cursor（§17.4）；批量写入分批提交、单条隔离（领域 §7.6）；`@Sql` 手写模板禁止 N+1（一次取齐或 JOIN）；禁止无界 `IN`。

**18.5 归档与分区**：`t_proc_outbox` / `t_proc_processed_event` / `t_proc_idempotency_record` / `t_proc_audit_event` / `t_proc_acl_call_log` 按时间分区，过期**按分区 DROP**（避免大 `DELETE` 事务与索引膨胀）；审计与对账留痕按合规期限归档（L11 / L30）。Outbox 清理策略：published 后短审计窗口删除，或 CDC 场景 insert+delete 同事务（B10）。

**18.6 容量假设 → 压测门禁**：供应商 / Vendor 角色 / 日均 PO 与行 / 发票与 IR 例外率 / 峰值系数 / 批量对账量级取自总体 §8.3（**草案，禁止当既定事实**）；冻结前以真实样本压测，把 P99、慢查询 Top-N、Outbox backlog 结论回填总体 §8.3 与总体 §12.2。

**18.7 EAV 边界重申**：核心/事务/高频字段必须物理列；扩展字段走 SDK EAV（`ExtensionMode`）；EAV 上做范围查询视为性能事故（CORE-09、能力基线 §3）。

## 19. 可观测、韧性与运行就绪（B10 / B11）

**19.1 结构化日志字段（全链路统一）**：`ts, level, trace_id, span_id, tenant_id, actor_id, actor_type, resource_type, resource_id, event_id, endpoint, outcome, latency_ms, error_code`。**禁止**记录 PII、报价明文、AI `output` 原文、HMAC 密钥、`envelope_json` 原文。

**19.2 OTel span 划分**：`HTTP inbound → ApplicationService → Repository / ACL 出站 → OutboxWriter → Relay → Consumer → Inbox 占位 → 业务副作用`；跨进程经 `traceId` 透传（与 HTTP MDC 一致，事件规范 §3）。

**19.3 指标（RED per route + USE for 资源 + 业务）**

| 指标 | 定义 | 告警 |
|------|------|------|
| `http_requests_total{route,status}` / `http_request_duration_seconds` / error rate | RED | 见 §19.4 |
| `proc_outbox_oldest_unpublished_seconds` | `now() - min(created_at) WHERE status IN (PENDING,FAILED)` | **最关键**：中继/ broker 故障 |
| `proc_outbox_backlog` / `proc_stuck_rows` / `proc_dlq_total` | 积压 / 卡住 / 死信 | 持续增长即升级 |
| `proc_consume_fail_rate` / `proc_inbox_duplicate_total` | 消费失败 / 重复投递 | 幂等是否生效 |
| `proc_recon_diff_count{channel}` / `proc_ai_degrade_rate` | 对账差异 / AI 降级 | 与总体 §8.3 SLO 对齐 |

**19.4 告警规则（阈值 → 动作 → 升级）**：阈值数值属 L30 / 总体 §8.3 待冻结；结构固定为「指标 + 窗口 + 阈值 → 自动动作（重试/熔断/降级）→ 通知 Owner → 超时升级 SRE / 财务域」；告警须带 `trace_id` 样本与 runbook 链接，禁止无动作告警。

**19.5 就绪与优雅停机**：liveness（进程存活）与 readiness（依赖装配 / 配置 / 连通性）分离；`/ops/readiness` 沿用三层分离（部署态/配置态/运行期）且**就绪 ≠ 放行许可**；SIGTERM 先停止接新请求、drain 在途、再关连接池，编排器宽限期 > 最慢请求。

**19.6 Outbox 运行纪律（06 卷必须实现）**：① 业务表 + outbox **同本地事务**；② 中继 `SELECT ... FOR UPDATE SKIP LOCKED` 轮询，多实例按 `partition_key` 分片避免同聚合并发重排；③ **broker confirm 之后**才置 `PUBLISHED`（先标记后确认 = 丢事件）；④ 超限转 `platform.dead_letter.v1` 并告警；⑤ 大 payload 用 Claim Check；⑥ 清理/归档按 §18.5；⑦ 轮询延迟或 DB 负载成为实测瓶颈后，才评估 CDC/Debezium，并须监控复制槽 LSN 与 WAL 保留（B10 明确这是最大运维风险）。

**19.7 SLO 与诚实登记**：数值引用总体 §8.3 草案，error budget 用于决定是否放行发布；**日终 01:00 对账不宣称「每小时不变量」**（06 卷 §12 已如实登记），关键通道小时级巡检作为补充。

## 20. 安全 SDL 与 AI 治理落地（B11 / 合规 §21–§24）

**20.1 Webhook HMAC**（`X-Bone-Signature`，能力基线 §5.3 自建）：签名覆盖 **timestamp + 原始 body 字节**；`kid` 版本化密钥 + **定期轮换**；时间戳窗口 + **nonce 重放缓存**（窗口内 `eventId`/nonce 唯一）；**常量时间比较**；失败记安全告警且不泄露原因细节。四类负向探针（错误签名 / 重放 / 过期 / 篡改 body）之外，v0.2 增补：⑤ 轮换期旧 `kid` 仍可用、⑥ 未知 `kid` 拒绝、⑦ body 被 JSON 重新序列化后签名失配。

**20.2 外部账号生命周期**：邀请 → 激活 → 定期复核 → **冻结**（供应商 `EXITED` / Vendor `INACTIVE_VENDOR` / 风险 `SUSPENDED` 时自动冻结）；支持供应商侧委派管理员，权限仍受 `vendor_id` 绑定；BFF **不接受客户端传入 `vendor_id`**；账号与 `tenant_id + vendor_id + supplier_id` 三重谓词绑定。

**20.3 文件上传**（资质证照 / 合同附件 / 发票附件）：MIME 白名单 + 大小上限 + 病毒扫描 + 私有对象存储 + 短时效签名 URL；业务库只存引用与哈希；文件名不可信、路径不可拼接；扫描未完成不得置 `VERIFIED` / `SUBMITTED`。

**20.4 IDOR / 越权**：所有详情与写操作按 §20.2 三重谓词；越权返回 `403` + 零数据（不得靠 404 泄露存在性差异）；批量接口逐条鉴权，禁止「取一批再过滤」。

**20.5 审计防篡改**：`t_proc_audit_event` 只追加；`before_hash/after_hash` 之外增加**链式哈希**（`prev_hash`）或 WORM/不可变存储；审计库账号与业务库账号分离；禁止 `UPDATE/DELETE` 权限给应用账号；按 `trace_id` 可重建时间线。

**20.6 AI 治理：人工在环的可审计覆盖**（03/02 卷落地）：每条 AI 建议记录 `review_id / model_version_snapshot / ai_available 三态 / 建议内容哈希`；人工**采纳或覆盖**必须留 `decided_by + decision + reason + 时间戳`；`model_version_snapshot` 仅作版本溯源，**不得冒充参与证据**（只认 LLM 节点自报 `aiAvailable`）；`UNKNOWN` 不得展示为「AI 未参与」；生成内容显著标识 + 留存；评测集 / 漂移监控 / 升版回归门禁（L09 / L13）冻结前不得上线自动决策。

**20.7 PII 与长保留 topic**：事件长期保留与可重放，故 payload **只传 ID 与 hash**（B8）；确需个人数据用按主体加密密钥以便 crypto-shred；AI 入参禁 PII（合规 §24）；对客生成内容按合规 §29 标识。

**20.8 安全 / AI 负向探针（各卷 §11 引用）**：S-1 轮换期旧密钥误拒/未知密钥误放；S-2 nonce 重放；S-3 病毒扫描未完成的附件被置 `VERIFIED`；S-4 审计行被 `UPDATE`；S-5 AI 建议被人工覆盖但无 `decided_by`；S-6 事件 payload 出现身份证号；S-7 供应商退出后外部账号仍可登录。逐条注入必红、还原必绿。

**23.2 容量口径**：行数用「万 / 千」或带千分位分隔符书写（避免与错误码编号混淆）；QPS 区分常态与峰值；批量上限须与 §17.4 `max_page_size` 一致；每个索引在 §13.2 复述一次 access pattern，**不得只写「同上」**。

**23.3 SLO 口径**：业务 SLO 用业务结果（准入 TAT、PO 下达时延、匹配结果回传时延、outbox 投递时延），技术 SLO 用 RED/USE；error budget 决定是否放行发布；告警必须带自动动作 + Owner + 超时升级，禁止「只通知不动作」。

**23.4 降级口径**：FMEA 每行必须写清「恢复后如何核对」——事件驱动用 Inbox/Outbox 对账，批处理用重跑 + 差异台账，外部系统用增量轮询对账（D3 §4）；**Finance 裁决、付款放行、AI 自动决策三类一律不可降级为「推断通过」**。

**23.5 回滚口径**：回滚前先停写、再按 `trace_id` 圈定影响面；已发事件**不得撤回**，用补偿事件或重放 `REBUILD` 修投影（§16.7）；涉及外部系统的回滚须有幂等补偿，无法补偿的写进待决而非假装可回滚。

**23.6 保留口径**：业务主档按合规期限软删保留；PII 列按主体密钥加密以便 crypto-shred（§20.7）；报价密文在授标关闭后按客户要求可删除，但**hash-chained 审计不可删**；密钥销毁须晚于最后一份密文的保留期。

**23.7 读模型口径**：跨聚合列表一律走本卷投影表或一次取齐 JOIN，禁止 N+1 与无界 `IN`（§18.4）；投影是**最终一致**，必须给 staleness 上界与「读不到时回源」策略，禁止把投影当权威强一致数据。

**23.8 测试口径**：契约测试基于 `contracts/openapi.yaml` / `asyncapi.yaml`；负向探针（§11）逐条「注入必红 / 还原必绿」；性能用例以 §13.2 容量草案为输入，冻结前回填 P99 与慢查询 Top-N（§18.6）。
