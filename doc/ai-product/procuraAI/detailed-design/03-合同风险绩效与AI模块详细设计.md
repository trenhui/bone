## 1. 模块定位与边界

**拥有的业务结果**：合同从起草、AI 辅助审查、法审、用印到生效/终止的全生命周期；供应商风险预警、绩效计分与整改（CAPA）闭环；procuraAI 作为**独立智能体**以端口方式接入，不侵入业务域。

| 在范围内 | **非目标（Non-goals）** |
|----------|------------------------|
| Contract / Clause / 合同审查结论挂接 / 用印审批 | ❌ 不做电子签章 CA 能力（接 OA/ERP，D3 §4 webhook） |
| RiskAlert / CorrectiveAction / PerformanceScore | ❌ 不做付款冻结裁决（Finance/风控触发，01 卷只消费事件） |
| procuraAI M2 风险审查 / M7 起草 / M5 问答 / 预警 | ❌ **AI 不自动法审、不自动用印、不自动关闭 CAPA**；人工最终决策 |
| 合同价 → PriceCondition 派生（写归 04 卷） | ❌ 不回写 `contract_no` 作为结论（D3 §2 实证：`contract_no` 是**审查入参关联键**） |

**AI 治理基线（总体 §5.1 + 合规）**：AI 仅辅助 + 人工最终决策；PII 禁入；三态能力码（`available/unknown/unavailable`）fail-closed；`model_version` 是入口可填快照，**不得冒充参与证据**；证据不回传 `output` 原文；生成内容显著标识 + 留存可审计。

## 2. C4 L3 组件视图

> **关键链路时序（总纲 §21.5）**：[关键链路时序图](../assets/procuraAI-关键链路时序.svg) 序列 ① / ② —— `ContractSigned` 前置与「AI 结论不进资金裁决链路」边界。下方 ASCII 仅描述组件结构；跨组件时序、外部 INBOUND 与故障分支一律以该图为准，不用 ASCII 框图代替时序。

```
adapter/web   ContractController · ClauseController · RiskAlertController · CapaController
adapter/messaging  ContractReviewedConsumer · RiskAlertRaisedConsumer(01卷反向)
     │
     ▼
application  ContractApplicationService   （起草/送审/用印/生效）
             ContractReviewLinkService    （review_id / review_snapshot_ref 挂接）
             RiskAssessmentService        （风险聚合、阈值判定）
             CapaApplicationService       （整改闭环编排）
             PerformanceScoreService     （计分卡与只读投影）
     │  port/out: AiReviewPort → procuraai-runtime · OaAclPort ·
     │            ContractQueryPort(读) · WorkflowStatusPort(S) · EventPort
     ▼
domain       Contract / Clause / ContractReviewLink / RiskAlert /
             CorrectiveAction / PerformanceScore
     ▼
infrastructure  t_proc_contract / t_proc_clause / t_proc_contract_review_link /
                t_proc_risk_alert / t_proc_corrective_action / t_proc_performance_score
```

| 组件 | 职责 | 拥有的状态 | 依赖 |
|------|------|-----------|------|
| `ContractReviewLinkService` | AI 结论以 `review_id` + `review_snapshot_ref` 挂接，不改写合同号 | `t_proc_contract_review_link` | D3 `review_snapshot` |
| `RiskAssessmentService` | 聚合信用/履约/合规信号，输出 `RiskAlert` | `t_proc_risk_alert` | `vendor_profile`（只读）、外部信用源 |
| `CapaApplicationService` | 整改计划、复核、关闭；子流程用串行节点模拟 | `t_proc_corrective_action` | WF 主干（含 `rejectToNode` / `CC`） |
| `AiReviewPort` | 调独立 AI 运行时，降级 `rules_only` | 无（无状态调用） | HMAC/mTLS、traceId |

> **独立 AI 运行时**：`procuraai-runtime` 独立库/对象存储（快照、语料、向量），业务模块只经端口调用（总体 §5.1、§8.1）；**不把 LLM 网关塞进业务模块**。

## 3. 领域模型与不变量

| 聚合根 | 关键实体 | 强一致不变量 |
|--------|----------|--------------|
| `Contract` | 主体、金额、有效期、`contract_no`、状态、用印实例 | **INV-01** `(tenant_id,contract_no)` 唯一；**INV-02** `EFFECTIVE/TERMINATED` 终态不可回写；**INV-03** `EFFECTIVE` 前必须法审通过 + 用印审批通过 |
| `Clause` | `STANDARD/ALTERNATIVE/FORBIDDEN`、版本、`legal_reviewed` | **INV-04** 仅 `legal_reviewed=true` 的条款可被起草引用；**INV-05** `FORBIDDEN` 条款出现即阻断送审 |
| `ContractReviewLink` | `review_id, review_snapshot_ref, risk_level, model_version_snapshot` | **INV-06** 结论只挂 `review_id`，**不得写 `contract_no` 作为结论**；**INV-07** 快照不可变、不存 `output` 原文 |
| `RiskAlert` | 来源、严重度、`alert_task` 引用、处置状态 | **INV-08** 同一 `(supplier_id, source, source_ref)` 去重；**INV-09** 预警不直接改 Supplier 主档（发事件由 01 卷裁决） |
| `CorrectiveAction` | 计划、责任人、复核结论、WF 实例 | **INV-10** 关闭须复核通过 + 审批；**INV-11** 子流程缺失时用串行节点 + `stage` 字段模拟，不得伪造嵌套实例 |
| `PerformanceScore` | 交付/质量/成本/合规维度、期间 | **INV-12** 只追加、按期唯一；评分输入可追溯（`evidence_ref`） |

## 5. 状态机

> **v0.2（总纲 §21.1–§21.3）**：本节状态须落为枚举 + **显式迁移表** `Map<State, Map<Event, Transition>>`，守卫集中在 domain 层；**迁移表未列出即拒绝**（fail-closed），非法迁移返回 §17.2 的 `invalid_transition`（带 `current_state/attempted/allowed[]`）；状态迁移与 `@Version` CAS 同事务；终态不可回写由 domain 守卫 + 唯一约束双保险。本节小写领域事件（如 `supplier.activated`）属**领域内部事件**，不落 Outbox、不进注册表（总纲 §16.1）。

**Contract**：`DRAFT → REVIEWING → LEGAL_REVIEWED → PENDING_SEAL → EFFECTIVE → EXPIRED / TERMINATED`

| From | Event | Guard | To |
|------|-------|-------|----|
| `DRAFT` | `submit_review` | 无 `FORBIDDEN` 条款 + AI 审查快照已挂接（降级时标 `rules_only`） | `REVIEWING` |
| `REVIEWING` | `legal_approved` | 法务人工确认（**AI 不得代替**） | `LEGAL_REVIEWED` |
| `LEGAL_REVIEWED` | `seal_requested` | 用印审批启动 | `PENDING_SEAL` |
| `PENDING_SEAL` | `sealed` | WF 用印审批通过 + OA `contract.signed` 回执 | `EFFECTIVE` |
| `EFFECTIVE` | `expire / terminate` | 到期或终止审批 | `EXPIRED` / `TERMINATED` |

**CorrectiveAction**：`OPEN → PLAN_SUBMITTED → IN_PROGRESS → VERIFIED → CLOSED`；`REJECTED` 用 WF `rejectToNode` 退回 `PLAN_SUBMITTED`。

**RiskAlert**：`OPEN → ACKNOWLEDGED → MITIGATING → RESOLVED / FALSE_POSITIVE`。

**禁止迁移**：`EFFECTIVE → DRAFT`；`TERMINATED → 任意`；`DRAFT → EFFECTIVE` 跳步；AI 结论直接置 `LEGAL_REVIEWED`；`CLOSED → OPEN` 须新建 CAPA。

> **WF 能力校准（能力基线 §4）**：退回指定节点、改派、转办、加签、抄送、挂起恢复均已实现，**直接复用**；真缺口仅子流程与 SLA 超时转交 ⇒ CAPA 子流程用串行节点 + `stage` 模拟，SLA 用日终巡检 + 通知催办 + `reassignTask` 人工干预。

## 6. API 契约

> **v0.2（总纲 §17 / 附录 A）**：错误码以总纲附录 A 为唯一真源（含新增 `317xx` 段）；错误体采用 RFC 9457 `application/problem+json` 并与 HC-003 `ApiResponse<T>` 兼容（§17.2）；大表 / 流水 / 审计 / DLQ 列表用 cursor 分页 + 服务端 `max_page_size`（§17.4）；状态码与可重试性见 §17.3；契约工件 `contracts/openapi.yaml`。

| 方法 | 路径 | 权限码 | 幂等键 | 说明 |
|------|------|--------|--------|------|
| `POST` | `/api/v1/procurement/contracts` | `procurement:contract:write` | `Idempotency-Key` | 起草（D3 §2 以 `contract_no` 关联） |
| `POST` | `/api/v1/procurement/contracts/{no}/reviews` | `procurement:contract:write` | `Idempotency-Key` | 发起 AI 审查（异步，返回 `review_id`） |
| `GET` | `/api/v1/procurement/contracts/{no}/reviews/{reviewId}` | `procurement:contract:read` | — | 结论（含三态能力码、快照引用，**不返回 output 原文**） |
| `POST` | `/api/v1/procurement/contracts/{no}/legal-approve` | `procurement:contract:approve` | `Idempotency-Key` | 人工法审通过 |
| `POST` | `/api/v1/procurement/contracts/{no}/seal` | `procurement:contract:approve` | `Idempotency-Key` | 用印审批（`SINGLE/ALL/ANY` 会签） |
| `GET` | `/api/v1/procurement/clauses` | `procurement:clause:read` | — | 条款库（分页） |
| `POST` | `/api/v1/procurement/risk-alerts` | `procurement:risk-alert:write` | `(supplier_id,source,source_ref)` | 预警登记（去重） |
| `POST` | `/api/v1/procurement/capas` | `procurement:corrective-action:write` | `Idempotency-Key` | 建整改单 |
| `POST` | `/api/v1/procurement/capas/{no}/verify` | `procurement:corrective-action:approve` | `Idempotency-Key` | 复核（人工） |
| `GET` | `/api/v1/procurement/performance-scores` | `procurement:performance-score:read` | — | 只读投影 |

请求示例（`POST /contracts/{no}/reviews`）：

```json
{
  "contract_no": "CT-2026-0088",
  "review_type": "RISK",
  "clause_library_version": "v3",
  "requested_by": "legal-2048"
}
```

响应 `202`：`{"code":"OK","data":{"review_id":"rv-01J...","ai_available":"UNKNOWN","status":"PENDING"},"trace_id":"..."}`

> **`ai_available` 三态**：`AVAILABLE / UNKNOWN / UNAVAILABLE`；`UNKNOWN` 不得展示为「AI 未参与」，降级 `rules_only` 时诚实标注（总体 §5.1、借鉴 synap-claim P0-3）。

**错误码**（总纲附录 A）：`31301` 条款未法审、`31302` 审查快照缺失、`31303` 终态合同回写、`31304` AI 结论回写原文（PII）、`31305` 未知能力码被压成未参与。D3 段 `31xxx` 复用；非法迁移 `409 invalid_transition`。

## 7. 事件契约

> **v0.2 契约校准（总纲 §16 / 附录 B）**：本表 `eventType` 的 **topic / partition_key / owner / consumers / schemaVersion 一律以总纲附录 B 事件契约注册表为准**，payload 字段**唯一真源 = `contracts/asyncapi.yaml`**；本表仅为字段速查，**不重复定义 topic**（避免双真源）。所有事件已按事件规范 §4「先登记注册表 → 再写 Producer」登记；门禁 **A8** 校验本表 eventType 均在注册表内、且注册表 topic 与 AsyncAPI channel 一一对应。顺序敏感链路 `partition_key = tenant_id + <aggregate_key>`（总纲 §6 双轨）且 payload 带 `aggregate_version` 供乱序丢弃；消费侧为 tolerant reader（§16.5）+ Inbox 幂等（§6），delivery 为 at-least-once。**`INBOUND`** 事件由外部上下文生产、沿用上游冻结 topic（L31 待裁决），采购域只读、不裁决。

| 方向 | eventType（topic / partition_key / owner 见总纲附录 B） | payload 字段速查（真源 `contracts/asyncapi.yaml`） | 幂等 / 顺序 / 失败 |
|------|-------------------|------------------|--------------------|
| 消费 | `ContractReviewed`（**INBOUND** / procuraAI，已冻结） | `review_id, contract_no, risk_level, risk_items_hash, review_snapshot_ref, ai_available, model_version_snapshot` | `review_id` 唯一；**不消费 `output` 原文** |
| 生产 | `ContractSigned`（LLD 新增） | `contract_no, supplier_id, effective_from, valid_to, price_condition_ref` | `contract_no`；同合同保序 |
| 生产 | `RiskAlertRaised`（已冻结，领域 §6.2） | `alert_id, supplier_id, severity, evidence_ref` | `(supplier_id,source,source_ref)` 去重 |
| 生产 | `CorrectiveOpened` / `CorrectiveSubmitted`（LLD 新增） | `capa_no, supplier_id, stage, workflow_instance_id` | `capa_no`；同 `capa_no` 保序 |
| 生产 | `PerformanceScored`（LLD 新增） | `supplier_id, period, total_score, evidence_ref` | `(supplier_id,period)` |
| 消费 | `SupplierChanged`（01 卷） | `supplier_id, supplier_version` | 更新合同主体只读投影 |
| 消费 | `InvoiceMatched`（**INBOUND** / Finance，只读） | `invoice_no, blocked_reason?` | 仅作风险信号，不裁决 |

## 9. 工程治理

> **v0.2（总纲 §14 / §15 / §19）**：金额与汇率语义见 §14（D-01–D-09）；长流程步骤按 `COMPENSATABLE / PIVOT / RETRIABLE` 三分类并登记补偿（§15），编排状态持久化 + 语义锁 / 可交换更新 / 重读值；Outbox 运行纪律见 §19.6（**broker confirm 后才置 `PUBLISHED`**、`FOR UPDATE SKIP LOCKED`、最老未发件年龄告警、Claim Check）；重放 `mode=REBUILD` 抑制不可逆副作用（§16.7）；指标与告警见 §19.3–§19.4。

>
> **时序证据（总纲 §21.4–§21.5）**：[关键链路时序图](../assets/procuraAI-关键链路时序.svg) 序列 ① / ② 给出生效路径与故障分支；E2E 必须覆盖重试、批量部分失败、提交后确认失败，并在 §11 负向探针留痕。

| 项 | 设计 |
|----|------|
| 事务 | Contract 与 Clause 引用同聚合本地事务；`ContractReviewLink` 与合同状态更新同事务；终态检查在 domain 层守卫 |
| 幂等 | 审查请求 `Idempotency-Key` + `review_id`；事件消费 `(consumer_group,event_id)`；预警业务键去重 |
| 补偿 | AI 审查超时/不可用 → 三态 `UNAVAILABLE` + `rules_only` 降级 + 人工复核，**不静默放行**；OA 回执丢失 → 15min 轮询增量对账（D3 §4） |
| 批量 | 批量审查 `POST /reviews/batch`（D3）：FIFO + 优先级、单条隔离、重试 ≤3、保留原始输入 |
| 并发 | `@Version`；终态不可回写在 domain 守卫 + 唯一约束双保险 |
| 缓存 | 条款库短 TTL + 版本戳；`clause_library_version` 参与 AI 请求指纹，避免版本漂移 |
| 降级 | LLM 不可用 `rules_only`；`UNKNOWN` 三态诚实展示；审查结论**不回传输出原文**（PII） |
| 留存 | `review_snapshot_ref` + `risk_items_hash` + 审计事件；留存期限按合规与客户合同（待 D7） |

> **定位**：把总纲 §23 八项要素实例化到合同 / 风险 / 绩效 / AI 接入；本章**不新增事件 / 错误码 / 权限码**，不动 v0.1 已冻结的 AI 三态与「人工最终决策」结论。数值均为草案（L38）。
> **依据**：B14（CLM 义务管理与 AI 合同审查治理），总纲 §23.9 → 03 卷。

**13.1 差异化核心算法：义务日历 + AI 字段级评测闭环 + CAPA 有效性**

1. **先义务、后审查**（B14 顺序不可倒）：已签合同先做条款抽取 → `ObligationCalendar`（义务 / 触发条件 / 通知期 N 天 / owner / 证据要求）→ 自动续约与到期告警；审查自动化排在其后。通知期从条款抽取，**抽取不到必须人工补录，不得默认 0 天**。
2. **义务状态机**：`PENDING → DUE（now ≥ deadline − N）→ FULFILLED | BREACHED`；`BREACHED` 只由 owner 关闭并附证据。自动续约在 `deadline − N` 触发「是否终止」人工决策，**AI 不得代为续约或终止**。
3. **条款 redline 基线**：条款库按 `clause_version` 版本化，审查结论挂 `review_id` 与 `clause_version`；同版本同输入必须得到同结果（可复现），升版需法务复核。
4. **AI 字段级评测**（非整体「准确率」）：`precision_field = TP/(TP+FP)`、`recall_field = TP/(TP+FN)`；高后果条款（责任上限 / 自动续约 / 单方终止 / 数据合规 / 管辖与赔偿）权重 `w=3`，其余 `w=1`；**加权 recall 不得随升版下降**（L41 定阈值）。
5. **三分区与人工闸门**：高置信 + 低后果 → 可直出建议供法务采纳；高置信 + 高后果 → 强制双人复核；`available=false` / 低置信 → `rules_only`，**不降级为「推断通过」**。记录 **override 率**与「自信的错误答案」计数（AI 高置信但被人工推翻），后者是漂移的先行指标。
6. **漂移复跑**：模型 / 提示词 / 条款库任一变更 → 用**固定评测集**复跑，比对字段级 precision / recall / 高后果 recall / override 率；未复跑即放量由发布门禁阻断（M3-12）。评测集与证据不回传 `output` 原文（§20.8，禁 PII）。
7. **CAPA 有效性验证**：整改关闭后 T+30 / T+90 复查同类风险是否复发，复发则 `REOPENED` 并重定根因；关闭动作必须附有效性证据，不允许「填完即关闭」。

| 条件 | 判定 | 动作 |
|------|------|------|
| 通知期已到但日历无告警 | 义务漏管 | 日终巡检转红 + P2 告警（M3-11） |
| 抽取不到通知期 | 不确定 | 人工补录前 `DUE` 不可自动计算，禁止默认 0 天 |
| 高后果字段 + 高置信 | 高风险结论 | 强制双人复核，记录 override |
| 模型升版未复跑固定评测集 | 漂移未证 | 发布门禁拒绝（M3-12） |
| AI 不可用 | `available=false` | `rules_only` + 人工最终决策，不推断通过 |
| CAPA 关闭无 T+30 有效性证据 | 假闭环 | 拒绝关闭，进差异台账 |

8. **反例**：AI 以 0.97 置信度把「自动续约」条款判为无风险，人工复核推翻 → 必须计入「自信的错误答案」并触发评测集增补，**不得静默采纳**。

**13.5 上线四闸门与回滚（总纲 §22.1 / 总体 §8.4）**

- **feature flag 粒度**：`tenant_id × contract_type × flow(OBLIGATION_CALENDAR / AI_REVIEW_V2 / CAPA_EFFECTIVENESS)`，AI 开关与义务日历开关解耦，默认全关。
- **历史数据回填**：已签合同批量抽取义务与通知期，**抽取不到的一律标 `UNKNOWN` 转人工补录**（不得压成「无义务」）；回填不触发对外通知。
- **灰度维度与观测窗**：按合同类型 5% → 25% → 100%，每级 ≥ 2 周（覆盖一次通知期），观测义务告警覆盖率 / override 率 / 自信错误数 / 高后果 recall。
- **回滚触发**：义务漏告警 ≥ 1、高后果 recall 下降、AI 结论出现 PII 原文外泄、`available` 三态被压成布尔。
- **本卷回滚代价（诚实登记）**：**已送达相对方的续约 / 终止通知不可撤回**，只能发更正通知；已由人工采纳的审查结论不因模型回退而自动改写，须人工逐条复核（§23.5）。
