## 1. 模块定位与边界

**拥有的业务结果**：从潜在供应商（PROSPECT）到可开通 Vendor 的**可信准入决策**：寻源项目 → RFx → 密封报价 → 评标 → 授标，以及背调、资质收集/核验、准入评分与审批。

| 在范围内 | **非目标（Non-goals）** |
|----------|------------------------|
| SourcingProject / RFx / Bid / Quotation / Award | ❌ 不替代法定招投标平台，不做公告/开标公证 |
| Qualification / Onboarding / BackgroundCheck | ❌ 不写 Supplier Golden Record（只发 `OnboardingApproved`，由 01 卷触发开通） |
| 准入审批、资质有效期监控、AI 辅助背调/评标 | ❌ **AI 不自动授标、不自动准入**；人工最终决策（总体 §5.1、合规基线） |
| 供应商自助提交资质/背调资料（门户入口在 05 卷） | ❌ 不做付款、不做合同用印（03 卷） |

**业界依据**：SAP MDG-S 的 Change Request 双人复核 + duplicate check（总纲 §13 B1）；Ariba/Coupa Sourcing 的 RFx / sealed bid / award 分段；ISO 28000 / 供应商尽调的背调与资质有效期监控；金监总局式 AI 治理基线（AI 仅辅助、人工最终决策、PII 禁入、显著标识与留存）。

## 3. 领域模型与不变量

| 聚合根 | 关键实体 | 强一致不变量 |
|--------|----------|--------------|
| `SourcingProject` | 品类、预算、寻源策略、时间窗 | **INV-01** `DRAFT` 可改，`PUBLISHED` 后项目关键字段冻结；**INV-02** 一个项目至少一个 RFx |
| `RFx` | `RFxLine`、邀请供应商清单、截止时间 | **INV-03** 截止时间单调、到期后禁止再收 Bid；**INV-04** 邀请清单与 `Supplier(ACTIVE)` 一致 |
| `Bid` | 密封报价密文、提交时间、供应商 | **INV-05** `(rfx_id, supplier_id, round)` 唯一；**INV-06** 开标前任何角色（含管理员）不得读明文 |
| `Quotation` | 报价结构（含税/未税、币种、有效期） | **INV-07** 由 Bid 解密产生，不可手工改写；价格流向 04 卷 `PriceCondition` |
| `Award` | 中标供应商/行、授标理由 | **INV-08** 每个 RFx 至多一个生效 Award；**INV-09** 必须人工确认，AI 评分不得直接置 `AWARDED` |
| `Qualification` | 证照类型/号/有效期/附件/核验状态 | **INV-10** `EXPIRED` 不得作为准入通过依据；**INV-11** OCR 结果须人工复核才生效 |
| `Onboarding` | 背调报告引用、评分、审批实例 | **INV-12** `APPROVED` 前不得发 `OnboardingApproved`；**INV-13** 一个 Supplier 同时仅一个 `IN_REVIEW` 准入单 |
| `BackgroundCheck` | 来源、结论、快照哈希 | **INV-14** 外部结论存快照，不回传 PII 原文 |

## 4. 数据库设计

> **v0.2（总纲 §14 / §18）**：金额列一律 `DECIMAL(19,4)` + `currency CHAR(3)`、汇率 `DECIMAL(19,8)`、数量 `DECIMAL(19,6)`、时间 UTC `DATETIME(3)`，**禁用 float/double**（D-01–D-09）；唯一键须处理软删与同码重建冲突（§18.3）；索引须给出 access pattern 理由（§18.2）。下表只列业务列，类型基线不重复抄写。

| `t_proc_rfx_line` | `rfx_id, line_no, item_id, qty, uom, target_price` | `uk(tenant_id,rfx_id,line_no)` | 随根落盘（`@Cascade`） |

## 5. 状态机

> **v0.2（总纲 §21.1–§21.3）**：本节状态须落为枚举 + **显式迁移表** `Map<State, Map<Event, Transition>>`，守卫集中在 domain 层；**迁移表未列出即拒绝**（fail-closed），非法迁移返回 §17.2 的 `invalid_transition`（带 `current_state/attempted/allowed[]`）；状态迁移与 `@Version` CAS 同事务；终态不可回写由 domain 守卫 + 唯一约束双保险。本节小写领域事件（如 `supplier.activated`）属**领域内部事件**，不落 Outbox、不进注册表（总纲 §16.1）。

**SourcingProject**：`DRAFT → PUBLISHED → BIDDING_CLOSED → AWARDED → CLOSED`；可 `CANCELLED`（终态不可回写）。

| From | Event | Guard | To |
|------|-------|-------|----|
| `DRAFT` | `publish` | RFx 至少 1 行 + 邀请清单非空 | `PUBLISHED` |
| `PUBLISHED` | `due_reached` | 系统时钟 ≥ `due_at` | `BIDDING_CLOSED` |
| `BIDDING_CLOSED` | `open_bids` | 双人复核 + 审计留痕 | `BIDDING_CLOSED`（开标标记） |
| `BIDDING_CLOSED` | `award_confirmed` | **人工确认** + 评分快照 | `AWARDED` |
| `AWARDED` | `close` | 授标已通知 | `CLOSED` |

**Qualification**：`PENDING → OCR_EXTRACTED → VERIFIED → EXPIRED / REJECTED`；`INV-10/11` 守卫。

**Onboarding**：`DRAFT → SUBMITTED → IN_REVIEW → APPROVED → VENDOR_PENDING → COMPLETED`；`REJECTED` 经 WF `rejectToNode` 退回 `DRAFT`。

| From | Event | Guard | To | 领域事件 |
|------|-------|-------|----|----------|
| `DRAFT` | `submit` | 背调 + 必需资质齐备且未过期 | `SUBMITTED` | `qualification_submitted` |
| `SUBMITTED` | `start_review` | WF 启动 | `IN_REVIEW` | — |
| `IN_REVIEW` | `approve` | 双人复核 + 评分达标 | `APPROVED` | `onboarding_approved` |
| `APPROVED` | `trigger_vendor_activation` | Supplier 状态允许 | `VENDOR_PENDING` | `vendor_activation_requested` |
| `VENDOR_PENDING` | `vendor_activated`（01 卷回传） | `VendorActivated` 幂等消费 | `COMPLETED` | — |

**禁止迁移**：`PUBLISHED → DRAFT`（关键字段已冻结）；`EXPIRED → VERIFIED`（须重新提交证照）；`APPROVED` 未经人工确认由 AI 直接置位；`CANCELLED / REJECTED → 非终态` 一律拒绝。

## 6. API 契约

> **v0.2（总纲 §17 / 附录 A）**：错误码以总纲附录 A 为唯一真源（含新增 `317xx` 段）；错误体采用 RFC 9457 `application/problem+json` 并与 HC-003 `ApiResponse<T>` 兼容（§17.2）；大表 / 流水 / 审计 / DLQ 列表用 cursor 分页 + 服务端 `max_page_size`（§17.4）；状态码与可重试性见 §17.3；契约工件 `contracts/openapi.yaml`。

| 方法 | 路径 | 权限码 | 幂等键 | 说明 |
|------|------|--------|--------|------|
| `POST` | `/api/v1/procurement/sourcing-projects` | `procurement:sourcing-project:write` | `Idempotency-Key` | 建项目 |
| `POST` | `/api/v1/procurement/rfx` | `procurement:rfx:write` | `Idempotency-Key` | 建 RFx（含行与邀请） |
| `POST` | `/api/v1/procurement/rfx/{rfxNo}/publish` | `procurement:rfx:approve` | `Idempotency-Key` | 发布（冻结关键字段） |
| `POST` | `/api/v1/procurement/rfx/{rfxNo}/bids` | `portal:bid:write`（供应商侧） | `(rfx_id,supplier_id,round)` | 密封投标；截止后 `31201` |
| `POST` | `/api/v1/procurement/rfx/{rfxNo}/open` | `procurement:rfx:approve` | `Idempotency-Key` | 双人复核开标，审计留痕 |
| `POST` | `/api/v1/procurement/rfx/{rfxNo}/award` | `procurement:rfx:approve` | `Idempotency-Key` | **人工确认**授标 |
| `POST` | `/api/v1/procurement/qualifications` | `procurement:qualification:write` | `(supplier_id,cert_type,cert_no)` | 证照提交（OCR 异步） |
| `POST` | `/api/v1/procurement/onboardings` | `procurement:onboarding:write` | `Idempotency-Key` | 发起准入 |
| `POST` | `/api/v1/procurement/onboardings/{no}/approve` | `procurement:onboarding:approve` | `Idempotency-Key` | 准入审批（WF 推状态） |
| `GET` | `/api/v1/procurement/qualifications/expiring` | `procurement:qualification:read` | — | 到期巡检（分页） |

请求示例（`POST /rfx/{rfxNo}/award`）：

```json
{
  "rfx_no": "RFQ-2026-0118",
  "supplier_id": 8801,
  "ai_score_ref": "ai-eval-7f2a",
  "reason": "综合评分第一且资质有效",
  "confirmed_by": "buyer-1024"
}
```

响应 `200`：`{"code":"OK","data":{"award_no":"AW-2026-0031","status":"EFFECTIVE"},"trace_id":"..."}`；缺 `confirmed_by` → `20xxx` 参数错误；非人工确认 → `31203`。

**错误码**（总纲附录 A）：`31201` RFx 已截止、`31202` 准入资料不全、`31203` AI 结论不得直接授标、`31204` 证照已过期、`31205` 开标前读取报价明文。非法迁移统一 `409 invalid_transition` 带 `current_state / attempted / allowed[]`。

## 7. 事件契约

> **v0.2 契约校准（总纲 §16 / 附录 B）**：本表 `eventType` 的 **topic / partition_key / owner / consumers / schemaVersion 一律以总纲附录 B 事件契约注册表为准**，payload 字段**唯一真源 = `contracts/asyncapi.yaml`**；本表仅为字段速查，**不重复定义 topic**（避免双真源）。所有事件已按事件规范 §4「先登记注册表 → 再写 Producer」登记；门禁 **A8** 校验本表 eventType 均在注册表内、且注册表 topic 与 AsyncAPI channel 一一对应。顺序敏感链路 `partition_key = tenant_id + <aggregate_key>`（总纲 §6 双轨）且 payload 带 `aggregate_version` 供乱序丢弃；消费侧为 tolerant reader（§16.5）+ Inbox 幂等（§6），delivery 为 at-least-once。**`INBOUND`** 事件由外部上下文生产、沿用上游冻结 topic（L31 待裁决），采购域只读、不裁决。

| 方向 | eventType（topic / partition_key / owner 见总纲附录 B） | payload 字段速查（真源 `contracts/asyncapi.yaml`） | 幂等 / 顺序 / 失败 |
|------|-------------------|------------------|--------------------|
| 生产 | `ProspectCreated`（LLD 新增，topic 见附录 B） | `supplier_id, project_id, category_id` | `eventId`；失败 DLQ 重放 |
| 生产 | `RfxPublished` | `rfx_no, due_at, invited_supplier_ids[]` | `rfx_no` 唯一；通知幂等 |
| 生产 | `BidSubmitted` | `rfx_no, supplier_id, round, payload_hash`（**不含报价明文**） | `(rfx_no,supplier_id,round)` |

| 生产 | `QualificationVerified` / `Expired` | `qualification_id, supplier_id, expires_at` | `eventId`；到期巡检补偿 |

## 9. 工程治理

> **v0.2（总纲 §14 / §15 / §19）**：金额与汇率语义见 §14（D-01–D-09）；长流程步骤按 `COMPENSATABLE / PIVOT / RETRIABLE` 三分类并登记补偿（§15），编排状态持久化 + 语义锁 / 可交换更新 / 重读值；Outbox 运行纪律见 §19.6（**broker confirm 后才置 `PUBLISHED`**、`FOR UPDATE SKIP LOCKED`、最老未发件年龄告警、Claim Check）；重放 `mode=REBUILD` 抑制不可逆副作用（§16.7）；指标与告警见 §19.3–§19.4。

>

## 13. 本卷专题深化（v0.3）

> **一期状态（R6 / B20，A10 守护）**：T9（hash-chained 审计 / 双密钥分持，寻源全量三期启用）。本章全部规格**保留为设计储备**，触发条件与逐项映射见 [一期边界与机制触发条件.md](../一期边界与机制触发条件.md) §2；不得把本章机制默认解读为「一期必须实现」。

> **定位**：把总纲 §23 八项要素实例化到寻源与准入；本章**不新增事件 / 错误码 / 权限码**，不动 v0.1 已冻结的 RFx / 授标 / 准入状态机。数值均为草案（L38）。
> **依据**：B13（电子密封投标 / 世界银行 e-Procurement 评估指引），总纲 §23.9 → 02 卷。

**13.1 差异化核心算法：双信封密封、双密钥分持与可验证开标**

1. **提交即加密**：客户端取服务端公钥加密 Bid 报价体，服务端**只存密文 + 金额 SHA-256 摘要**，不落明文、不落可解密的会话密钥；技术标与商务标分两个信封独立加密。
2. **双密钥分持**：解密主密钥按 2-of-3 门限拆分（采购 / 内控 / 合规各持一份），**任何单方（含 DBA、运维、采购经办）不得提前解密**；任一持有人缺席仍可 2 份开标，避免「投标人自持密钥」造成单点阻断。密钥托管 KMS 归属见 L40。
3. **服务器时钟截止**：截止判定只认服务端 UTC（§14 时间统一），客户端时间仅用于展示；截止后写入 `LATE` 并记 hash 链，不接受时间回拨、不接受补投。
4. **评分权重预公布**：`Score = Σ(wᵢ × normalizeᵢ(bidᵢ))`；权重表在投标开始前冻结并计算 `weights_hash` 写入审计链，开标后不得修改；算术对所有投标人一致，禁止逐投标人调权。
5. **hash-chained append-only 审计**：`hₙ = SHA256(hₙ₋₁ ‖ eventType ‖ actor ‖ server_ts ‖ payload_hash)`；投标、开封、解密、评分、异议、授标六个动作全部入链，链断点即 P0 事件。
6. **决策表**：

| 条件 | 判定 | 动作 |
|------|------|------|
| 截止前 + 单人持密钥请求解密 | 越权 | 拒绝 + 告警 + 入审计链（M2-11） |
| 客户端未截止 / 服务器 UTC 已过 | 迟到 | 拒收，记 `LATE`（M2-12） |
| 到点 + 少于 2 份密钥 | 无法开标 | 保持 `SEALED`，触发 P1 升级，**禁止单份强制解密** |
| 到点 + ≥2 份密钥 + 双人复核 | 可开标 | 合成密钥、一次性解密，解密动作全程录屏留痕 |
| `weights_hash` 与预公布值不符 | 参数被篡改 | 中止开标 + 合规调查，**不得按现权重继续评分** |
| 评标人与投标人存在关联 | 利益冲突 | 强制回避、替换评委；投诉渠道绕开评标组 |
| 异议期未届满 | 流程未闭环 | 授标保持 `PENDING`，不得提前发中标通知 |

7. **失败语义与反例**：解密失败 → **不降级为「按摘要猜测报价」**，整场保持 `SEALED`；KMS 不可用 → 不开标；反例：某投标人拒绝交出自持密钥，若采用「投标人自持密钥」设计将阻断开标——故本设计明确**密钥不由投标人持有**（B13）。密文可删但 **hash-chained 审计不可删**（§23.6）。

**13.5 上线四闸门与回滚（总纲 §22.1 / 总体 §8.4）**

- **feature flag 粒度**：`tenant_id × rfx_type × flow(SEAL_V2 / WEIGHTS_HASH / AUTO_SCORING)`，默认全关；评分自动化开关与密封开关解耦。
- **历史数据回填**：存量 RFx / Bid 补 `server_deadline_utc` 与审计链起点 hash；**回填不产生新的开标动作**，只补可证明性。
- **灰度维度与观测窗**：先内部演练项目 → 5% 真实项目 → 全量，每级 ≥ 2 个完整投标周期，观测链完整性 / 截止争议数 / 异议率。
- **回滚触发**：链断点、`weights_hash` 不符、密钥份额不足导致 > 1 场无法开标、截止判定争议 ≥ 1。
- **本卷回滚代价（诚实登记）**：**已开标且已公示的报价不可「重新密封」**，回滚只能停新 RFx 并回到旧流程，历史场次保留原密文与审计链；已发出的授标通知按 §23.5 不撤回，用更正通知补偿。
