## 1. 模块定位与边界

**拥有的业务结果**：租户内唯一、可追溯、按字段 Owner 分权治理的供应商 Golden Record；以及"合作资格（Supplier）"与"交易/付款资格（Vendor）"两套互不覆盖的状态机。

| 在范围内 | **非目标（Non-goals）** |
|----------|------------------------|
| Supplier / LegalEntity / Site / Contact / Factory / SupplierItem / SupplyRelationship 主档 | ❌ 不承载财务记账、不做付款冻结裁决（Finance 触发 `PAYMENT_BLOCKED`，本域不可自行放行） |
| Vendor（Company Code data）与 VendorActivation 闸门 | ❌ 不定义物料主档（Item 来自主数据域，经 `*QueryPort` 只读引用） |
| 变更请求分段审批、去重合并、Golden Record 分发 | ❌ 不裁决发票匹配（总体 §3.1、PA-04） |
| 供应商生命周期与退出前清算校验 | ❌ 不生成 DDL（手写 `bone-init.sql`，能力基线 §3.2） |

**假设**：RA-2 未关闭前，`legal_entity_id` / `org_id` 粒度以总体 §9.1 矩阵为占位；账套清单待 owner 确定。

**业界依据**：SAP MDG-S 官方将供应商主档分为 General / Company Code / Purchasing Org 三段，**各段由不同 specialist 双人复核 Change Request**，支持分层 Block/Unblock、删除标记与向 client systems 复制（总纲 §13 B1/B2）；DAMA-DMBOK 要求 Golden Record 有版本戳、survivorship 与合并留痕。

## 2. C4 L3 组件视图（组件 = 容器内主要结构块，非独立进程）

> **关键链路时序（总纲 §21.5）**：[关键链路时序图](../assets/procuraAI-关键链路时序.svg) 序列 ① —— `SupplierChanged` / `VendorActivated` 开通闸门与 Golden Record 分发。下方 ASCII 仅描述组件结构；跨组件时序、外部 INBOUND 与故障分支一律以该图为准，不用 ASCII 框图代替时序。

```
adapter/web  SupplierController · VendorController · ChangeRequestController
     │  @PreAuthorize("hasAuthority('procurement:<r>:<a>')") + ApiResponse<T>
     ▼
application  SupplierApplicationService   （主档变更 / 版本戳 / 字段 Owner 校验）
             VendorActivationService      （开通闸门编排，事务边界）
             GoldenRecordService          （survivorship / 合并 / 分发）
             DedupService                 （统一社会信用代码 + 模糊匹配）
             SupplierExitService         （退出前跨域清算校验）
     │  port/out: SupplierQueryPort(读) · ErpAclPort(外部) · SupplierEventPort(发件)
     ▼
domain       Supplier / Vendor / VendorActivation / LegalEntity / Site / Contact /
             Factory / SupplierItem / SupplyRelationship / SupplierChangeRequest / MergeAudit
     │  Repository<T,Long> 由 SDK 代理生成
     ▼
infrastructure  t_proc_*（单库） · WorkflowStatusPort(S) · ErpAclAdapter(③自建+HMAC)
```

| 组件 | 职责 | 拥有的状态 | 依赖 |
|------|------|-----------|------|
| `SupplierApplicationService` | 变更请求受理、分段审批推进、Golden Record 激活 | `t_proc_supplier`、`t_proc_supplier_change_request` | WF `WorkflowStatusPort`、审计 |
| `VendorActivationService` | `(supplier_id, legal_entity_id)` 闸门：准入 + 银行 + 税务 + 付款条件 + 重复发票检查 | `t_proc_vendor_activation`、`t_proc_vendor` | Finance ACL（只读校验）、`SupplierEventPort` |
| `GoldenRecordService` | 来源优先级仲裁、survivorship、合并审计 | `t_proc_supplier_merge_audit` | 版本戳、事件分发 |
| `DedupService` | 精确键 + 模糊匹配，输出候选不做自动合并 | 只读 | 外部信用源 ACL |
| `SupplierExitService` | 零未结 PO / 未结合同 / 未清应付 + 所有 Vendor 关闭 | 只读投影 | 三通道对账（06 卷） |

> 依赖方向 `adapter→application→domain←infrastructure`（总纲 §3）；一期与 Sourcing/Procurement 同进程，**经应用服务编排 + 本地事务**，不发 MQ。

## 3. 领域模型与不变量

| 聚合根 | 关键实体/值对象 | 强一致不变量（编号） |
|--------|----------------|---------------------|
| `Supplier` | LegalEntity 引用、Site、Contact、Factory | **INV-01** `(tenant_id, supplier_code)` 唯一；**INV-02** `supplier_version` 单调递增，任何字段变更须经变更请求；**INV-03** `EXITED` 为终态不可回写 |
| `Vendor` | Company Code data（付款条件/银行引用/冻结/重复发票检查） | **INV-04** `(tenant_id, supplier_id, legal_entity_id)` 至多一个有效 Vendor；**INV-05** `PAYMENT_BLOCKED` 只能由 Finance/风控事件置位，采购域无放行权限 |
| `VendorActivation` | 闸门检查项结果 | **INV-06** 幂等键 `(supplier_id, legal_entity_id)`；**INV-07** 任一检查项 FAIL ⇒ 不得产生 `ACTIVE_VENDOR` |
| `LegalEntity` | 统一社会信用代码、Company Code、税区、币种 | **INV-08** `(tenant_id, unified_credit_code)` 唯一，跨法人账务按 LE 隔离 |
| `SupplierItem` | 物料×供应商×组织、交期、MOQ | **INV-09** 引用 PriceCondition 版本；价格变更不影响已下 PO（快照隔离，领域 §5.3） |
| `SupplyRelationship` | org×supplier×category×site、有效期 | **INV-10** 有效期不得与已生效 PO 冲突（同库跨聚合，按 CORE-06 登记例外；失败语义：拒绝变更 + `31002`） |
| `SupplierChangeRequest` | 分段草稿（Central/CompanyCode/PurchasingOrg） | **INV-11** 生效前只写草稿表，**不覆盖 Golden Record**（MDG staging） |
| `MergeAudit` | 合并前后快照哈希、survivor 规则 | **INV-12** 每次合并必留痕，禁止物理删除被合并方 |

> **Supplier↔Vendor 角色分离**沿用领域 §2.2.1 决策：Supplier 是合作资格、Vendor 是交易与付款资格；`vendor_profile`（D3 §4.2）是信用画像表，**不是 Vendor 主档**。

## 4. 数据库设计

> **v0.2（总纲 §14 / §18）**：金额列一律 `DECIMAL(19,4)` + `currency CHAR(3)`、汇率 `DECIMAL(19,8)`、数量 `DECIMAL(19,6)`、时间 UTC `DATETIME(3)`，**禁用 float/double**（D-01–D-09）；唯一键须处理软删与同码重建冲突（§18.3）；索引须给出 access pattern 理由（§18.2）。下表只列业务列，类型基线不重复抄写。

> 所有表含总纲 §4 必备列（`id, tenant_id, created_at, updated_at, created_by, updated_by, deleted, version`）；DDL 手写 `bone-init.sql` 后补列级对账测试。下表仅列**业务列**。

| 表 | 业务列 | 唯一键 / 索引 | 冲突处理 |
|----|--------|---------------|----------|
| `t_proc_supplier` | `supplier_code, legal_name, trading_name, lifecycle_status, supplier_version, source_system, source_ref, golden_hash` | `uk(tenant_id,supplier_code)`；`idx(legal_name)` | `@Version` CAS，冲突 `409` |
| `t_proc_supplier_change_request` | `supplier_id, segment(CENTRAL/COMPANY_CODE/PURCHASING_ORG), payload_json, cr_status, workflow_instance_id, submitted_by` | `uk(tenant_id,cr_no)`；`idx(supplier_id,cr_status)` | 同 supplier 同 segment 仅一个 `IN_REVIEW` |

## 5. 状态机

> **v0.2（总纲 §21.1–§21.3）**：本节状态须落为枚举 + **显式迁移表** `Map<State, Map<Event, Transition>>`，守卫集中在 domain 层；**迁移表未列出即拒绝**（fail-closed），非法迁移返回 §17.2 的 `invalid_transition`（带 `current_state/attempted/allowed[]`）；状态迁移与 `@Version` CAS 同事务；终态不可回写由 domain 守卫 + 唯一约束双保险。本节小写领域事件（如 `supplier.activated`）属**领域内部事件**，不落 Outbox、不进注册表（总纲 §16.1）。

**Supplier 生命周期**（领域 §4.1）：`PROSPECT / ONBOARDING / ACTIVE / SUSPENDED / CORRECTIVE / EXITED`

| From | Event | Guard | To | 领域事件 |
|------|-------|-------|----|----------|
| `PROSPECT` | `onboarding_submitted` | 背调 + 资质齐备 | `ONBOARDING` | `supplier.onboarding_submitted` |
| `ONBOARDING` | `onboarding_approved` | CR 全段批准 + 至少 1 个 `ACTIVE_VENDOR` | `ACTIVE` | `supplier.activated` |
| `ACTIVE` | `risk_exceeded` | 风险事件/绩效不达标 | `SUSPENDED` 或 `CORRECTIVE` | `supplier.suspended` / `supplier.corrective_opened` |
| `SUSPENDED` | `restored` | 整改复核通过 + 审批 | `ACTIVE` | `supplier.restored` |
| `ACTIVE/CORRECTIVE` | `exit_approved` | **零未结 PO + 未结合同 + 未清应付 + 所有 Vendor `INACTIVE_VENDOR`** | `EXITED` | `supplier.exited` |

**Vendor 生命周期**（领域 §4.3）：`PENDING_VENDOR / ACTIVE_VENDOR / PAYMENT_BLOCKED / INACTIVE_VENDOR`

| From | Event | Guard | To |
|------|-------|-------|----|
| `PENDING_VENDOR` | `activation_passed` | 准入 + 银行核验 + 税务 + 付款条件 + 重复发票检查全 PASS | `ACTIVE_VENDOR` |
| `ACTIVE_VENDOR` | `payment_block_raised` | Finance/风控事件（**本域不可自发放行**） | `PAYMENT_BLOCKED` |
| `PAYMENT_BLOCKED` | `payment_block_released` | Finance 事件 + 人工复核留痕 | `ACTIVE_VENDOR` |
| 任一非终态 | `deactivate` | 无进行中 PO 或存量 PO 允许走完 | `INACTIVE_VENDOR` |

**ChangeRequest**：`DRAFT → SUBMITTED → IN_REVIEW → APPROVED → ACTIVATED`；`REJECTED` 用 `rejectToNode` 退回草稿重新提交（**不新建修订版本**，v0.3 已撤回该降级）。

**禁止迁移**：`EXITED → 任意`（终态）；`INACTIVE_VENDOR → ACTIVE_VENDOR` 须重新走开通闸门；`PENDING_VENDOR → ACTIVE_VENDOR` 未经闸门直接置位。

## 6. API 契约（contract-first，OpenAPI 先行）

> **v0.2（总纲 §17 / 附录 A）**：错误码以总纲附录 A 为唯一真源（含新增 `317xx` 段）；错误体采用 RFC 9457 `application/problem+json` 并与 HC-003 `ApiResponse<T>` 兼容（§17.2）；大表 / 流水 / 审计 / DLQ 列表用 cursor 分页 + 服务端 `max_page_size`（§17.4）；状态码与可重试性见 §17.3；契约工件 `contracts/openapi.yaml`。

| 方法 | 路径 | 权限码 | 幂等键 | 说明 |
|------|------|--------|--------|------|
| `POST` | `/api/v1/procurement/suppliers` | `procurement:supplier:write` | `Idempotency-Key` | 建档（生成 `PROSPECT` + DRAFT CR） |
| `GET` | `/api/v1/procurement/suppliers/{id}` | `procurement:supplier:read` | — | Golden Record（含三段，按 Owner 过滤字段） |
| `GET` | `/api/v1/procurement/suppliers` | `procurement:supplier:read` | — | `PageResult<T>`，`page/size/sort` |
| `POST` | `/api/v1/procurement/suppliers/{id}/change-requests` | `procurement:supplier:write` | `Idempotency-Key` | 提交分段变更（不覆盖主档） |
| `POST` | `/api/v1/procurement/change-requests/{crNo}/approve` | `procurement:supplier:approve` | `Idempotency-Key` | 分段审批；非法迁移 `invalid_transition` |
| `POST` | `/api/v1/procurement/vendor-activations` | `procurement:vendor:write` | `(supplier_id,legal_entity_id)` | 开通闸门（幂等复用） |
| `GET` | `/api/v1/procurement/vendors` | `procurement:vendor:read` | — | 按 LE / company_code 过滤 |
| `POST` | `/api/v1/procurement/suppliers/{id}/dedup-check` | `procurement:supplier:read` | — | 返回候选，不自动合并 |
| `POST` | `/api/v1/procurement/suppliers/merge` | `procurement:supplier:admin` | `Idempotency-Key` | survivorship + 合并留痕 |
| `POST` | `/api/v1/procurement/suppliers/{id}/exit` | `procurement:supplier:approve` | `Idempotency-Key` | 退出前清算校验 |

请求示例（`POST /vendor-activations`）：

```json
{
  "supplier_id": 8801,
  "legal_entity_id": 3101,
  "company_code": "1000",
  "payment_terms": "NET30",
  "bank_account_ref": "BA-ENC-9F2A",
  "tax_id": "91310000XXXXXXXXXX",

```

## 7. 事件契约

> **v0.2 契约校准（总纲 §16 / 附录 B）**：本表 `eventType` 的 **topic / partition_key / owner / consumers / schemaVersion 一律以总纲附录 B 事件契约注册表为准**，payload 字段**唯一真源 = `contracts/asyncapi.yaml`**；本表仅为字段速查，**不重复定义 topic**（避免双真源）。所有事件已按事件规范 §4「先登记注册表 → 再写 Producer」登记；门禁 **A8** 校验本表 eventType 均在注册表内、且注册表 topic 与 AsyncAPI channel 一一对应。顺序敏感链路 `partition_key = tenant_id + <aggregate_key>`（总纲 §6 双轨）且 payload 带 `aggregate_version` 供乱序丢弃；消费侧为 tolerant reader（§16.5）+ Inbox 幂等（§6），delivery 为 at-least-once。**`INBOUND`** 事件由外部上下文生产、沿用上游冻结 topic（L31 待裁决），采购域只读、不裁决。

| 方向 | eventType（topic / partition_key / owner 见总纲附录 B） | payload 字段速查（真源 `contracts/asyncapi.yaml`） | 幂等 / 顺序 / 失败 |
|------|-------------------|------------------|--------------------|
| 生产 | `SupplierChanged` | `supplier_id, supplier_version, changed_fields[], segment, cr_no, golden_hash` | `eventId`；同 `supplier_id` 保序；投递失败进 DLQ 重放 |
| 生产 | `VendorActivated` | `vendor_id, supplier_id, legal_entity_id, company_code, activated_at, purchasing_org?, payment_terms?, bank_account_ref?`（字段名真源 D3-v2 §2.1） | `eventId` + `vendor_id` 唯一 |
| 生产 | `SupplierDeduplicated`（LLD 新增） | `candidate_ids[], rule_code, decided_by` | 人工决策后才发，自动合并禁止 |
| 消费 | `QualificationExpired`（02 卷） | `qualification_id, supplier_id` | 触发 `SUSPENDED` 评估，不直接改主档 |
| 消费 | `RiskAlertRaised`（03 卷；**三期事件，一期接口预留、运行期不触发**） | `alert_id, supplier_id, severity` | 触发暂停/整改，幂等 `(consumer_group,event_id)` |
| 消费 | `OnboardingApproved`（02 卷） | `onboarding_id, supplier_id, score` | 触发 `VendorActivationService` |
| 消费 | `InvoiceMatched`（**INBOUND** / Finance ACL；**依赖跨域 ACL 交付（F-A），未交付前接口预留、运行期不触发**） | `match_id, invoice_no, po_no, match_status, matched_amount, exception_code?, matched_at`（字段级真源 D3-v2 §2.1；本域只消费 `invoice_no/match_status` 子集） | **本域不裁决、不回写付款状态** |

> **依据**：B12（MDM entity resolution / Golden Record），总纲 §23.9 → 01 卷。

**13.1 差异化核心算法：Golden Record 两阶段匹配与 survivorship 决策表**

1. **归一化**：统一社会信用代码 / 税号去空格、全角转半角、大写化；名称去企业后缀与组织形式后分词；地址按省市区标准化；电话去国家码。归一化值只用于候选键，**原始值永不覆盖**。
2. **阶段一 确定性阻塞**：以「税号」「名称前 6 字 + 省市」「银行账号 hash」构造 blocking key，只在同一 key 内生成候选对，禁止全表笛卡尔积。
3. **阶段二 概率打分**：`score = Σ(wᵢ × sᵢ) / Σwᵢ`；权重固定 税号 0.40 / 名称 0.25 / 地址 0.15 / 电话 0.10 / 银行账号 0.10；税号用精确相等（0 或 1），其余用 Jaro-Winkler。
4. **阈值三分区**（误合并比漏合并更危险，自动合并优先 precision；标注集与 precision 门槛见 L39）：

| 条件 | 判定 | 动作 | 可撤销性 |
|------|------|------|----------|
| `score ≥ 0.92` 且税号一致 | 高置信同一主体 | 进 `PENDING_MERGE` 自动合并队列，24h 内可一键撤销 | 可撤销（MergeAudit + 字段级 lineage） |
| `score ≥ 0.92` 但税号不一致 / 缺失 | **反例命中，禁止自动合并** | 转 steward 复核队列，强制填判定理由 | 不适用 |
| `0.70 ≤ score < 0.92` | 疑似重复 | steward 队列（SLA 见 L39），不阻断本条业务 | 人工裁决 |
| `score < 0.70` | 不同主体 | 只记候选日志，不提示 | 不适用 |
| 任意分值 + 双方均有 `ACTIVE_VENDOR` | 高风险 | 一律人工，双 Vendor 合并须财务确认 | 不适用 |

5. **survivorship 字段级（非记录级）**：`value = first(nonEmpty(sources ordered by 字段优先级))`，优先级 = 权威源 > 人工确认（带 `verified_at`）> 最新 `effective_from` > 最早入库；每个胜出字段必须写 `source_system / source_record_id / rule_id / decided_at` 的 lineage，**缺一条则整笔合并事务回滚**（M1-11）。
6. **失败语义**：匹配服务不可用 → **不降级为「按名称直接判重」**，新供应商落 `PENDING_REVIEW`；归一化异常 → 整批隔离到差异台账，不写主档。
7. **反例（必须有用例 M1-10）**：两家关联企业同名、同址、同电话，但统一社会信用代码不同，分值可达 0.94 → 必须命中「税号不一致」禁止自动合并；被自动合并即 P0 数据事故。合并后按「分发对账」逐下游核对 Golden Record 版本戳，差异进台账。

**13.5 上线四闸门与回滚（总纲 §22.1 / 总体 §8.4）**

- **feature flag 粒度**：`tenant_id × segment(GENERAL / COMPANY_CODE / PURCHASING_ORG) × flow(AUTO_MERGE / APPROVAL_V2)`，默认全关，自动合并单独开关。
- **历史数据回填**：存量供应商批量归一化 + blocking key 生成；抽样复核 ≥ 5% 且 precision 达门槛（L39）；**回填不触发 OUTBOUND 事件**，避免误分发。
- **灰度维度与观测窗**：按租户 5% → 25% → 100%，每级 ≥ 3 个工作日，观测 `mdm_merge_precision` / 投影 lag / 异议率 / 慢查询 Top-N。
- **回滚触发**：误合并 ≥ 1 起、precision 跌破门槛、投影 lag > 5min 持续 10min、DDL 双绿失败。
- **本卷回滚代价（诚实登记）**：Golden Record 一旦对外分发**不可撤回**，只能用补偿事件 + 投影重建纠正，**无法恢复下游已引用的快照**；因此自动合并强制保留 24h 撤销窗与全量字段级 lineage。已发事件按 §23.5 不撤回，仅补偿。

**13.6 数据分类与保留（总纲 §18.5 / §20.7）**

**13.7 只读投影与新鲜度（总纲 §16.7 / §19.6）**

- **投影表**：`t_proc_supplier_golden_projection`（供应商列表 / 门户下拉 / PO 抬头取数），一次取齐 JOIN，禁止 N+1 与无界 `IN`（§18.4）。
- **更新触发**：本卷 §7 已登记的 OUTBOUND 事件 + 日终全量校准（不新增事件）。
- **staleness 上界**：P99 5s；> 30s 自动读回源并告警 P2。
- **新鲜度证据**：`projection_version` + `last_event_occurred_at` 回传前端展示「数据截至」，禁止把投影当权威强一致数据（§23.7）。
- **重建入口**：replay `mode=REBUILD` 抑制不可逆副作用（§16.7）；读不到时回退主档单条查并记 miss 指标。
