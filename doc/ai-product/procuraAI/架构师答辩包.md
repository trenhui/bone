## 3. 三页取舍说明

### 第 1 页：边界重构前后对照（要求 8）

| 维度 | 重构前（旧 POC / ERP 承载） | 重构后（Procura） | 依据 |
|------|------------------------------|-------------------|------|
| 主档权威 | ERP 承载供应商/价格/合同主档；`D3` 以 `contract_no` 为集成主键 | **采购域为 Supplier Golden Record 权威**，ERP 为账务与库存执行；`review_id` 为 AI 结论关联键 | `领域 §6.1`、`D3-v2 §1` |
| 角色模型 | Supplier 一档走天下 | **Supplier（合作资格）↔ Vendor（交易/付款资格）分离**，`VendorActivation` 独立闸门 | `领域 §3`、`总体 §6.1` |
| 三单匹配 | 采购域保证跨域强一致 | **Finance 裁决**，采购域只产出 PO/GR/Invoice 数据 | `总体 §3.1`、`04 §7` |
| AI 边界 | 独立智能体产品，原口径「低风险自动归档」**已撤销** | **域内 AI 子能力**，fail-closed + 人工最终决策 | `总体 §5.1`、`文档资产登记 §5/§7` |
| 平台能力 | 纸面「平台已有 / 自建」 | **S/D/N 三态实证 + 复用/共建/自建三轨** | `能力基线 §2` |
| 工程协作 | 独立库 / 每客户私有化 | 单应用单库本地事务；跨单元才用事件 | `总体 §8.1`、B20 |

**迁移三阶段**：① 只读镜像 + 差异清单；② 双跑（写回 ERP，逐日对账）；③ 按租户/法人/品类灰度切流，停止双向写。回退与割接见 `总体 §8.4`。

### 第 2 页：MonolithFirst 取舍（B20）

- **取**：一期单应用多模块单库，同库跨聚合用本地事务；`总体 §8.1` 明确「不为同库同进程制造分布式复杂度」。
- **舍**：Saga 编排、schema registry、crypto-shred、hash-chained 审计、replay `REBUILD`、双轨 partition_key 一律标「**设计储备·拆分后启用**」，每项给具名触发条件（`一期边界与机制触发条件.md §2` T6–T11）。
- **例外及理由**：`procuraai-runtime` 独立部署（Python + GPU + vLLM 技术栈不匹配，B20 认可具名压力）；Outbox 一期存在仅服务**跨单元通知/审计**。
- **代价**：未来拆分须先补 DDL、事件 payload、`QueryPort` 读边界、对账三通道，否则拆分即数据一致性事故（`总体 §8.2` 已写明）。

### 第 3 页：Finance 裁决边界由来

- 三单匹配（PO / GR / Invoice）涉及采购域与 Finance 两个独立决策主体；**把「匹配结果一致」设为跨域强一致不变量**，等价于要求跨部署单元分布式事务，是伪命题。
- 因此采购域只**产出事实**（PO、GR、InvoiceSubmission），`InvoiceMatched` 由 Finance(ACL) 回传（2W/3W、容差、例外、冻结原因），采购域据此发 `PaymentRequested`；**采购域无放行接口**。
- 对账采用三通道 + 例外台账，删除旧的错误等式「未结应付 = 已收未付发票净额」。
- 对标 SAP MIRO/LIV 与 X12 810/820；`997` 仅语法回执，**不置 `MATCHED`**；ASN 非收货凭证。

## 4. 被否决的**领域边界**方案（R12：此前只有组件选型否决）

> 诊断指出 `总体 §14` MADR 的被否决方案集中在 LangGraph/AutoGen、pgvector 等**技术组件选型**，缺「被否决的领域边界方案及理由」。以下补齐两项，均为**边界层**取舍。

| # | 被否决的边界方案 | 否决理由 | 采纳方案 | 关联权衡点 |
|---|------------------|----------|----------|------------|
| **DB-1** | **「Supplier 与 Vendor 合并为单一供应商主档」**（用一组状态字段区分合作/交易资格，不设独立聚合） | 两类资格的**审批主体、生效条件、失效影响面**不同：合作资格由寻源/准入决定，交易/付款资格还要银行核验、税务、付款条件、重复发票检查；合并会让「准入通过」隐含「可建 PO / 可付款」，多法人下同一 Supplier 对不同法人应有不同 Vendor 状态，单档无法表达且易造成越权付款 | Supplier / Vendor 分离 + `VendorActivation` 独立闸门；SAP MDG-S General / Company Code / Purchasing Org 三层分段 | TP-3 前置 |
| **DB-2** | **「采购域内建三单匹配与付款放行」**（把 Finance 的匹配裁决并入采购域，减少一次跨系统往返） | ① 匹配规则、容差、冻结放行属财务控制权，采购域无权裁决；② 跨域强一致在独立部署单元上不可实现（会退化为分布式事务或伪一致）；③ 财务科目、税、汇率与付款批次的变更会反向污染采购域模型 | 采购域产出事实 + Finance(ACL) 回传 `InvoiceMatched` + `PaymentRequested` 解耦；三通道对账 + 例外台账 | **TP-3** |

**备选但未被采纳的第三方案**：「把 Item / Inventory / Warehouse 主档并入采购域」——因三者系统真源在各自域、且采购域只需只读视图，本轮在 `跨域契约与外部域依赖.md §1` 明示为**只读依赖**而不合并边界（并入会造成双向写与 Golden Record 冲突）。此条作为边界方案族的第三个否决记录。
