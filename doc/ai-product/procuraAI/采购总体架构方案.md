## 1. 战略与范围

### 1.1 系统定位

采购域是 BONE 平台上的**垂直业务域**，提供从寻源到付款请求（Source-to-Settle / Procure-to-Pay）的企业采购能力，并以 procuraAI 作为 AI 原生差异化子能力（风险审查、合同智能、信用画像、履约预警）。

| 对标 | 业界实践 | 本方案映射 |
|------|----------|------------|
| Source-to-Settle | SAP Ariba / Coupa 端到端采购 | Spend/Category→预算→请购→PO→收货→发票→付款请求全链路（§3 价值流） |
| 供应商主数据 | SAP MDG-S / Business Partner(CVI) / DAMA-DMBOK | Golden Record + **Supplier↔Vendor 角色分离** + 数据 Owner 分层（§6.1、§9.1） |
| 供应商生命周期 | Ariba SLM / Coupa Supplier Mgmt | 寻源→背调→准入→资质→工厂→合同→供货→绩效→风险→整改→退出（领域设计 §4） |
| 供应商协同 | SAP Business Network / Ariba Buying & Invoicing | PO 确认 / ASN / 自助开票 / IR 例外 / 绩效看板（§4.3） |
| 发票校验与付款 | SAP MIRO(LIV) + 容差 + MRBR 放行 / Ariba IR | **Finance 裁决，采购域产出数据与 PaymentRequested**（§3.1、§3.2） |
| 采购成本 | SAP Condition Technique / Info Record / PPV | 价格链 + 条件 + PPV/降本口径（领域设计 §5.3） |
| 审批流 | 通用 BPM 轻量化 | 复用 `bone-workflow-engine`（人审专用，非 BPMN）；主干能力已实证实现，仅子流程/SLA 共建（§10、PA-02、能力基线 §4） |
| AI 原生 | 采购智能体 | procuraAI（M1–M7 + 信用/条款/预警），独立 AI 运行时与治理（§5.1） |
| 平台能力 | Clean Core / side-by-side extensibility | 复用 + 采购域共建 v2（§2、领域设计 §8.1） |

### 1.2 能力边界

| 做（采购域职责） | 不做（边界） |
|------------------|--------------|
| 供应商主数据（Supplier/Vendor/Legal Entity/Site/Contact/Factory）、寻源、资质准入、合同、采购交易（PR/PO/成本/调拨/RTV）、收货协同与履约绩效、风险整改、供应商协同门户、AI 风险/合同智能；产出 PO/GR/发票数据并**向 Finance 发送 PaymentRequested** | **不执行发票校验（3-way match）、不作付款许可裁决、不执行付款**（Finance/ERP 权威，§3.1）；不直连/改写客户 ERP 表（经 ACL）；不提供大模型训练；不承载客户全量业务数据；不替代财务总账/库存实物账（仅集成对账） |

> **边界理由**：业界 P2P 中发票校验（MIRO/LIV）与付款（F110）属 AP/FI 职责，采购侧产出单据并把匹配通过的付款请求送回 ERP。把该控制设为采购域的「跨域强一致不变量」既不成立（跨系统无法强一致，DDD E-5.4），也会造成双裁决主体。

## 2. 架构愿景与原则

| 原则 | 落地 |
|------|------|
| **Clean Core** | 稳定平台核心封箱不动；采购易变业务逻辑外置为独立域模块；procuraAI 作为独立智能体嵌入，不污染核心 |
| **DDD 六边形 + CQRS**（CORE-01~12） | 上下文内 `adapter→application→domain←infrastructure`；写经聚合根 Repository，复杂读经 `QueryPort` 投影 |
| **平台能力三轨（复用 / 共建 / 自建）** | 依据能力基线 §1 的源码实证矩阵：S 态才可直接复用（Workflow 主干 / metadata-sdk / IAM / 事件信封 / 统一响应）；规范承诺但无实现者（HMAC 验签 / DLQ 转投 / 通用 Outbox starter / 统一任务中心与审计 schema）走共建或采购域自建；完全不存在者（B2B 门户 / 子流程 / 采购实体 DDL）新建。**禁止把「规范承诺」写进 WBS 的「已复用」栏**（能力基线 §2，对标 SAP Clean Core A–D 与 golden path） |
| **API-First + 事件驱动** | 跨上下文协作经领域事件（Outbox+幂等）；跨系统经 ACL+事件/API；REST 返回 `ApiResponse<T>`（HC-003） |
| **最终一致优先** | 跨聚合/跨部署单元默认最终一致（Outbox+幂等+对账）；强一致仅限单聚合；同库本地跨聚合事务须按 CORE-06 声明不变量、失败语义、并发成本并登记例外（DDD §E-5.4 决策树） |
| **边界单真源** | 领域语义真源 = 领域设计；技术架构真源 = 本文；**框架能力实证与落地约束真源 = 能力基线**；平台约束真源 = `Bone-DDD-最终实践方案.md` / 事件规范 / workflow README；本文不复制平台条文，只引用（§13、§15）。平台能力是否可用，以能力基线的 `file:line` 实证为准，不以文档自述为准 |
| **AI fail-closed** | AI 仅辅助、人工最终决策；降级诚实、PII 禁入（对齐金监总局 AI 安全指导意见 + procuraAI 降级纪律）；AI 运行时隔离（§5.1） |

## 3. 核心能力与价值流（Source-to-Settle）

```
支出分析/品类策略 Spend & Category ─▶ 预算检查 Budget Check ─▶ 请购 PR(Guided Buying / Catalog & PunchOut)
                                                                        │
   寻源 Sourcing ─▶ 准入 Qualification ─▶ Supplier→Vendor 开通 ─▶ 合同 Contract ─┤
                                                                        ▼
                                          采购订单 PO ─▶ 供应商确认 PO Ack ─▶ 发货通知 ASN
                                                 │                              │
                                                 ▼                              ▼
                                          收货 GR(Inventory)  ◀────────────────┘
                                                 │
                        供应商自助开票 Invoice(PO-based) ─▶ IR 例外队列(Finance)
                                                 │
                                                 ▼
                  匹配由 Finance 执行（2-way/3-way + 容差 + 冻结/放行）──▶ InvoiceMatched 事件
                                                 │
                                                 ▼
                    采购域发 PaymentRequested ─▶ ERP/Finance 执行付款(F110) ─▶ PaymentRecorded
  并行：供应商主数据 MDM（Golden Record）· 风险 Risk（预警/整改）· 绩效 Performance · procuraAI 审查
```

**价值流不变量**：
- **匹配与付款裁决在 Finance**：采购域保证 PO/GR/发票数据的完整性与可追溯，跨域最终一致；匹配结果由 `InvoiceMatched` 回传，采购域**不裁决付款许可**（§3.1）。
- **主数据权威**：Supplier/Vendor/物料主档以 Supplier MDM 为系统真源；交易上下文只读投影。
- **合同约束**：PO 条款不得劣于已审合同；procuraAI 审查结论回写 `review_id` / 风险项 / `review_snapshot`，**`contract_no` 仅作关联键**（契约见 `采购AI-接口契约与数据字典-v2.md` §2，为审查入参）。
- **Vendor 闸门**：只有已开通 Vendor 角色且绑定 Legal Entity / Company Code 的主体，才可被 PO 引用、开票与付款（PA-07）。
- **退出清算**：Supplier 退出前须关闭全部 Vendor 角色，并校验零未结 PO/合同/应付（领域设计 §4.1）。

### 3.1 匹配与付款的裁决边界（修订 P0-2）

| 职责 | 归属 | 产物 / 契约 |
|------|------|-------------|
| PO、PO 变更、收货协同数据 | 采购域 | `PurchaseOrderCreated`、`GoodsReceived` 事件 |
| 供应商发票录入 / PO-based 发票数据 | 门户 + 采购域（转交） | `InvoiceSubmitted` |
| **三单匹配、容差判定、冻结/放行、IR 例外处理** | **Finance / ERP（AP）** | `InvoiceMatched`（`match_id, invoice_no, po_no, match_status, matched_amount, exception_code, matched_at`；字段级真源 = `D3-v2 §2.1` 七字段）。2-way/3-way 判定、容差配置与冻结原因属 **Finance 侧内部语义**，不进事件 payload |
| 付款许可与付款执行 | Finance / ERP | `PaymentRecorded`（回传） |
| 付款请求 | 采购域（据匹配结果发起，不裁决） | `PaymentRequested` → ERP |

**一致性口径**：三者分处采购域 / Inventory / Finance，跨系统，**按 DDD E-5.4 决策树走「状态机 + Outbox + 幂等 + 补偿 + 定期对账」，不设为强一致不变量**。同库内 PO 与 PO Line 的金额不变量（`金额 = Σ 行金额`）仍在单聚合内强一致保护（CORE-03/06）。

**为何改**：v0.1 的 PA-04「三单匹配作为跨域强一致不变量 + 对账兜底」与本文 §2「强一致仅限单聚合」、DDD E-5.4「跨库/跨上下文 → 状态机+Outbox+幂等+补偿」及其自身缓解手段（对账 = 事后最终一致）三者互斥；且 v0.1 §3「才可付款」把财务裁决权揽入采购域，与 `InvoiceMatched` 事件方向（Finance 触发）冲突。

### 3.2 匹配类型、容差与例外（业界对标 SAP LIV / Ariba IR）

| 维度 | 规则 | 落点 |
|------|------|------|
| 匹配类型 | 实物/库存/高价值 → **3-way**（PO×GR×Invoice）；服务/订阅/无 GR → **2-way**（PO×Invoice）；Blanket PO 按累计额度核销 | **Finance 侧内部判定**（不进 `InvoiceMatched` payload；采购域只读 `match_status` / `exception_code`） |
| 容差 | 数量/价格/金额容差按品类与税区配置（业界 OMR6 tolerance keys 思路），超限不静默放行 | **Finance 侧配置**，不进事件 payload；采购域据 `match_status=EXCEPTION` 进入 IR 例外队列 |
| 例外 | 超容差 → 发票冻结 + IR 例外队列 + 人工放行（业界 MRBR 模式），保留审计轨迹 | `match_status` / `exception_code`（D3-v2 §2.1 真源字段） |
| 清算 | GR/IR 清算账户在收货贷记、发票校验借记，二者匹配后结清 | Finance 侧，采购域只读对账 |
| 特殊场景 | 预付款（特殊总账，不与应付净额相抵）、贷项凭证/红冲、部分付款、RTV 冲销 | 对账三通道单列例外口径（§6.3） |

| **`bone-app-purchase`（存量，保留）** | 低代码 Runtime 适配层 | **无 `@Table` 实体 / 无 Repository**；`PurchaseWorkflowStatusPort`(`WorkflowStatusPort`) + 4 个 `RuntimeActionHandler` | 复用其端口契约，不重写、不删改（能力基线 §7） |

> **存量边界（v0.3）**：仓库已有 `bone-apps/bone-app-purchase`（12 个主代码类，`bone-app-purchase/.../PurchaseWorkflowStatusPort.java:37`），是**低代码 Runtime 动作 + 工作流适配器**，不是 Java 领域实现。决策采用能力基线 §7 路径 A：保留为适配层，新模块统一 `bone-procurement-*` 命名，聚合状态回写统一经 `WorkflowStatusPort`；`PurchaseOrderPayHandler` 保留为演示/占位，**生产链路付款只认 `PaymentRequested` 事件**（PA-04），不得由 Runtime 动作直接触发付款。
>
> **依赖纪律（CORE-01/02/05/08）**：模块间不得直连对方数据库（边界约定，非 HC 条目）；**跨部署单元**写经领域事件 + ACL，读经按 CORE-05 自定义的业务侧 `*QueryPort`（框架无该接口，能力基线 §1.4）；持久化唯一走 metadata-sdk（HC-006）。**同一部署单元、同一库内走本地事务 + 应用服务编排，不强行引入 Outbox/MQ/Saga**（§8.1；DDD §CORE-08、E-3.1）。

### 4.3 供应商协同门户能力清单（JD ③ Supplier Collaboration，对标 SAP Business Network）

## 6. 领域与数据战略

### 6.1 主数据治理（对标 SAP MDG-S / Business Partner(CVI) / DAMA-DMBOK）

- **Golden Record**：Supplier 主档唯一版本化（`supplier_version`）；来源系统（SAP/U8/金蝶/Oracle）字段映射复用 `采购AI-接口契约与数据字典-v2.md §1.2` 统一字典（缓解多 ERP 口径不一）。
- **Supplier ↔ Vendor 角色分离与字段 Owner**（业界 vendor master 三层）：

| 层级 | 数据 Owner | 关键字段 | 归属上下文 |
|------|-----------|----------|------------|
| General data | 共享（主数据管家） | 名称、地址、统一信用代码、税号、Contact | Supplier MDM |
| **Company Code data** | **财务** | 统驭科目、付款条件、付款方式、付款冻结、银行账号、重复发票检查标志 | **Vendor**（按 Legal Entity / Company Code 隔离） |
| **Purchasing Org data** | **采购** | 订单币种、采购员、Incoterms、交货条件、供应商货品目录 | **Supplier / SupplyRelationship**（按采购组织隔离） |

- **转换闸门（VendorActivation）**：准入通过 + 银行账号核验 + 税务校验 + 付款条件配置 + 重复发票检查标志，才开通 Vendor 角色；未开通不得被 PO 引用（PA-07，状态机见领域设计 §4.3）。
- **数据管家（Stewardship）**：主档新建/变更走 workflow 审批；字段按 Owner 分权限维护；冲突以「主数据域为系统真源 + 版本戳 + Owner 优先级」仲裁。
- **分发**：主档变更 → Outbox → `domain.procurement.supplier_changed.v1` / `vendor_activated.v1` → 下游幂等更新投影（`QueryPort`）。

### 6.2 读写模型（CQRS）

- **写模型**：聚合根 Repository（metadata-sdk），强一致不变量在聚合内保护（CORE-03/11）。
- **读模型**：页面/统计/跨聚合组合走 `QueryPort` 投影；热点（信用画像、条款库、价格条件）短 TTL + 事件驱动失效，禁双真源（CORE-05、领域设计 §7.8）。

### 6.3 数据一致性模式与对账（修订 P0-2 / 删除错误等式）

- 同库跨聚合：按 CORE-06 声明业务不变量、失败语义、并发成本并登记例外（E-5.1/E-5.4）；**例外仅限同库本地事务**。
- 跨部署单元/跨进程：Outbox 保证发件原子；消费幂等落采购域 `t_proc_processed_event`（`consumer_group + event_id` 唯一键，**不跨上下文直写 blueprint 的 `bp_processed_event`**）；不可重试进 DLQ 重放（转投能力须自建，见能力基线 §5.2）。
- 跨系统（PO/GR/Invoice/付款）：最终一致 + Orchestrator 补偿动作（Saga）+ 定期对账；**不设强一致不变量**（§3.1）。
- **对账三通道**（借鉴 synap-claim 不变量实践，改为可核对定义）：

| 通道 | 核对对象 | 不变量（可核对口径） |
|------|----------|---------------------|
| `SUPPLY` | PO 承诺量 vs GR 实收累计 vs 未收量 | 未收量 = PO 承诺量 − GR 实收累计（按行、按版本） |
| `INVOICE` | 已开票 vs 已匹配/冻结/放行 | 发票状态机与 `InvoiceMatched` 事件序列一致，无重复发票号 |
| `PAYMENT` | 匹配放行金额 vs PaymentRequested vs PaymentRecorded | 已付累计 = Σ PaymentRecorded，**预付款单列特殊总账、不与应付净额相抵**；红冲/部分付款/RTV 单列例外台账 |

> **为何删等式**：v0.1 领域设计 §6.4「未结应付 = 已收未付发票净额」在预付款（业界须挂 special G/L）、贷项凭证红冲、部分付款、RTV 冲销下均不成立，属跨领域套公式。改为分通道、带例外台账的可核对定义。

## 7. 集成架构（对照 Clean Core / ACL）

```
采购域 ──ACL──▶ [ERP 适配器] ──▶ SAP / U8 / 金蝶 / Oracle（存量）
       ──ACL──▶ [Finance 适配器] ──▶ 应付/总账（发票校验、付款）
       ──ACL──▶ [Inventory 适配器] ──▶ 收货/库存
       ──ACL──▶ [Warehouse 适配器] ──▶ 仓储调拨
       ──Webhook──▶ OA（document.archived / contract.draft / contract.signed，见 D3 §4 事件订阅）
       ──API──▶ 外部信用源（天眼查/征信，vendor_profile.credit_source）

Finance → 采购域：InvoiceMatched（match_id / invoice_no / po_no / match_status / matched_amount / exception_code / matched_at）
          PaymentRecorded（payment_no / amount / paid_at）
采购域 → ERP/Finance：PaymentRequested（po_no / invoice_no / amount / vendor_id / legal_entity_id）
```

| 集成方式 | 适用 | 一致性 |
|----------|------|--------|
| 领域事件 + Outbox | 域内/跨部署单元异步协作 | 最终一致、幂等 |
| ACL 适配器 + API | 同步查询外部（如价格/库存校验） | 请求级一致性 |
| Webhook + HMAC | OA 主动推送（合同/付款/验收） | 至少一次、幂等 |
| 轮询增量（15min） | 客户无回调能力时降级 | 最终一致 |
| 双向同步 | 主数据 ↔ 存量 ERP | Golden Record 为权威，版本戳 + Owner 优先级解决冲突 |
| PaymentRequested / InvoiceMatched | 采购域 ↔ Finance 的付款闭环 | 事件驱动，Finance 裁决（§3.1） |

### 7.1 关键事件 payload 契约（对齐事件规范信封）

## 8. 部署架构

> 复用 `assets/procuraAI-部署架构.svg` 的 K8s + 容器形态（**该 SVG 已存在**；`采购AI-部署运维手册（D8）` 为待补交付物，不在本目录，不作为本文依赖）。§8.1 给出模块到部署单元的映射，解决 v0.1「9 模块 vs 单运行时」未对齐问题。

### 8.1 部署单元映射表（P0-3，一期形态）

| 部署单元（进程） | 包含的 Maven 模块 | 数据库 | 单元内协作 | 跨单元协作 |
|------------------|-------------------|--------|------------|------------|
| `bone-procurement-app`（单 Spring Boot 应用，随 BONE 平台统一发布） | 8 个业务模块 + `app` 壳 + **存量 `bone-app-purchase` 适配层**（随同一进程装配，能力基线 §7） | **单库**（metadata-sdk 托管，逻辑 schema 分上下文；DDL 手写进 `bone-init.sql`） | **本地事务 + ApplicationService 编排**；同库跨聚合按 CORE-06 登记例外 | 平台底座（IAM/Workflow/事件）经端口/本地 starter |
| `procuraai-runtime`（独立 AI 运行时） | procuraAI 子系统 | 独立库/对象存储（快照、语料、向量） | — | 业务模块经 AI 端口调用（§5.1） |
| `supplier-portal`（B2B 独立前端 + BFF） | `bone-procurement-portal` | 无直连业务库 | — | API 网关 + 领域事件（Separate Ways） |
| 外部系统（客户侧） | ERP / Finance / Inventory / Warehouse / OA | 各自独立 | — | ACL + Webhook/API/轮询 |

- **一期结论：单应用多模块、单库（含存量适配层同进程）**。因此 §4.2 的「跨模块写经领域事件」**仅适用于跨部署单元**（→ 平台、→ 门户、→ 外部系统）；单元内不引入 Outbox/MQ/Saga。存量 `bone-app-purchase` 与新聚合之间经 `WorkflowStatusPort` + 应用服务编排，不新开进程边界。
- 事件总线与 Outbox 的一期职责：① 平台/门户/外部系统的跨域通知；② 审计与对账留痕；③ 为未来拆分保留契约。**不为同库同进程的调用制造分布式复杂度**（DDD §CORE-08、E-3.1 Ceremonial Architecture 警示）。

### 8.2 演进触发条件与拆分顺序

| 触发条件（满足任一即评估拆分） | 首选拆分 | 说明 |
|--------------------------------|----------|------|

### 9.1 多法人 / 多组织 / 多租户维度模型（P1-6）

> 三者不可混用：**租户** = SaaS 隔离边界；**Legal Entity / Company Code** = 法律与账务主体；**组织（Purchasing Org / Plant）** = 采购与库存业务单元。

| 维度 | 定义 | 承载实体 | 隔离谓词 |
|------|------|----------|----------|
| `tenant` | 客户/租户 | 全部实体 | `tenant_id`（网关注入，强制） |
| `legal_entity` | 法人 / Company Code / 账套 / 税区 / 币种 | LegalEntity（独立聚合） | `legal_entity_id` + 账套 |
| `purchasing_org` | 采购组织（集中采购/分散采购） | SupplyRelationship / PurchaseCost | `org_id` |
| `plant / site / warehouse` | 工厂、供应商地点、收货/仓储点 | Site / Factory / GR | `site_id` / `plant_id` |

**可见性矩阵（冻结安全基线草案 v0.1，RA-2）**：本矩阵是权限码设计的终审依据（§9.1 → 附录 C 权限码）；四维隔离 × 四角色。允许/拒绝的边界以「否」为默认拒绝，越权一律 fail-closed。

| 角色 | 跨租户（`tenant_id`） | 跨法人（`legal_entity_id`） | 跨采购组织（`org_id`） | 跨站点（`site_id`/`plant_id`） | 数据敏感度 |
|------|--------|--------|------------|------------|--------|
| 平台管理员 | 否（除非运维授权 + 审计留痕） | 是（仅运维视图） | 是（仅运维视图） | 是（仅运维视图） | 脱敏后 |
| 集团采购 | 否 | 是（按授权） | 是（集中采购） | 是（按授权） | 业务级 |
| 法人采购/财务 | 否 | **否**（硬隔离） | 按授权 | 按授权 | 业务级 + 金额脱敏 |
| 供应商门户账号 | 否 | 仅绑定 Vendor 角色 | 仅绑定供货关系 | 仅绑定收货点 | 仅自身数据 |

**跨法人/跨组织交易**：内部交易与转移定价规则由财务定义；Transfer（调拨）跨法人时须带 `legal_entity_from/to` 并触发双方账务事件（业界 STO 思路，这也是 Transfer 归入采购域的理由）。

> **冻结状态：Frozen-Draft v0.1（2026-11-09）**。本矩阵**批准前不得变更任一隔离语义**，是 §9.1 → 附录 C 权限码的唯一终审来源。**待会签**（签名栏占位，未签 = 未生效，不得据此放行越权）：CISO `______` / 财务负责人 `______` / 采购负责人 `______` / 数据保护官 `______`。会签后升为 `Frozen v1.0` 并移除「Draft」标记；维度或角色增删须走 ADR + 本矩阵版本 bump。续诊 O4 闭合 R-4（安全基线悬空）。
