# BONE-AI RAG 方案诊断（企业复杂场景胜任度专项）

> **诊断对象**：`bone-ai/bone-ai-rag` 模块源码真态（commit `b819cf38`）+ 《BONE-AI RAG 能力方案》v1.2
> **诊断日期**：2026-10-24　**方法**：源码走查实证（重点核对 `RagApplicationService` / `ChunkRepository` / `NoDocAcl` / `RagAclPort`）+ 业界最佳实践（Modular RAG / 向量库+ANN / 生成侧 grounding / 评测门禁 / 多租户细粒度隔离）对标
> **与 10-23 诊断的关系**：10-23 诊断聚焦"名实相符"（装配断链、幂等半成品），其 P0 项已在 v1.1/v1.2 全部落地。本诊断聚焦**更深一层的问题——"作为已落地的这套能力，能否扛住企业复杂场景"**，并指出 v1.2 自我评估中低估或遗漏的维度。
> **结论先行**：架构方向正确、算法内核扎实，但**作为"已建成态"它仍是"试点级单租户简单检索库"**，距"企业复杂场景可用"还差 6~7 个硬阻塞项的闭环。

---

## 0. 总体判定：能否满足企业复杂场景？

**结论：当前形态不足以满足企业复杂场景，但差距是"补齐"而非"返工"。**

| 维度 | 现状 | 企业复杂场景要求 | 判定 |
|---|---|---|---|
| 检索算法内核 | 混合检索+RRF+rerank+MMR+引用强制 fail-closed，代码真序 | 达标 | ✅ 夯实 |
| 规模/性能 | 每查询**全部切片载入 JVM 内存** + Java 余弦/BM25，无 ANN、无索引下推 | 百万级切片、百并发、亚秒级 P99 | ❌ **硬阻塞** |
| 权限隔离 | 租户硬隔离 + 可选文档 ACL（默认 `null`=同租户全文档可见） | 多 BU / 多角色 / 字段级 ABAC | ❌ **硬阻塞** |
| 生成侧可控 | 检索侧"无出处不得生成"真落地；**生成侧 grounding 守卫未建** | LLM 不超上下文编造，可审计 | ❌ **硬阻塞（合规红线）** |
| 质量门禁 | 阈值（minScore/MMR/candidatePool）**无评测标定** | 上线前 golden set + RAGAS 门禁 | ❌ **硬阻塞（质量裸奔）** |
| 接入吞吐 | 同步、逐切片单次 embed（N 次推理往返） | 异步批处理、embedding 批调 | ⚠️ 大语料入库慢 |
| 租户级韧性 | 无 QPS 限额 / 熔断 / 背压 | 热租户不拖垮 JVM | ⚠️ 与规模项叠加成 OOM 风险 |
| 结构化/多语言 | 纯文本切片，无表格/版式感知，无多语言策略 | 合同/保险表格、中英文混码 | ⚠️ 召回质量受限 |
| 反馈闭环 | 仅离线 RAGAS 规划，无在线反馈 | 用户采纳/拒答 → 主动学习 | ⚠️ 难以持续进化 |

## 1. 已坐实的强项（应保留，不赘述）

- **算法内核是真落地且有单测**：`RrfFuser`(k=60 加权+末位钳制)、`Bm25Scorer`(语料统计单次 O(N) 优化)、引用强制**前置** fail-closed、`minScore` 量纲安全修复（v1.2 已锁死回归测试）。这部分 10-23 诊断的担心已消除。
- **装配层已接通**：rerank/embedding 按 `base-url` 条件装配、`RagInferenceProperties` 已注册、doc_version 幂等 ingest 已落地、ACL seam + 403 fail-closed + 降级可观测均已代码化。v1.2 不是"纸面方案"。
- **降级哲学正确**：读路径可用性优先 + 可观测（`degradations` 透出）+ 严禁切云端，是成熟做法。

> 下文不再重复上述已关闭项，只诊断"企业复杂场景"维度的真实差距。

## 2. 企业复杂场景的硬阻塞项（按阻塞度排序）

### A. 规模瓶颈：每查询全量内存扫描，无索引下推 / 无向量库 / 无分页

**代码实证**：
```java
// ChunkRepository.java:13
default List<RagChunk> findByTenantAndDocScope(Long tenantId, String docScope) {
  List<RagChunk> all =
      QueryBuilder.from(RagChunk.class).where(RagChunk::getTenantId).eq(tenantId).list(); // ← 全量
  ...
}
// RagApplicationService.java:200-216  对 all 逐切片算 BM25 + 余弦（JVM 内 O(N)）
```

**为什么是硬阻塞**：一次 `retrieve` = 把该租户（或租户+文档）的**全部切片连同 CSV 向量文本**一次性拉进 JVM → 全量 BM25 语料统计 + 全量 1024 维余弦。单租户语料到几千切片时，单查询即百万级浮点运算；百并发即撑爆内存/GC。这与 v1.2 把 R4（pgvector+ANN）标为"不为想象规模预付"存在张力——**保险/合同这类企业语料，单个产品线几千份条款文档、每份数十切片，正是会立刻撞上该墙的规模，而非"想象规模"**。

**建议**：R4 优先级应**立即上提为 P0**——迁移到 `pgvector`（或独立向量实例）+ HNSW ANN 索引，把向量检索与 BM25 下推到 DB，检索侧只取 `topK×倍数` 候选回 JVM 做 rerank。过渡期内把 `maxScan` 实际调到安全水位（2000~5000）+ **P99 检索延迟告警**作为止血，而非只留 10000 的"不可行点"上限。

### B. 权限隔离：默认 `NoDocAcl` 返回 `null` = 同租户内全部文档可见

**代码实证**：
```java
// NoDocAcl.java:17  return null;  // 语义：租户内全部文档可见
// RagApplicationService.java:123   visibleDocs==null 时不过滤 → 跨文档越权面敞开
```

**为什么是硬阻塞（企业级）**：企业真实形态是**单租户内多业务线 / 多部门 / 多角色**，且文档有保密分级（如 南京银行对公 vs 零售、长鑫不同产线）。仅有租户级隔离，意味着同租户任一调用方可读到该租户全部合同/理赔语料——这在企业采购合规审查中是**一票否决项**。v1.2 把 B4 标"⚠️ ACL 适配待 L3"，低估了严重性：它不是"补个适配"的小事，而是**没有细粒度 ACL 就无法接入真实企业租户**的上线阻断项。

**建议**：P0 完成 `RagAclPort` 接入文档中心真实 ACL（行级/角色级），并明确**默认必须 fail-closed**（接入前不允许 `null` 上线生产）。同时评估是否需要在 RAG 层补充**属性级（ABAC）元数据过滤**（见 D 项）。

### C. 生成侧 grounding 守卫缺失——"无出处不得生成"只走到检索侧

**代码实证 / 文档自陈**：v1.2 §6.2 已澄清——检索侧 fail-closed 丢弃无锚点切片只是"半条红线"；生成侧（gateway）**并无按 `RagResult` 锚点运行时校验生成接地的能力**，LLM 仍可能凭自身知识编造超出上下文的内容。

**为什么是硬阻塞（合规红线）**：BONE-AI 的核心卖点是"受控、可审计、不编造"。若生成侧无 grounding 校验，整条价值链路在最后一环断裂——检索再准，LLM 一自由发挥就回到"裸 LLM 瞎编"。对保险/合同这类**强监管、强问责**场景，这是不可上线的合规缺口。

**建议**：R1 接线时**必须由 gateway 新增 grounding 校验守卫**（生成后逐结论校验是否可回溯到检索 span，否则拒答/标低置信），把"无出处不得生成"从契约升级为**可验证守卫**。此项应与 B 项同列 P0。

### D. 质量门禁缺失——所有阈值都是"裸奔"上线

**现状**：`minScore` / `mmr-lambda` / `candidate-pool` 已有默认值，但**无任何评测集标定**（R5 标为"前置"却未建）。v1.2 自己也写"按评测校准"，但评测本身未落地。

**为什么是硬阻塞**：没有 golden set + RAGAS（faithfulness / context precision-recall / answer relevancy）门禁，"阈值合理"只是拍脑袋。minScore 量纲安全修好了"误杀"的事故，但**没修"阈值本身是否对"**——一个未经评测的 0.3 可能把 30% 正确命中滤掉，也可能把 30% 噪声放进上下文，无人知晓。

**建议**：P0 落地 R5——golden set + 指标字典 + CI 负向探针（rerank 越权 / 无依据路径 / 间接注入命中 / grounding 失守），以 **eval sidecar**（独立 Python 服务/CI job）承载，Java 侧暴露 `RagRetrieveOutcome` + 生成响应供其消费。**任何阈值调参前必须先有评测基线**。

### E. 接入吞吐：同步、逐切片单次 embed

**代码实证**：`RagApplicationService.ingest` 对 `segments` 循环，每片一次 `embeddingPort.embed(seg.text())` —— N 个切片 = N 次推理往返，全同步、无批量、无异步队列。

**为什么是企业级问题**：企业语料入库常是"一次灌入数万文档"。逐条同步 embed 既慢又浪费推理吞吐（batch embed 的 GPU 利用率远高于单条）。无幂等异步作业也意味着大批量失败难恢复。

**建议**：P1 做 embedding **批调用**（一次请求多向量）+ 异步 ingest 作业（消息队列/批处理），与 B/A 的"索引化迁移"协同（重建作业也是 R10 嵌入轮换的一部分）。

### F. 租户级韧性 / 配额 / 背压缺失（与 A 叠加成 OOM 风险）

**现状**：检索路径除 `maxScan` 粗护栏外，无每租户 QPS 限额、无熔断、无背压。结合 A 的"全量内存加载"，一个热租户（或被滥用）的并发检索即可把 JVM 堆打满。

**为什么是企业级问题**：多租户 SaaS 必须有隔离与配额，否则单租户异常影响全局 SLA。

**建议**：P1 在 `bone-ai-app` / gateway 层加租户级限流 + 检索路径内存预算保护（或推动 A 的索引化从根本消除全量加载）。

## 3. v1.2 自我评估中被低估或遗漏的维度

下列项 v1.2 要么标为"批二/缺口"但低估收益，要么完全未提及；对企业复杂场景它们直接决定"答得准不准"。

| # | 维度 | v1.2 状态 | 企业复杂场景为何关键 |
|---|---|---|---|
| G | **查询改写 / 多跳 / 分解** | B6 ❌ 缺口，"批二决策不建零消费方 machinery" | 企业用户问的是**复合问题**（含否定、跨文档比较、"哪条条款优先于哪条"）。单一 query 嵌入一次检索的召回天花板很低；multi-query / step-back / HyDE 是 2026 工业界 recall 提升标配 |
| H | **结构化 / 表格 / 版式感知检索** | 未提及 | 合同/保险条款充满**表格、附表、定义术语块**；纯文本切片会斩断表格语义，rerank 也救不回。需 layout-aware 切分 / 表格独立索引 |
| I | **多语言 / 混码检索策略** | 未提及（bge-m3 支持 100 语但未规划） | 跨境 / 中国港澳台分支、中英混排条款普遍；需语言感知的 rerank 与切分，否则跨语言召回腰斩 |
| J | **富元数据过滤（生效日期/废止/文档类型）** | 仅 doc_version（幂等用），无查询期过滤 | 企业条款有"仅在 X 日后生效""已被 Y 废止"等时效维度；检索应支持元数据下推过滤，否则召回过期条款 |
| K | **生产反馈闭环 / 主动学习** | 仅离线 RAGAS 规划 | 企业期望系统随使用变好：用户采纳/拒答 → 反哺切分/阈值/黑名单。**无在线反馈 = 质量静止** |
| L | **语义缓存** | B10 ❌ 缺口（优先级已上提） | 企业 KB 问答**重复率极高**（同一条款被大量坐席问）；无缓存则每问重算 embed+BM25+rerank，成本/延迟双高 |
| M | **可审计 trace** | 仅 `LoggingRagEventSink` WARN 日志 | 企业审计/SLA 要求每请求可追溯"用了哪些 chunk、分数、降级"；仅日志不满足，需 per-request trace 落库 |

> 注：G 与 v1.2 的"不做零消费方 machinery"纪律不矛盾——改写机制本身可随 R1（gateway/orchestration 接入，已有 producer）一并落地，不应再等"批二"。

## 4. 优化建议清单（按优先级 + 为什么）

### P0 —— 不满足则无法接入真实企业租户（阻断上线）

1. **规模：迁移 pgvector + HNSW ANN，向量/BM25 下推 DB（A）**
   *为什么*：全量内存扫描是当前唯一会随语料增长线性恶化的硬墙；保险/合同语料规模即可立刻触发。不做则"企业级"无从谈起。过渡期先下调 `maxScan` + P99 告警止血。
2. **细粒度 ACL 接入 + 默认 fail-closed（B）**
   *为什么*：同租户全文档可见是企业采购合规一票否决项；没有它连第一个真实租户都接不进。
3. **生成侧 grounding 守卫（C）**
   *为什么*：合规红线——"不编造、可审计"的价值在生成侧无校验即归零，强监管场景不可上线。
4. **评测门禁 R5 前置落地（D）**
   *为什么*：没有评测，所有阈值（含已修复量纲的 minScore）都是裸奔；质量无法证明、无法回归。

### P1 —— 质量、成本与韧性（上线后短期内必须）

5. **embedding 批调用 + 异步 ingest 作业（E）**
   *为什么*：大语料入库效率与推理成本，且是 R10 嵌入轮换重建作业的基础设施。
6. **租户级限流 / 熔断 / 内存预算（F）**
   *为什么*：多租户 SLA 隔离，防单租户拖垮全局（与 A 叠加的 OOM 风险）。
7. **查询改写 / 多跳（G，随 R1 落地）**
   *为什么*：复合问题召回天花板，企业问答准确率的杠杆点；已有 orchestration producer，不必再等。
8. **语义缓存（L）**
   *为什么*：高重复率场景降本提速立竿见影。
9. **可审计 trace 落库（M）**
   *为什么*：企业审计/SLA 刚需。

### P2 —— 召回质量深化

10. **结构化/表格/版式感知检索（H）**
    *为什么*：合同/保险表格语义，纯文本切片救不回。
11. **多语言/混码检索策略（I）**
    *为什么*：跨境/中国港澳台、中英混排条款召回。
12. **富元数据过滤（生效日期/废止/文档类型）（J）**
    *为什么*：时效维度防召回过期条款。
13. **生产反馈闭环 / 主动学习（K）**
    *为什么*：系统随时间进化，而非质量静止。
14. **嵌入版本轮换双写+重建+监控（R10，已规划）**
    *为什么*：换模型静默断崖的主动防御。

## 5. 给"能否满足企业复杂场景"的最终结论

- **能（方向/内核）**：检索算法内核、fail-closed 安全哲学、混合检索+rerank+MMR、引用强制、可观测降级、DDD 整洁分层——这些是 2026 工业界 Modular RAG 的标准正确做法，且已真代码落地。
- **暂不能（交付态）**：作为"已建成态"，它在**规模、细粒度权限、生成侧可控、质量门禁**四个维度仍是试点级，而这四个恰是企业复杂场景的入场券。任一缺失都会在上线评审被挡回。
- **行动建议**：把 A/B/C/D 四项列为**上线前 P0 必交付**，而非路线图远期的 R1/R4/R5。它们不是"锦上添花"，而是"没有就不能叫企业级 RAG"的底座。其余（E~M）按 P1/P2 节奏补齐即可。
