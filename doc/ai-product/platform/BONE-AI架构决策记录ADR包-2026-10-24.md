## ADR-1：三产品场景化威胁模型与输出内容安全 / 注入检测开关决策

### 1.1 背景与决策问题

详设 §2.1 默认开关表中，四项 LLM 治理能力的当前姿态是分裂的：

| 治理项 | 默认姿态 | 实现机制（代码真源） |
|---|---|---|
| 出口 PII 脱敏 | **默认开** | `PiiRedactor` + ISO 7064 / Luhn 校验位闸门 |
| 租户配额 | **默认开** | `TenantQuotaGuard`（Redis 分布式已代码落地） |
| 成本红线 | **默认开（强制）** | 超限 fail-closed |
| 提示注入检测 | **默认关** | `PromptInjectionGuard` 端口存在，宿主不提供 bean 即不生效 |
| 输出内容安全 | **默认关** | `ContentSafetyGuard` 端口存在，宿主不提供 bean 即不生效 |

（装配机制：`LlmGatewayAutoConfiguration` 以 `ObjectProvider.getIfAvailable(() -> null)` 消费两个 guard 端口——**没有默认 bean，就没有防线**；与 PII 脱敏 / 配额"默认开"形成鲜明对比。）

**决策问题**：三产品（procuraAI 采购风控 / SynapClaim 理赔 / Equity 财务）上线前，输出内容安全与注入检测各自应取什么默认姿态？威胁模型以什么结构归档、由谁签认？

### 1.2 业界对照

- **OWASP Top 10 for LLM Applications 2025（v1.1.0，已核验）**：与本决策直接相关的是四条——**LLM01 提示注入**（直接 + 间接，RAG 场景间接注入是主面，且"没有可靠通用防御，必须分层"）；**LLM02 敏感信息披露**（输出侧泄露）；**LLM05 不当输出处理**（下游代码/业务信任模型输出）；**LLM08 向量与嵌入弱点**（语料投毒、嵌入反演、检索绕过 ACL）。注意 OWASP 2025 版明确提示：RAG 与微调**不能**消除提示注入，只能缓解。
- **TC260-003 / GB/T 45654-2025（已核验）**：安全措施章要求"防止违法信息的生成、设置监看人员、建立关键词库与测试题库、定期安全审计"；安全评估章给出量化口径——生成内容人工抽检 ≥1000 条合格率 ≥90%，问题拒答抽检 ≥300 条拒答率 ≥95%，评估报告需三名负责人签字。**"默认关 + 无监看"在该口径下不可通过评估。**
- **NIST AI 600-1（已核验）**：对 deployer（在基础模型上构建应用的一方，即 bone-ai 平台与三产品）的建议动作包括：**下游使用前做输出校验**、**对 consequential decisions 设人工复核阈值**、**对 RAG 与微调管线做数据最小化**、留存生成内容审计轨迹。其中"输出校验"正是 `ContentSafetyGuard` 的位置。

### 1.3 信任边界与现有防线盘点

| # | 信任边界 | 进入模型上下文的通道 | 对应 OWASP | 现有防线（代码真源） | 缺口 |
|---|---|---|---|---|---|
| B1 | 用户输入 → 网关 | 用户 prompt | LLM01 直接 | 结构化校验（`jsonResponse` 时）；注入检测**端口在、默认无 bean** | 无默认防线 |
| B2 | 检索语料 → 提示词 | RAG chunk | LLM01 间接 / LLM08 | `<RETRIEVED_DATA>` 数据围栏 + 系统提示"是数据不是指令"；引用强制接地；NP4 探针（结构性契约） | 行为级间接注入判定待 LLM 裁判 |
| B3 | 模型输出 → 业务 / 客户 | 生成内容 | LLM02 / LLM05 | 出口 PII 脱敏默认开；接地守卫 `GroundingGuard`；`Confirmed` 类型护栏（批二已机械强制） | 内容安全（违法不良信息 / 价值观）**无默认防线** |
| B4 | 供应链 | 依赖 / 模型 / 语料 | LLM03 / LLM04 | SBOM / CVE 门禁前置；许可红线前置 | 语料来源核验（TC260 语料来源章）待接入方配合 |
| B5 | 消费侧 | 配额 / 成本 | LLM10 | 租户配额默认开 + 成本红线强制 + Redis 分布式配额 | 已闭环 |

**判断**：五条边界里 B3 是唯一"零默认防线且直接对外/对业务"的——这正是本 ADR 要决策的核心。

### 1.4 三产品威胁矩阵（NIST Map 结构）

| 维度 | procuraAI（采购风控） | SynapClaim（理赔） | Equity（财务权益） |
|---|---|---|---|
| 使用者 | 采购 / 风控（内部） | 理赔 / 核赔 / 医学多角色**共享单租户** | 财务（内部） |
| 语料 | 法规库、供应商资料 | 医学图谱、理算条款 | 财务制度、知识 |
| 产出对象 | 内部报告 + 供应商沟通材料（**半对外**） | 理赔通知书、客户沟通（**对外**） | 内部报告（数值敏感） |
| B1 用户面注入风险 | 中 | 中 | 低-中 |
| B2 间接注入面 | 中（外部资料入库） | **高**（语料量大、多源） | 中 |
| B3 输出外流风险 | 中（供应商可见） | **高**（客户可见 + 资金责任表述） | 中（数值错误即资金误判） |
| 当前姿态 | 两 guard 均默认关 | 两 guard 均默认关 | 两 guard 均默认关 |
| **建议姿态** | 内容安全**开**；注入检测灰度 | 内容安全**开**；注入检测**开 + 强误伤监控** | 内容安全**开**；注入检测灰度 |

### 1.5 建议决策

**D1.1 输出内容安全：三产品默认开。**
理由：① 它是平台默认开关表里唯一"治理下游直接受益项却默认关"的能力，与平台既有"默认保守"姿态（PII 脱敏 / 配额 / 成本红线 / RAG ACL deny / ingest PII 掩码全部默认开）不一致；② 输出直达业务表与客户，是 LLM02/LLM05 在下游的利用入口，而 `Confirmed` 类型护栏管的是"AI 结论不直接成为业务决定"，管不了"一段违规生成内容直接外发"；③ TC260 评估口径要求防违法信息生成 + 监看人员 + 测试题库，默认开是取证前提。落地形态：宿主 `bone-ai-app` 提供 `ContentSafetyGuard` 默认 bean（分类器实现走端口，初始可用"关键词库 + 分类模型"两级，与 TC260 第 9 章关键词库/测试题库要求对齐），`bone.ai.gateway.content-safety-enabled=false` 可显式关闭（留逃生口，关闭记 WARN）。

**D1.2 注入检测：默认关作为可接受基线，但必须绑定三件套。**
理由：启发式注入检测误伤面真实存在（高敏语料场景误伤 = 正常条款被判"含注入指令"而拒答，业务不可接受），OWASP 亦明确无通用可靠防御——所以"默认关"可以接受，"裸关"不行。三件套：① **误伤监控**：命中即发事件 + Micrometer 计数（`bone.ai.gateway.injection.blocked` / `inspection.skipped`），按租户维度可看；② **人工抽检**：每周按租户抽样 N 条命中记录人工判是否误伤，误伤率 > 5% 的规则下线重修；③ **按租户灰度能力**：注入检测 bean 支持 per-tenant 开关（语料信任度高的租户先开）。灰度顺序：Equity → procuraAI → SynapClaim（对外程度递增，最后开对外最强的）。

**D1.3 间接注入（RAG 主面）与威胁模型归档。**
数据围栏 + 引用接地 + NP4 结构性探针已落地，保留不动；NP4 从"结构性契约"升级为"行为级判定"（LLM 裁判回填），随 faithfulness 裁判一并做。三产品威胁模型文档按 NIST AI 600-1 Map 结构各归档一份（context / users / data flows / dependencies / foreseeable misuse），作为 TC260 安全评估报告的输入材料，三名负责人签字要求对齐 TC260-003 §8.1。

### 1.6 影响面

| 面 | 影响 |
|---|---|
| 代码 | `bone-ai-app` 新增 `ContentSafetyGuard` 默认 bean（分类器经端口）；`PromptInjectionGuard` 支持 per-tenant 开关（端口方法加 tenant 维度或配置经 `TenantProvider` 解析）；新增误伤监控指标 |
| 配置 | `bone.ai.gateway.content-safety-enabled`（默认 true）、`bone.ai.gateway.injection.per-tenant-enabled`（默认空=全关） |
| 文档 | 详设 §2.1 默认开关表（内容安全行改"默认开"）；接入指南 §1 gateway 行同步；本 ADR 签认版归档 |
| 运维 | 新增监看值班项（TC260 要求"设置监看人员"）；每周误伤抽检流程；关键词库 / 测试题库维护责任 |
| 性能 | 内容安全分类器增加出站时延（预算：同步分类 ≤50ms P99，超预算转异步旁路 + 拒答降级策略——具体阈值随压测标定） |

### 1.7 落地清单（签认后执行）

- [ ] L1.1 `bone-ai-app` 提供 `ContentSafetyGuard` 默认 bean（初始实现：关键词库 + 分类模型两级，关键词库从 TC260 第 9 章要求的关键词类别起步）

- [ ] L1.5 三产品威胁模型文档各一份（NIST Map 结构），交安全合规模口评审
- [ ] L1.6 NP4 探针升级为行为级判定（LLM 裁判回填，随 faithfulness 裁判）
- [ ] L1.7 详设 §2.1 / 接入指南 §1 / 总案 §6.3 口径同步

### 1.8 验证口径

- 内容安全：测试题库抽检合格率 ≥90%（TC260 口径）；负向探针（违规生成被拦截）全过；逃生口关闭时有 WARN + 事件留痕。
- 注入检测：误伤率抽检 ≤5%；灰度租户命中率 / 误伤率分租户可查（Micrometer 指标）。

## ADR-2：写入侧 PII 令牌化与 KMS 接入策略

### 2.1 背景与决策问题

写入侧 PII 已从"明文落库"补齐为**等长局部掩码默认开**（`SensitiveDataMasker`：身份证保 6+4 / 银行卡 Luhn 防误伤保后 4 / 手机号保 3+4 / 邮箱保首字符+域名；`ingest` 先掩码后嵌入；`bone.ai.rag.ingest.pii-mask-enabled=true`）。剩余问题：**掩码不可逆**——需要"按原文精确回查"的接入场景（如与外部系统按身份证号对账、按病历号调阅原文）无法满足。同时，掩码只覆盖四类模式，自由文本中的其他高敏片段（病历叙述、合同金额语境）仍可能明文落库。

**决策问题**：可逆 PII 保护用什么形态？KMS 何时引入？语料分级怎么做？

### 2.2 业界对照

- **PIPL 第 51/52 条**：去标识化（可恢复性受控）与匿名化（不可恢复）的分级思路——平台现状掩码 ≈ 单向去标识化，令牌化 / FPE ≈ 可控可逆的去标识化。
- **NIST AI 600-1**：对 deployer 的"RAG 与微调管线数据最小化"动作——存储态最小暴露是本 ADR 的一阶目标。
- **NIST SP 800-38G**：FF1/FF3 格式保留加密（Format-Preserving Encryption）——密文与明文同字符集、可指定等长，是与本平台"等长掩码 / span 锚点不漂移"架构**同构**的可逆方案。
- **信封加密 + KMS**：数据密钥加密存储、主密钥在 KMS，是密钥托管的业界标准形态（平台网关侧密钥托管已有 seam 先例：`ApiKeyProvider` 端口 + `@Bean` 适配，换 key 不重启）。

### 2.3 选项分析

| 选项 | 形态 | 优点 | 代价 / 风险 |
|---|---|---|---|
| A. 维持等长掩码（现状） | 单向、不可逆 | 零新增依赖；已测试（9+4 例回归）；语义保留 | 不支持可逆回查；只覆盖四类模式 |
| B. FPE（FF1）可逆加密 | 等长、可逆 | span 锚点不漂移（与掩码器架构同构，加一个 `FpeCryptoPort` 即可）；密文不泄露格式外的信息 | 需加密库（**许可核查**：候选实现需过 SBOM / CVE 门禁）；密钥管理 |
| C. Token Vault | 随机 token + 映射表 | 与业务系统完全解耦；可跨系统关联 | 映射表成为新的高敏资产（运维税）；检索"同值判断"保留但局部语义丢失；高可用要求 |
| D. `chunk_text` 整列加密 | 列级加解密 | 实现简单 | 检索前必须解密，等于没保护检索路径；与"先掩码后嵌入"的顺序语义冲突 |

### 2.4 建议决策

**D2.1 语料分级先行（一切的前提）**：接入方按 L1 公开 / L2 内部 / L3 高敏（理赔医学、合同金额、个人标识）标注语料；未标注默认按 L2 处理。分级元数据随 `doc_version` 入库（rag 已有幂等批键，天然承载）。

**D2.2 L3 语料的结构化标识符走 FPE（选项 B）**：身份证 / 银行卡 / 手机号等结构化字段在 ingest 时从"掩码"升级为"FPE 加密"（等长保持、密钥经 `PiiKeyProvider` 端口解析，复用 `ApiKeyProvider` 的 seam 模式——**库形态零必选依赖纪律**）；非结构化正文维持等长掩码；需要原文回查时经授权解密通道（密钥走 KMS 信封加密）。

**D2.3 KMS 经 seam 接入，不做库级重依赖**：`PiiKeyProvider` 端口 + 宿主适配器（与 `MicrometerLlmMetrics` / `ApiKeyProvider` 同构），初始实现可为配置密钥（开发态），生产切 KMS 时只换适配器。**KMS 选型与采购不在本 ADR 范围**，只定架构位置。

**D2.4 触发条件**：出现"可逆回查"需求的接入方入场时启动 FPE；否则维持掩码（不为想象需求预付复杂度——与 pgvector 的"不为想象规模预付"同纪律）。

### 2.5 影响面与落地清单

- [ ] L2.1 语料分级表（L1/L2/L3 定义 + 三产品映射）随接入方 onboarding 落地；`doc_version` 携带分级元数据
- [ ] L2.2 `SensitiveDataMasker` 同级新增 `FpeCryptoPort` seam + FF1 实现（**许可核查先行**，过 SBOM/CVE 门禁后才进主干）
- [ ] L2.3 `PiiKeyProvider` 端口 + 宿主适配器（初始配置态 → 生产 KMS 信封加密）
- [ ] L2.4 ingest 链按分级分流：L3 结构化字段 FPE、其余掩码；`INGEST_PII_MASKED` 事件扩展 `mode=mask|fpe` 维度
- [ ] L2.5 授权解密通道（谁可以解密、解密留痕——对齐审计链无旁路原则）

### 2.6 验证口径

- 等长性：FPE 密文长度 = 明文长度（回归测试锁死，span 锚点不漂移的口径不变）。
- 密钥轮换：轮换演练——旧密钥密文可读、新密钥写入、双轨期双解。
- 不泄露格式外信息：密文统计测试（同明文同密文、频度分析不可还原）。
- 性能：FPE 加解密 P99 增量 ≤10ms/字段（压测报告）。

## ADR-3：配额 / 密钥 / 成本权威态收口的部署形态

### 3.1 背景与决策问题

总案 v1.15 §4.7 已按诊断 §2.2 写入"两段式收口"：配额 / 密钥 / 成本的**权威态**提前收口 `bone-ai-app` 宿主，完整集中式网关仍按原触发条件（出现非 JVM 调用方等）演进。**待产品线确认的是部署形态选择**——三产品（procuraAI / SynapClaim / Equity）已共享同一 provider 且各自进程内嵌库。

### 3.2 业界对照

多产品团队共享一个 LLM 供应商时，业界标准做法是**统一网关面**（统一入口 + virtual key + 集中审计 + 全局限流）：库形态下 N 份配额状态、N 套配置、N 份审计分布在不同进程，"跨产品集中配额审计"这一触发条件事实上已满足（诊断 §2.2 的原判）。反向的教训是：把"出现非 JVM 调用方"作为唯一触发条件过晚——在那之前，成本与密钥的运维税已经付了很久。

### 3.3 选项与建议决策

| 选项 | 形态 | 代价 |
|---|---|---|
| A. 维持纯库形态 | 每产品进程内配额 / 密钥 / 成本 | 零改动；但 N 份状态、审计分散，诊断缺口原样保留 |
| B. **轻集中网关面（建议）** | `bone-ai-app` 宿主为权威态（配额 / 密钥 / 成本的单点真相），三产品仍经 SDK 调库、契约不变 | 宿主成为关键路径（需 HA + 降级预案：宿主不可用时按各产品本地兜底配额，事后对账） |
| C. 完整集中式网关 | 独立部署，非 JVM 调用方也走 REST | 运维面最大；按原触发条件演进 |

**D3.1**：第一阶段取 B（与总案 v1.15 §4.7 已写口径一致，本 ADR 确认并给出接入顺序）；C 的触发条件保持原文不动（非 JVM 调用方出现 / 跨组织接入），不因 B 提前。

**D3.2 接入顺序**：Equity（量最小，试错成本低）→ procuraAI → SynapClaim（最复杂，最后切）；每产品切换时双跑一周（新旧配额口径对账差异 < 0.1% 才算切完）。

### 3.4 落地清单与验证口径

- [ ] L3.1 `bone-ai-app` 宿主权威态部署形态确认（HA 规格、降级预案文档）
- [ ] L3.2 三产品按序接入，每产品双跑对账一周（差异 < 0.1%）
- [ ] L3.3 集中审计报表（按产品 / 租户 / 模型的成本与调用量）从 `MicrometerLlmMetrics` 已有指标直接出，不重复造采集
- 验证口径：任一产品可回答"上个月花了多少、谁花的、超配额的有没有被拦"三个问题，且答案来自单一权威态（不是拼三份进程内数据）。

## ADR-4：规模四件套的容量模型与触发阈值

> 本节把诊断 §3.2 / §3.3 / §3.4 / §3.5 四项 P2 从"需容量模型 / 失效策略"推进为**带公式和阈值的可执行决策**。每项独立生效，互不阻塞。

### 4.1 HITL 规模化（诊断 §3.2）

**容量模型**：需要裁决人 `N = D / (C × O)`，其中 D = 日均待裁量（件/日）、C = 人均日处置量（件/人/日，**初值 40，须按实测标定**）、O = 在线率（0~1，初值 0.8）。

**算例**：三产品合计 D=3000 → N = 3000 / (40 × 0.8) ≈ **94 人**。这意味着"按风险分派裁决人"的单维度路由不够——需要池化 + 路由 + 水位三层：

| 层 | 动作 | 阈值 |
|---|---|---|
| 路由 | 按 `riskLevel` + 领域标签（理赔医学 / 采购法规 / 财务）分派，取代单一按风险分派 | 技能错配率 < 10%（抽检） |
| 水位 | 队列深度 > 2 日产能（即 > (2×D)/(C×O)）→ P1 告警；> 3 日产能 → P0 | 48h SLA 破裂前 ≥24h 预警（2 日产能约等于 2 天消化量，留出介入窗口） |
| 扩容 | 水位持续 3 日超线 → 扩容或降载（提高 AI 自动通过率 / 收紧低风险项免裁） | — |

落地清单：`HitlCapacityProperties`（D/C/O 可配）；队列深度 gauge 接入 `LlmMetrics` 同款 Micrometer 模式；路由维度字段进 `HitlItem`；48h 批量升级保留为兜底而非主路径。
验证口径：压测注入 D×2 待裁量，验证告警在 24h 预警窗口内触发、SLA 不破。

### 4.2 租户标识模型（诊断 §3.3）

**现状**：`getTenantIdAsLong()` 遇非数值租户（`system` / UUID / 子域）返回 null → fail-closed 拒绝（`AI_HITL_TENANT_NOT_NUMERIC`）——把"非数值"等同于"非法"。

**D4.2.1**：抽象 `TenantIdentifier` 值对象（字符串主键），新增 `tenant_id_map(string_key, bigint)` 映射表；非数值租户走映射而非拒绝。**双轨期**：旧 bigint 列与语义保留（存量数据不迁移），新租户一律 string 键；映射未命中仍 fail-closed（拒绝语义不变，只是拒绝理由从"非数值"变为"未注册"——更准确，也更能定位问题）。
落地清单：`TenantIdentifier` 类型 + `TenantIdMapPort` seam；HITL / 配额 / RAG 三处消费点改经值对象；双轨回归测试（数值租户 / UUID 租户 / 未注册租户三态）。
验证口径：UUID 租户端到端可走通 HITL 全链；未注册租户仍被拒且错误码可定位。

### 4.3 语义缓存（诊断 §3.4）

**触发条件**（两个都满足才启动，不为想象收益预付）：① P99 检索延迟 > 500ms（复用 `slow-retrieve-ms` 口径）**持续 7 天**；② 查询重复率——embedding 相似度 > 0.95 的命中占比 > 30%（从 trace 回放统计，不新增采集）。

**失效策略**：缓存键 = `tenant_id + 查询指纹 + 作用域 doc_version 集合指纹`——语料一更新即失效（rag 已有 `doc_version` 幂等键，天然承载）；TTL 默认 24h 可配（覆盖"语料未变但业务语义漂移"的长尾）。

**D4.3.1**：缓存命中也计量（`cache.hit` 指标已有发射点）——防"缓存侧信道"（用响应时延反推是否命中即反推语料内容，LLM02 的变种）与 LLM10 无界消费。
落地清单：`SemanticCachePort` seam + 宿主实现（复用 `LlmResponseCache` 精确缓存的失效框架，扩展为相似度命中）；缓存键构造 + 指纹算法；租户隔离测试（A 租户查询不得命中 B 租户缓存）。
验证口径：重复查询集 P99 下降 ≥40%；doc_version 变更后旧缓存零命中；跨租户命中率 = 0（负向探针）。

### 4.4 第二自托管模型族（诊断 §3.5）

**触发条件**：主族退化（provider 错误率 > 5% 或 P99 > 3× 基线）持续 15 分钟，且场景要求不能降档到纯确定性 / 人工（即"能力降级不可接受"）——注意诊断已确认云端兜底不可用（数据不出域），所以第二族**必须自托管**。

**D4.4.1**：第二族与主族同规格不同族（规避同源故障），经已有 `ModelRouter` 端口路由——`ModelRouter` 是现成的六边形端口，新增一族 = 新 provider 适配 + 路由策略（默认主族、触发条件命中切二族、恢复后回切）；回切需防抖动（迟滞：连续 10 分钟健康才回）。
落地清单：二族 provider 适配（OpenAI 兼容客户端可直接复用）；`ModelRouter` 路由策略 + 迟滞参数；二族质量基线报告（同一 golden set 打分对比，faithfulness / 拒答率不劣于主族 5% 以内）。
验证口径：故障注入演练——主族不可用时 15 分钟内切二族、业务无感（除时延波动）；回切无抖动；二族在 golden set 上质量达标。
