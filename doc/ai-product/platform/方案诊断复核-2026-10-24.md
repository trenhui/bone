## 1. 阻断级（生产前必须闭环，否则合规性/数据不出域不成立）

### 1.1 类型护栏未落地——"资金/责任判定只收 Confirmed"只是约定
- **依据**：详设 §2.3 / §3.3 规则 6——两个 record **在 `bone-ai` 中不存在**，ArchUnit 无拦截对象；当前等价防线是运行期 `DecisionGate` + HITL 留痕。
- **业界对照**：金融/保险受监管系统普遍用**类型系统 + 编译期不变量**保证"AI 结论不能直接成为业务决定"（如 `Unconfirmed` vs `Authorized` 双类型 + 禁止隐式转换）。
- **为什么影响企业复杂场景**：三产品（procuraAI / SynapClaim / Equity）均涉及资金/责任/数值判定，一个开发者绕过 `DecisionGate` 直接把 `AiSuggestion` 落业务表，审计时无法机械发现。**对外宣称"机械强制"在此刻不成立**。
- **建议**：把类型护栏从"批二补建"**提前到首批生产前**（它只依赖两个 record + 一条 ArchUnit 规则，成本极低），否则接入文档不得写"已机械强制"，只能写"工程约定 + 评审项"。

### 1.2 RAG 文档级 ACL 仅 seam——同租户跨文档越权面
- **依据**：总案 §4.5 / 详设 §2.6 / RAG 方案 §7——默认 `NoDocAcl`（仅租户硬隔离）；`RagAclPort` 由接入方 `@Bean` 覆盖后才 fail-closed 403。
- **业界对照**：企业知识库/RAG 的权限模型必须是**文档级 + 行级**，且默认 deny（fail-closed），不能靠"约定由接入方补"。
- **为什么影响企业复杂场景**：企业往往是**单租户内多部门/多团队**（如 SynapClaim 的理赔、核赔、医学多个角色共享一个租户），兜底形态下任一能调 `/rag/retrieve` 的服务都能跨文档读取——这是真实数据泄露面，不是边界 case。
- **建议**：把"文档中心 ACL 接入"从 L3 可选**提升为 Go-Live 硬依赖**，且默认行为应改为"无 ACL 模型时**拒绝检索**而非放行全租户"（更保守的 fail-closed）。

### 1.3 写入侧 PII 明文落库——数据不出域/最小暴露不闭环
- **依据**：RAG 方案 §7.1——`ai_rag_chunk.chunk_text` 与 `embedding` 以明文落库；脱敏只在读取/生成出口。
- **业界对照**：PIPL 与"数据不出域"要求**存储态最小暴露**；检索语料常含身份证、病历、合同金额等高敏字段。
- **为什么影响企业复杂场景**：DB/备份/运维通道一旦泄露即明文外泄；且"脱敏只在出口"与"数据不出域"原则不自洽。
- **建议**：高敏语料在 ingest 阶段做**字段级令牌化/局部掩码**（保留检索语义，如身份证保留前 6 后 4）或 `chunk_text` 列**应用层加密（KMS）**；语料分级（理赔/合同默认高敏）。

### 1.4 注入检测 / 内容安全默认关 + 威胁模型未决策
- **依据**：详设 §2.1 默认开关表——提示注入检测、输出内容安全**默认关**；总案 §6 / 详设 §6.3 威胁模型为 L3 硬依赖（决策记录归档）。
- **业界对照**：受监管内容（保险/金融）应**默认保守**开启基础护栏，按场景威胁模型再精细化，而非默认关闭交调用方决定。
- **建议**：上线前对三产品做**场景化威胁模型决策**，至少对"输出内容安全"在涉及对外/对客户内容的产品侧默认开；注入检测默认关可接受但须配误伤监控与人工抽检（文档已提，须落到决策记录）。

## 2. 规模级（企业复杂场景的真实瓶颈）

### 2.1 向量检索过渡态无法支撑海量语料
- **依据**：总案 §4.5 / RAG 方案 §11（B7 ❌）——过渡态 = MySQL JSON + 应用层余弦；`max-scan` 默认 10000 但"几千条时延迟已劣化却无告警"（RAG 方案 §10 自身已承认）。
- **业界对照**：生产 RAG 规模标准是**专用向量库 + ANN（HNSW/IVF）**，百万~亿级切片靠索引下推，而非内存全载打分。
- **为什么影响企业复杂场景**：SynapClaim 的医学图谱/理算条款、procuraAI 的法规库、Equity 的财务知识——任一产品语料过百万切片，内存全载 + 应用层余弦即系统性劣化；且 `max-scan` 是"不可行点才触发"的上限，正常水位下已慢无告警。
- **建议**：① `max-scan` **下调到实测安全水位（2000~5000）** + 接 **P99 检索延迟告警**（RAG 方案已建议，优先级上提）；② pgvector + HNSW **提前到第二批前**，不为"想象规模"拖延；③ 过渡态期间严格限制单租户语料规模。

### 2.2 集中式网关演进触发条件与现状自相矛盾
- **依据**：总案 §4.7——演进触发条件之一是"跨产品集中配额审计"；但现状已是 **3 个产品（procuraAI / SynapClaim / Equity）共享 provider 且各自进程内嵌库**。
- **业界对照**：多产品团队共享一个 LLM 供应商时，**统一成本控制、统一密钥托管、全局限流、集中审计**在库形态下极难做——N 份配额状态、N 套配置、N 份审计分布在不同进程。
- **为什么影响企业复杂场景**：这正是"跨产品集中配额审计"触发条件已满足的场景，却仍用库形态。骨子里 `bone-ai-app` 聚合宿主已具备集中 REST 面的雏形，只差把"配额/密钥/成本"的**真源**收口到宿主而非散落各产品进程。
- **建议**：重新评估——在 `bone-ai-app` 宿主基础上，把**配额、密钥、成本计量的权威态**提前收口为可控的"轻集中式网关面"（契约不变、库仍复用），而非等到出现非 JVM 调用方才演进。

### 2.3 评测体系严重后置——"按评测校准"沦为口号
- **依据**：全方案反复"阈值压测/评测后修订"，但 eval 多为目标态（详设 §2.7 / §5 现状基线）；RAG 方案 R5 自己写"评测须前置……没有评测，所有'按评测校准'都是空话"。
- **业界对照**：RAGAS /  golden set / CI 负向探针是**阈值标定的前提**，不是事后补。
- **为什么影响企业复杂场景**：`minScore` / `mmr-lambda` / 候选池 / 置信度 0.85 等全是"初值"，无 golden set 支撑就在生产拍定值 = 黑盒调参；且 rerank 越权、无依据路径、grounding 失守等负向探针也依赖 eval 管线。
- **建议**：**评测前置（R5）必须先于任何阈值标定**——先建最小 golden set + 指标字典 + CI 负向探针（rerank 越权、无依据路径、间接注入、grounding），用 eval sidecar（Python/RAGAS）承载，Java 侧只暴露 `RagRetrieveOutcome` + 生成响应；阈值初值标注"未校准"直至首个评测报告。

> **执行跟进（2026-10-24 后续）**：R5 已实质落地，本节原"沦为口号"的判断已不成立——① **JUnit 确定性门禁** `RagGoldenSetEvalTest`（随 `mvn verify` 强制）锁死检索链回归（引用过剔 / RRF 权重 / 分词退化 / 阈值误杀）；② **Python sidecar** `eval/eval_rag.py` 三模式：`score`（golden vs actual 的 recall/precision + 门槛门禁）、`probes`（4 个负向探针 NP1 无依据拒答 / NP2 接地拒答 / NP3 rerank 越权 / NP4 间接注入围栏）、`contract`（零依赖自校验，CI 必跑，证明引擎本身正确）；③ **仍待补**：真实语料的 golden set 扩充、faithfulness 的 LLM/NLI 裁判回填（行为级间接注入判定，NP4 现为结构性契约）。详见文末 §7。

## 3. 工程与运维级

### 3.1 可观测实际未接线——生产"盲飞"
- **依据**：详设 §2.1 `LlmMetrics` Noop 默认；§3.2 gen_ai.* 待 Micrometer（L3）；§6.2 证据落盘成功率告警待配；看板 ⏳。
- **建议**：上线前接 Micrometer + 成本/延迟/错误率/短路率/降档率看板 + trace 落盘成功率 ≥99.9% 告警；AI 成本与质量"看不见"在 enterprise 不可接受。

### 3.2 HITL 规模化能力缺失
- **依据**：仅"创建后 48h 批量升级"（详设 §4 #14），无裁决人**容量/技能路由/负载均衡/队列水位**。
- **为什么影响企业复杂场景**：三产品上线后待裁项可能日均数千，单一"按风险分派裁决人"不足以承接；裁决人池枯竭、技能错配会让 48h SLA 系统性破裂。
- **建议**：补裁决人池 + 容量水位 + 技能/风险路由 + 队列积压告警；把 HITL 当作**生产工作流**而非五态状态机看待。

### 3.3 租户标识模型限制（BIGINT 数值编码）
- **依据**：详设 §2.2——`getTenantIdAsLong()` 非数值（如 `system`/UUID/子域）返回 null → fail-closed 拒绝（`AI_HITL_TENANT_NOT_NUMERIC`）。
- **为什么影响企业复杂场景**：企业常见字符串租户键（子域、UUID、组织编码），当前模型会**直接拒绝**合规租户。
- **建议**：抽象租户标识为字符串主键或增加映射层，避免把"非数值"等同于"非法"。

### 3.4 语义缓存后置（成本杠杆未用）
- **依据**：精确缓存默认关（仅 temperature=0），语义缓存 R9 目标态。
- **为什么影响企业复杂场景**：保险条款/法规问答**重复率极高**，检索 + rerank 是主要延迟/成本源；缓存是最大降本点。
- **建议**：在租户隔离实证后**提前评估** R9（embedding 相似度命中 + TTL），注意语料更新即失效的失效策略。

### 3.5 模型单供应商，无跨族质量降级
- **依据**：锁定 Qwen3.5/3.8-27B 一族；云端备援"随客户形态、默认 fail 到确定性/人工"，即无云兜底。
- **为什么影响企业复杂场景**：单模型族 = 质量 SPOF；provider 退化只能降档到纯确定性/人工（= 能力降级而非质量降级）。
- **建议**：规划**第二个自托管模型族**作质量降级档（非云、数据不出域），提升关键场景韧性。

## 4. 已做对、应保留的强项（勿回退）

1. **fail 到确定性/人工、绝不 fail 到直连模型**——合规场景唯一正确选择，业界网关 fail-open 在此不适用。
2. **证据链无旁路 + 同步落盘拒返**——"响应对不上快照拒绝返回"是审计级保证，超多数开源网关。
3. **无依据不编造 / 引用强制 fail-closed**——RAG 立身之本，且代码真序已落地（非话术）。
4. **不引重型 Agent 框架 + 显式状态机**——受监管领域（保险/采购/金融）的正确取向，自主循环仅限四条件试点。
5. **许可红线前置 + SBOM/CVE 门禁**——供应链安全结构前置，Python 深依赖承载密钥风险已规避。
6. **治理靠结构强制（ArchUnit）而非约定**——除类型护栏外均已机械落地。
7. **流式 SSE 零新依赖补齐 + PII 不强逐片脱敏的取舍**——工程判断成熟。
8. **降级只走本域路径且可观测**——"假装已精排"被明确拒绝，符合数据不出域红线。

## 5. 企业复杂场景就绪路线图（优先级排序）

| 优先级 | 项 | 动作 | 关闭时点 |
|---|---|---|---|
| P0 | 类型护栏（§1.1） | 补建 `AiSuggestion`/`Confirmed` + ArchUnit 规则 6 | 首批生产前 |
| P0 | 跨文档 ACL（§1.2） | 文档中心 ACL 接入 + 默认 deny | Go-Live 硬依赖 |

## 6. 一句话建议

方案**方向正确、纪律严格、合规取向领先业界**，但"企业复杂场景"考验的不是治理理念而是**规模、隔离、评测、可观测四根支柱的落地完整性**。当前四根支柱都有"目标态/待建"缺口，且部分缺口（类型护栏、跨文档授权、写入侧 PII）直接触碰合规红线——应把这批从"批二/目标态"**上提为 Go-Live 硬依赖**，与现状已落地的强项共同构成可上生产的完整闭环。
