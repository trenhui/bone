## 2. 残留问题（F1–F6）

### F1 ⚠️ 总案 C3 置信度三档与详设 §4 #3 冲突（真实跨文档矛盾，高优先）

- **证据**：总案 §2.1 C3（第 48 行）「置信度分级（**初始 ≥0.85 直出 / 0.7–0.85 复核 / <0.7 强制人工**）」；详设 §4 #3（第 404 行）「**0.85 = 自动放行线**（与金额/AI 可用性合取）；**0.7 = HITL 待裁列表展示线**（<0.7 强制在列、不得直出）」，并明确「原『0.7–0.85 复核』档在无抽样机制前不单列操作」。
- **冲突点**：① 总案称 0.7–0.85 是「**复核**」、<0.7 是「**强制人工**」；详设称 0.7 是「**展示线**」（<0.7 强制在列但不等于强制人工，≥0.7 仍可能转人工）。② 总案称 ≥0.85「**直出**」；详设称 0.85 是「**合取放行线**」（金额>阈值或 AI 不可用仍转人工，非纯直出）。
- **危害**：产品侧按总案设计 HITL 流程会多出一层「复核」状态与 SLA，与 `DecisionGate` 实际合取语义不符；L3 评审若只看总案会误判家底。
- **修复**：总案 C3 置信度分级改为与详设同构（0.85 合取放行线 / 0.7 展示线 / 删中间「复核」档），并补 v1.14 变更注。**（本次已执行）**

### F2 ⚠️ README 版本指针滞后（低优先，文档卫生）

- **证据**：README 目录索引称详设「v1.6」、接入指南「v1.4」、SBOM「v1.1」，实际已为 v1.7 / v1.5 / v1.2；且《方案诊断报告》头部仍写「诊断对象：整体方案 v1.8 / 详设 v1.1 / 接入指南 v1.0 / SBOM v1.0」，与当前严重脱节。
- **修复**：README 版本指针刷新（本次已执行）；《方案诊断报告》头部加「本报告诊断基线为 v1.8/v1.1/v1.0，对应修订见各文档 v1.11+ 变更注」的边界说明（避免被误读为当前态）。

### F3 ⚠️ 平台模块默认 5000 元金额阈值（务实风险，中优先）

- **证据**：详设 §4 #17「决策闸门金额阈值 5000 元……**域特异默认值，产品须显式评估**——非金额场景传 null 即跳过金额闸门」。
- **问题**：诊断 P3 原建议「默认 fail-closed（未显式配置即转人工）」，当前方案仅以文档注记缓解、未改默认值。平台模块带保险域语义默认值（5000 元「赔付金额」）仍可能因产品疏忽被误继承（如合同金额场景）。
- **建议**：将 `OrchestrationRequest.amount` 默认值从 5000 改为 **null（未配置即转人工）**，或在 `DecisionGate` 中把「未显式配置阈值」视为 fail-closed。文档同步删除「域特异默认值」措辞。属小改、低风险、高防御价值。

### F4 🔴 系统级「死缝」反模式无自动化门禁（过程缺陷，高优先）

- **证据**：本项目已**四次**踩「端口/缝已设计、零消费方」坑——`RerankPort`（有 NoOp 实现但 `RagApplicationService` 不注入）、`HttpBgeEmbeddingClient`/`HttpBgeRerankClient`（零装配）、`LlmMetrics`（端口就位零消费）、`ApiKeyProvider`（接口就位、客户端构造期固化 key、零实现零消费）。本次虽逐个修掉，但**没有任何机制防止复发**。
- **危害**：这类缺陷在「方案描述已具备、代码零接线」时最隐蔽——文档先于代码写成「已落地」，评审与接入方均被误导（正是 N7/R1 的根因）。
- **建议**：新增两类 ArchUnit 门禁（已在 gateway 落地示范，建议扩至全 11 模块）：① domain 内 `*Port` 接口必须由模块内类实现；② `*Port` 接口须被 application/infrastructure/config 层实际消费。**（gateway 示范规则本次已执行，实跑全绿）**

### F5 ⚠️ ArchUnit 规则数口径不一（低优先）

- **证据**：详设 §3.3 列 7 条「第一批门禁」，§5 称「11 模块各 7 条」，v1.7 头称 gateway「含 ArchUnit 11 条」；实际 gateway `ArchitectureTest` 引用 `BoneDddArchRules` 共 12 条（含框架共享规则）。
- **建议**：统一口径为「文档显式 7 条 + 框架共享 `BoneDddArchRules` N 条」，避免「各 7 条」被误解为全量。

### F6 ⚠️ 诊断报告作为「当前态真源」的误读风险（文档卫生，低优先）

- **证据**：《方案诊断报告》《RAG方案诊断与优化》头部版本号停留在修订前基线，且用语为「诊断对象 = 旧版本」，未声明「本报告为历史修订记录、当前态见各文档 v1.11+ 变更注」。
- **建议**：两份报告头部加一行边界说明，或将结论段标注「已修订闭环」，防止 L3 评审误读为当前缺陷。

## 6. 业界最佳实践对齐（v1.8 增补，2026-10-23 深夜）

> 复核基线为 v1.7/v1.5；以下为基于「2026 主流 LLM 网关最佳实践」补做的差距闭合，不改动已评审骨架，仅补能力 + 订正一处文档口径。

### 6.1 最大能力缺口关闭：流式 SSE

- **差距**：复核时网关**全链同步**——`LlmClient.chat` 一次性返回。而 SSE/流式已是 OpenAI 兼容生态与 LiteLLM / Portkey / Kong 等网关的**事实标配**（首 token 体验、长文逐步呈现、降级兜底）。这是相对 2026 同业实践最显著的单项缺口。
- **落地（详设 v1.8 / 接入指南 v1.6）**：
  - 门面新增 `LlmClient.streamChat(req, Consumer<LlmStreamEvent>)`（默认缓冲回退，**零改传输实现即可用**）+ `LlmStreamEvent` sealed 事件（Token/Done/Error）；应用层 `streamInvoke` **复用 `invoke` 全治理链**（红线→路由→配额→注入→脱敏→缓存命中），仅末端逐片下发、首 token 记 TTFT、流末做内容安全/校验/缓存/计量/证据。
  - 传输层仅 `JdkLlmTransport` 走 **JDK `HttpClient` 真 SSE**（零新依赖），`ResilientLlmTransport` 透传（熔断只守卫「流获取」不守卫「流消耗」）。
  - **契约一致性定案**：流式与 `invoke` 同口径——面向调用方返回原文，PII 脱敏只在「出站请求」与「证据落库」两处，不做逐片流式脱敏（避免跨 chunk 边界漏脱敏与证据标签泄露调用方）；含 PII 强零泄露场景可强制缓冲模式。
