## 一、纠正上一轮的错误结论

上一版报告称"机器内存不足以同时承载 10 个后端 JVM 与 9 个前端 dev server"，
并把多条失败归为"服务反复掉线"。**该结论已作废**，实测反证：

| 层 | 实测 |
|---|---|
| 前端 9 个 Vite dev server | shell 3000 / iam 3003 / metadata 3004 / masterdata 3005 / integration 3006 / system 3007 / extension 3008 / generator 3009 / commerce 3012 —— **全部 200** |
| 后端 10 个服务 | nacos 8848 / gateway 8888 / iam 8081 / blueprint 8082 / system 8083 / masterdata 8084 / integration 8085 / generator 8086 / extension 8088 / metadata 9001 —— **全部在线** |
| 内存 | `memory_pressure` 报 `free percentage 34%`（健康） |

**我为什么错**（这是本轮最值得记的东西）：
1. **沙箱禁掉了 `ps`**（实测 `operation not permitted`，`dangerouslyDisableSandbox=true` 也一样），
   我对"进程占多少内存"**没有任何直接证据**，却断言了内存耗尽；
2. 只能用 curl 探测反推进程存活，而**经网关拿到的是熔断器 503**（`GW_UPSTREAM_UNAVAILABLE`），
   我把它读成了"服务挂了"—— 早前报 503 的 4 个端点**直连全部 200**；
3. `memory_pressure` 明明报了"free 49%"（健康）**被我忽略**，反而用 `vm_stat` 的 Pages free
   自己乘页大小 —— **本机页大小是 16384，我按 4096 算，整整错了一个量级**。

> 这正是本项目记忆里那条纪律的又一次应验：**「环境问题」是能立刻停掉追问且几乎总是错的归因**。
> 该条记录项目里已有，我仍然犯了一次。判据已升级并写入记忆与技能：
> **判"服务是否在"必须直连 + 端口探测交叉验证；判"内存是否紧张"只看 `memory_pressure`。**

## 三、本轮修复的 3 个真实缺陷

### 3.1 `destroyOnClose` → `destroyOnHidden`（8 处 / 5 文件）

antd **5.27.6** 已废弃 `destroyOnClose`，页面控制台持续报 deprecation warning。
全在 masterdata：`QualityIssueBoard` / `TemplateManagement`（3 处）/ `DomainWorkbench` /
`GovernanceBoard` / `ReferenceDataManagement`（2 处）。**这是巡检里唯一的 console error**，现已清零。

### 3.2 表单校验显示英文（40 处漏 `message`）

**症状**：提交时页面出现 `'displayName' is required` / `'name' is required` 这类中英混排。

**根因（全仓 40 处 `rules={[{ required: true }]}` 没写 `message`）**，分布：
EntityManagement 8 / PluginManagement 6 / MonitorAlert 5 / SystemDeployment 4 /
EntityDetail 3 / RuntimeDataManagement 3 / DictManagement 3 / 其余分散。

**修法**（不是逐个补 message，那要改 40 处且易漏）：给 6 个应用各加
`src/components/AppAntdProvider.tsx`（`ConfigProvider locale={zhCN}` + **`form.validateMessages`**），
入口 `main.tsx` 包一层。

**关键实测（差点走错路）**：`locale={zhCN}` **改不掉**这个英文。英文来自 **rc-field-form** 的
`defaultValidateMessages`（`node_modules/rc-field-form/lib/utils/messages.js`），
而 **antd 的 `locale/zh_CN` 里 `Form` 键是空对象** ⇒
**唯一正确入口是 `ConfigProvider form={{ validateMessages: {...} }}`**。

**另一个决策点**：Provider 放 `@bone/shared-utils` 最省事（9 个应用都依赖它），但**那里没声明
`antd` 依赖**（只有 dayjs/i18next/react-i18next）⇒ 会给无 antd 场景强加依赖。
**改为各应用内建**（antd 是各应用直接依赖），不需动任何 `package.json`。

修复后验证：`md-entities`（原本 `'displayName' is required`）→ **无英文提示**。

### 3.3 `Form.Item defaultValue` 用在受控字段上（真 bug）

`ConnectorManagement.tsx` 的 `config` 字段是 `name="config"` 的受控字段，
却把 JSON 模板写在 `<TextArea defaultValue={...}>` 上 ⇒ **antd 不会注入，用户看到空 textarea**。
改用 `Form initialValues`。antd 的告警原文：`defaultValue will not work on controlled Field`。

### 关于 `FlowDesign.tsx` 的自我教训

我尝试把 `Tabs.TabPane` 迁到 `items` API，**连续用 Python/Edit 反复制造语法错误**
（误以为 JSX `{}` 容器内的对象字面量需要转义成 `{'{'}` → 反复改坏；还丢了逗号、删了换行）。
最终靠 `git show HEAD:<path>` 读回干净基线、再用 Edit 做**唯一一处**最小改动
（雪花 ID `Map<number>` → `Map<string>`）才收敛，`tsc` 通过。

> **纪律**：同一文件的多处改动要一次做完并立刻 `tsc --noEmit` 验；改到出乱就**回基线重来**，
> 不要在坏状态上叠加修补。注意 `git checkout` 会连带丢掉本轮其它改动，**禁用**；
> `git show HEAD:<path>` 读文件是安全的。
>
> `Tabs.TabPane → items` 的迁移**留作待办**，要改必须一次成型并立刻验。
