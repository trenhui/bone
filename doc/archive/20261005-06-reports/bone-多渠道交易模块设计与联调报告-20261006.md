## 二、多渠道接扩展点的设计（核心）

### 2.1 三个扩展点，十五个实现

```
ChannelOrderExtPoint      pullOrder / ackOrder                → TB/JD/DY/PDD + Default = 5
ChannelProductExtPoint    listProduct / delistProduct / syncInventory → 5
ChannelLogisticsExtPoint  pushShipment / queryTrace           → 5
```

启动实测（bone-blueprint 日志）：`Extension Points: 4 / Total Extensions: 20 / Enabled: 20 / Unique Codes: 20`
（20 = 15 个渠道实现 + 5 个既有的订单计价扩展）。

**新增第五个渠道的代价 = 新增 3 个 `@Extension` 类，其余零改动**（应用服务、Controller、前端都不动）。

### 2.2 路由维度为什么用自定义维度 `channel`

| 候选 | 结论 | 理由 |
|---|---|---|
| `scenario` | ❌ | 已被「业务场景」占用（拉单/上架/发货）。再塞渠道会让二维信息挤进一维，无法表达「抖音的发货」。 |
| `condition`（SpEL） | ❌ | 四级路由里 **L2 表达式优先于 L3 维度**，任何带 condition 的候选都会抢在精确命中前胜出，渠道路由会被意外劫持。 |
| 自定义维度 `channel` | ✅ | 四个渠道规则互斥，L3 模糊匹配天然只有一个命中，且与业务场景正交。 |

装配点只有一处：`ChannelExtensionPortAdapter.bizContext(...)`，用
`BizContext.dimension("channel", code)` + `ExtensionContextManager.with(...)`。
收口的理由很实在——装配代码散在四个应用服务里，就会出现「某处忘了设 channel 维度 → 落到默认实现 → 渠道功能静默不可用」。

### 2.3 兜底实现

`DefaultChannel*Extension` 不带任何路由维度 → 引擎判定为默认实现，只在 L4 命中；
四个渠道实现带 `channel=XXX`，在 L3 命中。二者不互相抢占。

### 2.4 业务接口与技术注解分离

`@ExtensionPoint` / `@Extension` 是框架注解，`domain` 层不允许有框架依赖（ArchUnit 硬约束）。
所以：领域侧定义**纯接口契约**（`domain/extension/channel/*ExtPoint`），
基础设施侧用**同名技术接口再挂注解**（`infrastructure/extension/channel/Extension*ExtPoint`），
由适配器把二者接起来。

## 三、领域模型与状态机

| 聚合根 | 表 | 状态机 |
|---|---|---|
| `Channel` | `bp_channel` | enabled / orderSyncEnabled（能力在扩展实现，配置在表里——**能力与配置必须分离**，否则改一次启用状态就要发版） |
| `ChannelProduct` | `bp_channel_product` | `UNLISTED → LISTING → ONLINE → DELISTING → OFFLINE`，异常落 `FAILED` |
| `Inventory` | `bp_inventory` | `available / reserved` 双账（多渠道共享实物库存的唯一真源） |
| `Shipment` | `bp_shipment` | `CREATED → SHIPPED → IN_TRANSIT → SIGNED`，异常落 `FAILED` |
| `ShipmentTrace` | `bp_shipment_trace` | 追加写，不更新 |

**状态先行原则**：上架先落 `LISTING` 中间态再调渠道。反过来（先调渠道后落库）会在「渠道成功 + 本地回滚」时
留下「渠道有商品、本地无记录」的幽灵商品，且无法自动发现；先落中间态则崩溃后可通过扫描 LISTING 超时记录补偿。

## 四、本轮修复的四个真实问题

### 4.1 R9「一事务一聚合」：把可观测字段踢出业务事务

`pullAndCreate()` 原本在落单事务里顺手 `channelRepository.update(channel)` 写 `lastSyncAt`，
`listProduct()` 同理写 `extImplCode` —— 结果一个事务里持久化了两个聚合类型，被 ArchUnit 拦下。

修法不是删功能，而是**换正确位置**：

```java
// 业务事务内：只发布事件
domainEventPublisher.publish(new ChannelRoutedEvent(tenantId, code, "PULL_ORDER", Instant.now()));

// 提交后、独立事务：ChannelRoutedEventHandler 投影到渠道（REQUIRES_NEW）
@Transactional(propagation = Propagation.REQUIRES_NEW)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(ChannelRoutedEvent event) { ... }
```

收益不只是过门禁：可观测写入失败只丢一条投影，**不会把已成功的订单/上架一起回滚**——
这正是「可观测」应有的失败语义（反过来才是本末倒置）。

顺带把 `extImplCode` 的推导从「应用服务里硬编码 switch」收敛到端口
`ChannelExtensionPort.resolveImplCode(channelCode, useCase)`，由基础设施适配器实现，消除第 N 份真源。

### 4.2 R2 反贫血：`setOrderSync(boolean)` → `enableOrderSync()` / `disableOrderSync()`

同步开关不是「赋个值」，而是有前置约束的业务动作（停用渠道不得开启）。写成 setter 会把约束推给调用方，
漏判就会出现「停用渠道仍在拉单」；写成具名方法约束内聚在聚合内，无法绕过。

### 4.3 `ShipmentTrace` 的 `created_at cannot be null`

`AbstractEntity` 的审计字段 SDK 不代填，写入时被兜成 500，导致「发货并回传渠道 / 同步轨迹 / 签收」三个用例失败。
已在 `ShipmentTrace.of()` 里显式 `setCreatedAt/setUpdatedAt/setDeleted`。

### 4.4 i18n 门禁红灯（11 个错误码未登记台账 / 无译文）

新增的 11 个 `BP_CHANNEL_* / BP_INVENTORY_* / BP_SHIPMENT_*` 只进了代码，没进
《Bone-错误码登记》§6台账与前端语言包。已补齐：台账 11 行 + `zh-CN` / `en-US` 各 11 条。
另修 `Bone-DDD-最终实践方案.md` 里 2 处指向已改名文档的断链（`写端点授权缺口决策清单` → `写端点授权收敛报告`）。

### 8.2 巡检中修掉的 2 个**探针**缺陷（不是产品缺陷，但会掩盖真问题）

1. **按 `rows>0` 判定「支付管理」恒红** —— 支付页是「发起 / 查询」表单页，
   `PaymentController` 本就没有列表端点（只有 `initiate` / `callback` / `{id}` / `{id}/refund`）。
   判据改为按**页面形态**分流：列表页看行数，表单页看 `input.ant-input` 数量。
2. **发起支付被拒 `BP_ORDER_STATUS_CONFLICT: PAID`** —— 探针挑的「订单列表第一行」早已支付过，
   重复发起被服务端正确拒绝。改为支付前用 `/api/v1/channel-orders/pull` **现造一笔 CREATED 单**；
   `paymentId` 同理必须从 `initiate` 响应体取（mock 支付链接里只有 `order` 和 `token`，没有 `paymentId`）。

### 8.3 一个被**证伪**的怀疑（记录下来避免下次重复排查）

UI 上架填的「商品名称 / 挂牌价」在 DB 里看不到 —— 一度怀疑 `listProduct()` 重复上架时不更新快照。
定向验证（`POST /api/v1/channel-products` 重复上架 `JD/900001`）证明**会更新**
（`重上架名称校验 / 77.70`）。真因是**时序**：UI 巡检之后跑的 `multichannel.py`
又用旧值重新上架覆盖了一遍。教训：`tail` 一眼看到的 DB 值不代表最后一次写，判归属要看执行顺序。
