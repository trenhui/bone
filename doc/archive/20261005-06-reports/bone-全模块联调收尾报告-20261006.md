## 二、额外定位并修复的缺陷 B：`/error` 未放行 ⇒ 业务异常全被误报成 401

### 症状与排查弯路

修完权限码后，file 的 upload/delete 仍返回 401。我先后排除了「密钥不一致」（两边 `secret-key` md5 相同）、
「token scopes 类型不对」（是 List 且含目标码）、「DB 绑定错误」（admin→SUPER_ADMIN→82 正确）、
「主类 scanBasePackages 缺包」（已含 `com.bone.core.security.jwt`）—— **全都不是**。

### 决定性证据（开 TRACE 日志）

给 file 开 `logging.level.org.springframework.security=TRACE` + `logging.file.name=/tmp/file-sec.log`
（**必须写文件**：`mvn spring-boot:run | tail -N` 会缓冲日志，TaskOutput 读不到）：

```
Securing GET /api/v1/file/files/0/x.txt
  Invoking JwtAuthenticationFilter (7/13)
  AnonymousAuthenticationFilter : Did not set SecurityContextHolder since already authenticated   ← 认证成功！
  Invoking AuthorizationFilter (13/13)
Securing GET /error                                        ← 业务异常后转发到 /error
  AuthorizationDeniedException: Access Denied               ← /error 不在 permitAll ⇒ 被拦 ⇒ 401
```

**因果链**：认证通过 → Controller 抛异常（对象不存在）→ 容器 FORWARD 到 `/error`
→ `/error` 不在 `permitAll` → `AuthorizationDeniedException` → **返回 401**。

⇒ **任何业务异常都会被误报成"未认证"**，把真实的 404/403/500 全部掩盖。
这正是我在前几轮把 401 误判成"密钥不一致/授权缺失"的根源。

### 修复与效果

在 file 的 `SecurityConfig` `permitAll` 白名单加 `"/error"`（附 why 注释）。

| 请求 | 修复前 | 修复后 |
|---|---|---|
| 无 token `/files/test` | 401 | **401**（语义正确，不变） |
| 有 token `/files/test` | 200 | **200**（不变） |
| 有 token `/files/0/x.txt`（对象不存在） | 401 ❌ | **404** ✅ 真实业务码 |
| 有 token `/nonexist` | — | **404** |

### 横向发现：全仓 8 个模块都有这个隐患

`iam` / `system` / `masterdata` / `integration` / `metadata-server` / `blueprint` / `generator` /
`extension-studio` 的 `SecurityConfig` **均未放行 `/error`**（实测 `grep -c '"/error"'` 全为 0）。

它们没暴露，是因为都有 `@RestControllerAdvice`（bone-web 的 `globalExceptionHandler`）
在 filter 内就把异常转成 `ApiResponse`，**不会走到 FORWARD `/error`**。
**file 是唯一例外** —— 它的 `download` 端点直接写 `HttpServletResponse`（`in.transferTo(out)`），
路径上没有兜底 advice ⇒ 必然走 `/error`。

**本轮只改 file**（唯一实际暴露的），其余 7 个建议在各自下次改动该模块时顺手补上，
理由与修法已写进 file 的 `SecurityConfig` 注释里。

## 四、本轮沉淀的可复用方法

### 定位"业务异常被误报成 401"的通用手法
1. 开 `logging.level.org.springframework.security=TRACE`；
2. **日志必须写文件**（`logging.file.name=...`）—— `mvn spring-boot:run | tail -N` 会缓冲，TaskOutput 读不到；
3. 判读：`AnonymousAuthenticationFilter : already authenticated`（认证成功）
   + 紧随的 `Securing GET /error`（业务异常转发）⇒ 确诊。

### 两条否定判断的教训（本轮又验证一次）
- **`find` 异常退出（SIGTERM）不能作"不存在"的依据** —— 我据此错判"SDK 源码不在本仓"，而它就在
  `bone-engine/bone-metadata-sdk`；
- **跨轮次下"外科手术级"结论前，先 `ls -la <artifact>` 确认测的是最新构建** —— 那个"缺 `m.id` 的 SQL"
  来自旧 jar。**服务重启 ≠ jar 更新**。
