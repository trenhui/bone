## 一、本轮基线：环境从零恢复

接手时环境是**残缺**的：只有 blueprint / metadata-server / studio-generator / extension-studio / gateway
五个服务在跑，iam / system / masterdata / integration / file 全部未启动，Nacos 未运行。

恢复过程中撞到**三个环境陷阱**，每个都造成了大量误判时间。这是本轮最实用的产出：

| # | 陷阱 | 症状（极具误导性） | 真因 | 处置 |
|---|---|---|---|---|
| 1 | `SERVER__PORT=59538`（IDE 注入） | 日志明确打 `Started IamApplication in 2.993 seconds`，但 8081 一直 000。看起来像"服务起不来/被 OOM 杀" | Tomcat 实际监听 **59538** 而非 8081 | 启动一律 `env -u SERVER__PORT -u SERVER__HOST -u SERVER_PORT` |
| 2 | shell 有 `HTTP_PROXY` | 服务没起返回 **502**（不是 000）；**同一命令内前后两次探测给出矛盾结果** | 代理拦截了 `127.0.0.1` | 探测一律 `curl --noproxy '*'` |
| 3 | 16GB 扛不住 10 个 JVM | 并发启动时**日志停在同一秒、无任何异常栈**，看起来像"启动很慢" | 内存耗尽后被系统回收（实测 free pages 最低 1792 ≈ 28MB，swap 1.9GB，Pageins 550 万次） | 严格串行 + 堆压到 320~448MB + `-XX:TieredStopAtLevel=1` |

### 1.1 一个值得单独记录的技术结论：fat jar 对 5 个模块必然启动失败

`iam / system / masterdata / integration / file` 的 `application.yml` 含
`spring.config.import: nacos:bone-common.yaml`，报 `Incorrect ConfigDataLocationResolver chosen`。

排查走了三层排除（**注意：Nacos 明明活着、8848 返回 200，也照样报这个错**）：

- resolver 类在 jar 里 ✓
- starter 与 `spring-alibaba-nacos-config` 的 `META-INF/spring.factories` 都在、且含 `ConfigDataLocationResolver=` ✓
- Spring Boot 3.5.16 的 `ConfigDataLocationResolvers` 仍用 `SpringFactoriesLoader`（未迁走）✓
- **⇒ 落在 nested jar 上**：Spring 的 factories 加载器扫不到 fat jar 内嵌 jar 的 `META-INF/spring.factories`，
  于是 `NacosConfigDataLocationResolver` 未注册。

两个关键陷阱：**命令行 `--spring.config.import=` 与 `SPRING_APPLICATION_JSON` 都覆盖不了它**
（yml 里的 import 列表是**合并**不是替换）——所以"让 Nacos 配置消失"这条路走不通。

**处置**：这 5 个模块改用 `mvn -o spring-boot:run`（exploded classpath）启动，实测正常
（`Load config[dataId=bone-common.yaml]` + `Started`）。另 5 个无 `config.import` 的模块 `java -jar` 正常。

已把这套流程固化为 **`scripts/dev/up-all-services-e2e.sh`**（分阶段：Nacos → 网关 → 依赖 Nacos 的 5 个 → 其余 4 个；
串行等待 health 通过再起下一个；小堆参数；`--noproxy` 探测），可直接复跑。

## 二、修复的后端架构缺陷：studio-generator 从不校验平台 JWT

### 2.1 缺陷描述

`studio-generator` 的 `SecurityConfig` 只有 `httpBasic()` + `anyRequest().authenticated()`，
**没有任何 JWT 校验**。而网关与前端统一发 `Authorization: Bearer <JWT>` ⇒ 生成器**全部端点在真实链路上恒 401**
（`AUTH_UNAUTHORIZED: 未认证或缺少访问凭据`），直连 8086 也一样。

横向对比确认这是**遗漏而非有意设计**：全仓 8 个模块都依赖 `bone-security`（JWT 验签所在模块），
**唯独 studio-generator 没有**；`bone-blueprint` 等模块都有 `JwtAuthenticationFilter`。

更值得注意的是它为何能长期存活：`httpBasic()` 分支让既有契约测试（`withBasicAuth()`）**全绿**，
而生产流量走 Bearer 永远进不来——典型的"测试全绿但线上不可用"。

### 2.2 修复内容（照 bone-blueprint 范式，5 处协同）

| 文件 | 改动 |
|---|---|
| `bone-engine/studio-generator/pom.xml` | 加 `bone-security` 依赖（补齐第 9 个模块） |
| `.../infrastructure/security/JwtAuthenticationFilter.java` | **新增**，继承 SDK 的 `AbstractJwtAuthenticationFilter`，验签后把 userId/tenantId 写入 MDC |
| `.../config/SecurityConfig.java` | `.addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)`；**保留 httpBasic**（既有契约测试依赖） |
| `.../StudioGeneratorApplication.java` | `@ComponentScan` 补 `"com.bone.core.security.jwt"` |
| `.../resources/application.yml` | 补 `bone.iam.jwt.secret-key`（缺失会落到 SDK 默认 `change-me-...`，与签发方不一致） |

两处坑在修复过程中真实踩到并已写入代码注释：
- `JwtConfig`/`JwtTokenService` **无任何自动配置**（`bone-security` 无 `spring.factories` /
  `AutoConfiguration.imports`）⇒ 不扫包就报 `required a bean of type JwtTokenService that could not be found`；
- 端点路径是 `/api/v1/generator/data-sources`（**带连字符**）。

### 2.3 测试锁定 + 负向探针

新增 `JwtAuthenticationFilterTest`（5 用例，`@SpringBootTest` + `MockMvc` + `springSecurity()`）：

| 判据 | 作用 |
|---|---|
| `bearerTokenIsAccepted` | **核心**：带合法 Bearer 必须 2xx（修复前恒 401） |
| `requestWithoutTokenIsRejected` | 防"过滤器放行所有人"的反向退化 |
| `forgedTokenIsRejected` | 防"只看 Bearer 前缀就放行" |
| `secretKeyIsSharedWithIssuer` | 密钥不得为 SDK 内置 `change-me-*` 默认值 |
| `jwtBeansAreAvailable` | 防 `@ComponentScan` 漏包的回归 |

**顺带发现第 3 个缺陷**：`src/test/resources/application.yml` **shadow 掉了主配置的 `bone.iam.jwt`**
⇒ 测试环境落到 `change-me-...` 默认值，而测试里签发与验签都用它而"自洽"
⇒ **密钥配错这类缺陷在测试中永远测不出来**。已补上同款声明。

**负向探针（精确命中）**：删掉 `.addFilterBefore(...)` 一行 ⇒ 只有 `bearerTokenIsAccepted` 转红
（`401 expected:<SUCCESSFUL> but was:<CLIENT_ERROR>`），其余 4 条仍绿 ⇒ 判据精确、
没有过度敏感。`cp` 还原后复验 **5/5 绿**。

## 三、修复的前端缺陷：40+ 处类型错误背后的真实运行期 bug

前端 9 个微应用原本有 **6 个应用共 40+ 处 `tsc` 错误**。逐条核查后发现
**多数不是类型洁癖，而是真实运行期缺陷**——后端有全局 `Long→String` 序列化器（雪花 ID 保护），
但页面代码里大量地方仍按 `number` 处理，**19 位 ID 超出 2^53 会被静默截断**：

| 文件 | 缺陷 | 实际后果 |
|---|---|---|
| `EntityScopeContext.tsx` | `Number(localStorage.getItem(...))` | 选中态永远匹配不上，每次刷新回落首个模型 |
| `EntityManagement.tsx` | `selectedRowKeys.map(Number)`（批量发布/删除两处） | **操作到错误的实体** |
| `modelTransfer.ts` | `createRes.data as unknown as number` | 同类截断风险 |
| `PluginManagement.tsx` | `UNBOUND_EXT_POINT_ID = 0` 与 string 型 `extPointId` 比较 | `'0' !== 0` 恒真 ⇒ **"未绑定"判断静默失效** |
| `PluginManagement.tsx` | `undeployingId: number \| null` 与 `record.id` 比较 | **卸载 loading 永不显示** |
| `QualityResult.tsx` | 雪花 ID 录入用 `InputNumber` | 输入即截断 |
| `Marketplace.tsx` / `PluginManagement.tsx` | 同上两处 `InputNumber` | 同上 |
| `DependencyGraph.tsx` | 6 处 `Map<number,…>` / `Set<number>` / `number[][]` | 依赖图布局键类型错 |
| `QualityRuleManagement.tsx` | `entityId ?? 0` 给 string 字段兜底 | 类型错 + 语义错 |
| `FlowDesign.tsx` | `Map<number, string>` 但键是 string ID | 连线映射失效 |
| `SystemDeployment.tsx` | 模拟数据 `id: 1/2` 与 `id: string` 不符 | 部署历史渲染类型错 |
| `useCodeGeneration.ts` | `tenantId: 0`（number） | 平台租户 ID 类型错 |
| `masterdata-app/api.ts` | `executeCheck` 返回 `ApiResponse<number>` | checkId 截断风险 |

统一修法：**ID 维度一律 `string`；雪花 ID 输入框改 `Input` 而非 `InputNumber`；`Map`/`Set`/数组键类型同步改 `string`**；
模拟数据的假 ID 补引号。**修完 9/9 微应用 `tsc --noEmit` 全绿**（含 iam / commerce / shell 三个原本就绿的）。

### 5.2 5 条分页断言回归 —— **已定位并修复**（真因在 E2E 脚本，不在后端）

**排查路径**（每步排除一个可能）：读 `ConfigPageQuery`（`page`/`size` ✓）→ `ConfigPageReq`（✓）→
MapStruct 生成的 `ConfigAssemblerImpl.toQuery`（`setPage`/`setSize` 都传了 ✓）→
`ConfigApplicationService.page`（传给仓储 ✓）→ `SystemConfigRepository.pageByKeyword`
（`query.page(page, size)` ✓）⇒ **后端整条链路完好**。

直接实测两种参数，结论明确：

| 请求 | 结果 |
|---|---|
| `?pageNum=1&pageSize=3` | `rows=8 total=8 size回显=10` ← size 被忽略、回落默认 10 |
| `?page=1&size=3` | `rows=3 total=8 size回显=3` ← **正确生效** |

全仓核对：`system`/`masterdata`/`metadata`/`integration` 的 `*PageReq`/`*PageQuery` **全部已是
`page`+`size`**；`grep -rln "pageNum" --include="*.java"` 在各模块 `src/main/java` 下**零命中**
⇒ 后端契约已彻底统一，**只有 E2E 脚本滞后**。

修 `scripts/e2e/chains.py` 8 处（`pageNum=`→`page=`、`pageSize=`→`size=`）并更新过期注释。
**复验**：`系统配置·行数不超过 pageSize(3): rows=3 total=8` ✅、`系统日志: rows=3 total=5` ✅。

> **教训**：分页契约统一后，测试脚本会静默失效，且表现为「断言红」而不是「参数错」。
> E2E 脚本里凡是写死分页参数的地方，契约变更时必须同步。

### 5.3 【重大发现】`bone-metadata-sdk` 1.0.0 的 `Repository#findById` 缺陷 —— **需你裁定修法**

上一版报告把 `创建受限账号` 404 判断为"部门树租户口径不一致"，**这个判断是错的**。
连查 4 轮后定位到真因，**推翻了此前所有假设**。

**抓到的 SQL**（把 SDK 的 `SqlExecutor` 日志开到 DEBUG 后拿到）：

```sql
SELECT m.deleted, m.id, m.name, ..., m.tenant_id
  FROM iam_dept m
 WHERE m.deleted = :deleted_0 AND m.deleted = false AND m.tenant_id = :_sdk_tenant_id
 params={deleted_0=770000000000000002, _sdk_tenant_id=0}
```

两个致命问题：
1. **`m.id = :id` 条件完全缺失**（SQL 里根本没有 id 条件）；
2. **传入的主键值被绑定到软删占位符 `deleted_0` 上**（`:deleted_0=770000000000000002` 就是我传进去的部门 id）。

⇒ `findById` **永远返回 null**。

**决定性反证**：非 0 租户（9001）生成的 SQL **一模一样**（同样缺 `id`、值同样绑到 `deleted_0`），
对照组 `findByIdFindsDeptOfNonZeroTenant` 同样红。
⇒ **不是"平台租户 0 特殊"，是单查路径整体失效**。我之前 7 轮排除全部错在同一个预设：
「列表路径通 ⇒ 单查路径也通」。

**影响面**：全仓 `.findById(` 共 **147 处**、覆盖 **7 个模块**
（blueprint 4 / metadata-server 5 / studio-generator 10 / iam 11 / integration 15 / masterdata 13 / system 6）。
凡依赖它做存在性判定的写路径都会静默失败 —— 线上表现为「资源不存在」类 404/500，
**而数据其实好好地在库里**。这也解释了为什么 `depts/tree`（列表）通、建账号（单查）不通。

**SDK 源码不在本仓**（外部 jar `com.bone:bone-metadata-sdk:1.0.0`，来自 `~/.m2`），本仓改不了。
**请你裁定**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（治本，推荐）** | 在 SDK 侧修 `SqlQueryBuilder` 的条件绑定 | 改的是外部依赖，不在本仓；收益是 147 处一次性修好 |
| **B（绕行，不推荐）** | 本仓 147 处 `findById` 换成 `QueryBuilder`/`Criteria` 显式查询 | 工作量大，且会推翻 HC-006「持久化只用 SDK」的收敛方向 |

### 5.4 E2E 脚本里的雪花 ID 截断（同前端 `Number()`，已修）

`deptId: int(did)` / `orderId: int(oid)` / `paymentId: int(pid)` 共 7 处改为 `str(...)`。
Python 的 `int()` 与 JS 的 `Number()` 一样对 19 位雪花 ID 静默截断。

但 `orderId`/`paymentId` 的截断是同类真实隐患，改掉是对的。
