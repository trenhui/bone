### 1.2 `ci-check.sh` 跑通：修了 3 处才通

这是本轮最费工夫的部分 —— 脚本此前**必挂**，且每次挂的原因都不同。

**修 ①：ArchUnit 步缺 `failIfNoSpecifiedTests`**

```
[2/16] Failed to execute goal surefire:test on project bone-architecture-test:
       No tests matching pattern "*ArchitectureTest"
```

`bone-architecture-test` **不是 reactor 业务模块，而是 ArchUnit 共享规则的 `test-jar`**
（各模块以 `<scope>test</scope>` 引用，磁盘上**连目录都没有**、`find` 结果 0 个 java）。
`mvn test` 在 reactor 跑时会对它也执行一次 surefire，而它没有任何测试类 ⇒ 模式无匹配即失败。

**关键发现**：`scripts/check.sh` 的两处 ArchUnit 调用**早就带了**
`-Dsurefire.failIfNoSpecifiedTests=false`，**只有 `ci-check.sh` 漏了**
⇒ 同一个参数在两个脚本里必须一致，改一处要查另一处。

**修 ②：14 个未格式化文件（4 个模块）**

全是 commerce 多渠道交易模块（前序会话）的遗留、**未提交**：
`ChannelBuyer*`（4 个）、`ChannelBroadcast*`（7 个）、`IntegrationOutboxRecord`、
`CodeGenerationHistory`、`AlertRecord`、`SystemLog`。
`mvn -o -q -pl <4 模块> spotless:apply` 一次修完。

**修 ③：`mvn jacoco:check` 裸 goal 必挂（两层原因，缺一不可）**

```
[4/16] Failed to execute goal jacoco:check (default-cli) on project bone-parent:
       The parameters 'rules' for goal ... are missing or invalid
```

1. **缺 `goal@executionId`**：门槛 `<rules>` 配在 `bone-parent/pom.xml` 里
   `id=check` 的 **execution 级** configuration，裸 `mvn jacoco:check` 走 `default-cli`
   **拿不到它** ⇒ 参数缺失。修法 `jacoco:check@check`。
2. **必须 `-pl` 限定**：父 POM 把 jacoco 声明在 `<pluginManagement>`，裸调用会对
   **全仓每个模块**执行。而真正配了插件的**只有 `bone-metadata-sdk`**
   （全仓 `grep -rln jacoco-maven-plugin` 只有 2 处：sdk 自身 + 父 POM），
   未接入模块没有有效覆盖率数据 ⇒ `bone-datasource` 报
   "Coverage checks have not been met"，属于**对未接入模块的误报**。

**这里注释与实现不符**：脚本注释本就写着"仅对配置 jacoco 插件的模块生效"，
但命令实际对全仓执行。修法是**让实现向注释对齐**，而不是改注释迁就实现。

**jacoco 门禁的负向探针**（证明门槛真在生效、不是被跳过）：

```
-Djacoco.minimum.line=1.0
⇒ Rule violated for bundle bone-metadata-sdk:
   lines covered ratio is 0.4, but expected minimum is 1.0
⇒ BUILD FAILURE
```

正向 `All coverage checks have been met` + EXIT=0。

## 三、新增门禁 + 清掉一个假门禁

### 3.1 新门禁 `scripts/ci/check-error-endpoint-permit-all.py`（`check.sh` 第 26 步 + CI blocking）

**判据**：凡声明 `.authorizeHttpRequests(...)` 的 `SecurityConfig`，
其 `permitAll` 白名单必须含 `"/error"`。

**豁免两种**（否则必然误报）：
① 收口是 `anyRequest().permitAll()` 的整体放行型（联调/匿名 profile，`/error` 天然可通）；
② 不含 `authorizeHttpRequests` 的非 Web 配置类。

**实现要点**：
- 不用正则硬匹配整个调用（嵌套括号 + lambda 体极易截断），
  改为从 `.authorizeHttpRequests(` 起做**括号配平扫描**切块；括号未配平时取剩余部分
  （宁可误报不可漏检）。
- **内置自检**：`SECURITY_CONFIG_GLOBS` 里的模块路径若不存在 ⇒ 直接失败。
  理由是路径写错会让该模块**静默不被检查**，那正是"假绿"。

**负向探针（两个模块各验一次，精确命中）**：

| 探针 | 门禁输出 | 还原后 |
|---|---|---|
| `bone-system` 的 `"/error"` → `"/errorXXX"` | 只报 system 一个，EXIT=1 | ✅ 8 个全放行，EXIT=0 |
| `bone-blueprint` 同样注入 | 只报 blueprint 一个 | ✅ 8 个全放行，EXIT=0 |

⇒ 判据抓的正是"缺 `/error`"这一个失效模式，不过度敏感。

### 3.2 ⚠️ 清掉一个**假门禁**：`check-controller-authorization-url-bypass.py`

按纪律对每个 `scripts/**/check-*.py` 查 hooks 引用数（`check.sh` + `ci.yml`），
发现它是**唯一的孤儿（hooks=0）** —— 2026-10-04 建成、跑起来是绿的，
但**从未接入任何流水线**，等于"看起来有门禁、实际谁也不拦"。

它的判据是**两层授权的叠加风险**：URL 层 `permitAll` 决定"要不要认证"，
方法层 `@PreAuthorize` 决定"这次调用准不准"。
漏写 `@PreAuthorize` 在普通路径上只是"任何登录用户可写"，
而在被 `permitAll` 覆盖的路径上是**"任何人可写"** —— 爆炸半径差一个量级。

已接入 `check.sh`（21/26）与 `ci.yml`（blocking）。**复审：零孤儿**。

> 值得记的分工：`check-gate-liveness` 查的是「CI 里 blocking 门禁条数 ≥ 基线」（只增不减），
> **反方向的孤儿它查不出来**，两者互补不能互相替代。

## 四、三个会伪装成"门禁通过"的机制（本轮全部踩到）

这三条单独列出来，因为它们的共同特征是**输出看着正常、实际已失败**。

### 4.1 Spotless 失败走 `exit 1` 而非 `exit_code=1`

后果：**后续 25 步照跑、每步都输出 ✅，但整体 `EXIT=1`**。
只看"每步都绿"会误判成门禁没问题。

**诊断判据**：门禁 `EXIT≠0` 但输出里**零个 `❌`** ⇒ 必有步骤是 `exit 1` 而非 `exit_code=1`，
去 `head -40` 找 `[ERROR]` 行。

### 4.2 熔断会「0.9 秒直接拒绝执行」

连续失败 3 次后写 `.git/hooks/.check-fail-count`（值 3），
再跑时**不执行任何步骤**、直接输出 `[MELTDOWN] 架构约束连续失败 3 次` 并 `EXIT=1`（耗时 987ms）。

修完真红后重跑前必须 `rm -f .git/hooks/.check-fail-count`，
否则会以为"脚本坏了/环境有问题"。这与「网关熔断同理」是同一类现象 ——
**先看是不是熔断/限流，再怀疑代码**。

### 4.3 步骤编号冲突不会被任何门禁抓到

在中间插入新门禁时我只改了分母（`/24]`→`/25]`→`/26]`）而没顺延后续分子，
造成日志里**两个 `[21/26]`**。门禁照跑、退出码正常，只有编号乱跳。

**正解**：插入后把其后所有步骤分子统一 +1，改完用
`grep -oE '^\s*echo -e "\$\{YELLOW\}\[[0-9]+/26\]' | sort -u` 核对 1..26 连续无重复。

## 五、`mvn <plugin>:<goal>` 裸调用的两类必踩坑

本轮两次都栽在这类问题上，值得单列。

| 坑 | 现象 | 修法 |
|---|---|---|
| **拿不到 execution 级配置** | `The parameters 'rules' ... are missing or invalid` | `goal@executionId`，如 `jacoco:check@check` |
| **多模块仓库里对所有模块执行** | 未接入门禁的模块因无数据而误报 | `-pl` 限定到真正配置的模块 |

两者**可叠加**（本次 jacoco 同时踩中，只修一层仍会挂）。

另一个同源问题：**"两处同一命令，一处带保护参数一处不带"是真实存在的** ——
`check.sh` 的 ArchUnit 调用早带保护参数，只有 `ci-check.sh` 漏了。
改这类参数必须两处一起查，且补的那处要写清 why（否则下个人会当冗余参数删掉）。

## 七、沉淀的可复用手法

### 7.1 门禁加步骤的标准流程

1. 写脚本 → **先跑负向探针**（改坏一个模块，判据必须精确命中且不误报其它）
2. 接入 `scripts/check.sh`（含编号：插入后其后分子统一 +1，核对 1..N 连续）
3. 接入 `.github/workflows/ci.yml`（标 blocking）
4. **孤儿审计**：对每个 `check-*.py` 查 hooks 引用数，`hooks=0` 即孤儿
5. 跑 `check-gate-liveness.py` 确认条数 ≥ 基线

### 7.2 定位"401 误报"这类安全语义错乱

开 `logging.level.org.springframework.security=TRACE` + **`logging.file.name=<文件>`**
（`mvn spring-boot:run | tail -N` 会缓冲住日志，TaskOutput 读不到），
看 `already authenticated`（认证成功）紧跟 `Securing GET /error`（业务异常转发）即可确诊。

### 7.3 门禁 `EXIT≠0` 但看不到 ❌ 时的排查顺序

1. `head -40` 找 `[ERROR]` 行（`exit 1` 型失败不会打 ❌）
2. 查 `rm -f .git/hooks/.check-fail-count`（熔断会 0.9 秒直接拒绝）
3. 检查裸 `mvn <plugin>:<goal>` 是否需要 `goal@executionId` 与 `-pl`
