## 二、判定为**合理**的设计（有证据支撑）

### R1. 网关补 `/api/v1/payments/**` 路由 —— 方向正确，但**不充分**（见 D1）

- 证据：修复前 `GET /api/v1/payments/1` 经网关 404，直连 8082 返回业务 404（`BP_PAYMENT_NOT_FOUND`）→ 确属网关未登记。
- 路径审计算法（解析 `PlatformApiPaths` 常量 + 双向检查「缺失路由 / 孤儿路由」）设计有价值，可沉淀为门禁。

### R2. `bone-integration` 补 `bone-web` 依赖 —— 正确，且副作用可控

我上一轮只做了口头评估，本轮补上证据：

| 自动配置 | 生效条件 | 在 integration 的实际情况 |
|---|---|---|
| `BoneWebExceptionAutoConfiguration` | 无特殊条件 | ✅ 生效（这正是要补的） |
| `IdempotencyAutoConfiguration` | `@ConditionalOnBean(IdempotencyStore.class)` | ❌ 不生效（integration 未提供该 Bean） |

→ **幂等切面不会因补依赖而被意外引入**，副作用为零。评估得到证实。

`@Order(HIGHEST_PRECEDENCE)` 加在 `IntegrationExceptionAdvice` 上也是对的：两个 `@RestControllerAdvice` 都处理 `BizException`，无 `@Order` 时 Spring 排序不确定，同一错误码可能这次 404、下次走框架分支。已实测模块特有映射（`INT_FLOW_NOT_FOUND` → 404）未受影响。

### R3. 库存 `tenantId` 由 `long` 改 `Long`、判定 `== null || < 0` —— 正确

- 证据：`Order.tenantId` 直接是平台租户 `0`，admin 即属此租户。`<= 0` 会让平台租户下单**永不占库存、可超卖**，是实打实的资损风险。
- 用包装类型 `Long` 显式判空，把 NPE 从「调用处拆箱」前移到「语义判空处」，异常点贴近成因，排查成本低。

### R4. Mock 库存网关补日志 —— 正确的可观测性改进

`reserve/confirm/release` 原为静默空方法，属该工程自己 javadoc 里警告的「看起来正常运行却什么都没做」。补 INFO 留痕后，**才可能实证**「平台租户下单真的触发了 `reserveStock`」——否则修复 2 只能靠推理，不能靠证据。

## 三、判定为**不合理 / 有隐患**的设计

### D1【严重】「支付链路打通」的结论在生产语义下**不成立**

**反例实验**：不带 `Authorization` 头打支付回调（模拟真实支付渠道 server-to-server 调用）

```
POST /api/v1/payments/callback   (无 token, 签名正确)
→ 401 {"errorCode":"GW_UNAUTHORIZED","message":"未授权：无效或缺失 token"}
```

**根因**：blueprint 内部 `SecurityConfig` 确实把 `/api/v1/payments/callback` 设为 `permitAll`，但**网关在转发之前就要求 JWT 并拒绝了**。我只补了「路由登记」，漏了「网关免鉴权白名单」这半步。

**为什么上一轮没发现**：全流程测试都带 admin token。真实渠道方不持有 Bone 的 JWT——**用超级管理员凭证测所有端点，等于把所有鉴权边界测成了假阳性**。这是测试设计的系统性盲区。

### D2【中】403 修复用了脆弱的字符串契约，且**零测试保护**

```java
if ("org.springframework.security.access.AccessDeniedException".equals(name) || ...)
```

- 出发点我认同：为避免 L3 依赖变更，用类名判定绕开 `bone-web` 对 security 的强依赖。
- 但这是 **fail-silent** 设计：Spring Security 一旦重命名 / 换授权栈，判定静默失效，异常回退到 500 兜底——**退回的正是本次要修的 bug**，且没有任何告警。
- 全仓搜索确认：**没有任何 `*Test.java` 覆盖 `isAccessDenied` / `accessDeniedExceptionHandler`**。
- 更标准的做法：新建 `BoneSecurityExceptionAutoConfiguration`，用 `@ConditionalOnClass(AccessDeniedException.class)` + 真实 `instanceof`——既保留零强依赖，又能被编译器与重构工具追踪。

### D3【中】「只有 integration 违反 HC-003」——结论过强，掩盖了语义层缺陷

全仓有 **7 个各自为政的异常处理器**（`bone-web` / iam / masterdata / system / metadata-server / extension-studio / integration）。我上一轮只验了「响应是否是 `ApiResponse` 信封」这一层，没验「状态码语义对不对」。补测后：

| 模块 | 输入错误类型 | 实测 | 判定 |
|---|---|---|---|
| iam | 路径变量类型错 | **500 `COMMON_INTERNAL_ERROR`** | ❌ 应为 400 |
| metadata | 路径变量类型错 | **500 `COMMON_INTERNAL_ERROR`** | ❌ 应为 400 |
| system | `GET /dict/types/abc` | 200 + `data:null` | ✅ **误判，实为正确**（`code` 声明为 `String`，"abc" 是合法输入） |
| integration | 缺分页 / 类型错 | 400 信封 | ✅ 已修复 |
| blueprint / masterdata / generator | 类型错 / 405 | 400 / 405 信封 | ✅ |

→ 客户端输入错误被记成 `COMMON_INTERNAL_ERROR`，**污染 5xx 错误预算**——这与我在 403 修复里自己论证的「鉴权失败不应混进错误预算」是同一类问题，我却没有一视同仁地检查。

> 顺带修正自己的一处误判：`system` 那行我一度怀疑是「无效输入返回成功」，查 Controller 后发现 `code` 是 `String` 类型，200+null 是正确行为。**该条不成立。**

### D4【弱】断言强度不足，存在绿灯幻觉

`scripts/e2e/chains.py` 共 **57 条断言**，其中 **23 条仅断言 HTTP 状态码**、无数据校验。状态码 200 只能证明「请求没被拒」，不能证明「业务结果正确」。D1 正是这类盲区造成的。

### D5【过程】提交归属与报告陈述不符

| 报告声称 | 实际 |
|---|---|
| `414d593ec` 含缺陷 1/2/3（网关路由 / 库存 / 403） | `414d593ec` **只含缺陷 2（库存 tenantId）** |
| — | 缺陷 1（网关 payments 路由）、缺陷 3（403）被**并发流水线** `aa2e77d0d` 连带提交收走 |

在并发流水线共存的仓库里，工作树改动被他人提交带走，导致「我的修复」的归属与内容对不上。报告按提交号陈述不可靠，应按**文件路径**陈述。

### D6【表述】「库存联动」实际未真正发生

Mock 库存网关补日志后，只能证明 `reserveStock` **被调用**，不能证明库存**被扣减**——它仍是 no-op 占位实现。报告第六节第 1 条有标注，但正文「库存联动修复」的措辞容易让人误读为库存已真实联动。

## 四、方法论层面的自评

| 问题 | 说明 |
|---|---|
| **凭证视角单一** | 全部用例用 admin token，鉴权边界全部测成假阳性。应至少双视角：超管 / 受限用户 / 无凭证外部方。 |
| **只验形式不验语义** | 契约合规 ≠ 语义正确（iam 500 就是例子）。断言应同时覆盖信封 + 状态码语义 + 关键字段。 |
| **结论先于证据** | 「只有 integration 违反」由单一样本得出，未做交叉验证即写进报告。 |
| **未证伪自身怀疑** | 若未回查 Controller 签名，`system` 会被误报为缺陷（本轮已排除）。 |

**一个意外收获（原报告未记录）**：下单时客户端传 `unitPrice=50`，服务端实际按主数据价格 `129 × 0.88 = 113.52` 计价——**服务端忽略客户端价格、以主数据为准**，这是正确的防篡改设计，值得写进契约文档。
