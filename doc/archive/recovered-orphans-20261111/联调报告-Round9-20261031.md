## 三、P1：长表单提交拦截提示不可见（真缺陷，已修）

### 3.1 实证推翻上一轮假设

写专项探针 `scripts/e2e/ui/purchase-order-submit-feedback-probe.mjs`（落盘截图/表单文本/网络三类证据），
实测采购订单新建弹窗：

- 表单内 **8 条 Alert**，其中 **4 条带【规则名】**（如 `SUB-ITEMS-01`：行项目金额合计 = 采购金额）；
- 网络面板 **无 POST**（确实被前端规则拦下，后端直连 POST → 201）；
- 但截图显示：提示渲染在 **15+ 字段长表单的底部**，提交按钮都不在同一屏。

⇒ 上一轮「静默失败」不准确。**真缺陷是：提示存在但用户看不见** ——
点完提交「什么都没发生」，GOV.UK error-summary / Nielsen 可见性反馈原则都明确反对这种模式。

### 3.2 处置（`BoneDynamicForm.tsx`）

- 置顶 **error summary**：「提交被拦截：共 N 项需修正」+ 逐条列表；warning 同样置顶但标注「确认后仍可提交」；
- 拦截时 `scrollIntoView` 到可视区——**先探测 API 能力再调用**（jsdom 无此 API，只降级不报错，避免单测炸）；
- 该块在 DOM 上**先于所有分区**，保证屏幕阅读器与视觉同时命中。

### 3.3 验证

- 新增 2 个用例：① 带条数的汇总文案；② 汇总节点在 DOM 上先于第一个分区；
  ③ 拦截 ⇒ 不发起提交；④ 规则通过不误伤。
- **变异验证**：删掉置顶块 → `Unable to find /提交被拦截：共 1 项需修正/`，测试转红。
- 探针重跑：出现「提交被拦截：共 4 项需修正」+ 规则列表。
