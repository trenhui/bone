# ClaimSphere 存量系统集成与快速部署（FDE）方案

**FDE = Fast Deployment Engine（快速部署引擎）**

> 定义：一套**标准化、可复制、轻量可落地**的交付方法论与工程产物——让 ClaimSphere 在 4-6 周内以低侵入方式接入客户存量理赔环境，先旁路验证、再人机协同、后自动化，全程可回退、可灰度、可审计。
>
> **文档关系**：本文档是 ClaimSphere 的"交付/集成层"方案，上游依赖《ClaimSphere 智能理赔平台设计方案》（确定性分层/防腐层/评测方法论）、《产品需求文档》（功能与验收）、《Synap 创业方案》（商业与节奏）。三者中已有的绞杀者迁移、ACL 防腐、评测方法论在本方案中落地化。

## 一、企业为什么买单（核心卖点，买方视角）

### 1.1 价值主张量化（对客户算得清账）

|**卖点**|**量化承诺**|**业界对标（2026年公开数据）**|**买方动因**|
|---|---|---|---|
|单案成本下降|15-25元 → ≤8元（↓≥50%）|IBM Claims Connection Group：人工处理时间↓30-50%、运营成本↓35%|直接降低核赔人力开支，ROI 可计算（见 PRD §17）|
|直付/快赔时效|3-7天 → ≤30秒（报销模式）；医院端直付为演进|招商信诺"诺e赔"：直付医院"签字确认直接离院"、AI快赔1分钟结案；腾讯微保商保直付试点|员工体验与留存、客户投诉量下降|
|欺诈拦截|赔付损失率 3-5% → ↓≥30%|Shift Technology（保险欺诈检测）|减少赔付漏损，直接改善综合成本率|
|决策 100% 可解释|证据链 + 条款引用 + 决策轨迹|Health Affairs：理赔AI需公平性/透明度/人工参与/拒赔责任|监管审计、客户申诉应对（拒赔必须有据）|
|新保司接入 ≤7天|配置化交付（2-4周 → ≤7天）|合合信息：标准化API快速接入现有理赔核心系统"无需大规模重构"|运营弹性，TPA 承接新保司的能力上限|
|私有化/信创|数据不出域，适配麒麟/鲲鹏/海光|暖哇×华为：鲲鹏/昇腾底座 + 私有化交付|金融数据安全监管刚需，PIPL 合规|

### 1.2 为什么是"现在"买单（时机论）

1. **政策窗口**：北京等地智能体新政明确支持保险机构布局智能体（2026-07）；195号文验证了 AI 落地采购的合规路径
2. **数电票/医保商保互通**：电子发票、医保商保试点（招商信诺等 15 家机构接入"医保+商保"清分结算）大幅降低材料核验成本——**数据连接红利正在兑现**
3. **同业已验证**：元保、合合、暖哇等已落地，客户不再需要"教育市场"，但多数是单点工具或绑定自有生态——**全链路 + 确定性工程 + 私有化仍缺位**
4. **买方痛点刚性**：小额案件挤占人力、复杂案件缺精力（合合一线调研结论），核赔员重复劳动是真实的日常

> **结论**：卖的不是"AI 概念"，是**可计算 ROI 的核赔人效提升 + 可过审计的确定性工程**。

## 二、技术壁垒（为什么对手难抄）

### 2.1 壁垒分层（由深到浅）

|**层**|**壁垒内容**|**为什么难抄**|**业界印证**|
|---|---|---|---|
|1. 数据飞轮|真实授权案件 + 人工复核结果回流，规则/模型越用越准|数据获取受合规约束（授权脱敏），竞争对手无法合法获得同类语料；**模型可买、数据难买**|合合/暖哇均以"理赔数据沉淀+数据飞轮"为护城河表述|
|2. 规则资产库|保单条款、免责、理算规则的数字化 + 版本治理|行业 Know-how 的工程化沉淀，需与业务专家共同建模，非通用 LLM 能替代；规则变更走正式审批（监管要求），资产具备审计价值|CSDN 集成实践：核保/理赔规则变更需正式流程审批，模型输出无法解释规则版本|
|3. 医学知识图谱|诊断-条款映射、合理用药审核、诊疗时间轴|跨医学+保险双领域知识，需持续维护 ICD/药品/耗材库|暖哇：保险医学知识库为垂直模型核心|
|4. 确定性工程|AI 只做证据、金额计算走确定性代码；可解释、可回退、可审计|纯 AI 方案天然不可控，需 AI+规则融合架构与工程纪律（评测/灰度/版本绑定）|IBM：Business Automation Workflow + 规则 + AI 组合；CSDN：结论不能由模型出（合规/准确/效率三因）|
|5. 私有化/信创交付|适配国产数据库/OS/CPU，数据不出域|需持续的工程投入与客户现场交付能力，大厂不愿做深度行业定制|暖哇×华为联合方案即为私有化交付形态|

### 2.2 一句话壁垒

> **全链路 Agent 架构可以 3 个月复刻，规则资产与授权数据需要 2-3 年积累。** 模型是商品，行业数据 + 业务规则 + 确定性工程是资产。

## 三、与存量理赔系统打通（集成架构）

### 3.1 集成对象与现状（As-Is 盘点）

客户环境常见存量系统（按对接优先级）：

|**系统**|**对接内容**|**对接难度**|**对接优先级**|
|---|---|---|---|
|TPA/保司理赔系统|案件、审核结论、材料影像|中（接口或文件）|P0（旁路审核的前提）|
|保司核心（承保/保单）|保单有效性、责任范围、免赔额|中|P0|
|OA/HR/企业微信|员工报案入口、通知触达|低|P0（获客入口）|
|财务/资金系统|支付指令、对账文件|中|P1（Phase C 需要）|
|医院HIS/医保|直付结算（演进方向）|高|P2（V3+）|
|电子票据平台|发票验真、开票|中|P1|

### 3.2 四层集成模式矩阵（业界最佳实践）

|**集成层**|**模式**|**技术**|**典型场景**|**侵入性**|
|---|---|---|---|---|
|数据层|CDC 实时同步 / ETL 批处理 / 文件交换|binlog 订阅、SFTP、对象存储|保单、历史案件导入|低（只读）|
|接口层|REST API / 事件 / Webhook|Higress 网关、RocketMQ|报案受理、审核结果回写|中|
|流程层|人工交接 / 工作台嵌入|iFrame + SSO + 待办集成|核赔员审核（不动原系统）|低|
|身份层|SSO / OIDC / LDAP|统一身份|登录打通|低|

### 3.3 集成关键原则（来自理赔自动化实战）

1. **默认只读旁路**：先不写存量系统，审核建议旁路输出，业务风险最低（对应 Phase A）
2. **幂等设计**：所有写回操作带幂等键（如 `idempotency_key = 报案号`），防止接口超时重试导致重复立案/重复支付——理赔自动化最容易出事故的细节
3. **先 mock 后真实**：集成对接先用 mock 数据跑通全链路，再逐步替换真实接口，报错时可隔离"模型输出问题"与"接口问题"
4. **审计三件套**：每个 AI/集成节点落三类日志——输入摘要（≤200字）、模型输出（完整）、平台动作结果（HTTP 状态码+耗时），用于事后复现与瓶颈定位
5. **防腐层（ACL）**：外部系统 DTO 不进核心域，适配器内做字段映射（设计方案 §5.3 已有）
6. **结果回写双通道**：有接口走 API 回写；无接口场景走文件/邮件人工导入兜底，保证 100% 场景可交付
7. **断点续传/可重跑**：数据同步任务支持断点续传与幂等重跑，不因单次失败阻塞后续

### 3.4 三个典型集成场景

**场景 1：员工报案入口集成（OA/HR/企微）**
```
员工在 OA/企微发起理赔 → Webhook 转发 ClaimSphere → 自动受理+材料预检
→ 缺件/异常推送提醒 → 完整案件进入审核流水线
```
- 交付物：企微/OA 适配器模板（配置化，无需定制开发）

**场景 2：存量理赔系统旁路审核（P0 核心场景）**
```
存量系统案件（CDC/文件）→ ClaimSphere 只读同步 → AI 审核建议（带证据链）
→ 建议回传存量系统工作台（嵌入/API/邮件）→ 核赔员参考处理
```
- 交付物：理赔系统适配器 + 工作台嵌入 SDK + 建议回写双通道

**场景 3：支付/对账对接（Phase C）**
```
ClaimSphere 决策通过 → 资金状态机（两段式）→ 调财务/资金系统 API 或输出对账文件
→ 回执确认 → 结案
```
- 交付物：资金适配器 + 对账文件模板 + 幂等重试

### 3.5 集成工作量控制

|**适配器**|**模板复用度**|**单客户定制工作量**|
|---|---|---|
|理赔系统|70% 复用|3-5 人日|
|保单/承保|70% 复用|3-5 人日|
|OA/企微报案|90% 复用|1-2 人日|
|资金/财务|60% 复用|3-5 人日|
|医院HIS（演进）|40% 复用|10-15 人日|

> 关键：**FDE 的工程化目标就是让"每个新客户接入"从项目制变成配置制**——单客户集成工作量压到 ≤15 人日，支撑"新保司接入 ≤7 天"承诺。

## 四、落地路径：三阶段渐进（轻量、可回退、可灰度）

|**阶段**|**模式**|**行为**|**对客户影响**|**回退代价**|
|---|---|---|---|---|
|**Phase A（4-6周）**|Shadow 旁路|只读存量数据，AI 审核建议与人工结论对照，产出评测报告|零侵入，业务无感|零成本（关掉同步即可）|
|**Phase B（4-8周）**|Assisted 辅助|核赔员工作台嵌入：AI 建议 + 证据链 + 置信度，人工终审（不出款）|核赔员提效，流程不变|低（关闭建议开关）|
|**Phase C（≥8周）**|Automated 自动化|低风险案件自动通过 + 自动支付；高风险/大额人工；后督抽检|流程变革，人力重分配|按案件比例灰度回退|

**阶段切换门槛**（与评测方法论一致）：Phase A 评测达标——字段提取准确率≥95%、规则匹配准确率≥90%、人工复核率≤30%、重大错误率 0——才进入 Phase B/C。

**灰度纪律**（理赔自动化实战最佳实践）：
- 灰度三步走：内部测试全自动 + 人工双录对照 → 单分支 5% 新案分流 → 看三指标（自动化完成率/人工介入率/结案时效）决定放量
- **变量隔离**：灰度期间不同时改模型版本和工作流版本；模型、提示词、工作流三版本绑定记录，回滚可对齐
- 转人工案件单独复盘：七成介入是字段校验问题（改 Schema/提示词），少数是接口问题（改集成层），别盲目动模型

**部署形态**：
- 试点期：单机/轻量形态（Docker Compose 或 4 节点小集群），降低首单部署门槛
- 生产期：K8s 集群（设计方案 §9.3）；信创环境（麒麟 OS + 鲲鹏/海光 CPU）适配
- AI 推理：敏感数据（病历/身份）本地 vLLM，非敏感数据（条款检索）云端 API，按客户合规要求切换

## 五、FDE 工程产物（快速部署引擎交付物）

|**产物**|**内容**|**价值**|
|---|---|---|
|1. 集成适配器模板库|保司/TPA/理赔/资金/HIS/医保 5-6 类适配器，配置化（YAML 定义字段映射、同步策略）|单客户集成从项目制变配置制，≤15 人日/客户|
|2. 规则迁移工具|客户规则（Excel/DRL/制度文档）→ 结构化导入 + 冲突检测 + 沙箱验证|规则资产数字化，替代人工梳理|
|3. 数据沙箱 + 评测包|授权脱敏样本、有正确答案的测试集、评测报告自动生成（字段/规则/复核率/时长/错误率）|证明"减少重复劳动"的可量化证据，支撑销售与准入|
|4. 部署包|Helm Charts / Docker Compose 双形态；信创环境适配脚本|轻量可落地，降低首单门槛|
|5. 工作台嵌入 SDK|iFrame + SSO + 待办集成 + 建议回写组件|核赔员无感接入，不动原系统 UI|
|6. 三态开关|Shadow / Assisted / Automated 一键切换（功能开关 + 案件比例灰度）|客户可按信任度渐进，全程可回退|
|7. 运维手册|监控告警、审计导出、数据保留与删除策略、切换演练|合规交付，应对监管检查|

**模块化组合交付**（业界实践：合合/暖哇均支持分步上线）：客户可按业务优先级分阶段上线——材料识别 → 核责建议 → 风控筛查 → 自动支付，适配不同数字化投入节奏。

## 六、节奏与验收（总周期示意）

```
Gate 0（2周）：场景定义 + 客户/数据验证（未通过则暂停）
    ↓
MVP 开发（6-10周）：解析 + 规则知识库 + 核责引擎 + 工作台 + 评测集
    ↓
Phase A 旁路验证（4周）：零侵入，评测达标（字段≥95%、规则匹配≥90%、复核率≤30%、零重大错误）
    ↓
Phase B 辅助上线（4-8周）：核赔员提效，关闭建议即可回退
    ↓
Phase C 自动化（≥8周）：低风险自动 + 灰度放量 + 后督抽检
```

**每个阶段都以"客户可验证的业务指标"为验收，不以"技术跑通"为验收。**

## 七、集成落地风险与对策

|**风险**|**对策**|
|---|---|
|存量系统接口不开放/不稳定|文件交换兜底；只读优先（不改写存量）；断点续传 + 幂等重试|
|存量数据质量差（缺字段、口径不一）|数据沙箱先行验证；字段映射白名单；坏数据标记转人工，不阻塞流程|
|业务方不信任 AI 结论|Shadow 阶段用评测报告建立信任；Assisted 阶段"人工终审权"保留；拒赔责任归属明确（AI 建议、人工/保司终审）|
|合规（数据出境、日志保留）|敏感数据本地 vLLM；DPA 约定数据不用于训练；资金/决策日志≥7年（PRD §13.3）|
|部署环境信创/资源受限|轻量部署形态 + 信创适配；AI 推理按需降级（云端/本地切换）|

## 八、与现有文档的关系与闭环

```plaintext
Synap 创业方案（为什么做、卖给谁、节奏）
        ↓
ClaimSphere 设计方案（确定性分层、防腐层、评测方法论）
        ↓
ClaimSphere PRD（功能、验收、KPI）
        ↓
本方案 FDE（如何接入存量、如何部署、如何证明价值）—— 交付闭环
```

**FDE 的核心主张**：理赔 AI 的落地难点不在模型，而在"把模型的理解翻译成系统动作"（字段、状态、接口调用）+ "让客户看得见的业务价值"。FDE 把这层翻译与证明做成工程化产物，让每个新客户接入从"定制项目"变成"配置化交付"。
