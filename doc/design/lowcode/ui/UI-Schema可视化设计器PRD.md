## 1. 背景与目标

### 1.1 问题陈述

`bone-ui-schema.schema.json`（v1.1）与运行时引擎（`uiSchemaEngine.ts` + `useBoneUiSchema`）已落地，单文件 DEMO v1.7 已验证全套交互（三栏 IDE：结构树 + 多态属性面板 + 活预览；变体自动裁决；规则追踪 + 联动演练；inspect 点选定位；试运行；语义自检 + 机器协议校验）。但生产侧仍缺一个**产品化设计器**：今天配一个报销单界面要手写数百行 JSON，字段拼写漂移、规则悬空引用、`$` 变量写错全部在运行时才暴露，实施顾问无法向客户演示"改配置即生效"。

不做的代价：ui-schema 协议停留在"开发者手写契约"阶段，父 PRD 的 B 路径叙事（实施自助建模上线）无载体，A 路径（少写 CRUD）每次仍要手写整份 JSON。

### 1.2 变更动机（为什么是现在）

1. **协议已冻结可用**：schema.json v1.1 + 引擎同口径（9 聚合函数、`submit.when`、容差 epsilon、条件深度≤3 fail-closed），设计器有稳定靶子可对齐。
2. **交互已低成本验证**：DEMO v1.7 覆盖三场景（报销/智能理赔/采购），交互模式（Preview-as、规则追踪 + 联动演练、试运行、Cmd+K）对标 Retool/Appsmith/Salesforce/VSCode 最佳实践，无需再做可用性探索。
3. **宿主已就绪**：父 PRD UID-9 四 Tab（结构｜界面｜数据｜发布）要求「界面 Tab=Must」，设计器正是该 Tab 的实现载体。

### 1.3 目标与成功标准

| 目标 | 可验证指标 | 优先级 |
|------|------------|--------|
| A 路径开发者配界面不再手写 JSON | 单场景（报销）建模→预览可用页耗时 ≤ 15 分钟（父 PRD §0.3 口径；基线"手写约 2 人时"为预估待验证） | P0 |
| 所见即所得零漂移 | 设计器预览与运行时渲染一致率 100%（共享 fixture 契约测试，§7） | P0 |
| 错误左移 | 自检 err 阻断发布；灰度期规则悬空引用/拼写漂移故障数降为 0 | P0 |
| B 路径可演示 | 实施顾问可独立完成三场景样板演示（配角叙事，不单独设 SUS 门禁——沿用父 PRD §0.1 决策） | P1 |

### 1.4 与平台能力的关系

| 关联 | 说明 |
|------|------|
| 父 PRD | 本 PRD = 父 PRD UID-9「界面 Tab」+ VM-002（publish-preview）的设计器实现；Must/Should 切分以父 PRD §0.2 为准，冲突时以父 PRD 为准 |
| 架构约束 | 分层/边界/门禁见 `doc/architecture/Bone-DDD-最终实践方案.md`（HC-001～HC-008 引用编号，不复述）；前端规范见 `doc/architecture/bone-前端架构.md` §6 |
| 协议真源 | `ui-protocol/bone-ui-schema.schema.json`（v1.1）；DEMO 为交互原型，**不直接上线**（单文件技术债，产品化时重写为工作区模块） |
| AI 中台 | AI 辅助起草规则/样板见《BONE-AI能力中台最佳方案》，列为 v2.0 候选（§11.2），本迭代不做 |

### 1.5 核心竞争力

与宜搭/JeecgBoot 在线表单、Retool/Appsmith 相比，差异化只有一条：**协议即真源 + 双端同构**——设计器预览与生产运行时跑同一套语义（同一 fixture 两端互跑，§7.2），配出来是什么，线上跑的就是什么；变体按身份自动裁决（Preview-as）与规则命中可追踪，是后两者均无的调试能力。

## 2. 用户与场景

### 2.1 用户角色

| 用户类型 | 特征描述 | 核心诉求 |
|---------|---------|---------|
| 应用开发者（主要，A 路径） | 懂领域建模，会手写简单 JSON，不想写页面源码 | 配界面不写 Table/Form；改完即预览，发布即生效 |
| 实施顾问（次要，B 叙事） | 面向客户演示与交付，不写代码 | 点一点就能改出客户要的报销/理赔/采购界面；演示不翻车 |
| 业务管理员（次要） | 只改显示名、码表 label、提示文案 | 不碰结构也能安全改文案，改不坏 |

### 2.2 典型使用场景

| 场景 | 用户操作 | 系统行为 | 结果 |
|------|---------|---------|------|
| 报销单加"税号"联动 | 发票类型选专票→税号必填 | 命中追踪条亮起 LINK-1，自检无 err，试运行通过 | 发布后专票报销必填税号 |
| 理赔切核赔视角 | 身份模拟切 reviewer | 变体自动裁决为核赔工作台（badge ⚡） | 所见即核赔员所见 |
| 采购高风险处置 | 风险等级选 HIGH→理由必填；点"采纳" | HITL 参数摊开展示，提交规则校验理由完整性 | 结论可追溯、可审计 |

### 2.3 用户故事

1. 作为应用开发者，我想要从实体一键生成表单/列表/详情三视图骨架，以便不从空白 JSON 起手。
2. 作为应用开发者，我想要点选控件库添加字段、用上移下移排序，以便不用记忆 controlKind 拼写。
3. 作为应用开发者，我想要属性面板只暴露协议 props 白名单，以便配不出非法 schema。
4. 作为应用开发者，我想要码表只做显示名覆写/隐藏选项，以便不违反"UI 层不新造 value"红线。
5. 作为应用开发者，我想要用 when 编辑器（atom/all/any/not）配联动规则，以便三层嵌套内所见即所得。
6. 作为应用开发者，我想要从规则模板（专票/大额/双人复核/快赔四条件）起草，以便常用模式一次成型。
7. 作为应用开发者，我想要提交规则支持 submit.when 与容差参数，以便"驳回时才校验"这类场景可配。
8. 作为应用开发者，我想要动作条可配 HITL（reasonTypes/maxRounds/二次确认），以便审批动作语义完整。
9. 作为应用开发者，我想要按角色/档位/渠道/设备配变体并一键 Preview-as，以便验证"不同人看不同界面"。
10. 作为实施顾问，我想要试运行只跑校验不执行业务动作，以便演示提交拦截不污染数据。
11. 作为实施顾问，我想要规则命中追踪条点 chip 直达规则定义，以便客户追问时当场定位。
12. 作为实施顾问，我想要开 inspect 点预览字段直达配置行，以便边讲边改。
13. 作为业务管理员，我想要只改文案（label/notice/message）且自检通过即发布，以便小改不动结构。
14. 作为业务管理员，我想要 JSON 非法时草稿不丢失，以便误粘贴可恢复。
15. 作为平台维护者，我想要手写 JSON 与设计器产出双向无损互转，以便老用户不强制迁移。

### 2.4 关键场景详述（User Journey）

**场景：报销单新增"专票→税号必填"联动并发布**
- 触发条件：打开费用报销实体的界面 Tab，当前为已发布基线。
- 用户操作步骤：① 从模板新建联动规则"专票→税号必填"；② 预览切发票类型=专票，确认税号显现+追踪条命中；③ 点试运行，确认无 ERROR；④ 点发布。
- 系统响应：自检 err=0 才放行发布按钮；发布写入 catalog 草稿→发布流程（复用 VM-002）；预览 mock 水印常驻。
- 结束状态：线上专票报销必填税号；规则变更可追溯到本次发布。

## 4. 功能需求（MoSCoW）

| ID | 需求描述 | 优先级 | 验收标准（Given/When/Then 或检查项） |
|----|----------|--------|--------------------------------------|
| FR-01 | 实体绑定：选实体一键生成三视图骨架 | Must | Given 任意 RUNTIME 实体，When 点生成，Then 表单/列表/详情骨架可预览且自检 err=0 |
| FR-02 | 结构配置：分区 + 控件库点选添加 + 排序/复制/删除 + 属性面板（props 白名单） | Must | 非白名单 props 配不出来；200 字段 schema 内操作响应 ≤ 200ms（预估待验证） |
| FR-03 | 字典覆写：仅 labelOverride/hidden，新造 value 被自检判 err | Must | Given 覆写不存在的 value，When 自检，Then err"UI 层不得新造 value"且发布被阻断 |
| FR-04 | 联动规则：when 编辑器（atom/all/any/not，深度≤3）+ then + 5 类模板 + **联动演练**（一键按 when 反推填值、复位恢复） | Must | 超 3 层嵌套 fail-closed 不命中且 console/editor 双提示；模板起草字段可改；演练值有备份，复位不丢用户原值（DEMO v1.7 已验证交互） |
| FR-05 | 提交规则：9 聚合函数 + submit.when + tolerance/minReasons + messageKey | Must | 明细合计 0.01 容差内外两种用例试运行结论正确 |
| FR-06 | 动作条：actionCode/visibleWhen/confirm/HITL（reasonTypes/maxRounds） | Must | HITL 点击摊开展示参数并标注"未真实执行"；visibleWhen 隐藏的按钮 disabled 且有 title 解释 |
| FR-07 | 变体：key/priority/match 编辑 + Preview-as 五维身份 + 自动/强制 badge + base↔变体 Diff 评审视图 | Must | 角色改 approver 时报销自动切审批工作台；无 match 变体报 info 防遮挡 base；Diff 以分区/控件两级标出新增/删除/变更（DEMO v1.5 已验证交互） |
| FR-08 | 预览：三视图 + 设备三档 + 试运行（不执行业务）+ 命中追踪 + inspect 定位 + 页头密度（分区/控件数、列表行数）+ 移动端 390px 栅格坍缩单列 | Must | 追踪 chip 点击直达规则并闪光；试运行不产生任何写操作（无后端调用）；手机档双列栅格自动变单列、表格横向滚动不断版 |
| FR-09 | 自检：重复字段/props 白名单/悬空引用/`$` 拼写/变体一致性/字典覆写 + **机器协议校验**（实例 vs schema.json：类型/枚举/必填/`additionalProperties`，`x_` 豁免） | Must | `$Me` 拼写判 err；自检 err>0 时发布按钮禁用；发布阻断条件 = 机器 FAIL 或语义 err（DEMO v1.7 已验证交互） |
| FR-10 | JSON 双向同步 + 导入导出 + 撤销重做 + 草稿/发布 | Must | 非法 JSON 不丢草稿（隔离展示错误）；撤销栈 ≥ 50 步；发布复用 catalog 流程 |
| FR-11 | 三场景样板库（报销/智能理赔/采购）一键载入 | Must | 每个样板自检 err=0；样板标注 mock 数据来源 |
| FR-12 | 分区内拖拽排序（DEMO 已验证） | Should（v1.1 首批转正） | 与上移下移同效；拖拽过程不触发输入框失焦 |
| FR-13 | 自由画布 VM-001 / `ui_config` 表 / 版本回滚 RC-006 / 环境导出导入 | Should（v1.1） | 需 L3 审批（DDL/依赖/删码），见 §9 |

## 4.1 向后兼容性（迭代 PRD 必备）

- **老数据**：既有手写 JSON 全部可导入；`x_` 演示扩展字段报 warn 不阻断；`schemaVersion` minor 向前兼容，major 升级须配迁移说明（[TBD: 当前线上最大 minor 版本，后端 owner 补充]）。
- **老用户**：JSON 作者可继续手写，设计器只做增量载体，不强制迁移，不改变现有发布路径。
- **API 兼容**：本迭代不新增后端接口（只读码表沿用 SDK 现有能力）；v1.1 `ui_config` 表另行评审。

### 6.2 成功指标

**北极星指标**：A 路径单场景建模→可用页耗时（基线手写约 2 人时·预估待验证 → 目标 ≤ 15 分钟）。

**过程指标**：
- 预览/运行时一致率：100%（共享 fixture 双端互跑，0 失败）。
- 灰度期自检 err 阻断率：100% 阻断（0 带病发布）。
- 试运行使用率：发布前试运行覆盖率 ≥ 80%（预估待验证）。

**反向指标（Guardrail）**：运行时渲染故障率不上升；误发布（发布后 24h 内回滚）率 ≤ 1%（预估待验证）。

**回滚条件**：任一 Guardrail 跌破即暂停灰度，回退设计器入口 Feature Flag，已发布 schema 不受影响（设计器只写草稿）。

## 7. 测试策略

### 7.1 测试原则

- 测外部行为与协议契约，不测内部实现。
- 优先复用现有接缝：生产引擎 `uiSchemaEngine.ts` 的测试 fixture 即设计器引擎的测试输入。
- 双端一致性即最高优先级测试：同一 fixture，两端（设计器纯函数 ↔ 生产引擎）互跑，断言逐条一致。

### 7.2 测试范围

| 模块/功能 | 测试类型 | 覆盖要点 | 参考 |
|----------|---------|---------|------|
| 条件/联动/提交/变体裁决纯函数 | 单元（L1） | eq/in/between、all/any/not、深度>3 fail-closed、`$me/$myteam/$all`、priority+match、容差 epsilon | 生产引擎现有单测 + DEMO 已验证用例转正 |
| 双端一致性 | 契约（L2） | 三场景样板 fixture 双端互跑 0 差异 | 新增，放入 `./scripts/check.sh` |
| 自检规则 | 单元（L1） | 每条 lint 一正一反用例（含 `$Me` 拼写、变体 key 重复） | DEMO lint 用例转正 |
| 三场景走通 | E2E | 报销联动→试运行→发布；理赔变体切换；采购 HITL | 沿用 bone-frontend 现有 E2E 框架 [TBD: 确认框架选型，前端 owner 补充] |
| 非法 JSON/超深条件/未知操作符 | 异常 | 不崩溃、不丢草稿、可恢复 | §4 异常处理原则 |

### 7.3 测试验收标准

- 核心用户故事（§2.3 P0 项）有 E2E/集成覆盖；异常流程有异常测试；双端一致性测试脱离外部依赖可独立运行。
