# 费用报销系统 · 元数据建模方案（基于 BONE 低代码平台）

> **文档定位**：业务示范样例 + 平台缺口探针。  
> **参考基线**：[`BONE-低代码最小闭环PRD.md`](../BONE-低代码最小闭环PRD.md)（**v0.50** · §2.5.9 L1）、[`BONE-低代码Runtime数据面设计.md`](../BONE-低代码Runtime数据面设计.md)（**v0.49** · §0.1 矩阵）、[`../ui/元数据工作区前端融合方案.md`](../ui/元数据工作区前端融合方案.md)、[`../ui/README.md`](../ui/README.md)、原型 `#scene=expense`、`FIELD_TYPES` 真源。  
> **v0.50 落地注记（2026-10-11 · 行级 ACL 旁路封堵）**：① **子表端点旁路封堵**：`listChildren`/`replaceChildren` 前置主行行级 ACL 断言——非本人/非审批人/非管理员枚举或替换他人单据明细 → 404（报销明细不再可被「知道主行 id」的第三方枚举）；② **REFERENCE 候选旁路封堵**：`lookup-options` 候选行级过滤——引用字段指向 `t_expense_category`（无 created_by 主数据）豁免全量；指向他人私有单据时仅返回操作者可见候选（防候选列表泄露全部行）（Runtime §4.7.1 + §9.7）。
> **v0.49 落地注记（2026-10-11 · 行策略 approver 维度）**：① **报销「本人 + 审批人可见」已完整闭环**（RLS「策略即 WHERE」落地，Runtime §4.7.1）：`meta_entity.row_policies` 声明 `owner_or_approver`（`created_by = :operator OR approver_id = :operator`），本人 + 单据指定审批人可见，其余 404；② `t_expense_claim.approver_id` 列 + **meta_field 声明**（0038）——单据创建/提交时指定审批人（前端动态渲染「审批人」字段，写路径放行）；③ 解析安全：when 仅支持「列 = :operator」+ AND/OR、列白名单 = 物理列集合、`:operator` 参数化、未知列保守回退；④ `:role` 角色组策略 / 列级 FLS 仍 v1.1（诚实标注）。
> **v0.47 落地注记（2026-10-11 · 业界对标落地）**：① **打款入参契约化**：`confirmPayout` 的 `params_schema` 由 `RuntimeActionService.validateParams` 统一校验（type/min/max/pattern/enum，越界 → 422 `META_RUNTIME_ACTION_INVALID_PARAMS`），Handler 不再各自校验（Runtime §4.8.2）；② **报销写前置钩子 `ExpenseClaimWriteHook`**：SUBMITTED（含）之后禁止改 `amount`（防绕过审批改单后打款），`RuntimeWriteHook` SPI 挂载，422 `META_RUNTIME_VALIDATION_FAILED`（Runtime §4.8.3）；③ 行级 ACL v1.1 设计（RLS 语义）将报销「本人 + 审批人可见」作为首个策略样例（Runtime §4.7.1）。
> **v0.46 落地注记（2026-10-11 · L1 落地）**：**L1 由「缺口探针」变为已实现（0037 迁移 + 引擎 + 前端三控件）**——① `t_expense_claim_item` 明细子表（CHILD_TABLE，claim_id FK + sort_order + amount 服务端强制 min:0.01）；② `t_expense_category` 类别主数据（REFERENCE，初始 5 类）；③ 主实体补建 `category_id`（ENUM `category` 演迁为 REFERENCE，labelField=name）+ `attachment`（ATTACHMENT JSON 清单）+ `items`（CHILD_TABLE 声明）；④ meta_entity_relation 双轨登记 + 子实体权限细码；⑤ 前端 `RuntimeDataManagement.tsx` 明细弹窗/REFERENCE 下拉/附件清单。
> **v0.45 落地注记（2026-10-11 · 生产就绪补漏）**：① 打款逃逸由「拟议」变为**已实现**——`ExpenseClaimConfirmPayoutHandler`（原 `PaymentApplicationService` 改名，0036 迁移），禁止项已遵行；② `amount` 的 `validation_rules={"min":0.01}` 由「死数据」变为**服务端强制**（RC-007 轻量子集接线，`JdbcRuntimeRecordService.validateRules`）；③ 金额精度诚实化口径不变（存储 DECIMAL(20,6)，界面按 scale=2 渲染，见 PRD G20）。  
> **业界对标**：简道云/宜搭「报销首秀」；Concur 四阶段作**能力探针**（非本迭代 Must）。

## 1. L0 · 黄金路径（= PRD §2.5.9）

### 1.1 定位
员工填单 → ENUM 审批 → 打款逃逸；**自动生成界面**；不新建微应用。

### 1.2 能力（对照 `FIELD_TYPES`）

真源含 `ENUM`，**无 REFERENCE / FILE**。

| 能力 | L0 | 说明 |
|---|---|---|
| CRUD + DECIMAL + 双 ENUM | ✅ | Meta* / Tag |
| **REFERENCE 类别主数据** | ✅ **v0.46 已实现** | lookup-options + label；`t_expense_category`（0037 初始 5 类） |
| **CHILD_TABLE 明细行** | ✅ **v0.46 已实现** | `expense_claim_item` 明细弹窗；整组替换事务（listChildren/replaceChildren） |
| **ATTACHMENT 附件** | ✅ **v0.46 已实现** | JSON 清单（name/url/size），前端清单式渲染 |
| 提交/审批按钮 | ⚠️ v1.1 UIF-008 | MVP 手工改枚举 |
| 确认打款 | ✅ `ExpenseClaimConfirmPayoutHandler`（v0.45 落地） | 禁止只改 PAID |
| 明细 / 类别实体 / FILE | ✅ L1 已实现（v0.46） | §3 |

### 1.3 字段（初建 8 + L1 三列 · `cost_center` 仅 1→n）

同 PRD §2.5.9 字段表：`claim_no` / `title` / `amount` / **`category_id`（v0.46：ENUM `category` → REFERENCE）** / `expense_date` / `status` / `applicant` / `remark` + **L1：`attachment`（ATTACHMENT）/ `items`（CHILD_TABLE 声明）**；热加载演示 `cost_center`。

状态：`DRAFT → SUBMITTED → APPROVED | REJECTED → PAID`（PAID 仅经逃逸）。

### 1.4 落地切片（可开工 · 对齐融合方案）

| 切片 | 做什么 | Must？ |
|------|--------|--------|
| W0～W0b | 共用壳：默认 RUNTIME、`/data` 绑 id、四 Tab、发布常驻 | ✅ |
| W1a T1–T3 | ENUM DDL + 透传 + 控件 | ✅（场景串联前置） |
| W1a T4 | 种子 `expense_claim` | ✅ |
| W2 | Meta* + `projectColumns` → Runtime `fields=` | ✅ |
| 数据读 | `GET …/runtime/entities/t_expense_claim/records?fields=&sort=&q=` | ✅ 既有 API |
| 逃逸 | ✅ `ExpenseClaimConfirmPayoutHandler`（v0.45 落地） | ❌ 另任务（见下） |
| L1 | 头明细/FILE | ❌ |

**读 vs 打款**：列表/详情/改 ENUM → Runtime CRUD（[设计文](../BONE-低代码Runtime数据面设计.md) §2）；真打款 → 同一动态通道 `…/actions/confirmPayout` + 手写 Handler（§4），**禁止** `PUT status=PAID` 冒充，也**禁止**写死 `/expense-claims`。

### 1.5 15 分钟路径
模板起盘 → `?tab=ui` → 发布 → 录 `128.50` → 加 `cost_center`。原型 `#scene=expense`。串联序：**巡检 → 报销 → 补货 → 访客**。

> **实施状态（已真实落地，非仅原型 / 非仅文档）**：模板经 `scripts/migration/0031_scenario_template_expense.sql`（id `9150`）落库，已与巡检/补货/访客**并列**出现在模板目录；经 `POST /templates/9150/instantiate`（deliveryMode=1 RUNTIME）实例化出实体 `expense_claim` 并**已发布**（status=1），运行时已写入 1 条演示记录 `EXP-DEMO-001`（金额 128.50 / `TRAVEL` / `APPROVED`）。L0 黄金路径在平台真实可演示。

### 1.6 字段码表（0031 实际 seed · 可对照验证）

`category`（ENUM）：`TRAVEL` 差旅 / `MEAL` 餐饮 / `TRANSPORT` 交通 / `OFFICE` 办公 / `OTHER` 其他（必填）。  
`status`（ENUM，5 态轻状态机）：`DRAFT` 草稿（默认）→ `SUBMITTED` 已提交 → `APPROVED` 已审批 | `REJECTED` 已驳回 → `PAID` 已打款。  
`amount` DECIMAL，`validation_rules={"min":0.01}`；`claim_no` 唯一；`cost_center` 仅 1→n 热加载演示字段。完整 9 字段见 PRD §2.5.9 与 0031。

### 1.7 审批路由（MVP 手工 → v1.1 引擎）

| 金额档 | MVP（手工改 `status`） | v1.1（VF-001 + UIF-008） |
|---|---|---|
| ≤ ¥1000 | 直属主管在「数据 Tab」改 `APPROVED`/`REJECTED` | 引擎按路由自动派单给直属主管 |
| ¥1000 < x ≤ ¥5000 | 部门负责人改 | 自动派单部门负责人 |
| > ¥5000 | 财务负责人改 | 财务负责人 + 总监会签（或签） |

> 多级会签/或签、条件分支属 **VF-001（Out of Scope）**；MVP 不承诺自动派单，仅渲染状态枚举 +（v1.1）动作按钮。

### 1.8 打款逃逸契约（拟议 · 不进 Mode B Must）

- **服务 / Handler（v0.45 已实现）**：`ExpenseClaimConfirmPayoutHandler`（bean 同名，`RuntimeActionDispatcher` 装配），**禁止**复用 blueprint 订单域 `PaymentApplicationService`（支付单生命周期 ≠ 报销打款，见 §0.1；同名类已改名）。
- **入参契约（v0.47 已接线）**：`params_schema`（0032 种子真源）声明 `channel`（enum: [PAYROLL, BANK_TRANSFER]，required）+ `note`（string，可选）——`RuntimeActionService.validateParams` 统一校验（类型/枚举/范围 → 422 `META_RUNTIME_ACTION_INVALID_PARAMS`），Handler 内重复校验已清除（Runtime §4.8.2）。
- **公开 HTTP（动态 · 与 Runtime / UIF-008 对齐）**：
  `POST /api/v1/runtime/entities/t_expense_claim/records/{id}/actions/confirmPayout`
  ——`entityCode` + `actionCode` 皆动态；**不要**再开 `/api/v1/expense-claims/{id}/…` 作为 MetaList 默认入口。
- **挂载**：MVP 可用 UIF-004 拼上述 URL；v1.1 UIF-008 按 catalog 动作声明自动出按钮。
- **同事务保证**：`status → PAID` + 付款凭证 +（可选）支付通道；**禁止**「只把 `status` 改成 `PAID`」冒充打款。
- **对称**：补货 `POST …/entities/t_replenishment/records/{id}/actions/receive`——同一通道形状，只换 code + Handler。详见 [Runtime 数据面设计](../BONE-低代码Runtime数据面设计.md) §4。

## 3. L1 · 真实形态（v0.46 已实现）

> 原「缺口探针（不进 Must）」→ **已落地**。实现 = 引擎（REFERENCE/CHILD_TABLE/ATTACHMENT 三类型，`RuntimeRelationSupport` + `RuntimeWriteValidator`）+ **0037 迁移**（明细子表 + 类别主数据 + 主实体补建）+ 前端三控件（`RuntimeDataManagement.tsx`）。

**目标模型（已实例化）**：`t_expense_claim` 1—N `expense_claim_item`（CHILD_TABLE，claim_id FK + sort_order + amount min:0.01 服务端强制）；`expense_category` 类别主数据（REFERENCE，labelField=name，初始 5 类）；主实体 `category_id`（原 ENUM `category` 演迁） + `attachment`（ATTACHMENT JSON 清单）+ `items`（CHILD_TABLE 声明字段，无物理列）。

**演迁路径**：L0 跑通 → v0.46 拆明细（0037）→ ENUM 类目迁主数据（REFERENCE）；meta_entity_relation 双轨登记与运行时 `validation_rules` 同构（0037 段 5）。

## 5. MVP 只承诺 L0（L1 已随 v0.46 落地）
