## 总评

三份文档的「自我诊断」已经相当诚实（§0.3 缺口表、G10–G20），但**文档说要做的事与代码实际状态存在双向漂移**，且 verifier 复核发现一个文档完全没写的高危洞（动作权限门禁半接线）。按当前状态直接进生产，资金类场景（confirmPayout）存在重复出金与越权触发两个真实风险。

## P1 · 生产化强项（上线后 30 天内完成）

1. **「手工改枚举」路径已死但 case 文档仍在教**：case §1.2/§1.7 与 RC-008（state_field 直写 422）直接冲突，0032 种子四动作（submit/approve/reject/confirmPayout）已是替代路径——case 未认，按文档演示会当场 422。case 基线还停在 PRD v0.40（PRD 实际 v0.42→v0.44 Draft）。
2. **版本叙述三处分裂**：PRD header v0.42 但修订表有 v0.44 行；Runtime 头写「OpenAPI v1.2.1 待同步」而 spec 已是 1.2.2；两文 Must 能力清单语义一致（R9–R15 ↔ Must-1）但 RC 编号只有 PRD 用。
3. **运行时能力缺口如实但不显眼**：关联/子表/多条件过滤/复合唯一/深分页游标全不存在（§0.3）——报销 L1（头+明细）在 REFERENCE 就绪前无法做，诚实性达标但「生产可用」的产品定位要按单实体能力重新表述。
4. **审计已接但窄于实现**：`RuntimeAuditSink`（非 PRD Must-1 所写 DefaultAuditService）已覆盖 create/update/updateState/adminFix；日志与监控指标有设计（§7）但无 Runbook/on-call 路径、无 Dashboard 工件。
5. **escape SPI 部署模型**：同进程 starter 装配已消歧（v0.43 §4.8），Handler 归属业务模块——机制就绪，缺的是真实出金 Handler 与下游幂等透传。

## P2 · 规划与治理（不阻塞上线，须入 v1.1 backlog）

- `filter` JSON 按 §2.6 提前到 v1.0.5 是对的方向（否决则 10 列阈值卡死）。
- Schema 演进（§2.8）、变更事件 Outbox（§7.2）、四码拆分、FLS——按既定排期执行。
- 密钥/凭据管理空白（三文 0 命中）：escape 真实出金前必须有 secret 治理方案。
- 合规/保留策略（D9 + §3.4#17）：回收站数据、audit 表无限期增长无清理策略。

## 为什么这些是「生产级」判据而非「演示级」

- 演示：单租户、单人、1 条种子记录、stub 出金——全部 P0 都不会暴露。
- 生产：多用户、重试/超时常态、真实资金、水平扩展——P0-1/P0-2/P0-3 组合 = 越权双花事故；P0-5 = 数据泄露敞口；P0-6 = 前端联调必然踩空。
- 三份文档的框架（状态字段保护、实体级权限、幂等、审计、诚实缺口表）方向全部正确，verifier 确认 v0.42–v0.43 的六项修复主张 6/6 属实——问题不在「想错了」，在「说了没做完」和「做完没写」。

## 修复顺序建议（性价比排序）

1. P0-1 权限接线（一行级改动，关掉越权面）→ 
2. P0-2 补偿留痕（pending 态 + dispatch 前写日志）→ 
3. P0-4 小容量压测（单实体 1 万行 offset P99 实测量级）→ 
4. P0-6 契约同步（delete If-Match + restore + Describe 状态位 + 错误码三处登记）→ 
5. P1-1 case 文档按 0032 现实重写审批路由 → 
6. P0-3/P0-5 出金通道与限流 → 生产前最后两个硬门槛。
