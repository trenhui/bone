## 1. 要回答的四个问题（结论先行）

### 1.1 主数据与租户的关系是什么？—— **记录归租户、模型应归平台模板（当前两层混在一层）**

| 层 | 内容 | 归属 | As-Is | 裁决 |
|----|------|------|-------|------|
| **域模板 / 数据标准 / 质量规则包** | 「客户」「供应商」「物料」「科目」长什么样 | **平台（tenant_id=0）** | ❌ 缺失，每租户从零建 | [Target] 平台预置 + 租户实例化 |
| **主数据实体定义 + 字段扩展 + 分类体系** | 租户在模板上加的字段、自建分类树 | **租户（tenant_id>0）** | ✅ `md_entity`/`md_field` 有 `tenant_id` | 保持 |
| **主数据记录 + 版本 + 质检数据** | 真实业务数据 | **租户（tenant_id>0），行级隔离** | ✅ `md_record` 有 `tenant_id` | 保持 |

> **证据**：`bone-init.sql` §8.1 `md_entity`/`md_field`/`md_record` 三表均已含 `tenant_id BIGINT NOT NULL DEFAULT 0`（SDK 自动过滤/回填）。
> **遗留待决**：`doc/architecture/ddl-required-columns-baseline.json` 仍将 `md_entity`/`md_record` 标为 `needs-owner-decision`（note：疑似全局模板 / 疑似应按租户隔离），与现行 DDL 已含 `tenant_id` 的事实不一致——**基线文件已漂移，须重跑 `scripts/check-ddl-required-columns.py` 刷新**。本文 §3 给出的两层模型即为该 Owner 裁决的正式结论：
> **「模板是平台的、实例和记录是租户的」**。

### 1.2 主数据与应用 / 模块的关系是什么？—— **As-Is 没有直接关系，只能穿透元数据三级反查**

```
md_entity.meta_entity_id  →  meta_entity.id
                              meta_entity.module_id  →  bone_module.id
                                                        bone_module.app_id  →  bone_application.id
```

| 维度 | As-Is 事实 | 说明 |
|------|-----------|------|
| `md_*` 有 `app_id`？ | **无** | 全表检索无任何应用/模块列 |
| `md_*` 有 `module_id`？ | **无** | 同上 |
| 唯一关联 | `md_entity.meta_entity_id → meta_entity.id`（ADR-0002） | 「模型从哪来」可查，「归谁/给谁用」不可查 |
| 结论 | **「这个主数据属于哪个应用」在 As-Is 下答不出来**，只能答「它的模型来自哪个应用」 | 治理责任与消费关系双双缺失 |

**更关键的是语义判断**：主数据的价值恰恰在于**跨应用复用**（一份「客户」被 OMS、FMS、CRM 同时引用）。因此**不能**简单地给 `md_entity` 加一个 `module_id` 把它塞进某棵应用树——那会把主数据退化成"又一个业务实体"，重演元数据扁平化的老问题。

**正解：把「归属」拆成三种语义**（§3.2 详述）：
- **建模来源**（继承，间接）：`source_entity_id → meta_entity.module_id`，回答"模型从哪来"
- **责任归口**（新增，直接）：`owning_app_id`，回答"谁对它负责"（Data Owner 所在业务域），**可空**，缺省为平台共享域
- **消费订阅**（新增，多对多）：`mdm_entity_subscription`，回答"给谁用"

### 1.3 谁能用主数据管理？—— **As-Is 只有抽象的「数据管理员」，缺治理角色与权限码**

| 角色 | DAMA / 业界对应 | As-Is |
|------|----------------|-------|
| 平台管理员（MDM 平台运营） | Platform Operator | 仅有 `is_admin` 超管兜底 |
| **数据责任人 Data Owner** | Data Owner（业务侧问责） | ❌ 无 |
| **数据管家 Data Steward** | Data Steward（日常治理） | ❌ 无（详设只写了泛化的「数据管理员」） |
| 数据录入员 Data Contributor | Contributor | ❌ 无（有 API 无角色） |
| 审批人 Approver | Approver（SoD 职责分离） | ❌ 无（审批流未落库） |
| 应用开发者 / 集成专员 Consumer | Data Consumer | ❌ 无（订阅关系缺失） |

**权限码 As-Is**：仅 `masterdata:entities:read` / `masterdata:entities:write` 两个，且登记在前端 `packages/shared-types/src/bonePermissionCodes.ts`（`maturity: 'Target'`）；**后端 `bone-iam` 检索无 `masterdata` 命中**——即权限目录未落地，字段/记录/质量/分发全裸奔。权限码全集见 §4.4。

### 1.4 主数据管理模块的定位是什么？—— **平台内跨应用共享业务对象的「单一可信数据源 + 治理闭环」**

一句话定位：

> **元数据管「结构怎么定义」，主数据管「实例以哪一份为准」；主数据模块是 Bone 平台内被多个应用共同引用、需要跨系统保持一致的核心业务对象的权威来源（SSOT），并对它的准入、质量、变更、分发负全责。**

三个必须回答的边界问题：

| 边界 | 结论 |
|------|------|
| **主数据 vs 元数据** | 元数据定义 `meta_entity`（结构、字段、关系）；主数据持有 `md_entity` + `md_record`（实例、版本、质量）。二者**不双写**，经 `convert` 单向复制 + `source_entity_id` 追溯（ADR-0017）。 |
| **主数据 vs 业务数据** | 业务数据是"某个应用在某个事务里产生的事实"（订单、凭证）；主数据是"跨应用被引用的共享对象"（客户、供应商、物料、科目、组织）。**判别标准见 §2.2**。 |
| **主数据 vs 集成** | 主数据**不实现**任何连接器运行时；对外分发/回写一律走 `bone-integration`（ADR-0017 决策 4）。 |

## 2. 定位、能力边界与准入标准

### 2.1 模块定位（能做什么）

```
                    ┌─────────────────────────────────────────┐
   平台层(tenant=0) │  域模板 · 数据标准 · 质量规则包 · 分类骨架   │  ← 平台管理员
                    └──────────────────┬──────────────────────┘
                                       │ 实例化 / 版本升级
                    ┌──────────────────▼──────────────────────┐
   租户层(tenant>0) │  ① 建模  ② 采集  ③ 治理  ④ 发布  ⑤ 分发    │  ← Data Owner / Steward
                    └──────────────────┬──────────────────────┘
                                       │ 订阅 / API / 事件
                    ┌──────────────────▼──────────────────────┐
   消费层           │  OMS · FMS · HRM · CRM · 外部系统          │  ← 应用开发者 / 集成专员
                    └─────────────────────────────────────────┘
                                  ⑥ 监控（质量看板 / 血缘 / 采用率）
```

**六段式能力链（这就是"串联"的骨架）**：

| # | 能力 | 内容 | As-Is |
|---|------|------|-------|
| ① | **建模** | 域模板实例化 / 从元数据实体 convert / 字段扩展 / 分类体系（Taxonomy） | 部分（convert ✅、分类 ❌） |
| ② | **采集** | 手工录入、Excel 批量导入、集成接入（走 bone-integration） | 部分（导入 ✅、集成接入 ❌） |
| ③ | **治理** | 质量规则定义与执行、重复检测与黄金记录合并、整改工单 | 部分（规则+检查 ✅、去重合并 ❌、整改闭环 ❌） |
| ④ | **发布** | 变更申请 → 审批（SoD）→ 版本 + 生效期 → 发布 | ❌（仅 `publish` 一键落库，无审批、无状态机） |
| ⑤ | **分发** | 应用订阅、变更事件、集成出口登记 | ❌ |
| ⑥ | **监控** | 质量分趋势、血缘追溯、下游采用率 | 部分（血缘 API ✅、看板 ❌） |

### 2.2 准入标准：什么才配叫主数据（防止"万物皆主数据"）

业界最大的 MDM 失败模式是**把 MDM 当数据库用**——什么都往里塞，结果治理成本爆掉。Bone 必须有显式准入门禁：

| 判据 | 说明 | 阈值建议 |
|------|------|---------|
| **共享性** | 被 ≥2 个应用/模块引用 | 必须 |
| **稳定性** | 结构变更低频（月级而非日级） | 必须 |
| **可标识** | 有稳定业务主键（`record_code`） | 必须 |
| **权威性** | 有明确权威来源系统（source of origin） | 必须 |
| **引用性** | 被业务数据外键/编码引用 | 必须 |
| **体量** | 记录数在十万级以内（百万级应走业务库） | 建议 |

> 典型 Bone 主数据域：**客户、供应商、物料/产品、组织机构、会计科目、员工、项目、地区/币种/行业（参考数据）**。
> **反例（不要做成主数据）**：订单、交易流水、日志、单据——它们是业务事实数据。

### 2.3 参考数据（Reference Data）—— 与主数据的辨析与分工 **[Target]**

> **已核实**：`bone-init.sql` 中**无 `sys_dict` / 数据字典类表**，Bone 当前不具备参考数据能力——本节是真空补位，非重复造轮子。

| 维度 | 主数据（Master Data） | 参考数据（Reference Data） |
|------|---------------------|---------------------------|
| 是什么 | 业务对象**实例** | 代码表 / 枚举 / 分类**标准值域** |
| 例子 | 客户、供应商、物料、员工、科目 | 币种、国家地区、行业代码、计量单位、语言、税种 |
| 体量 | 万～十万级 | 几十～几千条 |
| 变更频率 | 高频（业务驱动） | 极低频（且常锚定外部标准：ISO 4217 / GB/T 2260 等） |
| 谁维护 | **租户**自治（Steward 治理） | **平台**统一维护，租户只读或仅可追加私有值 |
| 治理强度 | 审批 + 版本 + 质检 + 去重 | **无审批、无版本、无订阅**；仅校验引用完整性 |
| 消费方式 | API / 事件订阅 / 集成分发 | 字典式缓存，前端下拉直接取 |

**设计结论**：参考数据**不进主数据治理流**（否则治理成本与收益严重倒挂），走独立的轻量通道：
- 平台层维护标准值域（含外部标准映射列，如 ISO code / GB code）；
- 租户只读，或申请追加**租户私有值**（不得修改平台值）；
- 主数据字段可声明「引用某参考数据集」，作为**值域校验**依据——这是参考数据与主数据唯一的耦合点，也是最容易被忽略的一致性保障。

> 业界依据：DAMA-DMBOK 将「主数据管理」与「参考数据管理」列为并列的两个知识域；SAP 以 customizing / 值表形式集中下发参考数据；ISO 8000 对主数据与参考数据的质量要求分别定义。

### 2.4 明确不做（Out of Scope）

- ❌ 不实现连接器 / ETL 运行时（归 `bone-integration`）
- ❌ 不做通用 BI 分析（归分析域）
- ❌ 不重复实现建模能力（结构定义归 `meta_*`，主数据只做**升格与治理**）
- ❌ 不承载百万级以上事务型数据

## 3. 关系模型设计（解决「与租户、应用到底是什么关系」）

### 3.1 租户两层模型

```
平台层 (tenant_id = 0)
  mdm_domain_template     域模板：客户/供应商/物料/科目…（含默认字段、默认分类骨架、默认质量规则包）
  mdm_template_version    模板版本（semver），租户可选择是否跟随升级
        │
        │ 实例化（复制 + template_id 追溯）
        ▼
租户层 (tenant_id > 0)
  md_entity      主数据实体（template_id 可空=租户自建；source_entity_id=来自 meta_entity）
  md_field       字段（模板字段不可删，仅可禁用；租户可加扩展字段）
  mdm_category   分类树（DDL 已有，代码未用 → G4）
  md_record      记录（行级隔离，唯一键 (tenant_id, entity_id, record_code)）
  md_record_version / mdm_record_version  版本与审批留痕
```

**核心规则**：
1. 租户**不能改模板本身**，只能在实例上加扩展字段 / 禁用模板字段（与 ADR-0017「删除字段=软禁用」一致）。
2. 模板升级由平台发布新版本，租户**自主选择**是否同步（避免平台升级打挂租户）。
3. `md_record` **永远归租户**——即使实体来自平台模板。

**首批域模板清单**（不预置模板的 MDM 等于让每个租户从空白开始，是平台失职）：

| 域编码 | 域名 | 建议治理等级 | 关键字段（默认） | 默认质量规则 | 默认分类骨架 |
|--------|------|------------|----------------|-------------|-------------|
| `PARTY_CUSTOMER` | 客户 | L2 标准 | 客户编码、名称、统一社会信用代码、类型、状态、归属组织 | 编码唯一、名称非空、信用代码格式校验 | 客户分级（A/B/C）+ 行业 |
| `PARTY_SUPPLIER` | 供应商 | L2 标准 | 供应商编码、名称、信用代码、资质等级、合作状态 | 编码唯一、信用代码唯一（跨客户查重） | 品类 + 资质等级 |
| `MATERIAL` | 物料/产品 | L3 严格 | 物料编码、名称、规格、计量单位、品类、状态 | 编码唯一、单位须存在于参考数据、规格非空 | 品类树（多级） |
| `ORG_UNIT` | 组织机构 | L3 严格 | 组织编码、名称、上级、层级、负责人、生效期 | 层级环检测、上级必须存在 | 组织树（与 IAM 部门树可对齐） |
| `FIN_ACCOUNT` | 会计科目 | L3 严格 | 科目编码、名称、上级、余额方向、层级 | 编码规则校验、上级必须存在 | 科目树（多级） |
| `EMPLOYEE` | 员工 | L2 标准 | 工号、姓名、所属组织、岗位、入职日期 | 工号唯一、所属组织须存在于 ORG_UNIT | 按组织 + 岗位序列 |
| `PROJECT` | 项目 | L1 轻量 | 项目编号、名称、负责人、起止日期、状态 | 编号唯一、日期区间合法 | 项目类型 |

> 平台**首批只做 7 个**，不追求全覆盖——模板质量比数量重要（业界反模式：模板铺得太开但每个都缺字段，租户反而要重做）。

### 3.2 应用三级关系（建模来源 / 责任归口 / 消费订阅）

| 语义 | 载体 | 基数 | 回答的问题 | 层级 |
|------|------|------|-----------|------|
| **建模来源** | `md_entity.source_entity_id → meta_entity.module_id → bone_module.app_id` | 1:1（只读继承） | 模型从哪来 | [Target] 显式化 |
| **责任归口** | `md_entity.owning_app_id → bone_application.id` | N:1，**可空** | 谁对它负责（Data Owner 所在业务域） | [Target] 新增 |
| **消费订阅** | `mdm_entity_subscription(app_id, md_entity_id, mode, …)` | **N:M** | 给谁用 | [Target] 新增 |

> 三者互不替代：一个「客户」主数据可以**建模来源**是 IAM 模块、**责任归口**是 CRM 业务域、**被 OMS/FMS/CRM 三个应用订阅**。这正是主数据"跨应用共享"的本质。

**与元数据导航的关系**：元数据侧「应用 → 模块 → 实体 → 字段」是**建模导航**（谁建模谁管）；主数据侧是**治理导航**（域 → 实体 → 记录 → 质量 → 订阅）。两套导航在「主数据实体详情」处交汇——详情页同时展示**来源模型**（跳转元数据）与**订阅应用**（跳转应用管理）。

### 3.3 建议新增 / 启用的表（DDL 变更须走 L3 审批，真源 `bone-init.sql`）

| 表 | 用途 | 状态 | 优先级 |
|----|------|------|--------|
| `mdm_domain_template` + `mdm_template_version` | 平台域模板与版本（§3.1） | 新建 | P1 |
| `mdm_entity_subscription` | 消费应用订阅关系（N:M） | 新建 | P1 |
| `mdm_steward_scope` | **Steward 授权范围**（全域 / 分类子树 / 组织范围）——记录级数据权限 | 新建 | P1 |
| `mdm_quality_issue` | 质量问题整改工单（UC-T9） | 新建 | P2 |
| `mdm_reference_set` + `mdm_reference_value` | 参考数据值域（§2.3） | 新建 | P2 |
| `mdm_category` / `mdm_record_category` | 分类体系 | **DDL 已有，代码未接** | P1 |
| `mdm_record` / `mdm_record_version` / `mdm_entity` / `mdm_qcheck_detail` | 规划表 | **DDL 已有，代码未接** | P0（先裁定收口，见 G1） |
| `md_entity`（或收敛后的 `mdm_entity`）加 `template_id`、`owning_app_id`、`domain_code`、`governance_tier` | 归属、模板追溯、治理等级 | ALTER | P1 |
| `md_record`（或 `mdm_record`）加 `deleted`、`version` | 软删与乐观锁（基线判定缺失） | ALTER | P1 |

**v1.1 的两处"减法"（避免过度建表）**：
1. ~~**砍掉 `mdm_change_request`**~~ **（2026-11-13 终局裁决撤销，见 §11.9 / 终局架构裁决 §2-B1）**：单记录版本状态机的 `status` / `approved_by` / `approved_at` / `change_description` 四列，只能表达「一条记录的一次审批」，**表达不了供应商三段视图（General / CompanyCode / PurchasingOrg）并行路由、各段不同 specialist、缺一不可、审批与应用三权分立**。SAP MDG 的 CR 独立存在正因如此，与「是否跨记录」无关。独立 CR 从 [Vision] **升回 [Target/P0]**；`mdm_change_request` / `mdm_change_request_segment` / `mdm_change_request_trail` 列入 DDL 草案（L3 待审）。本轮已交付领域内核、端口契约、编排、API 与联调（§11.9），生产 adapter 与建表属 L3。
2. **`is_versioning` / `workflow_enabled` 两个布尔不直接暴露给 UI**：升级为 `governance_tier` 枚举（§4.3），由等级推导默认值，避免租户面对一堆语义不明的开关。

> ⚠️ 上表**不是 SQL 副本**，落地一律改 `bone-init.sql` 真源 + 刷新基线，见 [数据库开发规范](../../architecture/数据库开发规范.md)。
> ⚠️ **DDL 变更走 expand/contract**：开发库仍可全量重建，但生产须按 [《ADR-生产数据库增量迁移策略》](../../architecture/adr/ADR-生产数据库增量迁移策略.md) 编写 `scripts/migration/{version}_{description}.sql`（Expand nullable+DEFAULT → Migrate → Switch → Contract）。**v1.0 曾以"无增量迁移"为由低估了 G1 双表收敛的成本，此处更正。**

## 4. 参与者、角色与权限码

### 4.1 角色定义（对齐 DAMA-DMBOK 与 SAP MDG）

| 角色 | 一句话定位 | 管什么 | 不碰什么 | 载体 |
|------|-----------|--------|---------|------|
| **平台管理员**（MDM 平台运营） | 经营域模板与规则包，跨租户巡检 | 域模板 CRUD + 版本、全局质量规则包、跨租户治理看板 | 不碰任何租户记录 | `is_admin`（平台域权限码） |
| **Data Owner**（数据责任人，业务侧） | 对某个主数据域**负业务责任** | 任命 Steward、定治理策略（是否开审批流/版本）、裁定争议合并、批准发布 | 不做日常录入 | 新增 `mdm_entity.owner_account_id` + 角色 |
| **Data Steward**（数据管家） | 日常治理执行者，**带授权范围** | 采集、清洗、去重合并、质量整改、分类维护、发起变更 | ① 不审批自己的提交（SoD）② **只能治理 `mdm_steward_scope` 授权范围内的记录**（§4.3） | 新增 `mdm_entity_steward` 关联 + 范围行 |
| **Data Contributor**（录入员） | 提数的人 | 单条新增/编辑（进 DRAFT）、批量导入 | 不能发布 | 租户域权限码 |
| **Approver**（审批人） | 变更把关 | 审批变更申请，**不得审批本人提交** | 不能同时是 Steward（同一实体） | IAM 角色 + SoD 校验 |
| **Consumer / 集成专员** | 用数的人 | 订阅主数据、配置分发（走 bone-integration） | 不能改主数据内容 | `mdm_entity_subscription` |
| **系统 / Job** | 自动化 | 定时质检、对账、去重扫描、生效期切换、过期归档 | — | 定时任务 |

### 4.2 双管理员红线（沿用 IAM 姊妹篇 §2.2 的三条，新增两条）

1. **平台管理员不代租户做治理**：只供给模板与规则包，实体实例与记录由租户自助完成。
2. **租户不产生域模板**：模板是平台资产；租户只能实例化 + 扩展（与 IAM「租户不自造权限码」同构）。
3. **职责分离（SoD）**：同一 `md_entity` 上，Steward 提交的变更不能由本人审批——后端强制校验，非前端提示。
4. **发布即生效**：发布动作写 `effective_from`，支持**定时生效 / 立即生效**；已发布记录走**新版本**（`is_current` 切换），不覆盖历史。
5. **对外只走集成**：任何跨系统分发必须经 `bone-integration`，禁止主数据模块直连外部库。
6. **消费侧不得直连 `md_*` / `mdm_*` 表**：主数据是独立服务（:8084），其他模块取主数据**必须经 API**（或后续 SDK 客户端），禁止跨库 JOIN——与 Bone「禁止 MyBatis-Plus/JPA、持久层统一走 bone-metadata-sdk」是同构的红线，**服务边界优先于查询便利**。
7. **不是所有域都要重度治理**：治理强度由 §4.3 的等级决定，**默认 L1**；把参考数据或小代码表套上审批+版本是典型的过度治理，会直接劝退租户。

### 4.3 治理等级（Governance Tier）与授权范围 **[Target]**

> v1.0 直接把 `is_versioning` / `workflow_enabled` 两个布尔开关抛给租户，是**把设计难题转嫁给用户**。业界（SAP MDG 的 activation level、Semarchy 的 entity-level governance settings）都用**分级**来打包这些开关。

| 等级 | 适用 | 审批 | 版本 | 质检门禁 | 去重 | 审计 | 默认 |
|------|------|:----:|:----:|:-------:|:----:|:----:|:----:|
| **L1 轻量** | 项目、内部代码表、低频小域 | ❌ | ❌ | 警告 | ❌ | 基础 | ✅ **默认** |
| **L2 标准** | 客户、供应商、员工 | ✅ | ✅ | 警告 | 可选 | 完整 | |
| **L3 严格** | 物料、科目、组织机构（涉合规/涉财） | ✅ 双人 | ✅ | **硬门禁** | ✅ | 完整 + 变更全留痕 | |

- 等级**由模板给出建议值**（§3.1 清单已标注），租户可上调，**下调需二次确认**（防止悄悄降低管控）。
- 等级 → 开关映射：`L1 ⇒ workflow_enabled=0, is_versioning=0`；`L2/L3 ⇒ 1,1`；L3 额外启用质检硬门禁与双人审批。

**授权范围（Steward Scope）——补齐"记录级"数据权限**：

Bone 现有权限体系只有**功能权限**（权限码）。但 MDM 的治理权限天然是三维的：

| 维度 | 问题 | 载体 |
|------|------|------|
| 功能权限 | 能不能发布 / 审批 | 权限码 `masterdata:*`（§4.4） |
| **域权限** | 能管哪个主数据域 | `mdm_entity_steward`（实体×账号） |
| **记录权限（范围）** | 能管域里的**哪些记录** | `mdm_steward_scope`（新增） |

`mdm_steward_scope` 三种范围类型：

| scope_type | 含义 | 典型场景 |
|-----------|------|---------|
| `ALL` | 本域全部记录 | 域只有一个 Steward（默认） |
| `CATEGORY` | 仅指定分类子树 | 物料域按品类分给多个 Steward |
| `ORG` | 仅指定组织范围 | 客户域按大区/分公司分给多个 Steward |

> 业界依据：Semarchy xDM 的 row-level security、SAP MDG 基于公司代码/组织的数据权限。缺了记录权限，多组织企业只能靠"给所有人全域权限"来干活，等于没有权限。

### 4.5 Steward RACI 与 SoD 矩阵 **[Target/P0]**（2026-11-13 新增）

> **为什么单独成节**：DAMA-DMBOK2 与各 MDM 落地复盘把「配了平台、没配 Steward 与责任矩阵」列为头号失败模式。终局裁决 §2-D1~D3 要求组织与代码同步落地；只有功能权限码而没有具名责任人，三段路由会退化成「谁都能批、出事无人负责」。本节定义责任矩阵，代码侧由 `ChangeRequestApplicationService.requireActor` 与领域内核 SoD 硬约束守护。

**角色定义（必须具名，禁止占位符）**

| 角色 | 责任 | 终局要求 |
|---|---|---|
| **具名 Data Owner** | 域的语义与治理等级最终负责；下调治理等级需二次确认 | 每个主数据域 1 名具名账号，`mdm_entity_steward` 登记，不得留空 |
| Data Steward（分段） | General / CompanyCode / PurchasingOrg 各自的字段审批 | 三段各 1 名具名 specialist；不得由提交人兼任 |
| Contributor | 提交变更请求 | 具名账号，且必须与登录账号一致 |
| Approver | 分段裁决 | 只能裁决自己被预派的那一段 |
| Activator | 应用已批准 CR、写 Active 区 | 不得是提交人或任一审批人 |
| MDM 平台管理员 | 端口装配、能力开关、死信重放 | 无业务字段审批权 |
| 审计 / 合规 | 决策流水、停用演练、漂移对账 | 只读，不参与写路径 |

**Steward RACI（分段并行变更请求）**

| 活动 | Contributor | Data Owner | 分段 Steward | Activator | 平台管理员 | 审计 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| 提交 CR / 三段路由指派 | **R** | **A** | C | – | I | I |
| General 段裁决 | I | **A** | **R** | – | I | I |
| CompanyCode 段裁决 | I | **A** | **R** | – | I | I |
| PurchasingOrg 段裁决 | I | **A** | **R** | – | I | I |
| 双人复核 / SoD 后端校验 | – | **A** | C | – | **R** | I |
| 应用并发布 Active | I | **A** | I | **R** | C | I |
| 死信重放 / 版本对账 | – | I | – | C | **R/A** | C |
| 一键停用与演练 | I | **A** | I | I | **R** | C |

**SoD 矩阵（后端硬校验，不依赖前端隐藏按钮）**

| # | 禁止组合 | 守护点（源码） | 负向判据 |
|---|---|---|---|
| S1 | 提交人 = 分段审批人 | `ChangeRequest.decide` | 自审注入 → 必红 |
| S2 | 非预派 Owner 审批某段 | `SegmentApproval.decide` | 越权审批注入 → 必红 |
| S3 | 三段全部由同一账号签完 | `ChangeRequest.apply` | 双人复核不满足 → 必红 |
| S4 | 应用人 = 提交人或审批人 | `ChangeRequest.apply` | 三权分立注入 → 必红 |
| S5 | 请求体代签他人账号 | `ChangeRequestApplicationService.requireActor` | actor ≠ JWT userId → 必红 |
| S6 | 未齐三段即写 Active 区 | `apply` 先于 `ChangeRequestActivationPort.activate` | 未审批直接发布 → 必红 |
| S7 | 自报 tenantId 读写他人 CR | `requireSameTenant` / `currentForCaller` | 跨租户注入 → 必红 |

> RACI 的**具名署名与日期**由平台组 + 各域 TL 按 `平台能力共建RFC.md` 模板填写，本族不代填；代码侧已用「具名账号 + 登录态绑定」把空路由变成不可通过的结构性约束。

#### UC-MD-P4 跨租户治理巡检 **[Target]**

> v1.0 只给了指标名没给算法，"质量分"无法落地计算。v1.1 补齐定义（口径统一，否则各租户各算各的、无法横向对比）。

| 指标 | 定义（算法） | 目标值 | 说明 |
|------|-------------|--------|------|
| **完备率** | 已填字段数 / 应填字段数（按实体字段的 required 计） | ≥ 95% | 逐记录算再取均值 |
| **唯一率** | 1 − 重复组内冗余记录数 / 记录总数 | ≥ 99% | 依赖 UC-T6（Vision 期用编码重复近似） |
| **合规率** | 通过全部质量规则的记录数 / 参检记录数 | ≥ 98% | 按最近一次质检任务计 |
| **及时率** | SLA 内完成更新的记录数 / 应更新记录数 | ≥ 90% | SLA 按域配置（默认 3 个工作日） |
| **质量分** | `0.3×完备率 + 0.3×合规率 + 0.2×唯一率 + 0.2×及时率` | 分域展示 | 权重可配；跌穿阈值触发告警（详设 §0） |
| **采用率** | 被 ≥1 个应用订阅的主数据域数 / 已发布域数 | 越高越好 | **衡量主数据"有没有人用"的关键指标** |
| **分发成功率** | 分发成功次数 / 分发总次数 | ≥ 99.5% | 失败进 `bone-integration` 死信 |

看板维度：租户数 × 主数据域数、记录总量、质量分趋势、待发布变更数、逾期未整改工单数、订阅应用数。

## 6. 端到端流程串联（四条主线）

### 流程 A：从模板到可消费（主数据域建设全链路）—— 把割裂的功能串成一条线

```
平台管理员                        Data Owner / Steward                    消费应用
──────────                       ───────────────────                    ────────
UC-P1 域模板 + 规则包
UC-P2 版本发布 ──模板──▶ UC-T1 域实例化（模板 / convert）
                         UC-T2 任命 Owner+Steward、配治理策略
                         UC-T3 分类体系搭建
                         UC-T4 质量规则绑定
                         UC-T5 记录采集（录入/导入/集成接入）
                         UC-T6 去重合并 → 黄金记录
                         UC-T4 执行质检 ──不合格──▶ UC-T9 整改闭环 ──┐
                                  ▲                                  │
                                  └────────── 复检 ◀────────────────┘
                         UC-T7 变更申请→审批→发布（版本+生效期）
                                  │
                                  └──发布事件──▶ UC-C1 订阅
                                                 UC-C2 消费取数
                                                 UC-C3 变更事件
UC-P4 治理巡检 ◀──质量分/采用率──────────────────────────────────────┘
```

**关键串联点**：
1. **UC-T1 是唯一入口**：无论从模板还是从元数据 convert，之后流程完全一致——这是消除"两条路各走一半"的关键。
2. **UC-T2 治理策略是总开关**：`workflow_enabled` / `is_versioning` 决定后续是否走审批与版本——DDL 列已存在，接上即可。
3. **UC-T4 ⇄ UC-T9 是质量闭环**：质检不是终点，整改复检才是。As-Is 断在"生成报告"这一步。
4. **UC-T7 → UC-C* 是价值兑现点**：不发布、不分发，主数据就等于没建。
5. **权限码是全程通用语言**：`masterdata:*` 在 §4.3 生产 → 各 Handler `@PreAuthorize` 执行。

### 流程 B：日常治理闭环（周期性）

```
定时 Job：执行质检 → 生成任务/报告 → 失败项转整改工单 → 指派 Steward
  → Steward 整改 → 复检通过 → 工单关闭 → 质量分回升 → 看板更新
  → 质量分跌穿阈值 → 写 bone-integration 死信 + 通知（详设 §0 Target）
```

### 流程 C：变更与审批（SoD）

```
业务变化（如客户更名）→ Contributor 提变更（DRAFT）
  → Steward 完善并提交审批（PENDING_APPROVAL）
  → Approver 审批（非提交者本人）→ APPROVED
  → Owner 发布（新版本 + 生效期）→ PUBLISHED，旧版 SUPERSEDED
  → 发布事件 → 订阅应用增量更新 → 审计留痕
```

### 流程 D：消费侧接入

```
应用开发者：应用详情「订阅主数据」→ 选域 → Owner 批准
  → 配置集成连接器（bone-integration）→ 联调取数（UC-C2）
  → 订阅变更事件（UC-C3）→ 运行期监控分发成功率
```

### 7.1 G1 裁定：收敛到 `mdm_*`（推荐结论）与四步执行路径

> v1.0 只写了"二选一"未给出确定性结论与路径，v1.1 补齐。

**为什么选 `mdm_*`（而不是承认 `md_*` 为真源）**：

| 判据 | `mdm_*` | `md_*`（现状运行表） |
|------|---------|---------------------|
| **版本/生效期** | `mdm_record` 有 `is_current` / `effective_from` / `effective_to` / `version_number` / `parent_record_id` | **全无**——UC-T7（版本+生效期）无法落地 |
| **治理策略** | `mdm_entity` 有 `is_versioning` / `workflow_enabled` | 无——UC-T2 治理等级无列可写 |
| **软删 / 乐观锁** | 多数表带 `deleted` + `version` | `md_record` **两者皆无**（基线亦判定缺失） |
| **文档一致性** | 详设 §4、DDL §8、ADR-0017 均已声明 `mdm_*` 为真源 | 若选它，须回改详设 §0/§4 与 ADR-0017 |
| **命名规约** | `mdm_` 与平台命名族一致 | `md_` 前缀易歧义（Markdown 等） |

**⚠️ 收敛的必要补充（v1.0 漏项）**：`mdm_*` 八表中**没有字段表**，但主数据确有独立字段定义（`MasterDataField` → `md_field`，ADR-0017 亦提及"追加 `mdm_field`"）。→ 收敛时必须**新建 `mdm_field` 表**，否则字段无处安放。

**四步路径（expand/contract，生产走迁移脚本）**：

| 步 | 动作 | 环境 |
|----|------|------|
| ① **Expand** | `bone-init.sql` 补齐：`mdm_entity` + `template_id`/`owning_app_id`/`domain_code`/`governance_tier`；`mdm_record` + `deleted`/`version`；**新建 `mdm_field`** | 真源 DDL（L3 审批） |
| ② **Migrate** | `scripts/migration/{ver}_masterdata_mdm_convergence.sql`：`md_entity`→`mdm_entity`、`md_field`→`mdm_field`、`md_record`→`mdm_record`（`data` JSON → `current_data`；status 映射；`version_number=1`），保留 ID 映射对照备查 | **生产增量** |
| ③ **Switch** | 8 个聚合的 `@Table` 切换（2 个已在 `mdm_*`）；**API 契约不变，前端无感** | 代码 |
| ④ **Contract** | 确认无引用后从 DDL 移除 `md_entity` / `md_field` / `md_record` | 真源 DDL |

> **更正 v1.0 的错误论证**：v1.0 曾以 modules/README「无增量迁移：改表即改 init，开发库 DROP DATABASE 后重建」为由，认为收敛成本极低。**该论证只适用于开发环境**——Bone 另有《[ADR-生产数据库增量迁移策略](../../architecture/adr/ADR-生产数据库增量迁移策略.md)》，生产必须走 expand/contract 迁移脚本（大表用 gh-ost / pt-osc）。收敛仍需排期与备份，不可当作"顺手改"。

**实施批次建议**：
- **批次 1（P0）**：G1 裁定 + G2 统一 + G3 归属建模（含 DDL 变更 L3 审批、`mvn test` + ArchUnit + 基线自证）

## 11. 终局架构裁决：身份集中、视图联邦（2026-11-13）

> 本章沉淀自「procuraAI 供应商主数据终局架构裁决」，是平台对「供应商等主数据是否接入 BONE 主数据平台」的正式答复，也是 §1.4「单一可信数据源 + 治理闭环」定位在跨域场景下的落地约束。
>
> **结论先行：接，且终局一次定死。** 不采用「域内先自建 MDM、二期上移权威」的 Registry→Coexistence 渐进路线——权威上移必然带来语义重定义、数据迁移与换 ID，属于会被推翻的过渡态。

### 11.1 归属裁决与业界依据

| 层 | 归属 | 内容 |
|---|---|---|
| 平台层（唯一 system of entry） | `bone-masterdata` | 统一身份 `party_id`、General data、域模板（`PARTY_SUPPLIER`）、数据标准、质量规则、数据管家、字段 Owner 与 survivorship 规则、Golden Record、分发 |
| 契约层 | Published Language + ACL | 稳定 `party_id`、xref 映射、版本化事件、字段 Owner 三层矩阵；**不采用 Shared Kernel 共享实体**，避免分布式单体 |
| 域层（终局仍留域内） | 各业务域 | Vendor 双状态机、开通闸门、`EXITED` 清算、多法人账务、PII 字段级加密、价格条件、PO 校验、业务审批链 |

- **平台真源已裁决归属**：本文 §2.2 准入六判据把供应商列为典型主数据域（反例才是订单/流水），§3.1 首批 7 个域模板含 `PARTY_SUPPLIER`，§2 三轨分派明写「平台即产品、PR 回灌、不建第二套」。
- **业界依据**：DAMA-DMBOK2 的 Consolidation / Coexistence 混合 Hub；SAP MDG-S 与 S/4HANA Business Partner (CVI) 的 General / Company Code / Purchasing Org 三视图——General data 由主数据管家跨模块共享，域视图归业务。治理模型为 **federated**：中央锁语义、规则与字段 Owner，域委托执行。
- **不等于全托管**：把 Vendor 状态机、多法人账务、PO 不变量塞进通用 hub 是业界明确警告的 kitchen-sink 反模式；纯 Registry 又没有持久 Golden Record，撑不起 AI 关联与字段级 lineage。
- **消费侧禁令**：业务域只持 `party_id` + 自有视图列，禁止跨库 JOIN 平台表、禁止复制第二份 Golden Record、禁止以本地 ERP 编码作为跨域身份真源。

### 11.2 能力状态校准：以源码为唯一真源

| 能力 | 2026-11-13 源码实测 | 处置 |
|---|---|---|
| 发布审批工作流 / SoD / 治理等级 / 域模板 | **implemented** | 移出 backlog；由能力探针守护，代码回退即判红 |
| 目录同步全链路 / 质量规则引擎 | partial（相关类已有，闭环未接） | 保留 backlog |
| Golden Record 合并与字段级 lineage | **partial**（领域内核 + 编排 + API + HTTP 联调已落地；`mdm_golden_record` / `mdm_merge_audit` 建表与 JDBC adapter 未交付） | 升 `P0-Target` |

**防漂移机制**：`tools/masterdata-compliance-collector/collect.py` 的 `scan_capabilities()` 判定三态 `implemented / partial / missing`；`assert_backlog_consistency()` 在「源码已完成却仍列 backlog」「源码未完成却无跟踪」「backlog 项缺探针」三种情况下让 `collect.py --check` 判红。附录 A/B 由 `--sync-doc` 从同一真源生成，消除人工双真源。

**二次校准（本轮联调后，以实测为准）**：旧 `golden-record-merge` 探针 `scope=domain`，完成标志却锚定 ApplicationService / Controller，是**永远不可能命中的死判据**（假阴）；本轮改 `scope=all` 并拆出 `orchestration` 判据。更关键的是「编排 / API 接通」≠「能力完整交付」：`implemented` 现在要求 `bone-init.sql` 中对应 `CREATE TABLE` 全部存在（`ddl` 判据）——实测源码 Javadoc 里出现 `mdm_golden_record` / `mdm_xref` 表名就会被纯源码正则误判成 DDL 已交付（假绿）。探针额外输出 `orchestrated` / `delivered` / `ddlMissing`，附录 A 可见；`assert_backlog_consistency()` 增加「判为 implemented 但交付判据未命中」自检。无 `ddl` 配置的老能力三态语义逐字不变。

### 11.3 本轮落地：Golden Record 共享服务层领域内核

包 `com.bone.masterdata.domain.model.goldenrecord`（纯领域对象，不继承 SDK 聚合根、不携带 `@Table`；持久化形态由后续 adapter 决定，领域语义不随 adapter 变化）。

| 类 | 职责 |
|---|---|
| `SourceRecord` / `MergeCommand` / `MergeResult` | 候选源记录、不可变合并输入、裁决输出（只有 `APPLIED` 可进入分发） |
| `FieldSurvivorshipRule` / `SurvivorshipPolicy` | 字段级胜出策略：`SOURCE_PRIORITY` / `RECENCY` / `STEWARD_OVERRIDE` / `MANUAL_REVIEW`；字段 Owner 由治理组织配置，域侧不得写死 |
| `FieldProvenance` | 字段级 lineage：`sourceRecordId / sourceSystem / ruleId / observedAt / stewardAccountId` |
| `GoldenRecord` | 不可变快照；构造时逐字段校验 lineage 完整性 |
| `MergeAudit` | 逐字段胜出决策 + 合并前后完整快照，支撑整笔撤销与事后仲裁 |
| `GoldenRecordMerger` | 共享服务层领域内核：合并、确定性选源、整笔回滚 |

五条硬不变量（对应终局裁决的可验证判据）：

1. 跨租户候选源记录 → `DomainException` fail-closed，不静默丢弃；
2. 统一社会信用代码 / 税号出现不同值 → `MANUAL_REVIEW_REQUIRED`，**禁止自动合并**（防错并主体）；
3. 任一胜出字段缺完整 lineage → 整笔拒绝，不产出「部分可溯源」的黄金记录；
4. `MANUAL_REVIEW` 或无具名 `STEWARD_OVERRIDE` → 整笔转人工，不部分应用；
5. 回滚只恢复到合并前完整快照（含 lineage），且当前版本必须等于审计 `after` 版本，防覆盖并发写入；重复回滚拒绝。

**为什么这不是过渡方案**：`party_id`、字段 Owner 矩阵、survivorship 规则、lineage 语义与审计口径在终局图中原位存在，后续只需替换 ApplicationService / DDL / API adapter，**零语义重定义、零数据迁移、零换 ID**。判断标准即：任何一期产物必须能在终局图里定位。

**明确禁写**（会被终局废弃）：域侧 `GoldenRecordService` / `DedupService` / `MergeAudit` / 分段 CR / `golden_flag`；「单向只读投影、二期上移权威」的双写与割接代码；把业务状态机塞进通用 hub。

### 11.4 xref 与 Outbox 分发契约

- `identity/EntityKeyMapping(+Registry)`：本地 `ERP/SRM` 编码 ↔ 平台 `party_id`。同租户同 `(sourceSystem, localId)` 只允许指向一个 `party_id`，改绑 fail-closed；解析出现多个有效 `party_id` 视为数据污染直接拒绝；跨租户隔离，同一 `party_id` 允许一对多本地编码（多法人多账套）。
- `dispatch/MasterDataRecordDispatchedEvent`：`EntitySubscription` 只登记订阅授权、不负责投递；平台 Outbox 中继负责分发，消费侧按 `tenantId|partyId|recordVersion|eventType` 幂等去重。事件**只携带 `payloadHash`、不回传字段原文**（PII 最小化），并由单测以反射方式守护信封不得新增 `payload` 字段或 `getPayload()`。
- 终局要求：Golden Record 分发不可撤回，因此必须有 24h 撤销窗、字段级 lineage 与补偿事件；类型化字段值存储替代当前 `MasterDataRecord.data` 的单个 JSON blob，否则「每胜出字段可溯源、缺一条整笔回滚」无法持久化。

#### 11.8.1 出站端口契约（六边形）

| 端口 | 位置 | 契约要点 | 终局生产实现（未交付） |
|---|---|---|---|
| `GoldenRecordPort` | `domain/gateway/GoldenRecordPort.java:16` | `findCurrent` / `findAudit`；`appendSnapshot(snapshot, audit)` 必须**同事务**落快照与审计（`:30`）；`clearCurrent(tenant, party, tombstone)` 撤销到「无」时必须回写已标记撤销的审计墓碑（`:38`） | JDBC adapter + `mdm_golden_record` / `mdm_merge_audit` |

| `MasterDataOutboxPort` | `domain/gateway/MasterDataOutboxPort.java:12` | `append` 按幂等键唯一；`existsByIdempotencyKey` 供编排层防重复投递 | 事务性 Outbox 表 + 中继 + 唯一索引 |

**为什么放 `domain/gateway` 而非 `domain/repository`**：模块 ArchUnit 规则 `domainRepositoriesShouldOnlyDeclareWhitelistedMethods` 对 `..domain.repository..` 下以 `Repository` 结尾的接口施加方法白名单，`applicationSaveMustPairWithPublishOrExempt` 又要求 application 层 `save()` 配 `publishFrom()`。Golden Record 的「快照 + 审计 + Outbox」是跨聚合事务性写入，不属于既有 `save` 语义，硬塞进仓储包会触发架构规则误伤；`domain/gateway/*Port` 与既有 `CurrentUserPort` 同构。分发通过 `MasterDataOutboxPort.append` 事务性落地，等价于 E-5.4「写入必配发布」，且比进程内事件更可靠（可重放、可幂等）。

#### 11.8.2 编排用例与副作用边界

`application/GoldenRecordApplicationService.java:103` 的 `resolveAndMerge` 串联五个环节，**整条写路径标注 `@Transactional`（`:102` / `:165`）**，保证 xref 登记、快照+审计、Outbox 追加同事务，任一失败全部回滚：

1. **租户校验**（`:255`）：命令 `tenantId` 必须与登录态 `CurrentUserPort.currentTenantId()` 相等，缺失或不一致 fail-closed；API 不接受调用方自报租户。命令里的 `SourceRecordSpec` 不带租户，源记录租户由编排层强制取命令租户，杜绝从 HTTP 注入跨租户候选源。
2. **xref 解析**（`:267`）：本地 `ERP/SRM` 编码只是查表键，绝不成为身份真源；`ResolvedIdentity(partyId, pendingRegistration)` 把「待登记映射」作为**待提交值**返回，不立即落库。
3. **survivorship 合并**：调用 `GoldenRecordMerger.merge`，领域内核裁决身份冲突、lineage、具名裁决与版本单调。
4. **仅 `APPLIED` 才写入**（`:132`）：转人工 / 拒绝时**零快照、零 xref 登记、零分发**，避免「映射已建但主体未成立」的污染。
5. **幂等分发**：`dispatchIfAbsent` 先查幂等键再 `append`；生产 Outbox 表须有唯一索引兜住并发。

`rollback`（`:166`）恢复合并前**完整内容**后重新签发**更高的版本戳**（`current.version + 1`）：若直接把领域内核返回的旧快照当当前状态，版本会倒退，消费侧按版本单调去重时会把补偿事件当陈旧事件丢弃。补偿事件 `GOLDEN_RECORD_ROLLED_BACK` 与撤销墓碑同事务落地；并发防覆盖、重复回滚仍由领域内核裁决。

#### 11.8.3 复核中修正的四处实现自洽性缺陷

这四条不是新增需求，而是把领域内核已有硬约束真正传导到应用/API 层时发现的漏洞，均由联调用例守护：

| # | 缺陷 | 后果 | 修正 |
|---|---|---|---|
| 1 | xref 注册早于合并裁决 | 税号冲突转人工时映射已落库，下次同本地键被错绑到未成立主体 | 改为 `ResolvedIdentity` 延迟登记，仅 `APPLIED` 后写入 |
| 2 | 首次建记录回滚时 `clearCurrent` 不回写审计 | 审计仍为未撤销态，事后仲裁看不到撤销人/原因 | 端口签名加 `MergeAudit tombstone`，适配器按 `mergeId` 覆盖审计状态 |
| 3 | `payloadHash` 用裸 SHA-256 | 税号 / 统一社会信用代码等**低熵 PII 可被离线字典反推**，等同泄露 | 改 HMAC-SHA256，密钥由 `bone.masterdata.golden-record.digest-pepper` 注入且无默认值，缺失或过短拒绝装配 |
| 4 | `GET /{partyId}` 把 `tenantId` 当请求参数 | 调用方可自报租户读取他人黄金记录 | 租户一律取登录态，命令里的 `tenantId` 也逐笔比对 |

联调夹具 `InMemoryGoldenRecordAdapter` 特意按 DB 语义做**审计行拷贝**（读取时重建 `MergeAudit`），而不是共享可变对象引用——否则第 2 条缺陷会因引用共享而测不出来（假绿）。

#### 11.9.2 独立 Change Request（`ChangeRequest.java:36`）

三段 `GENERAL / COMPANY_CODE / PURCHASING_ORG` 并行路由，聚合全不可变、状态迁移返回新实例，决策流水只追加。**五条硬约束**：

#### 11.9.3 Outbox 中继与版本对账（`MasterDataOutboxRelay.java:43`）

`OutboxDelivery.java:14` 在事件信封之外引入投递状态机 `PENDING → DELIVERED / DEAD` + 重试计数；`OutboxRelayStorePort:7` 管状态，`MasterDataProjectionPort:13` 管消费侧授权 / 幂等 / 版本水位。

| # | 硬约束 | 实现 |
|---|---|---|
| 1 | 订阅/租户绑定 | `isAuthorized` 不通过即失败入死信，绝不静默投递 |
| 2 | 信封校验 | 版本戳与 `schemaVersion` 为正、`payloadHash` 为 64 位小写十六进制（HMAC-SHA256） |
| 3 | 幂等 + 单调（N7/N8） | `lastVersion` 前置 + `applyIfNew` 幂等键双重守护；崩溃重放零第二份投影 |
| 4 | 有界重试 | `relayBatch:70` 失败计数递增，达上限转 DEAD 并保留原因，可人工重放 |
| 5 | 可核对 | `reconcile:120` 比对发件箱已投递最大版本与投影版本，并检出重复投影（负向控制用例证明对账不是恒绿） |

**端到端链路**：Golden Record / CR 应用 → `MasterDataOutboxPort.append` → `OutboxRelayStorePort.findPending` → `applyIfNew` → `reconcile`。联调夹具 `InMemoryOutboxRelayStore` 同时实现生产侧写入端口与中继状态端口，共用一份行，避免「两套内存列表各自为政」的假联调。

#### 2. DDL 草案（MySQL 8 / utf8mb4；字段名与 `bone-init.sql` 既有 `mdm_*` 约定对齐后再提交）

```sql
-- 1) Golden Record 快照头：版本戳单调递增，禁止 UPDATE 覆盖旧版本
CREATE TABLE mdm_golden_record (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id       BIGINT       NOT NULL,
  party_id        VARCHAR(64)  NOT NULL,
  record_version  BIGINT       NOT NULL,
  payload_hash    CHAR(64)     NOT NULL COMMENT 'HMAC-SHA256，字段值绝不入总线',
  is_current      TINYINT(1)   NOT NULL DEFAULT 1,
  created_at      DATETIME(3)  NOT NULL,
  created_by      BIGINT       NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_mdm_gr_version (tenant_id, party_id, record_version),
  KEY idx_mdm_gr_current (tenant_id, party_id, is_current)
) COMMENT='平台唯一 system of entry 的黄金记录快照头';

-- 2) 类型化字段值与字段级 lineage：缺任一条 lineage 的整笔合并由领域内核拒绝
CREATE TABLE mdm_field_lineage (
  id                BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id         BIGINT       NOT NULL,
  party_id          VARCHAR(64)  NOT NULL,
  record_version    BIGINT       NOT NULL,
  field_code        VARCHAR(128) NOT NULL,
  field_value       TEXT         NULL COMMENT '按字段类型分列存储时改为对应类型列',
  source_system     VARCHAR(64)  NOT NULL,
  source_record_id  VARCHAR(128) NOT NULL,
  survivorship_rule VARCHAR(64)  NOT NULL,
  trust_rank        INT          NOT NULL DEFAULT 0,
  observed_at       DATETIME(3)  NOT NULL,
  decided_by        VARCHAR(64)  NULL COMMENT 'STEWARD_OVERRIDE 具名裁决人',
  PRIMARY KEY (id),
  UNIQUE KEY uk_mdm_fl_field (tenant_id, party_id, record_version, field_code),
  KEY idx_mdm_fl_source (tenant_id, source_system, source_record_id)
) COMMENT='字段值级 lineage；禁止把 Golden Record 压成单个 JSON blob';

-- 3) 合并审计：撤销只置标记，不物理删，保证重复回滚被拒
CREATE TABLE mdm_merge_audit (
  tenant_id       BIGINT       NOT NULL,
  merge_id        VARCHAR(128) NOT NULL,
  party_id        VARCHAR(64)  NOT NULL,
  before_version  BIGINT       NOT NULL,
  after_version   BIGINT       NOT NULL,
  decisions_json  JSON         NOT NULL,
  created_at      DATETIME(3)  NOT NULL,
  rolled_back     TINYINT(1)   NOT NULL DEFAULT 0,
  rollback_reason VARCHAR(512) NULL,
  rolled_back_by  VARCHAR(64)  NULL,
  rolled_back_at  DATETIME(3)  NULL,
  PRIMARY KEY (tenant_id, merge_id),
  KEY idx_mdm_ma_party (tenant_id, party_id)
) COMMENT='合并裁决与撤销墓碑';

-- 4) xref：同一本地键只允许一个生效 party_id；改绑必须先把旧行置 inactive（领域内核 fail-closed）
CREATE TABLE mdm_xref (
  id             BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id      BIGINT       NOT NULL,
  source_system  VARCHAR(64)  NOT NULL,
  local_id       VARCHAR(128) NOT NULL,
  party_id       VARCHAR(64)  NOT NULL,
  active         TINYINT(1)   NOT NULL DEFAULT 1,
  active_epoch   BIGINT       NOT NULL DEFAULT 0 COMMENT '0=生效；失效行写本行 id，使 MySQL 可用唯一索引约束单活映射',
  created_at     DATETIME(3)  NOT NULL,
  deactivated_at DATETIME(3)  NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_mdm_xref_active (tenant_id, source_system, local_id, active_epoch),
  KEY idx_mdm_xref_party (tenant_id, party_id)
) COMMENT='本地编码 ↔ 平台统一身份；本地编码不得成为身份真源';

-- 5) 事务性 Outbox：业务写入与 append 同事务；中继按 state 投递，达上限转 DEAD 并保留原因
CREATE TABLE mdm_outbox (
  idempotency_key VARCHAR(255) NOT NULL COMMENT 'tenantId|partyId|recordVersion|eventType',
  tenant_id       BIGINT       NOT NULL,
  party_id        VARCHAR(64)  NOT NULL,
  record_version  BIGINT       NOT NULL,
  event_type      VARCHAR(64)  NOT NULL,
  schema_version  INT          NOT NULL,
  event_id        VARCHAR(128) NOT NULL,
  payload_hash    CHAR(64)     NOT NULL,
  occurred_at     DATETIME(3)  NOT NULL,
  state           VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/DELIVERED/DEAD',
  attempts        INT          NOT NULL DEFAULT 0,
  last_error      VARCHAR(512) NULL,
  delivery_note   VARCHAR(64)  NULL,
  updated_at      DATETIME(3)  NOT NULL,
  PRIMARY KEY (idempotency_key),
  KEY idx_mdm_outbox_pending (state, updated_at),
  KEY idx_mdm_outbox_party (tenant_id, party_id, record_version)
) COMMENT='只存 payloadHash，不回传 PII 原文';

-- 6) 独立分段 CR 头：三段并行审批 + 双人复核 + 三权分立，单记录版本状态机无法承载
CREATE TABLE mdm_change_request (
  tenant_id          BIGINT       NOT NULL,
  change_request_id  VARCHAR(128) NOT NULL,
  party_id           VARCHAR(64)  NOT NULL,
  target_version     BIGINT       NOT NULL,
  change_description VARCHAR(512) NOT NULL,
  status             VARCHAR(32)  NOT NULL COMMENT 'DRAFT/IN_REVIEW/APPROVED/REJECTED/APPLIED/CANCELLED',
  created_by         VARCHAR(64)  NOT NULL,
  created_at         DATETIME(3)  NOT NULL,
  applied_by         VARCHAR(64)  NULL,
  applied_at         DATETIME(3)  NULL,
  applied_unique     VARCHAR(256) NULL COMMENT '仅 APPLIED 行写 tenant|party|version，保证同目标版本唯一发布',
  PRIMARY KEY (tenant_id, change_request_id),
  UNIQUE KEY uk_mdm_cr_applied (applied_unique),
  KEY idx_mdm_cr_party (tenant_id, party_id, target_version)
) COMMENT='平台侧独立变更请求；域侧只消费 party_id';

-- 7) 三段 specialist 路由与裁决
CREATE TABLE mdm_change_request_segment (
  tenant_id         BIGINT       NOT NULL,
  change_request_id VARCHAR(128) NOT NULL,
  segment           VARCHAR(32)  NOT NULL COMMENT 'GENERAL/COMPANY_CODE/PURCHASING_ORG',
  assigned_owner    VARCHAR(64)  NOT NULL COMMENT '具名 Data Steward，禁止空路由',
  state             VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
  decided_by        VARCHAR(64)  NULL,
  decided_at        DATETIME(3)  NULL,
  reason            VARCHAR(512) NULL,
  PRIMARY KEY (tenant_id, change_request_id, segment),
  KEY idx_mdm_crs_owner (tenant_id, assigned_owner, state)
) COMMENT='三段并行；缺任一段不得创建 CR';

-- 8) 决策流水（只追加，不回传字段值）
CREATE TABLE mdm_change_request_trail (
  id                BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id         BIGINT       NOT NULL,
  change_request_id VARCHAR(128) NOT NULL,
  seq               INT          NOT NULL,
  action            VARCHAR(32)  NOT NULL,
  segment           VARCHAR(32)  NULL,
  actor             VARCHAR(64)  NOT NULL,
  occurred_at       DATETIME(3)  NOT NULL,
  reason            VARCHAR(512) NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_mdm_crt_seq (tenant_id, change_request_id, seq)
) COMMENT='提交/裁决/应用/撤销全链路留痕';
```

#### 3. 落库前必须补的工程判据（owner / L3）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 全部表带 `tenant_id`，adapter 强制以登录租户为过滤条件 | 防止跨租户读写；领域内核已 fail-closed，DB 层是第二道 |
| 2 | `appendSnapshot`、`clearCurrent`、`activate` 必须**同事务** | 快照 / 审计 / Outbox 任一缺写都会造成不可回滚或不可分发 |
| 3 | `mdm_outbox.idempotency_key` 唯一索引 + `state` 索引 | 并发去重与中继批量扫描；无唯一索引则 N7 必现 |
| 4 | `mdm_xref` 单活映射唯一约束（MySQL 用 `active_epoch` 生成列或等价方案） | 域内核只做逻辑裁决，DB 需兜住并发改绑 |
| 5 | `mdm_change_request.applied_unique` 仅 APPLIED 行填值 | 保证「同一目标版本只有一个已应用 CR」，并行发布竞态由 DB 拒绝 |
| 6 | 生产 adapter 注入 HMAC `digest-pepper`，禁止默认值 | 低熵 PII 裸哈希可离线反推 |
| 7 | expand/contract 迁移脚本 + 回滚三条验证 | 生产库不可全量重建；见 ADR-生产数据库增量迁移策略 |
| 8 | 消费侧 `applyIfNew` 的幂等键与版本水位**同本地事务** | 否则进程崩溃仍会重复投影 |
