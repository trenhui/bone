## 1. 要回答的四个问题（结论先行）

### 1.1 主数据与租户的关系是什么？—— **记录归租户、模型应归平台模板（当前两层混在一层）**

| 层 | 内容 | 归属 | As-Is | 裁决 |
|----|------|------|-------|------|
| **域模板 / 数据标准 / 质量规则包** | 「客户」「供应商」「物料」「科目」长什么样 | **平台（tenant_id=0）** | ❌ 缺失，每租户从零建 | [Target] 平台预置 + 租户实例化 |
| **主数据实体定义 + 字段扩展 + 分类体系** | 租户在模板上加的字段、自建分类树 | **租户（tenant_id>0）** | ✅ `md_entity`/`md_field` 有 `tenant_id` | 保持 |
| **主数据记录 + 版本 + 质检数据** | 真实业务数据 | **租户（tenant_id>0），行级隔离** | ✅ `md_record` 有 `tenant_id` | 保持 |

> **证据**：`bone-init.sql` §8.1 `md_entity`/`md_field`/`md_record` 三表均已含 `tenant_id BIGINT NOT NULL DEFAULT 0`（SDK 自动过滤/回填）。
> **遗留待决**：`doc/architecture/ddl-required-columns-baseline.json` 仍将 `md_entity`/`md_record` 标为 `needs-owner-decision`（note：疑似全局模板 / 疑似应按租户隔离），与现行 DDL 已含 `tenant_id` 的事实不一致——**基线文件已漂移，须重跑 `scripts/check-ddl-required-columns.py` 刷新**。本文 §3 给出的两层模型即为该 Owner 裁决的正式结论：
> **「模板是平台的、实例和记录是租户的」**。

### 1.2 主数据与应用 / 模块的关系是什么？—— **As-Is 没有直接关系，只能穿透元数据三级反查**

```
md_entity.meta_entity_id  →  meta_entity.id
                              meta_entity.module_id  →  bone_module.id
                                                        bone_module.app_id  →  bone_application.id
```

| 维度 | As-Is 事实 | 说明 |
|------|-----------|------|
| `md_*` 有 `app_id`？ | **无** | 全表检索无任何应用/模块列 |
| `md_*` 有 `module_id`？ | **无** | 同上 |
| 唯一关联 | `md_entity.meta_entity_id → meta_entity.id`（ADR-0002） | 「模型从哪来」可查，「归谁/给谁用」不可查 |
| 结论 | **「这个主数据属于哪个应用」在 As-Is 下答不出来**，只能答「它的模型来自哪个应用」 | 治理责任与消费关系双双缺失 |

**更关键的是语义判断**：主数据的价值恰恰在于**跨应用复用**（一份「客户」被 OMS、FMS、CRM 同时引用）。因此**不能**简单地给 `md_entity` 加一个 `module_id` 把它塞进某棵应用树——那会把主数据退化成"又一个业务实体"，重演元数据扁平化的老问题。

**正解：把「归属」拆成三种语义**（§3.2 详述）：
- **建模来源**（继承，间接）：`source_entity_id → meta_entity.module_id`，回答"模型从哪来"
- **责任归口**（新增，直接）：`owning_app_id`，回答"谁对它负责"（Data Owner 所在业务域），**可空**，缺省为平台共享域
- **消费订阅**（新增，多对多）：`mdm_entity_subscription`，回答"给谁用"

### 1.3 谁能用主数据管理？—— **As-Is 只有抽象的「数据管理员」，缺治理角色与权限码**

| 角色 | DAMA / 业界对应 | As-Is |
|------|----------------|-------|
| 平台管理员（MDM 平台运营） | Platform Operator | 仅有 `is_admin` 超管兜底 |
| **数据责任人 Data Owner** | Data Owner（业务侧问责） | ❌ 无 |
| **数据管家 Data Steward** | Data Steward（日常治理） | ❌ 无（详设只写了泛化的「数据管理员」） |
| 数据录入员 Data Contributor | Contributor | ❌ 无（有 API 无角色） |
| 审批人 Approver | Approver（SoD 职责分离） | ❌ 无（审批流未落库） |
| 应用开发者 / 集成专员 Consumer | Data Consumer | ❌ 无（订阅关系缺失） |

**权限码 As-Is**：仅 `masterdata:entities:read` / `masterdata:entities:write` 两个，且登记在前端 `packages/shared-types/src/bonePermissionCodes.ts`（`maturity: 'Target'`）；**后端 `bone-iam` 检索无 `masterdata` 命中**——即权限目录未落地，字段/记录/质量/分发全裸奔。权限码全集见 §4.4。

### 1.4 主数据管理模块的定位是什么？—— **平台内跨应用共享业务对象的「单一可信数据源 + 治理闭环」**

一句话定位：

> **元数据管「结构怎么定义」，主数据管「实例以哪一份为准」；主数据模块是 Bone 平台内被多个应用共同引用、需要跨系统保持一致的核心业务对象的权威来源（SSOT），并对它的准入、质量、变更、分发负全责。**

三个必须回答的边界问题：

| 边界 | 结论 |
|------|------|
| **主数据 vs 元数据** | 元数据定义 `meta_entity`（结构、字段、关系）；主数据持有 `md_entity` + `md_record`（实例、版本、质量）。二者**不双写**，经 `convert` 单向复制 + `source_entity_id` 追溯（ADR-0017）。 |
| **主数据 vs 业务数据** | 业务数据是"某个应用在某个事务里产生的事实"（订单、凭证）；主数据是"跨应用被引用的共享对象"（客户、供应商、物料、科目、组织）。**判别标准见 §2.2**。 |
| **主数据 vs 集成** | 主数据**不实现**任何连接器运行时；对外分发/回写一律走 `bone-integration`（ADR-0017 决策 4）。 |

## 2. 定位、能力边界与准入标准

### 2.1 模块定位（能做什么）

```
                    ┌─────────────────────────────────────────┐
   平台层(tenant=0) │  域模板 · 数据标准 · 质量规则包 · 分类骨架   │  ← 平台管理员
                    └──────────────────┬──────────────────────┘
                                       │ 实例化 / 版本升级
                    ┌──────────────────▼──────────────────────┐
   租户层(tenant>0) │  ① 建模  ② 采集  ③ 治理  ④ 发布  ⑤ 分发    │  ← Data Owner / Steward
                    └──────────────────┬──────────────────────┘
                                       │ 订阅 / API / 事件
                    ┌──────────────────▼──────────────────────┐
   消费层           │  OMS · FMS · HRM · CRM · 外部系统          │  ← 应用开发者 / 集成专员
                    └─────────────────────────────────────────┘
                                  ⑥ 监控（质量看板 / 血缘 / 采用率）
```

**六段式能力链（这就是"串联"的骨架）**：

| # | 能力 | 内容 | As-Is |
|---|------|------|-------|
| ① | **建模** | 域模板实例化 / 从元数据实体 convert / 字段扩展 / 分类体系（Taxonomy） | 部分（convert ✅、分类 ❌） |
| ② | **采集** | 手工录入、Excel 批量导入、集成接入（走 bone-integration） | 部分（导入 ✅、集成接入 ❌） |
| ③ | **治理** | 质量规则定义与执行、重复检测与黄金记录合并、整改工单 | 部分（规则+检查 ✅、去重合并 ❌、整改闭环 ❌） |
| ④ | **发布** | 变更申请 → 审批（SoD）→ 版本 + 生效期 → 发布 | ❌（仅 `publish` 一键落库，无审批、无状态机） |
| ⑤ | **分发** | 应用订阅、变更事件、集成出口登记 | ❌ |
| ⑥ | **监控** | 质量分趋势、血缘追溯、下游采用率 | 部分（血缘 API ✅、看板 ❌） |

### 2.2 准入标准：什么才配叫主数据（防止"万物皆主数据"）

业界最大的 MDM 失败模式是**把 MDM 当数据库用**——什么都往里塞，结果治理成本爆掉。Bone 必须有显式准入门禁：

| 判据 | 说明 | 阈值建议 |
|------|------|---------|
| **共享性** | 被 ≥2 个应用/模块引用 | 必须 |
| **稳定性** | 结构变更低频（月级而非日级） | 必须 |
| **可标识** | 有稳定业务主键（`record_code`） | 必须 |
| **权威性** | 有明确权威来源系统（source of origin） | 必须 |
| **引用性** | 被业务数据外键/编码引用 | 必须 |
| **体量** | 记录数在十万级以内（百万级应走业务库） | 建议 |

> 典型 Bone 主数据域：**客户、供应商、物料/产品、组织机构、会计科目、员工、项目、地区/币种/行业（参考数据）**。
> **反例（不要做成主数据）**：订单、交易流水、日志、单据——它们是业务事实数据。

### 2.3 参考数据（Reference Data）—— 与主数据的辨析与分工 **[Target]**

> **已核实**：`bone-init.sql` 中**无 `sys_dict` / 数据字典类表**，Bone 当前不具备参考数据能力——本节是真空补位，非重复造轮子。

| 维度 | 主数据（Master Data） | 参考数据（Reference Data） |
|------|---------------------|---------------------------|
| 是什么 | 业务对象**实例** | 代码表 / 枚举 / 分类**标准值域** |
| 例子 | 客户、供应商、物料、员工、科目 | 币种、国家地区、行业代码、计量单位、语言、税种 |
| 体量 | 万～十万级 | 几十～几千条 |
| 变更频率 | 高频（业务驱动） | 极低频（且常锚定外部标准：ISO 4217 / GB/T 2260 等） |
| 谁维护 | **租户**自治（Steward 治理） | **平台**统一维护，租户只读或仅可追加私有值 |
| 治理强度 | 审批 + 版本 + 质检 + 去重 | **无审批、无版本、无订阅**；仅校验引用完整性 |
| 消费方式 | API / 事件订阅 / 集成分发 | 字典式缓存，前端下拉直接取 |

**设计结论**：参考数据**不进主数据治理流**（否则治理成本与收益严重倒挂），走独立的轻量通道：
- 平台层维护标准值域（含外部标准映射列，如 ISO code / GB code）；
- 租户只读，或申请追加**租户私有值**（不得修改平台值）；
- 主数据字段可声明「引用某参考数据集」，作为**值域校验**依据——这是参考数据与主数据唯一的耦合点，也是最容易被忽略的一致性保障。

> 业界依据：DAMA-DMBOK 将「主数据管理」与「参考数据管理」列为并列的两个知识域；SAP 以 customizing / 值表形式集中下发参考数据；ISO 8000 对主数据与参考数据的质量要求分别定义。

### 2.4 明确不做（Out of Scope）

- ❌ 不实现连接器 / ETL 运行时（归 `bone-integration`）
- ❌ 不做通用 BI 分析（归分析域）
- ❌ 不重复实现建模能力（结构定义归 `meta_*`，主数据只做**升格与治理**）
- ❌ 不承载百万级以上事务型数据

## 3. 关系模型设计（解决「与租户、应用到底是什么关系」）

### 3.1 租户两层模型

```
平台层 (tenant_id = 0)
  mdm_domain_template     域模板：客户/供应商/物料/科目…（含默认字段、默认分类骨架、默认质量规则包）
  mdm_template_version    模板版本（semver），租户可选择是否跟随升级
        │
        │ 实例化（复制 + template_id 追溯）
        ▼
租户层 (tenant_id > 0)
  md_entity      主数据实体（template_id 可空=租户自建；source_entity_id=来自 meta_entity）
  md_field       字段（模板字段不可删，仅可禁用；租户可加扩展字段）
  mdm_category   分类树（DDL 已有，代码未用 → G4）
  md_record      记录（行级隔离，唯一键 (tenant_id, entity_id, record_code)）
  md_record_version / mdm_record_version  版本与审批留痕
```

**核心规则**：
1. 租户**不能改模板本身**，只能在实例上加扩展字段 / 禁用模板字段（与 ADR-0017「删除字段=软禁用」一致）。
2. 模板升级由平台发布新版本，租户**自主选择**是否同步（避免平台升级打挂租户）。
3. `md_record` **永远归租户**——即使实体来自平台模板。

**首批域模板清单**（不预置模板的 MDM 等于让每个租户从空白开始，是平台失职）：

| 域编码 | 域名 | 建议治理等级 | 关键字段（默认） | 默认质量规则 | 默认分类骨架 |
|--------|------|------------|----------------|-------------|-------------|
| `PARTY_CUSTOMER` | 客户 | L2 标准 | 客户编码、名称、统一社会信用代码、类型、状态、归属组织 | 编码唯一、名称非空、信用代码格式校验 | 客户分级（A/B/C）+ 行业 |
| `PARTY_SUPPLIER` | 供应商 | L2 标准 | 供应商编码、名称、信用代码、资质等级、合作状态 | 编码唯一、信用代码唯一（跨客户查重） | 品类 + 资质等级 |
| `MATERIAL` | 物料/产品 | L3 严格 | 物料编码、名称、规格、计量单位、品类、状态 | 编码唯一、单位须存在于参考数据、规格非空 | 品类树（多级） |
| `ORG_UNIT` | 组织机构 | L3 严格 | 组织编码、名称、上级、层级、负责人、生效期 | 层级环检测、上级必须存在 | 组织树（与 IAM 部门树可对齐） |
| `FIN_ACCOUNT` | 会计科目 | L3 严格 | 科目编码、名称、上级、余额方向、层级 | 编码规则校验、上级必须存在 | 科目树（多级） |
| `EMPLOYEE` | 员工 | L2 标准 | 工号、姓名、所属组织、岗位、入职日期 | 工号唯一、所属组织须存在于 ORG_UNIT | 按组织 + 岗位序列 |
| `PROJECT` | 项目 | L1 轻量 | 项目编号、名称、负责人、起止日期、状态 | 编号唯一、日期区间合法 | 项目类型 |

> 平台**首批只做 7 个**，不追求全覆盖——模板质量比数量重要（业界反模式：模板铺得太开但每个都缺字段，租户反而要重做）。

### 3.2 应用三级关系（建模来源 / 责任归口 / 消费订阅）

| 语义 | 载体 | 基数 | 回答的问题 | 层级 |
|------|------|------|-----------|------|
| **建模来源** | `md_entity.source_entity_id → meta_entity.module_id → bone_module.app_id` | 1:1（只读继承） | 模型从哪来 | [Target] 显式化 |
| **责任归口** | `md_entity.owning_app_id → bone_application.id` | N:1，**可空** | 谁对它负责（Data Owner 所在业务域） | [Target] 新增 |
| **消费订阅** | `mdm_entity_subscription(app_id, md_entity_id, mode, …)` | **N:M** | 给谁用 | [Target] 新增 |

> 三者互不替代：一个「客户」主数据可以**建模来源**是 IAM 模块、**责任归口**是 CRM 业务域、**被 OMS/FMS/CRM 三个应用订阅**。这正是主数据"跨应用共享"的本质。

**与元数据导航的关系**：元数据侧「应用 → 模块 → 实体 → 字段」是**建模导航**（谁建模谁管）；主数据侧是**治理导航**（域 → 实体 → 记录 → 质量 → 订阅）。两套导航在「主数据实体详情」处交汇——详情页同时展示**来源模型**（跳转元数据）与**订阅应用**（跳转应用管理）。

### 3.3 建议新增 / 启用的表（DDL 变更须走 L3 审批，真源 `bone-init.sql`）

| 表 | 用途 | 状态 | 优先级 |
|----|------|------|--------|
| `mdm_domain_template` + `mdm_template_version` | 平台域模板与版本（§3.1） | 新建 | P1 |
| `mdm_entity_subscription` | 消费应用订阅关系（N:M） | 新建 | P1 |
| `mdm_steward_scope` | **Steward 授权范围**（全域 / 分类子树 / 组织范围）——记录级数据权限 | 新建 | P1 |
| `mdm_quality_issue` | 质量问题整改工单（UC-T9） | 新建 | P2 |
| `mdm_reference_set` + `mdm_reference_value` | 参考数据值域（§2.3） | 新建 | P2 |
| `mdm_category` / `mdm_record_category` | 分类体系 | **DDL 已有，代码未接** | P1 |
| `mdm_record` / `mdm_record_version` / `mdm_entity` / `mdm_qcheck_detail` | 规划表 | **DDL 已有，代码未接** | P0（先裁定收口，见 G1） |
| `md_entity`（或收敛后的 `mdm_entity`）加 `template_id`、`owning_app_id`、`domain_code`、`governance_tier` | 归属、模板追溯、治理等级 | ALTER | P1 |
| `md_record`（或 `mdm_record`）加 `deleted`、`version` | 软删与乐观锁（基线判定缺失） | ALTER | P1 |

**v1.1 的两处"减法"（避免过度建表）**：
1. **砍掉 `mdm_change_request`**：MVP 的单记录审批**不需要独立表**——`mdm_record_version` 已有 `status` / `approved_by` / `approved_at` / `change_description` 四列，直接承载审批态即可（见 UC-T7）。独立 CR 表只在**跨记录批量变更 / 跨实体变更**时才必要（SAP MDG 的 CR 之所以独立，是因为它跨对象、多步骤、需并行审批），Bone 现状降为 [Vision]。
2. **`is_versioning` / `workflow_enabled` 两个布尔不直接暴露给 UI**：升级为 `governance_tier` 枚举（§4.3），由等级推导默认值，避免租户面对一堆语义不明的开关。

> ⚠️ 上表**不是 SQL 副本**，落地一律改 `bone-init.sql` 真源 + 刷新基线，见 [数据库开发规范](../../architecture/数据库开发规范.md)。
> ⚠️ **DDL 变更走 expand/contract**：开发库仍可全量重建，但生产须按 [《ADR-生产数据库增量迁移策略》](../../architecture/adr/ADR-生产数据库增量迁移策略.md) 编写 `scripts/migration/{version}_{description}.sql`（Expand nullable+DEFAULT → Migrate → Switch → Contract）。**v1.0 曾以"无增量迁移"为由低估了 G1 双表收敛的成本，此处更正。**

## 4. 参与者、角色与权限码

### 4.1 角色定义（对齐 DAMA-DMBOK 与 SAP MDG）

| 角色 | 一句话定位 | 管什么 | 不碰什么 | 载体 |
|------|-----------|--------|---------|------|
| **平台管理员**（MDM 平台运营） | 经营域模板与规则包，跨租户巡检 | 域模板 CRUD + 版本、全局质量规则包、跨租户治理看板 | 不碰任何租户记录 | `is_admin`（平台域权限码） |
| **Data Owner**（数据责任人，业务侧） | 对某个主数据域**负业务责任** | 任命 Steward、定治理策略（是否开审批流/版本）、裁定争议合并、批准发布 | 不做日常录入 | 新增 `mdm_entity.owner_account_id` + 角色 |
| **Data Steward**（数据管家） | 日常治理执行者，**带授权范围** | 采集、清洗、去重合并、质量整改、分类维护、发起变更 | ① 不审批自己的提交（SoD）② **只能治理 `mdm_steward_scope` 授权范围内的记录**（§4.3） | 新增 `mdm_entity_steward` 关联 + 范围行 |
| **Data Contributor**（录入员） | 提数的人 | 单条新增/编辑（进 DRAFT）、批量导入 | 不能发布 | 租户域权限码 |
| **Approver**（审批人） | 变更把关 | 审批变更申请，**不得审批本人提交** | 不能同时是 Steward（同一实体） | IAM 角色 + SoD 校验 |
| **Consumer / 集成专员** | 用数的人 | 订阅主数据、配置分发（走 bone-integration） | 不能改主数据内容 | `mdm_entity_subscription` |
| **系统 / Job** | 自动化 | 定时质检、对账、去重扫描、生效期切换、过期归档 | — | 定时任务 |

### 4.2 双管理员红线（沿用 IAM 姊妹篇 §2.2 的三条，新增两条）

1. **平台管理员不代租户做治理**：只供给模板与规则包，实体实例与记录由租户自助完成。
2. **租户不产生域模板**：模板是平台资产；租户只能实例化 + 扩展（与 IAM「租户不自造权限码」同构）。
3. **职责分离（SoD）**：同一 `md_entity` 上，Steward 提交的变更不能由本人审批——后端强制校验，非前端提示。
4. **发布即生效**：发布动作写 `effective_from`，支持**定时生效 / 立即生效**；已发布记录走**新版本**（`is_current` 切换），不覆盖历史。
5. **对外只走集成**：任何跨系统分发必须经 `bone-integration`，禁止主数据模块直连外部库。
6. **消费侧不得直连 `md_*` / `mdm_*` 表**：主数据是独立服务（:8084），其他模块取主数据**必须经 API**（或后续 SDK 客户端），禁止跨库 JOIN——与 Bone「禁止 MyBatis-Plus/JPA、持久层统一走 bone-metadata-sdk」是同构的红线，**服务边界优先于查询便利**。
7. **不是所有域都要重度治理**：治理强度由 §4.3 的等级决定，**默认 L1**；把参考数据或小代码表套上审批+版本是典型的过度治理，会直接劝退租户。

### 4.3 治理等级（Governance Tier）与授权范围 **[Target]**

> v1.0 直接把 `is_versioning` / `workflow_enabled` 两个布尔开关抛给租户，是**把设计难题转嫁给用户**。业界（SAP MDG 的 activation level、Semarchy 的 entity-level governance settings）都用**分级**来打包这些开关。

| 等级 | 适用 | 审批 | 版本 | 质检门禁 | 去重 | 审计 | 默认 |
|------|------|:----:|:----:|:-------:|:----:|:----:|:----:|
| **L1 轻量** | 项目、内部代码表、低频小域 | ❌ | ❌ | 警告 | ❌ | 基础 | ✅ **默认** |
| **L2 标准** | 客户、供应商、员工 | ✅ | ✅ | 警告 | 可选 | 完整 | |
| **L3 严格** | 物料、科目、组织机构（涉合规/涉财） | ✅ 双人 | ✅ | **硬门禁** | ✅ | 完整 + 变更全留痕 | |

- 等级**由模板给出建议值**（§3.1 清单已标注），租户可上调，**下调需二次确认**（防止悄悄降低管控）。
- 等级 → 开关映射：`L1 ⇒ workflow_enabled=0, is_versioning=0`；`L2/L3 ⇒ 1,1`；L3 额外启用质检硬门禁与双人审批。

**授权范围（Steward Scope）——补齐"记录级"数据权限**：

Bone 现有权限体系只有**功能权限**（权限码）。但 MDM 的治理权限天然是三维的：

| 维度 | 问题 | 载体 |
|------|------|------|
| 功能权限 | 能不能发布 / 审批 | 权限码 `masterdata:*`（§4.4） |
| **域权限** | 能管哪个主数据域 | `mdm_entity_steward`（实体×账号） |
| **记录权限（范围）** | 能管域里的**哪些记录** | `mdm_steward_scope`（新增） |

`mdm_steward_scope` 三种范围类型：

| scope_type | 含义 | 典型场景 |
|-----------|------|---------|
| `ALL` | 本域全部记录 | 域只有一个 Steward（默认） |
| `CATEGORY` | 仅指定分类子树 | 物料域按品类分给多个 Steward |
| `ORG` | 仅指定组织范围 | 客户域按大区/分公司分给多个 Steward |

> 业界依据：Semarchy xDM 的 row-level security、SAP MDG 基于公司代码/组织的数据权限。缺了记录权限，多组织企业只能靠"给所有人全域权限"来干活，等于没有权限。

### 4.4 权限码全集（[Target]，对齐 `{domain}:{resource}:{action}`）

| 域 | 权限码 | 说明 | 归属 |
|----|--------|------|------|
| 平台域 | `masterdata:template:read` / `masterdata:template:write` | 域模板与版本 | 仅平台管理员 |
| 平台域 | `masterdata:governance:read` | 跨租户治理看板 | 仅平台管理员 |
| 租户域 | `masterdata:entities:read` / `:write` | 实体定义（**已登记，maturity=Target**） | Owner / Steward |
| 租户域 | `masterdata:fields:read` / `:write` | 字段扩展 | Steward |
| 租户域 | `masterdata:category:read` / `:write` | 分类体系 | Steward |
| 租户域 | `masterdata:records:read` / `:write` | 记录录入与导入 | Contributor / Steward |
| 租户域 | `masterdata:records:publish` | 发布（版本 + 生效） | Owner |
| 租户域 | `masterdata:records:approve` | 审批变更申请（SoD） | Approver |
| 租户域 | `masterdata:quality:read` / `:write` / `:execute` | 规则、执行质检 | Steward |
| 租户域 | `masterdata:issue:write` | 质量整改闭环 | Steward |
| 租户域 | `masterdata:subscription:read` / `:write` | 消费订阅与分发 | Consumer / Owner |
| 租户域 | `masterdata:steward:assign` | 任命 Owner / Steward | Owner |
| 租户域 | `masterdata:lineage:read` | 血缘追溯 | 全部租户内用户 |

#### UC-MD-P4 跨租户治理巡检 **[Target]**

> v1.0 只给了指标名没给算法，"质量分"无法落地计算。v1.1 补齐定义（口径统一，否则各租户各算各的、无法横向对比）。

| 指标 | 定义（算法） | 目标值 | 说明 |
|------|-------------|--------|------|
| **完备率** | 已填字段数 / 应填字段数（按实体字段的 required 计） | ≥ 95% | 逐记录算再取均值 |
| **唯一率** | 1 − 重复组内冗余记录数 / 记录总数 | ≥ 99% | 依赖 UC-T6（Vision 期用编码重复近似） |
| **合规率** | 通过全部质量规则的记录数 / 参检记录数 | ≥ 98% | 按最近一次质检任务计 |
| **及时率** | SLA 内完成更新的记录数 / 应更新记录数 | ≥ 90% | SLA 按域配置（默认 3 个工作日） |
| **质量分** | `0.3×完备率 + 0.3×合规率 + 0.2×唯一率 + 0.2×及时率` | 分域展示 | 权重可配；跌穿阈值触发告警（详设 §0） |
| **采用率** | 被 ≥1 个应用订阅的主数据域数 / 已发布域数 | 越高越好 | **衡量主数据"有没有人用"的关键指标** |
| **分发成功率** | 分发成功次数 / 分发总次数 | ≥ 99.5% | 失败进 `bone-integration` 死信 |

看板维度：租户数 × 主数据域数、记录总量、质量分趋势、待发布变更数、逾期未整改工单数、订阅应用数。

| 关键约束 | **禁止**主数据模块直连外部库（ADR-0017 决策 4） |

#### UC-MD-T9 质量整改闭环 **[Target]**

质检失败明细 → 生成整改工单（指派 Steward、期限、状态）→ 整改 → 复检 → 关闭；未关闭工单在实体看板红点提示，作为发布的软门禁（L3 为硬门禁）。

#### UC-MD-T10 模型漂移对账 **[Target]**（v1.1 新增，补元数据↔主数据的串联断点）

| 项 | 内容 |
|----|------|
| 参与者 | 系统 Job + Steward |
| 前置 | 主数据实体由 `convert` 从 `meta_entity` 生成（UC-T1 主流程 B） |
| 主流程 | ① 定时比对 `md_entity`(及其字段) 与源 `meta_entity` 的结构差异 → ② 生成漂移清单（新增字段 / 删除字段 / 类型变更 / 改名）→ ③ 在实体详情「模型同步」Tab 提示 → ④ Steward 逐项选择「同步 / 忽略 / 标记为本域自定义」→ ⑤ 同步动作按 ADR-0017 字段策略执行（新增=追加非必填；删除=**软禁用**不物理删；类型破坏性变更=**阻断并告警**） |
| 关键约束 | **禁止自动同步**——结构变更会影响已发布记录与下游订阅方，必须人工裁决并做影响分析 |
| 串联出口 | 与 UC-T1 构成闭环：T1 是一次性转换，**T10 是持续对账**；二者缺一，主数据就会随元数据演进而静默腐化 |

## 6. 端到端流程串联（四条主线）

### 流程 A：从模板到可消费（主数据域建设全链路）—— 把割裂的功能串成一条线

```
平台管理员                        Data Owner / Steward                    消费应用
──────────                       ───────────────────                    ────────
UC-P1 域模板 + 规则包
UC-P2 版本发布 ──模板──▶ UC-T1 域实例化（模板 / convert）
                         UC-T2 任命 Owner+Steward、配治理策略
                         UC-T3 分类体系搭建
                         UC-T4 质量规则绑定
                         UC-T5 记录采集（录入/导入/集成接入）
                         UC-T6 去重合并 → 黄金记录
                         UC-T4 执行质检 ──不合格──▶ UC-T9 整改闭环 ──┐
                                  ▲                                  │
                                  └────────── 复检 ◀────────────────┘
                         UC-T7 变更申请→审批→发布（版本+生效期）
                                  │
                                  └──发布事件──▶ UC-C1 订阅
                                                 UC-C2 消费取数
                                                 UC-C3 变更事件
UC-P4 治理巡检 ◀──质量分/采用率──────────────────────────────────────┘
```

**关键串联点**：
1. **UC-T1 是唯一入口**：无论从模板还是从元数据 convert，之后流程完全一致——这是消除"两条路各走一半"的关键。
2. **UC-T2 治理策略是总开关**：`workflow_enabled` / `is_versioning` 决定后续是否走审批与版本——DDL 列已存在，接上即可。
3. **UC-T4 ⇄ UC-T9 是质量闭环**：质检不是终点，整改复检才是。As-Is 断在"生成报告"这一步。
4. **UC-T7 → UC-C* 是价值兑现点**：不发布、不分发，主数据就等于没建。
5. **权限码是全程通用语言**：`masterdata:*` 在 §4.3 生产 → 各 Handler `@PreAuthorize` 执行。

### 流程 B：日常治理闭环（周期性）

```
定时 Job：执行质检 → 生成任务/报告 → 失败项转整改工单 → 指派 Steward
  → Steward 整改 → 复检通过 → 工单关闭 → 质量分回升 → 看板更新
  → 质量分跌穿阈值 → 写 bone-integration 死信 + 通知（详设 §0 Target）
```

### 流程 C：变更与审批（SoD）

```
业务变化（如客户更名）→ Contributor 提变更（DRAFT）
  → Steward 完善并提交审批（PENDING_APPROVAL）
  → Approver 审批（非提交者本人）→ APPROVED
  → Owner 发布（新版本 + 生效期）→ PUBLISHED，旧版 SUPERSEDED
  → 发布事件 → 订阅应用增量更新 → 审计留痕
```

### 流程 D：消费侧接入

```
应用开发者：应用详情「订阅主数据」→ 选域 → Owner 批准
  → 配置集成连接器（bone-integration）→ 联调取数（UC-C2）
  → 订阅变更事件（UC-C3）→ 运行期监控分发成功率
```

### 7.1 G1 裁定：收敛到 `mdm_*`（推荐结论）与四步执行路径

> v1.0 只写了"二选一"未给出确定性结论与路径，v1.1 补齐。

**为什么选 `mdm_*`（而不是承认 `md_*` 为真源）**：

| 判据 | `mdm_*` | `md_*`（现状运行表） |
|------|---------|---------------------|
| **版本/生效期** | `mdm_record` 有 `is_current` / `effective_from` / `effective_to` / `version_number` / `parent_record_id` | **全无**——UC-T7（版本+生效期）无法落地 |
| **治理策略** | `mdm_entity` 有 `is_versioning` / `workflow_enabled` | 无——UC-T2 治理等级无列可写 |
| **软删 / 乐观锁** | 多数表带 `deleted` + `version` | `md_record` **两者皆无**（基线亦判定缺失） |
| **文档一致性** | 详设 §4、DDL §8、ADR-0017 均已声明 `mdm_*` 为真源 | 若选它，须回改详设 §0/§4 与 ADR-0017 |
| **命名规约** | `mdm_` 与平台命名族一致 | `md_` 前缀易歧义（Markdown 等） |

**⚠️ 收敛的必要补充（v1.0 漏项）**：`mdm_*` 八表中**没有字段表**，但主数据确有独立字段定义（`MasterDataField` → `md_field`，ADR-0017 亦提及"追加 `mdm_field`"）。→ 收敛时必须**新建 `mdm_field` 表**，否则字段无处安放。

**四步路径（expand/contract，生产走迁移脚本）**：

| 步 | 动作 | 环境 |
|----|------|------|
| ① **Expand** | `bone-init.sql` 补齐：`mdm_entity` + `template_id`/`owning_app_id`/`domain_code`/`governance_tier`；`mdm_record` + `deleted`/`version`；**新建 `mdm_field`** | 真源 DDL（L3 审批） |
| ② **Migrate** | `scripts/migration/{ver}_masterdata_mdm_convergence.sql`：`md_entity`→`mdm_entity`、`md_field`→`mdm_field`、`md_record`→`mdm_record`（`data` JSON → `current_data`；status 映射；`version_number=1`），保留 ID 映射对照备查 | **生产增量** |
| ③ **Switch** | 8 个聚合的 `@Table` 切换（2 个已在 `mdm_*`）；**API 契约不变，前端无感** | 代码 |
| ④ **Contract** | 确认无引用后从 DDL 移除 `md_entity` / `md_field` / `md_record` | 真源 DDL |

> **更正 v1.0 的错误论证**：v1.0 曾以 modules/README「无增量迁移：改表即改 init，开发库 DROP DATABASE 后重建」为由，认为收敛成本极低。**该论证只适用于开发环境**——Bone 另有《[ADR-生产数据库增量迁移策略](../../architecture/adr/ADR-生产数据库增量迁移策略.md)》，生产必须走 expand/contract 迁移脚本（大表用 gh-ost / pt-osc）。收敛仍需排期与备份，不可当作"顺手改"。

**实施批次建议**：
- **批次 1（P0）**：G1 裁定 + G2 统一 + G3 归属建模（含 DDL 变更 L3 审批、`mvn test` + ArchUnit + 基线自证）
- **批次 2（P1，低风险高感知，不依赖 G1 可先做）**：G6 权限码 + G8 文档补登记 + G12 基线刷新
- **批次 3（P1，依赖批次 1）**：G7 导航重组 + G4 分类 + G9 模板 + G5 审批发布（须先落地 §4.3 治理等级）+ G10 订阅分发 + G16 模型对账
- **批次 4（P2，随迭代）**：G11 质量闭环 + G13 多租户规范补充 + G15 参考数据 + G17 反向反馈
- **[Vision]**：G14 去重与黄金记录合并

> **依赖红线**：G7 / G4 / G9 / G5 全部依赖 G1 收敛后的实体模型——**未裁定就做导航重组与分类体系，等于在漂移的地基上盖楼**（v1.0 把 G7 与 G1 分在两批却未标注依赖，此处更正）。

| **持续对账而非一次性复制** | ADR-0017 阶段二（事件同步 + 定时对账）；Informatica 的 model drift detection | UC-T10（G16） |
