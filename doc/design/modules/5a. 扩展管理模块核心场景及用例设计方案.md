## 1. 要回答的四个问题（结论先行）

### 1.1 扩展管理与租户的关系是什么？—— **行级隔离已有、路由第一维已有，但租户码无校验、权限未随租户分层**

| 层 | 内容 | 归属 | As-Is 证据 | 裁决 |
|----|------|------|-----------|------|
| 扩展点契约 | 接口 FQCN、业务域、分类 | **平台可预置（tenant_id=0），租户可自建** | `exts_extension_point.tenant_id` DEFAULT 0，`uk(tenant_id, point_code)` | 保持；平台预置首批扩展点 [Target] |
| 扩展实现（插件）+ 制品 + 路由配置 | 实现类、JAR 版本、维度、灰度 | **租户（行级隔离）** | `exts_extension_impl` / `exts_plugin_version` 均含 `tenant_id` | 保持 |
| 路由租户维度 | 按租户码分流到不同实现 | `exts_extension_impl.tenant_code` 参与四级路由第一级 | `DefaultExtensionPointRouter` 精确匹配 + `BizContext.tenant` | 保持 |

**两处 As-Is 缺口**：

1. **租户码无一致性校验**：`tenant_code` 默认 `'DEFAULT'`，登记时不校验是否为 `'*'`（通配）或存在的 `iam_tenant.code`。填错不报错，只是该租户路由永远不命中，靠 `is_default` 兜底掩盖——排错成本高（详设 §4.2 排错索引第一条就是这个问题的表象）。→ **[Target] G2：登记校验 + `'DEFAULT'` 迁移**。
2. **权限未随租户分层**：JWT Scope `extension:points:read|write`、`extension:plugins:deploy` 是全局能力位，不区分「平台管理员」与「某租户管理员」，也没有与 `bone_app_permission`（应用内 ADMIN/DEVELOPER/VIEWER）联动。→ **[Target] G3：权限分层**（§4）。

### 1.2 扩展管理与应用的关系是什么？—— **As-Is 没有任何关系，这是模块割裂的根源**

| 维度 | As-Is 事实 | 说明 |
|------|-----------|------|
| `exts_*` 有 `app_id` / `module_id`？ | **无** | 全表检索（`bone-init.sql` §5）无任何应用/模块列 |
| `BizContext` 有应用维度？ | **无** | 固定维度仅 `tenant / bizCode / useCase / scenario / env / userGroup`（`BizContext.java`）；`bizCode` 语义未与 `bone_application.code` 建立约定 |
| 控制台有应用视角？ | **无** | 概览 / 扩展点 / 插件 / 依赖图 / 市场 / 观测页平铺，回答不了「应用 X 用了哪些扩展点、哪些实现、路由是否生效」 |
| 市场安装装到哪？ | **无答案** | `POST /marketplace/{itemId}:install` 安装后的实现不归属任何应用 |

**正解：把「应用」补为扩展实现的一级归属**（§3.2 详述），与主数据姊妹篇的「建模来源 / 责任归口 / 消费订阅」三分法同构：

- **宿主载体**（继承，间接）：实现类随哪个宿主 JVM 发布（classpath 边界，详设 §4.2 热部署边界），回答「代码在哪运行」
- **责任归口**（新增，直接）：`exts_extension_impl.app_id → bone_application.id`，回答「谁开发、谁对它负责」，**可空**（平台通用插件）
- **路由维度**（约定，新增）：`biz_code` 显式约定为 `bone_application.code`（或 `BizContext` 新增 `app` 固定维度，二选一见 §10），回答「给哪个应用生效」

### 1.3 谁能用扩展管理？—— **四类人 + 一个系统参与者，As-Is 只有裸 Scope**

| 角色 | 业界对应 | 能做什么 | 不能做什么 | As-Is 载体 |
|------|---------|---------|-----------|-----------|
| **平台管理员 / 架构师** | SAP 平台层（BAdI 定义者）、Shopify 平台 | 定义扩展点契约、维护市场目录、跨租户巡检 | 不代租户配路由、不写租户实现 | JWT Scope + `is_admin` |
| **应用开发者**（含 ISV） | SAP 增强开发者、Salesforce Package 开发者、Forge 应用开发者 | 开发 `@Extension` 实现、上传 JAR、部署、绑定扩展点、配灰度，**限本应用** | 不碰其他应用的插件、不定义平台契约 | `extension:plugins:deploy`（当前不限应用，见 G3） |
| **租户管理员** | Salesforce Org Admin、钉钉/飞书组织管理员 | 安装市场插件 [Target]、启停、配路由维度与参数、看执行与审计 | 不上传制品、不改契约 | ❌ 当前无独立权限位 |
| **运维 / SRE** | 平台 SRE | 观测执行日志、指标 [Target]、按排错索引处置、执行回滚 | 不改路由语义 | `extension:*:read` |
| **宿主系统**（系统参与者） | 数据面 | 经 SDK 按 `BizContext` 路由调用、上报执行日志 | — | `:ingest` Scope |

### 1.4 模块定位是什么？—— **元数据管结构、主数据管实例、扩展管差异逻辑**

一句话定位：

> **扩展管理模块是 BONE 平台「差异逻辑」的权威治理入口：把业务链路中因租户、行业、场景而变化的算法与流程，收敛为稳定扩展点契约 + 可治理的多实现路由，让差异在不动核心代码、不复制实体的前提下按维度生效。**

三个必须回答的边界问题：

| 边界 | 结论 |
|------|------|
| **扩展 vs 元数据** | 元数据管「模型与 CRUD 路径」；扩展管「行业算法与流程差异」（详设 §1.0）。为字段差异复制实体是反模式（详设 §1.5 设计门禁） |
| **扩展 vs 集成** | 扩展点解决**进程内**同步差异（计价、校验、路由）；跨系统数据交换一律走 `bone-integration`；禁止用 MQ 事件替代扩展点接口（详设 §4.5） |
| **ExtPoint vs Plugin Runtime** | 两个层级不得混淆（详设 §4.4 红线 EXT-PL-01）：第一阶段只做 ExtPoint（SPI / 路由 / 灰度）；独立 ClassLoader、沙箱属 Plugin Runtime 独立方案，不并入本模块用例主线 |

## 2. 定位、能力链与准入标准

### 2.1 七段式能力链（这就是「串联」的骨架）

```
平台层            ① 契约定义（扩展点登记）        ← 平台管理员 / 架构师
                    │
开发侧            ② 开发实现 → ③ 制品上传 → ④ 部署绑定   ← 应用开发者
                    │ （状态机：UPLOADED→VALIDATED→STAGED→ACTIVE→DEPRECATED）
租户侧            ⑤ 路由配置与灰度（维度 / 默认实现 / traffic）  ← 租户管理员
                    │ （publish-runtime = 生效切换点）
观测侧            ⑥ 执行观测 → ⑦ 回滚 / 卸载 / 废弃      ← 运维 / SRE
                    │
分发 [Target]     市场目录 → 一键安装 → 回到 ③④⑤        ← 租户管理员
```

| # | 能力 | 内容 | As-Is |
|---|------|------|-------|
| ① | 契约定义 | 扩展点登记（FQCN、业务域、分类）、启停 | ✅ |
| ② | 开发实现 | `@Extension` + 维度注解，随宿主发布 | ✅（SDK 侧） |
| ③ | 制品上传 | JAR 上传、SHA-256、状态机、版本保留 | ✅（含 magic-number / `deployment_status` DDL，见附录 C） |
| ④ | 部署绑定 | `:deploy`（LRO）→ `:bind` → `:publish-runtime` | ✅ |
| ⑤ | 路由灰度 | 四级路由 + `traffic` 稳定分桶 + `strict-mode` 兜底 | ✅ |
| ⑥ | 执行观测 | 执行日志游标、审计、[Target] RED 指标 | 部分 |
| ⑦ | 回滚废弃 | `:rollback` / `:undeploy` / Deprecated | ✅ |
| ⑧ | 市场分发 | 静态目录 + `:install`；远端 OCI [Vision] | ✅ v1（安装后归属断链，见 G5） |

### 2.2 准入标准：什么才配做成扩展点（防止「万物皆 ExtPoint」）

| 判据 | 说明 |
|------|------|
| **差异真实存在** | 至少预见 2 个租户 / 场景需要不同实现；单实现逻辑直接写在领域服务里 |
| **契约稳定** | 接口只允许 additive 演进；频繁变化的入参出参不配做扩展点 |
| **性能可控** | 位于业务主链路、有超时与舱壁预算（`ExtensionExecutionGuard`） |
| **可用元数据/配置表达的不做** | 字段级差异、开关型差异用元数据引擎或 `config_json` 表达，不建扩展点（详设 §1.5 反模式） |

> 典型 Bone 扩展点：促销计价、审批会签、行业 BOM 展开逻辑、单据编号规则、出口报关字段映射。
> 反例：把「是否开启审批」做成扩展点（配置开关即可）；把「某个字段取值公式」做成扩展点（元数据表达式即可）。

## 3. 关系模型设计（解决「与租户、应用到底是什么关系」）

### 3.1 租户两层模型

```
平台层 (tenant_id = 0)
  exts_extension_point   平台预置扩展点契约（促销计价、审批会签、编号规则…）
        │
        │ 租户引用 / 自建
        ▼
租户层 (tenant_id > 0)
  exts_extension_impl    扩展实现（路由维度 + config_json，行级隔离）
  exts_plugin_version    制品版本（JAR + checksum + 状态机）
  exts_plugin_execution_log / exts_audit_log   执行与审计（行级隔离）
```

**核心规则**：
1. 扩展点契约**优先平台预置**（`tenant_id=0`），租户可自建——与主数据「模板平台供、实例租户建」同构；首批平台扩展点清单见 §5.1 UC-EX-P1。
2. 实现、制品、路由配置**永远归租户**；`tenant_code` 是路由维度而非归属字段（归属看 `tenant_id`）。
3. [Target] `tenant_code` 登记时校验为 `'*'`（通配）或存在的 `iam_tenant.code`（G2），消除「填错码 → 永不命中 → 靠默认实现掩盖」的静默故障。

### 3.2 应用三级关系（宿主载体 / 责任归口 / 路由维度）

| 语义 | 载体 | 基数 | 回答的问题 | 层级 |
|------|------|------|-----------|------|
| **宿主载体** | 实现类所在宿主 JVM（`@EnableExtensionPoints` + classpath） | 1:1（只读事实） | 代码在哪运行 | As-Is |
| **责任归口** | `exts_extension_impl.app_id → bone_application.id` | N:1，**可空**（平台通用插件） | 谁开发、谁负责 | [Target] 新增 |
| **路由维度** | `biz_code = bone_application.code` 约定（或 `BizContext` 新增 `app` 维度，§10 裁决） | N:1 | 给哪个应用生效 | [Target] 约定 |

> 三者互不替代：一个「促销计价实现」可以**运行在**订单宿主、**责任归口**是营销应用、**生效于** biz_code=`marketing` 的调用。补齐后，「这个插件属于哪个应用、给谁用」才答得出来。

**与控制台导航的关系**：详设 §2 现有页面（概览 / 扩展点 / 插件 / 依赖图 / 市场 / 观测）保持不变，[Target] 在**应用详情页新增「扩展」Tab**（UC-EX-G5）：本应用扩展点 → 实现 / 版本 / 状态机 → 路由与灰度 → 执行健康。这是把割裂功能串到应用视角的那根线。

### 3.3 DDL 变更建议（真源 `bone-init.sql`，变更走 L3 审批 + expand/contract）

| 表 | 变更 | 用途 | 优先级 |
|----|------|------|--------|
| `exts_extension_impl` | 加 `app_id BIGINT NULL` + 索引 | 责任归口（§3.2） | P0 |
| `exts_extension_impl` | `tenant_code` 登记校验（应用层校验 + 注册 Handler 查 `iam_tenant.code`） | G2 一致性 | P0 |
| `exts_extension_point` | 加 `contract_version VARCHAR(20)`（SemVer） | 契约演进可追溯（G6） | P2 |
| 市场表 | 维持 [Vision]（`ext_marketplace_item` 须先 ADR，详设 §6.1 命名脚注） | — | — |

> ⚠️ 上表**不是 SQL 副本**；落地一律改 `bone-init.sql` 真源。生产迁移按《ADR-生产数据库增量迁移策略》走 `scripts/migration/`（3a 姊妹篇 §7.1 同款路径）。

## 4. 参与者、角色与权限码

### 4.1 权限码全集（[Target]，对齐 `{domain}:{resource}:{action}`）

| 域 | 权限码 | 说明 | 归属 |
|----|--------|------|------|
| 租户域 | `extension:points:read` / `extension:points:write` | 扩展点读 / 增删改启停（As-Is） | 架构师 / 平台管理员 |
| 租户域 | `extension:plugins:read` / `extension:plugins:write` | 实现元数据读 / 写（**新增**，当前 write 未拆分） | 应用开发者 |
| 租户域 | `extension:plugins:deploy` | 上传 / 部署 / 回滚 / 卸载（As-Is） | 应用开发者 |
| 租户域 | `extension:runtime:publish` | `:publish-runtime` 生效切换（**新增**，部署 ≠ 生效，SoD 点） | 租户管理员 |
| 租户域 | `extension:plugins:bind` | `:bind` / `:unbind`（**新增**，拆出独立码） | 应用开发者 / 租户管理员 |
| 租户域 | `extension:observe:read` | 执行日志 / 审计 / 指标（**新增**） | 运维 / 全部角色 |
| 租户域 | `extension:marketplace:install` | 市场安装（**新增**） | 租户管理员 |
| 平台域 | `extension:marketplace:manage` | 市场目录维护（**新增**） | 平台管理员 |

**关键设计——部署与生效分离 [Target]**：As-Is 的 `:deploy` 一步完成「置 `is_active` + 推送运行时元数据」，即**部署即生效**，`:publish-runtime` 只是重复推送。本方案把两者拆开：`:deploy` 只把制品推进到 `STAGED`，`:publish-runtime` 才切 `ACTIVE` 并推送路由——部署是开发者动作，让路由对真实流量生效是租户管理员动作（Salesforce「包安装」与钉钉「管理员启用应用」共同的分界，也是多租户平台 SoD 的最低要求）。**落地依赖状态机联动改造**：`deployment_status` 列已建（附录 C `deployment-status-ddl`），但 `:deploy` 语义须从直达 `ACTIVE` 改为停在 `STAGED`，属行为变更——迁移期提供兼容开关（默认保持 As-Is），切流后分权生效，并同步修订既有契约测试（`ExtensionApiLroTest` 等）。

**环境晋升约束（沿用详设 §7.1 [Target]）**：生产环境禁 `:upload`，仅允许 `:deploy` / `:publish-runtime`——制品进入生产必须经环境晋升（dev → test → prod），租户管理员不直接向生产上传 JAR。

> **落地注意**（IAM 姊妹篇 UC-P3 踩过的坑）：新增权限码须同步 ① `iam_permission` 种子 ② `DefaultPermissionCodes.adminFallback()` ③ `bonePermissionCodes.ts` catalog ④ 变更绑定后清 `AccountAuthorityCache`。

### 4.2 角色与 `bone_app_permission` 的映射 [Target]

| 扩展角色 | 判定来源 | 说明 |
|---------|---------|------|
| 应用开发者（本应用插件） | `bone_app_permission.role ∈ {ADMIN, DEVELOPER}` 且插件 `app_id` = 该应用 | 应用内自洽，无需新表 |
| 租户管理员 | 租户域角色（IAM） | 可操作本租户全部扩展资源 |
| 平台管理员 | `is_admin` | 跨租户巡检与市场目录 |

> 无需新建「扩展角色表」——应用级权限复用 `bone_app_permission`，租户级复用 IAM 角色，仅补权限码即可。这与 3a 姊妹篇「Steward Scope」不同：扩展的隔离粒度是应用/租户两级，暂无记录级诉求。

## 6. 端到端流程串联（三条主线）

### 流程 A：从契约到生效（主链路）—— 把割裂的功能串成一条线

以「促销计价」为例（对齐详设 §1.5 场景表）：

```
平台管理员/架构师                应用开发者                          租户管理员
──────────────                ──────────                        ──────────
UC-EX-P1 登记 OrderPricingExtPoint
（FQCN + 业务域 + 超时预算）
        │
        └──契约──▶ UC-EX-D1 实现 @Extension（standard / tenant-T 定制两个实现）
                   UC-EX-D2 上传 JAR（UPLOADED→VALIDATED）
                   UC-EX-D3 :deploy + :bind 扩展点
                            │
                            └──部署就绪──▶ UC-EX-T1 核对维度（tenant_code=T、biz_code）
                                           :simulate 模拟命中
                                           UC-EX-T2 灰度 traffic 5→50→100
                                           :publish-runtime（生效切换点）
                                                   │
                                                   ▼
                              宿主业务链路：BizContext(tenant=T, bizCode=…)
                              → SDK 四级路由 → 定制实现命中
运维/SRE：UC-EX-G1 观测失败率/耗时；UC-EX-G3 异常回滚；UC-EX-G4 废弃旧实现
```

**关键串联点**：
1. **UC-EX-P1 是唯一契约入口**：实现、绑定、路由全部以扩展点 FQCN 为锚，契约不登记后面全断。
2. **部署 ≠ 生效 [Target]**：As-Is `:deploy` 即生效；分离后 `STAGED` 只是制品就绪，`:publish-runtime` 才把路由推给数据面（§4.1，须状态机联动改造与兼容开关）。
3. **状态机是骨架**：`UPLOADED→…→DEPRECATED` 每一步对应一个用例的动作，控制台状态机可视化页就是这条线的进度条。
4. **租户维度是生效开关**：`tenant_code` 校验（G2）保证「给谁生效」不再靠默认实现兜底掩盖。

### 流程 B：同点多实现（租户定制 + 兜底）

```
标准实现（is_default=true, tenant_code='*'）      ← 平台通用，永远兜底
租户 T 定制实现（tenant_code='T'）                ← 四级路由第一级精确命中
新行业实现（condition 表达式 / scenario 维度）     ← 表达式级或场景级分流
→ strict-mode=false 时四级均未命中再兜底最宽泛实现（详设 §4.3）
```

### 流程 C：市场安装 [Target]

```
平台运营目录（UC-EX-P2）→ 租户浏览 → :install → 选归属应用（G1）
→ 免上传实例化 → 复用 UC-EX-D3→T1 主链路 → 生效 → 纳入 UC-EX-G5 应用扩展视图
```
