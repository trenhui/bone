# 13. 工作流设计器方案（前端设计器 · 设计态写路径 + 试运行）

> 版本：v1.0 · 2026-10-27
> 关联：`12. 工作流引擎设计.md`（引擎内核与 BONE 集成层）、迁移 `0065_wf_process_draft.sql`
> 状态：**M0 已落地并随 `dev` 提交推送**；可视化画布与 REST 层尚未做（见 §8、§9）

---

## 0. 一页结论

- **建议做，但范围必须收敛**：采用 **受限主轴 + 分支槽（constrained main-axis + branch slots）** 模型，**不做自由画布**。自由画布（任意连边的无限画板）会让图一致性、布局、撤销/重做、持久化变成无底洞，绝大多数自研设计器都止步于此。
- **设计器的前置不是画布，而是设计态写路径 + 试运行**：业务方改一个审批人不必再发版；配错的条件/兜底边/指派参数能在发布前用样例数据跑出来。
- **M0 已落地**：设计态写路径（草稿/校验/发布/上下线/版本查询）、纯函数试运行器、前端 `workflow-dsl` 包（`FlowDoc` 文档树 ↔ 引擎 DSL 的 `compile`/`parse`）。
- **明确不做**：可视化画布 UI、REST Controller（需先定宿主应用的 HTTP 层）、并行分支、变量快照 / 事件台账。

## 1. 定位与动机

### 1.1 痛点

`0056` 落地后 `wf_process_def` 只有**读路径**（仓储注释明确「v1 无发布写路径」）。流程定义只能靠迁移脚本 / 种子数据落库——业务方改一个审批人、调一个条件阈值，就要走一次发版流程。设计器要解决的就是这条「业务可编辑」的链路。

### 1.2 为什么先做写路径与试运行，而不是画布

画布是设计器的「皮」，没有后端写路径，画布产出的 JSON 无处落地；没有试运行，画布再漂亮也发现不了「单据流到错误审批人」这类静默事故。因此 M0 把**写路径 + 试运行 + DSL 编译层**做扎实，可视化画布作为 v2 叠加。

### 1.3 业界对标（设计取舍的来源）

| 来源 | 借鉴点 |
|------|--------|
| 宜搭 / 钉钉 / 飞书审批流 | 流程本质是**线性主轴 + 固定槽位**的条件分支，而非自由 DAG；用户配置「槽位」而非「连线」 |
| BPMN 2.0 `BPMNDiagram`（DI 段） | 布局（坐标）与语义（流程）**同存一个 artifact、同版本同回滚**；引擎解析时忽略 DI 段，不会出现「定义回滚了、坐标没回滚」的错位 |
| 低代码表单设计器（Schema-driven） | 前端编辑**结构化文档树**，由编译器摊平为引擎格式；结构不变量在类型层成立，而非靠运行时校验兜底 |

## 2. 核心设计取舍（业界最佳实践）

| 维度 | 本方案选择 | 反模式（不做） | 理由 |
|------|-----------|----------------|------|
| **画布形态** | 受限主轴 + 分支槽 | 自由画布（任意连边） | 避免图一致性 / 布局 / 撤销重做的无底洞 |
| **前端数据模型** | 编辑 `FlowDoc` 文档树 | 直接编辑 `{nodes, edges}` | 文档树天然版本化、可 diff；「在中间插入节点」这类操作在图模型里要手写图算法 |
| **编译** | `compile()` 把树摊平为 DSL | 前端直接构造图 | 不变量由结构保证（见 §4.1），不需要校验兜底 |
| **反解析** | `parse()` 快路径直接读 `ui.flowDoc` 原文 | 图 → 树反推算法 | 单出口 DAG 反推成树在一般情况下多解，反推 shaky |
| **校验归属** | **后端权威**，前端只投影清单 | 前后端各写一份规则 | 两份规则必然漂移，且漂移方向不可控 |
| **草稿** | 可脏（保存即返回违规作提醒） | 草稿必净 | 业务人员总有中间态，草稿不该被校验挡住 |
| **发布** | 不可变版本快照，fail-closed 拒绝违规 | 版本行可变 | 在途实例按启动时钉住的 `def_version` 装载，版本行可改会漂移审批依据 |
| **试运行** | 复用引擎同一套求值器 | 另写一套简化逻辑 | 否则「模拟说走 A、实际走 B」，比不做更糟 |
| **坐标存储** | `definition_json` 存**原文**（含 `ui` 段） | 反序列化后重新序列化 | 重序列化会静默丢弃引擎不读的 `ui` 段，表现为每次发布后版式归零 |

## 3. 数据模型：`FlowDoc` ↔ 引擎 DSL

### 3.1 引擎 DSL（`WorkflowDefinitionJson`，引擎唯一真源）

```
WorkflowDefinitionJson {
  key: string
  name?: string
  version: number
  engineSchemaVersion: number   // 当前 = 1，与前端 ENGINE_SCHEMA_VERSION 对齐
  nodes: DefinitionNode[]
  edges: DefinitionEdge[]
  assignments: Record<nodeCode, AssignmentRule[]>
  ui?: UiSection                 // 引擎不读，仅设计器用
}
```

- `NodeType`：`START | APPROVE | CONDITION | CC | END`
- `ApprovalMode`：`SINGLE | ALL | ANY | RATIO`（注意：**无 `AUTO`**，`AUTO` 是适配器里 `mode == null` 的映射）
- `AssignmentStrategy`：`LINE_MANAGER | DEPT_HEAD | LEVEL_UP | ROLE | USER | FIELD | INITIATOR_SELECT`
- **各策略在 `params` 的必需键（`PARAM_KEY_BY_STRATEGY`，前后端单真源）**：

  | 策略 | 必需参数键 | 踩坑点 |
  |------|-----------|--------|
  | `LINE_MANAGER` | 无 | — |
  | `DEPT_HEAD` | 无 | — |
  | `LEVEL_UP` | `level` | — |
  | `ROLE` | `roleCode` | — |
  | `USER` | `userId`（**单数**） | 写成 `userIds` 后端读到 `null` → 解析空列表 → 节点静默挂起 |
  | `FIELD` | `fieldCode` | — |
  | `INITIATOR_SELECT` | `fieldCode` | — |

- `ConditionAtom` 的 13 个算子：`isNull / isNotNull / eq / neq / gt / gte / lt / lte / in / notIn / between / earlierThan / laterThan`，与后端 `StructuredConditionEvaluator` **逐一对应，不得扩展**。

### 3.2 设计器文档树（`FlowDoc`）

```
FlowDoc { key, name, steps: Step[] }

Step =
  | ApproveStep { kind:'approve', code, label, mode:ApprovalMode, quorum?, rules:AssignmentRule[] }
  | CcStep      { kind:'cc',      code, label,                  rules:AssignmentRule[] }
  | ConditionStep {
      kind:'condition', code, label,
      branches: Branch[],        // 显式分支（≥1）
      defaultBranch: Branch      // 必存在，编译时固定排在出边末位
    }

Branch { id, label, when: Condition | null, body: Step[] }   // when=null ⇒ 默认边(else)
```

**不变量由结构保证，而非校验兜底**：`ConditionStep` 必有 `defaultBranch` ⇒ 编译出来必然「恰一条默认边且在末位」；`START`/`END` 刻意不出现在文档树里（发起节点唯一 `WF-002`、结束节点至少一个 `WF-003`，二者都不该是用户可编辑对象），由编译器自动补。

### 3.3 引擎不读的 UI 段（`UiSection`）

```ts
UiSection {
  layout?: Record<nodeCode, {x, y}>   // 画布坐标
  flowDoc?: FlowDoc                    // 文档树原文：parse 的精确来源
  collapsed?: string[]                 // 折叠状态
}
```

先例同 BPMN 的 DI 段：布局与语义同版本、同回滚。后端以 `FAIL_ON_UNKNOWN_PROPERTIES=false` 容忍它，并有契约测试钉死——否则将来谁换了严格 mapper，存量定义会集体读不回来。

## 4. 编译与解析（`compile` / `parse`）

### 4.1 `compile()`：文档树 → 引擎 DSL

**核心思路**：把「串并联」结构一次性摊平。每一层序列编译时先编译它的**后继（continuation）**，再让每个分支体指向同一个 continuation——这正是「分支汇合」语义，也让「空分支体」自然退化为「条件节点直接连到后续节点」，无需特殊分支处理。

**不变量由结构保证（不是靠校验兜底）**：

- 发起节点唯一、结束节点追加在末尾 ⇒ `WF-002` / `WF-003` 天然满足；
- 审批 / 抄送 / 发起节点各自恰一条出边 ⇒ `WF-014` / `WF-015` / `WF-018` 天然满足；
- 条件节点出边 = 显式分支（按序）+ 默认分支（末位）⇒ `WF-006` 天然满足。

编译器**不做业务校验**：`RATIO` 忘填 `quorum`、`ROLE` 忘填 `roleCode` 这类归后端统一裁决（`WF-019` / `WF-020`）。前端若自己判一遍必然与后端漂移。

**节点按遍历顺序重排**（`orderNodesByTraversal`）：递归编译天然产出「后继先入数组」的倒序，重排后同一份文档每次编译产出的 JSON 完全一致——这是 `compile(doc)` 可做结构相等断言、版本 diff 稳定的前提。

**写回 `ui.flowDoc`**（`keepFlowDoc` 默认 `true`）：为 `parse` 的快路径提供无损原文本。

### 4.2 `parse()`：引擎 DSL → 文档树（双路径，故意不对称）

| 路径 | 触发 | 结果 |
|------|------|------|
| **快路径** | 定义带 `ui.flowDoc`（设计器编译时写入） | 直接取回原文，**无损** |
| **慢路径** | 旧定义（迁移 / 种子数据，无 `ui.flowDoc`） | 按图结构重建，**有损**（`lossy:true` + 警告） |

慢路径的「图 → 树」反推用**各分支头可达集的交集**求分支汇合点——单出口 DAG 反推在一般情况下多解，这条路不可靠，因此返回 `lossy:true` 并附告警；**界面对有损定义必须禁用保存**，避免「打开旧流程、随手保存、分支被抹平」。

## 5. 后端权威校验（单一真源）

**前端不重写校验规则**：后端 `WorkflowDefinitionValidator` 有 20 条 `WF-xxx`，前端若照抄一份，两份规则必然漂移，且漂移方向不可控（要么「前端放过、后端拒绝」用户白填一遍，要么更糟「前端拒绝、后端放过」用户以为已修好）。

前端只做两件事：

1. 把后端返回的违规清单**按 `locator`（节点编码）分组**，点一下高亮到画布对应节点——不要靠解析 `message` 文本反推节点，那会让后端改一句文案就变成前端故障；
2. 为高频错误码补一句「怎么办」提示文案。

`validation.ts` 已内置的高频码提示：

| 错误码 | 含义 |
|--------|------|
| `WF-002` | 必须有且只有一个发起节点（系统自动生成） |
| `WF-003` | 末尾缺少结束节点，检查最后路径是否断头 |
| `WF-005` | 节点无后继，流程在此卡死 |
| `WF-006` | 条件节点需至少一条分支 + 一条默认边，默认边在最后 |
| `WF-007` | 审批节点必须配置审批人 |
| `WF-012` | 必须选择完成方式（单签/会签/或签/比例会签） |
| `WF-013` | 指派策略不在支持列表 |
| `WF-014` | 审批节点只能一条出边；分流改用条件分支 |
| `WF-018` | 抄送节点需配置抄送对象 |
| `WF-019` | 比例会签必须指定「至少 N 人通过」，N≥1 |
| `WF-020` | 指派策略缺少必填参数（角色/人员/字段），运行期解析不出人并挂起 |
| `WF-021` | 定义 JSON 无法解析（通常手工编辑出错） |

**草稿校验返回违规作提醒；发布 fail-closed 直接拒绝**——配错的流程绝不发布。

## 6. 设计态写路径（`WorkflowDefinitionCommandService`）

承载：草稿保存 / 校验 / 发布 / 上下线 / 版本查询。三条不可让步的纪律：

1. **草稿可脏、发布必净**：草稿保存时把违规**一并返回**作提醒；发布则 fail-closed 有违规即拒，绝不「先发上去再改」。
2. **JSON 原样存储**：`definition_json` 一律存调用方提交原文，**不**反序列化后重序列化，否则 `ui` 段被静默丢弃、发布后版式归零。
3. **版本号单调占位**：新版本号 = 该 key 现有最大版本 + 1（与上下线状态无关）；并发发布靠唯一键 `uk_wf_def_ver` 兜底而非 `SELECT MAX`——两人同时发布会撞号，唯一键把脏数据变成一次明确的失败。

**版本不可变**：`wf_process_def` 每行都是在途实例的审批依据（实例钉启动时的 `def_version`）。「回滚」的正确做法是**拿旧版内容发布成新版本**，而非把旧行改回启用——后者会让已发布 v3 突然变回 v2 内容。

**乐观锁 `revision`**：覆盖已有草稿必须携带读到的 `revision`，SQL 以 `AND revision = ?` 判定是否被他人覆盖，缺失即拒绝（避免「以为在改、其实覆盖别人」）。

**操作人必填**：写路径审计列必须回答「谁改的」，不接受匿名写入。

对外方法：`validate` / `findDraft` / `saveDraft(key, json, expectedRevision, operatorId)` / `discardDraft` / `publish` / `setEnabled` / `listLatest` / `listVersions` / `findVersion`。异常：`WorkflowDefinitionInvalidException`（发布校验不过）、`WorkflowDefinitionConflictException`（revision 过期 / 版本并发冲突，409）、`WorkflowDefinitionRequestException`（请求级错误）。

## 7. 试运行（`WorkflowSimulator` + `WorkflowSimulationService`）

**为什么是设计器里 ROI 最高的一块**：流程配错的三种典型形态——条件写反、兜底边指向错、指派策略参数拼错——共同点是**发布期语法检查全绿、运行期也不报错**，只是单据流到错误审批人、或原地挂起。这类问题只能靠「拿真实数据跑一遍」发现，看定义看不出、看线上日志也没人会去查一张已通过的单据。

**纯函数、零 IO、零副作用**：不建实例、不派单、不落库、不通知。

**复用引擎同一套求值器**（`WorkflowBranchEvaluator` / `WorkflowConditionEvaluator`）——模拟结论与实际运行结论同源。若模拟另写简化逻辑，就退化成「模拟说走 A、实际走 B」，比不做更糟。

**暴露发布前可见的三类问题**：

- 条件写反 / 兜底边指向错：`ConditionTrace` 逐分支记录命中/不成立；
- 指派参数拼错：`ApproverResolver` 真实解析，解析不出人则告警「运行期该节点会挂起」；
- 自审批守卫（D4）：解析到发起人本人时提示「运行期将触发自审批守卫并挂起」。

`WorkflowSimulationService.simulate(definitionJson, sampleData, initiatorId, entityCode, recordId)` 把仿真与审批人解析串起来，返回 `SimulationReport`（路径 / 分支判定明细 / 各节点解析出的审批人 / 违规清单 / 致命错误）。仿真器带防环上限（v1 不支持回环审批，超限即报错而非转圈）。

## 10. 风险与开放问题

1. **REST 宿主未定**：M0 只有领域服务与 SDK 仓储，没有 Controller。接入时需确定挂载的 Spring Boot 应用与鉴权方式。
2. **慢路径有损**：旧定义（无 `ui.flowDoc`）经 `parse` 重建会丢失分支结构细节，界面须对 `lossy` 定义禁用保存。
3. **画布形态待拍板**：本方案锁定「受限主轴 + 分支槽」，画布渲染的具体交互（拖拽 vs 表单式配置）需产品确认，但不影响 M0 的写路径与 DSL 层。
4. **`ui` 段向后兼容**：引擎以 `FAIL_ON_UNKNOWN_PROPERTIES=false` 容忍 `ui` 段，但需契约测试守住——任何改 mapper 严格度的动作都会让存量定义读不回来。
