## 1. 定位与业界对标

### 1.1 定位

把「审批流」做成 **BONE 平台的一等公民能力**：报销 / 采购 / 智能理赔 / HR / 财务共用同一套引擎与同一套持久化，各自只做「流程定义 + 少量配置」。

对标宜搭 / AppBuilder / 钉钉 / 飞书的业界实践：**审批流是表单/实体引擎的亲兄弟，共用实体、权限、审计**——而不是外挂一个通用 BPMN 引擎。严格遵循：

- **不引 Camunda / Flowable / Temporal**：平台 `dependencyManagement` 里虽有 `camunda-bom` 7.24.0，但来自已删除的遗留配置 `application-enterprise.yml`，全仓零 `org.camunda.*` 引用、未进 classpath；通用 BPMN 引擎与「零新依赖 + 元数据驱动 + 单一真源」纪律冲突。
- **不造通用 BPMN/DMN 引擎**：只做「实体数据驱动的分支状态机 + 角色指派」这一审批流专用子集。

### 1.2 业界对标

| 引擎 | 定义模型 | 持久化 | 平台集成形态 | 对本设计的启示 |
|---|---|---|---|---|
| Camunda 7 | BPMN 2.0 XML | 自有约 20 张表 + MyBatis | engine + spring-boot-starter | 定义版本化、实例钉版本；history 一等公民；job executor 异步重试 → 我们的 outbox 中继 |
| Flowable | BPMN 2.0 | 自有 + MyBatis/JPA | engine + spring starter | 启动器即集成点——佐证「不设桥接模块」 |
| jBPM | BPMN2 + 规则 | JPA | kie-services | 规则引擎叠加对审批流过重 |
| Zeebe | BPMN 2.0 | 自有存储 | 独立 broker + exporter | 运行数据导出分析 → 我们的轨迹查询 / 报表 |
| AWS Step Functions | ASL JSON 状态机 | 托管 | SDK | 结构化 JSON 定义 + choice 状态 → 我们的 CONDITION 节点 |
| 宜搭 / 钉钉 / 飞书审批 | 结构化节点 JSON（审批/条件/抄送） | 平台内建 | 平台内建 | 审批人策略链、兜底告警、加签/转办/委派、审批中锁单 |

### 1.3 借鉴的六条设计原则

1. **定义是版本化不可变数据，实例启动时钉版本**（Camunda）——运行中途改定义不影响在途实例。
2. **发布期校验尽量前移**：结构错误在设计期拦截，不留到运行期炸。
3. **并发用 CAS / 乐观锁**，禁 `SELECT ... FOR UPDATE`（本项目持久化纪律）。
4. **副作用走事务性 outbox**：引擎 `phase` 权威，业务 `status` 是投影，最终一致 + 对账兜底。
5. **人审关键路径 fail-closed**：审批人解析不出 ⇒ 挂起 + 告警 + 管理员干预，绝不静默放行或跳过。
6. **人工干预是一等公民**（改派 / 终止 / 催办）——没有干预入口的 fail-closed 就是死单制造机。

## 2. 架构总纲

### 2.1 模块布局（4 模块，无桥接层）

| 模块 | 职责 | 依赖 |
|---|---|---|
| `bone-workflow-domain` | 定义模型 / 发布期校验 / 条件求值 / 实例与任务状态机 / 引擎用例接口 | 零框架、零平台（ArchUnit 守护） |
| `bone-workflow-ports` | 端口 SPI（§2.3） | 仅 domain |
| `bone-workflow-runtime` | `WorkflowEngineImpl` 用例编排（推进 / 完成判定 / CAS / 干预） | domain + ports |
| `bone-workflow-starter` | 自动装配 + **BONE 集成适配器**（原桥接层整体并入，包 `adapter` / `spi`） | runtime + ports + `bone-metadata-sdk` + `bone-metadata-server` |

```
bone-workflow-domain ──► bone-workflow-ports ──► bone-workflow-runtime ──► bone-workflow-starter（适配器+装配）
```

### 2.2 为什么不做独立桥接层（合并决策）

v1 曾设独立模块 `bone-workflow-platform` 承载全部平台耦合，动机是「跨系统复用：引擎保持平台零依赖，各系统各自接线」。**方向对（端口抽象保留），但模块粒度选错了**，本文撤销该模块：

1. **只有一个平台消费者**。为假想中的第二、第三个宿主预建适配模块是投机抽象；复用性由端口契约本身保证——真出现第二个宿主时，由它按端口写适配器（在它自己的代码库里），不需要 BONE 预置。
2. **业界没有「bridge 产品」这种形态**。Camunda = engine + spring-boot-starter，Flowable 同，jBPM = kie-api + kie-services：平台集成从不是与引擎并列的独立模块，而是引擎发行版的一部分。
3. **独立模块的四个真实成本**：①版本 lockstep——桥接层只适配一个引擎版本，却要双模块协同演进，一个行为改动动两处；②装配顺序陷阱——本项目 2026-10-21 已实证 `@ConditionalOnBean` 对 SDK 仓储代理恒假导致**引擎静默不装配、零报错**，模块越多顺序越难控；③游离分层规约——第五模块同时依赖 engine + sdk + metadata-server，架构规则要为其开特例；④HC-006 诱惑——「桥接层是持久化重地」最容易被「SDK 不好写条件 UPDATE」诱导成裸 JDBC（并行实现果然走了这条路并登记豁免，本文驳回，见 §10-B）。
4. **边界不丢**：domain 纯净仍由 ArchUnit 跨模块守护；「引擎 vs BONE」的边界从模块间降到 starter 内的包间，依赖规则更少而非更多。

**合并后的接入收益**：StatusPort / RecordPort / IdGenerator / AuditPort 适配器由 starter 内置提供，业务系统接入从「实现 2–3 个端口」降为「流程定义种子 + `wf_binding` 配置」。

### 2.4 装配纪律（缺一即踩坑）

1. 引擎本体（`WorkflowEngine` bean）**仅在全端口就位时装配**；缺端口不是引擎的错，不打挂宿主启动。
2. 适配器与引擎装配分属两个 Spring Boot 自动配置类：**适配器自动配置类**定义端口 bean；**引擎自动配置类**（现有 `WorkflowEngineAutoConfiguration`）用 `@ConditionalOnBean` + `@AutoConfigureAfter(适配器自动配置类)`。**同一配置类内 `@ConditionalOnBean` 不可靠**（评估时机早于同类 bean 注册）。
3. 端口 bean 必须是**具体类**（内部委托 SDK 仓储），不能是 SDK `RepositoryFactoryBean` 代理——接口类型作构造参数时 Spring 无法静态推断 product type，类型条件恒假（2026-10-21 已实证）。
4. 负向验证：摘掉任一端口 bean ⇒ 引擎不装配且宿主正常启动，配一条回归用例钉死。

### 2.5 复用模型

| 层 | 归属 | 报销 / 采购 / 理赔 / HR / 财务各自要做的 |
|---|---|---|
| 引擎内核（推进 / 完成判定 / 条件求值 / 并发 CAS / 干预） | 共享 · engine | 直接复用 jar |
| `wf_*` 持久化 + 租户 / 审计 / 乐观锁 | 共享 · starter 适配器 | 直接获得 |
| 组织目录解析 | 共享 · `RoleMemberProvider`（bone-iam 侧实现一次） | 直接用 |
| 状态推进 / 读单据 / id / 审计 | 共享 · starter 适配器 | 直接用 |
| 流程定义 + `wf_binding` | **每系统定制** | 定义种子 + 绑定配置（运营可改） |

> 术语纠正：「RLS」是口头俗称——落地形态是 SDK `@TenantScope(MANUAL)` + 显式租户谓词 + 应用层过滤，**不是**数据库行级安全策略。

## 3. 定义模型与发布期校验

- **结构化 JSON 整图快照**：节点 / 边 / 指派规则统一存 `wf_process_def.definition_json`，不拆物理表（流程定义是「整图版本化」对象，拆表只增加 join 与版本一致性负担；设计器读 JSON 即可渲染）。
- **版本化**：`def_key + def_version`，`DRAFT → PUBLISHED` 才可用；**实例启动时钉版本**，在途实例不受后续发布影响。
- **`findLatestPublished` 确定性规则**：取 `status='PUBLISHED' AND enabled=1` 中 `max(def_version)`，不得用 `updated_at` 决胜（同秒更新即不确定）。
- **形状纪律**：审批 / 发起节点**恰有 1 条无条件出边**；条件只能挂 `CONDITION` 节点（多分支 = 多个 CONDITION 节点串联）；默认边（else）必须末位。
- **发布期校验**（`WorkflowDefinitionValidator`，运行期前移拦截）：

| 组 | 规则 |
|---|---|
| 结构 | 断头边 / 孤立节点 / 环 / 缺默认边 / 默认边非末位 |
| 审批节点 | 必须配指派规则（WF-007）；策略须在白名单（WF-013）；**恰 1 条无条件出边（WF-014）** |
| 发起节点 | **恰 1 条无条件出边（WF-015）** |
| CC 节点 | **v1 发布期拒绝（WF-016）**——治「配了不生效」（当前 `advanceFrom` 直接穿透，不产任务/通知/留痕） |
| 条件 | 未知算子判不成立并由静态检查拦下；缺 `fieldCode`/`operator` 判不成立 |

## 4. 运行时语义

### 4.1 状态机

- **实例 Phase**：`RUNNING / SUSPENDED / APPROVED / REJECTED / WITHDRAWN`（已实现）；**`TERMINATED`**（管理员强制终止，与发起人 `WITHDRAWN` 区分）为 v1 规划、**尚未落地**——`Phase` 枚举当前无此值，干预四用例（§4.4）实现时同批加入。
- **任务 Status**：`PENDING / APPROVED / REJECTED / CANCELLED`；`TRANSFERRED / DELEGATED` 为 v2 预留。
- **守卫**：终态不可回写；撤回仅发起人且未终结；恢复仅发起人且 `SUSPENDED`（仍解析不出则明确报错，不出「恢复成功」假象）；同结论重复提交幂等；`ALREADY_DECIDED` 防改判。

### 4.2 三个并发关键方法（实现错就静默出生产事故）

桥接 / 适配层实现 `WorkflowInstanceRepository` 时，以下三法必须落成**存储层原子语义**，绝不能用「先查后改」：

1. **`compareAndSetTaskStatus`** — `UPDATE ... WHERE id = ? AND status = :expected`。
2. **`compareAndSetPhase`** — `UPDATE ... WHERE id = ? AND phase = :expected`。
   > **口径修正（v3）**：端口签名为 `(instanceId, expected, next)`，**没有 expectedVersion 参数**。`version` 列照旧 `+1`，仅作同行其他列的丢失更新检测，**不作为第二个 guard**——guard 必须是「当前状态」本身；v1/v2 文档「phase + version 双条件」的表述作废（无法在不读的情况下 guard 一个可能已过期的 version）。
3. **`compareAndAdvanceNode`** — **节点级原子推进**：把「该节点是否已完成」的判定与「推进到下一节点」放进**同一条 UPDATE**。已由并行实现验证（H2 原样执行）的口径：
   - 任何形态下节点内出现 `REJECTED` 不得推进；
   - `ALL`（会签）：该节点**全部任务均落在已决策显式集** `('APPROVED','REJECTED','CANCELLED')` 且无人驳回（另有「节点至少有一个任务」的存在性守卫，防空节点 vacuously 通过）；
   - `SINGLE/ANY`：至少 1 人 `APPROVED`（其余待办由 `cancelPendingTasksOfNode` 善后）。

   > **为什么必须原子**：两个会签人同时点「同意」时，各自都读到「对方还没通过」的旧快照 ⇒ 双方都判「未齐」⇒ **流程永远卡在待办**（会签经典死锁，且无任何报错）。判据必须由存储层在同一条语句里依据最新行状态计算；数学上可证不死锁：`adv` 严格晚于自己的 `taskCAS`，双方互等会导出矛盾。
   >
   > **已决策口径 = 显式集，不是「无 PENDING」**（v3 修订，已随代码落地）：`status IN ('APPROVED','REJECTED','CANCELLED')`。原实现用 `NOT EXISTS PENDING` 是 **fail-open**——v2 落 `TRANSFERRED/DELEGATED` 后，转办中的任务不是 PENDING，会被当成「已决策」而**静默推进会签节点**（有人还没表态，流程继续往下走——审批系统最严重的事故形态）。显式集让未知状态落在 **fail-closed**：节点卡住 + 对账告警，人来处理。
   >
   > **v2 落转办/委派时的两条路**（产品裁决，代码勿擅选）：①转办生成**新 assignee 的 PENDING 任务**、原任务置 `TRANSFERRED`——此时须把 `TRANSFERRED` 纳入「未阻塞」集合或改按 `assignee_id` 判据，否则节点卡死；②产品定义「转办即弃权」——把 `TRANSFERRED` 加入已决策显式集。两者都可，**唯独不能保持现状不表态**。

### 4.3 幂等 · 幽灵待办 · fail-closed

- **start 幂等**：靠 `wf_active_instance` 指针表的 PK 原子化（§5.4），连点 / 网络重试不产生双实例。
- **幽灵待办**：单签/或签节点任一人通过后，`cancelPendingTasksOfNode` 作废其余 PENDING，不在「我的待办」留死条目。
- **fail-closed**：审批人解析不出 ⇒ 挂起（不是放行也不是跳过）+ **告警** + 管理员强制指派兜底。三件套缺一即为死单制造机。

### 4.4 管理员干预（v1，从 v2 提前）

> **落地状态：未实现**（`WorkflowEngine` 接口当前 7 个用例，无以下四方法；`Phase` 枚举无 `TERMINATED`）。这是阶段 1 的编码清单，不是既有能力——没有干预入口，挂起兜底（§4.3）就是死单制造机。

| 用例 | 守卫 | 语义 |
|---|---|---|
| `reassignTask` | 任务 PENDING 且实例未终结 | 改派 + 审计留痕 + 通知新办理人 |
| `terminateInstance` | 实例非终态 | 作废全部待办 + `phase → TERMINATED` + outbox 投影 |
| `urgeTask` | 任务 PENDING | 催办通知 + 审计；无状态变更 |
| `listInstanceHistory` | — | 实例 + 全量任务轨迹（决策人/结论/意见/时间），审批单据详情页直接用 |

| `WorkflowAuditPort` | 平台动作执行留痕链路 | 与业务操作日志同一条时间线 |
| `WorkflowIdGenerator` | 平台雪花 id | — |
| `NotificationPort` | 站内信适配器（实现可后置，先日志兜底并告警） | **通知失败不阻断审批主链路**（记 WARN），审批是主链路、通知是尽力而为 |

### 5.2 实现纪律（五条，缺一即踩坑）

1. **持久化全部走 `bone-metadata-sdk`**（HC-001/006）：三 CAS 的「带子查询的条件 UPDATE」用 SDK `@Sql` 自定义仓储方法。`SqlSecurityGuard` 只禁 DDL / 多语句 / **参数值内**的 SQL 关键字，**不禁子查询**——「SDK 无法表达」不成立（v1 曾据此登记裸 JDBC 豁免，本文驳回，§10-B）。
2. **租户**：`@Sql` 通道不经过 `TenantFilterInjector`，用 `@TenantScope(MANUAL)` + 显式 `tenant_id` 谓词，值从 `TenantContext` 取。漏租户谓词 = 多租户串数据，且单租户单测完全看不出来。
3. **自由文本参数坑（已实证）**：SDK 参数校验会拒绝含 SQL 关键字（`SELECT/UPDATE/DELETE/INSERT/DROP/EXEC`，大小写不敏感）的字符串值 ⇒ **审批意见里写 "please update" 会抛错 500**。落地时必须让 comment 走不触发该校验的通道（或推动 SDK 对该参数豁免），并配回归用例「意见含 update 字样必须成功」。
4. **审计归属**：写审计列（`created_by/updated_by`）的 `operatorId` **由引擎用例显式传入**（端口六方法签名已带 `operatorId`，引擎全部用例持有操作人）。适配器**不得**从 `TenantContext` 取租户 id 冒充操作人——审计列要回答「谁」，租户 id 回答「哪个租户」（v1 实现曾把租户 id 写进 `updated_by`，「谁批的」永远答不出；已修，端口 javadoc 有纪律说明 + 负向测试）。租户值仍从 `TenantContext` 取；outbox 中继器按行内 `tenant_id` 重建上下文。
5. **装配纪律**：§2.4 四条。

### 5.3 双写一致性：状态投影 outbox 与对账

引擎先提交 `wf_*` 再推业务 `status`，`invokeAction` 失败即「引擎已 APPROVED、业务单还 SUBMITTED」的撕裂态。设计（phase 权威，status 是投影）：

| 机制 | 设计 |
|---|---|
| 事务边界 | 适配层应用服务对 `start / completeTask / withdraw / resume / terminate` 包 `@Transactional`；`wf_*` 变更与 outbox 行**同生同死** |
| 投影写入 | `WorkflowStatusPort` 的 5 个 `mark*` = 同事务写 `wf_status_outbox`（`state=NEW`） |
| 中继器 | 定时 poll `NEW/FAILED` → `invokeAction` → 置 `DONE`；失败指数退避；超阈值置 `FAILED` 并告警 |
| 对账 job | 周期性比对 `wf_instance.phase` 与业务 status，不一致以 **phase 权威**重投影 |
| 幽灵审批兜底 | 对账顺带扫「业务单据已删/已作废 ⇒ 自动终止实例」——业务侧绕过流程终态化时，流程不会继续批一个不存在的单据 |

### 5.4 活动实例指针与重提语义

**引擎契约**（端口 javadoc + `WorkflowEngineImpl.start()` 实证）：一张单据同时只允许一个**未终结**实例；终态后可再 `start`——「驳回 → 修改 → 重新提交」是一等流程，不是异常。

由此两条约束：①`uk_entity_record (tenant_id, entity_code, record_id, deleted)`（母数据表惯例）**不可用于 `wf_instance`**——终态与重提实例同 key，重提必撞 1062；②引擎 start 幂等本身是 read-then-insert，**唯一键是使其原子化的唯一机制，不能简单删掉**。

**解法：`wf_active_instance` 指针表**（DDL 见 §7）：

- `start`：与 `wf_instance` 插入**同事务**插指针行；撞 PK ⇒ 读既有实例幂等返回；
- 终态流转**同事务**删指针行；
- `findInstanceByRecord` 语义 = 返回 `id` 最大者（最新一次提交）；
- 重提资格（`APPROVED` 后能否再提交）由业务状态机动作的 `from_status` 约束，引擎不代决；
- 备选（未采用）：MySQL 生成列 `active_flag AS (CASE WHEN phase IN ('RUNNING','SUSPENDED') AND deleted=0 THEN 1 END) STORED` + 唯一键忽略 NULL——零新增表但有 H2 方言风险，集成测试在 H2 验证通过后可切换。

### 5.5 审批中口径、绑定配置与接入契约

| 议题 | v1 决策 | 理由 |
|---|---|---|
| 审批中单据编辑 | **禁止**：适配层在 runtime update 入口按活动实例拦截 | 「批的」与「提交的」必须同一份数据；锁定后条件实时读 ≡ 提交时快照。v2 若放开，必须给实例存 `condition_snapshot_json` |
| 条件字段缺省 | 有序比较（gt/gte/lt/lte/between）左值缺省判**不成立**（引擎已修：原实现字符串强转会让缺金额静默落最低档——fail-open） | 建模纪律：默认边（else）必须指向 fail-safe 路径；条件字段在实体层必填，双保险 |
| 发起人自选 | 提交表单携带审批人字段（提交后即冻结，天然防审批中改人）+ `FIELD` 策略读取 | 引擎不中介选择交互；`INITIATOR_SELECT` v1 不自建交互态 |
| 实体 → 流程绑定 | `wf_binding` 表（`entity_code → def_key + start_action`），运营可改 | `definitionKey` 不硬编码在 action handler——否则换流程要发版 |
| 状态机最小动作集 | 接入系统必须提供 `submit / approve / reject / withdraw / suspend / resume`（映射 `start` + statusPort 5 个 `mark*`）；缺任一 ⇒ fail-fast + 接入检查清单报错 | 缺动作时运行期才炸，太晚 |
| SLA | `due_at` 列预留 + 定时扫描；v2 动作序 = 提醒 → 自动转交 → 自动同意（默认关闭） | 自动同意是放口子，企业场景默认不开 |
| 人事联动 | v2：账号禁用事件 → 待办自动改派；v1 至少提供管理员改派 API | 审批中员工离职不改派 = 死待办，是真实生产刚需 |

## 7. `wf_*` DDL 草案（**L3 · 待架构师审批**）

> 列遵循 BONE `TenantAbstractEntity` 通则：主键恒 `id BIGINT`；`tenant_id BIGINT` + 审计列（`created_by/created_at/updated_by/updated_at/deleted`）+ 乐观锁 `version INT`（全仓惯例，**INT 非 BIGINT**）。
> 母数据表唯一键惯例 `(…, deleted)` 只适用于「同 code 不重建」的主数据；运行时表按各自生命周期设计。
> H2 同构 schema 已被并行实现用于原子 SQL 回归（`deleted` 在 H2 用 INT）。

```sql
-- 流程定义（模板级，可版本化、可发布）
CREATE TABLE wf_process_def (
  id          BIGINT       NOT NULL,
  tenant_id   BIGINT       NOT NULL,
  def_key     VARCHAR(128) NOT NULL,   -- 流程标识：expense / purchase / claim / hr / finance
  def_name    VARCHAR(255) NOT NULL,
  def_version INT          NOT NULL,   -- 定义版本（实例钉版本用；勿与乐观锁列同名）
  status      VARCHAR(32)  NOT NULL,   -- DRAFT / PUBLISHED
  enabled     BIT          NOT NULL DEFAULT 1,
  definition_json MEDIUMTEXT NOT NULL, -- 节点/边/指派规则完整快照（TEXT 64KB 对大流程不够）
  created_by  VARCHAR(64)  NOT NULL,
  created_at  TIMESTAMP    NOT NULL,
  updated_by  VARCHAR(64),
  updated_at  TIMESTAMP,
  deleted     BIT          NOT NULL DEFAULT 0,
  version     INT          NOT NULL DEFAULT 0,  -- 乐观锁
  PRIMARY KEY (id),
  UNIQUE KEY uk_def_key_version (tenant_id, def_key, def_version, deleted)
);
-- 同一 def_key 可并存多个 PUBLISHED 版本（在途实例钉旧版）；
-- findLatestPublished = status='PUBLISHED' AND enabled=1 中 max(def_version)，不得用 updated_at 决胜。

-- 流程实例（运行时，钉版本）
CREATE TABLE wf_instance (
  id               BIGINT       NOT NULL,
  tenant_id        BIGINT       NOT NULL,
  entity_code      VARCHAR(128) NOT NULL,  -- 业务实体：expense_reimbursement / purchase_order / ...
  record_id        VARCHAR(128) NOT NULL,  -- 业务单据 id
  def_key          VARCHAR(128) NOT NULL,
  def_version      INT          NOT NULL,
  current_node_code VARCHAR(128) NOT NULL,
  phase            VARCHAR(32)  NOT NULL,  -- RUNNING / SUSPENDED / APPROVED / REJECTED / WITHDRAWN / TERMINATED
  started_by       VARCHAR(64)  NOT NULL,
  started_at       TIMESTAMP    NOT NULL,
  finished_at      TIMESTAMP    NULL,      -- 终态时间（流程时效分析用；RUNNING/SUSPENDED 为 NULL）。注意：当前实现不读写该列（WfSql 无引用），v2 时效分析时同批落地，届时对账 job 一并补刷历史行
  updated_at       TIMESTAMP    NOT NULL,
  created_by       VARCHAR(64)  NOT NULL,
  created_at       TIMESTAMP    NOT NULL,
  updated_by       VARCHAR(64),
  deleted          BIT          NOT NULL DEFAULT 0,
  version          INT          NOT NULL DEFAULT 0,  -- 乐观锁（阶段 CAS 用）
  PRIMARY KEY (id),
  KEY idx_entity_record (tenant_id, entity_code, record_id, id)  -- findInstanceByRecord 取 id 最大者
);
-- 无 (entity_code, record_id) 唯一键：驳回/撤回后重提是新实例，历史按单据可累积；
-- 「同时只有一个活动实例」由 wf_active_instance 指针表保证（§5.4）。

-- 活动实例指针（start 幂等的原子化靠这把锁）
CREATE TABLE wf_active_instance (
  tenant_id   BIGINT       NOT NULL,
  entity_code VARCHAR(128) NOT NULL,
  record_id   VARCHAR(128) NOT NULL,
  instance_id BIGINT       NOT NULL,
  created_at  TIMESTAMP    NOT NULL,  -- HC-008 四列齐全（指针行随实例同事务生灭，无独立生命周期，但按平台通则建列）
  updated_at  TIMESTAMP    NOT NULL,
  deleted     BIT          NOT NULL DEFAULT 0,
  PRIMARY KEY (tenant_id, entity_code, record_id)
);
-- start 同事务插入（撞 PK ⇒ 读既有实例幂等返回）；终态 phase CAS 同事务删除。
-- 写入/删除必须与 wf_instance 同事务，否则指针与实例漂移。

-- 审批任务（会签/或签产生多行）
CREATE TABLE wf_task (
  id           BIGINT       NOT NULL,
  tenant_id    BIGINT       NOT NULL,
  instance_id  BIGINT       NOT NULL,
  node_code    VARCHAR(128) NOT NULL,
  assignee_id  VARCHAR(64)  NOT NULL,
  status       VARCHAR(32)  NOT NULL,  -- PENDING / APPROVED / REJECTED / TRANSFERRED / DELEGATED / CANCELLED
  decision     VARCHAR(32),            -- APPROVE / REJECT；与 status 冗余但保留：幂等判据 + 任务级审计语义
  comment      VARCHAR(1024),
  due_at       TIMESTAMP,              -- SLA（v2 超时转交用）
  decided_at   TIMESTAMP,              -- 决策时间（轨迹查询用）
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  created_by   VARCHAR(64)  NOT NULL,
  updated_by   VARCHAR(64),
  deleted      BIT          NOT NULL DEFAULT 0,
  version      INT          NOT NULL DEFAULT 0,  -- 乐观锁（任务 CAS 用）
  PRIMARY KEY (id),
  KEY idx_assignee_status (tenant_id, assignee_id, status, deleted),  -- 我的待办
  KEY idx_instance        (tenant_id, instance_id, deleted)
);
-- 会签完成判定口径（compareAndAdvanceNode 的子查询，v3 已按此落地）：
--   已决策 = status IN ('APPROVED','REJECTED','CANCELLED') 显式集；节点还需存在性守卫（至少 1 条任务）
--   v2 落 TRANSFERRED/DELEGATED 属 fail-closed：卡节点 + 对账告警，绝不静默推进（§4.2 有两条产品路线）

-- 状态投影发件箱（双写一致性，§5.3）
CREATE TABLE wf_status_outbox (
  id           BIGINT       NOT NULL,
  tenant_id    BIGINT       NOT NULL,
  instance_id  BIGINT       NOT NULL,
  entity_code  VARCHAR(128) NOT NULL,
  record_id    VARCHAR(128) NOT NULL,
  intent       VARCHAR(32)  NOT NULL,   -- APPROVED / REJECTED / WITHDRAWN / SUSPENDED / RESUMED / TERMINATED
  payload_json TEXT         NULL,       -- 动作参数（驳回原因等）
  state        VARCHAR(16)  NOT NULL,   -- NEW / DONE / FAILED
  retry_count  INT          NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMP   NULL,
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  deleted      BIT          NOT NULL DEFAULT 0,  -- HC-008 四列齐全；归档 = 置 deleted（轮询查询须带 deleted=0）
  PRIMARY KEY (id),
  KEY idx_poll (state, next_retry_at)
);

-- 业务实体 → 流程定义绑定（definitionKey 的运营入口，§5.5）
CREATE TABLE wf_binding (
  id           BIGINT       NOT NULL,
  tenant_id    BIGINT       NOT NULL,
  entity_code VARCHAR(128) NOT NULL,
  def_key      VARCHAR(128) NOT NULL,
  start_action VARCHAR(64)  NOT NULL DEFAULT 'submit',  -- 触发启动的业务动作码
  enabled      BIT          NOT NULL DEFAULT 1,
  created_by   VARCHAR(64)  NOT NULL,
  created_at   TIMESTAMP    NOT NULL,
  updated_by   VARCHAR(64),
  updated_at   TIMESTAMP,
  deleted      BIT          NOT NULL DEFAULT 0,
  version      INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_binding (tenant_id, entity_code, deleted)
);
```

> 节点 / 边 / 指派规则**不拆物理表**，统一存 `wf_process_def.definition_json`（§3）。

## 8. 接线示例（报销）

金额三档与 `ExpenseApprovalRouter` 现行口径逐条对齐（≤1000 直属主管 / ≤5000 部门负责人 / >5000 财务负责人**会签**）。形状纪律见 §3；条件为结构化 JSON（`{"fieldCode":"amount","operator":"gt","value":5000}`，下方为简写）。

```java
// 流程定义（一次，随模板实例化；可运营侧维护后由定义仓储发布）
definitions.publish(new WorkflowDefinition("expense", 1,
    List.of(
        node("start", START),
        node("cond_null", CONDITION, null, "金额是否缺失"),   // 数据质量守卫：缺金额 → 最高档（fail-safe）
        node("cond_high", CONDITION, null, "金额 > 5000"),
        node("cond_mid",  CONDITION, null, "金额 > 1000"),
        node("mgr",     APPROVE, SINGLE, "直属主管审批"),
        node("dept",    APPROVE, SINGLE, "部门负责人审批"),
        node("finance", APPROVE, ALL,    "财务负责人审批（会签）"),  -- >5000 档 = 原 router countersign
        node("end", END)),
    List.of(
        edge("start", "cond_null"),
        edge("cond_null", "finance", "amount isNull"),  // 缺省 → 最高档，绝不静默落最低档
        edge("cond_null", "cond_high"),                 // else（默认边必须末位）
        edge("cond_high", "finance", "amount > 5000"),
        edge("cond_high", "cond_mid"),
        edge("cond_mid", "dept", "amount > 1000"),
        edge("cond_mid", "mgr"),
        edge("mgr", "end"), edge("dept", "end"), edge("finance", "end")),
    Map.of(
        "mgr", List.of(rule(LINE_MANAGER)),
        "dept", List.of(rule(DEPT_HEAD)),
        "finance", List.of(rule(ROLE, "FINANCE_HEAD")))));
```

接入四步：①`wf_binding` 配 `expense_reimbursement → expense`；②业务 `submit` 动作（逃逸，§10-C）→ 查 binding 取 `def_key` → `engine.start(...)`；③任务决策端点 → `engine.completeTask(...)`；④5 个 `mark*` 落 outbox，中继器经 `invokeAction` 落地业务 status。

**迁移 `ExpenseApprovalRouter` 的行为等价清单**（替换前逐条核对，防悄悄改审批策略）：

| 检查项 | router 现行 | 引擎版 |
|---|---|---|
| 档位边界 | ≤1000 LOW / ≤5000 MID / 其余 HIGH（等号归低档） | 同（`cond_mid` else = ≤1000） |
| HIGH 档会签 | `countersign=true`（G2-v1.1） | `ApprovalMode.ALL` |
| 金额缺省 | `bandOf(null)` NPE（500） | `isNull` 守卫 → 最高档（**行为变更，需业务确认**） |
| 指派解析 | `InMemoryApproverResolver`（MVP 内存实现） | 统一走引擎 `ApproverResolver` → IAM |
| 删除物 | `ExpenseApprovalRouter` + `InMemoryApproverResolver` | 消除两套并行路由的漂移风险 |

## 10. L3 待审批项

### A. `wf_*` DDL（§7 六表）

新增 `wf_process_def / wf_instance / wf_active_instance / wf_task / wf_status_outbox / wf_binding`。建表时机必须在集成层上线**之前**——表不存在时读写直接报错，刻意不兜底（审批数据落错表比启动失败更危险）。已实证修正：定义版本列与乐观锁列同名 `version`（MySQL 1060）→ `def_version`；`tenant_id` 曾误写 `VARCHAR(64)` → 全仓惯例 `BIGINT`。

**HC-008 门禁对齐（2026-10-23 补）**：`check-ddl-required-columns.py` 要求新增表四列（`tenant_id/created_at/updated_at/deleted`）齐全——§7 草案中 `wf_active_instance` 原缺 `created_at/updated_at/deleted`、`wf_status_outbox` 原缺 `deleted`，**按原草案落 `bone-init.sql` 即被门禁拦下**。已补列（指针行随实例同事务生灭、outbox 行处理完归档，理由见表注释）；H2 同构 schema 与 `INSERT_ACTIVE_INSTANCE` 已同步供值，outbox 四个查询补 `deleted=0` 过滤。

**设计与已实现的差距（审批时必须知情）**：

并行实现（未入库）已有 13 个 H2 用例全绿（含会签原子性回归、重复启动不双建、陈旧指针自愈、租户隔离、fail-closed 口径，H2 原样执行生产 SQL 形态）——三 CAS 的 SQL 形状本身已验证，差距在表的使用与持久化通道：

| 表 | 设计用途 | 当前实现是否使用 |
|---|---|---|
| `wf_process_def` / `wf_instance` / `wf_task` | 定义 / 实例 / 任务 | ✅ 已用 |
| `wf_active_instance` | 一单据一活动实例的原子指针 | ✅ 已用（`claimActiveInstance`/`compareAndSetPhase` 内联释放/`reclaimIfStale` 陈旧指针自愈） |
| `wf_status_outbox` | 状态投影最终一致 | ✅ 已用（`OutboxStatusPort` 为默认 StatusPort + `StatusProjectionRelay` 中继 + H2 回归） |
| `wf_binding` | 实体 → 流程绑定 | ❌ 未用——`definitionKey` 仍由调用方硬编码，运营不可改（§5.5） |

**含义**：A 批下来即得「并发幂等到数据库层 + 双写最终一致」的完整版本；剩 `wf_binding` 一座桥（不阻链路，阻运营）。

### B. 持久化通道：决议走 SDK `@Sql`，**不登记豁免**

并行实现曾申请豁免（`sdk-persistence-bypass-baseline.json` 登记 3 项），理由是「`compareAndAdvanceNode` 需单条带子查询的条件 UPDATE，SDK `updateByCriteria` 无法表达」。**本文驳回**：

1. 论据只对 Criteria API 成立，对 `@Sql` 通道不成立——`@Sql` 接受任意 SQL 文本，`SqlSecurityGuard` 只禁 DDL / 多语句 / 参数值内关键字，**子查询合法**（已读源码实证）。
2. 「H2 原样执行生产 SQL 做并发回归」的诉求用 SDK 通道同样满足（H2 数据源上跑同一条 `@Sql`）。
3. 豁免先例一开，后续所有「SDK 不好写」都会走裸 JDBC——HC-006 的防线即溃。

**处置**：并行实现（未入库）的 Jdbc* 仓储在阶段 1 改写为 SDK `@Sql` 仓储方法；`sdk-persistence-bypass-baseline.json` 已登记的 3 条豁免随改写一并移除。

### C. 动作逃逸 + 权限迁移（**唯一有生产影响的一项**）

`RuntimeActionDispatcher` 只给逃逸动作派发 Handler——要让 `submit` 驱动 `engine.start(...)`，`submit` 必须是逃逸动作；而 `RuntimeAccessGuard.canInvoke` 对逃逸动作**强制要求动作级细码**。不配套迁移 ⇒ prod 下既有提交者 403。

| 动作 | 现状 | 改为 | 需要的细码 |
|---|---|---|---|
| `submit` | 非逃逸 | 逃逸 + Handler 调 `engine.start` | `runtime:expense_reimbursement:submit` |
| `approve` | 非逃逸 | 逃逸 + Handler 调 `engine.completeTask` | `runtime:expense_reimbursement:approve` |
| `reject` | 非逃逸 | 逃逸 + Handler 调 `engine.completeTask` | `runtime:expense_reimbursement:reject` |
| `withdraw` | 非逃逸 | 逃逸 + Handler 调 `engine.withdraw` | `runtime:expense_reimbursement:withdraw` |

备选：只改 `submit` 一个动作（授权面冲击最小，但审批轨迹不进 `wf_task`）。**请裁决取哪种**。回滚 = 撤销 `is_escape=1` + 回收细码，`wf_*` 数据保留不影响业务。dev 口径 `security.enabled=false` 时匿名主体带 `platform.admin`，不影响本地联调。

### D. IAM 组织层级字段（可选，但影响核心场景）

已核实事实：平台 IAM **无组织层级字段**（`Dept` 只有 `name/parentId/orderNo`，全仓无 `leaderId/superior/managerId`）；且 `bone-iam` **不能作为 Maven 依赖引入**（独立部署服务，只走 HTTP；本地 `1.0.0` 产物包结构与现行源码不符）。后果：`LINE_MANAGER / DEPT_HEAD / LEVEL_UP` 解析不出人 ⇒ 引擎挂起（失败关闭，不是放行）——「≤1000 直属主管审批」这个最常用场景目前跑不通。

路径：①给 IAM 加 `leader_id`（及部门负责人）+ 查询端点，经 `RoleMemberProvider` SPI 接入——最正统但改动 IAM；②先用 `FIELD` / `INITIATOR_SELECT` 策略（表单上选审批人）跑通链路，组织层级后补——最快见效。**建议 2 先跑通、1 排期**。
