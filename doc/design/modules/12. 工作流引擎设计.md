## 1. 定位与业界对标

### 1.1 定位

把「审批流」做成 **BONE 平台的一等公民能力**：报销 / 采购 / 智能理赔 / HR / 财务共用同一套引擎与同一套持久化，各自只做「流程定义 + 少量配置」。

对标宜搭 / AppBuilder / 钉钉 / 飞书的业界实践：**审批流是表单/实体引擎的亲兄弟，共用实体、权限、审计**——而不是外挂一个通用 BPMN 引擎。严格遵循：

- **不引 Camunda / Flowable / Temporal**：平台 `dependencyManagement` 里虽有 `camunda-bom` 7.24.0，但来自已删除的遗留配置 `application-enterprise.yml`，全仓零 `org.camunda.*` 引用、未进 classpath；通用 BPMN 引擎与「零新依赖 + 元数据驱动 + 单一真源」纪律冲突。
- **不造通用 BPMN/DMN 引擎**：只做「实体数据驱动的分支状态机 + 角色指派」这一审批流专用子集。

### 1.2 业界对标

| 引擎                 | 定义模型                 | 持久化                 | 平台集成形态                       | 对本设计的启示                                                    |
| ------------------ | -------------------- | ------------------- | ---------------------------- | ---------------------------------------------------------- |
| Camunda 7          | BPMN 2.0 XML         | 自有约 20 张表 + MyBatis | engine + spring-boot-starter | 定义版本化、实例钉版本；history 一等公民；job executor 异步重试 → 我们的 outbox 中继 |
| Flowable           | BPMN 2.0             | 自有 + MyBatis/JPA    | engine + spring starter      | 启动器即集成点——佐证「不设桥接模块」                                        |
| jBPM               | BPMN2 + 规则           | JPA                 | kie-services                 | 规则引擎叠加对审批流过重                                               |
| Zeebe              | BPMN 2.0             | 自有存储                | 独立 broker + exporter         | 运行数据导出分析 → 我们的轨迹查询 / 报表                                    |
| AWS Step Functions | ASL JSON 状态机         | 托管                  | SDK                          | 结构化 JSON 定义 + choice 状态 → 我们的 CONDITION 节点                 |
| 宜搭 / 钉钉 / 飞书审批     | 结构化节点 JSON（审批/条件/抄送） | 平台内建                | 平台内建                         | 审批人策略链、兜底告警、加签/转办/委派、审批中锁单                                 |

### 1.3 借鉴的六条设计原则

1. **定义是版本化不可变数据，实例启动时钉版本**（Camunda）——运行中途改定义不影响在途实例。
2. **发布期校验尽量前移**：结构错误在设计期拦截，不留到运行期炸。
3. **并发用 CAS / 乐观锁**，禁 `SELECT ... FOR UPDATE`（本项目持久化纪律）。
4. **副作用走事务性 outbox**：引擎 `phase` 权威，业务 `status` 是投影，最终一致 + 对账兜底。
5. **人审关键路径 fail-closed**：审批人解析不出 ⇒ 挂起 + 告警 + 管理员干预，绝不静默放行或跳过。
6. **人工干预是一等公民**（改派 / 终止 / 催办）——没有干预入口的 fail-closed 就是死单制造机。

## 2. 架构总纲

### 2.1 模块布局（2 模块：内核 `core` + Starter）

> **演进说明（2026-10-23）**：原方案为 4 个 Maven 模块 `bone-workflow-domain → bone-workflow-ports → bone-workflow-runtime → bone-workflow-starter`。经实证诊断后**收敛为 2 个模块**——`bone-workflow-core`（合并 domain + ports + runtime）+ `bone-workflow-spring-boot-starter`。理由见 §2.1.1 / §2.1.2。

| 模块                                  | 包                                                                                        | 职责                                                                                                                                                                                                 | 对外依赖                                                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `bone-workflow-core`                | `com.bone.workflow.domain` · `com.bone.workflow.ports.spi` · `com.bone.workflow.runtime` | **引擎内核（纯 Java，零 Spring / 零平台）**：①`domain` 流程定义 / 实例 / 任务模型、条件求值、分支选择、发布期校验；②`ports.spi` **8 个端口契约**（7 个必需 + `NotificationPort` 可选，§2.3）；③`runtime` `WorkflowEngineImpl` 用例编排（推进 / 完成判定 / CAS / 干预） | 仅 JDK + Jackson + SLF4J                                                                    |
| `bone-workflow-spring-boot-starter` | `com.bone.workflow.starter`（`adapter` / `outbox` / `persistence` / `spi`）                | **平台集成（全部基础设施）**：Boot 3 自动配置、JDBC 适配器、状态投影 outbox + 中继、生产 SQL 集中地（`persistence.WfSql`）、BONE 外接 SPI                                                                                                 | core + `bone-metadata-engine-runtime` + `bone-metadata-server` + `bone-core` + spring-jdbc |

```
bone-workflow-core  （domain → ports → runtime，包间分层，纯 Java 可独立复用）
        │
        ▼
bone-workflow-spring-boot-starter  （JDBC 适配器 + outbox 中继 + BONE 集成 + Boot 3 装配）
```

#### 2.1.1 原方案为什么拆成 4 个模块（初衷）

六边形 / 清洁架构的直觉是「每层一个制品」，依赖方向严格向内：`domain`（纯逻辑，零框架）→ `ports`（契约）→ `runtime`（编排）→ `starter`（装配 + 平台适配）。拆成独立 Maven 模块的本意是**用编译期物理隔离把「引擎不得依赖平台」焊死**——domain 模块在 `pom.xml` 里根本没有 Spring / bone-core 依赖，谁想在 domain 里 `@Autowired` 一个平台 bean，编译期直接失败，而非运行期在平台外才爆炸。

#### 2.1.2 为什么 4 个模块是过度设计（实证后收敛）

1. **ports 与 runtime 没有独立消费者**。`bone-workflow-ports` 的 jar 离开 domain 没有独立意义（端口契约本就是 domain 六边形的一部分）；`bone-workflow-runtime` 只有一个编排类 `WorkflowEngineImpl`。二者都不具备「独立发布 / 独立复用」价值——拆开只会让「改一个端口签名」变成跨三模块的 choreography，且 Maven reactor 多三个工程、CI 多三轮。
2. **业界没有「按层拆分引擎制品」的形态**（共同规律 = 引擎本体一个纯 Java 制品 + 平台集成一个 starter 制品）：
   - Camunda = `camunda-bpm-engine` + `camunda-spring-boot-starter`
   - Flowable / Activiti = 单核心 + `flowable-spring-boot-starter`
   - jBPM = `kie-api` + `kie-services`
   - Spring Batch = `spring-batch-core` + `spring-boot-starter-batch`
   端口（ports）在上述引擎里**都是内核的一部分**，而非与内核并列的独立制品。
3. **合并不丢纪律，但守护点必须跟着搬家**。ArchUnit 改按**包名**守护（`com.bone.workflow.domain..` 不得依赖 `..runtime` / `..starter` 等），与拆分模块时的依赖方向约束**等价**，只是从「模块间」降到「包间」。⚠️ 但有一处必须显式补上：**core 的测试看不见 starter 的类**（依赖方向是 starter → core），因此「引擎命名空间不得依赖框架 / 平台」这条跨模块纪律**不能只写在 core 里**——已在 starter 侧补 `StarterArchitectureTest`（唯一能同时看到 core + starter 两个制品的视角），并恢复 starter 的 `archunit.properties` 冻结开关。缺这一处 ⇒ 「starter 里放一个 `com.bone.workflow.domain` 包下的 Spring 类」可畅通无阻，引擎纯度静默失守。

#### 2.1.3 两个模块的边界与职责（收敛后明确划分）

| 维度           | `bone-workflow-core`                                 | `bone-workflow-spring-boot-starter`                      |
| ------------ | ---------------------------------------------------- | -------------------------------------------------------- |
| **一句话职责**    | 审批流的**全部纯逻辑**：定义模型、发布期校验、条件 / 分支求值、状态机、三 CAS 编排、干预用例 | 审批流的**全部基础设施与平台耦合**：Boot 3 装配、JDBC 持久化、outbox 双写、BONE 外接 |
| **允许知道什么**   | 只知道自己的模型与端口契约                                        | 知道 core、平台元数据引擎、`bone-core`、Spring JDBC                  |
| **绝不允许知道什么** | Spring / 平台元数据 / `bone-core` / 适配器层（反向引用即环形依赖）       | 引擎内部的编排细节（不得绕过 `WorkflowEngine` 用例接口直接改 `wf_*` 状态）       |
| **可独立复用的形态** | 纯 Java jar，任何 JVM 宿主直接依赖即可用（不止 BONE 平台）              | 需 Spring Boot 3 + BONE 平台服务，不可移植                         |
| **谁来改**      | 流程语义变更方（产品 / 引擎 owner）                               | 接入方 / 平台方                                                |

**三条边界纪律（机器可校验）**：

1. **引擎纯净**：包 `com.bone.workflow.domain..` / `ports..` / `runtime..` 内任何类不得依赖 Spring、平台元数据、`bone-core` 或 `com.bone.workflow.starter..` —— 由 **starter 侧** `StarterArchitectureTest` 断言（唯一能同时看到两个制品的视角，见 §2.1.2 第 3 条）。
2. **层序不变**：core 内 `domain ← ports ← runtime` 单向依赖，由 **core 侧** `ArchitectureTest` 断言（含「domain 只许被 domain/ports/runtime 访问」）。
3. **依赖白名单**：引擎只许依赖 JDK + Jackson（数据绑定）+ SLF4J（日志），引入其它第三方库须显式评审 —— 同由 starter 侧规则从白名单侧兜底。

> **为什么纪律 1 写在 starter 而不是 core**：core 的测试 classpath 上没有 starter 的类（依赖方向是 starter → core），写在 core 里对 starter 侧的违规**结构性失明**。这不是「重复断言」，而是补上一个真实存在的盲区。

### 2.2 为什么不做独立桥接层（合并决策）

v1 曾设独立模块 `bone-workflow-platform` 承载全部平台耦合，动机是「跨系统复用：引擎保持平台零依赖，各系统各自接线」。**方向对（端口抽象保留），但模块粒度选错了**，本文撤销该模块：

1. **只有一个平台消费者**。为假想中的第二、第三个宿主预建适配模块是投机抽象；复用性由端口契约本身保证——真出现第二个宿主时，由它按端口写适配器（在它自己的代码库里），不需要 BONE 预置。
2. **业界没有「bridge 产品」这种形态**。Camunda = engine + spring-boot-starter，Flowable 同，jBPM = kie-api + kie-services：平台集成从不是与引擎并列的独立模块，而是引擎发行版的一部分。
3. **独立模块的四个真实成本**：①版本 lockstep——桥接层只适配一个引擎版本，却要双模块协同演进，一个行为改动动两处；②装配顺序陷阱——本项目 2026-10-21 已实证 `@ConditionalOnBean` 对 SDK 仓储代理恒假导致**引擎静默不装配、零报错**，模块越多顺序越难控；③游离分层规约——第五模块同时依赖 engine + sdk + metadata-server，架构规则要为其开特例；④HC-006 诱惑——「桥接层是持久化重地」最容易被「SDK 不好写条件 UPDATE」诱导成裸 JDBC（并行实现果然走了这条路并登记豁免，本文驳回，见 §10-B）。
4. **边界不丢**：domain 纯净仍由 ArchUnit 跨模块守护；「引擎 vs BONE」的边界从模块间降到 starter 内的包间，依赖规则更少而非更多。

**合并后的接入收益**：StatusPort / RecordPort / IdGenerator / AuditPort 适配器由 starter 内置提供，业务系统接入从「实现 2–3 个端口」降为「流程定义种子 + `wf_binding` 配置」。

### 2.3 端口清单

| 端口                             | 职责                                     | 状态               |
| ------------------------------ | -------------------------------------- | ---------------- |
| `WorkflowDefinitionRepository` | 定义快照读写（整图 JSON）                        | 已有 · 必需          |
| `WorkflowInstanceRepository`   | 实例 / 任务持久化 + 三 CAS（§4.2）               | 已有 · 必需          |
| `ApproverResolver`             | 指派策略解析（USER/FIELD/ROLE/LINE_MANAGER/…） | 已有 · 必需          |
| `WorkflowRecordPort`           | 读业务单据数据（条件求值取数）                        | 已有 · 必需          |
| `WorkflowStatusPort`           | 状态投影（6 个 `mark*`，含 `markTerminated`；v1 写 outbox） | 已有 · 必需          |
| `WorkflowAuditPort`            | 审计留痕（与业务操作日志同时间线）                      | 已有 · 必需          |
| `WorkflowIdGenerator`          | 实例 / 任务 id 生成（宿主可注入雪花 id 或 UUID；**排序口径不依赖 id 形态**，见 §5.4）       | 已有 · 必需          |
| `NotificationPort`             | 任务创建 / 催办 / 改派 / 挂起告警 / 终态通知（终态四路径与 resume 派单均已回调，§4.4）           | 已有 · **可选**      |
| `RoleMemberProvider`（SPI）      | 组织目录查询，由宿主 / bone-iam 侧实现              | 已有 · starter.spi |

**计数口径**：`ports.spi` 包下共 **8 个接口** = **7 个必需**（进 `EngineConfiguration` 的 `@ConditionalOnBean` 清单，缺一即引擎不装配）+ **1 个可选**（`NotificationPort`）。

- `NotificationPort` 不参与必配集：宿主未接通知能力时由 `NotificationPort.NOOP` 空实现兜底（starter 以 `ObjectProvider` + `getIfAvailable(() -> NOOP)` 装配）——通知是尽力而为，缺失不应让引擎不可用。

> **v1 通知口径澄清（2026-10-23 原结论）**：`NotificationPort.NOOP` 是 **starter 默认**实现（未注入通知 bean 时即默认 NOOP），故 v1 实际仅打日志、不落站内信。§6「通知最小集（站内信）」属**规划目标**，非 v1 现状。需由产品明确：v1 通知是 **MUST** 还是 **DEFERRED**——二选一并钉死。
>
> **P0-3 已闭环（2026-10-26）**：starter 默认通知端口已从 `LoggingNotificationPort`（仅日志）改为 **`PersistenceNotificationPort`**（写入 `wf_notification` 表，办理人经 `WorkflowInboxQuery` 查收件箱）——即 v1 站内信 **MUST** 已落地。缺 bean 时仍回退 `NOOP`，不阻断引擎；宿主接 IM / 邮件网关时可自备 `NotificationPort` 覆盖（但需另提供 `WorkflowInboxQuery` 实现以保留收件箱入口）。通知失败绝不阻断审批主链路（端口内部吞异常）。

- `RoleMemberProvider` **不属于 `ports.spi`**：它是 starter 侧的宿主接入 SPI（`com.bone.workflow.starter.spi`），供 `ApproverResolver` 实现类在解析 `ROLE` / `LINE_MANAGER` / `DEPT_HEAD` / `LEVEL_UP` 策略时查询组织目录，不进引擎内核契约包。

引擎用例接口：v1 **全部已实现**——`start` / `completeTask` / `withdraw` / `resume` / `reassignTask` / `urgeTask` / `terminateInstance` / `assignTask` / `listInstanceHistory` / `transferTask`（审批人本人转办）/ `addSign`（审批人本人加签）（§4.4）。


### 2.4 装配纪律（缺一即踩坑）

1. 引擎本体（`WorkflowEngine` bean）**仅在全端口就位时装配**；缺端口不是引擎的错，不打挂宿主启动。
2. 适配器与引擎装配分属两个 Spring Boot 自动配置类：**适配器自动配置类**定义端口 bean；**引擎自动配置类**（现有 `WorkflowEngineAutoConfiguration`）用 `@ConditionalOnBean` + `@AutoConfigureAfter(适配器自动配置类)`。**同一配置类内 `@ConditionalOnBean` 不可靠**（评估时机早于同类 bean 注册）。
3. 端口 bean 必须是**具体类**（内部委托 SDK 仓储），不能是 SDK `RepositoryFactoryBean` 代理——接口类型作构造参数时 Spring 无法静态推断 product type，类型条件恒假（2026-10-21 已实证）。
4. 负向验证：摘掉任一端口 bean ⇒ 引擎不装配且宿主正常启动，配一条回归用例钉死。

## 3. 定义模型与发布期校验

- **结构化 JSON 整图快照**：节点 / 边 / 指派规则统一存 `wf_process_def.definition_json`，不拆物理表（流程定义是「整图版本化」对象，拆表只增加 join 与版本一致性负担；设计器读 JSON 即可渲染）。
- **版本化**：`def_key + def_version`，`DRAFT → PUBLISHED` 才可用；**实例启动时钉版本**，在途实例不受后续发布影响。
- **`findLatestPublished` 确定性规则**：取 `status='PUBLISHED' AND enabled=1` 中 `max(def_version)`，不得用 `updated_at` 决胜（同秒更新即不确定）。

> **禁用定义语义澄清（2026-10-23）**：`enabled=0` 仅影响**新启动**——`findLatestPublished` 跳过禁用版本，故新提交找不到该流程。在途实例因**启动时钉版本**（`def_key + def_version` 已固化在 `wf_instance`），不受后续禁用影响，会正常走完。运营须知悉：「禁用流程定义」≠「停掉所有在途单」，后者需逐单 `terminateInstance`（§4.4，已实现）。

- **形状纪律**：审批 / 发起节点**恰有 1 条无条件出边**；条件只能挂 `CONDITION` 节点（多分支 = 多个 CONDITION 节点串联）；默认边（else）必须末位。
- **发布期校验**（`WorkflowDefinitionValidator`，运行期前移拦截）：

| 组     | 规则                                                               |
| ----- | ---------------------------------------------------------------- |
| 结构    | 断头边 / 孤立节点 / 环 / 缺默认边 / 默认边非末位                                   |
| 审批节点  | 必须配指派规则（WF-007）；策略须在白名单（WF-013）；**恰 1 条无条件出边（WF-014）**           |
| 发起节点  | **恰 1 条无条件出边（WF-015）**                                           |
| CC 节点 | **已落地（2026-10-26）**：解析抄送人 → 逐人发知会（站内信 `type=CC`）→ 立即穿透；**不建任务、不参与完成判据**。校验改为「必须有抄送人指派规则 + 恰 1 条出边（WF-018）」，不再一律拒绝（原 WF-016 作废） |

## 4. 运行时语义

### 4.1 状态机

- **实例 Phase**：`RUNNING / SUSPENDED / APPROVED / REJECTED / WITHDRAWN / TERMINATED`（全部已实现；`TERMINATED` 为管理员强制终止，与发起人 `WITHDRAWN` 区分，2026-10-23 随干预四用例落地）。
- **任务 Status**：`PENDING / APPROVED / REJECTED / CANCELLED`；`TRANSFERRED / DELEGATED` 为 v2 预留。
- **守卫**：终态不可回写；撤回仅发起人且未终结；恢复仅发起人且 `SUSPENDED`（仍解析不出则明确报错，不出「恢复成功」假象）；同结论重复提交幂等；`ALREADY_DECIDED` 防改判。

### 4.2 三个并发关键方法（实现错就静默出生产事故）

桥接 / 适配层实现 `WorkflowInstanceRepository` 时，以下三法必须落成**存储层原子语义**，绝不能用「先查后改」：

1. **`compareAndSetTaskStatus`** — `UPDATE ... WHERE id = ? AND status = :expected`。
2. **`compareAndSetPhase`** — `UPDATE ... WHERE id = ? AND phase = :expected`。
   > **口径修正（v3）**：端口签名为 `(instanceId, expected, next)`，**没有 expectedVersion 参数**。`version` 列照旧 `+1`，仅作同行其他列的丢失更新检测，**不作为第二个 guard**——guard 必须是「当前状态」本身；v1/v2 文档「phase + version 双条件」的表述作废（无法在不读的情况下 guard 一个可能已过期的 version）。
3. **`compareAndAdvanceNode`** — **节点级原子推进**：把「该节点是否已完成」的判定与「推进到下一节点」放进**同一条 UPDATE**。已由并行实现验证（H2 原样执行）的口径：
   - 任何形态下节点内出现 `REJECTED` 不得推进；
   - `ALL`（会签）：该节点**全部任务均落在已决策显式集** `('APPROVED','REJECTED','CANCELLED')` 且无人驳回（另有「节点至少有一个任务」的存在性守卫，防空节点 vacuously 通过）；
   - `SINGLE/ANY`：至少 1 人 `APPROVED`（其余待办由 `cancelPendingTasksOfNode` 善后）。
   > **为什么必须原子**：两个会签人同时点「同意」时，各自都读到「对方还没通过」的旧快照 ⇒ 双方都判「未齐」⇒ **流程永远卡在待办**（会签经典死锁，且无任何报错）。判据必须由存储层在同一条语句里依据最新行状态计算；数学上可证不死锁：`adv` 严格晚于自己的 `taskCAS`，双方互等会导出矛盾。
   >
   > **已决策口径 = 显式集，不是「无 PENDING」**（v3 修订，已随代码落地）：`status IN ('APPROVED','REJECTED','CANCELLED')`。原实现用 `NOT EXISTS PENDING` 是 **fail-open**——v2 落 `TRANSFERRED/DELEGATED` 后，转办中的任务不是 PENDING，会被当成「已决策」而**静默推进会签节点**（有人还没表态，流程继续往下走——审批系统最严重的事故形态）。显式集让未知状态落在 **fail-closed**：节点卡住 + 对账告警，人来处理。
   >
   > **v2 落转办/委派时的两条路**（产品裁决，代码勿擅选）：①转办生成**新 assignee 的 PENDING 任务**、原任务置 `TRANSFERRED`——此时须把 `TRANSFERRED` 纳入「未阻塞」集合或改按 `assignee_id` 判据，否则节点卡死；②产品定义「转办即弃权」——把 `TRANSFERRED` 加入已决策显式集。两者都可，**唯独不能保持现状不表态**。

### 4.3 幂等 · 幽灵待办 · fail-closed

- **start 幂等**：靠 `wf_active_instance` 指针表的 PK 原子化（§5.4），连点 / 网络重试不产生双实例。
- **幽灵待办**：单签/或签节点任一人通过后，`cancelPendingTasksOfNode` 作废其余 PENDING，不在「我的待办」留死条目；强制指派的「同人同节点双待办」由**数据库条件插入**（`saveTaskIfAbsent`，§4.2 同纪律）挡住，并发双点不双插。
- **fail-closed**：审批人解析不出 ⇒ 挂起（不是放行也不是跳过）+ **告警** + 管理员强制指派兜底。三件套缺一即为死单制造机。

> **兜底缺口已闭合（2026-10-23 第二轮）**：`assignTask(instanceId, nodeCode, assigneeId, operatorId, reason)` 已落地——SUSPENDED 且无任务时新建 PENDING 任务（条件插入去重）并经阶段 CAS 恢复 RUNNING，与 `terminateInstance`（整单终止）共同构成「强制指派 / 整单终止」两条人工介入通道（§4.4）。原「只能等 IAM 改造或整单终止」的缺口不再存在。

### 4.4 管理员干预（v1，从 v2 提前）

> **落地状态：全部实现（2026-10-23 第二轮闭合；2026-10-26 补 `transferTask` / `addSign`）**。`reassignTask` / `urgeTask` / `resume` / `terminateInstance` / `assignTask` / `listInstanceHistory` / `transferTask` / `addSign` 八个用例均已实现并有测试覆盖；`Phase.TERMINATED` 已入枚举，`WorkflowTask.Status.TRANSFERRED` 已入任务状态机。终态四路径（通过 / 驳回 / 撤回 / 强制终止）均回调 `notifyTerminated`，`resume` 重建待办回调 `notifyTaskCreated`——「只改状态不通知」的缺口已补（§2.3 端口契约与实现一致）。

| 用例                    | 守卫                | 语义                                        |
| --------------------- | ----------------- | ----------------------------------------- |
| `reassignTask`        | 任务 PENDING 且实例未终结 | 改派（管理员干预，不限操作人身份）+ 审计留痕 + 通知新办理人              |
| `assignTask`          | 实例未终结（SUSPENDED 时经阶段 CAS 恢复） | 强制指派：条件插入去重（§4.3）+ 恢复 RUNNING + 审计留痕 |
| `terminateInstance`   | 实例非终态             | 作废全部待办 + `phase → TERMINATED` + outbox 投影 + 终态通知 |
| `urgeTask`            | 任务 PENDING        | 催办通知 + 审计；无状态变更                           |
| `transferTask`        | 任务 PENDING 且操作人=当前办理人、实例未终结 | 审批人本人转办：原任务置 `TRANSFERRED` + 新建新办理人 PENDING + 审计留痕 + 通知；与管理员 `reassignTask` 区分（后者静默改人、无 TRANSFERRED 留痕） |
| `addSign`             | 任务 PENDING 且操作人=当前办理人、实例未终结、同节点目标无非重复待办 | 审批人本人加签：同节点新增新办理人 PENDING 任务，节点完成仍按该节点 `ApprovalMode` 统一判定（会签节点须被加签人一并通过）；与管理员 `assignTask` 区分（后者是兜底注入） |

### 5.2 实现纪律（五条，缺一即踩坑）

1. **持久化全部走 `bone-metadata-sdk`**（HC-001/006）：三 CAS 的「带子查询的条件 UPDATE」用 SDK `@Sql` 自定义仓储方法。`SqlSecurityGuard` 只禁 DDL / 多语句，**不禁子查询、不扫合法 DML 关键字**——「SDK 无法表达」不成立（v1 曾据此登记裸 JDBC 豁免，本文驳回；**2026-10-24 已全量落地**，§10-B）。
2. **租户**：`@Sql` 通道不经过 `TenantFilterInjector`，用 `@TenantScope(MANUAL)` + 显式 `tenant_id` 谓词，值从 `TenantContext` 取。漏租户谓词 = 多租户串数据，且单租户单测完全看不出来。
3. **自由文本参数坑（已实证 · 2026-10-24 已在 SDK 根源修复）**：SDK 处理器此前的 `validateParameters` 会拒绝含 SQL 关键字（`SELECT/UPDATE/DELETE/INSERT/DROP/EXEC`，大小写不敏感）的字符串值 ⇒ **审批意见里写 "please update" 会抛错 500**。现已从 SDK 移除值级关键字/分号扫描（参数值经 `#{}` 预编译绑定，本就无注入面；真注入面只有 `${}` 原文替换，由 `^[a-zA-Z0-9_]+$` 标识符约束与 `tableName` 白名单把守，均有负向测试）。回归用例：`SdkWorkflowInstanceRepositoryH2Test#commentContainingSqlKeywords_roundTripsThroughSdkChannel`（`"please update the amount; DROP TABLE wf_task"` 必须原样存取——退化成扫值即红）。
4. **审计归属**：写审计列（`created_by/updated_by`）的 `operatorId` **由引擎用例显式传入**（端口六方法签名已带 `operatorId`，引擎全部用例持有操作人）。适配器**不得**从 `TenantContext` 取租户 id 冒充操作人——审计列要回答「谁」，租户 id 回答「哪个租户」（v1 实现曾把租户 id 写进 `updated_by`，「谁批的」永远答不出；已修，端口 javadoc 有纪律说明 + 负向测试）。租户值仍从 `TenantContext` 取；outbox 中继器按行内 `tenant_id` 重建上下文。
5. **装配纪律**：§2.4 四条。


> **错误码 → HTTP 映射（2026-10-23 落地）**：`WorkflowErrorCode` 每个常量现自带 `httpStatus()`（422 / 403 / 409），作为「引擎错误 → 平台 HTTP 状态」的**单一真源**。宿主 `GlobalExceptionHandler` 应直接按 `ex.code().httpStatus()` 响应并附 RFC 9457 problem-details，<b>不得</b>靠解析 message 翻译（否则同语义两处各写一套、迟早漂移）。错误码分类口径见 `WorkflowErrorCode` javadoc。本引擎不定义平台业务异常类型——翻译发生在宿主装配层。

> **分支错误码契约（2026-10-23 第二轮落地）**：`WorkflowBranchEvaluator.select` 的全部失败（多条分支同时命中 / 多条默认边 / 默认边非末位 / 条件结构非法 / 无命中且无默认边）一律抛 `WorkflowEngineException(BRANCH_AMBIGUOUS / BRANCH_INVALID / BRANCH_NO_MATCH)`。此前这 4 处抛裸 `IllegalStateException` 而 `BRANCH_*` 三码「定义了全仓零引用」——宿主只能落 500 无稳定码，契约旁路；现已逐处负向测试锁定（退化成裸异常即红）。

> **分支歧义不得留下静默死单（2026-10-26 修正）**：**多条分支同时命中是运行时可达的**——条件重叠与**业务数据相关**（如 `amount>1000` 与 `amount>5000` 在 `amount=8000` 时同时命中），发布期的语法/结构检查查不出来。而此时任务已 CAS 决策、实例已推进到该条件节点，若只抛异常，实例会停在**既无待办、又无告警**的节点上——没人知道它卡住，管理员只能翻库发现。故 `advanceFrom` 在捕获分支失败后**先按 fail-closed 三件套挂起 + 管理员告警**，再把稳定错误码抛给宿主翻译（422）；`resume` 亦已支持**非审批节点**（条件/抄送）挂起后重跑该节点续跑——否则条件节点没有指派规则，恢复必然撞 `NO_ASSIGNEE`，死单不可恢复。「挂起 → 修复 → 恢复」通道由此闭合。

### 5.3 双写一致性：状态投影 outbox 与对账

引擎先提交 `wf_*` 再推业务 `status`，`invokeAction` 失败即「引擎已 APPROVED、业务单还 SUBMITTED」的撕裂态。设计（phase 权威，status 是投影）：

| 机制     | 设计                                                                                                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 事务边界   | 适配层应用服务对 `start / completeTask / withdraw / resume / terminate` 包 `@Transactional`；`wf_*` 变更与 outbox 行**同生同死**。**当前缺口**：引擎侧无事务信封承载点（metadata-server 的 `runtime/workflow` 接入包未建），崩溃在「phase CAS 后、意图入箱前」的窗口由对账补救（§9 阶段 2） |
| 投影写入   | `WorkflowStatusPort` 的 6 个 `mark*`（含 `markTerminated`）= 同事务写 `wf_status_outbox`（`state=NEW`）                                                                                        |
| 中继器    | 定时 poll（NEW / 到期 FAILED / 超时 CLAIMED）→ **原子 claim**（仅抢到 `CLAIMED` 的副本执行）→ `invokeAction` → 置 `DONE`；失败指数退避；超阈值置 `FAILED` 并告警。多副本部署下靠原子 claim 防业务动作（approve/reject）重复执行（修订细节见 §10-E） |
| 同实例按序  | 按 `created_at` 升序取（**不按 id**——UUID 宿主下 id 字典序≠时间序）+ SQL **队头守卫**（同实例有更早的在途意图时不返回）；本批次内某实例失败即跳过其余意图，防终态投影颠倒 |
| 对账 job | `StatusProjectionRelay.runReconcile`（`@Scheduled`，默认 30s）：扫「对账窗口内终态实例**完全没有任何同 intent 意图行**」的（= 崩溃在 phase CAS 与入箱之间），以**确定性 id**（`reconcile-{instance}-{phase}`）补投；重复对账撞主键即跳过，不会把有上限重试变成无限重试。TERMINATED 等无业务动作的终态补投后按「无动作意图」标记 DONE，闭合证据链 |
| DONE 清理 | `markDone` **不置 deleted**（DONE 行是「投影已落地」的唯一证据）；清理走独立的 `purgeDone`（`@Scheduled` 每日，保留期 7 天）。**保留期必须 > 对账窗口（6h）**——否则窗口内实例的 DONE 行被清后会被重判缺投影，重复执行业务动作。两个坑（归档即软删 / 硬删不设窗口）单独看都隐蔽，故在 DDL 注释、SQL 注释与测试三处钉死同一套语义 |
| 幽灵审批兜底 | 规划未落地：对账顺带扫「业务单据已删/已作废 ⇒ 自动终止实例」——业务侧绕过流程终态化时，流程不会继续批一个不存在的单据（§9 阶段 2）                                                                                                                          |

### 5.4 活动实例指针与重提语义

**引擎契约**（端口 javadoc + `WorkflowEngineImpl.start()` 实证）：一张单据同时只允许一个**未终结**实例；终态后可再 `start`——「驳回 → 修改 → 重新提交」是一等流程，不是异常。

由此两条约束：①`uk_entity_record (tenant_id, entity_code, record_id, deleted)`（母数据表惯例）**不可用于 `wf_instance`**——终态与重提实例同 key，重提必撞 1062；②引擎 start 幂等本身是 read-then-insert，**唯一键是使其原子化的唯一机制，不能简单删掉**。

**解法：`wf_active_instance` 指针表**（DDL 见 §7）：

- `start`：与 `wf_instance` 插入**同事务**插指针行；撞 PK ⇒ 读既有实例幂等返回；
- 终态流转**同事务**删指针行；
- `findInstanceByRecord` 语义 = 返回 `started_at DESC, id DESC` 首行（**最新一次提交**）。排序键是时间列而非 id——id 形态由宿主 `WorkflowIdGenerator` 决定（端口契约允许雪花或 UUID），UUID 字典序≠时间序，按 id 取「最新」会把已终结旧实例当进行中复用、或把进行中新实例误判陈旧指针（2026-10-23 第二轮修正，H2 负向用例锁定）；
- 重提资格（`APPROVED` 后能否再提交）由业务状态机动作的 `from_status` 约束，引擎不代决；
- 备选（未采用）：MySQL 生成列 `active_flag AS (CASE WHEN phase IN ('RUNNING','SUSPENDED') AND deleted=0 THEN 1 END) STORED` + 唯一键忽略 NULL——零新增表但有 H2 方言风险，集成测试在 H2 验证通过后可切换。

## 7. `wf_*` DDL 草案（**2026-10-24 已落 `scripts/migration/0056_wf_workflow_tables.sql`，L3 备案**）

> 列遵循 BONE `TenantAbstractEntity` 通则：`tenant_id BIGINT` + 审计列（`created_by/created_at/updated_by/updated_at/deleted`）+ 乐观锁 `version INT`（全仓惯例，**INT 非 BIGINT**）。  
> 母数据表唯一键惯例 `(…, deleted)` 只适用于「同 code 不重建」的主数据；运行时表按各自生命周期设计。  
> H2 同构 schema（`bone-workflow-spring-boot-starter/src/test/resources/wf-schema-h2.sql`）与生产 DDL **逐列同构、方言差异已逐条注明**（勿"修"）：`deleted` / `enabled` 生产 `TINYINT(1)`、H2 `TINYINT`（H2 2.x 不接受宽度后缀）；`definition_json` 生产 `JSON`（平台 JSON 列先例，写入期校验）、H2 `TEXT`（损坏 JSON 种子用例需要能写入非法文本以验证 fail-loudly）；`params_json` 生产与 H2 **均为 `TEXT` 而非草案的 `MEDIUMTEXT`/`JSON`**——它实际承载自由文本原因（驳回/挂起/终止理由，见 `OutboxStatusPort`），JSON 类型会拒掉合法写入。
>
> ⚠️ **引擎 id 列用 `VARCHAR(64)` 而非平台通例的 `BIGINT`（有意偏离，评审须知）**：`WorkflowIdGenerator` 端口**刻意不决定 id 形态**——宿主可能注入平台雪花 id，也可能注入 UUID（见端口契约）。若列写死 `BIGINT`，UUID 宿主在生产会直接写入失败；`VARCHAR(64)` 两种形态都能承载。平台实体表用自己的 `id BIGINT` 惯例不受影响，因为那些表的 id 恒为雪花长整型，而 `wf_*` 的 id 是**引擎生成、宿主决定形态**的（`PlatformWorkflowIdGenerator` 以 `String.valueOf` 渲染平台雪花 id）。**`tenant_id` 仍为 `BIGINT`**（它恒为平台雪花 id，无形态歧义）。代码与 H2 回归 schema 已按此实现（`VARCHAR(64)`），本文对齐实现口径。

> **草案 → `0056` 已落地的结构差异（2026-10-24，评审须知；列类型差异见本节首注）**：
> ① `wf_process_def` 的 `uk_def_key_version` 唯一键**未建**——v1 无发布写路径（定义由迁移/种子落库），唯一约束留给写路径落地时同批加（加早了会让「补丁式修订旧版本行」的直接运维操作被 DB 拒绝）；
> ② `wf_binding` 的 `uk_binding` 唯一键**刻意不建**——「同一实体多条生效绑定」由查询侧 fail-fast（`IncorrectResultSizeDataAccessException`）而非 DB 拒绝表达：v1 只读，运营将来配错时错误必须指向「配多了」，而不是写入时报一个看不懂的唯一键冲突；`start_action` 同步改为**可空、无默认值**（空 = 默认提交动作，由调用方解释，不在 DB 层硬编码 `'submit'`）；

### C. 动作逃逸 + 权限迁移（**唯一有生产影响的一项**）

`RuntimeActionDispatcher` 只给逃逸动作派发 Handler——要让 `submit` 驱动 `engine.start(...)`，`submit` 必须是逃逸动作；而 `RuntimeAccessGuard.canInvoke` 对逃逸动作**强制要求动作级细码**。不配套迁移 ⇒ prod 下既有提交者 403。

| 动作         | 现状  | 改为                                   | 需要的细码                                    | `requires_idempotency` |
| ---------- | --- | ------------------------------------ | ---------------------------------------- | ------------------- |
| `submit`   | 非逃逸 | 逃逸 + Handler 调 `engine.start`        | `runtime:expense_reimbursement:submit`   | **必须 true**（start 幂等复用实例，重试不得双开） |
| `approve`  | 非逃逸 | 逃逸 + Handler 调 `engine.completeTask` | `runtime:expense_reimbursement:approve`  | **必须 true**（stale-CLAIMED 补执行 = 状态推进两次） |
| `reject`   | 非逃逸 | 逃逸 + Handler 调 `engine.completeTask` | `runtime:expense_reimbursement:reject`   | **必须 true**（同上） |
| `withdraw` | 非逃逸 | 逃逸 + Handler 调 `engine.withdraw`     | `runtime:expense_reimbursement:withdraw` | **必须 true**（阶段 CAS 幂等，但业务侧不得双退） |

> **幂等开关是重试安全的前提（2026-10-23 第二轮补；2026-10-26 修正 P0-2）**：中继的幂等键现为<b>发件箱行 id</b>（每个意图一行、全局唯一），同一条意图重试复用同一 id ⇒ 平台去重，避免重复推进；而同一实例的<b>重复意图</b>（如 suspend→resume→suspend 产生的两条 `SUSPENDED`）行 id 不同 ⇒ <b>不被折叠</b>，各自的业务侧投影都生效。原 `{instanceId}:{intent}` 键会把重复意图错误折叠，导致第二次挂起的业务侧投影丢失，已改为 `intent.id()`。`RuntimeActionApplicationService` 仅在 `def.isRequiresIdempotency()` 为真时才把键传给平台（L184：`def.isRequiresIdempotency() ? idempotencyKey : null`）——4 个逃逸动作若不开此开关，键被**静默丢弃**，stale-CLAIMED 补执行 / 退避重试 = approve/reject 业务状态推进两次。§10-C 迁移表因此增加 `requires_idempotency=true` 列，接入清单对 4 个动作 fail-fast 校验。

备选：只改 `submit` 一个动作（授权面冲击最小，但审批轨迹不进 `wf_task`）。**请裁决取哪种**。回滚 = 撤销 `is_escape=1` + 回收细码，`wf_*` 数据保留不影响业务。dev 口径 `security.enabled=false` 时匿名主体带 `platform.admin`，不影响本地联调。
