## 一、已确认的根因（影响方案选型）

`JdbcRuntimeRecordService.entityHasColumn(name)` = `entity.hasColumn(name) || SYSTEM_COLUMNS.contains(name)`。
- `meta_field` 派生列不含系统列，故对 `tenant_id/created_at/...` **恒返回 true**。
- 代码因此**强制**每张 RUNTIME 物理表带 `tenant_id`/`deleted` 等系统列：缺失即 SQL 报错（Fail-fast），**并非**文档所说「不含则不隔离 / 跨租户串数据」。
- 推论：任何「按物理表真实列是否存在」的分支判断，都不能用 `entityHasColumn`，须改用 `INFORMATION_SCHEMA` 或显式元数据标志。

## 二、待执行项（按优先级）

### P0-1 · RUNTIME 表结构自动生成 / 迁移
- **问题**：§5.3.1 第 3 步仍人工 DDL；「已发布实体加字段」不在物理表落列 → 运行期 500。违背「元数据驱动」承诺。
- **方案**：catalog `publish` / 字段变更 → 经 `MetaTableExecutor`（ADR-0015 收敛路线）自动 `CREATE/ALTER`；或托管 Flyway/Liquibase。
- **Why**：消除手敲 DDL 的线上故障面；让「建模即生效」真正成立。
- **风险/门禁**：DDL 须带 `tenant_id/deleted/version/created_*/updated_*`（对齐 `bone-init.sql` 规范）；ALTER 须先 `INFORMATION_SCHEMA` 比对，禁破坏性变更（删列/改类型）。

### P0-2 · 运行时 `created_by`/`updated_by` 写入（接操作者）
- **问题**：`JdbcRuntimeRecordService` 不注入当前操作者 → 审计 `by` 列落 NULL（仅靠 DB 默认填 `at` 列）。
- **方案**：`RuntimeRecordController` 从 `TenantContext`/SA-Token 取操作者，透传给 `JdbcRuntimeRecordService.create/update`（新增 `operatorId` 参数）；物理表存在 `created_by/updated_by` 列时写入。
- **Why**：审计合规（信创/ToB 硬要求），且与 §5.A catalog 侧行为对齐。
- **依赖**：须先确认物理表 DDL 约定含 `created_by/updated_by`（见 P0-1）。

### P0-4 · 生产默认 Redis 后端（缓存 + 幂等）
- **问题**：§10.6 `replicas: 2` 但 §11 缓存/幂等**默认 Caffeine / 进程内** → 跨副本：重试重复创建、发布后读旧元数据。
- **方案**：`RuntimeEntityCatalog` 与 `StudioIdempotencyStore` 默认 `backend=redis`；多副本部署强开 Redis；准入检查卡 `replicas>1 且无 Redis → 拒绝`。
- **Why**：消除多副本正确性问题（确定性故障）。

### P0-5 · 运行时写入校验
- **问题**：`meta_field.validation_rules` 已落 DDL 但运行期零校验（必填/类型/唯一全放空）。
- **方案**：写前按 `meta_field.required`/`type`/`unique` 校验（引擎内或 SDK 校验器）；唯一冲突转 `META_DUPLICATE`。
- **Why**：声明式平台不校验 = 脏数据污染下游主数据/集成。

### P0-6 · 发布期 schema 前置校验
- **问题**：缺列/类型不符等到运行期才 500；与 P0-3 文档纠偏同源（缺列应前置拦截，而非运行期报错）。
- **方案**：`MetaEntityApplicationService.publish` 发布前比对 `INFORMATION_SCHEMA.COLUMNS` 与 `meta_field`；缺列/类型不符直接 4xx 拦截。
- **Why**：把运行期故障前移为发布期可诊断错误；同时给 P0-1 的 DDL 生成提供安全闸门。
- **落点**：`MetaEntityCatalogController` 的 `publish`（`@PreAuthorize('metadata:publish')`）→ `MetaEntityApplicationService`。

### P1-7 · ADR-0015 收敛（MetaTableExecutor SPI）
- **问题**：模式 B 直用 JDBC 绕开 SDK 统一通道，ArchUnit 门禁覆盖不到，拆库/分片难维护。
- **方案**：在 SDK 抽象 `MetaTableExecutor` SPI（或扩展 `SqlBuilder` 支持元模型表名/列白名单），engine 切到 SDK 通道，`JdbcRuntimeRecordService` 退化为 Adapter。
- **Why**：统一持久化通道；与「执行统一走 Repository」架构条文一致；P0-1 的 DDL 生成可同落此 SPI。
- **门禁**：更新 `tools/metadata-compliance-collector` 的 `runtime-jdbc-service` 扫描项，移除 As-Is 例外标注。

## 三、建议收口顺序

1. **P0-6 → P0-1**：先有发布期 schema 校验闸门，再上自动 DDL（P0-1），避免自动化放大脏模型。
2. **P0-4**：配置级改动，独立可先行，风险最低、收益确定。
3. **P1-7**：作为 P0-1/P0-5 的承载通道，与之一并设计，避免二次重构。
4. **P0-2 / P0-5**：依赖 P0-1 的 DDL 约定落地后实施。
