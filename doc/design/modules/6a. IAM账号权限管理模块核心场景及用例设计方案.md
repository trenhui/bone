## 1. 要回答的三个问题（结论先行）

### 1.1 部门、用户有归属租户吗？—— 有，行级隔离已落地（As-Is）

| 资源 | 表 | 租户归属 | 隔离方式 |
|------|-----|---------|---------|
| 租户 | `iam_tenant` | 平台专属 | 仅平台管理员 CRUD；`id=0` 为平台租户 |
| **账号（用户）** | `iam_account` | **有** `tenant_id NOT NULL` | 行级隔离；唯一键 `(tenant_id, username)`，跨租户允许重名 |
| **部门** | `iam_dept` | **有** `tenant_id NOT NULL` | 行级隔离，每租户一棵独立部门树 |
| 角色 | `iam_role` | 有 | 行级隔离 |
| 菜单 | `iam_menu` | 有 | 行级隔离，租户自管本租户菜单树 |
| 权限目录 | `iam_permission` | **平台级共享，无 tenant_id** | 租户经角色绑定消费，不可自建权限码 |

领域侧 `Account`/`Dept` 均继承 `TenantAggregateRoot`；读侧 `resolveTenantFilter` 对租户上下文>0 强制过滤，写侧 `resolveInsertTenantValue` 以可信 `TenantContext` 覆写（ADR-0029），平台管理员代租户写走 `TenantContextRunner.callAs`（ADR-0031）。

### 1.2 用户属于部门吗？—— **当前不属于（As-Is 缺口，本方案 P0）**

`iam_account` **没有 `dept_id`**，账号与部门之间没有任何归属关系：部门树建得再全，也只是信息孤岛——这是「模块功能割裂」的最大根源。修补方案见 §6 G1。

### 1.3 用户管理要不要放到组织机构管理下？—— **要（导航层合并，后端聚合不动）**

业界通行做法是「**组织与人员一体**」：

| 产品 | 做法 |
|------|------|
| 飞书 / 钉钉 / 企业微信 | 「通讯录」单入口：左侧组织树 + 右侧成员列表，成员必须挂部门 |
| Microsoft Entra ID | Users 与 Groups 平行，但管理台按目录树浏览成员 |
| Ant Design Pro 中后台模板 | 组织机构页标准主从布局：左树（部门）+ 右表（成员） |
| AWS IAM Identity Center | Users 归属 Organization 维度统一管理 |

**Bone 落地建议**：
- **导航与页面层**：主入口改为「组织机构」页（左部门树 + 右成员表联动），菜单分组按业务语义重组（§6 G2）——用户心智是「在组织里管理人」，而不是「组织一个菜单、用户另一个菜单」。**采用双入口**：保留 `/accounts` 独立页（批量导入/导出、跨部门筛选等批量操作更顺手），组织页内嵌「成员」Tab 作为日常入口；两者共用同一套权限码与后端接口，不做功能分叉。
- **后端领域层**：`Account` 与 `Dept` 保持**两个独立聚合**（部门停用/删除不应级联摆布账号聚合；跨聚合引用只存 ID），不合并——合并聚合会放大事务边界并违反 ADR-0030 的读侧边界。
- **一人多部门的取舍**：G1 先落**单 `dept_id`（主部门）**，满足「成员归属某部门」的 90% 场景；「主部门 + 兼任多部门」（飞书/钉钉模型）需 `iam_account_dept(account_id, dept_id, is_primary)` 关系表与数据权限引擎配合，列为 **[Vision]**，单字段方案不阻塞其演进（届时可保留 `dept_id` 作主部门冗余列）。
- **路由与权限码不变**：`/accounts` 路由、`iam:accounts:read|write` 权限码保持，仅前端页面重组，存量授权零影响。

## 2. 双管理员定位（能做什么 / 不能做什么）

> 设计结论沿用详设 §2.9：**单登录页 + 登录后按 `tenantId` 分流**（阿里云/飞书模式），安全边界在权限码而非前端守卫。载体是**角色**而非新账号类型。

### 2.1 定位矩阵

| 维度 | 平台管理员（运营方） | 租户管理员（企业方） |
|------|---------------------|---------------------|
| **一句话定位** | 平台运营者：经营租户、维护权限目录与平台菜单、全局巡检 | 租户 IT 管理员：在本租户内搭建组织、管理成员、定义业务角色 |
| **tenant_id** | 0（平台租户） | >0（随租户） |
| **As-Is 载体** | `is_admin=1` 超管（fallback 全部权限码） | `TENANT_ADMIN_<code>` 角色（bootstrap 自动创建） |
| **管什么** | 租户全生命周期（创建/配额/启停）、权限目录 `iam_permission`、平台级菜单、全局会话、平台域审计 | 本租户账号/角色/组织机构/菜单/审计；本租户应用成员授权 |
| **不碰什么** | 不代租户做业务操作（仅代开通，不代配置） | 平台域（`/tenants`、`/permissions`、平台菜单、全局会话）一律 403 |
| **权限码域** | 全部，含平台域 `iam:tenants:*`、`iam:permissions:*`、`iam:sessions:*` | 仅租户域 `iam:accounts:*`、`iam:roles:*`、`iam:depts:*`、`iam:menus:*`、`iam:audit:*`、`iam:apps:*` |
| **租户视角的"天花板"** | 可看任何租户（代操作须显式指定租户） | 永远只见本租户（行级隔离强制，越权传参被忽略） |

### 2.2 两类管理员的职责红线（防越权设计）

1. **平台管理员不代做租户内配置**：租户开通后，组织/成员/角色配置由租户管理员自助完成；平台管理员代写仅存在于 bootstrap 事务内（`TenantContextRunner.callAs`）。
2. **租户管理员既不产生权限码，也不得绑定平台域权限码**（两条都要，缺一即漏）：
   - **不造码**：`iam_permission` 平台级共享，租户无写接口；
   - **不绑平台码**：租户**可以读取**共享权限目录，若允许把 `iam:tenants:*` / `iam:permissions:*` / `iam:sessions:*` 绑进本租户角色，其成员即可凭该码调用平台域接口——这些接口的 `@PreAuthorize` **只校验权限码、不校验调用者 tenantId=0**（如 `TenantController`），等于「租户自授平台能力」。
   - **实现（As-Is，本次复核后补齐）**：`RoleApplicationService.assignPermission` 在绑定侧拦截——调用方为租户上下文（tenantId>0）且待绑权限含平台域码（`Permission#isPlatformScoped()`，按 `resource_path ∈ {tenants, permissions, sessions}` 判定）时抛 `IAM_PERMISSION_PLATFORM_ONLY`（403）；平台管理员（tenant 0）不受此限。平台域集合当前为代码常量，[Target] 收敛为 `iam_permission.scope` 列。
3. **前端守卫只是体验**：`PlatformRoute` 重定向不承担安全，`@PreAuthorize` 403 才是边界。

## 4. 核心用例

> 用例卡格式：参与者 / 前置条件 / 主流程 / 异常分支 / 权限码。**As-Is** 已实现的标注；**[Target]** 为本方案新增设计。

### 4.1 平台管理员用例组

#### UC-P1 租户开通（Onboarding）——全链路的起点（As-Is）

| 项 | 内容 |
|----|------|
| 参与者 | 平台管理员 |
| 前置 | 已登录（tenant 0） |
| 主流程 | ① 填写租户名称/编码/配额 → ② `POST /tenants` 同事务：租户落库 → 创建 `TENANT_ADMIN_<code>` 角色 → 绑定租户域权限码 → 创建 `<code>_admin` 管理员账号（在 `TenantContextRunner.callAs(tenantId,…)` 内写，防 ADR-0029 覆写到 tenant 0）→ 账号-角色绑定 → ③ 响应返回 `initialPassword` **仅此一次** → ④ 平台管理员线下转交租户 |
| 异常 | 任一步失败整体回滚（`Propagation.MANDATORY`）；配额/编码冲突返回业务错误码 |
| 权限码 | `iam:tenants:write` |
| 串联出口 | 租户管理员拿到凭据后进入 UC-G1 → UC-T1 |

#### UC-P2 租户生命周期管理（As-Is）

| 项 | 内容 |
|----|------|
| 参与者 | 平台管理员 |
| 主流程 | 租户列表（keyword 检索）→ 查看详情（配额使用率）→ 编辑配额（`max_accounts`/`max_roles`，`TenantQuotaEnforcer` enforcement）→ 停用/启用 → 删除（`id=0` 平台租户禁删） |
| 异常 | 停用后该租户全部账号登录被拒；配额收紧不回收存量，仅约束增量 |
| 权限码 | `iam:tenants:read` / `iam:tenants:write` |

#### UC-P3 权限目录与平台菜单维护（As-Is）

| 项 | 内容 |
|----|------|
| 参与者 | 平台管理员 |
| 主流程 | ① 新权限点登记 `iam_permission`（模块/资源/动作三元组）→ ② 同步 `DefaultPermissionCodes.adminFallback()`（**漏加=超管 403 的历史坑**）→ ③ 同步 `bone-init.sql` 种子与运行库幂等补种 → ④ 平台菜单树维护（`iam_menu`，tenant 0 视角） |

| 权限码 | `iam:permissions:read` / `iam:permissions:write` |

#### UC-P4 平台审计与巡检（As-Is）

| 项 | 内容 |
|----|------|
| 参与者 | 平台管理员 |
| 主流程 | 全局会话查看/强制下线（`iam:sessions:*`）→ 平台域操作审计检索/CSV 导出（10000 行上限）→ 审计保留期设置（`iam_audit_settings`） |
| 权限码 | `iam:sessions:read|write`、`iam:audit:read|write` |

#### UC-P5 应用注册与授权（As-Is，衔接「应用管理」）

| 项 | 内容 |
|----|------|
| 参与者 | 平台管理员 |
| 主流程 | 注册应用/模块（`/apps`、`/apps/{id}/modules`）→ 为租户/成员授予应用角色（admin/developer/viewer）→ 应用内权限码由各模块登记 |
| 说明 | 应用/模块聚合根属 IAM 上下文（ADR 已定），前端页面在 bone-iam-app（`/iam#/apps`） |

## 5. 端到端流程串联（三条主线）

### 流程 A：从零到可用（租户开通主链路）——把割裂的功能串成一条线

```
平台管理员                     租户管理员                        业务成员
──────────                   ──────────                       ────────
UC-P1 租户开通 ──凭据──▶ UC-G1 登录+强制改密
UC-P3 权限目录就绪            UC-T1 组织搭建（部门树）
UC-P5 应用注册               UC-T3 建业务角色+绑权限码
                             UC-T2 成员入驻（挂部门+绑角色）──凭据──▶ UC-G1 登录
                             UC-T4 菜单定制                     按角色权限使用平台
                             UC-T5 审计自查 ◀──────── 审计记录 ◀──────┘
UC-P4 平台巡检（会话/审计）
```

**关键串联点**：
1. **UC-P1 是唯一需要两类管理员交接的环节**（initialPassword 一次性转交）——此后两条管理员线互不交叉。
2. **UC-T1→UC-T2 是组织与成员的串联点**：依赖 G1（`dept_id`）落地，否则流程在成员入驻处断链。
3. **UC-T3 是成员→能力的唯一桥梁**：成员自身无直连权限（无 `iam_account_permission`，MVP 仅 RBAC），所有能力都经「角色」获得。
4. **权限码是全程通用语言**：UC-P3 生产 → UC-T3 消费 → UC-T4 渲染 → 各模块 `@PreAuthorize` 执行。

### 流程 B：权限调整（角色变化）

```
业务诉求（如新岗位）→ 租户管理员 UC-T3：新建/调整角色 → 绑定权限码（租户域内）
  → 给成员授予/回收角色 → 下一次登录或种子刷新后生效 → UC-T5 审计留痕
```

> 生效语义：**角色-权限变更经 `AccountAuthorityCache` evict 通道即时生效**；直接改库必须手动清 Redis 缓存（key `iam:authz:scopes:account:<accountId>`），否则最长滞后 30 分钟。

### 流程 C：成员离职 / 安全事件

```
触发（离职/异常）→ 租户管理员：禁用账号（status=0，立即拒绝登录）
  → 平台管理员 UC-P4/G3：必要时全局会话强制下线 + 吊销 refresh
  → 审计留痕 → 追溯（UC-T5 租户域 / UC-P4 平台域）
```

## 6. 割裂修补清单（Gap → 方案 → 优先级）

| ID | 割裂点 | 方案 | 优先级 | 层级 |
|----|--------|------|--------|------|
| **G1** | **账号无部门归属**：`iam_account` 无 `dept_id`，成员挂不进组织树 | ① DDL：`iam_account` 加 `dept_id BIGINT NULL`（索引 `idx_iam_account_dept`）+ `bone-init.sql` 同步；② `Account` 聚合加可选 `deptId`（跨聚合只存 ID，不级联）；③ 创建/编辑表单加部门 `TreeSelect`；④ 组织机构页左树右表联动、按部门过滤成员 | **P0** | [Target] |
| **G2** | **导航割裂**：账号、组织机构、菜单三个菜单并列，无业务分组 | 菜单重组为业务语义分组：「组织与成员」（组织机构+账号并入一页主从布局）/「权限与角色」（角色+权限目录）/「安全与审计」（审计+会话+设置）；路由与权限码不变，仅页面与 shell 菜单调整 | P1 | [Target] |
| **G3** | **授权无闭环**：角色页看不到成员、账号页角色下拉无归属校验提示 | 角色列表加 `memberCount`（`iam_account_role` 聚合）+ 角色详情抽成员 Tab；账号页展示已绑角色并支持行内调整 | P1 | [Target] |
| **G4** | **应用授权与 IAM 角色两张皮**：应用成员（admin/developer/viewer）与租户角色体系无关联 | 梳理为：应用成员授权是**应用域的独立 RBAC 面**（对齐 GitHub Org/Collaborator 模型），文档明确二者边界与适用场景；[Vision] 再考虑统一到策略引擎 | P2 | [Target] |
| **G5** | **审计不可跳转**：审计记录与被变更对象无链接 | 审计列表按 `resource_type+resource_id` 生成跳转（有读权限时） | P2 | [Target] |
| **G6** | **部门停用不约束成员**（G1 落地后暴露） | 禁用部门时提示在编成员数；成员列表按部门状态弱化标识 | P2 | [Target] |
| **G7** | **租户可自授平台能力**：绑定侧只校验角色归属、不校验权限码域，租户管理员能把 `iam:tenants:write` 等平台域码绑进本租户角色，而平台域接口只做 `hasAuthority` 校验 | `RoleApplicationService.assignPermission` 增加平台域拦截（`Permission#isPlatformScoped()` + `IAM_PERMISSION_PLATFORM_ONLY` 403）；平台管理员不受限 | **P1（安全）** | ✅ **As-Is（本次已修）** |
| **G8** | **登录事件不入审计**：审计拦截器在无主体请求（`/login`、登录失败）下 `TenantContext` 为空，写 tenant-scoped 表被 SDK 拒绝，最该留痕的登录反而全丢 | 审计写入包 `TenantContextRunner.runAs(tenantId, …)`，无主体时以平台租户 0 兜底 | **P1** | ✅ **As-Is（本次已修）** |

**实施批次建议**：G1（DDL+聚合+表单）单独一批（含 `mvn test`+ArchUnit+补 DDL 自证）；G2+G3 一批（纯前端+菜单）；G4~G6 随迭代。
