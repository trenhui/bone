## 1. 概述

### 1.1 背景

Bone 控制台当前仅支持中文：前端 UI 文案 100% 硬编码中文、错误提示直接展示后端中文 `message`、AntD `ConfigProvider` locale 写死 `zhCN`；后端无 `MessageSource` / `LocaleResolver` / `Accept-Language` 解析、时间字段未统一 UTC 时区策略。

但架构已预留正确接缝：《Bone-国际化规范.md》（2026-05-17）已定义稳定键、前后端分离、UTC 时区原则；错误码已落地为稳定的 `errorCode` 字符串（各模块 `*ErrorCodes` + `*Errors`，码不带文案，`ProblemDetail.errorCode` 为跨系统契约）；`globalContext` 已预留 `locale: 'zh-CN' | 'en-US'` 类型——只是写入点全部写死 `'zh-CN'`。

### 1.2 目标

- 首期支持 **`zh-CN` + `en-US`** 双语，架构按可扩展设计（后续加语言只加语言包）。
- 打通 locale 单源传递链路，支持运行时切换、子应用继承。
- **首期（P0–P2）验收范围**（与 §7 路线图逐条对应，避免"目标写了、阶段没做"）：
  - 错误消息本地化（errorCode → 前端 `errors` 命名空间）——用户感知最强；
  - 语言切换与子应用继承（locale 单源链路）；
  - 日期/数字格式化（UTC + `Intl` / `dayjs`；**前置**：§6.4 后端时间字段 UTC 契约先落地，否则时间显示会静默偏移）；
  - **壳层高频通用文案**（`common` / `nav`：导航、菜单、空态、按钮）；
  - 业务枚举显示多语言（`enums` 命名空间 + `dict.label` 兜底链）。
- **[Vision]（不写入首期验收）**：各微应用**全量页面**文案 key 化（§7 P3）。
  > 为什么首期要带上壳层通用文案：若只做错误文案，英文用户体验会变成"英文报错 + 全中文界面"，比纯中文更割裂；带上壳层后至少形成可用的英文界面骨架。全量页面文案改动面覆盖 8 个应用数百组件，收益取决于是否真有英文用户，故仍推迟（§7 P3）。

### 1.3 范围

**纳入（首期 = P0–P2）**：前后端错误消息本地化、日期/数字格式化、语言切换与继承、壳层通用文案（`common` / `nav`）、**业务枚举的多语言显示**（**值域编译期可知的内置枚举**由前端 `enums` 命名包承担；后端 SysDict 继续作为**值域真源**返回 `code`/`value`/`sort`/`status` 与 `label` 兜底。前端默认用 `i18n.t(\`enums.${dictType}.${dictCode}\`)`，**未命中回落 `dict.label`**；不修改后端 SysDict 表结构）。

**分期**：各微应用**全量页面** UI 文案属 §7 P3，划为 [Vision]，不写入首期验收（理由见 §1.2）。

**明确不做**（降低复杂度，避免范围蔓延）：

| 排除项 | 原因 |
|--------|------|
| 业务数据多语言（实体字段、租户名等） | 属数据建模，非控制台 i18n |
| 租户级语言配置（`iam_tenant` 加 language 列） | DDL 变更属 L3，需架构审批，等有真实诉求 |
| 后端 SysDict 字典多语言 label 改造 | **首期内置枚举的文案由前端 `enums` 命名空间承担**（默认命中语言包，未命中回落 `dict.label`），故不需要给 SysDict 加翻译列。注意边界：**运行期由运营/租户新建的字典条目无法被前端预置**，此时只能显示 `dict.label`（中文单语）；若未来要求这类条目也双语，走独立 `i18n_message` 表（属"业务数据多语言"），**不是**给 `sys_dict` 加列。详见 §3.1 |
| 后端全量业务文案翻译（MessageSource） | 见 §3/§6.3 决策，默认不做 |
| 前端 UI 文案/错误文案放入 system 模块后台配置 | UI 文案是代码的一部分（改文案与改组件同 PR 走 review）；errorCode 是契约（禁止运营改乱告警口径）。详见 §3.1 分层决策 |
| 新建独立"国际化翻译管理"后台 | 语言数 ≥ 5 + 专业翻译团队时才值得，当前 zh-CN + en-US 纯静态 JSON 足够。属 [Vision] |

## 2. 现状与差距

> 本节为 **As-Is**，基于全仓扫描（2026-09-25）。

| 项 | 设计规范 | 实现现状（含证据） |
|----|----------|----------|
| 后端稳定 `errorCode` | 7 模块 `*ErrorCodes` + 状态码表 | ✅ 码常量已落地，`IamErrors.DEFAULT_HTTP_STATUS` 是"码→状态"真源（类加载期 `checkEveryCodeRegistered()` fail fast）；但各 `*ExceptionHandler` 仍有硬编码中文 |
| 码表 ↔ 台账一致性 | 《Bone-错误码登记》§6 台账为准 | ⚠️ **已漂移，现已可脚本校验**：`*ErrorCodes.java` / `*Errors.java` 去重后 **142** 个码值（v1.6 新增 `CommonErrorCodes` 后实测），§6 台账 **111** 条——**代码有台账无 70 条**（未登记）、台账有代码无 39 条（前瞻/漏实现）。`scripts/check-i18n-sync.py` 已落地，存量 70+123 条进**显式白名单** `config/i18n/errorcode-baseline.json`，**新增码一律不豁免** |
| `ProblemDetail.errorCode` | OpenAPI `ProblemDetail.yaml` 已把 `errorCode` 列为 **required** | ✅ **P0-A 后端 handler 已收口（2026-09-25，代码待评审）**：`bone-core` 统一 `ProblemDetails` 工厂 + `CommonErrorCodes`；**bone-web、IAM、masterdata、system、generator 五个 handler 已全部产出 `ProblemDetail`（含 `errorCode`），`data` 不再为 `null`**（见 §12.3）；**bone-blueprint 为样板**；metadata-server、extension-studio 此前已产出。待收口：各模块契约测试（§12.3 #3）、存量 `LocalDateTime` 时间字段 UTC 契约（§6.4）。 |
| 后端运行时 i18n | — | ❌ 无 `MessageSource` / `LocaleResolver` / `Accept-Language`，无 `messages*.properties` |
| 前端 i18n 库 | 规范建议 react-i18next | ❌ 16 个 package.json 零 i18n 依赖 |
| 前端 locale 管道 | Shell 切换、子应用继承 | ❌ `BoneAppProvider` locale 硬编码 `zhCN`；`globalContext.locale` 三处写入全写死 `'zh-CN'`；`bone:theme:change` 事件**仅 `bone-iam-app` 订阅**（其余 6 个微应用无订阅代码） |
| locale 事件机制 | 单一机制 | ⚠️ **两套并存**：design-system 的 `BoneAppProvider` 监听原生 `bone:theme-change`（`window.dispatchEvent`），Shell/iam-app 走 `core-event-bus` 的 `bone:theme:change`——二者 payload 形状与触发点都不同 |
| UI 文案 | — | ❌ 100% 硬编码中文（表头/Toast/空态/状态 Tag） |
| 错误展示 | errorCode→文案映射 | ❌ 直接 `message.error(response.message)` 散点，变量形态实测 **78 处**（extension 28 / masterdata 24 / metadata 22 / iam 3 / system 1），多数为 `response.message \|\| '中文兜底'` 双兜底；全部位于 `apps/*/src/pages`（React 组件内） |
| 业务枚举文案 | 前端 `enums` 语言包 + `dict.label` 兜底 | ❌ 现状是**页面本地数组**：`connectorTypes` / `fieldTypes` / `ruleTypes` / `operationTypes` 各写一份 `{ value, label: '数据库' }`；真正调用 SysDict API 的只有 `bone-system-app` 的字典管理页；且 `sys_dict.type` 大小写无约束（seed `SYS_STATUS` vs 领域测试 `order_status`） |
| 共享包可被消费性 | 前端代码放 `shared-utils` | ⚠️ `@bone/shared-utils` 目前**无任何 app 引用**；`package.json` 无 `exports` 字段（`main` 指向 `src/index.ts`），`@bone/shared-utils/i18n` 这类子路径当前解析不到 |
| 时间/数字 | UTC + `Intl.NumberFormat` | ❌ 仅 3 处 `new Date(v).toLocaleString()`（含 `shared-utils/src/format.ts` 自身），无 `Intl.*` |
| **时间字段 UTC 契约** | API 输出带偏移 ISO-8601（`...Z`） | ✅ **已落地（2026-09-25，代码待评审）**：`bone-blueprint`（v1.6 样板）+ `bone-system`（6 DTO / 5 MapStruct assembler）+ `bone-iam`（4 DTO / 3 `*WebConverter` + `MeController`）+ `bone-masterdata`（4 DTO / 4 `*WebConverter`），全部 `LocalDateTime`（`masterdata` 的 `MasterDataFieldDetailResp` 原用 `java.util.Date`）→ `Instant`、边界 `ZoneOffset.UTC` 归一、`application.yml` 加 `spring.jackson.time-zone: UTC`/`write-dates-as-timestamps: false`、`UtcTimeContractTest` 全绿（system 7 + IAM 3 + masterdata 4）。<br>**实测澄清契约面**：真正会序列化进 API 响应的时间字段仅集中在 **14 个 `adapter/web/dto/response/*Resp`**（IAM 4 + masterdata 4 + system 6）；其余全部 `LocalDateTime`/`Date` 在 domain / infra / entity 层、不进 API 响应，**不该动**。所谓"160 文件"是被夸大的契约面。其余模块（metadata / generator / integration / extension / studio）adapter/web 层无时间字段，无需改动。详见 §6.4 |

**一句话定位**：处于「可 i18n」而非「已 i18n」。规范 §6 两项检查项（新 errorCode 加 en-US 文案键、关键错误不硬编码中文）当前均未勾选。

> **对方案范围的影响（重要）**：`ProblemDetail` 的"分布不均"曾直接决定 P1 的成色——`showError()` 的 errorCode 分支**只在产出了 ProblemDetail 的模块生效**。截至 2026-09-25，后端 8 个模块（IAM / metadata-server / extension-studio / masterdata / system / generator / bone-web / blueprint）**已全部产出 `ProblemDetail`**，英文用户不再因模块而异。剩余阻断项是 §6.2.4 契约测试（守住"非 2xx 必带 errorCode"）与 §6.4 时间字段 UTC 契约（目前仅 blueprint 落地）。因此 §6.2.1 把"统一到 `bone-core` 模型"列为 P0 阻断项，现已解除；§6.2.4 用契约测试守住。

## 3. 核心原则

| 原则 | 说明 |
|------|------|
| 稳定键 | 后端 `errorCode`、前端 i18n key **不随文案变化**（改文案不破聚合/告警/契约） |
| 展示分离 | 展示文案在前端语言包；后端 `message` 始终为中文 fallback |
| 单源 locale | 由 Shell 决定语言，经既有 `core-event-bus`（`bone:theme:change`）广播，子应用**被动继承**，不自决 |
| 回退链 | 本表下方「回退链唯一真源」为准（`errors.{code}` 命中 → `[errorCode] + 后端中文 message` → 后端中文 message），§3 / §5.4.2 / 《Bone-国际化规范》§3 三处表述以本节为准 |

**关键决策**：后端**不做业务文案翻译**（不引入 `MessageSource` 全量翻译）。展示文案归前端，后端只给稳定 `errorCode` + 中文 `message`（fallback）。理由：与《Bone-国际化规范.md》§1「分离」一致；避免文案散落两处、违背错误码「可聚合/可 i18n」契约；前端本就需持有双语文案，多一套后端翻译是重复维护。

**回退链 UX 设计**（重要，影响英文用户体验）：

| 场景 | 英文用户看到 | 保障机制 |
|------|------------|---------|
| errorCode 存在 + en-US 有翻译 | ✅ 英文翻译 | **主路径**，CI 阻断缺失 |
| errorCode 存在 + en-US 无翻译 | ⚠️ `[IAM_LOGIN_FAILED] 用户名或密码错误` | 显示 errorCode 前缀比纯中文好给英文用户参考；**CI 必须阻断**这种 PR |
| 无 errorCode（硬编码 handler 未改造） | ⚠️ 后端中文 message | 最后兜底；通过 §6.2.2 把所有 handler 补齐 errorCode 逐步消除 |

> zh-CN 语言包**必须**与 en-US 同步维护（同一套 errorCode key），否则中文用户也会看到裸 `errorCode`。这一点同样由 §8 CI 脚本保障。

**回退链唯一真源（本节定义，其他章节引用）**：

1. `data.errorCode` 存在且 `errors.{errorCode}` 命中 → 显示**翻译文案**（唯一最佳路径）；
2. `data.errorCode` 存在但语言包未收录 → 显示 `[errorCode] + 后端中文 message`（给英文用户一个可检索的稳定标识，CI 阻断该状态进入主干）；
3. `data.errorCode` 为 `null`（handler 未改造 / 未产出 `ProblemDetail`）→ 显示后端中文 `message`（最后兜底，由 §6.2 逐模块消除）。

> **与《Bone-国际化规范》§3 的差异（需同步）**：规范当前写「无翻译 → 显示后端 `message` → 显示 `errorCode`」，即**先中文后码**；本方案调整为**码始终与中文并列**（`[码] 中文`），理由是纯中文对英文用户零信息量、纯裸码对中文用户零可读性，并列是双语期成本最低的降级。§9 已把"规范同步"列为交付项。

### 3.1 i18n 文案真源分层（重要，别搞混）

不同类型的文案有不同的真源和维护者，**不是全部一个来源**。搞混会导致职责混乱和漂移风险：

| 文案类型 | 真源 | 维护者 | 为什么不能换 |
|----------|------|--------|-------------|
| **① 前端 UI 文案**（菜单/按钮/表头/空态/Tooltip） | 前端静态 `en-US.json` / `zh-CN.json` | 开发者（PR 走 review） | UI 文案是**代码的一部分**——改文案和改组件布局/交互走同一个 PR（Git diff 天然就是审计），分离会导致"组件删了但配置残留" |
| **② 错误文案**（`errorCode` → 翻译） | 前端静态 `errors` 命名空间 + 后端 Java `*ErrorCodes` 常量 | 开发者（PR + CI 强制绑定） | errorCode 是**跨系统契约**——监控聚合、告警规则、日志检索全靠它，不能让运营改乱口径。新增 errorCode 时开发者同时写好双语文案是最自然的工作流，CI 强制绑定（§8） |
| **③ 业务枚举的多语言显示**（订单状态 Tag、支付方式下拉） | **文案**：前端静态 `enums` 命名空间；**值域**：后端 SysDict（`type`/`code`/`value`/`sort`/`status` + `label` 兜底） | 开发者（同 UI 文案） | 见下方详细说明——**SysDict 不负责文案，只负责值域；"翻译归前端"的前提是该枚举的值域在编译期可知** |
| **④ 运营要能动态修改的文案**（如运营商定制的欢迎语） | — | 运营/产品 | **Bone 首期无此需求**。如果未来有，单独新建 `i18n_message` 表（属 tenant customization / message-template 存储，**不是** UI 翻译），**绝对不复用 SysDict** |

#### 关键：业务枚举的翻译链路（别搞反）

```
后端 SysDict 查询（业务数据源）
   │ 返回 JSON：{ type: 'ORDER_STATUS', code: 'PAID', value: 1, label: '已支付' }
   │                                           ↑ 中文兜底，翻译未命中时才用
   ▼
前端列表状态 Tag 组件（状态列渲染）
   │
   ├─ 1) 取后端返回的 type + code：dictType='ORDER_STATUS', dictCode='PAID'
   ├─ 2) 构造 i18n key：`enums.${dictType}.${dictCode}` → 'enums.ORDER_STATUS.PAID'
   │     ★ key **原样**使用后端 type，禁止任何大小写/驼峰转换（见下方说明）
   ├─ 3) 查语言包：i18n.t('enums.ORDER_STATUS.PAID')
   │     en-US.json: { enums: { ORDER_STATUS: { PAID: "Paid" } } }
   │     zh-CN.json: { enums: { ORDER_STATUS: { PAID: "已支付" } } }
   ├─ 4) 未命中（key 不存在）→ 回退 dict.label（'已支付'），**绝不显示裸 key**
   └─ 5) 渲染 Tag → 用户看到 "Paid" / "已支付"（随 locale 切换）
```

**后端 SysDict 的 `label` 字段只作为中文兜底**，前端渲染时用 `i18n.t(\`enums.${dictType}.${dictCode}\`)` 做翻译，**未命中时才回退 `dict.label`**。这是本方案 §5.3 语言包 `enums` 嵌套结构存在的意义——`enums.ORDER_STATUS.PAID` 正好命中真正的嵌套 JSON。

**key 必须原样使用后端 `type`，禁止大小写/驼峰转换**（已核实）：`bone-init.sql` 中 `sys_dict` **只有 CREATE TABLE（356 行）、无任何 INSERT 种子数据**——字典的 `type`/`code` 是**运行时由业务/管理员录入**的，字面大小写本就无固定真源。因此前端**绝不能**做 `ORDER_STATUS → OrderStatus` 之类的归一化映射：一旦转换，转换规则与后端录入值必然漂移，还凭空多一层映射表要维护。约定：语言包 `enums` 下的 key 与后端 `type` **字面完全一致**（建议字典录入统一用大写下划线）。

> ⚠️ **配套缺口（P2 前置，实测 2026-09-25）**：既然 key 与 `type` 字面绑定，就必须约束 `type` 的字面形态，否则语言包永远对不上：
> - **大小写无约束**：`scripts/seed-system-dicts.py` 用 `SYS_STATUS` / `SYS_YES_NO`（大写下划线），而 `SysDictTest` 用 `order_status`（小写下划线）——`enums.${type}.${code}` 是**大小写敏感**查找，一个 case 不一致就静默回落到中文，且无任何机制发现。
> - **长度不一致**：`DictType` 值对象允许 `value.length() > 64` 才报错，而 DDL 是 `type VARCHAR(50)`——51~64 字符的类型会在入库时失败（或被截断），属既有缺陷。
>
> 处理方式（三选一，属 P2 前置、只需一处生效）：① 在 `DictType` 值对象上加规范化 + 字符集校验（统一 `UPPER_SNAKE`，`[A-Z][A-Z0-9_]*`）并修正长度上限；② 语言包 key 只与**内置清单**对齐（不依赖运营录入值），运营新增条目一律走 `label` 兜底；③ 两者都做（推荐）。**涉及 DDL 长度调整属 L3，需架构师审批。**

**枚举翻译回退链**（防裸 key）：`i18n.t(\`enums.${dictType}.${dictCode}\`)` 未命中时（key 不存在，i18next 返回 key 本身），**回退到 `dict.label`**（中文兜底），绝不把 `enums.ORDER_STATUS.PAID` 这类裸 key 显示给用户。

> **范围边界**：`enums` 命名空间只覆盖**静态已知**的业务枚举（订单状态、启用/禁用等）。`sys_dict` 是运行时数据，若上线后新增字典类型而前端未预置翻译，走 `dict.label` 中文兜底即可——这是运行时数据的正常降级，**不属于缺译缺陷**。

#### 判定标准：值域可知性（这条决策的真正依据）

"后端 SysDict 不负责翻译、前端按 code 查 `i18n.t()`"是否成立，**不取决于前后端分工偏好**，而取决于两条客观判据：**文案归谁维护**、**值域能否在编译期枚举**。按这两条，实际是三层，不是一刀切：

| 枚举来源 | 值域编译期可知？ | 文案归属 | 结论 |
|----------|----------------|---------|------|
| **代码枚举**：后端 Java 枚举 / 前端常量（连接器类型 `REST`/`JDBC`、字段类型、操作类型…） | ✅ 是 | 前端 `enums` 语言包 | 本方案成立；key 建议取**代码里的枚举标识**，不必绑 DB 字符串（当前这些文案就散落在页面本地数组里，见下方 As-Is） |
| **系统内置字典**：`SYS_STATUS` / `SYS_YES_NO` / `SYS_LOG_LEVEL` / `SYS_ALERT_LEVEL` 等 | ⚠️ 半是（有清单，但 DB 行可被运营改） | 前端 `enums` 语言包 + `label` 兜底 | 成立，**但必须先把"内置清单"落成机器可读真源**（否则 `enums` 覆盖率无法校验，见 §8.2） |
| **运行期新建字典**：租户/运营在字典管理页新增的 `type`/`code` | ❌ 否（前端不可能知道） | 只能 `label`（中文单语） | 前端**无法**承担；要双语只能新建 `i18n_message` 表（属"业务数据多语言"，§1.3 排除项），**不给 `sys_dict` 加列** |

> **As-Is（2026-09-25 核实）**：当前前端枚举文案**根本不是**从 SysDict 来的——`ConnectorManagement.tsx` 的 `connectorTypes`、`FieldManagement.tsx` 的 `fieldTypes`、`QualityRuleManagement.tsx` 的 `ruleTypes` 都是页面内硬编码的 `{ value, label: '数据库' }` 数组；真正调用 SysDict API 的只有 `bone-system-app` 的字典管理页。因此 P2 的正确顺序是：**先收敛到统一入口（§5.3）→ 再把这些数组抽进 `enums` 语言包**，而不是"把后端 label 换成前端翻译"。

**为什么不在 SysDict 表加翻译列/关联表？（已核实真实表结构）**

已读取 `bone-init.sql` 中 `sys_dict` 真实定义（**356–374 行**，`CREATE TABLE sys_dict`）：建模为 `type VARCHAR(50) + code VARCHAR(100) → label VARCHAR(100) / value VARCHAR(255)`（另有 `type_name VARCHAR(100)` 仅承载类型显示名），是**二维 (type,code) 键值对，无 locale 列、无 module 维度**。把 i18n 塞进去的硬伤如下（**注意：不包含"长度不够"——枚举 label 本就是短标签，`VARCHAR(100)` 绰绰有余；"长度"论据只对错误长文案成立**）：

1. **维度缺失**——i18n 是 `(locale, module, key) → text` 的**三维**查找；`sys_dict` 只有 `(type,code)` 二维、无 locale。要么把 locale 塞进 code（key 污染、lookup 退化），要么给 `sys_dict` 加列——那是改**公共表结构**，牵连所有字典消费方（status/sort 语义全变），违反最小改动。
2. **语义混装**——SysDict 是**值域真源**（有哪些 code、`value` 业务语义、`sort` 排序、`status` 启停），文案是**展示资产**。二者同表同源后，"调整排序 / 停用某项"（运营日常）与"改文案"（应走代码 review）会混进同一条审批路径与同一个变更记录。
3. **治理越界 + 不可审计**——`label` 由运营在字典管理页直接可改，且 `sys_dict` **只有 `updated_at` / `version`、无历史表**：改完即覆盖，文案变更不进 Git、无法 diff、无法回溯，也无法与组件改动同一 PR 评审。
4. **构建期不可校验**——静态 JSON 能在 CI 里做覆盖率差集（§8.2）；DB 行的覆盖情况只能等运行时才暴露，且没有"缺译"信号——出问题时用户看到的是中文或裸 key。

> 因此结论不是"加翻译列**完全多余**"，而是：**对值域编译期可知的内置枚举，加列收益低于成本**（还要触发 L3 DDL 审批，见下）；**对运行期新增的字典条目，加列也解决不了双语**（仍要另建关联表）。两条路都不划算，所以首期不做。

#### 数据模型三选型对比（基于业界最佳实践）

| 方案 | 评价 | 适用 |
|------|------|------|
| **① 静态 locale 文件**（各子应用 `en-US.json` / `zh-CN.json`） | ✅ **最佳 / 默认** | UI 文案、errorCode 映射、枚举翻译——全部代码级资产，随包发布、构建期校验、零运行时代价 |
| **② 专用 `i18n_message` 表** | ⚠️ 仅当确有「运行期可编辑 / 租户覆盖」业务文案 | 商品名、自定义 label、通知模板等**动态内容**（属 tenant customization / message-template，**不是**翻译 UI chrome），且须走 `bone-metadata-sdk`（HC-001）+ 独立缓存 + 版本/回退建模 |
| **③ 复用 `SysDict`** | ❌ **反对** | 维度错（无 locale）、**语义错**（值域真源 ≠ 展示文案）、**治理错**（运营可改、无 review / 无历史表）、污染公共表 |

> **结论**：UI/代码翻译**不放关系库**是业界共识（react-i18next / FormatJS / Rails i18n / Django 全部默认静态资源文件 + 翻译流水线）。Bone 首期 zh-CN + en-US 纯静态 JSON 足够；若未来出现运营高频改文案且要实时生效的真实诉求，新建专用 `i18n_message` 表，**绝不复用 SysDict**。

**什么时候该推翻本决策？** 满足以下任一条时重新评估（注意：出路是**新建独立表**，不是给 SysDict 加列）：

1. **运营高频改文案且要求实时生效、不发版**——纯静态 JSON 满足不了；
2. **租户级文案覆盖**——A 租户要"已支付"、B 租户要"付款完成"；静态 JSON 是全局的，无法按租户分化；
3. **允许租户自定义字典条目**——值域"编译期可知"的前提彻底失效。

此时建 `i18n_message` 表，按 `(tenant_id, locale, module, message_key) → content` 建模（枚举场景可取 `message_key = enums.{type}.{code}`），配独立缓存 + 版本/回退，并走 `bone-metadata-sdk`（HC-001）持久化。**不复用 SysDict。**

> **本方案的降级承诺（写进验收口径）**：运行期新增的字典条目在 en-US 下**显示 `label` 原文（中文）**——这是已知且接受的降级，不算缺译缺陷；若业务要求"自定义条目也必须是英文"，须先满足上面的第 3 条，属**本期范围外**。

### 3.2 与业界最佳实践对照

本方案关键决策均可映射到国际化领域的成熟实践，避免自创轮子（直接回应「基于业界最佳实践」的诉求）：

| 业界最佳实践 | 本方案落点 |
|--------------|-----------|
| 翻译作为**代码资产**随包发布，而非运行时 DB（i18next / FormatJS / Rails i18n / Django 默认） | 静态 `en-US.json` / `zh-CN.json`（§5.2–§5.3）；拒绝 SysDict、专用表仅限动态内容（§3.1） |
| **稳定键**：key 不随文案变化，便于聚合/告警/契约 | errorCode + 前端 i18n key 双稳定（§3 原则表） |
| **展示分离**：后端给稳定码 + fallback，展示归前端 | 后端只给 `errorCode` + 中文 `message`，前端映射（§3/§6.1） |
| **构建期校验缺译**（fail build） | CI `check-i18n-sync.py` 阻断缺 key 的 PR（§8.2） |
| **专业翻译流水线**而非产品内 admin 表单（Crowdin / Weblate） | 首期静态 JSON + PR review；翻译后台列为 [Vision]，仅语言数 ≥ 5 + 专业团队才启用（§1.3） |
| **避免字符串拼接**，用插值/复数 | i18next `{{var}}` / `count` + ICU 升级路径（§5.3） |
| **locale 单源 + 子应用继承**（微前端） | Shell 决定 → `core-event-bus` 广播 → 子应用被动继承（§4/§5.5） |
| **无 FOUC**：语言包静态 import | 应用内 i18n 模块单实例 + 语言包静态 import（§5.2；跨应用不做全局单例） |
| **日期/数字用 Intl** | `dayjs` UTC + `Intl.NumberFormat`（§5.6） |
| **自动提取 key + i18n Lint** | `i18next-scanner` + `eslint-plugin-i18next`（§8.2.5） |

## 4. 整体架构与 locale 传递链路

### 4.1 链路

复用现有跨应用通信机制 **core-event-bus**（`@bone/core-event-bus` 的 `globalEventBus`，挂载于 `window.__BONE_EVENT_BUS__`），**不引入新的事件系统**。`GlobalContextChangeEvent` 的 payload 已定义 `locale: 'zh-CN' | 'en-US'` 字段（`packages/core/event-bus/src/globalContext.ts`）。

**现状勘误（勿按旧描述实现）**：

- 发射端：`bone-shell/src/App.tsx` 已在广播 `globalEventBus.emit('bone:theme:change', { theme, locale: 'zh-CN' })`（**locale 写死**），并在 qiankun props 的全局上下文里同样写死 `locale: 'zh-CN'`——共 3 处写死点（Shell 2 处 + `bone-iam-app/src/main.tsx` 1 处）。
- 消费端：**7 个微应用中只有 `bone-iam-app/src/main.tsx` 订阅了 `bone:theme:change`**（`apps/` 下 8 个应用 = bone-shell + 7 个微应用，勿混用这两个数字）；extension / generator / integration / masterdata / metadata / system **均无订阅代码**，需要新增（见 §5.5.1）。
- `BoneAppProvider` 消费的是**另一套机制**：design-system 内部的**原生 CustomEvent `bone:theme-change`**（非 event-bus），且 locale 完全未接入（`ConfigProvider locale` 写死 `zhCN`）。因此"扩展它消费 `bone:theme:change`"意味着**新增一条 `@bone/ui` → `@bone/core-event-bus` 的包依赖边**（属 L3 审批项，见 §7），与"零新增机制"的旧描述不符——请在实现前二选一（§5.5.2 给出 A/B 方案）。

```
Shell 启动（首次 / 刷新）
   │
   ├─ i18next.init() 已完成（§5.2.1）：LanguageDetector 按
   │    querystring ?lang > cookie bone_i18n > localStorage bone.locale > navigator.language
   │    检测出**唯一**结果，写入 i18n.resolvedLanguage（未命中则 fallbackLng：zh-CN）
   │
   │ ★ Shell **不做二次检测**：若自己再判 "localStorage 有就用它"，会**覆盖
   │   ?lang 的最高优先级**（传 ?lang=en-US 但本地存着 zh-CN 时会被判成 zh-CN），
   │   导致 i18next 与 globalContext 两边语言不一致——与 §5.5.2 的约定冲突
   ▼
Shell 读 i18n.resolvedLanguage，归一化到 supportedLngs（§5.5.2）
   │
   ├─► 写入 globalContext.locale
   ├─► BoneAppProvider 初始化 AntD ConfigProvider locale
   └─► globalEventBus.emit('bone:theme:change', { theme, locale })
        │
        ▼
     各子应用 main.tsx 订阅后 → 取 payload.locale → i18n.changeLanguage(locale)
     （现状：仅 bone-iam-app 已订阅；其余 6 个需新增订阅接线，见 §5.5.1）

───────────────────────────────────────────────────────

用户切换语言（运行时）
   │  (Shell 语言切换组件)
   ▼
写入 globalContext.locale + localStorage 持久化 + i18n.changeLanguage(locale)
   │
   ├─► BoneAppProvider 重渲染 ConfigProvider locale
   └─► globalEventBus.emit('bone:theme:change', { theme, locale })
            │
            ▼
        各子应用 main.tsx bus.on('bone:theme:change', ...)
        → 取 payload.locale → i18n.changeLanguage(locale)
        → 使用 useTranslation() 的组件随之重渲染（机制见 §5.5.4）

API 响应：{ success, code, message(中文fallback), data(=ProblemDetail{ errorCode, ... }) }
         → 前端 showError() 从 data.errorCode 查 i18n 展示
```

> 关键事实：**不新建 `BONE_LOCALE_CHANGE` 事件常量**，也**不新增第三套机制**。`bone:theme:change` 事件与 payload 的 `locale` 字段均已存在，缺的是「消费端接线」：Shell 改为从 `globalContext.locale` 取值广播、6 个微应用补齐订阅、`BoneAppProvider` 接入 locale（A/B 方案见 §5.5.2）。因此这是**复用既有总线 + 补接线**，而非"零改动"——工作量集中在 8 个应用的入口文件与 design-system 的一个组件。

> 同时需**收敛既有的两套机制**（§2 现状表最后两行）：`BoneAppProvider` 当前监听原生 `bone:theme-change`，Shell 走 core-event-bus 的 `bone:theme:change`。本方案确定 **core-event-bus 为唯一跨应用通道**；原生 CustomEvent 仅保留为 design-system 独立运行（脱离 Shell）时的退化路径，并在 §5.5.2 明确二者不互相替代。

### 4.2 X-Language header 决策

**本期不发 `X-Language` header**，划为 **[Vision]**。理由：

- 后端明确不做 `MessageSource` 翻译（§3/§6.3 决策），后端响应 message 始终是中文，header 发送毫无作用。
- 未来后端需要感知语言偏好（如日志审计、网关路由）时再启用，届时补到 §6.3 的 Vision 范围内。

### 4.3 关键约束

- locale 是**单源**：仅 Shell 写入 `globalContext.locale`，子应用只读并继承，禁止子应用自决语言。
- 切换**不刷新页面**：经 `globalEventBus.emit('bone:theme:change')` 热更新，各微应用订阅后 `changeLanguage` + 由 `useTranslation()` 驱动重渲染（机制与陷阱见 §5.5.4）。
- 持久化：locale 写入 `localStorage`，**唯一写入方是 Shell 的语言切换组件**（LanguageDetector 只读不写，`caches: []`，§5.2.1）；刷新时由 LanguageDetector 的 `order` 读取还原。
- **独立运行回退**：微应用脱离 Shell 单独跑时，`BoneAppProvider` 用 `i18n.resolvedLanguage`（LanguageDetector 已按 `querystring > cookie > localStorage > navigator` 检测）作为初始 locale，**不在组件内二次读 localStorage**（详见 §5.5.2）。

## 5. 前端设计

### 5.1 库选型 **[Target]**

**`react-i18next`**（业界标准，与 AntD `ConfigProvider` 正交、可共存）。不使用 `vue-i18n`（前端为 React/Qiankun）。

### 5.2 模块位置 **[Target]**

按《Bone-国际化规范.md》§3 目录建议，置于共享包。**注意 `showError` 不放 `shared-utils`**（它需要 `antd`，而 `@bone/shared-utils` 目前零 UI 依赖、`package.json` 只声明了 eslint/typescript；把 antd 引进来会让这个纯工具包反向依赖 UI 框架）：

```
packages/shared-utils/src/i18n/
  index.ts              # 初始化 i18next（lng 来自 LanguageDetector，fallback zh-CN）
  locales/zh-CN.json
  locales/en-US.json
  format.ts             # 基于 dayjs + Intl 的 date/number 封装（替换现有 format.ts）

packages/shared-services/src/
  errorDisplay.ts       # errorCode → i18n key 辅助 + showError()/useShowError()/messageHolder
                        # @bone/shared-services 已依赖 axios / react-query，是放置 UI 相关错误展示的合适层
```

> **消费方式（P0 前置，否则 import 直接失败）**：`@bone/shared-utils` 当前**没有任何 app 引用**（全仓仅 `vitest.config.ts` 与本包自身出现该名），且其 `package.json` **无 `exports` 字段**（`main` 指向 `./src/index.ts`），`tsconfig` 的 `@bone/* → ./packages/*` 别名也不指向 `src/`。因此落地前必须先做一件事（二选一，属配置改动、走 PR review）：
> - 给 `shared-utils` 加 `exports`（`"."`、`"./i18n"`）并在各 app 的 `vite.config.ts` / `tsconfig` 补 `@bone/shared-utils/i18n` 别名；或
> - 新代码统一从**包入口**导出（`import { i18n } from '@bone/shared-utils'`），避免子路径解析问题。

> **实例边界（微前端，重要）**：8 个应用各自独立 Vite 打包，`import { i18n } from '@bone/shared-utils/i18n'` 在运行时拿到的是**每个应用一份独立实例**（不是跨应用单例）——与 event-bus 不同，后者是靠 `window.__BONE_EVENT_BUS__` 才共享的。本方案**接受"每应用一实例"**，因为它与既有架构一致、避免新增全局单例生命周期问题，代价是每个应用都要自己 `init` 一次并订阅 locale 变更。若后续确实需要跨应用共享（例如组件库跨应用复用同一 i18next 实例），再按 event-bus 的做法挂 `window.__BONE_I18N__`，届时需处理"谁 init、谁释放"。
>
> 由此推出两条硬约束：① **每个应用都必须 `init`**（不能只靠 Shell init，"Shell 就绪子应用就绪"不成立）；② 语言包随 `index.ts` **静态 `import`**（非异步 fetch），避免首屏 FOUC；③ 各应用不得自决语言，只 `changeLanguage(payload.locale)`。

#### 5.2.1 i18n/index.ts 完整初始化代码（业界标准）

```ts
// packages/shared-utils/src/i18n/index.ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';

import zhCN from './locales/zh-CN.json';
import enUS from './locales/en-US.json';

/** 支持的语言列表（权威源，语言包文件按此命名） */
export const SUPPORTED_LANGUAGES = ['zh-CN', 'en-US'] as const;
export type SupportedLanguage = typeof SUPPORTED_LANGUAGES[number];

/**
 * 初始化 i18next。**每个应用内只执行一次**（模块级单实例；8 个应用各有自己的实例，§5.2「实例边界」）。
 * - initReactI18next：React 绑定插件，必须
 * - LanguageDetector：浏览器语言自动检测（querystring > cookie > localStorage > navigator），
 *                    比手写 navigator.language 更健壮
 */
i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    fallbackLng: 'zh-CN',
    supportedLngs: SUPPORTED_LANGUAGES,

    // 浏览器普遍上报 'en' / 'zh' 而非 'en-US' / 'zh-CN'；
    // 不开此项时 'en' 不属于 supportedLngs，会直接落到 fallbackLng=zh-CN
    // → 英文浏览器用户默认看到中文。开启后 'en' 归一化到 'en-US'。
    nonExplicitSupportedLngs: true,

    // 静态加载：首期量小（< 200 条），避免首屏 FOUC
    resources: {
      'zh-CN': { translation: zhCN },
      'en-US': { translation: enUS },
    },

    // 检测优先级：URL 参数 > Cookie > localStorage > 浏览器语言（只读，不写入）
    detection: {
      order: ['querystring', 'cookie', 'localStorage', 'navigator'],
      lookupQuerystring: 'lang',           // ?lang=en-US
      lookupCookie: 'bone_i18n',
      lookupLocalStorage: 'bone.locale',
      // ★ 单一写入方原则：持久化**只由 Shell 的语言切换组件写 localStorage**（§5.5.3）。
      //   若这里也 caches，LanguageDetector 会在 init 时回写同一 key，
      //   与 Shell 形成两个写入方，排查"语言自己变回去"类问题会非常困难。
      caches: [],
    },

    // 插值：React 自动 escape，不需要 i18next 再转义
    interpolation: {
      escapeValue: false,
    },

    // 开发环境：key 不存在时 console.warn（防静默漏译）
    saveMissing: false, // 首期 false，CI 脚本报错更可控
  });

export default i18n;
```

**依赖补充**：
```jsonc
// package.json
"dependencies": {
  "i18next": "^23.x",
  "react-i18next": "^14.x",
  "i18next-browser-languagedetector": "^8.x"   // 自动语言检测插件
}
```

> **演进路径**（[Vision]，语言包 > 500 条时）：改为 `i18next-http-backend` 懒加载，按 namespace 拆分语言包（`common.json` / `errors.json` / `nav.json`），用 React Suspense 包 `<App>` 保证首屏语言就绪再渲染。

### 5.3 语言包组织（命名空间）**[Target]**

```jsonc
// en-US.json
{
  "common": { "confirm":"Confirm", "cancel":"Cancel", "loading":"Loading…" },
  "nav":    { "console":"Console", "iam":"IAM", "metadata":"Metadata" },
  "errors": {
    "IAM_LOGIN_FAILED":"Login failed",
    "IAM_TENANT_ACCESS_DENIED":"No access to this tenant",
    "COMMON_VALIDATION_FAILED":"Validation failed: {{errors}}",
    "COMMON_FORBIDDEN":"No permission to access this resource",
    "COMMON_NOT_FOUND":"Requested resource not found",
    "COMMON_INTERNAL_ERROR":"Internal server error"
  },
  "fallback": {
    "updateRoleFailed":"Failed to update role",
    "loginFailed":"Login failed"
  },
  "enums": {
    "BOOLEAN": {
      "ENABLED": "Enabled",
      "DISABLED": "Disabled"
    },
    "ORDER_STATUS": {
      "CREATED": "Created",
      "PAID": "Paid",
      "CANCELLED": "Cancelled"
    }
  }
}
```

**enums 必须用真正的嵌套结构**（关键，不能平铺）：

i18next 默认把 `.` 作为**嵌套分隔符**。如果写 `"enums": { "ORDER_STATUS.PAID": "Paid" }`（一个 key 里带点号），`i18n.t('enums.ORDER_STATUS.PAID')` 会被解析成三层路径 `enums → ORDER_STATUS → PAID`，在平铺结构里**取不到值**，显示裸 key。所以 enums 必须按类型名嵌套：

```ts
// ✅ 正确：嵌套结构 + i18n.t('enums.ORDER_STATUS.PAID') 能命中
"enums": { "ORDER_STATUS": { "PAID": "Paid" } }

// ❌ 错误：平铺结构里的点号 key 会被 i18next 当成嵌套路径，取不到
"enums": { "ORDER_STATUS.PAID": "Paid" }
```

`errors` 命名空间不需要嵌套——后端 errorCode 本身已带域前缀（`IAM_LOGIN_FAILED`、`COMMON_VALIDATION_FAILED`、`COMMON_INTERNAL_ERROR`），全大写下划线不含点号，平铺即唯一，`i18n.t('errors.IAM_LOGIN_FAILED')` 直接命中。**key 集合必须与《Bone-错误码登记》§6 台账的码值逐字一致**（大小写、下划线都不许改），否则 §8.2 的差集校验会失败。

**`fallback` 命名空间（前端本地兜底文案，勿与 errors 混用）**：现有 78 处调用里有大量 `message.error(response.message || '更新角色失败')`——这类**前端自造兜底**在响应无 `errorCode` 时才会用到，它们**不是 errorCode**，禁止塞进 `errors`（会让 §8.2 的差集校验误判、也会让人误以为是后端契约）。统一放 `fallback.*`（key 按动作语义命名，如 `fallback.updateRoleFailed`），由 `showError(resp, { fallbackKey })` 引用（§5.4.2）。

`enums` 命名空间对应《Bone-API-规范.md》§14.2 的**对外字符串枚举**（`ENABLED`/`DISABLED`、订单状态等）。前端列表状态 Tag、下拉选项从枚举值映射文案（如 `i18n.t(\`enums.ORDER_STATUS.${row.status}\`)`；key 与后端 `dict.type` 字面一致，见 §3.1），不再硬编码「已支付/待付款」。

**必须新建"枚举取数统一入口"（P2 前置）**：当前枚举文案散落在各页面的本地数组（`connectorTypes` / `fieldTypes` / `ruleTypes` / `operationTypes`，见 §3.1 As-Is）。若 P2 只是把这些数组逐个改成 `i18n.t()`，会得到 20+ 份各自拼 key 的实现——大小写、兜底、是否传参全靠自觉。统一入口只做三件事：

```tsx
// packages/shared-components/src/i18n/useEnumLabel.ts（示意；也可放 @bone/ui，与业务解耦）
/** ① 取文案：语言包命中 → dict.label → 原始 code（三级，永不显示裸 key） */
export function useEnumLabel(type: string, code?: string | null, dictLabel?: string | null): string {
  const { t } = useTranslation();
  if (!code) return '-';
  const key = `enums.${type}.${code}`;
  const hit = t(key);
  // i18next 未命中会原样返回 key，据此判定，而非依赖 returnNull
  return hit !== key ? hit : (dictLabel || code);
}

/** ② 渲染：状态列统一走它，禁止各页面自建映射数组 */
export function EnumTag({ type, code, label }: { type: string; code?: string | null; label?: string | null }) {
  return <Tag>{useEnumLabel(type, code, label)}</Tag>;
}
```

- **禁止**页面再定义 `{ value, label }` 数组承载展示文案；选项列表改为 `code` 数组 + `useEnumLabel(type, code)` 生成 `label`。
- **禁止**在此入口之外拼接 `enums.` key（便于 §8.2 用正则统一审计）。
- 该入口同时是**兜底链的唯一实现点**——`dict.label` 兜底、`-` 空值处理、`code` 最后兜底都只写一次。

> **演进建议（[Vision]，治漂移）**：`enums` 命名空间当前靠前端手写，存在与后端 `sys_dict.type` 漂移的风险。语言包规模上来后，建议由 codegen 从后端枚举定义（`@Valid` 字符串枚举 / SysDict 类型）**自动生成** `enums` 骨架，从源头消除手写漂移。本期规模小（< 200 条）且字典为运行时数据，不引入。

**复数与插值约定**：错误/列表文案必须用 i18next 能力，禁止字符串拼接——
- 变量用 `{{var}}`：`"COMMON_VALIDATION_FAILED": "Validation failed: {{errors}}"`
- 复数用 `count`：`"records_deleted": "Deleted {{count}} record"` / `"_plural": "Deleted {{count}} records"`，由 i18next 按语言选形态。

> **演进建议（业界标准）**：当文案出现复杂复数/性别/选择（如斯拉夫语复数类、阿拉伯语双复数），i18next 原生 `_plural` 不足以覆盖时，改用 **ICU MessageFormat**（`i18next-icu` 插件，`{count, plural, one {...} other {...}}`、`{g, select, male {...} female {...} other {...}}`）。首期 zh-CN / en-US 用原生 `count` 即可，架构预留 ICU 升级路径，不在本期引入额外依赖。

### 5.4 错误展示统一函数（最高 ROI）**[Target]**

#### 5.4.1 类型定义（前置）

前端需补齐 `ApiResponse` / `ProblemDetail` 的 TypeScript 类型声明。**对齐真源**：`bone-core` 的 `com.bone.core.model.ProblemDetail` + OpenAPI `ProblemDetail.yaml`（后者已把 `errorCode` 列为 `required`），TS 类型应与其字段逐一对齐。

**落点（勘误：不要新建第三份类型）**：仓库**已有权威定义** `bone-frontend/packages/shared-types/src/common/api.ts`（其注释明确写"统一收敛到 ./common/api 的权威定义，避免重复声明"，且 `@bone/shared-types` 已被 shell / shared-services / 各 app 引用）。因此应在该文件上**扩展**，而不是在 `shared-utils` 新建 `types/api.ts`：

```ts
// bone-frontend/packages/shared-types/src/common/api.ts（在既有文件上扩展）
export interface ApiResponse<T = unknown> {
  success: boolean;            // ← 补：后端 bone-core ApiResponse 有此字段
  code: number;
  message: string;
  data: T | null;              // ← 由 T 改为 T | null：错误响应 data 为 ProblemDetail，未改造的 handler 甚至为 null
  timestamp?: string;          // ← 补：后端有此字段
```

#### 5.4.2 showError 实现

> **⚠️ AntD v5 约束**：`BoneAppProvider` 引用 `antd/locale/zh_CN` 即 AntD **v5**。v5 下静态 `import { message } from 'antd'; message.error()` **不继承** `ConfigProvider` 的 locale 与 theme，官方已标记为废弃用法。错误展示必须经 antd `<App>` 组件上下文，用 `App.useApp()` 取得 `message` 实例（§5.5.2 的 `ConfigProvider` 内需包一层 `<App>`）。因此 `showError` 设计为接收 `message` 实例的纯函数，由调用方在 `App.useApp()` 上下文内调用。

新建 `packages/shared-services/src/errorDisplay.ts`（**不放 `shared-utils`**：它需要 antd，见 §5.2 分层说明）：

```ts
// packages/shared-services/src/errorDisplay.ts
import { App } from 'antd';
// ★ MessageInstance 未从 antd 根入口导出（antd/es/index.d.ts 只有 export { default as message }），
//   必须从深路径引类型；写成 `import { App, type MessageInstance } from 'antd'` 编译即失败。
import type { MessageInstance } from 'antd/es/message/interface';
import { i18n } from '@bone/shared-utils/i18n';
import { useCallback } from 'react';
// 类型放既有权威定义（@bone/shared-types 已是 shared-services 的依赖，§5.4.1）
import type { ApiResponse, ProblemDetail } from '@bone/shared-types';

/** 调用方可选的本地兜底：响应既无 errorCode 也无 message 时，用动作语义 key 兜底 */
export interface ShowErrorOptions {
  /** 形如 'fallback.updateRoleFailed'（见 §5.3 的 fallback 命名空间） */
  fallbackKey?: string;
}

/**
 * 统一错误展示纯函数：接收 antd message 实例 + 响应，按回退链展示。
 * message 实例**必须**来自 App.useApp()（见 §5.4.2 顶部 v5 约束），不可用静态 import。
 */
export function showError(
  message: MessageInstance,
  resp: ApiResponse<ProblemDetail | unknown>,
  options?: ShowErrorOptions
): void {
  const problemDetail = resp.data as ProblemDetail | undefined;
  const errorCode = problemDetail?.errorCode ?? null;
  // 本地兜底文案（仅在前端自造兜底场景使用，key 在 fallback.*，不是 errorCode）
  const localFallback = options?.fallbackKey
    ? i18n.t(options.fallbackKey, { defaultValue: options.fallbackKey })
    : null;

  let display: string;
  if (errorCode) {
    // 命中 errorCode：尝试 i18n 翻译，并注入插值变量（如校验错误的 {{errors}}）
    // ★ 必须传第二参数：否则 COMMON_VALIDATION_FAILED 的 "Validation failed: {{errors}}"
    //   会渲染成空值或字面量，英文用户看不到具体字段错误。
    //   优先用结构化 errors（IAM 已填），回退到 detail 字符串（metadata-server 只填 detail）
    const key = `errors.${errorCode}`;
    const detailText = problemDetail?.errors?.length
      ? problemDetail.errors.map((e) => `${e.field}: ${e.message}`).join('; ')
      : problemDetail?.detail ?? resp.message ?? '';
    const translated = i18n.t(key, {
      errors: detailText,
      defaultValue: '',
    });
    display = translated && translated !== key
      ? translated
      : `[${errorCode}] ${resp.message ?? 'Unknown error'}`;
  } else {
    // 无 errorCode（handler 未改造）：后端中文 message → 本地兜底 key → 中性兜底串
    display = resp.message || localFallback || `[${resp.code}] Unknown error`;
  }
  message.error(display);
}

/** 组件内推荐用法：自动拿到 App.useApp() 的 message 实例（78 处调用点均位于 apps/*/src/pages） */
export function useShowError(): (
  resp: ApiResponse<ProblemDetail | unknown>,
  options?: ShowErrorOptions
) => void {
  const { message } = App.useApp();
  return useCallback((resp, options) => showError(message, resp, options), [message]);
}
```

> **已知限制（校验错误，必须知悉）**：Bean Validation 注解的字段级文案（`@NotBlank(message = "...")`）后端仍是中文，`detail` / `errors[].message` 在英文模式下会**中英混排**（如 "Validation failed: 用户名不能为空"）。彻底解决需把注解文案也走 i18n（属后端 `MessageSource` 范畴，见 §6.3 [Vision]）；首期接受此降级——`errorCode` 层（`COMMON_VALIDATION_FAILED`）已是英文，字段详情作兜底展示。

**回退链更新**（与 §3 对齐）：

| 场景 | 英文用户看到 | 说明 |
|------|------------|------|
| errorCode + en-US 有翻译 | 翻译后的英文 | ✅ 最佳路径 |
| errorCode + en-US 缺翻译 | `[IAM_LOGIN_FAILED] 后端中文message` | 比纯中文好，CI 应阻断（§8） |
| 无 errorCode（硬编码 handler） | 后端中文 message | 最后兜底，后端必须逐步补齐 |

#### 5.4.3 替换点

**实测基线（2026-09-25 扫描，勿再用旧数字估算工作量）**：变量形态 `message.error(...)` 共 **78 处**——extension 28 / masterdata 24 / metadata 22 / iam 3 / system 1 / generator・integration・shell 0。

两个必须处理的形态：

1. **纯后端文案**：`message.error(response.message)` → 直接换 `showError(response)`；
2. **双兜底**：`message.error(response.message || '更新角色失败')` → 换 `showError(response, { fallbackKey: 'fallback.updateRoleFailed' })`，中文兜底迁到语言包（§5.3 `fallback` 命名空间）。

```ts
    const resp = await call();
    if (resp.code !== 200) {
```

#### 5.4.4 非组件层（拦截器 / service）的调用策略 **[Target]**

**先澄清一个易被误判的事实**：78 处待替换点**全部位于 `apps/*/src/pages`（React 组件内）**，因此 §5.4.3 的 `useShowError()` 是主路径。本节的模块级 holder **不是**为这 78 处准备的，而是给**确实不在 React 树内**的场景兜底——目前主要是 `packages/shared-services/src/apiClient.ts` 的响应拦截器（401 时派发 `bone:auth:expired`、并把 `message` 挂到 `error.displayMessage`）以及后续可能新增的 service 层统一提示。

这类场景拿不到 `App.useApp()`（§5.4.2 的 AntD v5 约束），方案采用**模块级 holder**：

1. `shared-services/errorDisplay.ts` 内维护模块级变量 `messageHolder: MessageInstance | null`（§5.2 已说明为何不放 shared-utils）。
2. **`<App>` 的子组件**挂载时经 `App.useApp()` 取到 `message` 实例，写入 `messageHolder`（见下方桥接组件）。
3. 拦截器 / service 层调用 `showErrorAuto(resp)`：内部 `getMessage()` 取实例；实例尚未就绪（首帧前）则**降级**——不弹 Toast，仅 `console.error` + 把 errorCode 抛给调用方。

> ⚠️ 第 2 步的常见坑：必须是 **`<App>` 的子树**。`BoneAppProvider` 自身渲染出 `<App>{children}</App>`，**它自己调 `App.useApp()` 拿不到上下文**（hook 只能读到祖先 Provider），所以要在 `BoneAppProvider` 内加一个桥接子组件：
>
> ```tsx
> function MessageHolderBridge({ holder }: { holder: { current: MessageInstance | null } }) {
>   const { message } = App.useApp();
>   useEffect(() => {
>     holder.current = message;
>     return () => { holder.current = null; };
>   }, [message, holder]);
>   return null;
> }
> // ConfigProvider > App > [MessageHolderBridge + children]
> ```

> **为什么不用 antd 静态 `message`**：AntD v5 已将静态 `message.error()` 标记为废弃，它**不继承** `ConfigProvider` 的 locale/theme，会导致 Toast 文案与语言/主题不同步——正是本方案要避免的问题。

#### 5.5.4 「切换不刷新页面」的重渲染机制 **[Target]**

`i18n.changeLanguage(next)` **只改变语言状态，不会让任意组件重渲染**——只有订阅了 i18next 的组件（`useTranslation()` 的默认 `bindI18n: 'languageChanged'`）才会更新。这是"语言切了一半"问题的最常见根因，必须提前约定：

| 场景 | 机制 | 要求 |
|------|------|------|
| 组件内渲染文案（表头、按钮、空态、Tag） | `const { t } = useTranslation()` | 禁止直接用 `i18n.t()` 渲染——不订阅、不重渲染 |
| 列定义 / 选项数组等 `useMemo` 结果 | 依赖数组加 `i18n.language` | 否则 memo 命中缓存，表头永远停在旧语言 |
| 命令式提示（`message` / `notification` / `Modal.confirm`） | 调用瞬间取 `t()` | 天然是当前语言，无需订阅 |
| 第三方组件不响应语言变化（兜底） | 根级 `<App key={locale}>` 强制重挂子树 | 成本高（丢组件内部状态），仅作为最后手段 |

> 与微前端的配合：每个微应用有自己的 i18next 实例（§5.2），因此**各应用内部必须自行完成上述订阅约定**，Shell 无法代为触发重渲染；Shell 只负责广播 `locale`。

### 5.6 格式化 **[Target]**

#### 5.6.1 依赖引入

```jsonc
// packages/shared-utils/package.json（新增依赖 → L3 架构师审批；§7 P0-B）
"dependencies": {
```

> 注意：`dayjs` 当前只声明在 2 个应用（`bone-iam-app` / `bone-system-app`）里，`shared-utils` **没有**；把 `format.ts` 放进 shared-utils 就必须在 shared-utils 显式声明这四个依赖，并给该包补 `exports`（§5.2），否则各应用解析不到。

需额外引入的 dayjs **插件与 locale 包**（dayjs 默认不带 UTC/timezone/locale，必须显式注册）：

```ts
// packages/shared-utils/src/i18n/format.ts 顶部
import dayjs from 'dayjs';
import utc from 'dayjs/plugin/utc';
import timezone from 'dayjs/plugin/timezone';
import 'dayjs/locale/zh-cn';
import 'dayjs/locale/en';
import { i18n } from './index';  // 循环依赖安全：format.ts 被 formatDate 调用时 i18n/index.ts 已 init

dayjs.extend(utc).extend(timezone);

/**
 * i18next locale → dayjs locale 映射表。
 * 避免 formatDate 里 `i18n.language === 'en-US' ? 'en' : 'zh-cn'` 硬编码，
 * 加第三种语言时只需扩展此表。
 */
const I18N_TO_DAYJS_LOCALE: Record<string, string> = {
  'zh-CN': 'zh-cn',
  'en-US': 'en',
  // 'ja-JP': 'ja',  // 未来加语言时扩展
};
const getDayjsLocale = (i18nLng: string): string =>
  I18N_TO_DAYJS_LOCALE[i18nLng] ?? 'zh-cn';

// ★ 关键：dayjs 全局 locale 同步——模块加载时自动跟随 i18next
// 这样任何地方直接用 dayjs().fromNow() 也会按当前语言显示（如 "3 minutes ago" / "3 分钟前"），
// 不需要每个调用点都手动链 .locale()
i18n.on('languageChanged', (lng) => {
  dayjs.locale(getDayjsLocale(lng));
});
// init 完成后立即同步一次初始 locale
dayjs.locale(getDayjsLocale(i18n.language));
```

#### 5.6.2 时区转换逻辑（关键）

> ⚠️ **前提修正（勿照旧稿实现）**：旧稿的 `dayjs.utc(v).tz(LOCAL_ZONE)` 成立的**前提是后端输出带偏移的 ISO-8601（`...Z`）**，而 §6.4 实测该前提**当前不成立**（后端无任何 Jackson 时区配置，160 个文件的 `LocalDateTime` 默认不带偏移）。在 §6.4 完成前套用旧写法会把无偏移时间当 UTC 解析，**静默偏移 +8 小时**。因此本节实现必须与 §6.4 同一 PR 或在其之后落地，且不得用 `.utc()` 的"强制解析"掩盖后端缺失——改用下方 `parseUtc()`：带偏移才转本地时区，不带偏移则告警 + 原样解析（宁可显示后端原始值，也不要凭空 +8h）。

```ts
// packages/shared-utils/src/i18n/format.ts（续上方）
import { i18n } from './index';  // 循环依赖安全：format.ts 被 i18n/index.ts 间接 import

/**
 * 归一化当前语言：与 §5.5.2 的 AntD locale 判定**同源**。
 * 必须用 resolvedLanguage 而非 i18n.language：后者在 ?lang=en 时可能是 'en'
 * （非 supportedLngs 成员），会导致"UI 是英文、日期却按中文格式化"的不同步。
 */
const currentLng = (): string => i18n.resolvedLanguage ?? i18n.language;

/** 浏览器本地时区，如 "Asia/Shanghai" */
const LOCAL_ZONE =
  Intl.DateTimeFormat().resolvedOptions().timeZone ?? 'Asia/Shanghai';

/**
 * 解析入口：只在输入**带偏移**（Z 或 ±HH:mm）时才按 UTC 解析并转本地。
 * 不带偏移的输入说明后端未按 §6.4 输出 UTC——此时**不静默兜底**：
 * 开发环境下 warn 出来，生产按原样解析（宁可显示后端原始值，也不要凭空 +8h）。
 */
const HAS_OFFSET = /(?:Z|[+-]\d{2}:?\d{2})$/;

function parseUtc(v: string | Date) {
  const raw = typeof v === 'string' ? v : v.toISOString();
  if (typeof v === 'string' && !HAS_OFFSET.test(v) && import.meta.env?.DEV) {
    console.warn('[i18n] 时间字段无时区偏移，后端未按 §6.4 输出 UTC：', v);
  }
  return HAS_OFFSET.test(raw) ? dayjs(raw).tz(LOCAL_ZONE) : dayjs(raw);
}

/**
 * 格式化日期时间。
 * - .tz(LOCAL_ZONE) 转为浏览器本地时区（尊重用户系统设置）
 * - .locale(getDayjsLocale(currentLng())) 按当前语言格式化（文案随语言切换）
 */
export function formatDate(v: string | Date | null | undefined): string {
  if (!v) return '-';
  return parseUtc(v).locale(getDayjsLocale(currentLng())).format('YYYY-MM-DD HH:mm:ss');
}

/** 日期只展示到天 */
export function formatDateOnly(v: string | Date | null | undefined): string {
  if (!v) return '-';
  return parseUtc(v).locale(getDayjsLocale(currentLng())).format('YYYY-MM-DD');
}

/** 相对时间（"3 分钟前" / "3 minutes ago"，dayjs 的 locale 包内置不同文案） */
export function formatRelative(v: string | Date | null | undefined): string {
  if (!v) return '-';
  return parseUtc(v).locale(getDayjsLocale(currentLng())).fromNow();
}
```

#### 5.6.3 数字/货币格式化

基于 `Intl.NumberFormat`（浏览器原生，无需额外依赖）：

```ts
export function formatNumber(
  v: number | string,
  options?: Intl.NumberFormatOptions
): string {
  const n = typeof v === 'string' ? Number(v) : v;
  if (Number.isNaN(n)) return '-';
  return new Intl.NumberFormat(currentLng(), options).format(n);
}

// 调用示例
formatNumber(1234567.89);           // zh-CN: "1,234,567.89"  en-US: "1,234,567.89"
formatNumber(0.1234, { style: 'percent' });
```

> **货币格式化首期不做（已核实）**：后端 `Money` 值对象（`bone-blueprint/src/main/java/com/bone/blueprint/domain/model/shared/valueobject/Money.java`）**只有 `BigDecimal amount`、没有 currency 币种字段**——所以"币种由 `Money` 的 currency 提供"不成立。首期 `formatNumber` 只做**纯数字 / 百分比**格式化；货币格式化待 `Money` 补充币种字段（属领域建模变更，非 i18n 范畴）后再启用，届时币种由业务契约显式提供，**不写死 CNY**。

#### 5.6.4 替换点与检查项

| 当前散点 | 替换为 | 检查方式 |
|---------|--------|---------|
| `SandboxManagement.tsx` / `ExecutionLogPage.tsx` 等直接 `new Date(v).toLocaleString()` | `formatDate(v)` | Grep `\.toLocaleString()` 清零 + CI 拦截 |
| `shared-utils/format.ts` 内已有的旧 format 函数 | 统一到本文件 | 保留或废弃旧函数，避免双份 |

**必须与后端 §6.4 对齐（依赖方向不要搞反）**：后端所有时间字段必须输出带偏移的 ISO-8601（`...Z`）——这是 P0-A 任务，当前**未满足**。前端**不再**用 `dayjs.utc(v)` 无条件"强制 UTC 解析"去兜底：那会把无偏移输入静默偏移 +8h，把后端缺陷伪装成前端正常（§5.6.2 `parseUtc()`）。正确做法是后端修契约 + 前端对无偏移输入告警。

## 6. 后端设计

### 6.1 保持「errorCode + 中文 message」不变 **[As-Is]**

不引入 `MessageSource` 翻译业务文案。后端职责：**统一的 `ProblemDetail` 模型**（§6.2.1）+ 稳定 `errorCode` + 中文 `message`（fallback）+ UTC 时间。

**同一原则贯穿枚举**：后端 SysDict 继续作为**值域真源**（有哪些 `type`/`code`、`value` 业务语义、`sort` 排序、`status` 启停、`label` 中文兜底），**不承担文案**；展示文案由前端 `enums` 命名空间承担（§3.1 价值链路与"值域可知性"判定）。

### 6.2 统一到 `ProblemDetail` 模型 + 覆盖硬编码 handler **[Target]**

#### 6.2.1 统一到既有 `ProblemDetail` 模型（P0，阻断项）

**现状勘误（P0 的起点不是"从零新增字段"）**：

| 事实 | 位置 |
|------|------|
| `bone-core` **已有**规范模型 `ProblemDetail`（含 `errorCode` / `traceId` / `errors` / `instance`，并有 `of(errorCode, status, detail)` 工厂） | `bone-framework/bone-core/src/main/java/com/bone/core/model/ProblemDetail.java` |
| OpenAPI 契约 **已把 `errorCode` 列为 `required`**，字段级错误另有 `FieldError.yaml` | `doc/architecture/openapi/components/ProblemDetail.yaml` |
| 已有两个模块在正确使用该模型，且各有 `problem(...)` 工厂 | `CatalogApiResponses`（metadata-server）、`StudioCommandResponses`（extension-studio），内部都是 `ProblemDetail.of(...)` + `setTraceId(MDC...)` |
| **IAM** 走的是自建 `LinkedHashMap`（缺 `errorCode` 键），`IamErrors.composeMessage()` 只把码拼进 `message` 前缀（`"IAM_LOGIN_FAILED: 用户名或密码错误"`） | `IamExceptionHandler.java:155-157` |
| **masterdata / system / generator / bone-web** 直接 `ApiResponse.error(code, "中文")`，**不产 `ProblemDetail`**，失败响应 `data` 为 `null` | 各模块 `GlobalExceptionHandler` |

**方案（P0 阻断项）**：**统一到 `bone-core` 的 `ProblemDetail` 模型**，不给手写 `Map` 打补丁——否则会固化出"两种 ProblemDetail 形状"，前端类型、契约测试、OpenAPI 校验都要分叉。具体三件事：

1. IAM 的 `buildProblemDetail(...)` 从 `Map<String,Object>` 改为返回 `ProblemDetail`（见下方代码）；
2. 四个"无 data"的 handler 改为产出 `ProblemDetail`（§6.2.3 清单）；
3. 把 `problem(status, errorCode, detail)` 工厂**上提到 `bone-core`**（现为 metadata / extension 各一份），避免第 3、4、5 份复制；顺带把信封统一到既有的 `ApiResponse.fail(code, message, data)`。

```java
// IamExceptionHandler.buildProblemDetail() 改为复用 bone-core 模型（旧 Map 版本删除）
private ProblemDetail buildProblemDetail(
    int status, String detail, String errorCode, HttpServletRequest request) {
  ProblemDetail problem = ProblemDetail.of(errorCode, status, detail); // errorCode/title/type/status/detail
  problem.setInstance(request != null ? request.getRequestURI() : null);
  problem.setTraceId(MDC.get("traceId"));
  return problem;
}

// 信封：与 metadata / extension 一致（bone-core 既有工厂），不再 new LinkedHashMap
return ResponseEntity.status(status)
    .body(ApiResponse.fail(status, detail, problem));
```

- `errorCode` 来源分两类：
  - **业务异常** **[Target，尚未实现，勿按现状引用]**：现有 `BizException`（`bone-core/.../exception/BizException.java`）**只有 `private final int code`**（HTTP 状态语义，Lombok `@Data` 生成的 getter 是 `getCode(): int`），**没有** `errorCode` 字符串字段。因此需要给 `bone-core` 增量新增 `String errorCode` 字段 + 新构造函数（旧构造保持兼容、旧路径为 `null`），由 `*Errors.of(errorCode, detail)` 在构造时写入；改造完成后 `handleBizException` 才能透传 `ex.getErrorCode()`，无需 handler 手填常量（比"handler 显式传参"更不易漂移）。
    - ⚠️ 命名冲突提醒：`getCode()`（int，HTTP 语义）与新增的 `getErrorCode()`（String，业务码）**语义完全不同**，不可复用同一个字段、也不建议把 `code` 改成 String（会打断所有按 int 比较的调用点）。两者并存期间须在 Javadoc 写明区别。
  - **基础设施/兜底 handler**（AccessDenied、NoResourceFound、MethodNotSupported、HttpMessageNotReadable、Exception、Validation）：无业务码，由 handler 填对应常量（见 §6.2.2）；`DomainException` 等无法提取时可传 `COMMON_INTERNAL_ERROR` 或 `null`，前端回退链自然降级到中文 message。

**必须一并固定的两个字段约定**（两个既有实现的取值不同，统一时不能含糊）：

- `type`：IAM 现用 `https://bone.wps.cn/problems/{status}`，`ProblemDetail.of()` 默认写 `about:blank`，而 OpenAPI 示例是 `https://bone.wps.cn/problems/extension/plugin-not-found`。建议统一为 OpenAPI 风格的 `https://bone.wps.cn/problems/{domain}/{reason-kebab}`（例如 `.../problems/iam/login-failed`），并在 §6.2.4 契约测试里断言非空。
- `title`：`ProblemDetail.of()` 把 `title` 直接设为 `errorCode`，IAM 现用 HTTP 状态文本（`Forbidden` / `Not Found`）。建议 `title` 用 HTTP 状态文本（便于人读），`errorCode` 只承载业务语义——避免同一信息两处表达、也避免监控按 `title` 聚合到码值。

**注意**：`ApiResponse` 顶层模型**不**加 `errorCode` 字段——与《Bone-错误码登记》§1「业务码放 `data.errorCode`」一致；`code` 仅镜像 HTTP 状态。

**改动方式：在 IAM 内部加一个 4 参私有重载（降低影响面）**：`buildProblemDetail` 是 `IamExceptionHandler` 的私有方法，重载只为让"暂未分配 errorCode"的 handler 零改动：

```java
// 旧签名保留：内部以 null 委托，已有调用点零改动
private ProblemDetail buildProblemDetail(int status, String detail, HttpServletRequest request) {
    return buildProblemDetail(status, detail, null, request);
}

// 新增：需携带 errorCode 的 handler 用这个
private ProblemDetail buildProblemDetail(int status, String detail, String errorCode, HttpServletRequest request) {
    ProblemDetail problem = ProblemDetail.of(errorCode, status, detail);
    problem.setInstance(request != null ? request.getRequestURI() : null);
    problem.setTraceId(MDC.get("traceId"));
    return problem;
}
```

这样 IAM 内部只有 §6.2.2 的 6 个基础设施 handler 需要改动，其余 handler 不受影响；跨模块不受牵连（该方法本就是 IAM 私有）。**其他模块不各自复制这套私有方法**，一律用 §6.2.1 上提到 `bone-core` 的公共 `problem(...)` 工厂。

#### 6.2.2 硬编码中文 handler 补 errorCode（P0，阻断项）

当前 `IamExceptionHandler` 有 **6 个 handler** 未走 `*Errors.of()` 模式、硬编码中文 message 且无 errorCode 字符串（另：`handleBizException` 的 errorCode 由 `BizException` 携带、`handleDomainException` 因属未翻译域异常兜底、传 `null`）：

| Handler | 硬编码 message | 分配的 errorCode | 台账登记 | 代码常量现状（实测） | 建议英文文案 |
|---------|---------------|-----------------|---------|---------------------|-------------|
| `handleAccessDenied` | `"无权限访问该资源"` | `COMMON_FORBIDDEN`（403） | ✅ 已登记 | ✅ 已存在（`StudioErrorCodes.FORBIDDEN`），建议上提 `bone-core` | "No permission to access this resource" |
| `handleNoResourceFound` | `"请求的资源不存在"` | `COMMON_NOT_FOUND`（404） | ✅ 已登记 | ⚠️ 全仓无该常量 → 新增 `CommonErrorCodes.NOT_FOUND` | "Requested resource not found" |
| `handleMethodNotSupported` (405) | `"请求方法不被支持: {method}"` | `COMMON_METHOD_NOT_ALLOWED`（405） | ⚠️ **台账无 → 先登记** | ⚠️ 需新增 | "HTTP method not allowed" |
| `handleHttpMessageNotReadable` (400) | `"请求体格式错误"` | `COMMON_MALFORMED_REQUEST`（400） | ⚠️ **台账无 → 先登记** | ⚠️ 需新增 | "Malformed request body" |
| `handleException`（兜底） | `"系统内部错误"` | `COMMON_INTERNAL_ERROR`（500） | ✅ 已登记（登记册 §2 明文：未知异常 → `COMMON_INTERNAL_ERROR`） | ✅ 已存在（`StudioErrorCodes.INTERNAL_ERROR`） | "Internal server error" |
| `handleValidation` | 拼接 `"field: message; ..."` | `COMMON_VALIDATION_FAILED`（400） | ✅ 已登记 | ✅ 已存在（`StudioErrorCodes.VALIDATION_FAILED`） | "Validation failed: {{errors}}" |

**为什么不用 `IAM_` / `SYSTEM_` / `BONE_` 前缀（勘误，旧稿三段说明作废）**：

1. **《Bone-错误码登记》§3.1 的域前缀表是唯一合法集合**：`COMMON_ / IAM_ / META_ / MD_ / EXT_ / INT_ / SYS_ / GEN_ / BP_`——**没有 `BONE_`**；`SYSTEM_` 也不是前缀（系统域是 `SYS_`，且专门指 bone-system 的**业务**码，不适合做平台兜底）。
2. **这 6 个是基础设施语义而非业务语义**：无权限、资源不存在、方法不支持、请求体非法、内部错误、参数校验——**任何模块都可能触发**，挂模块前缀会退化成"N 个模块各来一套同义码"，破坏登记册 §2 的"可聚合"。
3. **复用台账既有 `COMMON_*` 码段**（§6 已登记 8 条：`COMMON_VALIDATION_FAILED` / `COMMON_UNAUTHORIZED` / `COMMON_FORBIDDEN` / `COMMON_NOT_FOUND` / `COMMON_CONFLICT` / `COMMON_IDEMPOTENCY_CONFLICT` / `COMMON_RATE_LIMITED` / `COMMON_INTERNAL_ERROR`）。其中 4 条代码常量已存在（`StudioErrorCodes.FORBIDDEN/INTERNAL_ERROR/VALIDATION_FAILED`、`COMMON_IDEMPOTENCY_CONFLICT`），另 4 条（`UNAUTHORIZED`/`NOT_FOUND`/`CONFLICT`/`RATE_LIMITED`）**只是登记未落码**——用到时在 `bone-core` 的 `CommonErrorCodes` 补常量即可，不必新造语义。
4. **新增码必须先登记台账**（登记册 §2「单一登记」+ §5 PR 流程）：本表两个 ⚠️ 码（`COMMON_METHOD_NOT_ALLOWED` / `COMMON_MALFORMED_REQUEST`）需在 PR 里同时更新 `doc/architecture/Bone-错误码登记.md` §6 `COMMON_` 表，否则 CI（§8.2）判为"码不在台账"。

- 这些 errorCode **必须**声明为 `public static final String` 常量，统一放 **`bone-core` 新增的 `CommonErrorCodes`**（bone-iam 已依赖 bone-core；放 handler 内部常量区也能扫到，但会诱导后续模块各写一份）。
- **扫描约束**（与 §8.2 对齐）：常量值必须是 `{PREFIX}_{SNAKE_CASE}` 形式且出现在台账里；不得在 handler 体内写裸字符串字面量，也不得只用枚举承载（枚举值扫不到）。
- `handleValidation` 的 `detail` 里已有具体字段+错误描述，英文文案可带参数（`{{errors}}`）。
- 表中"建议英文文案"**只是提议值**，真源是前端 `en-US.json` 的 `errors.*`（§3.1 ②）；PR review 时以语言包为准。

**改动范围**：每个 handler 改 `buildProblemDetail(status, detail, null, request)` → `buildProblemDetail(status, detail, errorCode常量, request)`，message 仍保持中文不变（fallback 契约）。

**完整 handler 改动示例**（明确 errorCode 在 handler 体内怎么取）：

```java
// IamExceptionHandler.java（改动前）
@ExceptionHandler(AccessDeniedException.class)
public ResponseEntity<ApiResponse<?>> handleAccessDenied(
        AccessDeniedException ex, HttpServletRequest request) {
    Map<String, Object> problem = buildProblemDetail(403, "无权限访问该资源", null, request);
    return ResponseEntity.status(403).body(new ApiResponse<>(false, 403, "无权限访问该资源", problem, null));
}

// IamExceptionHandler.java（改动后）
@ExceptionHandler(AccessDeniedException.class)
public ResponseEntity<ApiResponse<?>> handleAccessDenied(
        AccessDeniedException ex, HttpServletRequest request) {
    // COMMON_FORBIDDEN 等声明在 bone-core 新增的 CommonErrorCodes（public static final String）
    ProblemDetail problem = buildProblemDetail(403, "无权限访问该资源", CommonErrorCodes.FORBIDDEN, request);
    // 信封统一用 bone-core 既有工厂（与 metadata / extension 一致）
    return ResponseEntity.status(403).body(ApiResponse.fail(403, "无权限访问该资源", problem));
}

// handleValidation 同理（改动前）
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ApiResponse<?>> handleValidation(
        MethodArgumentNotValidException ex, HttpServletRequest request) {
    String detail = ex.getBindingResult().getFieldErrors().stream()
        .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
        .collect(Collectors.joining("; "));
    Map<String, Object> problem = buildProblemDetail(400, detail, null, request);  // ← null
    return ResponseEntity.badRequest().body(new ApiResponse<>(false, 400, "请求参数校验失败", problem, null));
}

// handleValidation 同理（改动后）—— COMMON_VALIDATION_FAILED 是跨模块公共码（已登记）
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ApiResponse<?>> handleValidation(
        MethodArgumentNotValidException ex, HttpServletRequest request) {
    String detail = ex.getBindingResult().getFieldErrors().stream()
        .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
        .collect(Collectors.joining("; "));
    ProblemDetail problem = buildProblemDetail(400, detail, CommonErrorCodes.VALIDATION_FAILED, request);
    // 结构化字段错误同时填 errors（真源：bone-core ProblemDetail.FieldError + OpenAPI FieldError.yaml）
    problem.setErrors(toFieldErrors(ex.getBindingResult().getFieldErrors()));
    return ResponseEntity.badRequest().body(ApiResponse.fail(400, "请求参数校验失败", problem));
}
```

> 实现者直接从 handler 常量区抄 errorCode 字符串即可，无需从异常对象或 message 里 parse——避免错误提取和空值处理的麻烦。

### 6.4 时区（P0-A，正确性项）**[Target]**

**现状实测（2026-09-25，勿按"规范已要求"默认成立）**：后端**没有**任何 UTC 序列化配置——全仓 grep 无 `spring.jackson.*` 配置、无 `Jackson2ObjectMapperBuilderCustomizer`、无 `ObjectMapper.setTimeZone`（`ObjectMapper` 的 12 处注入全部用于幂等/缓存，与 Web 序列化无关）；`@JsonFormat` 仅 7 处；`LocalDateTime` 出现在 **160** 个文件。默认 Jackson 序列化 `LocalDateTime` **不带任何时区/偏移信息**（形如 `2026-09-25T12:00:00`，或开启 `WRITE_DATES_AS_TIMESTAMPS` 时为数组）。

这不是"偶发漏加 `Z`"，而是**当前所有时间字段的默认形态**。把它当作已满足的前提会导致静默错误：前端 `dayjs.utc(v).tz(LOCAL_ZONE)`（§5.6.2）会把无偏移的时间**当作 UTC 解析再转本地**，稳态偏移 +8 小时，且不报错、不可见。

**任务（P0-A，独立于 i18n 改动的框架级变更）**：

1. 统一服务端输出语义：`LocalDateTime` 一律按 **UTC** 落库/读取，序列化输出 **带偏移的 ISO-8601**（`...Z`）；落配置 `spring.jackson.time-zone=UTC` + `WRITE_DATES_AS_TIMESTAMPS=false`（Spring Boot 默认已是 false，需显式确认）。
2. 明确"谁负责加 `Z`"：`LocalDateTime` 自身不带时区，要么统一改为 `Instant` / `OffsetDateTime`（全仓仅 94 处引用，改造面可控但属领域模型变更、需单独立项），要么在 Web 层统一补 `UTC` 语义——**二选一，写进 ADR-0038，不允许各模块自行解释**。
3. 回归范围：这动的是**全局序列化配置**，影响 160 个文件对应的全部时间字段，可能打断既有契约快照测试与前端硬编码期望值，**必须单独一个 PR + 全模块冒烟**，不与 errorCode 改造混在一起。
4. 验收断言：契约测试断言时间字段匹配 `^\d{4}-\d{2}-\d{2}T.*(Z|[+-]\d{2}:\d{2})$`；前端 `formatDate` 对**不带偏移**的输入显式告警（不静默兜底）。

> 顺序上必须先于 P1：时区错了，英文界面上的时间全是错的，且用户无法察觉。

### 8.2 CI 校验脚本（阻断级）

**核心问题**：errorCode（后端 Java String 常量）与前端语言包（JSON key）是**两端独立维护的数据**，易漂移。必须用脚本自动校验，防止"后端加了新码但前端漏了翻译"。

#### 8.2.1 脚本位置

```

                                 # python3 实现，与 scripts/check-*.py 系列一致；不依赖 rg / jq（§8.2.3）
```

#### 8.2.2 校验内容

**基线选择（关键修正）**：旧稿用「全仓 `*.java` 正则扫 `public static final String`」做基线，实测产出 **153 个候选值**，混入大量非错误码常量（`ADDRESS` / `EMAIL` / `NAME` / `ID_CARD` / `GENERAL` / `'EXT_'` 前缀常量 / `CREATED` / `DROPPED` …），要求语言包覆盖它们既无意义也不可行。修正为**双源 + 一个方向性规则**：

- **代码集合**（`*ErrorCodes.java` / `*Errors.java` 常量，实测 **136**）＝ **"真实可达"的码**，是语言包必须覆盖的对象；
- **台账集合**（§6 表，实测 109）＝ **"合法登记"的码**，用于阻断"加了码没登记"；
- **反向不阻断**：台账里存在但代码里没有的码（实测 43 条）**只告警不阻断**——登记册自己有过前例（`IAM_PASSWORD_MUST_CHANGE` 因"零抛出点"被删），若强行要求为前瞻条目写译文，就会重演"理想码清单"污染；这类条目应人工确认是"待实现"还是"该删"。

| 5 | **台账 ∃ 代码无（前瞻条目）** | 仅打印清单供人工确认，**不阻断**（见上方"反向不阻断"） | 🟡 警告 |

| 8 | **`ApiResponse` 顶层无 `errorCode` 字段** | 在 `bone-core` 的 `ApiResponse.java` 内断言无 `errorCode` 字段（§6.2.1 明确只在 `ProblemDetail`） | 🔴 阻断 PR |
| 9 | **`enums` 覆盖率（内置枚举）** | 以**内置清单**（`config/i18n/builtin-dicts.json`，P2 前置产出）为输入，校验每个 `(type, code)` 在 `enums` 语言包都有 key；差集 = 缺译 | 🔴 阻断 PR（P2 起启用） |
| 10 | **禁止绕开取数入口** | 除 `useEnumLabel`/`EnumTag` 所在文件外，源码中不得出现 `enums.` 拼接 | 🟡 警告 |

> **关于第 9 项的前置**：`enums` 覆盖率校验**必须**有一个"内置枚举清单"作为输入，而当前仓库并没有这份真源——`scripts/seed-system-dicts.py` 只是联调用的 API 灌数据脚本（`SYS_STATUS` / `SYS_YES_NO` / `SYS_LOG_LEVEL` / `SYS_ALERT_LEVEL`），既不是全量清单、也不参与构建。所以 P2 的第一件事是把清单落成机器可读文件（建议 `config/i18n/builtin-dicts.json`：`[{ "type": "SYS_STATUS", "codes": ["ENABLED","DISABLED"] }]`），它同时是 ① 语言包骨架生成的输入、② 本项校验的输入、③ `DictType` 命名规范的验收对象。清单缺失时脚本**跳过并告警**（不阻断），避免 P0/P1 阶段被未落地的前置项卡住。

> **两条扫描约束**（否则 CI 误报/漏报，与 §6.2.2 呼应）：
> ① 常量值只认 `^[A-Z][A-Z0-9_]{2,}$` 且**只扫 `*ErrorCodes.java` / `*Errors.java`**——不要扫全仓 `*.java`（会捞到 `'EXT_'`、`"GENERAL"` 这类非码常量）；新建的基础设施码集中放 `bone-core` 的 `CommonErrorCodes`，自然落入扫描范围。
> ② 不得只用枚举（`ErrorCode.IAM_XXX`）承载——枚举值扫不到，会被判成"后台缺码"。

#### 8.2.3 脚本（python3 版，可直接落地）

> **为什么从 bash 版改成 python3**（v1.4 的 bash 版实测仍跑不起来）：⑤ 它依赖 **`rg`（ripgrep），本机未安装**（`command -v rg` 无输出，`jq` 同样没有）——而 §8.2.4 要求 `scripts/check.sh` 调用它，本地提交时会直接 `command not found`；GitHub 托管 runner 是否预装 ripgrep 不受我们控制，不应作为门禁前提。仓库既有门禁（`check-sdk-persistence.py` / `check-doc-code-symbols.py` 等十余个）已**统一用 python3**，`check.sh` 里就是 `python3 scripts/xxx.py --check` 的调用形态——跟它保持一致最省事。
>
> 前四处硬伤（v1.4 已修）保留在案，供回溯：① `rg -oP` 多文件搜索输出 `file:match` 前缀，导致 `comm` 恒不相等；② `-h` 在 ripgrep 里是 `--help`；③ 全文档扫台账会把 §3.1 前缀表抓成码，须限定 §6 区间；④ 依赖本机没有的 `jq`。
>
> **实测结果（2026-09-25，python3 版）**：语言包未建时先报「语言包不存在（P0-B 未完成）」并 `exit 1`；建立语言包后输出「代码常量 **136** / 台账 §6 **109**」并报「有码未登记 70 条」。与 v1.4 bash 版的 133/109/67 相差 3 条——差异来自正则宽松度（python 版容忍 `String  X   =  "Y"` 的多余空格/换行，rg 版要求单空格），**同口径、非新问题**；落地时以脚本实测数为准，不要照抄文档里的历史数字。

```python
#!/usr/bin/env python3
"""i18n 同步校验：后端 errorCode 常量 <-> 错误码台账 <-> 前端语言包。

放在 scripts/ 下（与 check-*.py 系列一致），由 scripts/check.sh 与 CI 共同调用。
用法：python3 scripts/check-i18n-sync.py   （退出码 0 通过 / 1 阻断）
"""

import json
import re
import sys
from pathlib import Path

# 脚本位于 scripts/ 下，parents[1] 即仓库根（不依赖 cwd，也不依赖 git）
REPO = Path(__file__).resolve().parents[1]
SKIP = {"target", "node_modules", "dist", "build", ".git", "generated-code"}
LOCALES = "bone-frontend/packages/shared-utils/src/i18n/locales"
LEDGER = "doc/architecture/Bone-错误码登记.md"
DICTS = "config/i18n/builtin-dicts.json"
API_RESPONSE = "bone-framework/bone-core/src/main/java/com/bone/core/model/ApiResponse.java"

# 容忍多余空格/换行，比 `String \w+ = "` 更宽松（v1.4 bash 版漏掉 3 个对齐声明的常量）
CODE_RE = re.compile(r'public static final String\s+\w+\s*=\s*"([A-Z][A-Z0-9_]{2,})"')
# 只匹配 §6 台账表格的行首码列，避免把 §3.1 前缀表（| `IAM_` | ... |）抓成码
LEDGER_ROW_RE = re.compile(r'^\|\s*`([A-Z][A-Z0-9_]{2,})`\s*\|')


def walk(suffixes):
    """遍历仓库文件，跳过构建产物与生成代码。"""
    for p in REPO.rglob("*"):
        if not p.is_file() or p.suffix not in suffixes or (SKIP & set(p.parts)):
            continue
        yield p


def code_codes():
    """代码侧：只扫 *ErrorCodes.java / *Errors.java（扫全仓会捞到 ADDRESS/EMAIL 等非码常量）。"""
    out = set()
    for p in walk({".java"}):
        if p.name.endswith("ErrorCodes.java") or p.name.endswith("Errors.java"):
            out |= set(CODE_RE.findall(p.read_text(encoding="utf-8", errors="ignore")))
    return out


def ledger_codes():
    """台账侧：必须限定在 §6 区间内取码。"""
    f = REPO / LEDGER
    if not f.exists():
        return set()
    lines = f.read_text(encoding="utf-8", errors="ignore").splitlines()
    try:
        start = next(i for i, l in enumerate(lines) if l.startswith("## 6."))
        stop = next(i for i, l in enumerate(lines[start + 1:], start + 1) if l.startswith("## 7."))
    except StopIteration:
        return set()
    return {m.group(1) for l in lines[start:stop] if (m := LEDGER_ROW_RE.match(l))}


def error_keys(path):
    """语言包 errors 命名空间的 key 集合；文件不存在返回 None（P0-B 未完成）。"""
    f = REPO / path
    if not f.exists():
        return None
    return set(json.loads(f.read_text(encoding="utf-8")).get("errors", {}) or {})


def report(title, items):
    items = sorted(items)
    tail = " ..." if len(items) > 10 else ""
    print(f"❌ {title}（{len(items)} 条）: {' '.join(items[:10])}{tail}")


def grep_hits(suffixes, pattern, roots):
    rx = re.compile(pattern)
    return [
        f"{p.relative_to(REPO)}:{i}"
        for p in walk(suffixes)
        if roots & set(p.parts)
        for i, l in enumerate(p.read_text(encoding="utf-8", errors="ignore").splitlines(), 1)
        if rx.search(l)
    ]


def main():
    fail = 0
    codes = code_codes()
    ledger = ledger_codes()
    en = error_keys(f"{LOCALES}/en-US.json")
    zh = error_keys(f"{LOCALES}/zh-CN.json")

    if en is None or zh is None:
        print(f"❌ 语言包不存在（P0-B 未完成）：{LOCALES}/en-US.json | zh-CN.json")
        return 1

    print(f"=== check-i18n-sync ===  代码常量 {len(codes)} / 台账 §6 {len(ledger)} / en-US keys {len(en)}")

    # 1) 代码常量 ⊆ 台账（新增码未登记 → 阻断）
    if unregistered := codes - ledger:
        report("有码未登记台账", unregistered)
        fail = 1
    # 2) 3) 真实可达的码必须在两份语言包都有（缺译 → 阻断）
    if en_missing := codes - en:
        report("en-US 缺 errorCode", en_missing)
        fail = 1
    if zh_missing := codes - zh:
        report("zh-CN 缺 errorCode", zh_missing)
        fail = 1
    # 4) 两份语言包 errors key 对称
    if en != zh:
        print(f"❌ en-US / zh-CN errors key 不对称（差 {len(en ^ zh)} 条）")
        fail = 1
    # 5) 台账有、代码无（前瞻/漏实现）→ 仅告警，不阻断
    if phantom := ledger - codes:
        print(f"⚠️ 台账有、代码无（{len(phantom)} 条，确认是待实现还是该删）: {' '.join(sorted(phantom)[:10])} ...")

    # 7) 无裸 toLocaleString（警告）
    if hits := grep_hits({".ts", ".tsx"}, r"\.toLocaleString\(", {"apps", "packages"}):
        print(f"⚠️ 仍有 toLocaleString，请改用 formatDate(): {hits[:5]}")

    # 6) fallback 命名空间不混入 errorCode 形态的 key（警告）
    for name in ("en-US.json", "zh-CN.json"):
        pkg = json.loads((REPO / LOCALES / name).read_text(encoding="utf-8"))
        bad = [k for k in (pkg.get("fallback") or {}) if re.fullmatch(r"[A-Z][A-Z0-9_]{2,}", k)]
        if bad:
            print(f"⚠️ {name} 的 fallback.* 混入 errorCode 形态 key（应放 errors.*）: {bad[:5]}")

    # 8) ApiResponse 顶层不得出现 errorCode
    ap = REPO / API_RESPONSE
    if ap.exists() and re.search(r"private\s+\w+\s+errorCode", ap.read_text(encoding="utf-8")):
        print("❌ ApiResponse 顶层不得含 errorCode（应放 ProblemDetail）")
        fail = 1

    # 9) enums 覆盖率（P2 起启用；前置：内置清单 config/i18n/builtin-dicts.json）
    df = REPO / DICTS
    if df.exists():
        dicts = json.loads(df.read_text(encoding="utf-8"))
        miss = []
        for name in ("en-US.json", "zh-CN.json"):
            pkg = json.loads((REPO / LOCALES / name).read_text(encoding="utf-8"))
            enums = pkg.get("enums") or {}
            miss += [
                f"{name}:{d['type']}.{c}"
                for d in dicts
                for c in d.get("codes", [])
                if c not in (enums.get(d["type"]) or {})
            ]
        if miss:
            report("enums 缺译", miss)
            fail = 1
    else:
        print(f"⚠️ 未找到 {DICTS}（P2 前置未完成），跳过 enums 覆盖率校验")

    # 10) 禁止绕开枚举取数入口拼接 enums key（警告）
    if splice := grep_hits({".tsx"}, r"enums\.\$\{|`enums\.|\"enums\.", {"apps"}):
        print(f"⚠️ 存在绕开 useEnumLabel/EnumTag 的 enums key 拼接（§5.3）: {splice[:5]}")

    return fail


if __name__ == "__main__":
    sys.exit(main())
```

> **首次落地必做（存量漂移处理）**：当前 未登记 **70** 条、前瞻条目 **43** 条，脚本一开就会报一片。建议顺序：① 先跑一次**只出报告不阻断**；② 把真实业务码补登记台账 §6；③ 对 `metadata-engine/.../ErrorCodes.java` 里不符合前缀规范的历史码（`DATA_*` / `MODEL_*` / `INVALID_*` / `APPROVAL_FAILED` 等）按登记册 §3.2「存量整数码/历史码」规则豁免或改名，或在脚本里维护**显式白名单文件**（不允许隐式放行）；④ 43 条前瞻条目人工确认去留（登记册已有"零抛出点即删"的先例）；⑤ 再打开阻断。

#### 8.2.5 业界工具链：自动提取 + i18n Lint（防漂移）

仅靠人工维护 key 易漏译。业界标准做法引入两条自动化防线（均**不改业务代码**，只加 devDependency 与 CI 步骤）：

- **`i18next-scanner`**：扫描源码自动提取 `t('...')` / `useTranslation()` 调用中的 key，生成/补全语言包骨架，避免"用了 key 但 JSON 漏建"。
- **`eslint-plugin-i18next`**：禁止 JSX 中出现裸中文字面量、检测 `t()` 缺失 key，从源头拦截硬编码文案（对应 §8.1 最后一条检查项）。

这两条与 §8.2.2 的"errorCode 双语文案差集校验"互补：前者防**前端 UI key** 漂移，后者防**前后端 errorCode** 漂移。两者都是业界（i18next 官方推荐的）成熟工具，非自研。

> **分期与审批**：`i18next-scanner` 可在 P1 引入（生成骨架，不阻断）；`eslint-plugin-i18next` 的"禁止裸中文字面量"规则与 P3（全量页面文案）绑定，**首期不开**——否则 P0/P1 阶段所有存量页面立刻红灯。两者都是新增 devDependency（**L3 审批**）。

## 10. 风险与决策点

1. **后端是否要 MessageSource** — 本方案默认否（前端映射）。若产品要求「API 响应 message 直接是用户语言」，则改为 [Vision]→[Target]。
2. **P3 全量页面翻译** — 默认推迟到出现真实英文用户/出海需求；首期验收口径见 §1.2（P0–P2 含壳层通用文案），**不要按"全站已双语"对外承诺**。
3. **locale 持久化** — 用 `localStorage` 单端存储；如未来需跨端一致，再引入用户偏好字段（届时触发 §1.3 排除项的租户级配置）。
4. **与发版节奏** — 当前主线 `release/mvp-v1.0`（ahead 2），建议 i18n 骨架在 MVP 发布之后启动，避免混入发布分支。
5. **固化决策为 ADR** — 「后端不翻译 / 前端映射 / 枚举走 `enums` 命名空间 + `dict.label` 兜底 / SysDict 不改表 / 每应用一 i18n 实例 + core-event-bus 单源 / `ProblemDetail` 统一模型与 `COMMON_*` 基础设施码 / 回退链」是跨前后端架构契约，建议补 **ADR-0038（国际化架构决策）** 固化（现有 ADR 最新为 0037），避免后续有人引入 `MessageSource`、误改 SysDict 加翻译列、把 UI 文案挪到 system 后台（与 §6.3 [Vision] 边界冲突），或再给 IAM 手写第二套 `ProblemDetail`。
6. **L3 审批前置** — 依赖引入、包依赖边、CI 脚本、新码登记四项必须在 P0 开工前一次性报批（清单见 §7），否则实现到一半会卡在审批而不是技术。
7. **存量偏差** — §2 指出三处存量问题（代码常量 136 vs 台账 §6 109：未登记 70、前瞻 43；4 个 handler 不产 `ProblemDetail`；**时间字段无 UTC 契约、160 个文件受影响**），它们**不是本次 i18n 引入的**，但会直接决定 P1 的成色；建议在 P0-A 一并收口，若确认推迟，需在 PRD/验收里显式降级为"仅在 IAM / metadata / extension 三模块生效"、"时间显示不保证时区正确"。
8. **枚举的"值域可知性"边界**（§3.1）— 本方案的枚举翻译只覆盖**编译期可知**的枚举；**租户自定义字典条目**在 en-US 下显示 `label` 中文原文，属已接受的降级。若业务要求"自定义条目也双语/按租户覆盖"，需单独立项：`i18n_message` 表（`(tenant_id, locale, module, message_key) → content`）+ 独立缓存 + 版本回退 + 走 `bone-metadata-sdk`（HC-001）。**该需求出现前不动 DDL。**
9. **`DictType` 规范缺口**（§3.1 配套缺口）— 大小写无约束（seed `SYS_STATUS` vs 领域测试 `order_status`）会让 `enums.${type}.${code}` 静默回落中文；`DictType` 允许 64 字符而 DDL 为 `VARCHAR(50)`。建议 P2 前置处理：应用层统一 `UPPER_SNAKE` + 字符集校验（L2），长度对齐若改 DDL 则 L3。

## 11. 总结

Bone 国际化「规范已就位、实现为零」：架构接缝（稳定 errorCode、`globalContext.locale` 类型、事件总线、`bone-core` 的 `ProblemDetail` 模型）已预留，故加 i18n 是低成本而非推翻重来。方案坚持**稳定键 + 展示分离 + 单源 locale + 回退链**四项原则，前端承担主要工作（react-i18next + 错误统一函数 + locale 管道 + dayjs 格式化），后端只做**收敛而非新增**：把 8 个 handler 统一到既有 `ProblemDetail` 模型、复用 `COMMON_*` 基础设施码，外加一项**补欠账**——时间字段 UTC 契约（当前全仓无 Jackson 时区配置，160 个文件受影响，§6.4）——**不做业务翻译**。

> 与 v1.1 的差别在于一份诚实的成本结构：真正的工作量不在"引 i18n 库"，而在 ① 4 个 handler 从"无 ProblemDetail"迁到统一模型（否则 P1 只覆盖 3/8 模块）、② 78 处前端散点（含双兜底形态）的替换、③ 6 个微应用补订阅 + `BoneAppProvider` 的机制二选一、④ 存量码表与台账的 113 条差异（70 未登记 + 43 前瞻）先清零或显式白名单、⑤ **时间字段 UTC 契约**——全局序列化配置变更，影响 160 个文件的时间字段，必须单独 PR 全模块冒烟（§6.4）。这五件事都在 §7 的 P0 里显式列出并标注了审批级别。

**下一步**：评审通过 → 其余模块按 §12 的样板清单复制 → 再接 P1 前端散点替换（78 处）。
