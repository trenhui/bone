## 1. 要回答的五个问题（结论先行）

### 1.1 元数据与租户的关系是什么？—— **As-Is 是「模型 100% 租户私有」，缺平台模型层，导致 N 个租户 N 遍重复建模**

| 层 | 内容 | 归属 | As-Is | 裁决 |
|----|------|------|-------|------|
| **平台模型层** | 行业模板、通用域模型（客户/订单/支付/物料…）、内置模型、数据标准与字典 | **平台（tenant_id=0）** | ❌ **完全缺失** | [Target] 平台预置 + 租户实例化 |
| **租户共享层** | 租户级通用模型，跨应用复用（如租户自己的「组织」「员工」） | **租户（tenant_id>0）** | ❌ 无区分（与私有层混在一起） | [Target] 新增 `scope` 显式分层 |
| **应用私有层** | 挂在某应用某模块下的业务实体 | **租户（tenant_id>0）+ module_id** | ✅ `meta_entity.module_id` 已存在 | 保持并收紧 |

> **证据**：`bone-init.sql:757-781` `meta_entity.tenant_id BIGINT NOT NULL`（**无 DEFAULT 0**，与 `meta_code_template.tenant_id DEFAULT 0`、主数据 `md_entity DEFAULT 0` 口径不同）⇒ 当前**任何一条元数据都必须属于某个具体租户**，平台层模型在物理上无法表达。
> **证据**：`MetaEntity.create(...)` 中 `e.builtin = false` 恒写死，`is_builtin` 列全仓**无任何读取点** ⇒ 「内置模型」这一概念有名无实。
>
> **裁决结论（与主数据 §1.1 同构）**：
> **「通用模型与标准是平台的，实例化与业务模型是租户的，业务模型挂在应用模块下」。**
> 这条结论直接关闭 `meta_entity.tenant_id` 是否允许 0 的争议，也是 §3.1 三层模型的依据。

### 1.2 元数据与应用 / 模块的关系是什么？—— **只有一根「存在性校验」的弱关联，权限、过滤、部署单元三条全断**

```
meta_entity.module_id  →  bone_module.id  →  bone_application.app_id      （IAM 上下文）
meta_field.module_id   →  bone_module.id                                  （冗余，与实体归属可能不一致）
```

| 维度 | As-Is 事实 | 证据 | 后果 |
|------|-----------|------|------|
| **归属可写** | `module_id` **可空**，可建无归属实体 | `bone-init.sql:768` `DEFAULT NULL` | 列表里必然出现「未分组」黑洞 |
| **归属校验** | 只显式校验**存在性**；租户一致性**未被显式断言**，靠 SDK 读侧自动租户过滤**隐式兜住**（`SelectBuilder` → `TenantFilterInjector.inject`，ADR-0029）⇒ 能挡住，但属隐式依赖 | `IamModuleValidator#requireExists`（`bone-metadata-server/.../domain/service/IamModuleValidator.java:20-27`）；`bone-init.sql:1616` DDL 注释「SDK 自动过滤/回填」 | 一旦有人改用 `disableTenantFilter()` 或改为 Feign 调 IAM，防线即消失；应补显式断言 |
| **同租户跨应用** | 应用角色（`bone_app_permission.role` = ADMIN/DEVELOPER/VIEWER）在 metadata 侧 **0 处消费** | `bone_app_permission` 全仓仅在 IAM 侧使用 | **真正的 As-Is 越权**：持 `metadata:write` 即可在**任意**应用模块下建模/改模型 |
| **归属可过滤** | 列表查询对象 `MetaEntityPageQuery` 只有 `pageNum/pageSize/keyword/status`，**无 moduleId / appId** | `MetaEntityPageQuery.java` | 前端模型树只能「拉全量 + 前端分组」，规模一大即不可用；也无法按应用做权限收敛 |
| **应用角色未消费** | `bone_app_permission.role`（ADMIN/DEVELOPER/VIEWER，DDL 已建）在 metadata 侧 **0 处引用** | 全仓检索 | 「我是 OMS 开发者」在建模台里完全无效 |
| **部署单元** | 发布动作是**单实体** `POST /entities/{id}/publish` | 详设 §5.1 | 无法回答「这次上线改了什么」⇒ 无变更集、无回滚、无审批 |
| **消费引用** | 无任何「谁在用这个模型」的登记 | 无 | 改字段不知道会打挂谁 ⇒ 影响分析无从谈起 |
| **「我的应用」** | ~~假实现~~ ✅ **已修（2026-09-26，G15）**：`/apps/mine` 按 `bone_app_permission` 真过滤当前用户（平台管理员回退全量），前端已接线 | `AppApplicationService#myApps` | 建模台树的「应用」维度已含用户可见性语义 |

> **G1 ②（应用角色强制）的可行性与阻塞**：JWT 内**已含 `userId` claim**（`bone-security` `JwtTokenService`），网关另注入可信 `X-User-Id`
> （`JwtAuthGlobalFilter`，且会剥离客户端伪造头）⇒ 技术上可解析操作者账号 ID 并查 `bone_app_permission`。
> G15 已修（`/apps/mine` 真过滤），**G1 ② 剩余前置仅一个**：无主体场景（E2E 关闭安全、API-Key 模式）无法判定角色，
> 须先定「拒绝 / 平台权限豁免」策略后方可强制。

> **一句话**：As-Is 的「应用 → 模块 → 实体」只是**一棵展示用的树**，不是权限边界、不是过滤条件、不是部署单元、不是影响面。这就是"功能割裂"在技术上的根因。

### 1.3 谁能用元数据管理？—— **As-Is 只有 3 个权限码，把「建模」「发布」「运营改数据」三件事混成一个人**

`bone-init.sql:283-285` 的元数据权限码全集只有三条，且 `resource_path = '*'`（无应用/模块维度）：

| code | name | 说明 |
|------|------|------|
| `metadata:read` | 元数据-读 | 所有读 |
| `metadata:write` | 元数据-写 | **建模 + 改运行时业务记录 + 发布（publish 兼容 write）** |
| `metadata:publish` | 元数据-发布 | catalog 实体 publish |

由此产生三个真实风险（不是理论风险）：

1. **运营人员能改模型**：模式 B 的「运营台录数据」与「建模改字段」共用 `metadata:write`，发给运营的账号天然具备改表结构的能力。
2. **发布无审批、无环境**：`publish` 直接改 `meta_entity.status` 并 `align()` 物理表，**一步到生产**，无 dry-run、无审批、无回滚。
3. **跨应用无隔离**：有 `metadata:write` = 能改**本租户任意应用**的所有模型（跨租户由 SDK 隐式挡住，跨应用无防线）。

角色矩阵与权限码全集见 §4。

### 1.4 元数据管理模块的定位是什么？—— **建模元模型控制面，不是数据目录，更不是业务数据库**

一句话定位：

> **元数据管理是 Bone 的「系统长什么样」的唯一定义源（SSOT）：把业务概念（实体 / 字段 / 关系 / 标准）定义清楚，变成可运行的系统（模式 A 生成源码 / 模式 B 运行时 API），并对模型的归属、发布、演进与被消费负全责。**

三个必须先划清的边界（业界最常见的定位事故都出在这里）：

| 边界 | 结论 |
|------|------|
| **元数据 vs 数据目录（Data Catalog）** | 元数据库管的是**要建的系统**（建模元模型 / model-time metadata）；Atlan / DataHub / Alation 那类数据目录管的是**已存在的数据资产盘点**（业务/技术/操作元数据 + 血缘 + 术语表）。Bone 当前属于**前者**；血缘/标准/质量规则三张治理表归主数据（G6 裁定 2026-09-26，表已改名 `md_lineage`/`md_standard`/`md_quality_rule`），元数据模块不持有。 |
| **元数据 vs 主数据** | 元数据定义**结构**（`meta_entity` / `meta_field`）；主数据持有**实例与质量**（`md_entity` / `md_record`）。二者**不双写**，经 `POST /api/v1/masterdata/entities/convert?metaEntityId=` 单向复制 + `md_entity.meta_entity_id` 追溯（ADR-0017）。 |
| **元数据 vs 业务数据** | 模式 B 的运行时 CRUD 是「按模型读写业务记录」，**记录本身不是元数据**。建模权限与记录读写权限必须拆开（§4.3）。 |

### 1.5 为什么现在是割裂的？—— 六个断点

| # | 断点 | 表现 |
|---|------|------|
| 1 | **入口是功能，不是场景** | 菜单是「建模工作台 / 模型管理 / 关系管理 / 运行时数据」（`bone-shell/src/App.tsx:287-295`）——按**对象类型**排，不是按**用户要办的事**排 |
| 2 | **树是装饰** | 模型树接了 IAM 真数据，但后端无 moduleId 过滤、无应用角色 ⇒ 树不能收窄权限，也不能收窄查询 |
| 3 | **发布是点，不是包** | 单实体 publish，无变更集/审批/回滚/环境 |
| 4 | **交付后无回声** | 发布 → 生成源码 / 运行时 API，但**没有"谁在消费"的登记**，采用率、影响面全是黑盒 |
| 5 | **平台无沉淀** | 没有模板层，每个租户从零建模，最佳实践无法复用 |
| 6 | **血缘与标准归口冲突** | 表在 `meta_*`，实现在 masterdata，元数据模块看不见 |

## 2. 定位、能力边界与能力链

### 2.1 模块定位（能做什么）

```
                    ┌────────────────────────────────────────────┐
   平台层(tenant=0) │  行业模板 · 通用域模型 · 数据标准 · 字典 · 内置模型 │  ← 平台建模架构师
                    └───────────────────┬────────────────────────┘
                                        │ 实例化 / 版本升级
                    ┌───────────────────▼────────────────────────┐
   租户层(tenant>0) │ ①规划 ②建模 ③校验 ④发布 ⑤交付                │  ← 建模负责人 / 应用建模者
                    └───────────────────┬────────────────────────┘
                                        │ API / SDK / 生成物 / 集成
                    ┌───────────────────▼────────────────────────┐
   消费层           │ 业务应用 · 主数据 · 集成 · 运营台 · 外部系统     │  ← 开发者 / 运营 / 集成专员
                    └───────────────────┬────────────────────────┘
                                        │ ⑥消费登记 ⑦演进反馈
                                        ▼
                              血缘 · 影响分析 · 版本回滚
```

**七段式能力链（这就是"串联"的骨架）**：

| # | 能力 | 内容 | As-Is |
|---|------|------|-------|
| ① | **规划** | 应用/模块划分（解决方案边界）、选择基线模板、命名与编码规范 | 部分（IAM app/module CRUD ✅；模板 ❌） |
| ② | **建模** | 实体 / 字段 / 关系 / 枚举 / 校验规则 / 数据标准绑定 | ✅ 主体（CRUD）；关系仅语义、不落物理约束 ❌ |
| ③ | **校验** | 静态（命名/类型/必填/唯一/关系闭环）+ 发布期物理结构漂移检测 | 部分（发布期漂移校验 ✅ 本轮新增；静态规则集 ❌） |
| ④ | **发布** | **以模块/解决方案为单元**：dry-run DDL 预览 → 影响分析 → 审批 → 执行 → 生成快照 | ❌（仅单实体裸 publish，直冲生产） |
| ⑤ | **交付** | 模式 A（generator → 源码入 Git）/ 模式 B（`/api/v1/runtime/**` 动态 CRUD） | ✅ 双模式均可用（B 为 v1） |
| ⑥ | **消费登记** | 谁在用这个模型（应用 / 集成流 / 主数据 / 前端页面） | ❌ |
| ⑦ | **演进** | 版本 diff、回滚、弃用与下线、血缘与影响分析 | ❌（版本为 Vision P1） |

### 2.2 准入判据：什么该进元数据建模（防止"万物皆建模"）

元数据建模是**有成本的**：每建一个实体就意味着一张物理表 + 一套 API + 长期演进负担。

| 判据 | 说明 |
|------|------|
| **结构化** | 有稳定的字段集合，能画出表结构（非自由文本/非文档） |
| **事务性或配置性** | 会被业务应用读写（含低频配置表） |
| **需要 UI / API** | 希望自动获得列表页、表单、CRUD API |
| **容量可预期** | 记录量在千万级以内（超出应走专业业务库与分库分表） |

> **反例（不要建模）**：日志流水、埋点事件、文件内容、临时中间表——它们应走专门的存储，不要塞进元数据建模。
> **升格信号**：当某实体被 ≥2 个应用引用、且需要跨系统保持一致时，触发 **UC-MT8 升格主数据**（判据见 [3a §2.2](3a.%20主数据管理模块核心场景及用例设计方案.md)）。

### 2.3 明确不做（Out of Scope）

- ❌ 不做数据资产目录 / 数据发现（那是 Data Catalog 域）
- ❌ 不承载业务记录本身（模式 B 的记录是业务数据，不是元数据）
- ❌ 不实现 ETL / 连接器（归 `bone-integration`）
- ❌ 不重复实现主数据治理（升格后归 `bone-masterdata`，ADR-0017）
- ❌ 不做通用 BI 分析

## 3. 关系模型设计（解决「与租户、应用到底是什么关系」）

### 3.1 三层归属模型（新增 `scope` 列）

```
平台层 (tenant_id = 0)
  meta_model_template        行业模板 / 通用域模型（客户·订单·支付·物料…）+ 默认字段 + 默认校验 + 默认数据标准
  meta_model_template_version 模板版本（semver），租户可选择是否跟随升级
  ——（数据标准已归主数据，G6 裁定：md_standard）
        │
        │ 实例化（复制 + template_id 追溯）
        ▼
租户层 (tenant_id > 0)
  meta_entity   scope = PLATFORM_INSTANCE（来自模板，基模型只读） | TENANT_SHARED（租户通用） | APP_PRIVATE（挂模块）
  meta_field    （模板字段不可删，仅可禁用；租户可加扩展字段）
  meta_entity_relation
```

**核心规则**：

1. 租户**不能改平台模板本身**，只能在实例上加扩展字段 / 禁用模板字段（与 ADR-0017「删除字段=软禁用」同构）。
2. 模板升级由平台发新版本，租户**自主选择**是否同步（避免平台升级打挂租户）。新增字段默认非必填。
3. 唯一的 `uk_meta_e_code(tenant_id, code)` 保持不变 ⇒ 租户实例化后编码归租户。

### 3.2 应用三重语义（建模归属 / 部署单元 / 消费引用）

| 语义 | 载体 | 基数 | 回答的问题 | 层级 |
|------|------|------|-----------|------|
| **建模归属** | `meta_entity.module_id → bone_module → bone_application`（**收紧为必填** + 租户一致性校验 + 应用角色校验） | N:1 | 谁拥有这个模型（权限与责任边界） | [Target] 收紧 |
| **部署单元** | **解决方案 / 模块发布包**：一次发布 = 某模块下 N 个实体的变更集（含 DDL 预览、审批、快照、回滚） | 1:N | 这次上线改了什么、能不能退 | [Target] 新增 |
| **消费引用** | `meta_model_consumer(app_id \| system, entity_id, kind, …)`：谁在消费这个模型（业务应用 / 集成流 / 主数据 / 前端页面） | N:M | 改了影响谁 | [Target] 新增 |

> 三者互不替代：一个「订单」模型**建模归属** OMS/order 模块、**发布**随 OMS v2.3 解决方案包、**被** FMS（对账）、WMS（发货）、集成（同步 ERP）三个消费方引用。

### 3.3 建议新增 / 启用的表与列（DDL 变更须走 L3 审批，真源 `bone-init.sql`）

| 对象 | 用途 | 状态 | 优先级 |
|------|------|------|--------|
| `meta_entity.scope`（`PLATFORM_INSTANCE` / `TENANT_SHARED` / `APP_PRIVATE`） | 三层归属 | ALTER | **P0** |
| `meta_entity.template_id` / `template_version` | 平台模板追溯与升级 | ALTER | P1 |
| `meta_entity.module_id` **收紧 NOT NULL** + 加索引 | 归属必填 | ALTER（存量走「未分组」迁移） | **P0** |
| `meta_model_template` + `meta_model_template_version` | 平台模型层 | 新建 | P1 |
| `meta_release_package` + `meta_release_item` | 发布包（变更集）+ DDL 预览 + 审批 + 回滚 | 新建 | **P0** |
| `meta_model_snapshot` | 发布快照（generator CATALOG_SNAPSHOT 与回滚同源） | 新建 | P1 |
| `meta_model_consumer` | 消费登记（影响分析基础） | 新建 | P1 |
| `meta_entity_version`（详设 §15 已设计） | 版本历史与回滚 | 新建 | P1 |
| `meta_field.module_id` | **建议废弃**（与实体归属冗余且易不一致，字段归属取实体） | 清理 | P2 |
| ~~`meta_data_lineage` / `meta_data_standard`~~ | ✅ 已裁定（2026-09-26）：归主数据并改名 `md_lineage` / `md_standard` / `md_quality_rule` 移出 `meta_*` | **已落地** | — |

> ⚠️ 上表**不是 SQL 副本**，落地一律改 `bone-init.sql` 真源 + 刷新基线，见 [数据库开发规范](../../architecture/数据库开发规范.md)。

## 4. 参与者、角色与权限码

### 4.1 角色定义（对齐 Salesforce / Dataverse ALM）

| 角色 | Sales­force / Dataverse 对应 | 管什么 | 不碰什么 | As-Is |
|------|------------------------------|--------|---------|-------|
| **平台建模架构师**（Platform Modeler） | Platform App Builder / System Administrator | 平台模型层：行业模板、通用域模型、内置模型、数据标准与字典、跨租户巡检 | 不碰租户业务模型与业务记录 | ❌（仅超管兜底） |
| **租户建模负责人**（Model Lead） | Release Manager / Environment Admin | 租户共享层模型、应用与模块划分、发布审批、治理策略（是否强制审批/版本） | 不做日常建模录入 | ❌ |
| **应用建模者**（App Modeler / Developer） | App Builder / Maker | 在**自己有角色的应用模块内**建模：实体/字段/关系/校验，提交发布 | 不能发布到生产、不能改平台模板、不能改别的模块 | ❌（现 `metadata:write` = 改全部） |
| **发布审批人**（Release Approver） | Deploy / Change Set Approver | 审阅 DDL 预览 + 影响面，批准/驳回发布包，**不得审批本人提交**（SoD） | 不能同时是提交人 | ❌ |
| **运行时数据运维**（Runtime Operator） | 运营 / 数据录入 | 模式 B 实体的**业务记录** CRUD（运营台） | **不能改模型结构** | ❌（与建模共用 `metadata:write`） |
| **消费方**（Consumer：业务应用 / 集成 / 主数据） | Connected App / Application User | 只读消费已发布模型与运行时数据，登记订阅 | 不能改模型 | ❌（无登记） |
| **平台管理员** | Admin | 平台配置与应急 | — | `is_admin` 兜底 |

### 4.2 六条红线

1. **平台模型层不可被租户直接改**：租户只能实例化 + 扩展 + 禁用，不能改基模型。
2. **租户不自造平台模板**：模板是平台资产（与 IAM「租户不自造权限码」同构）。
3. **建模权与数据权分离**：能录业务记录 ≠ 能改表结构（拆 `metadata:model:write` 与 `metadata:runtime:write`）。
4. **应用角色是硬边界**：没有该应用 DEVELOPER/ADMIN 角色 ⇒ 不能在该应用下建模（消费 `bone_app_permission`）。
5. **发布必须过包**：以模块/解决方案为单元，含 DDL 预览 + 影响面 + 审批；破坏性变更（删字段 / 改类型 / 缩长度）显式二次确认并走**归档**而非物理删。
6. **归属断言必须显式**：`module_id` 的租户一致性不能只依赖 SDK 隐式租户过滤，须在校验器里显式断言（防止有人 `disableTenantFilter()` 或改走 Feign 后防线失效）。

### 4.3 权限码全集（[Target]，对齐 `{domain}:{resource}:{action}`）

| 域 | 权限码 | 说明 | 归属 |
|----|--------|------|------|
| 平台域 | `metadata:template:read` / `:write` | 平台模型层模板与版本 | 平台建模架构师 |
| 平台域 | `metadata:governance:read` | 跨租户模型巡检看板 | 平台建模架构师 |
| 租户域 | `metadata:model:read` / `:write` | **建模**（实体/字段/关系/校验），受应用角色约束 | 应用建模者 |
| 租户域 | `metadata:release:create` / `:approve` | 发布包创建与审批（SoD） | 建模者 / 审批人 |
| 租户域 | `metadata:runtime:read` / `:write` | 模式 B **业务记录** CRUD（运营台） | 运行时数据运维 |
| 租户域 | `metadata:version:read` / `:rollback` | 版本历史与回滚 | 建模负责人 |

## 6. 端到端流程串联（以 bone-blueprint 订单 / 支付为贯穿样例）

> 样例取自仓库样板工程 `bone-blueprint`（`Order` / `OrderItem` / `Payment` 已有实现），用于把割裂的功能串成一条用户能走完的路。

### 流程 A：从 0 到可运行（主线）

```
平台建模架构师                 租户建模负责人 / 应用建模者                  消费方（FMS / WMS / 集成 / 运营）
──────────────                ────────────────────────                  ─────────────────────────
UC-MP1 建「订单域」「支付域」模板
UC-MP2 发版本 v1.0.0 ──模板──▶ UC-MT1 建应用 OMS + 模块 order/payment + 授角色
                              UC-MT2 从模板实例化 Order / OrderItem / Payment（或全新建模）
                              UC-MT3 建模：字段（order_no 唯一必填 / amount / status 枚举）
                                           关系（Order 1:N OrderItem、Order 1:1 Payment）
                                           绑定数据标准（订单号格式、金额精度）
                              UC-MT4 静态校验 + 交付模式选型（Order=A 生成 / 支付配置=B 运行时）
                              UC-MT5 发布包：dry-run DDL 预览 → 影响面 → 审批 → 执行 → 快照
                                      │
                        ┌─────────────┴─────────────┐
                        ▼                           ▼
                   模式 A                        模式 B
              CATALOG_SNAPSHOT → generator    /api/v1/runtime/entities/payment_config/records
              → 源码入 Git → CI/CD                     │
                        │                              │
                        └──────────────┬───────────────┘
                                       ▼
                              UC-MC4 消费登记（FMS 对账 / WMS 发货 / 集成同步 ERP）
                              UC-MC1 业务应用取数   UC-MC2 运营台录数据
                              UC-MT8 Order 的「客户」升格主数据（→ 3a UC-T1）
UC-MP4 巡检 ◀── 实体数 / 采用率 / 僵尸模型 / 发布成功率 ──┘
```

**关键串联点**：

1. **UC-MT1 是唯一入口**：先有应用与模块 + 应用角色，才有建模权限边界——**没有这一步，后面所有权限都是空谈**。
2. **UC-MT2 决定复用度**：从模板实例化 = 平台最佳实践可复用；没有模板层（As-Is）就必然每个租户重造轮子。
3. **UC-MT4 → UC-MT5 是安全闸门**：校验不过不发布；发布必须过包（dry-run + 审批 + 快照），杜绝"点一下就改生产库"。
4. **UC-MT6 是价值兑现点**：发布完不成交付（源码或 API），模型就只是几行记录。
5. **UC-MC4 消费登记是回声**：没有它，UC-MG1 影响分析与采用率都是空中楼阁。

### 流程 B：变更演进闭环（周期性）

```
业务变化（订单新增「发票类型」字段）
  → UC-MT3 建模修改 → UC-MT4 校验（是否破坏性）
  → UC-MG1 影响分析（下游 3 个消费方 / 2 条集成流 / 1 张已生成表）
  → UC-MT5 发布包（dry-run DDL + 审批）→ 执行 + 快照版本 v_n+1
  → 通知消费方 → 消费方确认 → 完成；失败 → UC-MT7 回滚（反向发布包）
```

### 流程 C：消费侧接入

```
应用开发者：在我的应用里「引用模型」→ 选实体 → 建模负责人批准 → 登记 meta_model_consumer
  → 取数（SDK / runtime API）→ 订阅模型变更事件 → 模型变更时收到影响通知（流程 B）
```

### 流程 D：平台模板到租户（复用链路）

```
平台发模板 v1.0 → 租户实例化（UC-MT2）→ 平台发 v1.1 → 租户看 diff → 自主同步/忽略
  → 同步动作同样走 UC-MT5 发布包（模板升级不是"平台直接改租户库"）
```
