# 元数据管理模块详细设计方案

> **对齐**：[`Bone-DDD`](../../architecture/Bone-DDD-最终实践方案.md) · 主 PRD §4.4  
> **三模块定义与协作（单一真源）**：[元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md)  
> **仓库对照（As-Is）**：`bone-metadata-sdk`（数据面）· `bone-metadata-server`（**:9001**，catalog + EAV + `/api/v1/runtime/**`）· `bone-metadata-engine`（**模式 B** 计算面库，由 server 装配）· **模式 A** 见 `bone-engine/studio-generator`  
> **DDL**：`meta_*` 五表见 [`bone-init.sql`](../../../bone-init.sql) §4 · [数据库开发规范.md](../../architecture/数据库开发规范.md)

本文描述 **产品能力「元数据管理」** 的目标态；与三个 `bone-metadata-*` 工程模块的 **As-Is / Vision** 边界见上链对照文档，勿将下文包结构或 API 一律视为已实现。

**设计理念（对齐 [README](../../../README.md)）**：Bone 以 **元数据先行** 构建「数字大脑」；本模块是 **应用生成** 能力的主载体，通过 **模式 A（生成式）** 与 **模式 B（运行时）** 两条路径将模型变为可运行系统，并与 **ExtPoint**（个性化逻辑）、**主数据**（核心对象质量）、**集成**（外部协同）形成四大引擎闭环。

## 0. 实现映射（产品能力包）

### 0.1 双模式交付（单一真源：对照文档 §1.3）

| 维度 | **模式 A · 生成式** | **模式 B · 运行时** |
|------|---------------------|---------------------|
| 路径 | `meta_*` → **studio-generator** → 源码进 Git | `meta_*` → **bone-metadata-engine** → 动态 API → **sdk** 读写库 |
| 标准 CRUD | 生成 Controller / 页面 | **不生成** 业务 Controller（规划） |
| 适用 | 信创审计、DDD/ArchUnit、ExtPoint、复杂域 | 运营台、配置型实体、快速迭代 |
| As-Is | ✅ 主线 | 🔶 动态 CRUD 基线已在 server；SmartQL/规则分阶段 |

```text
         catalog / EAV（server + sdk）
                │
    ┌───────────┴───────────┐
    ▼                       ▼
 模式 A                  模式 B
 generator               engine
```

### 0.2 模块分工

| 能力 | 模块 | 模式 | As-Is |
|------|------|------|-------|
| 平台持久化、扩展字段 EAV | `bone-metadata-sdk` | A+B | ✅ 全平台 |
| 元模型控制面（catalog + EAV API） | `bone-metadata-server` :9001 | A+B | ✅ |
| 规则 / 表达式 / SmartQL / 动态 CRUD | `bone-metadata-engine` + server `/api/v1/runtime` | **B** | 🔶 CRUD 基线 As-Is；规则/SmartQL 分阶段 |
| 代码生成 / 模板 | `studio-generator`（`bone-engine/studio-generator`） | **A** | 🔶 见 [§8](./8.Studio%20Generator%20详细设计方案.md) |
| 业务实体 / 字段 / 关系（catalog） | server + SDK | A+B | ✅ REST |
| 建模 UI | `bone-metadata-app` :3004 | A+B | ✅ CRUD |

**协作原则**：`sdk` 为公共数据面；`engine`（B）与 `generator`（A）**非互斥**——同一 `meta_*` 可按实体标注 `GENERATIVE` / `RUNTIME`。详见 [元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md) §1.3、§3.3。

**术语**：**扩展字段 EAV**（server `/api/v1/metadata/fields:*`）与 **建模字段 `meta_field`**（catalog）不同，见对照文档 **§1.1**。与 **bone-masterdata** 边界见对照文档 **§8**。

### 0.3 与四大引擎协同（README 架构）

```text
智能元数据（本模块）─► 定义 meta_* / EAV（「是什么」）
        ├─[A] generator ──► 可审计源码 + ExtPoint 织入点
        └─[B] engine ─────► 动态 API（规划）
        ▼
主数据平台 ───────────► 已发布 MASTER_DATA 类实体 → mdm 治理
        ▼
ExtPoint 扩展引擎 ─────► 计价/审批等行业逻辑（非标准 CRUD）
        ▼
集成引擎 ─────────────► 对外系统数据交换
```

| 协作域 | 关系 |
|--------|------|
| **ExtPoint** | 模式 A 生成 DDD 骨架时预留扩展点接口；模式 B 执行链可回调扩展点（规划） |
| **主数据** | `meta_entity.type=1` 与 `mdm_*` 衔接；catalog 不等于主数据记录存储 |
| **集成** | 元数据定义对外实体映射；集成流同步物理表或主数据 |
| **IAM** | 建模与发布权限；元数据级行列规则（规划） |

## 1. 模块概述

元数据管理是 BONE **应用生成**能力的产品模块，涵盖业务建模、扩展字段、智能规则，以及 **两种交付路径**（§0.1）；工程上由 **sdk + server +（engine | generator）+ 前端** 协作实现（非单一 `bone-metadata-server` Jar）。

**核心目标**：
- 提供可视化的业务实体建模能力（catalog + EAV）
- 支持实体字段和关系的管理
- **模式 A**：基于元数据的代码自动生成（`studio-generator`）
- **模式 B**：基于元数据的运行时动态数据访问（`bone-metadata-engine`，规划覆盖标准 CRUD）
- 支持代码模板的管理和定制（模式 A）
- 提供实体版本管理和变更追踪

## 2. 功能设计

> 下列 §2.1～§2.3 为 **产品目标态**；实现落点见 §0 与 [实现映射文档](./元数据能力-实现映射与竞品对照.md) §7。

### 2.1 业务实体管理 **[As-Is · catalog REST + UI；版本历史 P1]**

**功能描述**：支持业务实体的创建、编辑、删除和发布，管理实体的字段和关系。

**详细功能**：
- **实体创建**：创建业务实体，设置名称、描述、类型、**交付模式**（`delivery_mode`：GENERATIVE / RUNTIME）等
- **字段管理**：添加、编辑、删除实体字段，设置字段类型、长度、约束等
- **关系管理**：定义实体之间的关系，支持一对一、一对多、多对多关系
- **验证规则**：为字段添加验证规则，如必填、唯一、格式验证等
- **实体版本**：管理实体的版本历史，支持版本对比和回滚
- **实体发布**：将实体从草稿状态发布为可用状态

**用户故事**：
> 作为开发人员，我希望创建业务实体并定义字段和关系，以便快速构建业务模型。

### 2.2 代码生成（模式 A）**[主责 studio-generator]**

**功能描述**：基于业务实体自动生成前后端代码，支持多种模板和生成配置（**模式 A · 生成式交付**）。标注为 `RUNTIME` 的实体**跳过**本节标准 CRUD 生成，改走 §2.4。

**详细功能**：
- **模板选择**：选择代码生成模板，如 React+Spring Boot、Vue+Spring Boot 等
- **生成配置**：设置代码生成的配置参数，如包名、模块名等
- **代码预览**：预览生成的代码结构和内容
- **批量生成**：支持多个实体的批量代码生成
- **生成历史**：查看代码生成的历史记录
- **异步生成**：支持异步生成代码，通过 WebSocket 推送进度

**用户故事**：
> 作为开发人员，我希望基于业务实体生成前后端代码，支持多种模板，以减少重复编码工作。

### 2.3 模板管理（模式 A）**[Vision · 与 §2.2 / generator 协同]**

**功能描述**：管理代码生成模板，支持模板的创建、编辑、发布和版本管理。

**详细功能**：
- **模板创建**：创建新的代码生成模板
- **模板编辑**：编辑模板内容，支持 FreeMarker 语法
- **模板预览**：预览模板渲染效果
- **模板发布**：将模板从草稿状态发布为可用状态
- **模板版本**：管理模板的版本历史
- **模板导入导出**：支持模板的导入和导出

**用户故事**：
> 作为开发人员，我希望管理代码生成模板，支持自定义模板，以满足不同项目的需求。

### 2.4 运行时元数据面（模式 B）**[Vision · 主责 bone-metadata-engine]**

**功能描述**：对已发布 `meta_*` 解释执行，提供标准 CRUD / 查询 API，由 **engine 编排 + sdk 持久化**，无需为每个实体生成 Controller。

**详细功能**：
- **动态 REST**：列表、详情、创建、更新、删除（路径以 [Bone-API-规范](../../architecture/Bone-API-规范.md) 登记为准）
- **SmartQL / 高级查询**：过滤、排序、关联加载（规划）
- **规则与校验**：表达式、业务规则在写入/读取时生效
- **交付模式标注**：实体级 `GENERATIVE` | `RUNTIME`
- **与模式 A 共存**：同一租户内按实体选型

**用户故事**：
> 作为实施顾问，我希望发布实体后立即具备标准 API，而无需等待代码生成与部署。

**工程约束**（对齐 [元数据能力对照](./元数据能力-实现映射与竞品对照.md) §2.3）：
- engine **不得** 重复实现 JDBC；执行统一走 `bone-metadata-sdk`
- 信创源码、复杂 ExtPoint、ArchUnit 门禁场景仍用 **模式 A**

### 3.3 关键实现

#### 3.3.1 业务实体管理

```java
package com.bone.metadata.application.command.handler;

import com.bone.metadata.application.command.cmd.CreateEntityCmd;
import com.bone.metadata.domain.model.entity.Entity;
import com.bone.metadata.domain.model.entity.vo.EntityName;
import com.bone.metadata.domain.repository.EntityRepository;
import com.bone.metadata.common.exception.BusinessException;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
@RequiredArgsConstructor
public class CreateEntityHandler {
    private final EntityRepository entityRepository;
    
    @Transactional
    public Long handle(CreateEntityCmd cmd) {
        EntityName entityName = new EntityName(cmd.getName());
        
        // 检查实体名称是否已存在
        if (entityRepository.existsByName(cmd.getName())) {
            throw new BusinessException("实体名称已存在");
        }
        
        Entity entity = Entity.create(
            entityName,
            cmd.getDescription(),
            cmd.getType()
        );
        
        entityRepository.save(entity);
        
        return entity.getId().getValue();
    }
}
```

#### 3.3.2 代码生成

```java
package com.bone.metadata.application.command.handler;

import com.bone.metadata.application.command.cmd.GenerateCodeCmd;
import com.bone.metadata.domain.model.codegen.CodeGeneration;
import com.bone.metadata.domain.model.codegen.Template;
import com.bone.metadata.domain.repository.CodeGenerationRepository;
import com.bone.metadata.domain.repository.EntityRepository;
import com.bone.metadata.domain.repository.TemplateRepository;
import com.bone.metadata.common.exception.BusinessException;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
@RequiredArgsConstructor
public class GenerateCodeHandler {
    private final CodeGenerationRepository codeGenerationRepository;
    private final EntityRepository entityRepository;
    private final TemplateRepository templateRepository;
    
    @Transactional
    public Long handle(GenerateCodeCmd cmd) {
        // 验证实体存在
        var entity = entityRepository.findById(cmd.getEntityId())
                .orElseThrow(() -> new BusinessException("实体不存在"));
        
        // 验证模板存在
        Template template = templateRepository.findById(cmd.getTemplateId())
                .orElseThrow(() -> new BusinessException("模板不存在"));
        
        // 创建代码生成任务
        CodeGeneration task = CodeGeneration.create(
            entity.getId(),
            template.getId(),
            cmd.getConfig()
        );
        
        codeGenerationRepository.save(task);
        
        // 异步处理代码生成
        // TODO: 发送消息到消息队列
        
        return task.getId().getValue();
    }
}
```

#### 3.3.3 模板管理

```java
package com.bone.metadata.application.command.handler;

import com.bone.metadata.application.command.cmd.CreateTemplateCmd;
import com.bone.metadata.domain.model.codegen.Template;
import com.bone.metadata.domain.model.codegen.vo.TemplateName;
import com.bone.metadata.domain.model.codegen.vo.TemplateType;
import com.bone.metadata.domain.repository.TemplateRepository;
import com.bone.metadata.common.exception.BusinessException;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
@RequiredArgsConstructor
public class CreateTemplateHandler {
    private final TemplateRepository templateRepository;
    
    @Transactional
    public Long handle(CreateTemplateCmd cmd) {
        TemplateName templateName = new TemplateName(cmd.getName());
        TemplateType templateType = new TemplateType(cmd.getType());
        
        // 检查模板名称是否已存在
        if (templateRepository.existsByName(cmd.getName())) {
            throw new BusinessException("模板名称已存在");
        }
        
        Template template = Template.create(
            templateName,
            templateType,
            cmd.getContent()
        );
        
        templateRepository.save(template);
        
        return template.getId().getValue();
    }
}
```

## 5. API 设计

## 7. 性能与安全

- **代码安全**：生成的代码包含安全最佳实践
- **审计日志**：记录所有元数据操作，支持审计追踪
- **模板安全**：模板内容安全检查，防止恶意代码注入

## 10. 微服务与Java工程结构

### 10.1 微服务设计

> **[Vision]** 目标态「元数据管理」微服务职责；**As-Is** 见 [元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md) §2～§5。

**微服务名称（规划）**：metadata-service

**服务职责（目标态全集）**：
- 业务实体 / 字段 / 关系（catalog）→ **As-Is**：**bone-metadata-server** `:9001`，`/api/v1/metadata/entities` 等 + SDK 持久化 `meta_*`（版本历史等仍为 P1）
- 扩展字段元数据 API → **As-Is**：**bone-metadata-server**（`:9001`，`/api/v1/metadata/fields:*`）
- **模式 A** 代码模板与生成 → **`bone-engine/studio-generator`**，非 server 主责
- **模式 B** 规则 / 表达式 / SmartQL / 动态 CRUD → **bone-metadata-engine**（可选嵌入宿主或独立数据面服务）

**API 前缀**：**`/api/v1/metadata`**（扩展字段 EAV + catalog 实体/字段/关系）。

**端口（As-Is）**：扩展字段服务 **9001**（`bone-metadata-server`）。历史 8084/8082 已废止；[wiki/03](../../wiki/03-本地开发与构建.md)。

### 10.2 Java工程结构 **[Vision]**

目标态 `bone-metadata-server` 在 **catalog** 包内落地实体/字段/关系 DDD 分层（与扩展字段 Controller 共存于同一 Jar）。**As-Is** 已含扩展字段（`/api/v1/metadata/fields:*`）及 **catalog REST**（`/api/v1/metadata/entities` 等）；**模式 A** 生成在 **studio-generator**；**模式 B** 动态面由 **bone-metadata-engine** 提供（规划），勿与 server 混淆。

与 [`Bone-DDD`](../../architecture/Bone-DDD-最终实践方案.md) 对齐：**CQRS**（`*CommandHandler` / `*QueryHandler`）+ **bone-metadata-sdk** 持久化。下文目录树中 `usecase/simple|standard` 为 **历史 Vision 命名**，**≠** 产品「模式 A/B 双模式交付」（见 §0.1）；Blueprint 已收敛为 Handler 直连。

### 10.5 与其他微服务集成

**服务依赖**：
- **bone-iam**：用于权限验证和用户认证（`:8081`）
- **file-service**：用于存储生成的代码文件
- **bone-system**：控制台 `/api/v1/console/*`（非独立 admin 服务；README 无 `bone-admin` 模块）

**集成方式**：
- **Gateway**：通过 `domain/gateway/` 目录下的网关接口调用其他微服务
- **消息队列**：通过领域事件机制接收其他服务的事件
- **共享缓存**：通过Redis共享跨服务数据
- **API网关**：通过API网关统一调用其他微服务

**集成流程**：
1. **权限验证**：经网关调用 **bone-iam** 进行用户认证和权限检查
2. **文件存储**：调用file-service存储生成的代码文件
3. **数据同步**：通过消息队列向订阅方（主数据/集成等）发送元数据发布事件（**[Vision]**）
4. **服务发现**：通过Nacos服务发现机制找到其他微服务

## 11. 总结

元数据管理是 BONE **应用生成**的产品能力包：目标态含可视化建模、**双模式交付**（§0.1）、模板与生成；**As-Is** 已落地 catalog/EAV（sdk + server :9001）、**模式 A** 生成链路；**模式 B**（engine 动态 CRUD）待接平台。定义与竞品见 [元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md)。

**关键成功因素**：
- **公共数据面（sdk）+ 控制面（server）**；**模式 A（generator）** 与 **模式 B（engine）** 按场景选型
- 灵活、直观的实体建模界面
- 模式 A：可审计源码与 DDD 交付；模式 B：标准 CRUD 免生成、快速上线
- 同一 `meta_*` 可驱动两种消费路径，对标 Salesforce / Mendix 分层

**符合规范**：
- 遵循《Bone-DDD》分层与 CQRS Handler 约定
- 应用层以 CommandHandler / QueryHandler 为入口（《Bone-DDD》§14、§20）
- 采用六边形架构，依赖方向正确
- 领域层纯净，仅使用 `@Getter` 和私有构造器
- 仓储接口为空接口，继承 `bone-metadata-sdk` 的 `Repository`
- 数据库表结构符合数据库规范，包含完整的中文注释
- 命名规范符合最新标准
- 与 [README](../../../README.md) 设计原则及 [Bone-API-规范](../../architecture/Bone-API-规范.md) 一致
- 与 **ExtPoint** 扩展引擎分工：标准能力走元数据双模式，行业差异走扩展点（见 §0.3）
