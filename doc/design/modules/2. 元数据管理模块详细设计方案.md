# 元数据管理模块详细设计方案

> **对齐**：[`Bone-DDD`](../../architecture/Bone-DDD-最终实践方案.md) · 主 PRD §4.4  
> **三模块定义与协作（单一真源）**：[元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md)

> **DDL**：`meta_*` 五表见 [`bone-init.sql`](../../../bone-init.sql) §4 · [数据库开发规范.md](../../architecture/数据库开发规范.md)  
> **HTTP 真源**：OpenAPI [metadata-runtime-v1.yaml](../../architecture/openapi/metadata-runtime-v1.yaml) · Controller `bone-engine/bone-metadata-server/.../catalog/adapter/web/controller/*` + `runtime/adapter/web/RuntimeRecordController.java`。  
> **错误码前缀**：`META_` · [Bone-错误码登记.md](../../architecture/Bone-错误码登记.md)。

## 术语表（防混淆）

| 术语 | 含义 | **不同于** |
|------|------|------------|
| **模式 A · 生成式** | catalog → studio-generator → 源码进 Git | 模式 B 运行时解释执行 |
| **模式 B · 运行时** | catalog → metadata-engine → `/api/v1/runtime/**` 动态 CRUD | 模式 A 代码生成 |
| **扩展字段 EAV** | 业务表运行时分配列 / 注册扩展属性（`fields:allocate`） | catalog `meta_field`（建模字段） |
| **catalog 建模字段** | `meta_entity` / `meta_field` / `meta_relationship` 数据模型 | EAV 动作式接口 |
| **delivery_mode** | DB `TINYINT` `0`=GENERATIVE / `1`=RUNTIME；API/文档使用枚举名 | 仅控制 RUNTIME 实体走 §5.3.1 |

本文描述 **产品能力「元数据管理」** 的目标态；与三个 `bone-metadata-*` 工程模块的 **As-Is / Vision** 边界见上链对照文档，勿将下文包结构或 API 一律视为已实现。

**设计理念（对齐 [README](../../../README.md)）**：Bone 以 **元数据先行** 构建「数字大脑」；本模块是 **应用生成** 能力的主载体，通过 **模式 A（生成式）** 与 **模式 B（运行时）** 两条路径将模型变为可运行系统，并与 **ExtPoint**（个性化逻辑）、**主数据**（核心对象质量）、**集成**（外部协同）形成四大引擎闭环。

## 0. 实现映射（产品能力包）

### 0.1 双模式交付（单一真源：对照文档 §1.3）

| 维度 | **模式 A · 生成式** | **模式 B · 运行时** |
|------|---------------------|---------------------|
| 路径 | `meta_*` → **studio-generator** → 源码进 Git | `meta_*` → **bone-metadata-engine** → 动态 API → **sdk** 读写库 |
| 标准 CRUD | 生成 Controller / 页面 | **不生成** 业务 Controller（运行时解释执行） |
| 适用 | 信创审计、DDD/ArchUnit、ExtPoint、复杂域 | 运营台、配置型实体、快速迭代 |
| As-Is | ✅ 主线（generator + catalog snapshot 已联动） | ✅ **CRUD v1**（`/api/v1/runtime/**` @ :9001）<br>⏳ 列裁剪 / 排序 / 过滤 / `If-Match` <br>💡 SmartQL / 规则 / 表达式 / 投影查询 |

> **图例**：✅ As-Is（已落地、CI 守护） · ⏳ Target（短期内排期，契约已声明） · 💡 Vision（路线图）。下文一律沿用此口径，避免「整节标 Vision 但 API 已上线」的误读。

```text
         catalog / EAV（server + sdk）
                │
    ┌───────────┴───────────┐
    ▼                       ▼
 模式 A                  模式 B
 generator               engine
```

### 0.2 模块分工

| 能力 | 模块 | 模式 | As-Is |
|------|------|------|-------|
| 平台持久化、扩展字段 EAV | `bone-metadata-sdk` | A+B | ✅ 全平台 |
| 元模型控制面（catalog + EAV API） | `bone-metadata-server` :9001 | A+B | ✅ |
| 动态 CRUD（按 `delivery_mode=RUNTIME`） | `bone-metadata-engine` + server `/api/v1/runtime` | **B** | ✅ v1（`JdbcRuntimeRecordService`，列见 §5.3.1） |
| 规则 / 表达式 / SmartQL / 投影查询 | `bone-metadata-engine` | **B** | 💡 引擎库已具备表达式与规则注册（见 [§9](./9.%20SmartMeta%20引擎模块技术说明.md)）；HTTP 暴露分阶段 |
| 代码生成 / 模板 | `studio-generator`（`bone-engine/studio-generator`） | **A** | ✅ 主线（`/api/v1/generator/**` @ :8086，消费 `CATALOG_SNAPSHOT`）；模板 REST CRUD 详见 [§8](./8.Studio%20Generator%20详细设计方案.md) |
| 业务实体 / 字段 / 关系（catalog） | server + SDK | A+B | ✅ REST |
| 建模 UI | `bone-metadata-app` :3004 | A+B | ✅ CRUD |

**协作原则**：`sdk` 为公共数据面；`engine`（B）与 `generator`（A）**非互斥**——同一 `meta_*` 可按实体标注 `GENERATIVE` / `RUNTIME`。详见 [元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md) §1.3、§3.3。

**术语**：**扩展字段 EAV**（server `/api/v1/metadata/fields:*`）与 **建模字段 `meta_field`**（catalog）不同，见对照文档 **§1.1**。与 **bone-masterdata** 边界见对照文档 **§8**。

### 0.3 与四大引擎协同（README 架构）

```text
智能元数据（本模块）─► 定义 meta_* / EAV（「是什么」）
        ├─[A] generator ──► 可审计源码 + ExtPoint 织入点 ✅
        └─[B] engine ─────► /api/v1/runtime CRUD v1 ✅；SmartQL/规则 💡
        ▼
主数据平台 ───────────► 已发布 MASTER_DATA 类实体 → mdm 治理
        ▼
ExtPoint 扩展引擎 ─────► 计价/审批等行业逻辑（非标准 CRUD）
        ▼
集成引擎 ─────────────► 对外系统数据交换
```

| 协作域 | 关系 |
|--------|------|
| **ExtPoint** | 模式 A 生成 DDD 骨架时预留扩展点接口；模式 B 执行链可回调扩展点（规划） |
| **主数据** | `meta_entity.type=1` 与 `mdm_*` 衔接；catalog 不等于主数据记录存储 |
| **集成** | 元数据定义对外实体映射；集成流同步物理表或主数据 |
| **IAM** | 建模与发布权限；元数据级行列规则（规划） |

## 1. 模块概述

元数据管理是 BONE **应用生成**能力的产品模块，涵盖业务建模、扩展字段、智能规则，以及 **两种交付路径**（§0.1）；工程上由 **sdk + server +（engine | generator）+ 前端** 协作实现（非单一 `bone-metadata-server` Jar）。

**核心目标**：
- 提供可视化的业务实体建模能力（catalog + EAV，✅）
- 支持实体字段和关系的管理（✅）
- **模式 A**：基于元数据的代码自动生成（`studio-generator`，✅）
- **模式 B**：基于元数据的运行时动态数据访问（`bone-metadata-engine` + `/api/v1/runtime/**`，✅ CRUD v1；💡 SmartQL/规则）
- 代码模板的管理和定制（模式 A，模板 REST 💡 Vision）
- 实体版本管理和变更追踪（💡 **Vision P1**，见 §5.1 `/versions`）

## 2. 功能设计

> 下列 §2.1～§2.3 为 **产品目标态**；实现落点见 §0 与 [实现映射文档](./元数据能力-实现映射与竞品对照.md) §7。

### 2.1 业务实体管理 **[As-Is · catalog REST + UI；版本历史 P1]**

**功能描述**：支持业务实体的创建、编辑、删除和发布，管理实体的字段和关系。

**详细功能**：
- **实体创建**（✅）：创建业务实体，设置名称、描述、类型、**交付模式**（`delivery_mode`：GENERATIVE / RUNTIME）等
- **字段管理**（✅）：添加、编辑、删除实体字段，设置字段类型、长度、约束等
- **关系管理**（✅）：定义实体之间的关系，支持一对一、一对多、多对多关系
- **验证规则**（🔶 `meta_field.validation_rules` JSON 列已落 DDL，运行时校验 💡 Vision）：为字段添加必填、唯一、格式验证等
- **实体版本**（💡 **Vision P1**）：管理实体的版本历史，支持版本对比和回滚（接口 `/versions` 见 §5.1）
- **实体发布**（✅）：将实体从草稿状态发布为可用状态

**用户故事**：
> 作为开发人员，我希望创建业务实体并定义字段和关系，以便快速构建业务模型。

### 2.2 代码生成（模式 A）**[主责 studio-generator]**

**功能描述**：基于业务实体自动生成前后端代码，支持多种模板和生成配置（**模式 A · 生成式交付**）。标注为 `RUNTIME` 的实体**跳过**本节标准 CRUD 生成，改走 §2.4。

**详细功能**（落地能力**以 [§8 Studio Generator 详设](./8.Studio%20Generator%20详细设计方案.md) 为真源**；下表标 As-Is 仅指本模块视角）：
- **模板选择**（✅）：基于 generator 已注册模板渲染 catalog 快照
- **生成配置**（✅）：包名、模块名等，由 generator `GenerateCodeCommand` 接收
- **代码预览**（🔶）：generator 支持，UI 集成待补
- **批量生成**（🔶）：多实体批量见 generator 详设
- **生成历史**（✅）：generator 内 `GenerationTask` 持久化
- **异步生成 + WebSocket 进度**（💡 Vision）：当前走 LRO `operations/{id}` 轮询；WebSocket 推送未排期

**用户故事**：
> 作为开发人员，我希望基于业务实体生成前后端代码，支持多种模板，以减少重复编码工作。

### 2.3 模板管理（模式 A）**[Vision · 与 §2.2 / generator 协同]**

**功能描述**：管理代码生成模板，支持模板的创建、编辑、发布和版本管理。

**详细功能**：
- **模板创建**：创建新的代码生成模板
- **模板编辑**：编辑模板内容，支持 FreeMarker 语法
- **模板预览**：预览模板渲染效果
- **模板发布**：将模板从草稿状态发布为可用状态
- **模板版本**：管理模板的版本历史
- **模板导入导出**：支持模板的导入和导出

**用户故事**：
> 作为开发人员，我希望管理代码生成模板，支持自定义模板，以满足不同项目的需求。

### 2.4 运行时元数据面（模式 B）**[主责 bone-metadata-engine + bone-metadata-server :9001]**

**功能描述**：对已发布 `meta_*` 解释执行，提供标准 CRUD / 查询 API，由 **engine 编排**（**Target** 持久化走 sdk；**As-Is** 见 [ADR-0015](../../architecture/adr/0015-metadata-runtime-jdbc-via-engine.md)），无需为每个实体生成 Controller。对标 Salesforce 声明式标准对象、Directus / Hasura 的 Metadata-Driven Runtime。

**子能力分阶段（对齐 §0.1 图例）**：

| 子能力 | 状态 | 真源 / 落地 |
|--------|------|-------------|
| 动态 CRUD（列表/详情/创建/更新/删除） | ✅ As-Is v1 | `RuntimeRecordController` + `JdbcRuntimeRecordService`（详见 §5.3.1） |
| 多租户隔离（行级 `tenant_id`） | ✅ As-Is | `CatalogTenantSupport` + 写入自动绑定 |
| 系统列守护（`id/tenant_id/version/deleted/*_at`） | ✅ As-Is | `JdbcRuntimeRecordService.SYSTEM_COLUMNS` 白名单 |
| `If-Match` 乐观锁 / `PATCH` 局部更新 | ⏳ Target | 见 §5.A |
| 列裁剪 / 过滤 / 排序 query 参数 | ⏳ Target | 当前固定 `SELECT *`，按 `id DESC` |
| SmartQL / 投影查询 / 关联加载 | 💡 Vision | engine 已具备表达式与规则注册（[§9](./9.%20SmartMeta%20引擎模块技术说明.md)），HTTP 暴露未排期 |
| 规则与校验（写入/读取时表达式生效） | 💡 Vision | `bone-metadata-engine-core` `BusinessRuleRegistry` 已可用，未接入 runtime controller |
| 与模式 A 共存（按实体 `delivery_mode` 选型） | ✅ As-Is | `MetaDeliveryMode` 枚举 + DDL |

**用户故事**：
> 作为实施顾问，我希望发布实体后立即具备标准 API，而无需等待代码生成与部署。

**工程约束**（对齐 [元数据能力对照](./元数据能力-实现映射与竞品对照.md) §2.3）：
- engine 应统一走 `bone-metadata-sdk` 持久化；信创源码、复杂 ExtPoint、ArchUnit 门禁场景仍用 **模式 A**。
- **As-Is 例外**：[ADR-0015](../../architecture/adr/0015-metadata-runtime-jdbc-via-engine.md)（原 ADR-MS-001）：当前 `JdbcRuntimeRecordService` 直接使用 `NamedParameterJdbcTemplate` 拼装动态 SQL，未走 `sdk` 的 `Repository` / `FluentQuery`。  
  *原因*：sdk DSL 暂未覆盖「动态表名 / 动态列 / 元模型驱动」场景，MVP 阶段优先打通端到端。  
  *收敛路线*：sdk 抽象 `MetaTableExecutor` SPI 后，engine 切到 sdk 通道（见 backlog `engine-sdk-meta-table-executor`）。
- **与 EAV 的边界（易混淆，必读）**：模式 B 运行时列白名单来自 **catalog `meta_field`**（`CatalogRuntimeEntityProvider` 读取），**不是** EAV `fields:allocate`。EAV 用于给**已有业务表**动态加扩展列；RUNTIME 实体通常走「catalog 建模字段 + 手工/迁移 DDL 建物理表」路径。两者可并存（同一业务表既有 catalog 字段又有 EAV 扩展列），但 **RUNTIME CRUD 不依赖 allocate**。见 §5.3.2。

#### 3.3.1 业务实体管理（catalog · As-Is 摘录）

> 真源：`bone-engine/bone-metadata-server/src/main/java/com/bone/metadata/catalog/application/command/handler/CreateMetaEntityHandler.java`

```java
package com.bone.metadata.catalog.application.command.handler;

import com.bone.core.exception.BizException;
import com.bone.core.util.DistributedIdGenerator;
import com.bone.metadata.catalog.application.command.cmd.CreateMetaEntityCommand;
import com.bone.metadata.catalog.common.CatalogTenantSupport;
import com.bone.metadata.catalog.domain.enums.MetaDeliveryMode;
import com.bone.metadata.catalog.domain.model.MetaEntity;
import com.bone.metadata.catalog.domain.repository.MetaEntityRepository;
import com.bone.metadata.sdk.query.criteria.Criteria;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
@RequiredArgsConstructor
public class CreateMetaEntityHandler {

  private final MetaEntityRepository metaEntityRepository;

  @Transactional
  public Long handle(CreateMetaEntityCommand cmd) {
    long tenantId = CatalogTenantSupport.currentTenantId();
    long existing =
        metaEntityRepository.countByCriteria(
            Criteria.<MetaEntity>create().eq("tenantId", tenantId).eq("code", cmd.getCode()));
    if (existing > 0) {
      throw BizException.of("实体编码已存在: " + cmd.getCode());
    }
    Long id = DistributedIdGenerator.generateLongId();
    int deliveryMode =
        cmd.getDeliveryMode() != null
            ? MetaDeliveryMode.fromCode(cmd.getDeliveryMode()).getCode()
            : MetaDeliveryMode.GENERATIVE.getCode();
    MetaEntity entity =
        MetaEntity.create(
            id, tenantId,
            cmd.getName(), cmd.getCode(), cmd.getDisplayName(), cmd.getDescription(),
            cmd.getTableName(), type, deliveryMode, cmd.getIcon());
    metaEntityRepository.insert(entity);
    return id;
  }
}
```

**真源命名细节**（避免被 §10.3 误读）：

- `MetaEntity` 继承 **`com.bone.core.domain.entity.AbstractEntity<Long>`**（非 `AggregateRoot`），用自有 `tenantId` 字段做租户隔离 — 见 [ADR-0016](../../architecture/adr/0016-metadata-catalog-abstract-entity-tenant.md)（原 ADR-MS-002）。
- 字段上的 `@Table("meta_entity")` / `@Column(name=...)` 是 **bone-metadata-sdk 自定义注解**（`com.bone.metadata.sdk.domain.annotation.*`），**非 JPA / 非 MyBatis-Plus**，由 SDK 自有 Repository 在运行期反射读取，因此 `domain.model` 严格意义上仍然 **不依赖任何外部 ORM 框架**，符合 DDD「领域层纯净」要求。

**与 §5.A Target 的差距**：当前签名返回 `Long id`，Controller 用 `ApiResponse.success(id)` 直接 200 OK；Target 态需迁移为 `ResponseEntity.created(URI("/api/v1/metadata/entities/" + id)).body(ApiResponse.success(id))`（AIP-133）；同时 `update` Handler 当前只抛 `BizException`，💡 后续应区分 `NotFoundException`（404）与 `BizException`（400），见 [Bone-API §11](../../architecture/Bone-API-规范.md)。

## 5. API 设计

> **真源**：[元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md) §5、§1.2 · [Bone-API-规范](../../architecture/Bone-API-规范.md) §2.3、§13.2。

### 5.A 横切约定（对齐扩展 §7.1）

> **业界基线**：本节字段语义对齐 [Google AIP-128/129/133/154/155](https://google.aip.dev/) 与 [Stripe API conventions](https://stripe.com/docs/api/idempotent_requests) — 创建用 `201 + Location`、更新用 `If-Match/ETag`、写操作支持 `Idempotency-Key`。**As-Is** 列只勾打通项，**Target** 列声明契约 + 排期路径；**禁止**把规划项标 As-Is。
>
> **范围口径**：以下三列分别是 **catalog**（`/api/v1/metadata/entities|fields|relationships`）、**EAV**（`/api/v1/metadata/fields:*`）、**runtime**（`/api/v1/runtime/**`）。同行三列状态可能不同。

| topic | catalog As-Is | EAV As-Is | runtime As-Is | Target（全模块对齐 AIP / Stripe） |
|--------|---------------|-----------|----------------|-------------------------------------|
| 成功信封 | ✅ `ApiResponse<T>` + `PageResult.records` | ✅ 同左 | ✅ 同左 | — |
| 失败 | ✅ `GlobalExceptionHandler` → `ApiResponse<ProblemDetail>` + `META_*` 错误码 | 同左 | 同左 | ⏳ 全量错误码台账与 OpenAPI schema 对齐 |
| 创建状态码 | ✅ `201 Created` + `Location`（entities/fields/relationships，对齐 AIP-133） | ✅ `fields:allocate` 返回 `201` | ✅ `201 Created` + `Location`（`runtime/entities/{code}/records/{id}`） | — |
| 更新乐观锁 | ✅ `meta_entity` / `meta_field` / `meta_entity_relation`：`PUT` + `publish` 支持 `If-Match: "v{n}"` → **412**；`ETag` 回显 | n/a | ✅ 物理表含 `version` 列时 runtime `PUT` 支持 `If-Match` | — |
| `PATCH` 局部更新 | 💡 | 💡 | 💡 | RFC 7396 JSON Merge Patch |
| 写幂等 | ✅ `POST .../publish` + `Idempotency-Key`（进程内 24h） | ✅ `fields:allocate` + `Idempotency-Key` | ✅ `POST .../records` + `Idempotency-Key` | 💡 Redis 集群级幂等存储 |
| 字段冲突 | ✅ 同实体内字段 `name/code` 唯一（`META_FIELD_DUPLICATE`） | ✅ 名称去重 | n/a | ⏳ 大小写不敏感校验 |
| 多租户 | ✅ `tenant_id` + `TenantContext`（`CatalogTenantSupport`） | ✅ 同左 | ✅ runtime 行写入自动绑定 | 💡 行级 + 列级（与扩展 IAM 协同） |
| 已发布实体可改性 | ✅ 仅允许「加字段 / 改非破坏属性」；删字段需先归档（`MetaEntity#updateBasic` 域校验） | n/a | n/a | 💡 影响分析 API |
| 列表分页 | ✅ `PageResult(records,total,page,size)` | ✅ 同左 | ✅ 同左 + `fields` / `sort` / `q`（列白名单内） | 💡 复杂过滤表达式 / SmartQL |
| 写审计 | ✅ `created_by/at` `updated_by/at`（系统列）；操作日志 💡 | 同左 | 同左 | 💡 写操作流水进审计模块 |

> **平台契约索引**：[Bone-API-规范 §8.1](../../architecture/Bone-API-规范.md#81-模块横切约定索引详设-50) · [可观测性 §4.2.1](../../architecture/Bone-可观测性规范.md#421-模块-sli-与指标映射与详设对齐)。
>
> **图例复用 §0.1**：✅ As-Is（CI 守护） · ⏳ Target（契约已声明 / 待统一拉齐） · 💡 Vision。`n/a` 表示该列无意义。
>

### 5.3.2 模式 B 运行时落地 Checklist（**务实可执行**）

> **目的**：避免「发布了 RUNTIME 实体却调不通 API」的常见陷阱（多半是物理表缺失或列名不合法）。本节列出 **8 步前置条件**，每步给出真源校验点；对应错误码全部源自 `JdbcRuntimeRecordService`。
>
> **与 EAV 分工**：本 checklist 使用 **catalog `meta_field`** + 物理 DDL；**不要求**先调用 `POST /api/v1/metadata/fields:allocate`（那是给已有业务表加扩展列的另一条能力，见术语表 §0 与对照文档 §1.1）。若业务需要「标准列 + 扩展列」并存，在步骤 3 建表时预留 EAV 分配的列名即可。

| 步骤 | 动作 | 必满足约束 | 校验点 / 失败错误码 |
|------|------|--------------|---------------------|
| 1 | 在 catalog 创建实体 `POST /api/v1/metadata/entities` | `table_name` 满足 `^[a-zA-Z][a-zA-Z0-9_]*$`；`delivery_mode=RUNTIME` | `META_RUNTIME_INVALID_IDENTIFIER`（非法标识符）|
| 2 | 在 catalog 为实体添加字段 `POST /api/v1/metadata/entities/{id}/fields` | 字段 `code` 与未来物理表列名 1:1；同样满足合法标识符 | 同上 |
| 3 | **创建物理表**（DDL，与 `table_name` 同名） | 强烈推荐含系统列：`id BIGINT PK`、`tenant_id BIGINT`、`deleted TINYINT DEFAULT 0`、`version BIGINT DEFAULT 0`、`created_at/updated_at DATETIME`、`created_by/updated_by VARCHAR` | 缺 `tenant_id` 则**跨租户串数据**；缺 `deleted` 则 DELETE 转硬删（见 `JdbcRuntimeRecordService.delete`）|
| 4 | 字段 → 列对齐 | 每个 `meta_field.code` 在物理表中存在同名列且类型兼容 | 写入时 sdk 报 SQL 语法或类型错误；建议在 catalog `publish` 前用 `INFORMATION_SCHEMA.COLUMNS` 校验（💡 自动化在 §5.A Target）|
| 5 | 发布实体 `POST /api/v1/metadata/entities/{id}/publish` | `status=DRAFT → PUBLISHED`；二次发布抛 `DomainException` | catalog 域校验，弱幂等 |
| 6 | 网关路由 | gateway 已默认把 `/api/v1/metadata/**`、`/api/v1/runtime/**` 同转 `:9001` | 见 [wiki/03](../../wiki/03-本地开发与构建.md) |
| 7 | 权限 scope | ✅ EAV / catalog / runtime 均已挂 `@PreAuthorize`（`metadata:read|write`） | publish 临时复用 `metadata:write`，⏳ 后续拆 `metadata:publish`（§5.0） |
| 8 | 烟囱验证 | `POST /api/v1/runtime/entities/{code}/records` 创建一条 → `GET .../records` 看到 → `PUT .../records/{id}` 改一字段 → `DELETE` 软删 | 失败错误码：`META_RUNTIME_ENTITY_NOT_FOUND`（实体未发布或非 RUNTIME）/ `META_RUNTIME_RECORD_NOT_FOUND`（id 不存在或被软删）|

**默认行为**（务实约束，避免误解）：

- **分页**：`size` 上限 **200**，超出按 200 截断（防止全表扫导致 OOM）。
- **过滤/排序**：✅ 支持 `fields=`（列裁剪）、`sort=`（`field` / `-field`）、`q=`（`field:value` 等值过滤）；默认 `id DESC`（见 §5.A）。
- **写入字段白名单**：服务端**自动剔除**不在 `meta_field` 内的键 + 系统列（`id/tenant_id/version/deleted/created_*/updated_*`），无须客户端自洁，但**不会**抛错——以避免污染。
- **乐观锁**：catalog `meta_entity` 与 runtime 物理表（含 `version` 列时）均支持 `If-Match` + `ETag`（§5.A ✅）。
- **软删**：物理表含 `deleted` 列时 DELETE 转 `UPDATE deleted=1`；不含则**硬删**——按需评估。
- **多租户**：物理表含 `tenant_id` 列时自动追加 `WHERE tenant_id=:tenantId` 与 `INSERT` 自动绑定；**不含则不隔离**，仅当面向系统级配置实体时才可省略。

> **何时不要用模式 B**：①复杂工作流 / 计价 / 审批 → 用 ExtPoint（[扩展详设 §1.5](./5.%20扩展管理模块详细设计方案.md#15-与智能元数据双模式协同)）。②跨实体事务、聚合查询、严格审计 → 用模式 A 生成代码（保留 ArchUnit / 调试栈）。③信创私有部署源码合规 → 模式 A。

## 10. 微服务与Java工程结构

### 10.1 微服务设计

> **As-Is**：能力族由 **`bone-metadata-sdk`** + **`bone-metadata-server`** :9001 + **`bone-metadata-engine`** + **`studio-generator`** 协作；并非单一 `metadata-service` 制品。详见 [元数据能力-实现映射与竞品对照.md](./元数据能力-实现映射与竞品对照.md) §2～§5。

**微服务名称（**[Vision]** · 名义聚合，非物理拆分）**：metadata-service

**职责（目标态全集 · As-Is 各自工程独立部署）**：
- 业务实体 / 字段 / 关系（catalog）→ **As-Is**：**bone-metadata-server** :9001，`/api/v1/metadata/entities` 等 + SDK 持久化 `meta_*`
- 扩展字段元数据 API → **As-Is**：**bone-metadata-server** :9001，`/api/v1/metadata/fields:*`
- **模式 A** 代码模板与生成 → **`bone-engine/studio-generator`**（独立服务，非 server 主责）
- **模式 B** 规则 / 表达式 / SmartQL / 动态 CRUD → **bone-metadata-engine**（库 + starter，由 server 装配 `RuntimeRecordController`）

**API 前缀**：**`/api/v1/metadata`**（EAV + catalog）、**`/api/v1/runtime`**（模式 B）、**`/api/v1/generator`**（代码生成）。

**数据库**：与平台共用 MySQL 库 **`bone`**（**非**独立 `metadata_db`）。

**端口（As-Is）**：扩展字段/catalog/运行时 → **9001**（`bone-metadata-server`）；代码生成 → **8085**（`studio-generator`）。历史 8084/8082 已废止；端口真源见 [wiki/03](../../wiki/03-本地开发与构建.md)。

### 10.2 Java 工程结构（**As-Is 摘要 + Target 标注**）

> **澄清三件事**（修正旧版示意中的常见误读）：
> 1. **`bone-metadata-server` ≠ 单体 metadata 服务**：仅承担 **catalog REST + EAV REST + runtime REST**（@ :9001）。代码生成 / 模板归 `studio-generator`，运行时引擎能力归 `bone-metadata-engine`。**目录树中不应再出现 `CodeGenerationController` / `TemplateController` / `CodeGenerationCleanupJob`** — 老版工程示例已删除。
> 2. **catalog 包名命名 As-Is**：实际是 `com.bone.metadata.catalog.**`（聚合根叫 `MetaEntity` / `MetaField` / `MetaEntityRelation`，前缀 `Meta` 避免与 `bone-core` 系统名冲突）。下面目录树以 As-Is 命名为准。
> 3. **EAV 包名 As-Is**：扩展字段 API 在 `com.bone.metadata.adapter.web.controller.MetadataController`（顶层未带 `eav` 子包），保留以维持向后兼容；新增 catalog/runtime 能力一律放进各自子包。

### 10.5 与其他微服务集成

> **现状声明**：`bone-metadata-server` 自身是**轻量控制面**，**不主动调用其他微服务**（grep 0 个 `@FeignClient` 在 server 模块下）。下表区分「**真实** As-Is」与「**目标态** Vision」，避免给读者「server 已接入 Nacos / file-service / Redis 共享缓存」的错觉。

**服务交互（As-Is + Vision）**：

| 对方服务 | 调用方向 | 状态 | 说明 |
|----------|----------|------|------|
| **bone-iam** :8081 | server ← gateway | ✅（间接） | 登录态由网关（SA-Token 全局过滤器）携带 token 透传，server 不直接 Feign 调 IAM |
| **bone-metadata-app** :3004 | UI → server | ✅ | Qiankun 微应用经网关访问 catalog / runtime API |
| **studio-generator** :8085 | generator → 共享 MySQL（**非** REST） | ✅ | generator 通过自有 `CatalogMetadataGatewayImpl` + SDK Repository **直读** `meta_entity` / `meta_field`（`status=PUBLISHED` 且 `delivery_mode=GENERATIVE`），**不走** server REST 也不走 Feign，体现 §0.2「sdk = 公共数据面」原则。Snapshot 列表查询走 generator 自己的 `GET /api/v1/generator/metadata-entity-snapshots` |
| **业务模块（如 blueprint / iam / mdm）** | 业务 → SDK → DB | ✅ | 通过 `bone-metadata-sdk` 直接读写 `meta_*` 与扩展字段；不强制经 server REST |
| Nacos 服务发现 | 双向注册 | 💡 Vision | server 当前无 Nacos 集成；多实例部署时再启用 |
| file-service | server → file-service | 💡 Vision | server 当前不生成 / 不存储文件；代码生成产物由 generator 自行落地（Git）|
| RocketMQ | server → 订阅方（mdm / integration） | 💡 Vision | 元数据发布事件异步分发（见 §7）|
| Redis（共享） | server → Redis | ⏳ Target | catalog 缓存 / 幂等窗口（见 §5.A、§7） |

**典型集成流程（As-Is，模式 A 发布 → 代码生成闭环）**：

```text
[用户] → bone-metadata-app (UI)
    └─→ Gateway (SA-Token 验登录)
         └─→ bone-metadata-server :9001
              └─ POST /api/v1/metadata/entities/{id}/publish
                   ├─ MySQL: meta_entity.status = PUBLISHED
                   └─ (✅ As-Is) 本地 ApplicationEventPublisher
                       └─ (💡 Vision) RocketMQ → mdm / integration 订阅方

──── 数据面直读（不经 server REST）────
[CI / 用户] → studio-generator :8085
    └─ GET /api/v1/generator/metadata-entity-snapshots
         └─ CatalogMetadataGatewayImpl
              └─ SDK Repository 直读同库 meta_entity / meta_field
                  （filter: status=PUBLISHED & delivery_mode=GENERATIVE）
              └─ 渲染源码 → Git

──── 业务方扩展字段（走 SDK 内置 Feign）────
[业务模块 :8xxx] → 业务进程内
    └─ MetadataServiceClient (Feign in SDK)
         └─ POST /api/v1/metadata/fields:search|allocate → server :9001
              └─ MySQL: meta_extension_field 等
```

> **设计要点**：
> 1. **跨服务读 catalog**：直读同库（generator 当前做法）— 简单可靠，但要求生产环境 server 与下游服务**共享同一个 `bone` 库**或采用复制方案；如演化为独立库需切换走 server REST。
> 2. **跨服务 EAV 扩展字段**：必走 SDK Feign（已封装）— EAV 涉及 `fields:allocate` 物理列分配的并发控制，必须经 server 统一仲裁，不可绕过。
> 3. **不要做的事**：当前**禁止**在 server 内 Feign 调 IAM / file-service / mdm 等业务方；保持 server 控制面纯净，跨服务依赖通过 SDK（数据面）或事件（消息面）解耦。

## 11. 总结

元数据管理是 BONE **应用生成**的产品能力包，按 **数据面（sdk）+ 控制面（server :9001）+ 双模式交付（generator / engine）+ 控制台（app :3004）** 协作落地，对标 Salesforce 元数据 API / Mendix Domain Model / Directus / Hasura 的分层思路。

**当前真实落地（As-Is，§0.1 图例 ✅）**：
- catalog REST（业务实体 / 字段 / 关系）@ `:9001`，**`201 Created` + `Location`**（对齐 AIP-133），**`@PreAuthorize(metadata:read|write)`**
- 扩展字段 EAV REST（`fields:search|searchByNames|allocate`）@ `:9001`，`fields:allocate` 同 ✅
- runtime CRUD（`/api/v1/runtime/entities/{code}/records`）同 ✅：`201 + Location`、`fields/sort/q` 列表、`If-Match`（有 `version` 列）、`Idempotency-Key` 创建
- 已发布 RUNTIME 实体解析缓存：**Caffeine**（默认）或 **Redis**（`bone.metadata.catalog.runtime-entity-cache.backend=redis`）；发布时自动失效
- 幂等存储：**in-memory**（默认）或 **Redis**（`bone.metadata.catalog.idempotency.backend=redis`）
- catalog `meta_field` / `meta_entity_relation` 已含 `version` 列 + `If-Match`（增量 DDL 见 `doc/deployment/sql/V20260528_meta_catalog_version_columns.sql`）
- IAM：`metadata:publish` 权限码 + publish 端点 `hasAnyAuthority(publish, write)`
- **模式 A** 代码生成链路：catalog `publish` → `CATALOG_SNAPSHOT` → studio-generator 渲染 → Git
- **模式 B v1** 动态 CRUD：`JdbcRuntimeRecordService`（含系统列守护、多租户隔离、软删）
- 建模控制台 UI @ `:3004`

**短期排期（⏳ Target，对齐 §5.A）**：
- 错误码 OpenAPI schema 与 `META_*` 台账全量对齐
- 生产环境开启 Redis：`bone.metadata.catalog.runtime-entity-cache.backend=redis` 与 `idempotency.backend=redis`（代码已就绪，默认 `memory`）

**路线图（💡 Vision）**：
- SmartQL / 投影查询 / 表达式与业务规则在 runtime 写入流生效（engine-core 已具备库能力，HTTP 暴露未排期）
- 模板管理 REST、`@Capability` AI 自动建模、影响分析 API

**关键成功因素**：
- **公共数据面（sdk）+ 控制面（server）**：同一 `meta_*` 可驱动两种消费路径；**模式 A（generator）** 与 **模式 B（engine）** 按场景选型，非互斥
- 模式 A：可审计源码与 DDD 交付；模式 B：标准 CRUD 免生成、快速上线
- engine ↔ sdk 边界见 [ADR-0015](../../architecture/adr/0015-metadata-runtime-jdbc-via-engine.md)；catalog 聚合根见 [ADR-0016](../../architecture/adr/0016-metadata-catalog-abstract-entity-tenant.md)

**符合规范**：
- 遵循《Bone-DDD》分层与 CQRS Handler 约定（命令 `@Transactional`、查询 `@Transactional(readOnly=true)`，ArchUnit 守护）
- 应用层以 CommandHandler / QueryHandler 为入口（《Bone-DDD》§14、§20）
- 采用六边形架构，依赖方向正确；领域层纯净
- 仓储接口为空接口，继承 `bone-metadata-sdk` 的 `Repository`
- 数据库表结构符合数据库规范，包含完整的中文注释（[`bone-init.sql`](../../../bone-init.sql)）
- 与 [README](../../../README.md) 设计原则及 [Bone-API-规范](../../architecture/Bone-API-规范.md) 一致
- 与 **ExtPoint** 扩展引擎分工：标准能力走元数据双模式，行业差异走扩展点（见 §0.3）

## 12. 前端架构设计

### 12.1 页面路由与布局

| 路由 | 页面 | 说明 |
|------|------|------|
| `/entities` | 实体管理（EntityManagement） | 元数据实体 CRUD + 发布 |
| `/entities/:entityId/fields` | 字段管理（FieldManagement） | 按实体查看和管理建模字段 |
| `/relations` | 关系管理（RelationManagement） | 实体间关系管理 |
| `/runtime` | 运行时数据（RuntimeDataManagement） | 模式 B 实体动态数据管理 |

### 12.2 状态管理

- 无全局 Store（各页面独立管理状态）
- 数据流：页面 → apiClient（Axios）→ 后端 → 页面 setState 刷新
- 错误处理：统一 Axios 拦截器处理 401/403/500

### 12.3 关键交互流程

**实体管理**：
1. 加载实体列表（分页 + 关键词搜索）
2. 新建/编辑实体（Modal 表单）
3. 发布实体（仅草稿状态可发布，发布后不可编辑）
4. 运行时实体链接跳转到运行时数据页

**字段管理**：
1. 选择目标实体 → 加载字段列表
2. 新建/编辑字段（指定类型、长度、是否必填）
3. 删除字段（已发布实体的字段不可删除）

**运行时数据管理**：
1. 选择已发布的 RUNTIME 实体
2. 根据 meta_field 动态渲染表格列
3. 记录 CRUD（动态表单根据字段类型渲染控件）

### 12.4 错误边界

- 所有 API 调用用 try/catch 包裹
- 网络错误显示"无法连接元数据服务"提示
- 后端返回的 ApiResponse.message 优先显示
- 编辑字段（Editing）状态通过 Modal 的 open/onCancel 控制

## 13. 错误码与异常处理

| 场景 | HTTP 状态码 | 错误码前缀 | 说明 |
|------|-------------|-----------|------|
| 实体不存在 | 404 | META_ENTITY_NOT_FOUND | EntityNotFoundException |
| 字段不存在 | 404 | META_FIELD_NOT_FOUND | FieldNotFoundException |
| 实体已发布不可编辑 | 400 | META_ENTITY_PUBLISHED | 已发布状态仅允许 `is_admin` 操作 |
| 字段名重复 | 400 | META_FIELD_DUPLICATE | 同一实体下 code 唯一 |
| 实体名重复 | 400 | META_ENTITY_DUPLICATE | code 全局唯一 |
| 非法操作 | 400 | META_INVALID_OPERATION | 例如删除已发布实体的字段 |

## 15. 版本管理设计（Vision P1）

### 15.1 版本化机制

每次 `PUT /entities/{id}` 更新前，当前版本存入 `meta_entity_version` 表：

```sql
CREATE TABLE IF NOT EXISTS `meta_entity_version` (
  `id` BIGINT NOT NULL COMMENT '主键（Snowflake）',
  `entity_id` BIGINT NOT NULL COMMENT '实体 ID',
  `version` INT NOT NULL COMMENT '版本号（从 1 递增）',
  `snapshot` JSON NOT NULL COMMENT '实体快照（含 meta_field 列表）',
  `created_by` VARCHAR(64) DEFAULT NULL,
  `created_at` DATETIME(3) NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_entity_id` (`entity_id`),
  KEY `idx_version` (`entity_id`, `version`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 15.2 API 设计

```
GET /api/v1/metadata/entities/{id}/versions          # 版本列表
GET /api/v1/metadata/entities/{id}/versions/{v}       # 版本详情
POST /api/v1/metadata/entities/{id}/versions/{v}/rollback  # 回滚到指定版本
```

### 15.3 前端交互

- 实体详情页增加"版本历史"面板
- 列表显示版本号、更新时间、更新人
- 选中版本可查看快照 diff（JSON 对比）
- "回滚"操作需二次确认
