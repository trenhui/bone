# 12. 工作流引擎 — 平台桥接与跨系统复用设计

> 状态：`design_ready`（引擎核心已实现并测试通过；桥接层 + `wf_*` DDL 待架构师审批，见文末 L3 清单）
> 引擎代码：`bone-engine/bone-workflow-engine/`（domain / ports / runtime / starter 四段式，平台零依赖，四模块 56 测试全绿，含 v2 新增 6 条判别力用例）
> 关联模块：报销（bone-app-expense）、采购、智能理赔（synap-claim）、HR、财务
>
> **v2 修订（2026-10-23）**：实证诊断（对照引擎源码 / `bone-init.sql` 约定 / SDK 能力 / `RuntimeStatusGuard`）后修订。修复 3 个 P0：`wf_process_def` 双 `version` 列、`uk_entity_record` 与「驳回后可重提」契约冲突、§5 示例形状非法；补双写一致性 / 活动实例指针 / 绑定 / 干预闭环设计；阶段重排。逐条对照见 §8。

## 1. 目标与定位

把「审批流」做成 **BONE 平台的一等公民能力**，让报销 / 采购 / 智能理赔 / HR / 财务等企业系统**共用同一套引擎与同一套持久化**，各自只写「系统相关」的薄适配。

对标宜搭 / AppBuilder 的业界实践：**审批流是表单/实体引擎的亲兄弟，共用实体、权限、审计**——而不是外挂一个通用 BPMN 引擎。本设计严格遵循这一点：

- **不引 Camunda / Flowable / Temporal**（平台 `dependencyManagement` 里虽有 `camunda-bom` 7.24.0，但来自已删除的遗留配置 `application-enterprise.yml`，全仓零 `org.camunda.*` 引用，未进 classpath；且通用 BPMN 引擎与「零新依赖 + 元数据驱动 + 单一真源」纪律冲突）。
- **不造通用 BPMN/DMN 引擎**：只做「实体数据驱动的分支状态机 + 角色指派」这一审批流专用子集。

## 2. 复用模型（为什么这 5 个系统能共用）

引擎对平台**零依赖**，靠 7 个端口契约与宿主对话。因此复用成本极低：

| 层 | 归属 | 报销 / 采购 / 理赔 / HR / 财务 各自要做的 |
|---|---|---|
| 引擎内核（推进 / 完成判定 / 条件求值 / 并发 CAS） | **共享** · bone-workflow-engine | 什么都不用做，直接复用 jar |
| 定义 / 实例 / 任务持久化（`wf_*`） | **共享** · 桥接层 + `wf_*` 表 | 什么都不用做，获得租户隔离 / 审计 / 乐观锁 |
| 审计留痕 | **共享** · 桥接层 → 平台动作执行链路 | 什么都不用做 |
| `ApproverResolver`（指派策略） | **每系统定制** | 接各自的**组织目录 / IAM**（直属主管 / 部门负责人 / 角色 / 发起人自选） |
| `WorkflowStatusPort`（推进业务 `status`） | **每系统定制** | 走各自**状态机动作端点**（`RuntimeActionApplicationService.invokeAction`），经 `RuntimeStatusGuard` 合法流转 |
| `WorkflowRecordPort`（读单据数据求值条件） | **每系统定制** | 读各自业务单据字段（金额 / 部门 / 类目…） |
| `WorkflowConditionEvaluator`（可选） | **共享默认** / 每系统可覆盖 | 默认用引擎自带结构化条件求值；若要与平台 UI 协议规则**同源**，注入同源实现并在测试里跑 `ConditionSemanticsSamples` 防漂移 |

**结论**：每个系统接入只需实现 **2–3 个**薄端口（组织目录解析 + 自身状态机推进 + 读字段），即可获得完整审批流能力（多级 / 会签或签 / 条件分支 / 驳回撤回 / 挂起恢复 / 并发安全）。这正是「被复用」的落地形态。

> 术语纠正：「RLS」是口头俗称——落地形态是 SDK `@TenantScope(AUTO)` 租户列注入 + 应用层过滤，**不是**数据库行级安全策略；本文档其余部分统一按此表述。

## 3. 平台桥接层设计

### 3.1 模块归属

新增独立模块 **`bone-workflow-platform`**（与 `bone-workflow-engine` 并列，依赖 `bone-workflow-engine` 的 `ports` + `domain`，以及 `bone-metadata-server` 的实体 / IAM / `RuntimeActionService`）。

- 引擎保持平台无关（domain/ports/runtime 不依赖任何平台模块）；
- 桥接层是「引擎 ↔ BONE 平台」的唯一接线点，集中承载所有平台耦合（实体映射、租户、IAM、状态机）；
- **分层合规待架构师确认**：直接调 `bone-metadata-server` 的 `RuntimeActionApplicationService`（application 层）是否违反 ADR-0028 入站边界纪律；备选是抽 `workflow-status-spi` 由 metadata-server 实现、桥接层只依赖 SPI。

### 3.2 7 端口 → BONE 实现要点

| 端口 | 桥接实现 | 关键注意 |
|---|---|---|
| `WorkflowDefinitionRepository` | `wf_process_def`（`definition_json` 存整图快照，1:1 对应 `WorkflowDefinition`）；版本号钉死 | 发布前必须经 `WorkflowDefinitionValidator` 完整校验（断头 / 缺默认边 / 孤立节点 / 环 / 未知算子 / 未知指派策略 / **审批与发起节点单出口（WF-014/015）/ CC 拒绝（WF-016）**） |
| `WorkflowInstanceRepository` | `wf_instance` + `wf_task` + `wf_active_instance` | 见 §3.3 并发三方法 + §3.5 活动实例指针 |
| `ApproverResolver` | 调 IAM / 组织目录 | 解析结果必须是合法账户 id；解析不出返回空 → 引擎挂起（fail-closed）；**挂起必须配告警 + 管理员强制指派兜底**（§6 阶段 1），否则死单无人知 |
| `WorkflowRecordPort` | 平台运行时读接口读业务单据 | 仅读、不写；审批中单据已锁（§3.6），读到的即提交时数据 |
| `WorkflowStatusPort` | `RuntimeActionApplicationService.invokeAction` 走声明的状态动作 | **不在服务端直写 `status`**（会被 `RuntimeStatusGuard` 的 `rejectIfPresent` 拦）；状态机单一权威；v1 经 §3.4 outbox 最终一致落地，**不同步 invokeAction** |
| `WorkflowAuditPort` | 平台动作执行留痕链路 | 与业务操作日志同一条时间线 |
| `WorkflowIdGenerator` | 平台雪花 id | — |

**实现纪律（四条，缺一即踩坑）**：

1. **持久化全部走 `bone-metadata-sdk`**（HC-001/006）。三个 CAS 的「带 `COUNT` 子查询的条件 UPDATE」走 SDK `@Sql` 模板 / `SqlExecutor`（受 `SqlSecurityGuard` 约束），**禁止裸 `JdbcTemplate`**——这是最容易被「SDK 不好写条件 UPDATE」诱导越界的地方。
2. **`@TenantScope(AUTO)`**：SDK 默认 `MANUAL` **不注入租户列**；漏配 = 多租户串数据，且单租户单测完全看不出来。
3. **上下文传播**：7 端口实现一律从平台租户 / 用户上下文（`TenantContext` / SecurityContext）取租户与操作人，不得经调用参数私传；outbox 中继器按行内 `tenant_id` 重建上下文。
4. **装配陷阱（本项目 2026-10-21 已实证）**：starter 以 `@ConditionalOnBean(7 端口类型)` 装配引擎——若端口实现是 SDK `RepositoryFactoryBean` 代理（接口类型即 bean 类型），条件**恒假 ⇒ 引擎静默不装配、零报错**。端口必须是具体 `@Component` 类（内部委托 SDK 仓储），或改按 Bean 名条件 + `@AutoConfigureAfter`；配一条「摘掉任一端口 bean ⇒ 引擎不装配」的负向验证。

### 3.3 三个并发关键方法（**实现错就会静默出生产事故**）

桥接层实现 `WorkflowInstanceRepository` 时，以下三个方法必须落成**存储层原子语义**，绝不能用「先查后改」：

1. **`compareAndSetTaskStatus`** — 单条任务状态 CAS（条件 UPDATE `WHERE status = expected`）。
2. **`compareAndSetPhase`** — 实例阶段 CAS（条件 UPDATE `WHERE phase = expected` **且** `version = expected`——两个条件同时用，不是二选一；否则乐观锁与阶段竞态互相覆盖）。
3. **`compareAndAdvanceNode`** — **节点级原子推进**：把「该节点是否已完成」的判定与「推进到下一节点」放进**同一条条件 UPDATE**（典型实现：带 `COUNT` 子查询判定该节点全部任务已决策且无人驳回，且 `current_node_code = nodeCode` 时才改 `current_node_code`）。

   > **为什么必须原子（不是应用层读两次）**：两个会签人同时点「同意」时，各自都读到「对方还没通过」的旧快照 → 双方都判「未齐」→ **流程永远卡在待办**（会签经典死锁）。判据必须由存储层在同一条语句里依据最新行状态计算。数学上可证不死锁：`adv` 严格晚于自己的 `taskCAS`，双方互等会导出矛盾，不可能成立。
   >
   > **这条是桥接层最易做错、且做错无任何报错的一点**——务必落成条件 UPDATE，并配一条「删掉原子实现必红」的回归测试。

   `COUNT` 子查询的**已决策口径**：`status IN ('APPROVED','REJECTED','CANCELLED')`。v2 落地 `TRANSFERRED`/`DELEGATED` 时必须同步修订该口径，否则被转办 / 委派的任务会被当成「永远未决策」→ 会签节点卡死。

### 3.4 双写一致性：状态投影 outbox 与对账

**问题**：引擎先提交 `wf_*` 状态、再调 `WorkflowStatusPort` 推业务 `status`。若 `invokeAction` 失败（`RuntimeStatusGuard` 拒绝 / 下游异常 / 进程重启），结果是**引擎已 APPROVED、业务单还 SUBMITTED** 的撕裂态，且无补偿路径。引擎 README 已声明「`phase` 是权威、`status` 是投影，不一致以 `phase` 为准重投影」——但「谁发现不一致、何时修」此前没有设计，本节补上。

| 机制 | 设计 |
|---|---|
| 事务边界 | 桥接层应用服务对 `engine.start / completeTask / withdraw / resume` 每次调用包 `@Transactional`；`wf_*` 变更与 outbox 行**同生同死** |
| 投影写入 | `WorkflowStatusPort` 的 5 个 `mark*` 方法 = 同事务写 `wf_status_outbox`（`state=NEW`），**不直接调 `invokeAction`** |
| 中继器 | 桥接层定时任务（平台 scheduler 或 `@Scheduled`）poll `NEW`/`FAILED` → `invokeAction` → 置 `DONE`；失败指数退避；超阈值置 `FAILED` 并告警 |
| 对账 job | 周期性比对 `wf_instance.phase` 与业务 record 的 status 投影，不一致以 **phase 权威**重投影 |
| 幽灵审批兜底 | 对账顺带扫「业务单据已删 / 已作废 ⇒ 自动终止实例」——业务侧绕过流程终态化时，流程不会继续批一个不存在的单据 |

### 3.5 活动实例指针与重提语义

**引擎契约**（端口 javadoc + `WorkflowEngineImpl.start()` 实证）：一张单据同时只允许一个**未终结**实例；终态（`APPROVED`/`REJECTED`/`WITHDRAWN`）后可再 `start` 新实例——「驳回 → 修改 → 重新提交」是一等流程，不是异常。

由此推出两条设计约束：

1. **`uk_entity_record (tenant_id, entity_code, record_id, deleted)`（母数据表惯例）不可用于 `wf_instance`**：终态实例与重提实例同 key 同 `deleted=0`，重提必撞 1062。运行时表与主数据表生命周期不同——实例按单据**可多次产生**，唯一性只能覆盖「活动」语义。
2. **引擎 start 幂等本身是 read-then-insert**（先查活动实例再插入），唯一键是使其原子化的**唯一**机制——所以不能简单删掉唯一键，必须换一把只锁「活动实例」的锁。

**解法：`wf_active_instance` 指针表**（DDL 见 §4）：

- `start`：与 `wf_instance` 插入**同事务**插指针行；撞 PK（`DuplicateKeyException`）⇒ 读既有实例幂等返回——连点 / 网络重试绝不会产生双实例；
- 终态流转（`compareAndSetPhase` → `APPROVED`/`REJECTED`/`WITHDRAWN`）**同事务**删指针行；
- `findInstanceByRecord` 语义 = 返回 `id` 最大者（最新一次提交），否则重提后 UI 读到旧终态实例；
- 重提资格（`APPROVED` 后能否再提交）由业务状态机动作的 `from_status` 约束，引擎不代决；
- 备选（未采用）：MySQL 生成列 `active_flag AS (CASE WHEN phase IN ('RUNNING','SUSPENDED') AND deleted=0 THEN 1 END) STORED` + 唯一键忽略 NULL——零新增表，但有 H2 方言风险；桥接层集成测试在 H2 验证通过后可切换。

### 3.6 审批中口径、绑定配置与接入契约

| 议题 | v1 决策 | 理由 |
|---|---|---|
| 审批中单据编辑 | **禁止**：桥接层在 runtime update 入口按活动实例拦截 | 「批的」与「提交的」必须是同一份数据，否则分支口径不可审计；锁定后条件实时读 ≡ 提交时快照。v2 若放开编辑，必须给实例存 `condition_snapshot_json` |
| 条件字段缺省 | 有序比较（gt/gte/lt/lte/between）左值缺省判**不成立**（引擎已修：原实现字符串强转会让缺金额静默落最低档——fail-open） | 建模纪律：**默认边（else）必须指向 fail-safe（更严格）路径**；条件字段在实体层必填，双保险 |
| 发起人自选 | 提交表单携带审批人字段（提交后即冻结，天然防审批中改人）+ `FIELD` 策略读取；引擎不中介选择交互 | `INITIATOR_SELECT` 保留在白名单但 v1 不自建交互态；v2 再议 |
| 实体 → 流程绑定 | `wf_binding` 表（`entity_code → def_key + start_action`），运营可改 | `definitionKey` 不硬编码在各 action handler——否则换流程要发版。v1 一实体一流程；多流程分流由流程内条件分支表达 |
| 状态机最小动作集 | 接入系统必须提供 `submit / approve / reject / withdraw / suspend / resume`（映射 `start` + statusPort 5 个 `mark*`）；缺任一 ⇒ 桥接层 fail-fast + 接入检查清单报错 | 缺动作时 `invokeAction` 在运行期才炸，太晚 |
| SLA | `due_at` 列预留 + 桥接层定时扫描；v2 动作序 = 提醒 → 自动转交 → 自动同意（默认关闭） | 自动同意是放口子，企业场景默认不开 |
| 人事联动 | v2：账号禁用事件 → 待办自动改派（上级 / 管理员）；v1 至少提供管理员改派 API | 审批中员工离职不改派 = 死待办，是真实生产刚需 |

## 4. `wf_*` DDL 草案（**L3 · 待架构师审批**）

> 列遵循 BONE `TenantAbstractEntity` 通则：必有 `tenant_id` + 审计列（`created_by/created_at/updated_by/updated_at/deleted`）+ 乐观锁列 `version INT`（全仓惯例，**INT 非 BIGINT**）；主键恒为 `id BIGINT`。
> 母数据表唯一键惯例 `(…, deleted)` 只适用于「同 code 不重建」的主数据；运行时表（实例 / outbox）按各自生命周期设计，见各表注。

```sql
-- 流程定义（模板级，可版本化、可发布）
CREATE TABLE wf_process_def (
  id          BIGINT       NOT NULL,
  tenant_id   VARCHAR(64)  NOT NULL,
  def_key     VARCHAR(128) NOT NULL,   -- 流程标识：expense / purchase / claim / hr / finance
  def_name    VARCHAR(255) NOT NULL,
  def_version INT          NOT NULL,   -- 定义版本（实例钉版本用；勿与乐观锁列同名——v1 草案双 version 列，MySQL 直接 1060）
  status      VARCHAR(32)  NOT NULL,   -- DRAFT / PUBLISHED
  enabled     BIT          NOT NULL DEFAULT 1,
  definition_json MEDIUMTEXT NOT NULL, -- 节点/边/指派规则完整快照（与 WorkflowDefinition 1:1；TEXT 64KB 对大流程不够）
  created_by  VARCHAR(64)  NOT NULL,
  created_at  TIMESTAMP    NOT NULL,
  updated_by  VARCHAR(64),
  updated_at  TIMESTAMP,
  deleted     BIT          NOT NULL DEFAULT 0,
  version     INT          NOT NULL DEFAULT 0,  -- 乐观锁（全仓惯例）
  PRIMARY KEY (id),
  UNIQUE KEY uk_def_key_version (tenant_id, def_key, def_version, deleted)
);
-- 语义注：同一 def_key 可并存多个 PUBLISHED 版本（在途实例钉旧版）；
-- findLatestPublished 必须确定性——取 status='PUBLISHED' AND enabled=1 中 max(def_version)，
-- 不得用 updated_at 决胜（同秒更新即不确定）。

-- 流程实例（运行时，钉版本）
CREATE TABLE wf_instance (
  id               BIGINT       NOT NULL,
  tenant_id        VARCHAR(64)  NOT NULL,
  entity_code      VARCHAR(128) NOT NULL,  -- 业务实体：expense_reimbursement / purchase_order / ...
  record_id        VARCHAR(128) NOT NULL,  -- 业务单据 id
  def_key          VARCHAR(128) NOT NULL,
  def_version      INT          NOT NULL,
  current_node_code VARCHAR(128) NOT NULL,
  phase            VARCHAR(32)  NOT NULL,  -- RUNNING / APPROVED / REJECTED / WITHDRAWN / SUSPENDED
  started_by       VARCHAR(64)  NOT NULL,
  started_at       TIMESTAMP    NOT NULL,
  finished_at      TIMESTAMP    NULL,      -- 终态时间（流程时效分析用；RUNNING/SUSPENDED 为 NULL）
  updated_at       TIMESTAMP    NOT NULL,
  created_by       VARCHAR(64)  NOT NULL,
  created_at       TIMESTAMP    NOT NULL,
  updated_by       VARCHAR(64),
  deleted          BIT          NOT NULL DEFAULT 0,
  version          INT          NOT NULL DEFAULT 0,  -- 乐观锁（阶段 CAS 用）
  PRIMARY KEY (id),
  KEY idx_entity_record (tenant_id, entity_code, record_id, id)  -- findInstanceByRecord 取 id 最大者
);
-- 无 (entity_code, record_id) 唯一键：驳回/撤回后重提是新实例，历史按单据可累积；
-- 「同时只有一个活动实例」由 wf_active_instance 指针表保证（见 §3.5）。

-- 活动实例指针（一张单据同时只允许一个未终结实例——引擎 start 幂等的原子化靠这把锁）
CREATE TABLE wf_active_instance (
  tenant_id   VARCHAR(64)  NOT NULL,
  entity_code VARCHAR(128) NOT NULL,
  record_id   VARCHAR(128) NOT NULL,
  instance_id BIGINT       NOT NULL,
  PRIMARY KEY (tenant_id, entity_code, record_id)
);
-- 规则：start 同事务插入（撞 PK ⇒ DuplicateKeyException ⇒ 读既有实例幂等返回）；
-- 终态 phase CAS 同事务删除。写入/删除必须与 wf_instance 同事务，否则指针与实例漂移。

-- 审批任务（会签 / 或签产生多行；含指派冻结快照）
CREATE TABLE wf_task (
  id           BIGINT       NOT NULL,
  tenant_id    VARCHAR(64)  NOT NULL,
  instance_id  BIGINT       NOT NULL,
  node_code    VARCHAR(128) NOT NULL,
  assignee_id  VARCHAR(64)  NOT NULL,
  status       VARCHAR(32)  NOT NULL,  -- PENDING / APPROVED / REJECTED / TRANSFERRED / DELEGATED / CANCELLED
  decision     VARCHAR(32),            -- APPROVE / REJECT；与 status 冗余但保留：引擎「同结论重复提交幂等」判据 + 任务级审计语义
  comment      VARCHAR(1024),
  due_at       TIMESTAMP,              -- SLA（v2 超时转交用；扫描机制见 §3.6）
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  created_by   VARCHAR(64)  NOT NULL,
  updated_by   VARCHAR(64),
  deleted      BIT          NOT NULL DEFAULT 0,
  version      INT          NOT NULL DEFAULT 0,  -- 乐观锁（任务 CAS 用）
  PRIMARY KEY (id),
  KEY idx_assignee_status (tenant_id, assignee_id, status, deleted),  -- 我的待办
  KEY idx_instance        (tenant_id, instance_id, deleted)
);
-- 会签完成判定口径（compareAndAdvanceNode 的 COUNT 子查询）：
--   已决策 = status IN ('APPROVED','REJECTED','CANCELLED')；未决 = 'PENDING'
--   v2 落 TRANSFERRED/DELEGATED 时必须同步修订该口径，否则转办/委派任务被当「永远未决策」卡死节点。
-- v1 只产生/流转 PENDING/APPROVED/REJECTED/CANCELLED；TRANSFERRED/DELEGATED 为 v2 预留。

-- 状态投影发件箱（双写一致性：引擎状态与业务 status 的最终一致，见 §3.4）
CREATE TABLE wf_status_outbox (
  id           BIGINT       NOT NULL,
  tenant_id    VARCHAR(64)  NOT NULL,
  instance_id  BIGINT       NOT NULL,
  entity_code  VARCHAR(128) NOT NULL,
  record_id    VARCHAR(128) NOT NULL,
  intent       VARCHAR(32)  NOT NULL,   -- APPROVED / REJECTED / WITHDRAWN / SUSPENDED / RESUMED
  payload_json TEXT         NULL,       -- 动作参数（驳回原因等）
  state        VARCHAR(16)  NOT NULL,   -- NEW / DONE / FAILED
  retry_count  INT          NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMP   NULL,
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_poll (state, next_retry_at)
);

-- 业务实体 → 流程定义绑定（definitionKey 的运营入口，见 §3.6）
CREATE TABLE wf_binding (
  id           BIGINT       NOT NULL,
  tenant_id    VARCHAR(64)  NOT NULL,
  entity_code  VARCHAR(128) NOT NULL,
  def_key      VARCHAR(128) NOT NULL,
  start_action VARCHAR(64)  NOT NULL DEFAULT 'submit',  -- 触发启动的业务动作码
  enabled      BIT          NOT NULL DEFAULT 1,
  created_by   VARCHAR(64)  NOT NULL,
  created_at   TIMESTAMP    NOT NULL,
  updated_by   VARCHAR(64),
  updated_at   TIMESTAMP,
  deleted      BIT          NOT NULL DEFAULT 0,
  version      INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_binding (tenant_id, entity_code, deleted)
);
```

> 注：节点 / 边 / 指派规则**不拆物理表**，统一存 `wf_process_def.definition_json`。理由：流程定义是「整图版本化」对象，拆表只会增加 join 与版本一致性负担；可视化设计器读 json 即可渲染。若未来需按节点检索，可在桥接层反序列化后查，不必落列。

## 5. 接线示例（报销）

金额三档与 `ExpenseApprovalRouter` 现行口径逐条对齐（≤1000 直属主管 / ≤5000 部门负责人 / >5000 财务负责人**会签**）。形状纪律：**审批 / 发起节点恰有 1 条无条件出边，条件只能挂 CONDITION 节点**（发布期 WF-014/015 强制）；条件为结构化 JSON（`{"fieldCode":"amount","operator":"gt","value":5000}`，下方为简写）。

```java
// 在 bone-app-expense（或桥接层）声明流程定义（一次，随模板实例化）
definitions.publish(new WorkflowDefinition("expense", 1,
    List.of(
        node("start", START),
        node("cond_null", CONDITION, null, "金额是否缺失"),   // 数据质量守卫：缺金额 → 最高档（fail-safe）
        node("cond_high", CONDITION, null, "金额 > 5000"),
        node("cond_mid",  CONDITION, null, "金额 > 1000"),
        node("mgr",     APPROVE, SINGLE, "直属主管审批"),
        node("dept",    APPROVE, SINGLE, "部门负责人审批"),
        node("finance", APPROVE, ALL,    "财务负责人审批（会签）"),  -- >5000 档 = 原 router countersign
        node("end", END)),
    List.of(
        edge("start", "cond_null"),
        edge("cond_null", "finance", "amount isNull"),  // 缺省 → 最高档，绝不静默落最低档
        edge("cond_null", "cond_high"),                 // else（默认边必须末位）
        edge("cond_high", "finance", "amount > 5000"),
        edge("cond_high", "cond_mid"),
        edge("cond_mid", "dept", "amount > 1000"),
        edge("cond_mid", "mgr"),
        edge("mgr", "end"), edge("dept", "end"), edge("finance", "end")),
    Map.of(
        "mgr", List.of(rule(LINE_MANAGER)),
        "dept", List.of(rule(DEPT_HEAD)),
        "finance", List.of(rule(ROLE, "FINANCE_HEAD")))));

// ApproverResolver 接 IAM：LINE_MANAGER → 申请人直属主管 id；DEPT_HEAD → 部门负责人；ROLE → 角色成员
// WorkflowStatusPort：5 个 mark* → 写 wf_status_outbox（§3.4），中继器经 invokeAction 落地业务 status
// 业务 submit 动作 → 查 wf_binding 取 def_key → 调 engine.start(...)
// 任务决策 → POST /wf/tasks/{taskId}/decision → engine.completeTask(...)（新端点，见 §6 阶段 1）
```

**迁移 `ExpenseApprovalRouter` 的行为等价清单**（替换前逐条核对，防悄悄改审批策略）：

| 检查项 | router 现行 | 引擎版 |
|---|---|---|
| 档位边界 | ≤1000 LOW / ≤5000 MID / 其余 HIGH（等号归低档） | 同（`cond_mid` else = ≤1000） |
| HIGH 档会签 | `countersign=true`（G2-v1.1） | `ApprovalMode.ALL` |
| 金额缺省 | `bandOf(null)` NPE（500） | `isNull` 守卫 → 最高档（**行为变更，需业务确认**） |
| 指派解析 | `InMemoryApproverResolver`（MVP 内存实现） | 统一走引擎 `ApproverResolver` → IAM |
| 删除物 | `ExpenseApprovalRouter` + `InMemoryApproverResolver` | 消除两套并行路由的漂移风险 |
