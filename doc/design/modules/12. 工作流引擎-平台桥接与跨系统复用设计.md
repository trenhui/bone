# 12. 工作流引擎 — 平台桥接与跨系统复用设计

> 状态：`design_ready`（引擎核心已实现并测试通过；桥接层 + `wf_*` DDL 待架构师审批，见文末 L3 清单）
> 引擎代码：`bone-engine/bone-workflow-engine/`（domain / ports / runtime / starter 四段式，平台零依赖，50 单测全绿）
> 关联模块：报销（bone-app-expense）、采购、智能理赔（synap-claim）、HR、财务

---

## 1. 目标与定位

把「审批流」做成 **BONE 平台的一等公民能力**，让报销 / 采购 / 智能理赔 / HR / 财务等企业系统**共用同一套引擎与同一套持久化**，各自只写「系统相关」的薄适配。

对标宜搭 / AppBuilder 的业界实践：**审批流是表单/实体引擎的亲兄弟，共用实体、权限、审计**——而不是外挂一个通用 BPMN 引擎。本设计严格遵循这一点：

- **不引 Camunda / Flowable / Temporal**（平台 `dependencyManagement` 里虽有 `camunda-bom` 7.24.0，但来自已删除的遗留配置 `application-enterprise.yml`，全仓零 `org.camunda.*` 引用，未进 classpath；且通用 BPMN 引擎与「零新依赖 + 元数据驱动 + 单一真源」纪律冲突）。
- **不造通用 BPMN/DMN 引擎**：只做「实体数据驱动的分支状态机 + 角色指派」这一审批流专用子集。

---

## 2. 复用模型（为什么这 5 个系统能共用）

引擎对平台**零依赖**，靠 7 个端口契约与宿主对话。因此复用成本极低：

| 层 | 归属 | 报销 / 采购 / 理赔 / HR / 财务 各自要做的 |
|---|---|---|
| 引擎内核（推进 / 完成判定 / 条件求值 / 并发 CAS） | **共享** · bone-workflow-engine | 什么都不用做，直接复用 jar |
| 定义 / 实例 / 任务持久化（`wf_*`） | **共享** · 桥接层 + `wf_*` 表 | 什么都不用做，免费获得多租户 / RLS / 审计 / 乐观锁 |
| 审计留痕 | **共享** · 桥接层 → 平台动作执行链路 | 什么都不用做 |
| `ApproverResolver`（指派策略） | **每系统定制** | 接各自的**组织目录 / IAM**（直属主管 / 部门负责人 / 角色 / 发起人自选） |
| `WorkflowStatusPort`（推进业务 `status`） | **每系统定制** | 走各自**状态机动作端点**（`RuntimeActionService.invokeAction`），经 `RuntimeStatusGuard` 合法流转 |
| `WorkflowRecordPort`（读单据数据求值条件） | **每系统定制** | 读各自业务单据字段（金额 / 部门 / 类目…） |
| `WorkflowConditionEvaluator`（可选） | **共享默认** / 每系统可覆盖 | 默认用引擎自带结构化条件求值；若要与平台 UI 协议规则**同源**，注入同源实现并在测试里跑 `ConditionSemanticsSamples` 防漂移 |

**结论**：每个系统接入只需实现 **2–3 个**薄端口（组织目录解析 + 自身状态机推进 + 读字段），即可获得完整审批流能力（多级 / 会签或签 / 条件分支 / 驳回撤回 / 挂起恢复 / 并发安全）。这正是「被复用」的落地形态。

## 3. 平台桥接层设计

### 3.1 模块归属

新增独立模块 **`bone-workflow-platform`**（与 `bone-workflow-engine` 并列，依赖 `bone-workflow-engine` 的 `ports` + `domain`，以及 `bone-metadata-server` 的实体 / IAM / `RuntimeActionService`）。

- 引擎保持平台无关（domain/ports/runtime 不依赖任何平台模块）；
- 桥接层是「引擎 ↔ BONE 平台」的唯一接线点，集中承载所有平台耦合（实体映射、RLS、IAM、状态机）。

### 3.2 7 端口 → BONE 实现要点

| 端口 | 桥接实现 | 关键注意 |
|---|---|---|
| `WorkflowDefinitionRepository` | `wf_process_def`（`definition_json` 存整图快照，1:1 对应 `WorkflowDefinition`）；版本号钉死 | 发布前必须经 `WorkflowDefinitionValidator` 完整校验（断头 / 缺默认边 / 孤立节点 / 环 / 未知算子 / 未知指派策略） |
| `WorkflowInstanceRepository` | `wf_instance` + `wf_task` | 见 3.3 并发三方法 |
| `ApproverResolver` | 调 IAM / 组织目录 | 解析结果必须是合法账户 id；解析不出返回空 → 引擎挂起 |
| `WorkflowRecordPort` | 平台运行时读接口读业务单据 | 仅读、不写 |
| `WorkflowStatusPort` | `RuntimeActionApplicationService.invokeAction` 走声明的状态动作 | **不在服务端直写 `status`**（会被 `RuntimeStatusGuard` 的 `rejectIfPresent` 拦）；状态机单一权威 |
| `WorkflowAuditPort` | 平台动作执行留痕链路 | 与业务操作日志同一条时间线 |
| `WorkflowIdGenerator` | 平台雪花 id | — |

### 3.3 三个并发关键方法（**实现错就会静默出生产事故**）

桥接层实现 `WorkflowInstanceRepository` 时，以下三个方法必须落成**存储层原子语义**，绝不能用「先查后改」：

1. **`compareAndSetTaskStatus`** — 单条任务状态 CAS（条件 UPDATE `WHERE status = expected`）。
2. **`compareAndSetPhase`** — 实例阶段 CAS（条件 UPDATE `WHERE phase = expected`，用 `version` 列或 `phase` 列）。
3. **`compareAndAdvanceNode`** — **节点级原子推进**：把「该节点是否已完成」的判定与「推进到下一节点」放进**同一条条件 UPDATE**（典型实现：带 `COUNT` 子查询判定该节点全部任务已决策且无人驳回，且 `current_node_code = nodeCode` 时才改 `current_node_code`）。

   > **为什么必须原子（不是应用层读两次）**：两个会签人同时点「同意」时，各自都读到「对方还没通过」的旧快照 → 双方都判「未齐」→ **流程永远卡在待办**（会签经典死锁）。判据必须由存储层在同一条语句里依据最新行状态计算。数学上可证不死锁：`adv` 严格晚于自己的 `taskCAS`，双方互等会导出矛盾，不可能成立。
   >
   > **这条是桥接层最易做错、且做错无任何报错的一点**——务必落成条件 UPDATE，并配一条「删掉原子实现必红」的回归测试。

## 4. `wf_*` DDL 草案（**L3 · 待架构师审批**）

> 列遵循 BONE `TenantAbstractEntity` 通则：必有 `tenant_id` + 审计列（`created_by/created_at/updated_by/updated_at/deleted`）+ `version` 乐观锁；主键恒为 `id BIGINT`。

```sql
-- 流程定义（模板级，可版本化、可发布）
CREATE TABLE wf_process_def (
  id          BIGINT       NOT NULL,
  tenant_id   VARCHAR(64)  NOT NULL,
  def_key     VARCHAR(128) NOT NULL,   -- 流程标识：expense / purchase / claim / hr / finance
  def_name    VARCHAR(255) NOT NULL,
  version     INT          NOT NULL,
  status      VARCHAR(32)  NOT NULL,   -- DRAFT / PUBLISHED
  enabled     BIT          NOT NULL DEFAULT 1,
  definition_json TEXT     NOT NULL,   -- 节点/边/指派规则的完整快照（与 WorkflowDefinition 1:1）
  created_by  VARCHAR(64)  NOT NULL,
  created_at  TIMESTAMP    NOT NULL,
  updated_by  VARCHAR(64),
  updated_at  TIMESTAMP,
  deleted     BIT          NOT NULL DEFAULT 0,
  version     BIGINT       NOT NULL DEFAULT 0,  -- 乐观锁
  PRIMARY KEY (id),
  UNIQUE KEY uk_def_key_version (tenant_id, def_key, version, deleted)
);

-- 流程实例（运行时，钉版本）
CREATE TABLE wf_instance (
  id               BIGINT       NOT NULL,
  tenant_id        VARCHAR(64)  NOT NULL,
  entity_code      VARCHAR(128) NOT NULL,  -- 业务实体：expense_reimbursement / purchase_order / ...
  record_id        VARCHAR(128) NOT NULL,  -- 业务单据 id
  def_key          VARCHAR(128) NOT NULL,
  def_version      INT          NOT NULL,
  current_node_code VARCHAR(128) NOT NULL,
  phase            VARCHAR(32)  NOT NULL,  -- RUNNING / APPROVED / REJECTED / WITHDRAWN / SUSPENDED
  started_by       VARCHAR(64)  NOT NULL,
  started_at       TIMESTAMP    NOT NULL,
  updated_at       TIMESTAMP    NOT NULL,
  created_by       VARCHAR(64)  NOT NULL,
  created_at       TIMESTAMP    NOT NULL,
  updated_by       VARCHAR(64),
  deleted          BIT          NOT NULL DEFAULT 0,
  version          BIGINT       NOT NULL DEFAULT 0,  -- 乐观锁（阶段 CAS 用）
  PRIMARY KEY (id),
  UNIQUE KEY uk_entity_record (tenant_id, entity_code, record_id, deleted)
);

-- 审批任务（会签 / 或签产生多行；含指派冻结快照）
CREATE TABLE wf_task (
  id           BIGINT       NOT NULL,
  tenant_id    VARCHAR(64)  NOT NULL,
  instance_id  BIGINT       NOT NULL,
  node_code    VARCHAR(128) NOT NULL,
  assignee_id  VARCHAR(64)  NOT NULL,
  status       VARCHAR(32)  NOT NULL,  -- PENDING / APPROVED / REJECTED / TRANSFERRED / DELEGATED / CANCELLED
  decision     VARCHAR(32),            -- APPROVE / REJECT
  comment      VARCHAR(1024),
  due_at       TIMESTAMP,              -- SLA（v2 超时转交用）
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  created_by   VARCHAR(64)  NOT NULL,
  updated_by   VARCHAR(64),
  deleted      BIT          NOT NULL DEFAULT 0,
  version      BIGINT       NOT NULL DEFAULT 0,  -- 乐观锁（任务 CAS 用）
  PRIMARY KEY (id),
  KEY idx_assignee_status (tenant_id, assignee_id, status, deleted),  -- 我的待办
  KEY idx_instance        (tenant_id, instance_id, deleted)
);
```

> 注：节点 / 边 / 指派规则**不拆物理表**，统一存 `wf_process_def.definition_json`。理由：流程定义是「整图版本化」对象，拆表只会增加 join 与版本一致性负担；可视化设计器读 json 即可渲染。若未来需按节点检索，可在桥接层反序列化后查，不必落列。

## 5. 接线示例（报销）

```java
// 在 bone-app-expense（或桥接层）声明流程定义（一次，随模板实例化）
definitions.publish(new WorkflowDefinition("expense", 1,
    List.of(
        node("start", START),
        node("mgr", APPROVE, SINGLE, "直属主管审批"),
        node("finance", APPROVE, SINGLE, "财务审批"),   // >¥5000 才走到（条件分支）
        node("end", END)),
    List.of(edge("start","mgr"), edge("mgr","finance","amount > 5000"),
            edge("mgr","end","amount <= 5000"), edge("finance","end")),
    Map.of("mgr", List.of(rule(LINE_MANAGER)), "finance", List.of(rule(ROLE,"FINANCE")))));

// ApproverResolver 接 IAM：LINE_MANAGER → 取申请人直属主管 id
// WorkflowStatusPort：APPROVED → RuntimeActionApplicationService.invokeAction(recordId, "approve")
// 业务 submit 动作 → 调 engine.start(...)；业务 approve 动作 → 调 engine.completeTask(...)
```

报销里早前写的 `ExpenseApprovalRouter`（金额分级派单）应**改为经引擎的 `ApproverResolver` 走**，消除「两套并行路由实现」的漂移风险。
