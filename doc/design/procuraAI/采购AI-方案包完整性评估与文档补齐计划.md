# procuraAI 方案包完整性评估与文档补齐计划

> **用途**：回答"方案离落地还缺哪些文档、为什么"——从"方案资产"到"可交付产品"的文档缺口盘点与补齐排期。
> **评估基准**：软件工程全流程 + FDE 交付模型（轻咨询/标准包/赋能）+ 政企私有化落地特殊性。

## 2. 落地文档缺口矩阵（12 类 · P0/P1/P2 优先级）

### P0 —— POC 启动前必须（4 周内补齐，缺了无法开工）

| # | 缺口文档 | 核心内容 | 为什么缺 / 缺了会怎样 |
|---|----------|----------|----------------------|
| D1 | **POC 试点方案** | 种子客户选择标准（央国企/政策压力）、30 份样本获取路径、基线测量方法（试点前人工耗时/漏检基线）、POC 成功标准（对齐立项评估 Go/No-Go） | 落地第一个动作就是 POC，但没有"剧本"——没有样本获取路径和基线测量法，POC 结果无法判定，Go/No-Go 闸门形同虚设 |
| D2 | **原型/交互设计（Hi-Fi）** | FR-803 原文高亮锚点界面、FR-205 处置流界面（修订→重审→定稿）、HITL 逐条确认面板、预警台账 | 用户确认"产品长什么样"是第一道验收——没有原型，开发无 UI 依据、客户无直观体验、评审无实物可看 |
| D3 | **接口契约与数据字典** | OpenAPI 规格（字段级 + 错误码 + 鉴权 + 版本）、risk_item/alert/review_snapshot/alert_task 字段定义、OA webhook 事件负载、异步任务状态机 | 前后端并行 + OA/ERP 对接联调的前提——没有契约冻结，联调扯皮、接口返工是政企项目最常见延期源 |
| D4 | **项目计划与排期** | WBS、里程碑（依赖 GPU/标注数据/客户配合）、人力计划（算法/后端/前端/测试/交付）、风险登记册 | 从"方案"到"项目"的最后一纸——没有排期与依赖清单，资源不到位（GPU、标注人力）会在中途爆发 |

### P1 —— 开发交付期（6–12 周，与开发并行）

| # | 缺口文档 | 核心内容 | 为什么缺 / 缺了会怎样 |
|---|----------|----------|----------------------|
| D5 | **测试与验收方案** | 功能/性能/安全用例集、评测集规格（200 条样本结构）、UAT 验收用例（对齐 PRD §10 基线：遗漏率/误报率/耗时/采纳率"怎么测、谁判定"） | 成功口径都是数字，但数字要变成可执行用例才有意义——没有验收用例，"达标"就无法客观判定，验收扯皮 |
| D6 | **标注规范与评测集构建** | 标注平台选择、双人标注+仲裁流程（Kappa ≥0.8 判定）、脱敏字段清单与脱敏算法选型、评测集版本管理 | 评测基线（L0-L5）与规则库回归都依赖标注质量——没有规范，200 条样本质量不可信，评测体系是空中楼阁 |
| D7 | **安全合规文档包** | 等保三级定级备案材料、密评配合清单、数据分级（A/B/C）与留存策略、应急预案、安全自查表 | **政企采购的硬性门槛**——招标/评审必查项，现场拿不出即出局；等保备案周期长，不提前启动会卡上线 |
| D8 | **部署运维手册** | 安装部署步骤（Docker Compose/K8s）、配置清单（模型/规则/租户/权限）、监控指标与告警规则、备份恢复、升级回滚 SOP | 私有化交付第一现场是客户 IT 部署——没有手册，每次交付都是"现场开发"，交付成本失控（FDE 的"标准包复制"承诺兑现不了） |

### P2 —— 运营/规模化（标杆验证后）

| # | 缺口文档 | 核心内容 | 为什么缺 / 缺了会怎样 |
|---|----------|----------|----------------------|
| D9 | **规则库维护 SOP** | 规则入库流程（法务确认→测试回归→灰度→全量）、规则测试用例模板（≥1 正+1 反）、版本回滚预案 | 规则库是数据飞轮核心——没有 SOP，法务无法接手维护，飞轮转不起来，企业源 ER01+ 沉淀停滞 |
| D10 | **角色培训教材** | 法务（标注/规则维护）、管理员（灰度/评测回归）、采购（确认流/预警）、IT（部署运维）四角色课程 | FDE 的"赋能交付"承诺（客户自运营）需要教材兑现——没有培训，交付后客户团队无法自运营 |
| D11 | **行业规则包规划** | 分行业预置规则清单（货物/工程/服务/框架协议）、行业评测集、行业白皮书素材 | 第二增长曲线（商业化 §3.2 行业规则包）——没有规划，规模化阶段无产品抓手 |

## 3. 补齐顺序建议（对齐 POC 时间线）

```
第 1 周    D1 POC 试点方案 + D4 项目计划 ──▶ 种子客户接触、样本获取启动
第 2–3 周  D2 原型（Hi-Fi）────────────────▶ 客户确认"长这样"，锁定 FR-803/205 交互
第 2–4 周  D3 接口契约 + 数据字典 ──────────▶ 前后端并行开工、适配器联调前提
第 4–6 周  D5 测试验收 + D6 标注规范 ───────▶ POC 数据回流前建好评测基线
并行      D7 安全合规材料 ────────────────▶ 等保备案提前申报（周期 1–3 个月）
POC 通过后 D8 部署运维手册 ────────────────▶ 标杆客户交付用
规模化决策 D9/D10/D11 ──────────────────▶ 运营与第二曲线
```

**核心原则**：P0 四份决定"能不能开工"，P1 四份决定"交付质量与成本"，P2 三份决定"能不能规模"——按这个顺序补，不做过度文档化。

---

## 4. 明确"不需要现在补"的（防过度文档化）

| 项 | 不现在补的理由 |
|----|----------------|
| OpenAPI 实现级细节（完整 swagger） | 属于代码产物，接口契约（D3）定到字段级即可，细节随代码产出 |
| 部署手册客户环境细节（IP/拓扑） | 客户环境未定，写了也作废——D8 写标准步骤，环境细节交付时填 |
| 代码工程规范（仓库结构/CI） | 开工时定，或直接复用 Bone blueprint 惯例（ArchUnit/Spotless 门禁） |
| 财务模型细节 | 立项审批时按实际人力/GPU/标注预算填，模板已有（商业化 ROI） |

---

## 5. 一句话结论

> **方案层（需求-设计-商业-决策）已到可评审状态；离落地缺的是"落地层七类工程文档"——原型、契约、测试、标注、安全合规、部署运维、项目排期。P0 四份（POC 方案/原型/接口契约/项目计划）决定能否开工，是当前最紧迫的补齐项。**
