## 一、结论先行

### 1.1 一句话方案

**不新建微应用、不画步骤条**，把 `EntityDetail.tsx` 从「字段/关系/校验」三 Tab 就地升级为「结构/界面/数据/发布」四 Tab 工作区；左侧菜单从 4 项收口为 2 项；**先补 5 个断点（W0-P0）让闭环真正闭合，再谈界面 Tab 的覆盖配置**。

### 1.2 与PRD 的三处**修正**（实测发现，PRD 假设不成立）

| # | PRD 假设 | 代码实测 | 影响 |
|---|---|---|---|
| **C1** | §5.2.1 称「界面 Tab = MetaList/MetaForm 预览」，隐含共享层已存在 | **MetaList/MetaForm 全仓零命中**；`@bone/ui` 只导出 tokens/theme/authority；`@bone/shared-components` 是**零消费死包** | 「界面预览列 ≡ 数据列」不是「接线」，是**从零新建 + 抽共享层**。W1 工作量被低估 |

### 3.2 W0b · UID-9 工作区壳（Tabs 重命名 + 状态提升）

**改法不是「加一个 Tab」，而是「重排 + 提升状态」**：

| 现状 | 目标 | 说明 |
|---|---|---|
| Tab: `fields` / `relations` / `validation` | Tab: **结构** / **界面** / **数据** / **发布** | 结构 = 字段（主）+ 关系（**同 Tab 内子 Tab 或折叠区**），校验降为结构页右侧问题面板 + 发布 Tab 前置检查 |
| `activeTab: useState('fields')`（`:132`） | `useSearchParams`：`?tab=structure\|ui\|data\|publish` | **Tab 与 URL 双向同步** ⇒ 刷新不丢、可分享、可深链（原型 `#scene=x&t-<tab>` 同思路） |
| 顶栏发布仅 `status===0`（`:653`） | 顶栏常驻「发布」+ **脏态徽标** | 1→n 场景的核心是「已发布实体加字段后再发布」⇒ **当前实现让1→n 无法在详情页完成**（发布按钮消失了），必须改 |
| 无脏态 | 「未发布 · N 项」徽标 + 条 | N 的算法：`字段/关系 updatedAt` 与「上次发布时刻」的差集计数（后端暂无快照 ⇒ MVP 用前端比较 `meta_entity.updatedAt` 与最近一次 publish-preview 时间戳，v1.1 接RC-006 快照） |

- **L1 / L2 分级徽标** + L2 二次确认
- 成功后按钮区：**「打开数据」**（补P0-8 的反向入口）+ 脏态清零

### 3.4 W2 · 界面 Tab 与「预览列 ≡ 数据列」

#### 3.4.1 列投影单一真源（这是 PRD §5.3.0a 成立的技术前提）

PRD 要求「界面预览列 ≡ 发布后数据列」。当前若各算一遍必然漂移。**唯一可靠做法：抽一个纯函数做列投影，双方共用。**

```ts
// packages/shared-services/src/metaProjection.ts（新增，单一真源）
export interface ColumnOverride { visible: boolean; label?: string; order?: number }
export function projectColumns(
  fields: MetaField[],       // catalog 快照 + 覆盖
  overrides: Map<string, ColumnOverride>,
  opts: { density?: 'default'|'compact'|'loose'; mode:'list'|'form' }
): MetaColumn[]
```

- **界面 Tab 预览** = `projectColumns(草稿fields, 草稿override)` + 演示数据
- **数据 Tab 列表** = `projectColumns(已发布fields, 已发布override)` + runtime records
- **请求参数** = `projectColumns(...).map(c=>c.code).join(',')` ⇒ 传给后端 `fields`（白名单校验已有，`RuntimePageQuery`）

⇒ 三者共用一个函数 = 结构上不可能漂移。这比「写测试保证一致」强一个量级。

#### 3.4.2 覆盖配置（override）的存储决策 —— MVP **建议不做持久化**

| 方案 | 代价 | 收益 | 判定 |
|---|---|---|---|
| A. 后端建 `meta_entity_ui_config` 表 | DDL + 实体 + API + 迁移 + 权限点 + 与发布快照的关系（L3 全套） | 跨用户共享 | ❌ MVP 不做 |
| **B. `localStorage` 草稿（键= `ui:{entityId}`）** | 约 30 行| 「恢复默认显示」可演示；不污染元数据；符合 PRD「覆盖不改元数据」原则 | ✅ **MVP 采用** |
| C. 后端只存 per-user 偏好 | 仍需 DDL + API | 跨设备 | v1.1 |
