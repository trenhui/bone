### 8.4 并发控制与锁策略

> **硬规则（2026-09-27 增补）**：业务/应用层**禁止 `SELECT ... FOR UPDATE`**。聚合并发默认走 SDK 原生 `@Version` 乐观锁；高冲突场景用唯一约束 / 条件更新 / 单写者串行队列。本规则与 [AGENTS.md §一.7](#一不可违反违反即阻断)、[Bone-DDD E-5.3](#e-5-事务事件与并发)、[数据库开发规范 §1](#1-总则与真源) 同源，三处只引用、不另立语义。

#### 8.4.1 为什么禁止 `SELECT ... FOR UPDATE`（悲观锁）

`SELECT ... FOR UPDATE` 在事务内对被查行加排他行锁，意图把「读 → 判 → 写」变成串行段。它在 Bone 的场景下风险大于收益：

1. **死锁**：死锁的根因是**加锁顺序不一致**。两个事务各自先锁 A 再等 B、或先锁 B 再等 A，就会形成循环等待（MySQL 检测到后回滚其一）。业务代码里跨聚合、跨表、跨索引的「读→改」顺序很难全局一致，尤其多入口（API、Job、`@Async`、MQ 消费）并发进入时，顺序更难保证。
2. **锁持有时间被事务拉长**：Bone 的写路径在 `@Transactional` 内，且常串联领域行为、RPC、事件发布。行锁从 `FOR UPDATE` 一直持有到事务提交，热点行在高并发下变成串行瓶颈，进而**锁等待超时雪崩**（`Lock wait timeout`）。
3. **间隙锁放大**：InnoDB 在 RR 隔离级别下，`FOR UPDATE` 会把行锁升级为 **next-key lock**（行 + 间隙），锁定范围超出你「想锁的那一行」，进一步抬高死锁与阻塞概率。
4. **跨实例彻底失效**：行锁是 **单 MySQL 实例**级别的。Bone 多副本 / 读写分离 / 分库部署下，实例 A 上的 `FOR UPDATE` 对实例 B 的并发写**毫无约束力**——你以为串行，实际仍竞态。这是它相对乐观锁最致命的缺陷。
5. **与多租户过滤交互脆弱**：Bone 的 SQL 经 `TenantSqlRewriter` 注入租户条件；手写 `FOR UPDATE` 若不经 SDK 通道，极易漏注租户或踩 SDK 的边界关键字解析，引入跨租户风险。

> 结论：**悲观锁既解决不了 Bone 的跨实例并发，又自带死锁与雪崩风险**，故业务层一律禁用。SDK 写路径自带的 `@Version` 乐观锁是等价且更安全的默认实现。

#### 8.4.2 默认方案：SDK 原生 `@Version` 乐观锁（已实现，ADR-0031）

`bone-metadata-sdk` 的通用写路径（`BaseRepository#update` → `DynamicUpdateBuilder`）**自动消费**实体上的 `@Version` 注解（D1 落地、blueprint `Order`/`Payment` 已启用 D2）：

- `SET version = version + 1`，`WHERE` 追加 `AND version = :old`（旧值取加载时实体字段）；
- 受影响行数 = 0（版本冲突 / 行不存在 / 越租户）时抛 `OptimisticLockingFailureException`；
- 成功后将新 `version` 回写实体（避免同一实体二次写假冲突）。

**用法（应用层）**：

```java
// 聚合根标注 @Version（DDL 见 §1：version INT NOT NULL DEFAULT 0）
@Version private Long version;

// 应用层只写领域行为 + 落库，不再手写版本管理
@Transactional
public void rename(RenameTenantCommand cmd) {
  Tenant tenant = tenantRepository.findById(cmd.id());
  try {
    tenant.rename(cmd.name());           // 领域行为
  } catch (DomainException ex) {
    throw IamErrors.of(TENANT_NAME_CONFLICT, ex.getMessage(), ex); // 见 E-5.3.1
  }
  tenantRepository.update(tenant);        // SDK 自动带 version 护栏
}
```

冲突时 SDK 抛 `OptimisticLockingFailureException`，应用层翻译为稳定的 `OptimisticLockConflictException`（→ 409），由调用方重试或提示用户「数据已被他人修改，请刷新后重试」。**不要在应用层吞掉该异常**——那是静默丢更新。

#### 8.4.3 替代方案矩阵（业界最佳实践）

| 方案 | 机制 | 适用场景 | 代价 / 注意 |
|------|------|----------|-------------|
| **乐观版本锁**（默认） | `@Version` + `WHERE version=:old` | 低~中冲突、交互式写入、跨实例安全 | 冲突需重试；`affected=0` 无法区分「冲突 / 不存在 / 越租户」，统一按冲突处理（ADR-0031 D1.7） |
| **条件更新（原子 UPDATE）** | `UPDATE t SET c=c+1 WHERE id=? AND c+1<=limit` | 计数 / 配额 / 状态机迁移等「判断即写入」 | **单条 SQL 原子完成，无需先读**，天然跨实例；首选用于热点计数 |
| **唯一约束** | `uk_(tenant_id, code)` | 唯一业务键、幂等流水、防重复创建 | 并发重复写只有一个成功，其余捕获 `DuplicateKeyException` 转幂等 |
| **单写者 / 串行队列** | 热点聚合路由到单一消费者（MQ 分区 / 单线程） | 极高频热点（如全局计数器） | 引入顺序与消费者恢复复杂度；仅热点用 |
| **分布式锁（Redis）** | `SET NX` 租约 | 跨实例且无法用上述原子操作的复杂临界区 | 需处理锁过期 / 误删 / 脑裂；能不用就不用，优先条件更新 |

> **业界共识**（Spring、Microsoft、AWS 等官方指南一致）：默认乐观并发；仅在「冲突率极高导致重试代价超过锁代价」且「能严格控制事务长度与加锁顺序」时，才考虑悲观锁，且必须用 `SKIP LOCKED` / 统一加锁顺序 / 短事务兜底。Bone 业务层不提供 `FOR UPDATE` 通道，故直接禁用。

#### 8.4.4 配额 / 计数类热点（iam_tenant 配额案例）

`TenantQuotaEnforcer` 这类「计数 → 判断 → 插入」场景，**不要**用 `FOR UPDATE` 串行段，也不要只做单 JVM 锁（跨实例失效）。正确做法：

```sql
-- 原子条件更新：DB 端单语句完成「读+判+写」，跨实例安全，无锁
UPDATE iam_tenant
   SET quota_used = quota_used + 1
 WHERE id = :tenantId AND tenant_id = :tenantId
   AND quota_used + 1 <= quota_limit;   -- 条件不满足 = 超额，affected=0
```

应用层判 `affected == 0` → 抛 `QuotaExceededException`；满足则继续插入业务行（同一事务）。这比「`SELECT ... FOR UPDATE` 后 `INSERT`」简单、无死锁、跨副本有效。

#### 8.4.5 例外：SDK 内部 `ColumnAllocator`

`bone-metadata-sdk` 的 `ColumnAllocationRepository` / `ColumnAllocator` 用 `FOR UPDATE SKIP LOCKED` 分配元数据列索引（`MAX(column_index)+1` 防重），是**框架自有能力**，命中 `sdk-persistence-bypass-baseline.json` 已登记通道，**不在禁止范围**。业务代码**不得新增 JDBC 出站端口引入 `FOR UPDATE`**（受同一基线约束，属 L3，需架构师审批）。

#### 8.4.6 自查 / 门禁

- 代码评审 / 夜间复核：在 `**/application/**`、`**/infrastructure/**`、`**/adapter/**` 搜 `FOR UPDATE`，命中且非 SDK `ColumnAllocator` / `ColumnAllocationRepository` → **硬约束违反**，回滚。
- 新聚合默认带 `version` 列（见 §1）；缺失 `@Version` 的聚合在并发写场景下会被记为「未声明冲突策略」。

## 10. 安全注意事项

- **默认密码**：`admin` / `123456`，首次部署后**必须**修改。
- **认证**：Spring Security 6 + JWT（JJWT 0.12.x），需关注 token 有效期与签名密钥；SA-Token 仅在 BOM 中声明，未实际启用。
- **数据库密码**：部分 `application.yml` 中硬编码了明文密码，生产环境**必须**改为环境变量或配置中心注入。
- **Redis 密码**：同样存在明文配置，需通过外部化配置处理。
- **API 文档**：SpringDoc 在生产环境建议关闭或增加认证拦截（`knife4j` 或 Spring Security）。
- **CORS**：前端微应用开发服务器开启了跨域头，生产环境需收紧为明确域名白名单。
- **密钥扫描现状**：`scripts/scan-secrets.sh` / `scripts/check.sh` 可本地执行；HC-004 的**实测状态以 [Bone-DDD G-1.7](<../architecture/Bone-DDD-最终实践方案.md#hc-hard-constraints>) 为唯一真源**，不得宣称密钥扫描已由 CI 阻断。
