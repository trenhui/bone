# 写端点授权收敛报告（存量缺口 68 → 0）

> 状态：**已全部落地** · 最后更新：2026-10-03
> 门禁：`scripts/check-controller-authorization.py` · 基线：`controller-authorization-baseline.json`（**0 条**）

---

## 一、这份文档解决什么问题

平台各模块的 `SecurityConfig` 统一是 `anyRequest().authenticated()` —— **认证强制、授权不强制**。
后果：任何登录用户都能调用没有 `@PreAuthorize` 的写端点。

门禁把这条约定变成机器可校验规则（写端点必须有 `@PreAuthorize`）。首版跑出**存量缺口 68 条**，
经三轮收敛（自动推导 → 权限模型裁定 → 逐条读业务实现复核），**基线已归零**。

**归零的含义**：仓库内每一个 `@Post/@Put/@Patch/@Delete` 端点，要么挂了 `@PreAuthorize`，
要么在门禁脚本里以**带理由的豁免**显式登记。两种情况都是机器可校验的，不存在"没人管的端点"。

### 2.2 第二批：补齐既有码名共识（integration 域，基线 43 → 29）

**证据**：前端 `bonePermissionCodes.ts` 早已定义 `integration:flows:read` / `flows:write` /
`connectors:write`，但后端 `DefaultPermissionCodes` 的 60 个码里**没有** `integration:` 前缀。
这说明前后端**已就码名达成共识，只差后端未登记 + 控制器未挂** —— 不是新决策，是补齐漂移。

| 控制器 | 采用码 | 端点数 |
|--------|-------|-------|
| `FlowController` | `integration:flows:write` | 6 |
| `ConnectorController` | `integration:connectors:write` | 6 |
| `MonitorController` | `integration:executions:write` | 2 |

**执行 / 重试为何合并为一个码**（原提案是拆 `executions:write` + `executions:retry`）：
两者调用同一个 `ExecuteFlowApplicationService.handle`，输入同为 `(flowId, inputData)`，
权限边界完全一致。SoD 要拆的是"审批 vs 提交"这类**决策权分离**，不是同一动作的多个入口。

**Connector `test` 归`connectors:write` 而非 `executions:write`**：读了服务实现后确认
`test` 只做连通性探测（`ConnectorTestService`），**不触发任何流程执行**。挂 executions 码会
让"能改连接器的人"被误判为"能触发集成执行"。

### 2.3 第三批：studio-generator 细粒度分权（基线 29 → 16）

选**方案 A（细粒度 5 码）**而非单一 `generator:write`：数据源能连真实库，爆炸半径与模板编辑差一个量级。

| 码 | 覆盖端点 | 租户管理员 |
|----|---------|-----------|
| `generator:templates:write` | `CodeTemplateController` 4个写端点 | 授予 |
| `generator:datasources:write` | `DataSourceController` create/update/delete/test-connection | 授予 |
| `generator:datasources:sync` | `tables:sync` / `tables:repair-columns` / `GeneratorShortcutController#syncTableMetadata` | **不授予** |
| `generator:codegen:write` | `CodeGenerationController` + 快捷生成 | 授予 |
| `generator:admin:write` | `StudioGeneratorAdminController#repairEntityNames`（批量改名） | **不授予** |

**`datasources:sync` 为何独立成码**（读实现后修正了初稿判断）：初稿以为它会执行源库 DDL，
实际调的是 `loadTables` 而非 `execute` —— **只读源库、不改表结构**。但它会
`removeByTableMetadataId` + `batchInsert` **整表覆盖** `gen_column_metadata`，
手工加的列映射会丢失。属破坏性元数据写入，爆炸半径大于模板编辑，故保留独立码。

### 2.4 第四批：file / 数据标准 / publish / 运维端点（基线 16 → 0）

## 三、逐条豁免（每条带理由，写在门禁脚本里）

### 3.1 类级豁免（5 个 Controller）

| Controller | 理由 |
|-----------|------|
| `JwksController` | JWKS 是 OIDC/OAuth2 公开元数据端点，任何方都需无认证读取（RFC 8414） |
| `AuthController` | 认证端点本身——授权发生在这一步，再要求 `@PreAuthorize` 会形成循环依赖 |
| `E2eEntity…Controller` / `ExtensionE2eController` | e2e 专用 fixture 端点，不在生产路由注册表内 |
| `NotificationController` | 站内信写端点的授权依据是**JWT 主体归属**（服务层强制），非权限码；`userId` 不可由调用方指定。挂码反而允许跨用户读取 |

> 原健康检查控制器已在早前删除（检查并入 `SystemController#health`，是 GET、
> 不在写端点判定范围），但其类级豁免条目一直留在门禁脚本里。本轮新增的
> 「类级豁免失配」判据把它抓了出来并已清理 —— 见 §6.3。

### 3.2 方法级豁免（5 条）—— 本轮新增的门禁能力

**为什么需要方法级**：类级豁免以**文件名**匹配，命中即跳过整个文件。
`ExtensionManagementController` 有 13 个写端点已挂 scope 校验，整类豁免等于把门禁关掉。
故新增 `EXEMPT_METHODS`，键为 `文件名#METHOD:路径`，逐条写理由。

| 端点 | 理由 |
|------|------|
| `ExtensionManagementController#POST:`（执行日志上报） | 数据面上报通道：上报方是业务进程（无终端用户 JWT 可言），故不挂用户权限码。**但并非匿名可写** —— `ReporterTokenFilter` 已加机器身份校验，见 §3.4 |
| `MfaController#POST:/enroll`、`/verify` | 能力未上线，恒抛 `IAM_MFA_NOT_AVAILABLE`（HTTP 501），不读主体、不落库、**无任何状态变更** —— 不存在可授权的资源。前端不暴露入口 |
| `MeController#PUT:`、`POST:/change-password` | 自助端点：主体取自 `CurrentPrincipalPort`，`accountId` **不可由入参指定**，故无越权面。正确语义是"任何登录用户都能改自己的资料"，挂码会把"改自己的密码"变成需要额外授权，**反而降低安全性** |

**豁免键失配会显式失败**（新判据，已做负向探针）：端点不存在、已加 `@PreAuthorize`、
或路径解析规则变化时，门禁报`方法级豁免键失效` 并 exit 1。否则「豁免」会退化成
「门禁看不见这个端点」，那比缺授权更难发现。

### 3.3 控制面 `permit-unauthenticated`：默认必须拒绝（2026-10-04 收敛）

上一节修的是**数据面**（上报通道）的匿名可写。本节修的是**控制面**同一性质的缺陷 ——
上一轮列为「既有风险、非本轮引入」的最后一项。

`SecurityConfig` 里的 `permitUnauthenticated` 开关一旦打开，等于给整个 Studio 控制面
（`/api/v1/extension/**`、`/api/v1/marketplace/**`、`/api/v1/deployment-status/**`）
挂 `permitAll()`：**插件上传、部署、版本切换、配置模板全部免凭证**。危害与缺
`@PreAuthorize` 同级，只是量级更大 —— 前者是一个端点，后者是整个控制面。

原配置有两个**叠加**问题：

| # | 问题 | 后果 |
|---|------|------|
| ① | `application.yml` 写的是裸字面量 `true`，**不是 `${ENV:default}`** | 连环境变量都覆盖不了（只有占位符才被 Spring 解析），部署方唯一能做的只有改代码重新打包 |
| ② | `dev` / `in-memory` / `metadata` 三个联调 profile **均未显式声明**该键 | 全靠继承基配置的 `true`，于是「忘记配置」＝一次静默降级为全站匿名 |

原注释写着「生产环境请保持 false」—— 在这种写法下这是**空承诺**：没有任何机制保证它。
更糟的是 profile 命名（`dev`）给人留下的印象恰恰相反：以为 dev 松、prod 紧，
实际两者都是松的。

**已改为失败关闭**：

| profile | 改前 | 改后 |
|---------|------|------|
| `application.yml`（基配置） | `true`（裸字面量） | `${BONE_EXTENSION_STUDIO_PERMIT_UNAUTHENTICATED:false}` |
| `in-memory` / `dev` / `metadata` | 继承 `true` | **显式** `${BONE_EXTENSION_STUDIO_PERMIT_UNAUTHENTICATED:true}` |
| `prod` | 靠 `spring.config.import` 间接继承 `metadata-mysql` 的 `false` | **显式**字面量 `false` |
| `metadata-mysql` | `false` | `false`（不变） |

三个设计要点：

- **放行成为一次有痕迹的显式动作**。联调 profile 写 `...:true` 是合规的：那正是我们希望
  的选择方式 —— 显式、可审计、`grep` 得到。R2 只约束**基配置**，因为它才决定
  「未声明该键的 profile」继承到什么。
- **单个环境变量即可关掉，无需改代码**：`BONE_EXTENSION_STUDIO_PERMIT_UNAUTHENTICATED=false`。
  CI 若要以联调 profile 跑真链路，直接注入即可。
- **`prod` 必须显式声明**。原先靠 `spring.config.import` 间接继承，而 import 是
  `optional:classpath:...` —— 键路径一旦漂移或文件改名，继承静默失效，
  生产退化为全站匿名且无人察觉。

**新增门禁** `scripts/check-security-fail-open-default.py`（本地 `check.sh` `[22/22]`，
CI `backend-quality` job 阻断），三条判据：

- **R1** 放行不得是裸字面量。裸 `true` 不可被环境变量覆盖、无法审计；
  裸 `false` 不违规 —— 拒绝即终态，不需要留逃生口。
- **R2** 基配置占位符默认值须为 `false`。
- **R3** 生产 profile 恒为字面量 `false`，不接受占位符 ——
  生产不该存在「注入环境变量即可放行」这条路径。

`src/test/resources` **整体豁免**：单测需要无 JWT 构造请求，那是测试替身而非部署配置；
纳入只会让门禁要么整体失效、要么逼测试伪造 JWT。

不用可收缩基线机制：存量 6 处已全部收敛，且本规则的安全含义是「裸 `true` 一律不允许」，
可收缩基线表达不了这种零容忍。

**六条负向探针全部通过**（`scripts/ci/probe-security-fail-open-default.py`，同 CI job 执行）：

| 探针 | 验证内容 |
|------|---------|
| N1 | 基配置改回裸 `true` ⇒ R1 精确失败并点名判据 |
| N2 | 基配置占位符默认值改回 `true` ⇒ R2 精确失败 |
| N3 | `prod` 改成占位符 ⇒ R3 精确失败 |
| N4 | 用 `git show HEAD:` 取**改动前的真实历史配置**（含裸 `true`）⇒ 被拦截 |
| N5 | 合法形态（基配置 `false` + 联调 profile 占位符 `true`）**不被误报** |
| N6 | 探针执行后仓库仍绿（无污染） |

N4 是关键一条：它用**真实回归样本**而非手写假样本，证明门禁能抓到改动前就存在的违规，
而不是只认当前磁盘状态。N5 防的是另一个方向 —— 门禁太凶会把联调 profile 也拦掉，
那样的门禁迟早被整体关掉。

### 3.4 数据面上报端点：不豁免，改为机器身份认证

上一版清单把 `POST /execution-logs:ingest` 列为「豁免但风险更高」。本轮按推荐方案 A 落地：

```
POST /api/v1/extension/execution-logs:ingest
POST /api/v1/extension/execution-logs/ingest
```

**问题**：`SecurityConfig` 对这两个路径 `permitAll()`（上报方是业务进程，不持有终端用户 JWT）。
原注释写"安全边界由网络层保障"，但该端点**确实在写库**，且请求体的
`className` / `status` / `errorMessage` 全部取自入参 —— 任何能访问该端口的人都能伪造执行日志，
污染 overview 看板与告警依据。这与「MeController 写自己的数据」性质完全不同，不能同案豁免。

**业界标准分工**：控制面（人操作扩展）用用户权限码，数据面（机器上报）用机器身份
（共享密钥 / mTLS / 网关ACL）。三者中共享密钥成本最低，且不要求上报方持有任何用户凭证。

| 侧 | 构件 | 说明 |
|----|------|------|
| studio | `ReporterTokenFilter` | 只拦两个 ingest 路径的 POST；校验不通过 → 401/503 + JSON 错误体，**不进业务方法** |
| studio | `ReporterTokenValidator`（domain 端口） | 判定逻辑收进可替换端口，不混进 `SecurityConfig`（配置类无法单测） |
| studio | `SharedSecretReporterTokenValidator` | 常量时间比对（`MessageDigest.isEqual`），避免时序侧信道 |
| studio | `bone.extension.studio.security.reporter-token` | 机器身份共享密钥，生产经 `BONE_EXTENSION_REPORTER_TOKEN` 注入 |
| studio | `bone.extension.studio.security.reporter-auth-required` | **默认 `true` = 失败关闭**，详见 §3.4.1 |
| SDK | `bone.extension.studio.report.token` → `X-Reporter-Token` 头 | 缺配置时 WARN 一次，且**不再发出注定被拒的请求** |

**失败关闭**：校验不通过直接 401/503 且**不落库**。测试断言的是「`filterChain` 是否被调用」
而非仅状态码 —— 一个「先写库再返回 401」的实现同样能返回 401，只断言状态码抓不到。

单元测试 18 条全绿（`ReporterTokenFilterTest` 11 + `SharedSecretReporterTokenValidatorTest` 7）。

#### 3.4.1 令牌未配置时必须**拒绝**而非放行（本轮修正的自身缺陷）

首版实现里，令牌未配置时 `isAcceptable()` 直接 `return true`，仅打一条 WARN。
**这等于把上一节刚修掉的匿名可写又放回来了**：安全配置的默认若是「放行」，那么
「忘记配置」就是一次**静默降级** —— 端点退化为匿名可写，且只有一条 WARN 日志，
足够被忽略；后果是执行日志被无声伪造。

业界安全配置的默认必须是**拒绝**（Kubernetes webhook secret、Vault AppRole、内部服务间
mTLS 都是这个取向）。正确的默认行为是：

| 场景 | 行为 | 上报方看到 |
|------|------|-----------|
| 已配置密钥 + 令牌正确 | 放行 | 200 |
| 已配置密钥 + 令牌错/缺失 | **401** + `EXTENSION_REPORTER_TOKEN_INVALID` | 「我该查自己的密钥」 |
| 未配置密钥（默认） | **503** + `EXTENSION_REPORTER_TOKEN_NOT_CONFIGURED` | 「我该去改部署配置」 |
| 未配置密钥 + 显式 `reporter-auth-required=false` | 放行（仅本地联调） | 200 |

- **503 与 401 必须分开**。前者是服务端部署问题（上报方补令牌无用），后者是上报方身份问题
  （去查自己的密钥）。合成一个码会让排障方向完全搞反，故 domain 端口增加了 `isConfigured()`。
- 未配置且要求校验时日志级别从 `WARN` 提到 **`ERROR`**：这不是「需要留意」，而是
  「上报功能当前不可用」，用 WARN 会混在常规噪声里被忽略。
- 上报方主动带了令牌、但服务端没配置 ⇒ 照样拒绝（503）。此时放行等于恢复匿名可写。
- SDK 侧配对：令牌未配置时**直接短路不发请求**（`channelUsable=false`）。
  否则每次上报都白跑一次网络往返并刷 WARN，把真正的根因淹没在重复日志里。

`reporter-auth-required` 默认 `true`，本地联调需**显式**经环境变量置 `false`
（`BONE_EXTENSION_REPORTER_AUTH_REQUIRED=false`）——把「拒绝」改成「放行」必须是一次
有痕迹的动作，不能是默认值。

### 3.5 运维端点为何不豁免而挂码

`SystemController` 的 deploy / upgrade / restart / shutdown 当前恒返回 501。
**但仍预挂 `sys:ops:execute`**：这四个动作一旦落地就直接操作运行中的实例，误调用会终止服务，
爆炸半径大于其他所有写操作。等实现时再补授权，必然出现「实现 PR 加了端点却漏了 `@PreAuthorize`」
这个真实漏法。**门禁先在位，实现时不必再补。**

- **只授超管，不授租户管理员**（`TenantAdminBootstrapSupport` javadoc 已记录理由）。
- 这与 `masterdata:standards:write` / `generator:*` 属同一原则：**跨域高危能力与平台基础设施不授出**。

## 四、权限码四层真源

改动任一 `@PreAuthorize` 都必须在四处同步，漏一处会导致**所有用户 403**（没人有这个码）：

| # | 层 | 文件 |
|---|-----|------|

  （`Detected Java version 21.0.12.1`）

> **一处需要纠正的判断**：上一轮我把 ArchUnit 的 `class file version 65.0` 失败归因为
> 「本机只有 JDK 17、项目需 21」的环境问题。**该结论是错的** —— 本机装有 Temurin 21，
> `javac -version` 与 `java -version` 都是 `21.0.12.1`，`~/.m2/toolchains.xml`（2026-10-03 创建）
> 也已正确指向它。真实原因是 `~/.zshrc:6` 硬编码
> `export JAVA_HOME=.../ms-17.0.16`，使交互式 shell 下 Maven 跑在 JDK 17 上。
> **教训**：报错信息里出现"版本不够"的字样时，在断定"环境缺版本"之前必须先实测
> `java -version` / `javac -version` / `mvn -v` 三者 —— 它们可能互不一致，
> 而"环境问题"是一个能立刻停掉追问、且几乎总是错的归因。

> classpath 构造要点（独立 javac 备用路径）：`~/.m2` 下同一 artifact 有几十个版本，
> 全量塞进去会同时混入 `javax.mail`/`jakarta.mail` 与多版 spring，产生**数十条假错误**（实测踩过）。
> 正解是按 artifact 目录**只取最高版本**（3124 jar），并按文件名首 2 字节 `PK` +
> 末尾 64KB 内的 EOCD 记录剔除截断/空 jar（本机有 5 个坏 jar，含 0 字节与截断的
> `spring-core-6.0.5.jar`）。

## 六、门禁脚本本轮增强

1. **方法级豁免**（`EXEMPT_METHODS`）+ 键失配判据。
2. **类级豁免失配判据**（§3.1 的健康检查控制器案例）：控制器被删/改名后条目会静默留下；
   日后同名文件重建会**白继承豁免**而不被检查。条目失配即报错。
3. **基线键改为短键** `文件名#METHOD:路径`：原先含仓库相对目录，一次目录调整（如
   `bone-platform/bone-iam/` → `bone-platform/iam/`）会让整份基线失配、引发数十条假红灯。
   短键让基线只随**授权语义**变化而失败。旧全路径键仍兼容读取。
4. **`--baseline` 重生成会带上 `exempt_methods`**，豁免在基线文件里可见（真源仍在脚本）。
