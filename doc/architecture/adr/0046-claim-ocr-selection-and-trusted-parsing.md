## 背景

智能理赔需要从理赔材料（身份证、银行卡、医疗发票、费用清单、病历、出院记录、保单等）中提取可信结构化数据进入理赔流程。初版选型结论（PaddleOCR 唯一主引擎 + Jev 为最终判定器）方向正确但不够严谨。评审指出三条必须修正的偏差：

1. 不应预设单一主引擎——传统 OCR、端到端文档 VLM、专用票据模型须按票种分别选型；
2. Jev（或任意模型置信度）不是 OCR 结果正确性的最终判定器，必须组合 OCR 置信度、字段规则校验、交叉识别、业务一致性校验；
3. 不应以单一引擎处理所有理赔材料，不同票种版式与准确性要求差异巨大。

此外补充了版本升级（PaddleOCR 已到 3.7.x / PaddleOCR-VL-1.6）、GLM-OCR 提至第一梯队及其许可注意（代码 Apache-2.0 / 模型 MIT / PP-DocLayoutV3 各自许可）、LightOnOCR-3 不应仅作烂图兜底等修正。

## 决策

智能理赔 OCR 采用如下已采纳方案：

- **选型分层**：第一梯队必须进入 PoC——PaddleOCR 3.7.x（基础底座：PP-OCRv6 + PP-StructureV3 + PaddleOCR-VL-1.6）、GLM-OCR（VLM 主力候选）、MiniCPM-OCR 1.0 + Jev（质量评估候选）；第二梯队专项验证——LightOnOCR-3、Qwen3-VL、RapidOCR。
- **Jev 定位**：质量评估模型，**非**唯一质量闸门；AUROC 不等于正确率，须用真实样本标定阈值、按票种/字段/风险分级，**关键字段仍需独立校验机制**。
- **架构**：七层管线（接入 → 预处理分类 → 多引擎识别 → 结构化抽取 → 可信度校验 → 决策路由 → 理赔业务层），遵循「专用识别 + 通用解析 + 字段级可信度 + 规则校验 + 人工审核」。
- **可信度机制**：五层（L1 OCR 置信度 / L2 规则校验 / L3 多模型交叉 / L4 业务一致性 / L5 原图及人工复核）；可信度须**字段级**而非文档级；不设全局 0.95 阈值。
- **证据链**：每个字段保存值、原文、坐标、页码、引擎、confidence（须标注来源）、校验状态、复核状态。
- **DDD 边界**：OCR 作为独立领域边界（`OcrEngine` / `OcrProvider` / `DocumentParser` / `OcrQualityEvaluator` / `FieldValidationRule` / `ReviewPolicy`），OCR 模块不承担保险责任判断。
- **落地路线**：阶段一（1~2 周）标准基础能力 → 阶段二（2~3 周）可信 OCR → 阶段三（3~5 周）理赔领域适配。
- **PoC 第一优先级指标**：关键字段错误放行率；验收目标关键金额/证件号字段准确率 ≥99.9%，自动通过字段错误率 ≤0.01%，并须满足统计口径与样本量纪律。

## 理由

- 理赔材料票种多、金额即钱，**数字幻觉（VLM 顺手改数字）是致命风险**，故拒绝「单一引擎 + 单一置信度判定」，改用分层选型与多层次校验组合。
- 医疗/保险数据敏感，倾向**自托管开源**满足不出域合规；PaddleOCR 与 GLM-OCR 均支持自托管且中文/票据能力强。
- 把 OCR 识别与理赔语义理解分离、保留字段级证据链，保障可审计、可追溯，契合金融合规要求。
- 以「关键字段错误放行率」而非「OCR 准确率」为第一指标，更贴合业务价值（自动放行 10000 个金额字段中有 2 个错 = 0.02% 放行率，比单报 99% 准确率更有意义）。

## 后果

### 正面

- 选型不再依赖单一模型，降低单点失效与厂商锁定风险。
- 字段级可信度 + 五层校验显著提升金额/证件等关键字段的可靠性。
- OCR 独立领域边界使后续换模型、加票种、接商业 OCR 不影响理赔核心域。

### 负面 / 风险

- 多引擎 + 规则 + 交叉校验带来更高工程复杂度与推理成本，须靠阶段二质量控制服务收敛。
- 通用文档解析榜单分（如 OmniDocBench 96.33）**不等于**理赔字段级准确率，所有能力须以真实脱敏样本自证，不能预置结论。
- 自托管降低外流风险但不等于满足全部合规要求，云端 API 使用须按部署环境与数据协议单独裁定。
- 关键字段 ≥99.9% 准确率目标须以充分样本量与置信区间支撑，小样本零错误不可宣称达标。

## 备选方案

| 方案 | 未采纳原因 |
|------|------------|
| 单一 PaddleOCR 主引擎 + Jev 终判 | 评审指出为过度简化：忽略票种差异、Jev 非终判、通用榜单≠字段准确率 |
| 直接采购商业 OCR API 作主流程 | 医疗/保险数据出域合规风险；仅可在非敏感件或交叉校验场景按协议使用 |
| 自训通用 OCR 大模型 | 阶段一~三均不优先；应先建标准能力与可信机制，领域适配以微调/模板为主 |

## 合规与迁移

- 本 ADR 为架构选型决策，不改动现有代码与门禁（HC 表不受影响）。
- 首个落地动作在阶段一：建立真实票据 Ground Truth 数据集、统一字段 Schema 与识别接口、产出 OCR 模型评测报告与标准化 OCR 服务。
- 引入任何第三方模型权重/代码前，须核对各自许可证（GLM-OCR 代码 Apache-2.0 / 模型 MIT / PP-DocLayoutV3 各自许可）。

## 实施状态（2026-11-06）

**已接受并已落地骨架**，代码位于 `bone-ai/bone-ai-document` 模块，65 项单测全绿（含 `ArchitectureTest` DDD 门禁）。

- 已实现：L2 确定性字段校验规则（金额格式/日期/身份证校验位/金额大小写一致性）、L3 多模型交叉校验、按风险分级标定的复核阈值（`RiskThreshold` + `DefaultReviewPolicy` 重写）、`TrustedOcrEngine` 可选次引擎接入、真实 `HttpOcrClient` 适配器装配（默认关闭）。
- 待续：真实 Jev 质量评估器、票据版式模板、`riskThresholds` 样本标定、多页定位、端到端 PoC（部署服务 + 开 `enabled`）。
