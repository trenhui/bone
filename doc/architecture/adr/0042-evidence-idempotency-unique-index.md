## 背景

### 1. 已落地的第一道幂等（查重）

`EvidenceTraceListener.onLlmCallRecorded` 已在插入前按 `trace_id + input_hash` 查重：

```java
if (alreadyRecorded(snapshot)) { /* 跳过落库 */ return; }
repository.insert(snapshot);
```

这挡住了**重试 / 补偿队列重放**这一类真实重复——它们到达监听器的时刻必然晚于首次落库，查重可见。动机来自 ClaimSphere §10.2「幂等消费」：重复快照会让审计链出现同一次调用的多条记录，回放与成本对账口径失真。

### 2. 但查重不是幂等，只是"大概率不重复"

查重与插入之间存在**并发窗口**：两个相同事件被两个线程同时处理时，双方都查不到对方未提交的行，于是双写。当前 Spring 进程内事件是同步单线程投递，该窗口实际不可达；但：

- 未来事件通道换成 MQ（集中式网关演进时）即引入多消费者并发；
- 补偿队列 / 人工重放接口可能主动并发投递。

**用「现在不会发生」当作保证，是把风险留给下一个人。**

### 3. 正解是数据库唯一约束，不是更强的内存判据

| 方案 | 能否兜住并发 | 评价 |
|------|------------|------|
| 内存 LRU 去重（已评估并否决） | 否 | 跨重启失效，还可能吞掉合法重试，属"假解决" |
| 加分布式锁 | 是 | 为一条日志级写入引入 Redis 依赖（L3），代价远大于收益 |
| **`(trace_id, input_hash)` 唯一索引** | **是** | 数据库天然串行化判重，零新依赖，且语义即"一次调用一条证据" |

唯一索引同时是**业务不变量的声明**：同一次调用（同输入）只能有一条证据。这个不变量本来就存在，只是此前没在存储层表达。

## 决策（待批准）

1. `bone-init.sql` 中 `ai_trace_snapshot` 增加唯一索引：

   ```sql
   UNIQUE KEY uk_ai_trace_snapshot_trace_hash (trace_id, input_hash, deleted)
   ```

   含 `deleted` 与表内既有唯一键风格一致（软删后可重新落证，避免软删行永久占用唯一位）。

2. `EvidenceTraceListener` 捕获重复键异常，转为**幂等跳过**（记 info 日志，不抛、不算故障）：

   ```java
   try { repository.insert(snapshot); }
   catch (DuplicateKeyException e) { log.info("证据并发重复，唯一索引兜底跳过: traceId={}", ...); }
   ```

   查重逻辑保留为快路径（多数重复无需触库写）。

3. 增量迁移脚本走 `scripts/migration/`，遵循《ADR-生产数据库增量迁移策略》；线上表加唯一索引前须先跑一次重复数据巡检（`SELECT trace_id, input_hash, COUNT(*) ... HAVING COUNT(*) > 1`），有历史重复需人工裁定清理策略——**这是本提案唯一需要人工判断的环节**。

## 影响与代价

- **正面**：事件消费幂等从"大概率"变成"由存储保证"；MQ 化改造的前置条件提前落地；重复数据被结构上禁止。
- **代价**：一次线上加唯一索引的 DDL 窗口（低数据量表，预计秒级）；需一次历史重复巡检。
- **不做的影响**：MQ 化后重复事件会污染审计口径，且问题在数月后才以"对账不平"的形式暴露，定位成本高。

## 替代方案

- **只保留查重、不建索引**：维持现状。否决理由见背景 2/3——窗口是真实存在的，只是尚未被触发。
- **用 Redis 分布式锁**：否决。为低频写入引入缓存依赖与运维面，收益与成本不匹配。
