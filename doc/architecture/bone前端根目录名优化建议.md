# 📁 Bone 前端根目录名优化建议

## 🎯 当前状态与优化目标

当前前端根目录使用 `bone-frontend/` 命名。基于对项目整体架构和业界最佳实践的分析，我们建议对前端根目录名进行优化，以实现以下目标：

1. **保持与后端命名一致性**：遵循后端的命名规范和风格
2. **提升命名简洁性**：减少冗余词汇，增强可读性
3. **符合工程化标准**：遵循前端工程化最佳实践
4. **支持多端扩展**：为未来可能的多端应用预留空间

## 🔍 后端命名规范分析

从后端工程结构文档中可以看到，Bone平台采用了清晰的分层架构：

```
com.bone
├── framework/           # 框架层
├── engine/             # 引擎层
├── platform/           # 平台层
├── business/           # 业务层
├── gateway/            # 网关层
├── starter/            # Starter层
├── client/             # 客户端层
└── tool/               # 工具层
```

后端各模块直接使用功能名称，没有重复添加"bone-"前缀，这体现了项目的命名简洁性原则。

## 💡 优化建议

### 建议的前端根目录名

**`frontend/`** - 推荐使用此名称

### 替代方案

1. **`bone-client/`** - 如果需要强调其作为客户端的角色
2. **`web-client/`** - 如果明确聚焦于Web端
3. **`bone-web/`** - 与后端的bone-web模块保持一定关联

## 📋 推荐理由

1. **简洁性**：`frontend/` 比 `bone-frontend/` 更简洁，去除了冗余的"bone-"前缀

2. **一致性**：与业内常见的前端目录命名实践一致（如Nest.js、Spring等框架的前端部分）

3. **清晰度**：直接表达了其作为前端代码仓库的性质

4. **与后端的协调**：虽然后端没有使用"bone-"前缀，但前端使用`frontend/`作为独立目录，可以清晰区分前后端代码

5. **扩展性**：不限制于特定前端技术栈或平台，为未来可能的扩展预留空间

## 🔄 迁移注意事项

如果决定采纳此建议并进行目录重命名，请考虑以下事项：

1. **修改所有引用路径**：更新所有配置文件、脚本和文档中对`bone-frontend/`的引用

2. **更新版本控制系统**：如果使用Git，考虑使用`git mv`命令以保留文件历史

3. **CI/CD流程调整**：检查并更新构建脚本和部署配置

4. **开发环境配置**：确保IDE和开发工具中的路径配置得到更新

## 📝 结论

建议将前端根目录从 `bone-frontend/` 重命名为 `frontend/`，以提升命名的简洁性、一致性和清晰度，同时与项目整体架构保持协调。
