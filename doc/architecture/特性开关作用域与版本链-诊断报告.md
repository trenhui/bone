# 诊断报告：特性开关的作用域键与版本链

> **状态**：**待产品 / 架构拍板**（本文只给方案对比与判据，不含已落地的字段变更）
> **日期**：2026-11-03
> **相关代码**：`t_feature_toggle` / `FeatureToggle` / `FeatureTenantToggleService` / `AutoApprovalApplicationService`
> **本文定位**：把「要不要加作用域键与版本链」从口头讨论变成可决策的方案对比。
> **注意**：本文**不建议**现在动实体字段 —— 理由见 §5「为什么现在不该加」。

## 1. 结论先行（TL;DR）

| 项 | 结论 |
|----|------|
| **作用域键（`scope_type`/`scope_value`）** | **暂不加**。当前只有 2 个特性键、2 个调用点、且都是租户级，无第二个作用域维度的实际需求。提前加 = 造一个没有消费方的字段（典型「配了不生效」隐患）。 |
| **版本链（`effective_from`/`effective_to`）** | **暂不加**。现有 `@Version` 乐观锁 + `updated_at` + `remark` 已能回答「现在是什么状态、谁改的、为什么改」；真正的版本链需求是「**回滚到历史配置**」与「**定时生效**」，这两个都还没有产品诉求。 |
| **真正该补的（低成本、高价值）** | ① **读侧「配了但不生效」的可见性**（配置存在 ≠ 生效）；② **改配置的审计留痕**（谁、何时、从什么改成什么）。这两项都不需要 DDL 变更。 |
| **需拍板的问题** | 见 §6 的 3 个问题。在回答之前，任何字段级改动都属于「按想象建模」。 |

## 3. 缺口一：作用域键

### 3.1 需求是什么

「同一个特性，不同作用域要不同状态」时，需要在 `(tenant_id, feature_key)` 之外再加一维，例如：

- **渠道级**：`AUTO_APPROVE` 在「线上渠道」开、在「代运营渠道」关
- **产品/险种级**：`AUTO_APPROVE` 对「车险」开、对「团险」关
- **地域/机构级**：`AUTO_APPROVE` 对「华东机构」开

### 3.2 业界标准做法对比

业界主流特性开关系统（LaunchDarkly / Unleash / OpenFeature / 自研开关表）在这块有两条路线：

| 方案 | 结构 | 优点 | 缺点 | 本仓适配性 |
|------|------|------|------|-----------|
| **A. 复合键**（推荐） | `scope_key` 是一个**规范化字符串**，如 `channel:ONLINE` / `channel:AGENCY`；UK = `(tenant_id, feature_key, scope_key)` | ① 一列搞定，任意维度可扩展；② UK 简单；③ 不改消费方签名（只在拼 key 处聚合）；④ 迁移成本低 | 语义靠 key 命名约定，无强类型 | **高** —— 消费方签名不变，scope 缺失时用默认 scope |
| **B. 多列正交** | `scope_type`（枚举）+ `scope_value`（字符串），UK = `(tenant_id, feature_key, scope_type, scope_value)` | 类型安全、scope_type 可枚举校验 | 加一个维度要加一行 DDL + 改枚举；空值语义（= 全局）需特殊处理 | 中 —— 改动面大，但更显式 |
| **C. 独立 scope 表** | `t_feature_toggle` 引用 `t_toggle_scope(id, type, value)` | scope 可复用、可挂元数据 | 两表 JOIN，SDK 仓储下写路径复杂 | 低 —— 当前量级不值得 |

**业界共识（可引用的通行做法）**：
- Unleash / 自研表的通行做法是**复合 scope 键**（方案 A），而非多列正交 —— 理由是「维度会持续增长」，多列正交每次加维度都要 DDL + 迁移 + 回填。
- **但前提是已经有第 2、第 3 个作用域的真实需求**。没有需求时加维度，是典型的「为想象中的未来建模」。

### 3.3 本仓现在该不该加

**不该。** 判据（可复核）：

1. **消费方只有 2 个调用点**，且都是租户级 —— 没有任何一个调用点需要区分第二个维度。
2. **开关只有 2 个特性键**（`AUTO_APPROVE` / `TRIAGE_LIMITS`）—— 都是「租户级开关」语义。
3. **活库 0 行** —— 说明连租户级配置都还没开始用；此时加维度键，是在给一张空表设计索引。
4. **`config_json` 已经是可扩展位** —— 若临时出现「同租户内按渠道区分」的真实需求，**先试 `config_json`**（如 `{"scope":{"channel":"ONLINE"}}`），零 DDL 成本。真的稳定了、且需要 DB 层约束时再升维。

> **⚠️ 关键风险提示**：加 scope 维度后，「某租户配了 `channel:ONLINE` 但没配 `channel:AGENCY`」的**回退语义**必须显式定义（取全局？取该租户的默认 scope？取关闭？）。
> 这是一个**业务决策**，不是技术细节 —— 不同选择会导致「部分渠道意外放量」。资金类开关（`AUTO_APPROVE`）尤其危险。

## 4. 缺口二：版本链

### 4.1 需求是什么

| 能力 | 现状能否满足 | 说明 |
|------|-------------|------|
| 「现在是什么状态」 | ✅ 能 | 直接读行 |
| 「谁改的、何时改的」 | ⚠️ 部分 | 有 `updated_by` / `updated_at`，但**改前的值没留** |
| 「为什么改」 | ⚠️ 部分 | 有 `remark`（人工填写），无结构化变更原因码 |
| 「**回滚到 3 天前的配置**」 | ❌ 不能 | 无历史表 |
| 「**明天 10:00 自动生效**」 | ❌ 不能 | 无 `effective_from` |
| 「**一条配置同时承载多租户**（如按保司维度批量下发的开关）」 | ❌ 不能 | 只能一行一租户 |

### 4.2 业界标准做法对比

| 方案 | 结构 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **A. 事件流（推荐给「审计」）** | 独立 `t_feature_toggle_history`（append-only）：`toggle_id, tenant_id, feature_key, from_state, to_state, rollout_pct, config_json, changed_by, changed_at, reason_code` | ① 天然支持回滚（读历史最后一条）；② 审计完整；③ **不动主表结构** | 需写历史（应用层或 DB 触发器） | **本仓当前最合适** |
| **B. 主表加生效区间** | `effective_from` / `effective_to`，查询取 `NOW() BETWEEN` | 支持定时生效 | ① 时区与时钟一致性麻烦；② 「多条同时生效」需唯一约束；③ 历史行仍需归档策略 | 有「定时生效」诉求时 |
| **C. 主表加版本号 + 全量快照列** | `revision` + 若干历史列 | 简单 | 只保留 N 版，深度回滚做不到；列宽膨胀 | 不推荐 |
| **D. 引入外部开关平台**（LaunchDarkly 等） | — | 成熟的灰度/分流/审计 | 引入外部依赖与网络依赖；数据出境/合规问题 | 不适合当前阶段 |

**业界共识**：
- 「**审计 + 回滚**」→ 事件流（append-only history table），**不改主表**。这是最主流的做法（GitOps 思路：配置变更即事件，可回放）。
- 「**定时生效**」→ 才需要 B 方案的生效区间。
- 两者**不要混在一个提交里**：审计需求几乎总会先到，定时生效需求很罕见。

### 4.3 本仓现在该不该加

**暂不加 B（生效区间），但值得考虑 A（审计事件流）。** 判据：

1. **「定时生效」当前无任何诉求** —— 消费方 2 个调用点全是同步判定，没有「到点自动切」的需求。加 `effective_from` 会引入时区/时钟/唯一约束三重复杂度，收益为零。
2. **「回滚」需求可预判但未到** —— 资金类开关（`AUTO_APPROVE`）配错了确实需要快速回退，但当前 `remark` + 人工改回去已够用（0 行数据、2 个调用点）。
3. **「谁改的、从什么改成什么」是真缺口** —— 现在改了 `state`，旧值无处可查。**但这个缺口用 A 方案（事件流）补，且不动主表结构。**

> ⚠️ 注意一个**易被忽略的耦合**：本仓有 `t_claim_flow_config`（同样的「生效版本」问题）的既有解法 ——
> **生成列 + 唯一键**：`active_key = IF(active_flag=1 AND deleted=0, flow_key, NULL)` + `UNIQUE(tenant_id, active_key)`。
> 如果将来 `t_feature_toggle` 真要引入多版本，**用同一套手法**（MySQL 无 partial unique index，唯一索引不视 NULL 为重复），
> 不要自己发明第二套「生效行」机制。

## 5. 为什么现在不该加字段（自主权分级视角）

按 [AGENTS.md](../../../AGENTS.md) 的自主权分级：

| 动作 | 级别 | 是否可由 AI 自主执行 |
|------|------|---------------------|
| 加 `scope_type`/`scope_value` 列 | **L3（DDL）** | ❌ 需架构师审批 |
| 加 `effective_from`/`effective_to` 列 | **L3（DDL）** | ❌ 需架构师审批 |
| 改实体字段 + 仓储签名 + 消费方 | **L2（业务逻辑）** | ❌ 需双人 Review |
| 改 `remark` 语义 / 加 WARN 日志 | L1～L2 | ⚠️ 需确认 |

而且**更根本的问题是：加字段本身不是需求**。现在动手等于：
- 表结构承担了「想象中的未来」⇒ 将来真要改时还要再改一次；
- 消费方签名被迫改动 ⇒ 而现在**没有任何消费方需要这个改动**；
- **「配了不生效」的面变大**：加了 scope 列却没有配套的回退语义定义，比不加更危险。

**这就是「先问消费方，再定字段」的由来**：不是流程保守，而是**没有消费方的字段就是纯负债**。

## 6. 需要拍板的 3 个问题

> 这三个问题的答案**直接决定**要不要动 DDL。回答前不动。

### Q1. 特性开关是否需要「租户以内」的第二个作用域维度？

- **不需要** → 维持现状（推荐）。临时需求走 `config_json`，稳定后再评估升维。
- **需要，且是渠道/险种/机构这类枚举** → 走 §3.2 方案 A（复合 `scope_key`），**同时必须回答 Q2**。
- **需要，且维度不可预知** → 仍走方案 A（这正是复合键优于多列正交的理由）。

### Q2. 若引入作用域，「某租户只配了部分作用域」时的回退语义是什么？

| 选项 | 行为 | 风险 |
|------|------|------|
| (a) 回落到该租户的默认 scope（`scope_key=''`） | 部分作用域生效，未配的用默认 | 默认 scope 自身必须是显式配置，否则又回到「继承全局」 |
| (b) 回落到全局 | 同上但跨租户 | **资金类开关风险最高**：一个租户只配了「关」，未配的渠道会「开」 |
| (c) 回落为「关闭」（fail-closed） | 未配作用域一律关 | 最安全，但灰度体验差（每个渠道都要显式配） |

**推荐 (c) 作为默认值**（与本仓既有 fail-closed 口径一致：`FeatureToggle.isOn` 非 `ENABLED` 即关闭）。

### Q3. 是否需要「定时生效」或「按保司维度批量下发」？

- **都不需要** → 不引入 `effective_*`（当前判断）。
- **需要定时生效** → 走 §4.2 方案 B，并复用 `t_claim_flow_config` 的「生成列 + 唯一键」手法。
- **需要批量下发** → 本质是要一个「开关集合」聚合根（`t_feature_toggle_set` + 明细行），是**另一个设计**，不是加两列能解决的。

## 7. 与本文无关、但顺带查清的两件事（避免上轮结论误导）

### 7.1 `t_claim_item.version` **不是**孤儿列（纠正上轮判断）

上轮说「`t_claim_item.version` 属无对应声明的列」。**该判断已被证伪**：

- `t_adj_liability.version` —— 实体 `AdjLiability` 上有 `@Version private Long version;`（**无** `@Column`）⇒ **是正常的 `@Version` 列**。
- `t_claim_item.version` —— `ClaimItem` 继承 `TenantAbstractEntity` → `AbstractEntity` → SDK `Entity`；`AbstractEntity` **不含** version 字段 ⇒ `ClaimItem` 确无 `@Version`。
  但 `t_claim_item` 是聚合 `ClaimCase` 的子表，其乐观锁由**聚合根 `ClaimCase` 的 `@Version`** 承担 ⇒ 子表是否需要独立 `version` 列，取决于 SDK 的级联写入语义（`@Cascade` 子集合）。

#### 7.1.1 SDK 级联写入的实际行为（2026-11-03 源码取证，答案已定）

| 取证点 | 结论 |
|--------|------|
| `TableMetadata.isVersioned()` | 「存在 `@Version` 列即启用」—— **按表判定**，不是按列 |
| `AggregateCascadeWriter.upsertChild` | 子表走 `sqlBuilder.buildDynamicUpdate(childType, child)` / `buildBatchInsert`，**不走** `BaseRepository` 的乐观锁分支 |
| `DynamicUpdateBuilder` | `if (table.isVersioned())` 才 `SET version = version + 1` + `WHERE version = :old`；`ClaimItem` 无 `@Version` ⇒ **该分支不进入** |

⇒ **`t_claim_item.version` 是一个「存在但不参与任何乐观锁」的静态列**：
子表 UPDATE 既不自增它、也不以它为条件（`WHERE` 只有主键 + 租户护栏）。
DDL 为 `bigint NOT NULL DEFAULT 0` ⇒ 依赖 DB 默认值写入。

**活库实测印证（2026-11-03）**：

| version | 行数 | created_at 区间 |
|---------|------|-----------------|
| `1` | 374 | 2026-05-11 ~ **2026-10-27** |
| `0` | 354 | **2026-10-28** ~ 2026-11-02 |

⇒ 现行代码写入的行**恒为 0**；`version=1` 的 374 行**全部是 2026-10-28 之前的历史存量**
（早期版本的实体曾在 `ClaimItem` 上挂 `@Version`，后被移除；那段期间的自增留下了 1）。
这与 SDK 取证结论**完全吻合**：自 10-28 起子表不再参与乐观锁 ⇒ 该列停止变化。

**结论：不做 L3 清理。** 理由：
1. 子集合不是独立聚合根，本来就不该有自己的乐观锁 —— 它的并发由**聚合根 `ClaimCase` 的 `@Version`** 统一承担（根保存失败 ⇒ 整个聚合不落库）。
2. 清列 = DDL 变更 = **L3，需架构师审批**。
3. **在没查清 SDK 对子表 `version` 的处理前删列，可能正好删掉级联写入所需的列**。本条已查清（见上表），但结论仍是「删它没有收益、只有风险」：留着的代价是**一个恒为 0 的死列 + 374 行历史值 1**（轻微），删掉的代价是**一次 DDL 迁移 + 一次 init 同步 + 活库 ALTER + 历史值取舍决策**（不轻），而收益仅是「表更干净」。
4. 若要清理，正确顺序是：① 先定历史 `version=1` 的 374 行怎么处理（归零？保留？—— 这是数据决策不是技术决策）→ ② 走 L3 审批 → ③ 再写迁移（含 `bone-init.sql` 同步）⇒ **不是本轮该做的事**。
