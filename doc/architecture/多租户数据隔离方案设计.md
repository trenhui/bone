# Bone 多租户数据隔离方案设计

> **文档性质**：在既有 `Bone-多租户规范.md`（上下文传递）与 ADR-0006（隔离三模式）/ ADR-0029（SDK 自动过滤）/ ADR-0038（平台模板作用域）/ ADR-0034（租户作用域显式化门禁）基础上，**补齐「哪些数据全局共享、哪些租户隔离」的跨模块分类裁决**，并对照业界最佳实践给出选型依据与风险整改清单。
> **日期**：2026-09-26
> **关联**：[Bone-多租户规范.md](./Bone-多租户规范.md)、[ADR-0006](./adr/0006-iam-tenant-isolation-modes.md)、[ADR-0029](./adr/0029-sdk-auto-tenant-filter.md)、[ADR-0038](./adr/0038-platform-model-template-and-scope.md)、[ADR-0034](./adr/0034-tenant-scope-explicitness-and-all-entry-gate.md)、[module-boundary-iam-system.md](./module-boundary-iam-system.md)

## 1. 结论先行（TL;DR）

1. **默认隔离模式 = 共享库 + 共享 Schema + `tenant_id` 行级隔离**（即 ADR-0006 的 `ROW_LEVEL`，现状已实现）。它是多租户 SaaS 的主流做法，租户密度高、成本低、迁移简单；代价是隔离强度依赖「纪律性强制」——Bone 用 SDK fail-closed（ADR-0029，已实现）把纪律下沉到框架，并用门禁守声明面（载体与实测状态见 `gate-state.json` 条目 `#16`「租户表 ↔ 实体声明」、`#12b`「租户边界」；**这两条目前都还不是 CI 阻断**，故本文不宣称"已固化"）。
2. **`tenant_id = 0` 专用于「平台全局数据」**（平台注册表、权限目录、模板目录、插件市场等），与「租户未知 `null`」严格区分（见 §4）。**这不是租户，是「跨租户共享层」**；该层的可见性机制必须显式选择（见通则 T1），不能靠"默认 0"隐含。
3. **数据分类裁决（§3）**：IAM 的账号/部门/角色/菜单/审计/审计设置/策略/令牌类表、主数据租户实例层、集成流/连接/执行日志/死信、元数据租户目录 → **租户隔离**（含 `sys_config`，证据链见 §3.2）；Tenant 注册表、Permission 权限目录、主数据平台模板层、元数据平台模板、生成器/扩展 Studio 的**平台种子/市场层** → **全局共享（tenant 0）**；生成器/扩展在租户上下文命中时实际写真实租户，属「平台种子层(0) + 租户实例层」overlay（§3.6）。**`sys_*` 不再是"整族全局"**：`sys_config` 已由证据判定为租户隔离，其余 5 张判 `待裁决`（不得按默认值写成已裁决）。
4. **保留升级通道**：对金融/政企等高保障大客户，按 ADR-0006 提供 `SCHEMA_LEVEL` / `DATABASE_LEVEL` 的**逐租户升级**能力（非默认），由 `iam_tenant.isolation_mode` 开关驱动，禁止生产期无 ADR 切换。（**目标态**：ADR-0006 自述 As-Is 无 `isolation_mode` 列，落地前不得表述为已在位，见 §8 项 1 / §11.1。）
5. **整改 9 类已知风险**（§5）：`R1` 主平台 `TenantInterceptor` 无头降级 0（fail-open）；`R2` integration 存量 `tenant_id=0` 回填**与代码上线顺序可能已颠倒**（发布阻塞项）；`R3` 实体未声明 `tenantId` 的缺口清单已漂移（基线需收缩 5 条、补 3 条）；`R4/R6` 生成器/扩展 Studio 与平台种子行可见性（含 `stampTenant` 只覆盖 2 类实体）；`R5` 跨租户入口扩张；`R7` 声明门禁两处盲区（15 张无实体映射表 + 一表多映射只校验一份的假阴性）；`R8` 租户离场清除仅覆盖 IAM；`R9` 通知/血缘等表**连 `tenant_id` 列都没有**（缺列型缺口，与 `R3` 互补）。
6. **三条跨模块通则**（本方案对 §3 全部裁决的收敛，也是后续新表准入的判据）：
   - **T1 平台共享行可见性二选一**：凡「平台种子/目录行 + 租户行」共存的数据，**要么拆表**（overlay，平台表不带租户语义 + 租户表带租户语义，先例：`mdm_reference_value` / `mdm_reference_value_tenant`），**要么整表不做租户作用域** + 走登记的只读通道（先例：`DomainTemplate`，规范 §8 约束 4）。**禁止同表混存 + 租户作用域**——SDK 注入的是严格等式 `tenant_id = :current`，0 值平台行会对真实租户**静默不可见**（实测形态见 §3.6）。也禁止新增 `tenant_id IN (0, :current)` 共享行语义（会成为第二个逃生舱）。
   - **T2 DDL 列 ≠ SDK 语义，必须显式登记**：`tenant_id` 列存在但实体不声明 ⇒ 查询无过滤（漏读风险）；实体声明但设计上是平台目录 ⇒ 0 值行不可见（隐身风险）。两种偏差都必须在 `tenant-entity-baseline.json` 里带理由登记，**不能只靠 DDL 或只靠代码**。
   - **T3 裁决必须绑定真源**：§3 的每一行裁决都要能对应到 §11 约定的四处真源（DDL、实体、baseline、门禁脚本）；裁决变更时四处同步，否则视为漂移。

## 2. 业界最佳实践对照（三种隔离模式）

| 模式 | 物理形态 | 隔离强度 | 租户密度 / 成本 | 运维复杂度 | 适用场景 |
|------|----------|----------|----------------|------------|----------|
| **DATABASE_LEVEL** 独立库 | 每租户独立数据库实例 | 最强（物理隔离，blast radius=单租户） | 最低密度、最高成本 | 高（备份/迁移/连接池按租户） | 大客户 / 强合规（金融、政务）买断式隔离 |
| **SCHEMA_LEVEL** 独立 Schema | 同库不同 schema（`tenant_a.*` / `tenant_b.*`） | 强（逻辑隔离 + 可物理拆分） | 中 | 中（DDL 多份、Flyway 按 schema 编排） | 商业版中等隔离、需要按租户导出/迁移 |
| **ROW_LEVEL** 共享表 + `tenant_id` | 同表同 schema，所有行带 `tenant_id` 判别列 | 中（依赖强制过滤，错配即串租户） | 最高密度、最低成本 | 低（单套 DDL/连接池） | 社区版 / MVP / 绝大多数 SaaS（Salesforce、大部分 B 端 SaaS 默认） |

**选型关键判据**（业界共识）：

- **隔离强度 vs 成本/密度** 是核心权衡。行级隔离把「隔离」从数据库层下沉到「应用 + 框架」层，用工程纪律换成本与弹性。
- **合规驱动例外**：受监管行业（银行、医保、政务）常要求特定大客户走 schema/库隔离，但不能因此让默认模式变复杂——因此是「按租户升级」而非「全局切换」。
- **行级隔离的三大命门**（前两条 Bone 已针对性解决，第三条是本次复核新暴露的）：
  1. **忘记带 `tenant_id`**（查询/写入漏条件）→ 静默串租户。Bone 用 SDK `TenantFilterInjector` **自动注入 + fail-closed**（`MissingTenantContextException`），且「实体声明 `tenantId` 字段」才是 SDK 认租户表的判据（DDL 有列 ≠ 识别，见 §5 `R3`，2026-09-26 实测仍有缺口）。
  2. **跨租户 IDOR**（用别人 ID 越权访问）→ Bone 用 `assertXxxBelongsToTenant` 样板 + `PlatformAccessGuard` fail-closed 拦截平台域接口。现状：`PlatformAccessGuard` 已对 `null` 拒绝（平台域第二道防线在位）；断言样板目前只是 `AccountApplicationService` 内的私有方法（`assertDeptBelongsToTenant`，2 处调用），**尚未收敛为共享工具/基类**——收敛项见 §9.9。
  3. **平台共享行被租户作用域"吃掉"**（反向失效：过滤过严而非漏过滤）→ 严格等式注入下 `tenant_id = 0` 的平台种子行对真实租户**不可见且不报错**（读到空列表）。故凡"平台种子 + 租户实例"共存，必须先按通则 T1 定机制（拆表 or 去租户作用域），见 §3.6 / §9.7。
- **共享数据的最优表达**：对「平台定义、租户只读引用 + 租户可私有扩展」的数据（如参考数据/模板），业界用 **overlay（两层叠加）** 而非把平台行塞进租户过滤——Bone 主数据 §8 约束 7 的拆分正是此实践。
- **连接池与缓存维度**：无论哪种模式，连接池、缓存 Key（`bone:{tenantId}:...`）、消息分区键（默认 `tenant_id`）都必须带租户维度，否则高密度行级隔离会在应用层串租户。

**结论**：Bone 选 ROW_LEVEL 为默认是正确且符合业界主流的；本方案在此基础上**固化分类裁决**并**保留高保障升级通道**，避免「为了个别大客户把全局改复杂」。

## 3. 数据分类裁决矩阵（全局共享 vs 租户隔离）

判据总则（§6 详述）：**用户产生的内容、PII、租户业务配置 → 租户隔离**；**平台资产、跨租户共享目录、系统运维数据 → 全局共享（tenant 0）**。

> **第一轮复核的三条硬修正**（细节见各小节）：① `sys_config` 由「全局」改判**租户隔离**（三处真源一致）；② `sys_*` 其余 5 张由「已裁决全局」改为**待 Owner 裁决**（基线登记的是 `needs-owner-decision`，不是已裁决）；③ 表名/表清单按 DDL 真源校正（`bone_application` 族、`int_execution_log`、`mdm_qcheck_*`；删除不存在的 `platform_meta_*` 与 `iam_*_ref`）。**第二轮复核的修正见 §3.0（覆盖边界）、§3.3/§3.6（状态与写入缺陷）、§5 `R7`/`R9`。**

### 3.2 bone-system（系统管理）

> **复核修订（硬修正）**：原方案写「现状 6 张表标记为 `needs-owner-decision`，本方案裁决为全局（tenant 0）」。两点都不成立：① 基线实际登记是 **`sys_config` = `pending`（已认定 per-tenant）+ 其余 5 张 = `needs-owner-decision`（证据不足、尚待裁决）**；② `sys_config` 有三处独立真源指向**租户隔离**，原方案的"全局"与它们冲突。

| 数据 | 表 | 裁决 | 落地状态 | 证据 / 依据 |
|------|----|------|------|------|
| 系统配置 | `sys_config` | **租户隔离** | 待整改（补实体声明） | DDL `UNIQUE KEY uk_sys_config_key (tenant_id, config_key)`；《7. 系统管理模块详细设计方案》§表清单同口径（`tenant_id + config_key 唯一`）；`tenant-entity-baseline.json` 记「表性质**已确认 per-tenant**」；种子数据按 `tenant_id` 写入。**原方案"平台级全局开关、非用户/租户级"不成立** |
| 系统日志 | `sys_log` | **待裁决**（Owner: bone-system） | 待裁决 | DDL 含 `tenant_id`、保留 180 天，但详设未提租户。裁决问题：运维排查是否需要跨租户视图——需跨租户 → 全局（须写明"运维视图 + 授权审计"）；仅租户自检 → 租户隔离 |

> **裁决纪律**：`待裁决` **不等于**默认全局。这 5 张表的实体都未声明 `tenantId`（DDL 有列），在裁决落地前它们**既不满足租户隔离，也没有 `by-design` 登记理由**——属 §5 `R3` 的未闭合项。裁决后二选一：租户隔离 → 补实体声明 + 存量数据归属回填（L4）；全局 → 改 `classification: by-design` 并写明「跨租户运维视图 + 授权审计」理由。
> **若确需「平台默认 + 租户覆盖」**：按通则 T1 只能**拆表**（平台默认层 + 租户覆盖层），或让平台默认层不做租户作用域。**禁止**在同一张租户作用域表里放 `tenant_id = 0` 的默认行——租户会读不到默认值且不报错（实测形态见 §3.6）。`sys_config` 现已判定租户隔离，故"平台默认值"不能靠同表 0 值行实现。

## 4. 隔离实施架构（对齐既有，非新造）

```
客户端 → 网关(JwtAuthGlobalFilter 注入 X-Tenant-Id) → JWT 解析(JwtAuthenticationFilter 写 TenantContext)
       → SDK(TenantFilterInjector 自动注入 tenant_id 谓词, fail-closed)
       → 应用层(TenantProvider 端口取租户, 不直接读上下文) → 跨租户校验(assertXxxBelongsToTenant / PlatformAccessGuard)
```

1. **信任链单一来源**：`tenant_id` 只从 JWT/网关注入头来，请求体 `tenantId` 被忽略（防越权）。
2. **`tenant_id = 0` vs `null` 是两条语义，不可混**：
   - `0` = 平台租户（特权跨租户视角，须 `platform:*` + 审计 + `disableTenantFilter()`）；
   - `null` = 租户未知（fail-closed，不兜底成 0，避免静默全租户读）。
   - `TenantProvider.currentTenantIdOrNull()` 返回 `null` 而非 0，正是为区分二者。
3. **SDK 自动过滤 + fail-closed**（ADR-0029）：租户表查询强制 `tenant_id = :_sdk_tenant_id`；上下文缺失且无可信 EQ 兜底 → 抛 `MissingTenantContextException`。逃生舱 `disableTenantFilter()` 仅限登记的平台/跨租户入口（ArchUnit 门禁约束）。**注意该保护的前提是"实体声明了 `tenantId`"**：DDL 有列而实体未声明时 SDK 直接返回、不注入也不报错——缺口清单与门禁盲区见 §5 `R3` / `R7`。
4. **IDOR 防护样板**：任何「用 ID 加载再操作」的跨聚合引用（部门、角色、应用…）必须先 `findById` 后断言 `Objects.equals(entity.getTenantId(), currentTenantId)`，不符抛 `DEPT_NOT_FOUND`/`TENANT_ACCESS_DENIED`。现状是私有方法级样板（`AccountApplicationService#assertDeptBelongsToTenant`），**建议收敛为共享断言工具/基类**（§9.9）。
5. **缓存 / 消息 / 日志带租户维度**：缓存 Key `bone:{tenantId}:...`，MQ 信封含 `tenantId` 且分区键默认 `tenant_id`，MDC 记 `tenantId`。
6. **DDL 列与 SDK 语义必须同一步**（通则 T2 的落地）：给表加 `tenant_id` 与让实体声明 `tenantId` 是**同一个决定的两半**，任何一半单独落地都会产生偏差（漏过滤 or 平台行隐身）。DDL 变更与实体声明必须在同一 Change 内完成，并在 `tenant-entity-baseline.json` 留下痕迹。

## 6. 分类决策准则（Governance Rubric）

新增数据表/实体时，按此决策树判定作用域（**顺序不可颠倒**：先答"谁产生"，再答"平台行与租户行是否共存"，最后才落基类与列）：

```
该数据是否由「某个具体租户的用户/业务」产生或专属？
├── 是 → 是否含 PII / 业务机密 / 租户私有配置？
│       ├── 是 → 租户隔离（继承 TenantAggregateRoot/TenantAbstractEntity，声明 tenantId）
│       └── 否 → 仍默认租户隔离（除非能证明是平台共享资产并留下证据）
│
└── 否（平台/跨租户资产）→ 表内是否还会出现「租户私有行」（双向混存）？
        ├── 会 → 必须按 T1 二选一：
        │       ├── 拆表 overlay：平台表（不做租户作用域）+ 租户表（做租户作用域，命名 _tenant /
        │       │   独立聚合），先例 mdm_reference_value / mdm_reference_value_tenant
        │       └── 整表不做租户作用域 + 登记的只读通道（仅当确无租户私有行）
        │       ✗ 禁止：同一张租户作用域表里放 tenant_id = 0 平台行（租户读不到且不报错）
        │
        └── 不会 → 全局共享（tenant 0）→ 是否属于以下任一类？
                ├── 租户注册表 / 权限目录 / 平台模板 / 参考数据平台值 / 插件市场
                │       → 不映射 tenant_id（首选）或 DDL 留列但**必须**在 baseline 登记理由
                └── 系统运维配置/日志（sys_* 类）→ 先裁决（租户自配 ⇒ 租户隔离），
                        不得默认按全局推进

另两条必答项（与作用域一同决定，不得留到实现期）：
  · 主访问路径的索引是否以 tenant_id 为前导列？（否 → 需说明理由或补索引）
  · 该表是否登记进租户离场清除清单？（未登记 → 新增即视为门禁缺口）
```

**铁律**：
- 租户隔离实体**必须在实体上声明 `tenantId`**（继承便捷基类或直接声明字段）——DDL 有列 ≠ SDK 识别，漏声明等于无过滤（通则 T2）。
- 全局数据**必须显式标注 `global/platform`**，**并且**在 `tenant-entity-baseline.json` / `ddl-required-columns-baseline.json` 里留下 `by-design` 理由；写面收敛到平台域权限（`platform:*`），防止「平台写」权限面扩散。
- **禁止同表混存**平台行（`tenant_id = 0`）与租户行（通则 T1）；跨租户读取一律走登记的 `disableTenantFilter()` / `@TenantScope(ALL)` 入口 + 审计。**禁止**在业务查询里手写 `tenant_id IN (0, :current)`（第二个逃生舱会弱化 fail-closed）。
- **唯一约束口径**（修正原 §9.6 的过宽表述）：租户内业务唯一键**必须含 `tenant_id`**；**全局标识不得含**（`token_hash`、平台目录 `code`、权限码等必须全局唯一）。判定问题只有一个：「两租户同名是否算冲突？」——是 → 含 `tenant_id`；否 → 保持全局唯一。

## 9. 复核优化：补充的业界最佳实践要点

> 对 §1–§8 的复核结论与优化项。复核发现的问题见 §9.8。

### 9.1 租户生命周期与离场（数据清除 / 合规擦除）
行级隔离下「删除一个租户」不是 `DROP SCHEMA`，而是**跨全部租户作用域表 `DELETE / 软删 + 硬清 WHERE tenant_id = X`**。必须配套：
- **先扩既有实现，不要重造**：`TenantDeletionGatewayAdapter.purgeTenantData()` 已在做跨表清除，但**只覆盖 IAM 7 张表**（`iam_role_permission` / `iam_account_role` / `iam_refresh_token` / `iam_audit_log` / `iam_audit_settings` / `iam_account` / `iam_role`）——integration / masterdata / metadata / system / generator / extension **一张未覆盖**。这既是 §5 `R8`，也是"离场清单会漂移"的实证。
- **Tenant Destroy Runbook**：清单的**数据源就是 §3 裁决矩阵**（避免两份清单），分批次软删→硬清，幂等、可审计、限流（避免长事务锁全表）；新增租户作用域表未登记清单即门禁失败。
- **合规擦除（GDPR / 被遗忘权）**：PII 字段支持按租户物理擦除或不可逆匿名化；与软删区分（软删可恢复、擦除销毁）。
- **级联归属校验**：租户删除前校验无悬空引用（部门/角色/集成流等），防止孤儿数据跨租户可见。

### 9.2 性能与规模治理
- **索引规约**：每个租户作用域表的「主访问索引」应以 `tenant_id` 为**前导列**，否则 `WHERE tenant_id=?` 易退化为全表扫。**实测分布**：已有 `idx_int_flow_tenant`、`idx_sys_dict_tenant`、`idx_sys_schedule_tenant` 等合规范例；反例是 `int_execution_log`（仅 `flow_id` / `status` / 时间索引）与 `sys_log`（仅 `level` / `service` / `trace_id` / `created_at`），需要补或说明理由。**注意**：现有 DDL 校验脚本只查列是否存在（`HC-008` / `#12c`），**不校验索引前导列**——故本规约需新增校验（§8 项 8 / §11）才谈得上"门禁"。
- **大租户分区**：超大规模租户可对热点表按 `tenant_id` 做 Hash/Range 分区，或触发 §1 的 `SCHEMA/DATABASE_LEVEL` 升级。
- **吵闹邻居（Noisy Neighbor）**：行级隔离共享连接池与计算，单租户重查询会波及其他租户。缓解：连接池按租户配额 / 语句超时；把 `TenantQuotaEnforcer` 从「账号/角色数」扩展到**查询成本配额**（行数/耗时）；每租户限流。

### 9.3 数据保护与备份恢复边界
- **PII 字段级加密**：账号邮箱/手机、主数据敏感字段按字段加密；高保障租户（`DATABASE_LEVEL`）启用**租户独立 KMS 密钥**，使隔离在密钥层也生效。
- **备份 / 恢复边界（重要权衡）**：共享 Schema 下**无法单租户时间点恢复**——恢复一租户必波及其他租户。缓解：① 逻辑备份带 `tenant_id` 过滤做租户级导出；② 对要求单租户恢复的大客户走 `SCHEMA/DATABASE_LEVEL`（隔离落在物理层）。该权衡须在对外 SLA 中明确，不得默认承诺单租户 PITR。

### 9.4 跨租户分析 / 报表治理
平台级分析（用量、计费、安全态势）需汇聚多租户数据，不能走业务查询通道：
- 必须走登记的 `disableTenantFilter()` 入口 + 强制审计 + **只读副本 / 数仓抽取**（不在业务库直接跨租户聚合）；
- 分析结果**聚合、脱敏**，禁止把单租户明细回写到租户作用域表（防反向注入）。

### 9.5 CI 隔离负向测试常态化
把「租户 A 数据对 B 不可见」做成 **CI 强制负向 / 模糊测试**：随机生成跨租户 ID 直查、越权写、`assertXxxBelongsToTenant` 变异用例，而非仅一条 happy-path 集成测试。**实现方式建议参数化而非手写**：以租户作用域实体清单（§3 矩阵 / baseline）为数据源生成用例，新增实体自动获得覆盖。现状可参照的样板：`RepositoryTenantIsolationTest`（blueprint）、`DomainTemplateTenantVisibilityTest` / `ReferenceDataOverlayTest`（masterdata）、`FluentQueryTenantScopeTest`（SDK）。

**必须补的第二类负向用例（本次复核新增）——平台共享行"不该隐身"**：断言真实租户上下文下能读到平台种子/目录行（`gen_code_template` 当前为反例）。只测"不该看见的看不见"会漏掉"该看见的看不见"这一半（§5 `R6`）。

### 9.6 唯一约束与软删的租户规约
- **唯一约束**（修正原表述的过宽）：判据只有一个——**「两个租户出现同名/同码是否算冲突？」** 算 → 必须含 `tenant_id`（范例 `uk_iam_account_username(tenant_id, username)`、`uk_iam_role_code(tenant_id, code)`、`uk_sys_config_key(tenant_id, config_key)`）；不算（全局标识）→ **必须保持全局唯一，不得加 `tenant_id`**：`uk_iam_refresh_token_hash(token_hash)`（令牌哈希必须全局唯一，否则跨租户撞哈希）、`uk_iam_permission_code(code)`（权限码目录）、`uk_iam_tenant_code(code)`（租户编码）。
- **软删行仍须保留 `tenant_id`**，以便按租户 purge；`deleted` 标志不替代租户维度。
- **落地载体**：本规约目前**没有**自动校验（`#12c` 只查列）——需新增"唯一键是否含/不含 `tenant_id` 的判定"校验（§8 项 8），否则仍是口头约定。

### 9.7 分类复核修正
- **生成器 / 扩展 Studio**（§3.6）：平台种子层(0) + 租户实例层 overlay 的方向成立，但**二版的"统一声明 `tenant_id` 强隔离"处方作废**——同表混存会让 0 值种子对租户隐身（`gen_code_template` / `ExtStudioPluginVersion` 为实测反例），改按通则 T1 二选一。
- **`sys_*`**（§3.2）：**`sys_config` 改判租户隔离**（三处真源一致）；其余 5 张标 `待裁决`（Owner: bone-system），不得默认按全局推进；"平台默认 + 租户覆盖"只能拆表实现。
- **`bone_application` / `bone_module` / `bone_app_permission`**（§8 项 6）：原写 `iam_*` 表名不存在，真名为 `bone_*`；DDL 三表均含 `tenant_id` → **租户隔离**（原"待核实"关闭）。
- **关联表**（§3.1）：`iam_role_permission` 无 `tenant_id`（随主实体，by-design）；`iam_account_role` **有** `tenant_id` 且实体自带 `tenantId`——两张表语义不同，不得合并表述。
- **元数据引擎侧**（§3.5）：删除不存在的 `platform_meta_entity` / `platform_meta_field` / `iam_*_ref`；引擎侧真实缺口是 `meta_field` 的第二份映射 `PlatformMetaField` 缺 `tenantId`，处置方向为**补租户声明**（原方案写"标 global"是反向）。
- **漏表补齐**（§3.1 / §3.3 / §3.4 / §3.5）：IAM 补 `iam_audit_settings` / `iam_policy` / `iam_refresh_token`；INT 补 `int_dead_letter` / `int_template` 并改正 `int_log → int_execution_log`；主数据补 `mdm_record_version` / `mdm_record_category` / `mdm_steward_scope` / `mdm_qcheck_*` / `mdm_quality_issue`；元数据补 `meta_code_template`（待核实）。
- **门禁盲区**（§5 `R7`）：15 张含 `tenant_id` 但无 `@Table` 实体的表不在声明门禁内，不能作为"已覆盖"论据。

### 9.9 IDOR 断言收敛（本次复核新增）
`assertXxxBelongsToTenant` 目前只是 `AccountApplicationService` 内的私有方法（2 处调用），其余模块各自实现或缺失。建议：
- 收敛为**共享断言工具/基类**（入参：实体租户、当前租户、错误码），并提供"缺租户上下文即拒绝"的统一语义（E-2 约束下由基础设施层提供，业务层不直读 `TenantContext`）；
- 由 ArchUnit/脚本**强制**：凡"按 ID 加载跨聚合引用"的写路径必须出现该断言（判据与新实体清单同源）。

**为什么**：IDOR 与漏过滤是两类独立失败（前者是"查得到但不该查"，即过滤正确却漏比对），当前只有 IAM 有样板，跨模块一致性无载体可查。

## 10. 实证验证结果（2026-09-26，两租户隔离验证）

**方法**：`scripts/verify_tenant_isolation.py`（标准库实现，可重复执行）。本地起 bone-iam(:8081) + bone-system(:8083)（metadata(:9001) 为存量运行实例），以平台管理员 `admin`（tenant 0）创建两个新租户（`POST /iam/tenants` 自动初始化各自租户管理员），各租户管理员在 IAM（部门/角色/账号）与元数据（实体/字段/发布/运行时记录）各造一批数据，再做双向跨租户负向验证。合计 **45 项，44 项通过**（验证后已清理测试租户与越权脏数据）。

### 10.1 验证通过项（隔离能力确认）

| 类别 | 验证点 | 结果 |
|------|--------|------|
| 全局共享数据 | 平台管理员可写/可读租户注册表与全局 `sys_config`；租户管理员读租户注册表 → 403 | PASS |
| 租户功能正确性 | 两租户各自创建部门/角色/账号（`deptId` 必填 400 生效）、元数据实体/发布/运行时记录（响应带正确 `tenant_id`） | PASS |
| 列表无泄漏 | 账号列表、部门树（`/depts/tree`）、角色列表、元数据实体列表均不含对方租户数据 | PASS |
| 读 IDOR | 用本租户 token 直读对方账号/角色 → **404**（SDK 租户谓词生效） | PASS |
| 写越权 | `PUT` 改名对方部门 → **404**；把账号挂到对方部门 → **404 `IAM_DEPT_NOT_FOUND`**（应用层 `assertDeptBelongsToTenant` 生效） | PASS |
| 元数据隔离 | 直读对方实体 → 拒绝（400「实体不存在」）；实体列表互不可见 | PASS |

### 10.2 验证发现并已修复的缺陷

- **F1（已修复）**：`IamExceptionHandler` 无 `ResponseStatusException` 处理器，Account/Role 详情的 404（含跨租户 IDOR 拒绝）被 `Exception` 兜底伪装成 **500**——隔离语义正确但 HTTP 契约破坏、污染 5xx 告警。已补 handler 按异常自身状态码返回（404），重建 jar 后复验通过。

### 10.3 验证确认的隔离缺口（待架构师决策，L3）

- **F2（实证确认，未修复）**：租户管理员调用 `POST /system/config` **返回 200 成功写入平台全局 `sys_config`**。根因：bone-system 除 `ConsoleController`（`sys:console:read`）外，Config/Log/Dict/Alert/ScheduleTask 等 Controller **均无 `@PreAuthorize` 护栏**，且权限目录未定义 `sys:config:*` 码。任何已登录租户用户可读写全局配置。修复方向：定义 `sys:config:read/write` 等权限码 + 为全局数据写面加平台域护栏（对齐 §3.2/§6「全局数据写面收敛到平台域权限」）。
- **F3（契约小项）**：元数据跨租户直读返回 400（`META_BIZ_ERROR`「实体不存在」），建议对齐 404 语义（与 F1 同类：存在即报不存在，避免向调用方泄露「存在但不可见」信号）。

### 10.4 覆盖边界

本次已覆盖 IAM（租户隔离核心）+ 元数据（SDK 强隔离通道）+ System（全局共享数据）。integration / masterdata / generator / extension 服务未在本地构建运行，其隔离依赖同一 SDK 不变量（ADR-0029），建议在联调环境补跑同脚本扩展；`verify-mvp-e2e.py` 已覆盖单租户主链路。

## 11. 真源绑定与漂移守护

> 本节的目的是让"文档说了什么"与"仓库是什么"不会再次分叉。本轮复核暴露的所有事实错误（§9.8 的 P10–P17）本质都是同一类问题：**裁决写在散文里，没有绑定到真源，于是静默漂移**。

### 11.1 四处真源与同步关系

| 真源 | 位置 | 回答什么问题 | 谁改它 |
|------|------|--------------|--------|
| DDL | `bone-init.sql` | 列与索引**物理上**长什么样（`tenant_id` 是否存在、唯一键/索引是否含租户列） | 走 L3 审批的 DDL 变更 |
| 实体 | `*/domain/**` 的 `@Table` 实体 | SDK **运行时**怎么判租户表（是否声明 `tenantId`） | 模块 Owner（随功能 Change） |
| 缺口/分类基线 | `tenant-entity-baseline.json`、`ddl-required-columns-baseline.json`、`sdk-persistence-bypass-baseline.json` | 哪些偏差是**已登记**的、理由是什么 | 与裁决同步（本方案 §3 是输入） |
| 门禁状态 | [`gate-state.json`](./gate-state.json) | 判据**是否真的在拦**（Active / Manual / Frozen / Planned） | 只改该文件，再由脚本渲染文档 |

**同步规则**（通则 T3 的操作化）：
1. 本方案 §3 的分类矩阵是**裁决真源**，但不是运行时真源——裁决变更必须**四处同步**（DDL/实体/baseline/门禁），任何一处滞后即视为漂移；
2. **禁止**在本文或其他文档里复写门禁状态表（AGENTS.md 纪律）：状态一律引用 `gate-state.json` 的条目编号；
3. 引用"尚未实现的目标态"时必须显式标注**目标态/规划中**（例：`iam_tenant.isolation_mode` 属目标态）；本地脚本拦截不得表述为 CI 阻断。

### 11.2 状态列约定（§3 矩阵）

| 状态 | 含义 | 允许的说法 |
|------|------|-----------|
| `已落地` | 代码+DDL 都已符合裁决，有证据可核 | 可写"已实现"，但不得延伸为"已全覆盖"（见盲区） |
| `待整改` | 裁决已定、实现未跟上 | 只能写"待整改"，禁止写成"已实现/规划中" |
| `待裁决` | 证据不足，需 Owner 关闭 | 只能写"待裁决"，**禁止**按默认值当"已裁决" |
| `待核实` | 表存在但访问通道/语义未确认 | 只能写"待核实"，不得进入"已覆盖"口径 |

### 11.3 建议的一致性校验脚本（§8 项 11）

新增 `scripts/check-tenant-scope-ruling.py`，在 `ci-check.sh` 中执行，四类判定：

1. **矩阵 ↔ baseline**：§3 矩阵中每个 `tenant-entity-baseline` / `ddl-required-columns-baseline` 条目都必须在矩阵中出现（双向），分类一致；
2. **DDL ↔ 归类**：含 `tenant_id` 的 DDL 表必须"有实体映射"或"在 baseline 有 `by-design` 理由"——直接消掉 `R7` 的盲区；
3. **索引规约**：租户作用域表的主访问索引含 `tenant_id` 前导列（或该表在豁免清单并有理由）；
4. **唯一键规约**：按 §9.6 的两分法判定（租户内唯一键含 `tenant_id`、全局标识不含）。

**为什么先做脚本而不是先改 DDL**：这四类判定都是只读扫描，成本低、可立即给出漂移清单；而 DDL 改动（下线平台表 `tenant_id` 列、补索引）涉及 L3/L4 与线上库，必须单独排期。

**三条隐含假设必须显式锁定**（否则脚本会复刻 `R7` 的假阴性）：

1. **注解形态唯一**：实测全仓 `@Table` 均为 `@Table("<name>")`（0 处带参数形式）——若后续出现 `@Table(value = "…")` 等形态，按正则取表名的判据会**静默漏判**；脚本应对"无法解析的 `@Table`"直接报错而非跳过。
2. **一表一实体——当前不成立**：`meta_field` 4 份映射、`meta_entity` 4 份、`bone_application` / `bone_module` / `bone_app_permission` 各 2 份。判据必须"**任一映射未声明租户即命中**"，并输出映射清单（现有门禁是覆盖式，只留一份）。
3. **租户字段命名唯一**：只认 Java 字段 `tenantId` 与列 `tenant_id` / `tenantId`；若引入其他命名（如 `tenant`），需同步扩展判据并登记。

### 11.4 引用一致性提示

- ADR-0038 的文件名为 `0038-platform-model-template-and-scope.md`，但文内标题自述为「ADR-0031」（仓库既存不一致）；**引用一律以文件名/链接为准**，本文不做编号裁决。
- `doc/_generated/**` 与 `doc/wiki/**` 属生成/引用层，分类结论以本方案 + baseline 为准；如出现与本方案冲突的描述，按 §11.1 的同步规则回改，而不是改本方案去迁就。
- `bone-platform/bone-masterdata/README.md` 曾有「`md_entity` / `md_record` / `md_field` / `md_lineage` … 已补 `tenant_id`，聚合统一继承 `TenantAggregateRoot`」的表述，与实测不符（这 3 张 `md_*` 表已无实体映射、`md_lineage` 在 DDL 基线内缺列）——**以本方案 §3.0/§3.3 与 baseline 为准**，该 README 需同步修正。
