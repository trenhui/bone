# HC-006 存量绕过 SDK 裁决（2026-10-08）

> 配套：`scripts/check-sdk-persistence.py` + `doc/architecture/sdk-persistence-bypass-baseline.json`
> 门禁语义：**新增文件**命中 JDBC/MyBatis import 即失败；存量只可收缩。
> 裁决权：模块 Owner。本次裁决由审计任务在用户授权下执行（"对合理建议全部执行，含待裁定项"）。

## 0. 结论速览

| 层 | 数量 | 含义 |
|----|------|------|
| `files`（真正技术债，待排期收敛） | 3 | 两个 `RefreshToken*`（须安全评审）、`MetaEntityCatalogPort`（须服务化） |
| `technicalExemptions`（结构性豁免，SDK 无法表达） | 10 | 引擎 DDL/INFORMATION_SCHEMA、租户批量删、定时全租户物理清理、平台级跨租户读（含审计设置）、跨租户/跨表指标、dev 调试工具 |
| `debugToolExemptions`（工具豁免） | 1 | `DatabaseDebugTool`（`@Profile("dev")`） |
| **合计** | **14** | 与基线条目数一致，无新增、无遗漏 |

**业界最佳实践判断**：HC-006 门禁本身（"新增零容忍 + 存量只可收缩"）是正确且必要的控制，与 Google/Spring 推荐的"依赖护栏 + 渐进式收敛"一致，**保留**。但原基线把 14 条全部平铺为 `files`（"待收敛债"），导致：
1. 把"SDK 根本无法表达"的写法（动态 DDL、`GROUP BY` 聚合、70+ 表批量删）也标成债，制造永不缩小的黑名单，"只可收缩"失去意义；
2. 把"真正可迁 SDK"的简单 CRUD 与"结构性豁免"混在一起，Owner 无法区分优先级。

因此**合理的执行不是盲目把 14 个文件改成 SDK**，而是把基线落地为脚本已设计的两层模型（技术/工具豁免 vs 真债），并对真债给出收敛路径与风险。

> **SDK 增强（2026-10-08，提交 `b54ca7cd` + 复核修正）**：探查发现原判定"SDK Criteria 不支持 groupBy/聚合"**不成立**——`aggregate`/`countByCriteria`/`deleteByCriteria`/DSL `groupBy` 早已存在，但 `AggregationBuilder` 与 `CountAggregationBuilder` **漏注租户过滤与软删谓词**（违反 ADR-0029 fail-closed、软删表聚合含脏数据）。已修复：两个聚合构建器复用 `TenantFilterInjector.inject(...)` 并补齐 `m.deleted = false`（opt-in `includeDeleted`），与 `SelectBuilder`/`CountBuilder` 完全对齐；新增 `aggregate(..., boolean includeDeleted)` 三处重载保证 API parity；聚合遇扩展表字段条件显式 fail-fast（避免静默丢过滤导致指标偏大）。回归测试 `TenantMetricAggregationTest` 覆盖租户作用域/软删排除/includeDeleted/无上下文 fail-closed/caller-EQ 兜底/扩展字段 fail-fast。
>
> **重要边界（复核修正）**：该修复让**租户作用域的单表聚合**变安全，但**并未**让 §1.1 的两个指标网关变得可直接迁移：① 它们都是**全库级/跨租户**统计（`GROUP BY tenant_id` 跨租户、`COUNT(*)` 不带租户条件），而 SDK 聚合通道是租户作用域的，直接调用会被 fail-closed 拦下；② `JdbcKeyMetricsGatewayAdapter` 还**跨 4 张表、跨模块**且异构软删（`deleted` 与 `is_active` 两种语义）。二者保留在 `technicalExemptions`，正确解法是**平台级跨租户/跨表指标能力**（或受控 `disableTenantFilter()` + 平台授权审计），而非把聚合表达式搬进租户通道。
>
> 另注：该聚合缺口目前**无生产调用方**（全仓 `aggregate(...)` 主代码零调用，仅测试使用），属**潜伏缺陷**（阻断未来迁移）而非在线数据泄露；修复价值在于消除 ADR-0029 漏洞并为后续租户内聚合铺路。
>
> 后续已补：GROUP BY/SELECT 列别名归一（统一 `m.` 限定，共用 `SqlInjectionPreventer.qualifyWithAlias`，消除两个构建器实现漂移）；`aggregateWithPagination` 不再改写调用方 `Criteria`（分页随 `AggregationContext` 传递），并补回归测试锁定。

## 1. 逐条裁决（证据驱动）

### 1.1 结构性豁免（technicalExemptions，9 条，SDK 无法表达）

| 文件 | 证据 | 为何豁免 |
|------|------|----------|
| `metadata-server/.../JdbcPhysicalStructureGatewayAdapter` | 物理表结构 / INFORMATION_SCHEMA 内省 | SDK 静态 Repository 无法表达 DDL/目录读取 |
| `metadata-server/.../CatalogInfrastructureConfiguration` | 上述适配器的装配 | 随引擎内部 JDBC 通道存在 |
| `metadata-server/.../RuntimeEngineConfiguration` | 同上 | 引擎运行时 JDBC 装配 |
| `metadata-server/.../TemplateReadAdapter` | 引擎内部动态模板读取 | 引擎边界，SDK 不可表达 |
| `studio-generator/.../DatabaseMetadataGatewayAdapter` | 数据库元数据内省 | INFORMATION_SCHEMA，SDK 不可表达 |
| `iam/.../gateway/TenantDeletionGatewayAdapter` | 70+ 租户表批量 `DELETE` + `FOREIGN_KEY_CHECKS=0` + 跨表 `JOIN` 删除（`DELETE rp FROM iam_role_permission rp INNER JOIN ...`） | SDK 无批量删/跨表删；by-design 运维操作 |
| `iam/.../persistence/AuditLogRetentionPortAdapter` | 定时全租户物理清理，**无请求级租户上下文**；按设计跨租户物理删，须走 `Criteria.disableTenantFilter()` 受控出口（ADR-0029 逃生舱）+ 平台授权与审计 | SDK 无法用租户通道表达 |
| `iam/.../gateway/AuditSettingsGatewayAdapter` | 单表 CRUD，**但端口被 `AuditLogCleanupJob`（每日 03:00 cron）逐租户循环调用以读取全部租户保留期** ⇒ 该端口本质是平台级跨租户读 | SDK 条件/聚合通道是租户作用域，且 `TenantFilterInjector` **优先 `TenantContext` 并忽略 caller 传入的 tenantId** ⇒ 直接迁移会在上下文存在时读到**别的租户**的设置（静默错配 + 越权读风险）。与上一条同类 |

> 这些项的"收敛"不是"改用 SDK"，而是（如未来需要）在 SDK 暴露对应能力（聚合端口、批量运维端口、动态元数据端口）后再回收。当前阶段维持豁免、仅可收缩。

### 1.2 工具豁免（debugToolExemptions，1 条）

| 文件 | 证据 | 为何豁免 |
|------|------|----------|
| `iam/.../debug/DatabaseDebugTool` | `@Profile("dev")`、`CommandLineRunner`、仅 dev 启动期打印 | 调试工具，非业务路径 |

### 1.3 真正技术债（files，3 条，待排期收敛）

| 文件 | 现状 | 推荐收敛路径 | 风险 |
|------|------|--------------|------|
| `iam/.../gateway/RefreshTokenIssuerGatewayAdapter` | 安全令牌存储（SHA-256 哈希 + 轮换 + 复用检测），单表 `iam_refresh_token` | 可 SDK 化（按 `token_hash` 用 Criteria 查询），但**须安全评审后迁移** | 中（令牌安全） |
| `iam/.../gateway/RefreshTokenSessionGatewayAdapter` | 同上表的会话视图（listByAccountId / revoke） | 同上，与 Issuer 合并迁移 | 中（令牌安全） |
| `masterdata/.../gateway/MetaEntityCatalogPortAdapter` | 直读 `meta_entity`/`meta_field`（bone-metadata 上下文），因 masterdata 尚无元数据服务客户端 | 收敛路径 = **建元数据服务客户端 / 联邦视图**，而非 SDK | 中（跨上下文直连） |

> **更正记录（复核推翻先前判断）**：本裁决初版把 `AuditSettingsGatewayAdapter` 列为"低风险首批迁移目标"。复核其**全部调用方**后发现 `AuditLogCleanupJob`（cron）逐租户循环调用该端口读**全部租户**设置 ⇒ 该端口本质是平台级跨租户读，与 `AuditLogRetentionPortAdapter` 同类，已移入 `technicalExemptions`。
> **教训：评估"某处能否收敛"必须看它的全部调用方的语义，不能只看那一个文件长什么样。** 单表 CRUD 看起来简单，但端口的调用方式决定了它属于哪个维度的问题。

> `MetaEntityCatalogPortAdapter` 的"债"本质是跨边界直连库，正确解法是服务化，不在 SDK 能力范围；单独跟踪，勿与 SDK 迁移混为一谈。

## 2. 门禁行为确认

`check-sdk-persistence.py --check` 计算：`extra = 当前命中 - files - (technical+debug 豁免)`。
- 当前命中 = 14 = files(4) + 豁免(10) ⇒ `extra = 0`，门禁通过。
- `stale_exempt`（豁免里已无代码）：0；`unreasoned`（豁免无理由）：0。
- 两层均"只可收缩"：item 被改造成走 SDK 后，应从对应层移除。

**修复**：`write_baseline()`（`--baseline` 模式）原会把 technical/debug 豁免一并抹掉，本次已改为保留既有两层，避免裁决丢失。

## 3. 不在本轮执行项

- **HC-006 引擎运行时 JDBC（`JdbcRuntimeRecordService`）**：见 `doc/design/_pending-fixes-HC006-engine.md`，被 Comet change `refactor/metadata-engine-boundary-ddd` 占用，**跳过**，待该 change 归档后由之重置。本裁决未触碰。
- **SDK 聚合安全增强（已完成）**：`AggregationBuilder`/`CountAggregationBuilder` 注入租户 + 软删谓词（对齐 `SelectBuilder`/`CountBuilder`），新增 `aggregate(..., includeDeleted)` 三处重载，扩展表字段条件 fail-fast；回归测试 `TenantMetricAggregationTest` 覆盖。修复的是**潜伏缺陷**（聚合通道无生产调用方），价值为消除 ADR-0029 漏洞并让"租户内聚合"可安全使用。
- **平台级跨租户/跨表能力（未做，方案见 §4）**：三个网关需要的是**不受租户作用域约束**的平台视角查询——① 两个指标网关（全库/分租户/跨表统计）；② `AuditSettingsGateway`（被 cron 逐租户循环读全部租户）。正确解法是在 SDK 显式提供"平台级查询"受控能力，而不是把它们硬塞进租户通道。此项属架构决策，未擅自动。
- **3 个 `files` 的代码迁移**：盲目改网关 API 有打断风险，且 `RefreshToken*` 涉及安全评审、`MetaEntityCatalogPort` 涉及服务化，**不在本轮改动代码**，仅登记为待办供 Owner 排期。建议顺序：`RefreshToken*`（安全评审）→ `MetaEntityCatalogPort`（服务化）。
- **`AuditSettingsGateway` 的可选前置改造（未做）**：若 Owner 希望该端口回归 SDK 租户通道，须先把 `AuditLogCleanupJob` 的逐租户循环改为 `TenantContextRunner.runAs(tenantId, ...)`（`TenantContextRunner` 已在 `bone-core` 可用），使上下文与目标租户**始终一致**，再迁 adapter。这属行为变更（定时任务），需单独排期与验证，非本轮可顺手完成。

## 4. 平台级指标能力方案（待 Owner 决策，未实现）

### 4.1 问题定义

三个网关要的是**平台视角**的查询，与 SDK 的**租户视角**语义不匹配：

| 网关 | 实际查询 | 与 SDK 的语义冲突 |
|------|----------|---------------------|
| `DeadLetterMetricsRefresher` | `GROUP BY tenant_id` 跨所有租户 + `@Scheduled`（无租户上下文） | 通道会注入 `WHERE tenant_id = :ctx`，把"分租户统计"压成"当前租户统计"，**语义相反** |
| `JdbcKeyMetricsGatewayAdapter` | 4 张表（跨 iam/system/integration/extension 模块）全库 `COUNT(*)`，异构软删（`deleted` 与 `is_active`），逐表 try/catch 降级 | 通道是**单表 + 租户作用域**，无法一次表达跨表全库概览 |
| `AuditSettingsGatewayAdapter` | 被 `AuditLogCleanupJob`（cron）**逐租户循环**读取全部租户设置 | 通道是**单租户作用域**，一次调用只能读一个租户；且 `TenantFilterInjector` 优先 `TenantContext`，caller 传的 `tenantId` 会被忽略 |

⇒ 它们不是"表达式写不下"，而是**查询维度与 SDK 契约不匹配**。这与另外的豁免（DDL 内省、批量删、物理清理）是**不同性质**的缺口：后两者是 SDK 不该管，这一个是 SDK **缺一个能力**。

### 4.2 候选方案

| 方案 | 做法 | 优点 | 缺点 / 风险 |
|------|------|------|------------|
| **A. 沿用逃生舱**（现状可用） | `Criteria.disableTenantFilter()` + 调用方自行鉴权 | 零新增 API，立即可用 | 授权靠**约定**（`TenantFilterInjector` 仅打 WARN），无编译期/运行期强制；任何人任何地方都能用 ⇒ 易扩散成"随处跨租户查询" |
| **B. 专用平台指标端口**（推荐） | SDK 新增 `PlatformAggregatePort`（或 `PlatformMetricsQuery`）：唯一允许跨租户/跨表聚合的入口，调用须显式携带平台授权令牌，并落审计事件 | **单一收口点**，可强制（无令牌即抛异常）、可审计、可被门禁识别；语义上把"平台视角"与"租户视角"在类型层面分开 | 需新增公共 API + 一条 ADR；聚合能力从任意单表扩展到跨表（可用"多次单表聚合 + 内存合并"实现，仍受单表租户约束放开） |
| **C. 指标走只读副本/独立 DSN** | 仪表盘类查询打到只读副本或独立数据源，不碰生产 OLTP | 生产库零压力；天然允许跨租户全库聚合 | 基建成本 + 复制延迟（"best-effort" 概览可接受）；与 Bone 单库部署形态有出入 |

### 4.3 建议

1. **方向选 B**：把"平台视角聚合"变成**显式、受控、可审计**的窄接口，而不是给所有查询开逃生舱。逃生舱（A）保留，但仅作为过渡且必须登记使用点。
2. **C 作为运维补充**：若后续仪表盘查询量增大或需要近实时全库统计，优先引只读副本，而不是继续在应用侧扩大跨租户查询面。
3. **迁移路径**（待决策后执行）：
   - `DeadLetterMetricsRefresher`：单表（`int_dead_letter`）⇒ 最容易迁，先落 `int_dead_letter` 的 SDK 实体映射，再走平台指标端口按 `tenant_id` 分组。
   - `JdbcKeyMetricsGatewayAdapter`：跨 4 表 ⇒ 用平台端口做 N 次单表计数 + 内存合并，保留其 graceful degradation（单表失败计 0）语义；异构软删需按表分别声明（`deleted` vs `is_active`）。
   - `AuditSettingsGatewayAdapter`：**先解耦调用方**——把 `AuditLogCleanupJob` 的逐租户循环改为 `TenantContextRunner.runAs(tenantId, ...)`，使上下文与目标租户一致（否则 SDK 会忽略 caller 的 `tenantId` 而读到别的租户）；解耦后即可作为普通租户通道查询迁移。
4. **需 Owner 拍板的问题**：① 是否新增 SDK 公共端口（涉及 ADR 与 API 兼容性）；② 平台指标的授权令牌如何签发与校验；③ 是否接受 C（只读副本）作为长期方案。

> 在决策落地前，这 3 个文件继续留在 `technicalExemptions`（门禁仍"新增零容忍、存量只可收缩"），**不得**为了门禁好看而把它们硬塞进租户通道——那会为了合规而牺牲查询语义正确性，甚至造成跨租户错配（审计设置场景下会读到别的租户的保留期）。
