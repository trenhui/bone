## 二、发现并修复的真实缺陷（2 处）

两处都属于典型的「注释/契约宣称 X，代码实际做了非 X」。

### 缺陷 1｜workflow 中继：重试达上限后未落终态，永久失败动作每 5 分钟重跑

**根因**：`StatusProjectionRelay` 中动作执行失败时，`markFailed` 被 SQL 护栏（`retry_count < maxRetries`）挡下返回 `false`，
而调用方**只打日志**，任由该行停留在 `claim()` 刚写入的 **`CLAIMED`** 状态。于是「超时 CLAIMED 抢占」路径每
`CLAIM_TIMEOUT` 把它重新取回、重复执行这个注定失败的动作 —— 与类注释承诺的「达到上限不再排期 / 不能永久空转」完全相反。

** MySQL 实测证据**（意图 `reconcile-610061-APPROVED`）：

| 字段 | 实测值 | 应有值 |
|---|---|---|
| `state` | `CLAIMED` | `FAILED`（终态） |
| `retry_count` | `8`（已超上限） | — |
| `updated_at` | 每 5 分钟刷新一次 | 不再变动 |
| `countTerminallyFailed()` | `0` | `1` |

副作用：因不是 `FAILED`，**死信存量监控对该死信完全失明**，「转人工」沦为一句空话；ERROR 在 22:31→23:06 持续刷屏。

**修复**：达上限时显式调用 `markTerminallyFailed`（`FAILED` + `next_retry_at` 推到远未来），
同时满足「`pollDue` 不再取回」与「`countTerminallyFailed` 可见」两条；并收紧类注释的不变式表述防止回归。

### 缺陷 2｜masterdata：质量报告列表不传 `qualityCheckId` 时恒返回 `[]`

**根因**：`QualityApplicationService.listReports` 把可能为 `null` 的入参直接交给 `findByQualityCheckId`，
DSL 落成 `quality_check_id = NULL`，SQL 三值逻辑下**永不命中**。同模块的 `listChecks` 对此有 `findAllChecks()` 分支，此处缺失。

**实测证据**：库里有上百条报告、`checks/{id}/report` 按 ID 单查返回 200，但 `GET /quality/reports` 永远返回空数组 —— 报告列表页必然长期空白。

**修复**：新增 `QualityReportRepository.findAllReports()`，与 `listChecks` 同口径做 null 分支。
