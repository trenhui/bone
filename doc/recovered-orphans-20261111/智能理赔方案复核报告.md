# 智能理赔详细技术方案（bone-ai 落地版）独立复核报告

> 复核范围：`doc/ai-product/synapClaim/智能理赔详细技术方案（bone-ai落地）.md`
> 复核基准：bone-ai 代码仓库实际现状 + 本机离线 Maven 仓库（`~/.m2/repository`）实测
> 复核方式：只读，未修改任何文件

---

## 一、结论（方案是否成立）

**方案整体成立，方向正确，但存在 3 项【阻塞】级落地性问题必须修正后才能作为可直接落地的技术方案；另有若干重要级内部不一致项。**

核心判断：

- 方案的"AI 不碰钱、资金走确定性代码、决策可解释可治理"三大红线与 bone-ai 现状高度契合，且与已落地的 orchestration HITL 五态、ClaimService 三档置信度、trace 证据快照完全同源，**架构方向是成立的**。
- 但方案在"落地性"这一复核重点上**没有真正落到离线约束与 HC-001 唯一持久化抽象**：决策图引擎选 JGraphT（离线不可用）、数据模型用 TiDB 原生 SQL 建表 + 直连 Mapper（违反 metadata-sdk 唯一持久化抽象，且非离线优先）、Outbox 依赖 RocketMQ（bone-ai 当前未集成，存在被当作既定基座的误导）。
- 置信度口径存在**一处明确的文档与实现矛盾**（单档 `<0.85` vs 已落地三档），必须在方案内统一，否则按方案落地会推翻 ClaimService 已实现的三档语义。

## 二、问题清单（按严重度分级）

### 【阻塞】级

#### B1. 决策图引擎选 JGraphT，离线 Maven 不可用 → 无法编译/打包

- **位置**：§6.1、§6.2、§14、附录 ADR「决策图存储 TiDB JSON + JGraphT 内存执行」。
- **事实依据**：本机 `~/.m2/repository/org/jgrapht/` **目录完全不存在（0 个子目录、0 个 jar）**。bone-ai 六个模块的 pom 中也未引用 JGraphT，无任何现成实现。离线模式只依赖本地仓库可用 jar，引入 JGraphT 会在 `mvn -o` 下直接失败。
- **修复建议**：
  1. **一期不引 JGraphT**，改自建轻量 DAG 执行器（约 200~400 行）：节点类型固定为 `START/RULE_NODE/AI_NODE/DECISION_NODE/END`，用入度为零拓扑执行（依赖顶多 5 类节点、层数 ≤ 3，无需通用图库），实现节点 fallback 与短路优化。置于 `bone-ai-orchestration` 新增 `decisiongraph` 子域，与现有 HITL 子域并列。
  2. 若二期确有通用图建模需求，再评估 JGraphT 是否能离线获得（当前离线仓库为空，属硬阻塞）。

#### B2. §8 数据模型用 TiDB/原生 SQL 建表 + 直连 Mapper，违反 HC-001 唯一持久化抽象（且离线优先主张不成立）

- **位置**：§7.2 `fundingEventMapper/accountMapper/claimMapper`、§8 全部 `CREATE TABLE`、附录「决策图存储 TiDB JSON」。
- **事实依据**：
  - bone-engine 已确立 **HC-001：bone-metadata-sdk 是唯一持久化抽象**（`bone-metadata-sdk` 提供 `@Table/@Column` 注解持久化 + `@Sql` 模板，文档明确「不要手写 `JdbcTemplate`，违反平台持久化 P0」）。
  - §8 方案直接给 TiDB SQL 建表，§7.2 直接写 `fundingEventMapper.insert(...)` 这类 MyBatis/JDBC 直连风格，与 HC-001 冲突——按 HC-001 应基于 metadata-sdk 的 `@Table/@Column` 实体 + repository 接口持久化。
  - 更关键：**复核发现离线约束的真实结论与任务假设相反**——`mysql-connector-j` 在本地仓库**存在真实可用 jar**（8.0.31/8.0.32/8.0.33/8.3.0/8.4.0 均为约 2.5MB 真实 jar，非 `.lastUpdated` 失败标记）；metadata-sdk 也内置 h2database 与 mysql-connector-j 依赖，方言支持 `MYSQL|H2|...`。**即 JDBC 与数据库持久化在离线模式下可用**，"JDBC 离线不可用"这一前置判断不成立。
- **修复建议**：
  - 一期表实体统一用 metadata-sdk `@Table/@Column` 建模（graph_definition/decision_execution/funding_event/liability/personal_quota/claim/decision_trace 各建对应实体类），repository 走 metadata-sdk 内置 CRUD，不写直连 Mapper。
  - 存储引擎优先考虑 metadata-sdk 已支持的 H2 嵌入式（`type: H2`）做离线开发/演示；生产再切 MySQL/TiDB（metadata-sdk 方言可切），天然满足离线可跑、HC-001 不破。

#### B3. 置信度口径：方案单档 `<0.85 强制转人工` 与已落地三档矛盾

- **位置**：§5.2「AI 评分…置信度 < 0.85 强制转人工」、§6.2 决策图「AI_NODE…<0.85→DECISION 转人工」、§13 风险对策「置信<0.85 强制人工」、附录 ADR「置信度阈值 <0.85 强制人工」、§10.2 R-MAN-01「置信<0.85」。
- **事实依据**：bone-ai `ClaimService` 已落地**三档语义**（`HITL_FORCE_THRESHOLD=0.7`、`AUTO_THRESHOLD=0.85`，注释明确「≥0.85 且非高风险直出；0.7-0.85 复核；<0.7 或高风险强制人工终审」）。orchestration `HitlService` 也以 `<0.7` 为强制 PENDING 阈值。方案全文统一使用"<0.85 强制人工"单档，会把 0.7–0.85 的复核档**误判为必须强制人工**，推翻已落地语义，且丢失"中档复核"的降载价值。
- **修复建议**：方案全篇统一为三档语义并显式对齐 R-MAN-01：
  - `<0.7`（或高风险）：强制人工终审（对应 R-MAN-01 的"强制转人工"）
  - `0.7–0.85`：复核档（进人工复核工作台，可自动确认或人工裁决）
  - `≥0.85 且无风险`：自动通过直出
  - 在 §10.2 R-MAN-01 与附录 ADR 加一句说明："R-MAN-01 的 `<0.85 转人工` 是产品单档简化口径，落地按三档：`<0.7` 强制人工、`0.7-0.85` 复核、`≥0.85` 直出，与 ClaimService 一致"。

### 【重要】级

#### I1. §5.2 声称"决策五段式用 orchestration 显式状态机实现"，与现状不符（当前无此状态机）

- **位置**：§5.1、§5.2、§14「状态机落 orchestration」。
- **事实依据**：`bone-ai-orchestration` 当前只有 `hitl` 一个子域（HitlStatus/HitlItem/HitlService），以及一个线性 `OrchestrationService`（规则预检→短路→LLM），**没有五段式状态机**，也没有每段超时/补偿的落地实现。§5.1 的五段式（证据就绪30s/规则5s/AI10s/图执行15s/决策3s）目前是**目标设计而非现成资产**，方案措辞"复用最小管线+显式状态机实现"高估了现状。
- **修复建议**：§5.2 改为明确定位"五段式状态机为**新增**落地项（落到 orchestration 决策图子域），一期可简化为顺序管线 + 全局超时兜底转人工"，不要写成"已存在"。

#### I2. Outbox/RocketMQ 被当作既定基座，但 bone-ai 当前未集成 RocketMQ

- **位置**：§2.1 存储层「RocketMQ(事件)」、§7.2 outbox、§7.3 Outbox/CDC。
- **事实依据**：rocketmq-client 5.3.1 离线 jar 可用，但 bone-ai 六个模块**当前没有任何 RocketMQ 依赖或代码**（grep 无结果）。方案把 RocketMQ 作为 §2 存储层既定组件列出，落地时属新增集成，存在离线可得但装配成本与失败路径（本地无 broker、无 sidecar）的落地风险。
- **修复建议**：一期资金事件/支付指令投递**先走进程内事件总线 + afterCommit**（Spring `@TransactionalEventListener`/`TransactionSynchronization`），配合资金表幂等唯一索引；RocketMQ 作为二期生产对账再引入（离线 jar 已具备，非阻塞，但不应写成一期既定基座）。

#### I3. §8 表覆盖缺失：无 HITL 待办、规则、evidence 三张关键表

- **位置**：§8 数据模型（仅 graph_definition/decision_execution/funding_event/liability/personal_quota/claim/decision_trace 七表）。
- **事实依据**：方案自身多处依赖却未建模：§6.2 人机回环产生" HITL 待办"（对应 orchestration HitlItem，需落库）；§10 规则存库热更（RuleAsset 需表）；§1.3/§2.2 证据采集（EvidenceCollection 聚合、decision_trace 虽列但无证据原始对象表）。现有七表无法支撑"决策可回放"完整闭环（证据→解析→核责→理算→决策）。
- **修复建议**：补充三张 metadata-sdk 实体表：`hitl_item`（对应 HitlStatus 五态 + ReasonType）、`rule_asset`（code/expression/status/grayPercent/hitBlock/version）、`evidence`（doc_type/ocr_confidence/解析结果/锁定标记）。决策回放由 decision_trace + evidence 联合支撑。

#### I4. §7.4 大额双人复核的资金状态机与 §7.1 两段式未对齐

- **位置**：§7.1（两段式 HARD_RESERVED→PAID）、§7.4（大额"先冻结、双人复核后 HARD_RESERVED→PAID"）。
- **事实依据**：§7.1 描述软预占+硬预占同一事务；§7.4 却要求大额"先冻结、复核后才硬预占"，语义上存在一个"复核冻结态"未在两段式状态图中表达（资金事件 stage 枚举 SOFT_RESERVED/HARD_RESERVED/PAID 也缺冻结态）。
- **修复建议**：在两段式状态机中补一个 `REVIEW_FREEZE`（复核冻结）状态，资金事件 stage 增加该值，并明确软预占与复核冻结的关系；否则大额流程无状态可落。

#### I5. §2.1/§8 多处 TiDB 与 §12 里程碑（4人/150人日）投入不匹配，工作量被低估

- **位置**：§2.1、§6.1、§8、§12。
- **事实依据**：方案同时要求新增决策图引擎 + 七张表 + fund-engine 资金域 + RAG 全链 + OCR 适配器 + 300 条评测集，且在 §12 以 4 人 ≈150 人日（10 周）交付，明显偏紧；其中决策图、fund-engine、RAG、OCR 四项均为新增大型件。属规划层面高估，非技术选型错误，列为重要级提醒。

### 【次要】级

#### M1. §5.1 决策图执行标"强一致"与 §7.1 资金行锁强一致语义混用

- **位置**：§5.1「图执行（决策图推理）强一致 15s」。
- **事实依据**：决策图推理本身是内存计算，用"强一致"表述与资金事务的行锁强一致不是同一概念，易误导（决策图强一致应为"决策结果确定性可复现"，非分布式事务一致）。
- **修复建议**：把该行改为"确定性（可复现）"，与资金强一致区分。

#### M2. 命名口径不一致：QLExpress vs qlexpress4

- **位置**：§10.1「QLExpress DSL」、§14「QLExpress 唯一」。
- **事实依据**：bone-ai-rules 实际引入的坐标是 `com.alibaba:qlexpress4:4.1.3`（本地仓库有 qlexpress4-4.1.3.jar）；另有 `com.alibaba:QLExpress:3.3.2`。方案写"QLExpress"可泛指，但建议明确到 qlexpress4 版本口径，避免实现时选错 artifact。

#### M3. 附录 ADR「决策图存储 TiDB JSON」与离线/一期降级建议矛盾未标注

- **位置**：附录 ADR。
- **事实依据**：ADR 结论写死 TiDB JSON + JGraphT，但离线约束下二者均需替换（见 B1/B2），ADR 未记录备选决策。
- **修复建议**：在 ADR 中追加降级决策记录（一期 H2/metadata-sdk + 自建轻量 DAG，JGraphT/TiDB 留二期），保证决策留痕与可实现一致。

## 三、落地性修正建议（离线约束下的选型替换）

| 方案原选型 | 离线可用性 | 一期修正方案 |
|---|---|---|
| JGraphT（§6.1） | **不可用**（本地仓库无目录） | 自建轻量 DAG 执行器（入度拓扑 + 节点 fallback + 短路），置于 orchestration `decisiongraph` 子域；二期有通用建模需求再评估 |
| TiDB JSON + 原生 SQL 建表（§6.1/§8） | JDBC 实际**可用**（mysql-connector-j 有真实 jar），但原生 SQL 违反 HC-001 | 用 metadata-sdk `@Table/@Column` 实体 + repository 持久化，方言切 H2（离线嵌入式）做开发/演示，生产切 MySQL/TiDB |
| 直连 Mapper（§7.2 fundingEventMapper 等） | — | 弃用，全部走 metadata-sdk 唯一持久化抽象 |
| RocketMQ Outbox（§7） | jar 可用但 bone-ai 未集成 | 一期进程内事件总线 + afterCommit + 幂等唯一索引；RocketMQ 二期引入 |
| OCR 适配器（Docling/PaddleOCR）（§2.2） | 需进一步核（未在复核范围） | 一期复用 PDFBox 文本抽取 + 规则验真，OCR 低置信转人工兜底 |

## 四、置信度口径统一建议

将方案全篇（§5.2、§6.2、§10.2 R-MAN-01、§13、附录 ADR）的"置信度 <0.85 强制转人工"统一为与 bone-ai `ClaimService` 一致的三档语义：

| 置信度 | 语义 | 落地动作 |
|---|---|---|
| `<0.7` 或高风险 | 强制人工终审 | 进 HITL PENDING，人工终审（不可自动通过） |
| `0.7–0.85` | 复核档 | 进人工复核工作台，可自动确认或人工裁决 |
| `≥0.85` 且非高风险 | 自动通过直出 | 直接 AUTO_APPROVE（决策图走资金状态机） |

**对齐说明**：R-MAN-01 的"<0.85 转人工"是产品侧单档简化口径，落地统一按三档（与 `ClaimService.HITL_FORCE_THRESHOLD=0.7`、`AUTO_THRESHOLD=0.85` 对齐）。方案应在 §10.2 与附录 ADR 显式加此说明，避免实现推翻已落地三档。

> 阈值本身（0.7/0.85）是初值，属评测集优化项，不在本复核范围内调整，只统一口径。

## 五、复核过程事实核验记录（本报告事实依据）

- `~/.m2/repository/com/mysql/mysql-connector-j/`：8.0.31/8.0.32/8.0.33/8.3.0/8.4.0 均有真实可用 jar（约 2.5MB），**无 .lastUpdated 失败标记** → 任务前置"JDBC 离线不可用"不成立。
- `~/.m2/repository/org/jgrapht/`：**目录完全不存在** → JGraphT 离线不可用（确认）。
- rocketmq-client 5.3.1、redisson 3.27.2、guava 30.1.1-jre、minio 8.5.1 均有真实 jar → 可用。
- pdfbox、qlexpress4（4.1.3）、QLExpress（3.3.2）、resilience4j 各组件离线可用。
- `bone-ai-orchestration`：仅 `hitl` 子域 + 线性 OrchestrationService（规则预检→短路→LLM），**无五段式状态机/每段超时补偿**；无任何资金相关代码（与"严禁碰资金"一致）。
- `ClaimService`：三档已落地（HITL_FORCE_THRESHOLD=0.7、AUTO_THRESHOLD=0.85）。
- `HitlService`：`CONFIRMATION_THRESHOLD=0.7`。
- `HitlStatus`：PENDING/CONFIRMED/REJECTED/MODIFIED/ESCALATED 五态（与方案 HITL 五态一致）。
- `RuleRegressionGate` 存在于 bone-ai-rules。
- `bone-metadata-sdk`：文档明确为唯一持久化抽象（HC-001，"不要手写 JdbcTemplate"），方言支持 MYSQL/H2 等，pom 依赖 mysql-connector-j 与 h2database → 离线可持久化。
- bone-ai 六模块当前无 RocketMQ、无 JGraphT 引用。

**存储统一原则**：一期所有持久化走 `bone-metadata-sdk`（HC-001），数据源方言用 H2 保障离线可编译可运行，避免为"离线"与"持久化"做二选一——离线不阻断持久化，JDBC 离线可用。
