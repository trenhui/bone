## 二、确诊问题与修复明细

### P0-1 配置/日志导出下载到内容是字符串 "undefined"（功能完全不可用）

- **根因**：`createApiClient` 响应拦截器已解包 `(r)=>r.data`；blob 场景下 `await` 拿到的就是 Blob 本体，页面却又取了一次 `.data` → `new Blob([undefined])`。类型层还误标 `ApiResponse<Blob>`，TS 因此发现不了。
- **修复**：`api.ts` 两个导出方法返回类型改为 `Promise<Blob>`（注释说明拦截器语义）；两个页面直接用返回值构造 Blob（带 `instanceof Blob` 防御），并补 `revokeObjectURL`。

### P0-2 日志筛选（级别/服务/时间范围）全部静默失效

- **根因**：页面搜索表单构造了完整 filters，`api.ts getLogs` 只转发 `keyword`；后端 `LogPageReq` 也没有时间字段（导出却有）。「UI 暴露的约束请求链不消费」——比没有筛选更糟。
- **修复（前后端贯通）**：
  - 前端 `getLogs` 全量透传（`level→logLevel`、`service→serviceName`、时间原样）；
  - 后端 `LogPageReq`/`LogPageQuery` 增加 `startTime/endTime`；`LogAssembler.toQuery` 由 MapStruct 自动生成改为 default 方法显式解析（复用 `toExportQuery` 的双格式 parse——这正是当年「编译通过但参数丢失」的位置）；`SystemLogRepository.pageByCondition` 增加时间范围下推（与导出抽公共 `appendTimeRange`）。

### P0-3 告警规则建了永远不会触发（监控假绿）

- **根因**：规则表单指标选项是 `cpu/memory/errorRate`，告警评估端口 `MicrometerMetricValueAdapter` 只认 `cpu.usage/memory.usage/api.error_rate/db.connections.active`。同一模块两套指标口径，规则恒被 skip。
- **修复**：表单选项改与评估端口一致的真口径（每项带中文 label 与口径说明 tooltip）；删去后端不可评估的 `disk/apiResponseTime` 选项——**留着一个建了不触发的选项就是预留假绿**。

### P0-4 告警事件「实测值」列永远为空

- **根因**：前端类型与列绑定 `value`，后端 `AlertRecordResp` 字段是 `actualValue`（类型契约漂移，编译期无感）。
- **修复**：`shared-types` `AlertRecord` 对齐后端（`actualValue` + ruleName/metricName/threshold/alertLevel），页面列绑定改正。

### P1-5 告警事件无「解决」入口

- 后端 `/system/alert/events/{id}/resolve` 存在，前端无调用。**修复**：`api.ts` 补 `resolveAlertEvent`，事件表加操作列（仅 TRIGGERED 显示，权限同写操作）。

### P1-6 健康状态显示错乱 + 两个恒死统计

- Actuator 返回 `UP/DOWN`，前端只认 `HEALTHY/...` → 图标恒红叉、颜色恒黑；`uptime/services` 取自不存在的字段，恒 `-`/0。
- **修复**：`UP→HEALTHY` 等显式映射；version 改从 `/system/info` 取真实值；两个死统计换成页面上真实存在的「规则总数 / 未解决告警数」。

### P1-7 系统配置不能增删

- 后端 create/delete 齐全，页面只有编辑。**修复**：补「新增配置」弹窗（configKey 唯一约束说明、敏感值加密开关）、删除列操作（Popconfirm + 权限门禁）、关键字搜索（后端 page 已支持 keyword，此前 UI 无入口）。

### P1-8 系统部署页展示假数据

- 两条写死的部署记录、K8s 三卡片写死常量、Helm 信息写死；4 个高危按钮点击必 501。
- **修复**：假记录改空态 + 「后端未提供端点」说明；K8s/Helm 写死卡片移除（无真实数据源的数字不展示）；四个按钮置灰 + tooltip 说明「运维动作由 CI/CD 承担」——高危动作放行前必须让用户看见「不可用」，而不是用一次失败交互告诉他。

### P1-9 定时任务关键词仅前端过滤

- 翻页后搜索范围只剩当页。**修复**：keyword 下推后端（回车/搜索按钮触发，所有刷新调用点保持筛选条件）。

### P1-10 配置导出按钮无门禁但后端要求 `sys:config:write`

- 无权限用户点击必 403。**修复**：导出按钮包 `Auth(SYS_CONFIG_WRITE)`，前后端权限对齐。

### P1-11 `configService` 死契约（共享包）

- base 为 `/api/v1/system/configs`（复数，后端无此路由）、字段 key/value（后端是 configKey/configValue），且**无任何消费方**——「读平台配置」从未生效过。**修复**：对齐真实端点与字段（按 key 读走 `/config/key/{key}`，写走「存在则 PUT/不存在则 POST」），保留其「失败静默降级 defaultValue」的原设计语义。

### P2 健壮性与体验

- 字典搜索输入即请求（无防抖，快速输入打爆后端且旧响应可覆盖新结果）→ 300ms 防抖，类型/项搜索统一；
- `toggleItemStatus/markDefault/exportType/runSync`、定时任务删除等无 catch 的 promise → 统一错误提示；
- 规则/事件表无分页 → 加分页（后端 page 能力已具备）；
- 日志分析弹窗补范围说明（后端 analyze 为全量统计，不受筛选影响，明示防误导）。

## 5.2 第二轮：关键词跨列 OR 搜索闭环（2026-10-22，MySQL + 变异验证）

**起点**：§5.1 遗留的 handler 关键词缺口。排查中发现并收敛了**同型的 SQL 优先级缺陷**（存量两处）。

| 判据 | 方法 | 结果 |
|---|---|---|
| handler 维度关键词（缺口本体） | live：`keyword=liveHandlerProbe<ts>`（仅 handler 命中） | **命中**（修复前该场景 total=0；UI placeholder 承诺的两维搜索至此两维都真生效） |
| 优先级回归（名称侧） | live：`keyword=探针禁用乙<ts>&status=ENABLED`（名称命中的 DISABLED 任务） | **total=0**（flat OR 缺陷下会泄漏 1 行） |
| 优先级回归（handler 侧） | live：`keyword=liveHandlerProbe<ts>&status=DISABLED` | **total=0** |
| 数据在场对照 | live：同 keyword 无状态过滤 | total=1 含该行——证明上面的 0 是过滤生效而非数据缺失 |
| 测试判别力（变异验证） | 临时退回 QueryBuilder 扁平 `or()` 链（历史缺陷形态）重跑 | `scheduleStatusFilterMustNotBeBypassedByNameMatch` **精确转红**（`expected:<1> but was:<2>`），其余 7 例保持绿——证明该用例唯一针对「OR 组与等值过滤的优先级」性质 |
| 全量回归 | `mvn test`（bone-system） | **228 全绿**（38 类；新增 8 个关键词 OR 集成测试） |

**技术决策**：跨列 OR 用 `Criteria.or(Consumer)` 条件组（子条件括号包裹为原生片段，与外层 AND 安全组合为 `(a LIKE ? OR b LIKE ?) AND status = ?`），而非 QueryBuilder 扁平 `or()` 链——后者经 `SqlBuilder.buildWhereClause` 扁平拼接（`WHERE (a OR b AND c)`），SQL 优先级退化为 `a OR (b AND c)`。同型缺陷存量两处一并收敛：`SystemConfigRepository.pageByKeyword`（`configKey OR (description AND configType)`，异类型配置会漏过类型过滤）、`ScheduleTaskRepository.pageByKeywordAndStatus`。另修正三处 javadoc 的 stale 论断（原记载 `Criteria.or` 会被拼成 `(a OR b) = :null` 的 SDK 缺陷——经真实执行验证已不成立，Select/Count/Tenant 各 Builder 均已正确处理原生片段）。排序同步从「无 ORDER BY 自然序」改为 `createdAt` 倒序（自然序在 OR 查询下不保证跨页稳定）。
