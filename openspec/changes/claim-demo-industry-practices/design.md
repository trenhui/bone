## Context

`doc/ai-product/synapClaim/07-delivery/prototypes/claim-workbench/` 已有三份单文件 HTML 原型，基于 tpa-test 环境真实 schema 与真实赔案数据（demoId=900000000001）还原。前一轮对 `pk-tpa-saas/tpa-sass-vue3/src/views` 的 96 个页面做了全面分析，识别出三类经过真实系统验证、可直接迁移的复杂业务 UI 模式。本设计把这些模式落到原型，使 DEMO 从"字段还原稿"升级为"方案级原型"。详见 proposal.md - Why。

约束：原型必须是单文件 HTML（内联 CSS/JS）、零外部 CDN 依赖、light 主题、与 IDE 主题一致；不接后端；不修改 Vue 源码。

## Goals / Non-Goals

**Goals:**

- 建立一套四页共用的设计令牌体系（配色、间距、字号、状态语义色、卡片/表格组件样式），保证视觉语言一致。
- 把三类高价值复杂 UI 模式（配置矩阵、标准/专属继承、阶段化工作台）以静态可交互的方式呈现在原型中。
- 保留真实字段与真实赔案数据，确保原型可指导真实实现。
- 提供页面间的互跳链接，让四页形成一套完整系统观感。

**Non-Goals:**

- 不实现真实业务逻辑、不接 API、不引入前端框架或组件库。
- 不追求像素级复刻线上（线上是 schema 驱动的 PKRender 低代码渲染），原型目标是"设计升级"而非"还原"。
- 不改动任何生产代码或 spec 能力。

## Decisions

### 决策 1：四类复杂 UI 模式的选取与落地页

从前一轮 P0 分析中选取最能体现专业深度、且能用静态原型表达的模式：

| 模式 | 来源（真实实现） | 落地页 | 落地方式 |
|---|---|---|---|
| 三层矩阵表格（计划/险种/责任两级表头、`spanMethod` 合并单元格） | `policyRuleConfig/tabs/liabilityRule` | 新增的 `claim-rule-config.html` | 纯 HTML `rowspan/colspan` 静态还原合并表头，空位显示"添加险种/添加责任"引导 |
| 因子笛卡尔积矩阵（勾选条件生成矩阵行列、保留已填值） | `EditLiabilityDialog/section/AdjustmentDetail.vue` | `claim-rule-config.html` | 用 JS 监听勾选项动态生成矩阵表头与行，改动条件时保留已输入值（`mergeTableData` 语义） |
| 语法引导式公式编辑器（函数/字段双栏点击输入、括号校验） | `SetExpressionDialog/index.vue` | `claim-rule-config.html` | 只读表达式串 + 双栏点击追加 + 轻量括号/运算符校验提示 |
| 七节点阶段化作业链路（签收→初审→录入→质检→审核→复核→推送） | `TPAFlowConfig/config.ts` | `claim-manage.html` | 顶部阶段导航条 + 配置化 Tab（待处理/处理中/已超时） |
| 额度五列信息架构（初始/已用/剩余/冻结/可用） | `optionConfig` 额度页 | `claim-detail.html` 理算区 | 多列对照卡片，金额右对齐 |

**理由**：这些模式是真实系统里最复杂、最能体现"UI 表达能力上限"的部分，静态原型足以表达其信息架构与交互意图，且迁移价值最高。**备选**：完整还原所有 96 页——工作量大且多数是 schema 空壳，无设计价值，否决。

### 决策 2：统一设计令牌而非各自为政

四页共用同一组 CSS 变量（`:root` 定义）：主色/成功/警告/危险/信息语义色、字号阶梯、间距阶梯、圆角、阴影、状态标签样式。

**理由**：让用户看到"一套系统"而非"四张拼凑的稿子"。**备选**：每页独立配色——破坏一致性，否决。实现上采用"每页内联同一份令牌定义"（单文件约束下的必然选择），代价是令牌重复，可接受。

### 决策 3：渐进式披露治理信息密度

审核详情页 54 个字段不做无差别平铺，按语义分组（基础标识/保司投保方/影像清点/流转时效/保司单号），用可折叠卡片 + 左侧锚点导航组织；关键决策信息（赔付金额、待关注风险）前置到顶部摘要区。

**理由**：符合列表→详情→决策的审核动线，降低认知负荷。**备选**：全部展开单页滚动——原页面即如此，正是要改进的问题，否决。

### 决策 4：真实数据优先，空数据转化为风险提示

测试环境中该赔案的发票/理算/领款/主被保人为空。原型如实体现为"待补全/暂无"，并在审核结论区转化为"待关注"风险清单（必填校验项）。

**理由**：审核页最该突出的就是"缺什么、能不能结案"。**备选**：编造示例数据填满——会误导评审，否决。

## Risks / Trade-offs

- **[静态公式编辑器无真实计算]** → 明确标注为"交互示意"，只演示输入方式，不做真实表达式求值，避免给人已可用的错觉。
- **[设计令牌四页重复内联]** → 单文件零依赖约束下的必然代价；若未来要长期维护，可抽取公共 CSS，但当前 DEMO 场景可接受。
- **[矩阵"保留已填值"用简化版 JS]** → 演示语义即可，不追求与生产 `mergeTableData` 完全一致。
- **[新增理算规则配置页无真实 schema 依据字段]** → 字段项沿用前一轮分析的真实规则配置术语（责任、险种、医院等级、医保、金额区间、赔付比例），保证术语可信；不新增虚构业务概念。

## Migration Plan

无生产迁移。交付方式：六份 HTML 直接放入 `doc/ai-product/synapClaim/07-delivery/prototypes/claim-workbench/`，用浏览器打开即用；不做部署。
