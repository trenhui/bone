## Why

2026-11-10 对 `04-design/总体技术方案.md` 做了一轮「按读取点取证 + 业界最佳实践」独立诊断，发现既有 11 轮复核主要覆盖文档表达与判据可判定性，漏掉 3 个只有按读取侧取证才暴露的实质缺口：配置版本绑定只在写入侧成立（重算仍取当期 ACTIVE 责任）、里程碑 A 的验收判据依赖被 A 明确排除的后续步骤、资金主链路幂等不变量与 L3 契约不符；另有 5 项架构级可优化点。这些口径继续以「已落地 / 已成立」的语气写在设计真源里，会误导后续实施与验收。

## What Changes

- 把 §5.1「版本绑定已落地」更正为「写入侧已落地、读取侧未接线」，并在 §4.1.2 / §8.3 同步时态；补代码证据（读取点）与后果。
- 修正 §13.1 里程碑 A 的判据依赖倒置：超集表达（分段 / 区间 / 累计）归 B，A 的判据不得引用 B 的交付物。
- 把 §4.1 幂等的「契约 vs 实现差异」升级为实现违约登记，补 L3 契约与代码的逐条证据。
- §4.1.3 明确双轨比对的证据等级（等价性 ≠ 正确性），禁止 PR 说明把「双轨全绿」写成「金额已证明正确」。
- §11 补 R10 多副本调度单写者；§11.1 补 Q5 端到端可观测、Q6 灾备 / 依赖隔离 / 留存裁决，并给 Q4 的「声明 RTO」一个工程默认值。
- §1.3 把「不用规则引擎」的理由限定为金额算术，登记决策表外置为二期选型，消除与 §7 QLExpress4 的自相矛盾。
- 统一 §9.1.1 迁移编号口径（以 `migration-manifest.json` 下一可用 order 为唯一真源，删除三处互斥占位号）；把 §13 · O-05 ② 从「待触发」闭环为「已否决 / 不适用」；把 O-11 的 `engine_version` 触发条件从自指的「首个读取点」改绑外部可观测发版事件。
- 在《方案质量诊断报告》§14.1 交人清单登记 4 类代码 / 门禁整改项（L3 / L4，本轮不实施）。

**明确不做（非目标）**：不改 Java 代码、DTO、DDL、迁移脚本、CI 配置、生产开关；不新增业务文档（D2「文档总数保持 63」）；不修改 §12 待决策表（L4）；不把目标态写成现状，不填压测实测值冒充基线。
