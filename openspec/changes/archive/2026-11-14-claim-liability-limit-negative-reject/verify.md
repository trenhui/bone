> 验证「责任额度上限负数收紧 + 存量归一化」的落地情况。主证据为提交前的完整验证跑：

## 结论

**变更全部落地并通过验证。** 缺陷是真的（负数额度曾被静默放行 = 静默取消限额），
修复按「写入期拒绝 + 读取期兜底保留」双层防御实施，收紧**未做成过度收紧**（0 与不填仍合法），
存量经 0096 归一为 0 且**零行为变更**，回归由单测 + E2E 双向固化。

## 判读要点

- **V4 是本轮最有说服力的一条**：它不依赖"测试全绿"，而是**同环境同参数的两实例对照**，
  直接把"缺陷存在"与"修复有效"两件事同时钉死。
- **V3 的变异二是防过度收紧**：若守卫被后续维护改成 `<= 0`，两条正向钉子会立刻转红。
  没有它们，一次"顺手收紧"就能把「不封顶」的唯一合法表达堵死。
- **V7 的零行为变更**有硬依据：理算期判据是 `signum() <= 0` ⇒ 负数与 0 同义，
  归一化前后任何赔案赔付金额逐分不变。

## 遗留与后续（不在本次范围）

- `liabilityUncapped()` / `QuotaStack#liabilityLayer` 的 `<= 0` 判据**保留**（读取期兜底），
  其注释已澄清"契约语义是 0、负数仅兜底"。若未来要彻底消除负数，需先确保所有环境都已应用 0096，
  再把判据收紧为 `== 0` 并同步迁移守卫 —— 属独立变更。
- 引入独立 `uncapped` 布尔列（替代"用数值表达无限额"）是更彻底的建模方向，
  但属列结构变更（L3），需单独评审。
- 生产环境的数据变更属 L3，需由 DBA / CI 在目标库执行 0096。
