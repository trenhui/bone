# Proposal: claim-liability-limit-negative-reject

> **语义收紧型变更**：把责任额度上限的「负数 = 不封顶」隐式哨兵改为「负数非法、0 = 不封顶」，
> 并对存量做零行为变更的归一化（0096）。

## Why

责任额度上限（`liability_limit`）是理赔责任配置里唯一一个**负数被当作合法语义**的金额字段。
三处证据说明这是缺口而非设计：

1. **风险方向与同类字段相反**。免赔额 / 日限额为负会被引擎夹成 0 ⇒ 少扣钱；而责任额度上限为负
   在理算期被解释为「**不封顶**」（`LiabilityRule#liabilityUncapped`：`signum() <= 0`）⇒
   **赔得更多**。运营手滑把 `-100` 写进「责任额度上限」，该责任即刻变成无限额赔付，系统毫无提示，
   配置面还显示「已配置」。
2. **同域三个同类字段早已一致地拒绝负数**：计划额度（`ClaimPlan`）、险种额度（`ClaimCoverage`）、
   额度账户（`QuotaAccount`）在装配期即抛 `DomainException`。责任额度是唯一漏网的一个，
   属于域模型内部的一致性缺口，而非"各模块各自的口径"。
3. **reference-impl S25 的契约是「额度 0 表示不限制」**，负数从未被定义过
   （见 `AdjustmentDualTrackFixture` 场景 `S25-零额度不封顶`）。代码里「负数按不封顶解释」是
   Bone 的自行扩展，且注释自称"对齐 reference-impl S25"——属**过度声称**。

从工程惯例看，负数充当"无限制"哨兵是典型的 **magic value / 隐式哨兵反模式**：
它不承载任何额外信息（要"不封顶"写 0 或留空即可），却让一个手滑变成高风险静默错误，
并且让下游财务/报表口径分裂（同一字段在不同系统里一个当"无限"、一个当"非法"）。

## What Changes

- **写入期收紧**：`LiabilityConfigApplicationService#assertRuleUsable` 拒绝负数责任额度上限；
  `0` 与不填（null ⇒ 落库 0）仍然合法，语义是「不封顶」——**收紧不做成过度收紧**。
- **错误消息可操作**：负数时给出「负数会被按「不封顶」解释，等于取消限额；不封顶请填 0 或留空」，
  而非只说"不合法"。
- **存量归一化**：`0096_normalize_negative_liability_limit.sql` 把存量负数归一为 `0`。
  **零行为变更**——理算期 `signum() <= 0` 意味负数与 0 本就同义，赔付金额完全不变；
  同步 bump `version`，避免持旧版本的应用实例用陈旧对象覆盖修复结果。
- **读取期兜底保留**：`liabilityUncapped()` 的判据仍是 `<= 0`。这是**读取期容错**而非契约语义：
  负数若仍存在（迁移前存量 / 绕过应用层的直连写入），按「不封顶」处理比按「负限额」处理安全
  （后者会让所有赔案算出 0 赔付）。注释同步澄清这一区分，避免配置期口径与理算期注释打架。
- **回归防护**：单测（4 条，含 2 条防过度收紧的正向钉子）+ API 级 E2E（负数 4xx / 0 通过）。

## 影响面

| 面 | 变化 |
|----|------|
| 配置面 API | 建/编责任时 `liability_limit < 0` 由 200 变 4xx；`= 0` 与不填不变 |
| 理算期 | **无变化**（`<= 0` 判据保留，负数与 0 同义） |
| 存量数据 | 负数 → 0（0096）；负数与 0 的赔付结果完全一致 |
| 前端 | 已用 `InputNumber min={0}` 阻止负数输入，**无需改动**；后端守卫是必需的第二道防线（客户端校验不可信） |

## 不做什么（明确排除）

- **不改** `liabilityUncapped()` / `QuotaStack.liabilityLayer` 的判据：那是读取期兜底，改了会让
  迁移前存量从"不封顶"变成"算出 0 赔付"，是**风险放大**而非修复。
- **不改** `payPercent`：`assertPercent` 已覆盖 0~100（上一轮我曾把它误列为缺口，此处纠正）。
- **不抢做**他人在途的迁移/前端改造，避免 add/add 冲突。
