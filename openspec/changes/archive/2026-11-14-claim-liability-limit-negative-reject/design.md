# Design: claim-liability-limit-negative-reject

## 决策：写入期拒绝 + 读取期兜底保留（双层防御）

业界在"收紧一个被容忍了多年的非法值"时的标准做法是**双层防御**，不是单点替换：

| 层 | 职责 | 本次动作 |
|----|------|---------|
| 写入期（配置面） | 阻止新的非法数据进入 | **收紧**：负数 → 4xx，0/不填放行 |
| 读取期（理算） | 面对仍存在的历史非法数据，行为可预期且安全 | **保留** `<= 0` 判据（按「不封顶」兜底） |

**为什么读取期必须保留 `<= 0`**：若把判据改成 `== 0`，迁移前的存量负数会从"不封顶"变成
"额度为负 ⇒ 恒达不到 ⇒ 赔付 0"。那是**把一个静默多赔的风险，换成静默不赔的风险**——
赔案金额直接归零，且同样无提示。所以读取期要选"更保守的一侧"：宁可多赔（不封顶），
不可算不出钱。

**为什么写入期必须收紧**：只做读取期兜底 = 负数继续入库，继续静默无限额赔付，
运营永远不知道自己写错了什么。配置期是唯一能给出**即时、可行动**反馈的位置
（运营当场看到"不能为负，请填 0 或留空"）。

## 为什么 0 仍然合法（防过度收紧）

「不封顶」必须有唯一、明确的表达方式。收紧时若用 `signum() <= 0` 判负，
就把唯一的合法表达（0）也拒掉了 ⇒ 运营无法表达"不封顶"，只能乱填正数（更糟）
或填不出配置。这是**过度收紧**，比原缺陷更危险。

因此守卫用 `signum() < 0`（只拦负数），并配两条正向钉子：
- `0` 显式填写 ⇒ 通过；
- 不填（null ⇒ `toDecimal` → `ZERO`）⇒ 通过。

两条都在单测与 E2E 里固化，防止后续维护把守卫"顺手改成 `<= 0`"。

## 错误消息设计

原 `assertNonNegative` 的消息是 `label + "不能为负: " + value`。对责任额度上限而言，
这只说"不合法"，运营不知道**改成什么**。本次给守卫加可选的 `consequence` 参数：

```
责任额度上限不能为负: -100（负数会被按「不封顶」解释，等于取消限额；不封顶请填 0 或留空）
```

原则：错误消息要说清**后果**与**正确写法**，让运营一次改对，而不是猜。

## 存量归一化：为什么归 0 且零行为变更

理算期判据 `signum() <= 0` ⇒ 负数与 0 在**理算上完全同义**。把存量负数改成 0：

- 任何赔案的赔付金额**逐分不变**（唯一依据就是上面这个判据）；
- 只是把"不可见的歧义"变成"明确的 0"；
- 附带收益：编辑路径会把命令值与库里原值**合并**后求值，若库里留着负数，
  运营编辑该责任（哪怕只改别的字段）都会被守卫拦下 ⇒ 归一化同时解除了这个卡点。

**乐观锁**：同步 `version = version + 1`。任何仍持有旧 version 的应用实例在下次编辑时
必然触发乐观锁冲突并重读，不会用陈旧对象把修复结果覆盖回去。
（数据修复与乐观锁共存的标准做法：不 bump 会留下"缓存里的旧值覆盖新值"的窗口。）

**幂等**：可重复执行，第二次影响 0 行。

## 为什么不在前端补提示

前端已有 `InputNumber min={0}`（责任额度上限、免赔额、日限额三项均如此），
负数在 UI 上根本输不进去 ⇒ 前端**没有缺口**。而后端守卫是必需的：
API 可被脚本、集成方、迁移工具直接调用，**客户端校验不可信**。
这也正是业界共识：校验必须在服务端重复一遍，前端那层只算体验优化。

## 参考对照

| 做法 | 本次是否采纳 | 理由 |
|------|--------------|------|
| 写入期拒绝 + 读取期兜底 | ✅ | 双层防御，风险最小 |
| 直接把负数当"不封顶"继续支持 | ❌ | 隐式哨兵，手滑即静默高风险 |
| 用 `null` 表达"不封顶" | ❌ | 改列语义与全链路（模板/前端/回读）成本过高，且 0 已足够明确 |
| 引入独立的 `uncapped` 布尔列 | ❌ | 超出本次范围（列变更 = L3 结构变更），记为后续可选演进 |
| 前端加提示文案 | ❌（已足够） | `min={0}` 已阻止输入 |
