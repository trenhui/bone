## Context

动机见 [proposal.md](proposal.md) 的 Why，行为契约见 [specs/claim/case360-embedded-workflow/spec.md](specs/claim/case360-embedded-workflow/spec.md) 与 [specs/claim/workbench-navigation-groups/spec.md](specs/claim/workbench-navigation-groups/spec.md)。

当前形态：`Case360Page` 的八个 Tab 中，`overview` 自带概览与 AI 结论卡，其余七个是「深链桥」——点击后带着 `claimId` 跳到独立作业页。六个单案作业页共享同一套壳（`PageHeader` + 案件 ID 输入条 + 未选案件空态 + 从 query 读取 ID），彼此独立取数。`ReviewWorkbenchPage`（决策与 trace）是队列型工作台、不绑定单案，不是同一对象的视图。

硬约束：侧栏由 IAM `GET /api/v1/iam/menus/current` 下发，迁移 0078 的 SIGNAL 钉死 `/claim#/*` 统一读码；单导航探针在数据层断言「菜单叶子 ↔ `routes.tsx` 非 hidden 路由」双向全等，在浏览器层逐个点击 `.ant-menu-item`。因此任何菜单条目的增删都必须与 IAM 迁移、探针同批改。

## Goals / Non-Goals

**Goals:**
- 让一次单案作业在案件视图内完成，达到「进入案件 → 切换视图 → 完成动作」的路径，不再手输 ID。
- 让侧栏的一长列菜单获得常驻可见的语义分组，且不损失信息 scent。
- 让已有深链、既有菜单入口、受保护动作与 AI fail-closed 全部保持原语义。
- 让新增行为由可判别（变异验证有效）的回归探针钉住。

**Non-Goals:**
- 不减少或撤下任何菜单条目，不改 IAM 数据、权限码、SIGNAL、后端契约与数据库。
- 不把队列型工作台（核赔工作台 / 决策与 trace）内嵌成单案视图；该 Tab 保留既有深链桥。
- 不新增角色配置表、不做真人卡片分类与树测试、不引入新的前端框架或状态库。

## Decisions

### D1：拆「无壳内容组件 + 页面壳」，而不是整页嵌入或路由跳转

六个单案页的现有实现都自带页面标题、ID 输入条、空态和取数逻辑。若把整页组件直接塞进 Tab，会出现双标题与双 ID 源；若继续用跳转，作业人员仍要离开案件视图。做法是把每个页面的业务内容抽成接受 `claimId` 的内容组件，页面壳继续从 query 读 ID 后渲染同一内容组件，案件 360 的 Tab 也渲染同一内容组件。

- 备选 A（整页嵌入）：改动最小，但双壳冲突，否决。
- 备选 B（iframe / 微前端嵌套）：引入第二套运行时与样式隔离成本，且探针会判「微应用内自绘菜单」，否决。
- 备选 C（只做跳转加速）：无法消除手输 ID 与上下文断裂，否决。

收益：同一业务逻辑只有一个实现，旧路由与内嵌视图共享，避免项目已踩过的「同一功能两套界面必然漂移」。

### D2：Tab 状态继续放 URL query，沿用既有解析真源

沿用 `?claimId=&tab=` 契约与既有 `parseCaseLocation` / `normalizeTab` 作为唯一真源，不引入 path 参数或前端全局缓存。理由：隐式缓存不可分享、不可回退、跨标签页丢失；同一语义两处配置源是项目反复踩过的坑。深链可进通知与客服工单，浏览器前进后退天然可用。

### D3：侧栏分组用常驻分组标题，不用折叠 SubMenu

分组映射按 hash 常量集中维护，渲染为常驻可见的 Section 标题，子项默认展开且仍是可直接点击的菜单项；未知 hash 落「未分组」并保留可点性。理由：NN/g 隐藏导航实验显示隐藏后使用率从 48–50% 降到 27%、任务时间至少慢 39%；同时折叠 SubMenu 会让单导航探针「菜单项可见 + 逐个点击」的断言失效。该决策同时满足产品证据与工程门禁。

- 备选（折叠四空间）：会被探针判红且违反可用性证据，否决。
- 备选（直接改 IAM 菜单树加目录）：需迁移 + SIGNAL + 权限回归，且 0078 有 DEMO 角色事故前例，本 change 否决。

### D4：本 change 不撤菜单，撤菜单另立 change

「功能组合」发生在对象层（案件视图），导航层只加常驻分组。菜单条目数保持不变，不触碰 IAM 与探针的数据层全等断言。待内嵌作业成为主路径、真实使用率可观测后，再单独评估「撤下哪些菜单 + IAM 迁移 + 探针同批改」，避免一次性同时撞门禁、探针与权限三道。

### D5：探针与 UI 冒烟同批改，并做变异验证

单导航探针新增「四空间标题常驻可见 / 15 条菜单项全部可见可点 / 菜单顺序不变」断言；工作台 UI 冒烟新增「案件内切换 Tab 不再出现 ID 输入框 / 深链分享与回退 / 长 ID 无截断」断言。按项目既有经验，计数类断言使用精确值，并用变异验证证明缺陷写法下相关断言确实转红，避免「全绿但没判别力」。

## Risks / Trade-offs

- [六个页面拆内容组件时可能改变既有页面行为] → 旧路由页面壳保持同一组件与同一取数入口；逐页跑单测、类型检查、lint，并用单导航探针逐项点击验证 hash / 顶栏标题 / 页面标题。
- [并行会话在途文件可能被代提交或改写] → 本 change 只读写自己范围内的文件，按精确路径暂存；提交前核对最新提交内容，不覆盖、不回滚他人在途改动。
- [常驻分组标题在 qiankun/shell 样式下的选择器兼容] → 用真实浏览器验证菜单项可见性与点击链路，并做变异验证；不依赖静态 DOM 猜测。
- [内嵌后受保护动作被误做成批量] → 规格已明确逐案人工终审，UI 冒烟加负向断言；资金、FRAUD 挂起恢复、后督 DIFF 视图不提供批量入口。
- [决策与 trace Tab 仍是跳转] → 已在 Non-Goals 明示：它是队列型工作台而非单案视图，保留深链桥，不假装已内聚。

## Migration Plan

无数据库迁移、无后端发布。前端按「内容组件抽取 → 案件 360 内嵌 → 侧栏分组 → 探针/冒烟同批改」顺序落地，每步都可独立跑既有验证基线（契约联调 40/40、UI 冒烟 18/18、单测 119/119、文档门禁 19/19）。

回滚：恢复案件 360 的深链桥渲染并移除分组映射即可，旧路由与菜单数据自始至终未改动，因此回滚不影响深链与权限；已写入的 AI 回流事件为 append-only 审计数据，不随前端回滚删除。

### 已确认的取舍要点

1. 拆壳：每个单案页抽接受 `claimId` 的内容组件，页面壳与案件 360 Tab 共用同一实现；`overview` 保留概览与 AI 结论卡，`trace`（队列型工作台）保留深链桥。
2. URL 唯一真源：沿用 `?claimId=&tab=` 与既有解析函数，不引入 path 参数或隐式缓存。
3. 常驻分组：按 hash 常量映射四空间，标题常驻、子项默认展开且仍可直接点击；未知 hash 落「未分组」并保留可点性；菜单名 / 顺序 / permission / icon / hash 一字不改。
4. 本 change 不撤菜单：先把功能可达性从菜单移到对象页，撤菜单待真实使用率可观测后另立 change，与 IAM 迁移、探针同批改。
5. 回归有牙：探针与 UI 冒烟同批新增断言，计数用精确值，并做三种缺陷写法的互补变异验证；受保护动作维持逐案人工终审。

### Spec Patch 与测试策略

**无 Spec Patch**：本轮只做实现取舍与任务拆分，不修改两份 delta spec 的任何 requirement / scenario，行为需求以 OpenSpec 为准。

验证顺序：`tsc --noEmit` → 改动文件 eslint（零警告）→ claim-app 全量单测 → 契约级联调 → UI 冒烟 → 单导航探针（真实浏览器）→ 文档族门禁 → 变异验证对照记录；全部实际运行并保存退出码与关键输出。
