# 头脑风暴摘要：报案 / 赔案拆分

> 状态：候选与已确认混排时以「已确认」标注；本文只记录取舍过程，正式方案见 `design.md`（唯一 Design Doc），行为要求见 `specs/claim/report-case-modeling/spec.md`（唯一规格）。

## 1. 问题重述

现状 `report : case = 1:1`，报案号与赔案号是同一列。要升级为 1:0..N，必须先决定：报案到底是什么、谁持有编号、幂等键归谁、存量怎么回填。

## 2. 候选方案与取舍

### C1 实体边界

| 候选 | 做法 | 结论 |
|---|---|---|
| C1-a | 赔案表内嵌报案字段 | 否决：无法表达「报案未立案」，每加报案属性都要复制，回到「同一语义两处真源」 |
| C1-b | 独立报案聚合 + 赔案单向引用 `report_id` | **已确认**：报案不持有赔案子集合，避免级联改赔案状态 |
| C1-c | 报案为根、赔案为 `@Cascade` 子集合 | 否决：赔案有自己的状态机与生命周期，级联保存会把「报案保存」变成「赔案状态批量改写」 |

### C2 编号

| 候选 | 做法 | 结论 |
|---|---|---|
| C2-a | 报案号 = 赔案号前缀替换（无独立生成器） | 否决：追加第二笔赔案时无法给出稳定的报案号来源 |
| C2-b | 独立 `RP` 前缀 + 共用编解码内核 | **已确认**：校验位只覆盖日期+载荷，回填 `CL→RP` 天然合法 |
| C2-c | 纯随机 10~12 位 | 否决：生日悖论下 1.25e7 单即 50% 碰撞 |

### C3 幂等键归属

| 候选 | 做法 | 结论 |
|---|---|---|
| C3-a | 幂等键搬到报案 | 否决：需同步改 `ClaimCase.draft()` 14 处调用方与既有单测，收益仅形式对称 |
| C3-b | 保留在赔案，报案与首案同事务创建 | **已确认**：并发冲突时整事务回滚，不产生孤儿报案（须用「行数不变」断言钉死） |

### C4 报案状态

| 候选 | 做法 | 结论 |
|---|---|---|
| C4-a | 落「赔付中/已结案」等进度态 | 否决：与赔案状态形成两份互相矛盾的真源 |
| C4-b | 只落 `REPORTED` / `CLOSED`，进度派生 | **已确认**：状态只表达「可否追加」 |

### C5 追加赔案的保单维度

| 候选 | 做法 | 结论 |
|---|---|---|
| C5-a | 允许请求覆盖保单/计划/被保人 | 否决：等于允许把 A 保单的赔付挂到 B 事故上 |
| C5-b | 从报案继承；请求体不设该字段，出现即 400 | **已确认**：没有字段就没有覆盖的可能；仍显式拒绝以防调用方误以为覆盖成功 |

### C6 存量回填

| 候选 | 做法 | 结论 |
|---|---|---|
| C6-a | 迁移里实现 Feistel 生成报案号 | 否决：SQL 里重写密码学置换，与 Java 真源分叉 |
| C6-b | `report_no = CONCAT('RP', SUBSTRING(claim_no,3))` + 复用赔案 id | **已确认**：校验位对日期+载荷计算，前缀替换后仍合法；`report_id = id` 自映射，无需映射表 |

### C7 前端追加入口

| 候选 | 做法 | 结论 |
|---|---|---|
| C7-a | 详情页新建 Modal 表单 | 否决：报案表单 321 行含动态明细与校验，复制一份等于规则写两遍 |
| C7-b | 复用报案页 `?reportNo=` 追加模式 | **已确认**：保单维度只读，提交走 append 端点 |

## 3. 风险清单（已在 design.md 展开）

- 事务边界：报案与首案必须同事务，否则孤儿报案；
- 跨租户挂靠：DB 无复合外键，靠应用层 + 迁移终态断言；
- 发票唯一：不得因拆表放松 `uk_tenant_invoice`；
- 回填幂等：`INSERT ... WHERE NOT EXISTS` + 5 条终态断言；
- 前端文案：详情页原「报案号」实际是赔案号，须纠正标签，否则客服按赔案号当报案号检索。
