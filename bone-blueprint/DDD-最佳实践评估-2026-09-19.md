# bone-blueprint DDD 最佳实践评估

> 评估日期：2026-09-19 ｜ 对象：`bone-blueprint`（134 个 main 类 / 38 个测试类 / 181 个 `@Test`）
> 方法：静态审查为主。**本轮未重跑 `mvn` 门禁**——该模块的 `archunit_store/` 已入库，在脏主树跑模块测试会改写冻结基线（见项目既有纪律）。所有"门禁通过"的陈述均来自 `README.md` / `TEST_GUIDE.md` / 上一轮工作日志的实跑记录，已逐条标注来源。

## 一、结论

**综合判定：达到业界 DDD 最佳实践，属「良好偏优」。战术设计（聚合/事件/一致性）接近教科书级；主要差距在工程护栏与文档同步，不在领域建模。**

| 分层 | 评级 | 一句话依据 |
|---|:---:|---|
| 战术设计（聚合 / 不变量 / 领域事件） | **A** | 充血聚合 + 状态机内聚 + 守卫条件与意图揭示命名；`ship()/deliver()` 显式论证「为何不发事件」 |
| 战略设计（上下文 / ACL / 数据所有权） | **A-** | 上下文映射、通用语言表（含**禁用同义词**）、E-1.2 机器可读表所有权声明 |
| 一致性（最终一致 / Outbox / 幂等） | **A-** | 三件套齐备 + 远程写移出本地事务 + 全租户对账安全网 |
| 分层与边界（依赖方向） | **B+** | application→infrastructure 零违规；**但 adapter 层存在 2 处直连域写仓储**（见 P0-1） |
| 门禁严谨性 | **B** | 27 条 ArchTest、冻结基线全为 0（真绿）；**但存在规则覆盖盲区**（见 P0-1 / P2-1） |
| 可测试性 | **C+** | 181 个 `@Test` 全是单元测试；**无任何装配级 / 契约级测试**（模块自述） |
| 文档与实现一致性 | **B** | 治理体系罕见地完善；**但有 3 处已漂移的描述**（见 P1-1 / P0-1 / P2-6） |

**一句话**：这个模块的问题**不是"不懂 DDD"**，而是"做得对的部分没有被门禁完整覆盖，且部分注释/README 停留在改造前的语义"。

## 三、已经做对、且值得其他模块照抄的（8 项）

1. **「不发事件」也要给理由** —— `Order.ship()` / `Order.deliver()` / `Payment.close()` 的 javadoc 都写了"为何不发 DomainEvent"。绝大多数项目要么无脑发事件，要么发了不解释；这里把判据固化成可评审的文本。
2. **`Payment.confirmSuccess` 的幂等语义分级** —— 同流水号重复 → 静默返回 `false`；**异流水号** → 抛错（防篡改覆盖）。退款同理：同金额幂等跳过、异金额抛错。资金场景的幂等不该一律静默。
3. **`Criteria.eq` 失败关闭**（`OrderRepository.findByIdInTenant`）—— 注释写明 `Criteria.eq` 会**静默丢弃 null 条件**，租户缺失时条件整条消失即退化为跨租户读取。这是真实踩过的坑，被写成防线。
4. **`getItems()` 故意收紧为包级可见** —— 因为 SDK 重载不回填 `@Transient` 集合，`order.getItems()` 会返回空列表造成"看起来成功实际没做"的静默错误（注释记录"历史上有两个订阅器踩过"）。
5. **`OrderItemInventoryExecutor` 骨架收敛** —— 创建/支付两条链路的明细遍历规则（空明细留痕、单笔失败不中断、明细取自读侧投影）收敛到一份骨架，避免双链路各自演进漂移。
6. **日志区分「命中」与「实际完成」** —— `CancelExpiredOrderJob` 打印 `命中/成功/失败` 三个计数，理由是"只打命中数时，命中 10 笔全部失败与全部成功在日志上完全同形"。
7. **`OrderItemRepository` 拒绝用包位置绕门禁** —— 类注释明确写"CORE-06 现按被持久化的聚合根类型计数，`OrderItem` 是聚合内实体，天然合规，无需靠包位置规避"。**主动拒绝作弊**是罕见品质。
8. **`common/BlueprintErrors` 的「码 → HTTP 状态」唯一真源** —— Map + 静态块反射校验全部常量，漏登记即类加载失败；`httpStatusOf` 不兜底。

## 四、问题清单

### P0-1 ｜ `adapter/schedule` 直连 domain 写仓储，且已有 javadoc 与实现矛盾

**证据**

| 文件:行 | 事实 |
|---|---|
| `adapter/schedule/CancelExpiredOrderJob.java:34` | `private final OrderRepository orderRepository;` |
| `adapter/schedule/CancelExpiredOrderJob.java:50` | `orderRepository.findCreatedExpiredBeforeAllTenants(before)` |
| 同文件 `:19-20`（javadoc） | 「逐笔下发 `CancelOrderCommand`（**经应用服务执行，adapter 不直连 domain 仓储**）」 |
| `adapter/schedule/OrderPaymentInconsistencyJob.java:8,38` | 同样注入 `OrderRepository` |
| `bone-framework/.../BoneDddArchRules.java:301-310` | 规则 `adapterControllersMustNotDependOnDomainRepository` 的谓词是 `resideInAPackage("..adapter..controller..")` |

**为什么是问题**

三层叠加：

1. **分层破坏**：`adapter` 只应依赖 `application`。Job 直连域写仓储，意味着该路径绕开了应用层的编排职责（租户显式化、事件发布、`OptimisticLockingFailureException` 翻译）。
2. **文档说谎**：javadoc 明确声明"不直连 domain 仓储"，而实现直连了。这是**注释与代码的静默矛盾**——比没有注释更危险，因为读者会据此建立错误心智模型。
3. **门禁盲区**：规则谓词限定 `..adapter..controller..`，`adapter.schedule` **不在其中**，所以它永远绿。README 反复写"参考样板不 freeze，须 0 违规"，这会让人以为 adapter 层已被全覆盖——**实际只覆盖了 controller**。

**根因**：ADR-0030 把全租户扫描方法 `findCreatedExpiredBeforeAllTenants` 并入了 `OrderRepository`。定时任务需要它，而应用层没有暴露对应方法，于是 Job 只能直连仓储。**读侧合并进域仓储后，"谁能拿到它"的问题没有同步收口。**

**建议（三选一，按推荐度排序）**

- **A（推荐）**：给 `OrderApplicationService` 加一个语义化方法，例如
  `List<OrderHeadProjection> findExpiredCreatedOrders(Instant before)`（`@Transactional(readOnly=true)`、内部注入租户审计），Job 改为只注入 `OrderApplicationService`。同文件已注入 `orderApplicationService`，改造量很小。
- **B**：把规则谓词从 `..adapter..controller..` 放宽为 `..adapter..`，并把两处 Job 的越层显式登记进 README 的 E-2 表格（承认而非隐藏）。**注意**：这会让 blueprint 从"不 freeze 须 0 违规"变成有违规，需先确认门禁政策。
- **C（最小动作，不能单独做）**：仅修 javadoc 使其与实现一致。**但这只是让谎言变成实话，架构问题仍在**，不建议单独采用。

### P0-2 ｜ 域仓储同时携带写能力与读能力，并被 adapter 持有

**证据**

- `OrderRepository extends Repository<Order, Long>`（`domain/repository/OrderRepository.java:36`）——SDK 的 `Repository` 自身声明 `save/update/delete/findByCriteria/countBy/aggregate(...)`。
- 同一接口内又声明读方法 `findOrderWithItems`（`:65`）、`findOrderPage`（`:93`）、`findStatusById`（`:85`）、`findCreatedExpiredBeforeAllTenantsSql`（`:81`）。
- README（`:47`）自述："ADR-0030 将写侧与领域读模型合并进同一仓储，CQRS 边界在**仓储**层，不在 **class** 层。"
- 上文 P0-1 的两个 Job 拿到的就是这个"写 + 读"合体接口。

**为什么是问题**

CQRS 端口拆分的一个核心价值是**能力最小化**：读侧调用方拿到 `XxxQueryPort`，就**物理上无法**调用 `save/update/delete`。ADR-0030 把读方法并回域仓储后，这个护栏消失了——现在任何能拿到 `OrderRepository` 的调用方（包括 adapter）都同时握有写能力。`BoneDddArchRules` 里那条 `isReadSideRepositoryMethod`（`:780`）只能在**方法粒度**区分读写语义，管不了"谁能持有这个接口"。

**这不是说 ADR-0030 错了**（它的收益——减少一层无实质内容的端口转发——是真实的），而是说：**合并的代价需要在架构决策里显式记账**，否则日后有人给 `OrderRepository` 加写方法时，没有任何规则会提醒他"你刚刚把写能力交给了所有读侧调用方"。

**建议**

1. 在 ADR-0030「取舍」一节补一行代价登记：**"读侧能力最小化护栏消失，改由方法命名与评审承担"**。
2. 若希望恢复护栏，可采用**角色接口**：`OrderRepository extends OrderWriteOps, OrderReadOps`，应用层按需注入窄接口。

### P1-1 ｜ README 对 `PaymentQueryPort` 的描述已过期（职责漂移未登记）

**证据**

| 位置 | 原文 | 实际 |
|---|---|---|
| `README.md:65` | 「查询支付单：`PaymentQueryPort.findById`（读侧直查，CQRS 读模型）」 | **接口里没有 `findById`**。`PaymentQueryPort` 只有 `findPayableExpiredBeforeAllTenants` / `findSuccessCreatedBeforeAllTenants` 两个**全租户运维扫描**方法 |
| `README.md:228` | 「**支付生命周期闭环** … → **查询**（`PaymentQueryPort`）→ …」 | 支付单查询实际走 `PaymentApplicationService.getById` → `PaymentRepository` + `PaymentDetailAssembler` |

**为什么是问题**

这解释了一个表面矛盾："为什么订单读合并进域仓储，支付读还留一个 QueryPort？"——**因为 `PaymentQueryPort` 已经不是 CQRS 读模型端口了，它是运维扫描端口**。但它的名字（`QueryPort`）、包位置（`application/query/port`）和 README 描述都还停在旧语义上。

**建议**

- 改名为 `PaymentOpsScanPort`（或 `PaymentReconciliationPort`）并迁到 `application/port/out`（它本质是出站运维端口，不是查询端口）。
- 同步修 `README.md:65` 与 `:228`，并把规则一句话写进「新模块最小路径」：**本聚合读 → 域仓储；跨聚合/全租户扫描 → `*QueryPort`/运维端口**。
- 顺手修 `PaymentQueryPort.java:17` 的悬空 javadoc 链接（`{@link OrderRepository#findCreatedExpiredBeforeAllTenants}` 未 import `OrderRepository`，链接解析不到）。

### P1-2 ｜ 无装配级测试（模块自述，实锤）

**证据**

- `pom.xml`：`excludedGroups=integration` 默认排除；无 `spring-boot-starter-test` 之外的测试基建（无 Testcontainers / MockMvc 契约测试）。
- `src/test/java` 共 38 个测试类，**全部为单元测试**；唯一带 `@Tag("integration")` 的 `EventTenantContextIntegrationTest` 默认不执行。
- `README.md:300-303` 自述：「**本模块仍无装配级测试**…本轮实机验证抓到的 4 个缺陷中有 3 个（Bean 名与框架冲突导致起不来、统一异常处理器未注册导致错误全变 500、SDK 读路径缺 `Instant` 转换导致读库 500）**单测全绿也照样存在**」。

**为什么是问题**

这条是**整个评估里唯一"业界最佳实践明确要求、而实际缺失"的项**——不是偏差，是缺口。三个漏网缺陷的共同特征是**都处在"组件装配与容器协作"这一层**，而单元测试的隔离性恰恰使其天然看不见这一层。

对一个**参考实现**而言，这个缺口的杠杆特别大：抄它的人会用它的形态、但不会继承它未被测试覆盖的风险。

**建议**

优先补"最小但闭环"的三条，不必追覆盖率：

1. **上下文加载测试** —— `@SpringBootTest` + 断言 `ApplicationContext` 能起来（专治 Bean 名冲突、缺配置）。
2. **一条 HTTP 主链路契约测试** —— `MockMvc` 打 `POST /api/v1/orders`，断言 `201` + `Location` + 错误信封结构（专治异常处理器未注册、序列化差异）。
3. **一条持久化往返测试** —— 需要真库或 Testcontainers，验证 `Instant` / `BigDecimal` 的读写往返（专治 `InstantConverter` 那类"写得进读不出"）。

### P1-3 ｜ 同一模块两种事务风格

**证据**

| 类 | 事务方式 | 行号 |
|---|---|---|
| `OrderApplicationService` | 声明式 `@Transactional` / `@Transactional(readOnly = true)` | `:75, :119, :136, :155, :177, :185` |
| `PaymentApplicationService` | 编程式 `TransactionTemplate` | `:66` 注入，`:35` import `org.springframework.transaction.support.TransactionTemplate` |

**为什么是问题**

`PaymentApplicationService.initiate` 的两段式事务（Tx1 落 PENDING → 事务外调渠道 → Tx2 回填 payUrl）确实**必须**编程式，这个取舍本身正确且注释充分。问题在于：

- **同一模块两套风格**会让读者以为这是随意的；参考实现尤其不该留下"两种都对"的印象。
- **编程式事务边界无法被静态门禁检查**。`oneAggregatePerTransaction`（`BoneDddArchRules:694`）只扫 `..application.command.handler..` / `..application.service..` 的**直接方法调用**，而 `TransactionTemplate.execute(...)` 内部的 lambda 是**另一次方法调用**，规则的 `getMethodCallsFromSelf()` 不追 lambda 体——**编程式事务成了门禁死角**。

**建议**

保留 `TransactionTemplate`（技术必要），但在类 javadoc 顶部**显式声明这是本模块唯一允许的编程式事务点及理由**，并加一条说明：「其余写路径一律声明式；编程式事务因 lambda 体内调用不被 `oneAggregatePerTransaction` 覆盖，新增时必须人工复核聚合数量」。把"例外"变成"登记过的例外"。

### P1-4 ｜ 领域事件处理器被迫依赖读侧投影才能拿到聚合内实体

**证据**

- `OrderCreatedEventHandler.java:29` / `OrderPaidEventHandler.java:29`：注入 `OrderRepository`，经 `OrderItemInventoryExecutor.forEachItem(orderRepository, tenantId, orderId, ...)` 取明细。
- `Order.java:34`：`@Transient private List<OrderItem> items`；`:120` `getItems()` 包级可见。
- 结论链：SDK 无级联落库 → `items` 必须 `@Transient` → 重载聚合不回填 → **订阅器无法从聚合拿明细** → 只能走读侧投影。

**为什么是问题**

这是 SDK 能力缺失（P1/CORE-11）**向事件层扩散的第二跳**。本来"聚合内实体"是领域概念，订阅器理应能通过聚合获得；现在它必须绕道**读模型**。这在 DDD 上是被迫的架构妥协：

- 事件的订阅方在**命令语境**（要执行 `reserveStock`）里用**查询模型**取数——CQRS 的读写分离在这里被反转了。
- 如果日后有人"修正"这个形态、把 `items` 改回可回填，`OrderItemInventoryExecutor` 的骨架会静默失效。

**建议**

不必改代码（SDK 不支持就别硬改）。但要在 **ADR-0030 或 SDK 技术债登记处补一行**：**"聚合内实体在事件订阅侧不可达，订阅器必须经读侧投影取明细。此为 SDK 无级联的已知扩散后果，收敛随 CORE-11。"** 让这成为登记事实，而不是被后人误读为设计失误。

### P1-5 ｜ 库存预留失败仅告警，无持久化补偿通道

**证据**

- `OrderCreatedEventHandler.java:24-27` javadoc：「单个商品预留失败不中断其余商品…但必须**留痕**——生产应落「预留失败待处理」记录或触发告警，否则库存与订单会静默不一致。」
- 实现：`OrderItemInventoryExecutor.forEachItem(...)`，**无本地写入、无 `@Transactional`**、失败路径只有日志。

**为什么是问题**

**对账链路不对称**：`OrderPaymentInconsistencyJob` 在检出"钱货不一致"时会**同事务落 Outbox**（使偏差可持久观测、可接告警/工单），而库存预留失败这条链路**只有日志**。同样是"最终一致链条上的断点"，一条有持久化安全网，一条没有。

README 已把"失败补偿对账"列为生产要求，属于**已登记的缺口**；但既然同模块已经示范了"落 Outbox 让异常可观测"这个更好的做法，两条链路不一致就显得可惜。

**建议**

把 `OrderItemInventoryExecutor` 的失败分支改为**落 Outbox**（复用 `OrderOutboxPort`），与 `OrderPaymentInconsistencyJob` 共用告警链路。改造点集中在一个骨架类，成本低、示范价值高。

## 五、根因分析

把所有问题归因，只有四条根因：

1. **SDK 能力缺失的二次扩散。** CORE-11（无聚合级联落库）→ `items` 必须 `@Transient` → 聚合内实体在事件侧不可达（P1-4）→ 明细需独立仓储（P1-4 / 已登记）→ 强类型 ID 无法转换（E-7.1 / 已登记）。**一个 SDK 缺口沿着"聚合内实体"这条线扩散出了四处妥协**，其中两处已登记、一处（P1-4）未登记。
2. **门禁规则的包谓词比架构意图窄。** 架构意图是"adapter 不得依赖 domain 仓储"，规则写的是"`..adapter..controller..` 不得依赖"。**意图与谓词之间的缺口就是 blind spot**（P0-1）。同类风险：任何以 `..controller..` 为后缀的规则都漏掉 `adapter.schedule` / `adapter.messaging`。
3. **改造后语义漂移，但注释/README 未同步。** ADR-0030 是一次大改（删端口、合并仓储、应用层直注域仓储）。改完后：`CancelExpiredOrderJob` 的 javadoc（P0-1）、`PaymentQueryPort` 的职责与 README 描述（P1-1）、`OrderPaidEventHandler` 的类注释（P2-6）**三处都停在改造前**。这不是疏忽，是**大重构缺少"注释复核"这道收尾工序**。
4. **门禁覆盖了"能静态判定"的，漏掉了"要装配才暴露"的。** 27 条 ArchTest 覆盖的是字节码可见的关系；而 Bean 名冲突、异常处理器注册、类型转换器缺失都只在**运行时装配**暴露（P1-2）。这是 ArchUnit 类工具的结构性边界。

### 8.1 结论修正：P0-1 的「分层破坏」判断不完整（重要）

**原判断（§四）**：`CancelExpiredOrderJob` 直连 `OrderRepository` 是三层叠加问题——分层破坏 + 文档说谎 + 门禁盲区。

**修正**：动手前做可行性核对时，发现两条被遗漏的事实，第 1 层（分层破坏）需要收窄：

| 被遗漏的证据 | 位置 | 含义 |
|---|---|---|
| 目标形态注释写「**定时 Job：全租户，已登记授权**」 | ADR-0030 §2（`@TenantScope(ALL)` 上方注释） | ADR **明确预期**由定时 Job 调用该仓储方法 |
| 门禁 `all_tenants_scan_only_by_schedule` 的豁免名单含 `..adapter.schedule..` | `bone-blueprint/src/test/.../ArchitectureTest.java` | blueprint **主动豁免**了 schedule 包调用全租户方法，并注明「全租户方法是平台运维入口」 |

**推论**：`CancelExpiredOrderJob` 直连域仓储是 ADR-0030 **有意的受控旁路**，不是无意的疏漏。原报告推荐的「方案 A（Job 改注入应用服务）」会让调用点落到 `OrderApplicationService`——**不在该门禁豁免名单内**，会**弄红一条既有安全门禁**（E-2 防护范围从「只有 schedule」扩到「application 也可」）。故方案 A 不可取。

**实际采用的修法**（原 A/B/C 之外的第三条路）：
1. 保留直连（符合 ADR 意图），但把**说谎的 javadoc 换成实话**——明确写出"本类为何直连域仓储（本模块唯一的受控例外）"，并指向 ADR-0030 授权与两道门禁。
2. **补上门禁盲区**：共享规则 `adapterControllersMustNotDependOnDomainRepository` 的谓词是 `..adapter..controller..`，故 `adapter.schedule / messaging / rpc` 全部逃逸。在 blueprint 的 `ArchitectureTest` 新增**本模块专用**规则 `adapter_no_domain_repository_all_packages`（谓词 `..adapter..`），**仅豁免 `CancelExpiredOrderJob` 一个类**（豁免写成完整类名，便于评审看到边界）。**不动共享的 `BoneDddArchRules`**，避免影响其他模块。
3. ADR-0030 新增 §11 登记该受控形态。

### 8.5 本轮新增的三条可复用认知

1. **「注释与实现矛盾」要双向排查**：既可能是代码错了，也可能是**注释停在改造前**。本例两者都有——`CancelExpiredOrderJob` 是注释错（实现有 ADR 授权），`OrderPaidEventHandler` 是注释描述了不存在的行为。**只朝"改代码"一个方向修，会把有意的设计改坏**。
2. **谓词窄于意图是 ArchUnit 类门禁的系统性风险**：`..adapter..controller..` 这类后缀谓词会静默漏掉同层的其他子包。**凡以 `..X..Y..` 结尾的谓词，都应核对"架构意图是否只有那一个子包"**。
3. **改架构前先查「既有门禁是否已就这个问题表过态」**：本例的 `all_tenants_scan_only_by_schedule` 直接改变了 P0-1 的最优解。忽略它，就会把"有意的旁路"当成"无意的疏漏"去修，进而弄红门禁——**比不修更糟**。
