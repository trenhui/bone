## SDK 租户缺口根治（方案 ②，2026-09-25 落地）

- 决议：选「把 `tenant_id` 从 UPDATE 的 SET 子句剔除」而非「insert 后回写实体」。理由：双来源(insert 取可信上下文/update 取实体字段)才是根因；剔除让 tenant 成为"仅 INSERT 写入一次"的归属列，与 ADR-0029 一致，且物理关闭"实体字段被填错值→UPDATE 改写行归属→跨租户破坏"向量。A 方案只是补丁且留该向量。

  2. **应用关系**：`meta_entity.module_id → bone_module → bone_application`，但只是**展示用的一棵树**——不是权限边界（`bone_app_permission.role` 在 metadata 侧 0 消费）、不是过滤条件（`MetaEntityPageQuery` 只有 pageNum/pageSize/keyword/status，**无 moduleId/appId**）、不是部署单元（publish 是单实体动作）、不是影响面（无消费登记）。
  3. **谁能用**：`iam_permission` 只有 `metadata:read/write/publish` 三条且 resource_path='*' ⇒ 建模/发布/运营改数据三件事混成一人。
  4. **定位**：建模元模型控制面（model-time），**不是 Data Catalog**（Atlan/DataHub 那类）；与主键据靠 ADR-0017 convert 单向衔接。
- ⚠ **自查纠错（重要方法论）**：初稿断言「A 租户可把实体挂到 B 租户模块下＝跨租户越权写」——回源后**证伪**：SDK 读侧 `SelectBuilder` → `TenantFilterInjector.inject`（ADR-0029）自动注入 tenant 过滤，`findById` 是租户 scoped 的，跨租户引用会被挡（返回 null → 「所属模块不存在」）。已改写为准确缺口：**租户一致性只是隐式兜住、无显式断言**（有人 disableTenantFilter 或改 Feign 即失效）+ **同租户跨应用越权**（应用角色未消费）才是真 P0。教训：写安全类结论前先读 SDK 过滤器实现，别只看 validator 代码。
- 其他实证证据：`meta_data_lineage`/`meta_data_standard`（bone-init.sql:1614/1630）**bone-engine 全仓 0 引用，实现却在 bone-masterdata 的 LineageController/DataStandardController** ⇒ 归口冲突（G6，须架构师裁定）；`align()` 不生成 FOREIGN KEY ⇒ 关系仅语义无物理约束（G7）；前端菜单按对象类型排非按场景排（App.tsx:287-295，G10）。
